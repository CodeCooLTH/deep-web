# 🧪 PROTOTYPE — ชีตคืนของ (throwaway)

> **คำถามที่ prototype นี้ตอบ:** ชีตคืนของควรหน้าตายังไงถึงจะใช้ง่าย
> user: *"ตอนนี้ใช้ยาก ถ้ากดปุ่มคืนของแล้วให้เลือกเป็น radio โอเลยดีกว่า จะได้ง่ายๆ"*
>
> **แผน:** 3 variants สลับด้วย `?variant=A|B|C` บนหน้า `/orders/[token]` เดิม
> (ชีตเปิดจากเมนู `⋮` เหมือนของจริง — ไม่สร้าง route ใหม่)

## รันยังไง

```
npm run dev          # ที่ seller.deepth.local:4000
```
เปิดออเดอร์ที่ **ของถึงมือลูกค้าแล้ว** → `⋮` → คืนของ → ใช้แถบล่างสลับ variant (หรือปุ่ม ←/→)

## ปัญหาของของเดิม (วัดจากโค้ดจริง)

- **7 คอนโทรลในฟอร์มเดียว** — number × N รายการ + select 2 + input 2 + checkbox 1 + input เหตุผล
- select 2 ตัว (`ใครออกค่าส่ง` × `เลขพัสดุขากลับ`) **ขึ้นต่อกัน** และมีคู่ที่เป็นไปไม่ได้
  (ลูกค้าออกเอง + ให้ระบบออกเลข iShip) ⇒ ต้องมีโค้ดสลับให้อัตโนมัติ = ผู้ใช้เห็นตัวเลือก
  เปลี่ยนเองโดยไม่ได้สั่ง ซึ่งอ่านเป็นบั๊ก
- ผู้ใช้ต้อง **แปลจาก "สถานการณ์จริง" เป็น 2 มิติ** เอง ทั้งที่ในหัวเขามีแค่ 4 เรื่อง

## แกนที่ทั้ง 3 variants แชร์กัน

ยุบ 2 select → **radio เดียว 4 ตัวเลือกที่เป็นภาษาคน** ⇒ คู่ที่เป็นไปไม่ได้หายไปจากโครงสร้าง
ไม่ต้องมีโค้ดสลับอัตโนมัติอีกเลย

| ตัวเลือก | = payer | = trackingSource |
|---|---|---|
| ร้านออกค่าส่ง · ให้ระบบออกเลขให้ | SHOP | ISHIP |
| ร้านออกค่าส่ง · ใช้ขนส่งเจ้าอื่น | SHOP | MANUAL |
| ลูกค้าออกค่าส่ง · ส่งเลขมาให้ | BUYER | MANUAL |
| ลูกค้าออกค่าส่ง · ไม่มีเลขพัสดุ | BUYER | NONE |

## ต่างกันตรงไหน (โครงสร้าง ไม่ใช่สี)

| | ลำดับ | รูปแบบหลัก |
|---|---|---|
| **A** | วิธีคืน → ของ | wizard 2 ขั้น · radio เป็นการ์ดใหญ่ |
| **B** | ทุกอย่างจอเดียว | radio เป็นแถวลิสต์ + รายการของอยู่บน |
| **C** | ของ → วิธีคืน | เลือกของด้วย checkbox+stepper เต็มจอ แถบสรุปยอดติดล่าง |

## 🛑 throwaway

- ไม่ยิง API จริง — `onSubmit` เป็น stub ที่โชว์ payload ที่จะส่ง
- ไม่มีเทส ไม่มี error handling
- แถบสลับซ่อนอัตโนมัติใน production build
- **ชนะแล้วต้องเขียนใหม่ให้ถูกมาตรฐาน** ไม่ promote โค้ดนี้ตรง ๆ แล้วลบทั้งโฟลเดอร์
