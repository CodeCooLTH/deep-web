## Goal

ทำให้คำถามลูกค้าที่ DeepBot ตอบไม่ได้ **กลายเป็นคำตอบที่ใช้ซ้ำได้ โดยไม่ต้องมี AI** — เพิ่มวิธีจับคู่ทางที่สอง (คลังคำถาม-คำตอบผูกกับกลุ่มคำ) ที่ทำงานหลังจากคำตรงตัวไม่เข้า พร้อมหน้าจัดการคลังและคิว "คำถามที่ตอบไม่ได้" ที่แปลงกองบันทึกที่มีอยู่แล้วให้เป็นงานที่ทำทีละข้อได้

### ทำไมงานนี้ก่อน AI Enhance — ตัวเลขจริงจาก prod (query 2026-07-31)

`AutoReplyLog.skipReason = 'NO_KEYWORD_MATCH'` = **401 แถว** (ตอนเขียน memory คือ 317 — โตขึ้น 84 แถวใน ~1 วัน) กระจายใน 2 ร้าน (243 / 158)

ข้อความซ้ำสูงสุด 4 อันดับแรกเป็น **ice-breaker / quick reply ของโฆษณา Meta** ซึ่งเป็นสตริงเดียวกันเป๊ะทุกครั้ง:

| ข้อความ (normalized) | ครั้ง |
|---|---|
| `สอบถามรายละเอียด` | 68 |
| `สนใจทำไฟหน้า` | 38 |
| `สอบถามโปรโมชั่น` | 36 |
| `ราคาโช้คหลังเวฟเท่าไหร่` | 28 |
| **รวม 4 ข้อ** | **170 / 401 = 42%** |

⇒ **การจับคู่แบบตรงตัวล้วน ๆ (ไม่มี AI ไม่มีความคล้าย) ปิดคิวได้ 42% ทันทีด้วยการกรอกคำตอบ 4 ข้อ** — นี่คือหลักฐานที่ทำให้งานนี้คุ้มก่อนงาน AI ทุกชิ้น

การกระจายความยาว (ตัวอักษรหลัง normalize): `0-3` 18 · `4-6` 25 · `7-12` 86 · `13-25` 198 · `26+` 74

### 🛑 สิ่งที่เจอตอน query แล้วต้องออกแบบรับ (ไม่มีในเอกสารเดิม)

คิวไม่ได้มีแต่คำถาม — มี **PII เต็มรูปแบบปนอยู่จริง** เพราะลูกค้าพิมพ์ที่อยู่จัดส่งเข้ามาแล้วไม่ตรงกลุ่มคำ ตัวอย่างจริงจาก DB (ตัดทอน):

- `สมประสงค์ ฉอยทิม 105 ม1 ตลุ่มสุ่ม อไทรโยค จกาญจนบุรี 71150`
- `... 59 หมู่ 6 ตำบลศาลายา อำเภอพุทธมณฑล จังหวัดนครปฐม 73170 ...` (171 ตัวอักษร)
- `0852995863`

และมีข้อความ "รับคำ" ที่ไม่ใช่คำถามเลย: `ครับ` (7) · `คับ` · `รับ` · `110` · `สนใจ` · `เลส` · `ปลายทาง`

⇒ ถ้าไม่กรอง คิวจะมีทั้ง **ขยะ** และ **ข้อมูลส่วนบุคคลของลูกค้าที่ถูกคัดลอกไปอยู่ในตารางใหม่** ซึ่งแย่กว่าการอยู่ในบันทึกแชทเฉย ๆ (ดู D5)

## Non-goals

1. **ไม่แตะ AI ใด ๆ** — ไม่เรียกโมเดล ไม่ผูกโควตา ไม่แตะ `ai-suggest-quota.service.ts` ไม่มีค่าใช้จ่ายต่อข้อความ (นี่คือคุณสมบัติหลักของ phase นี้ ไม่ใช่ข้อจำกัด)
2. **ไม่แตะ `KeywordEditorClient.tsx`** และไฟล์ใน `settings/auto-reply/[id]/**` เด็ดขาด — งาน v3 (S-18/S-20/S-21/S-22) ยังไม่ปิดและถือไฟล์เหล่านี้อยู่ (memory `feedback_parallel_dev_agents_no_commit`). การ์ด/ลิงก์ที่ควรอยู่ในหน้าแก้ไขกลุ่มคำตาม mockup §06 → **เลื่อนไป phase หลัง v3 ปิด** (ดู OOS-1)
3. ไม่ทำ pgvector / embedding / semantic search (decisions §4 — "เมื่อคลังโตเกิน ~200 ข้อ/กลุ่ม")
4. ไม่เพิ่ม/แก้ AI Enhance รายกลุ่มคำ (น้ำเสียง/กฎห้ามตอบ/ขอบเขตสินค้า) — mockup §01-§04 ทั้งหมดอยู่นอก phase นี้
5. ไม่ทำหน้าตั้งค่าตารางเวลา (ค้างข้อ 3 ใน memory) และไม่ทำแถบรับช่วงต่อในเธรด (ค้างข้อ 4)
6. ไม่เปลี่ยนพฤติกรรม gate ที่มีอยู่ 0–7 — QnA เสียบเป็นชั้นใหม่ **หลัง** การจับคำตรงตัวล้มเหลวเท่านั้น
7. ไม่แตะ `normalizeMessage()` — แตะเมื่อไหร่ `normalizedPhrase` ของทุกร้าน stale ทันที (คำเตือนหัวไฟล์ `auto-reply-normalize.ts`)

## การตัดสินใจเชิงออกแบบที่ผมทำเอง (user ล้มได้ทุกข้อ)

**D1 · QnA ทำงานเมื่อ "ไม่มีกลุ่มคำใดตรง" เท่านั้น**
ตรงกับ decisions §3 "คำตรงตัวชนะก่อนเสมอ" · **ไม่** ทำงานตอน `NO_RULE_MATCH` (กลุ่มคำตรงแต่ไม่มีกฎ = ตั้งค่าพลาด ควรให้ร้านเห็นว่าพลาด ไม่ใช่ให้คลังมากลบร่องรอย)

**D2 · QnA ที่ชนะ "ยืมกลุ่มคำเป็นเจ้าของ"**
`AutoReplyQna.keywordId` ที่ชนะถูกใส่กลับเป็น `winner.keywordId` → ผ่าน gate 6.5 (สถานะ LIVE/TEST), 6.6 (เวลาทำงาน), 7 (cooldown) **เหมือนกลุ่มคำปกติทุกประการ** แต่ข้อความที่ส่งมาจาก `AutoReplyQna.answer` โดยตรง **ไม่ผ่าน `resolveRule`**
เหตุผล: decisions §3 บอกว่าคลังต้องถูกคุมด้วยกติกาเดียวกับกลุ่ม — ถ้าไม่ยืมเจ้าของ คลังจะเป็นช่องทางที่ข้ามสถานะ/ตารางเวลา/cooldown ได้ทั้งหมด ซึ่งคือรูรั่วเดียวกับ "สวิตช์คนละที่" ที่รื้อทิ้งไปแล้ว
ผลข้างเคียงที่ยอมรับ: กลุ่ม `OFFLINE` ไม่ถูกโหลดเข้า ruleSet ⇒ QnA ของกลุ่ม OFFLINE ไม่ตอบใคร (ถูกต้องตามเจตนา)

**D3 · matcher ต้องยังบริสุทธิ์ (pure) และ `/simulate` ต้องเห็นผลเดียวกัน**
QnA set โหลดพร้อม ruleSet ใน `loadRuleSet()` และใช้ cache ตัวเดียวกัน (`auto-reply-cache`) · ฟังก์ชันจับคู่รับทุกอย่างเป็น argument ไม่มี I/O ไม่มี `new Date()` — บังคับโดยเทสเหมือน `auto-reply-match.service.ts`
เหตุผล: AC-020-05 บังคับว่าหน้าทดสอบต้องได้ผลตรงกับเส้นทางจริง ถ้า QnA เดินคนละทางจะเกิด "ทดสอบผ่านแต่ของจริงเงียบ" ทันที

**D4 · คิวเป็น "ตารางจริง" ไม่ใช่ `groupBy` บน `AutoReplyLog` ตอนเปิดหน้า**
เขียน upsert เข้า `AutoReplyUnansweredQuestion` ตอนเกิด `NO_KEYWORD_MATCH` (นับ `hitCount`, อัปเดต `lastSeenAt`) + สคริปต์ backfill 401 แถวเดิมครั้งเดียว
เหตุผล: `AutoReplyLog` โตไม่หยุดและไม่มี index บน `normalizedText` · คิวต้องมีสถานะ (`ข้าม`) ซึ่งเก็บใน log ไม่ได้ · การเขียนอยู่ใน `try/catch` แบบเดียวกับ `writeLog` — คิวพังต้องไม่ทำให้บอทพัง

**D5 · กรอง PII ออก "ตอนเขียน" ไม่ใช่ตอนแสดง**
ข้อความที่เข้าเงื่อนไขใดเงื่อนไขหนึ่งจะ **ไม่ถูกบันทึกเข้าคิวเลย**: มีเลขติดกัน ≥ 9 ตัว · มีคำบ่งชี้ที่อยู่ (`ตำบล|อำเภอ|จังหวัด|หมู่|ต\.|อ\.|จ\.` + เลขไปรษณีย์ 5 หลัก) · ยาวเกิน 80 ตัวอักษรหลัง normalize
เหตุผล: memory `feedback_rsc_pii_neutralize_at_source` — ที่อยู่/เบอร์ลูกค้าไม่ควรถูก **คัดลอก** ไปอยู่ตารางใหม่ที่มีปุ่ม "ส่งออกเป็นไฟล์" อยู่ข้าง ๆ · และข้อความพวกนี้ไม่ใช่คำถามอยู่แล้ว (จากข้อมูลจริง 100%)
ยังอยู่ใน `AutoReplyLog` ตามเดิม — ไม่ได้ลบอะไร แค่ไม่ทำสำเนาเพิ่ม

**D6 · หน้าใหม่แยกไฟล์เด็ดขาด** — `src/app/(paces)/seller/(dashboard)/settings/auto-reply/qna/**` (โฟลเดอร์ใหม่ ไม่มีไฟล์เดิม) ไม่มี S-id ใดใน phase นี้แตะ `[id]/**`

## ✅ เคาะแล้ว (user 2026-07-31 — เป็นส่วนหนึ่งของ baseline ห้ามตีความใหม่)

**A1 · จับคู่ = "ตรงตัวก่อน ความคล้ายเปิดทีหลัง"**
v1 จับคู่ **ตรงตัว 100% หลัง `normalizeMessage()` เท่านั้น** — ปิดคิวได้ 42% โดยตอบผิดไม่ได้เลย
ความคล้าย (trigram Dice ในหน่วยความจำ) **ออกแบบทางไว้แต่ยังไม่เปิด**: `matchQna()` รับพารามิเตอร์ `mode` ตั้งแต่แรก และ migration S-01 ใส่คอลัมน์ `AutoReplyKeyword.qnaSimilarityEnabled BOOLEAN NOT NULL DEFAULT false` ไปพร้อมกันเลย
เหตุผลที่ใส่คอลัมน์ตอนนี้ทั้งที่ยังไม่มีโค้ดอ่าน: dev DB = prod DB — การกลับไป `ALTER TABLE` รอบสองมีค่ามากกว่าคอลัมน์ที่นอนเฉย ๆ 1 คอลัมน์ · **ต้องมีคอมเมนต์กำกับใน schema ว่ายังไม่มีที่อ่าน** ไม่งั้นรอบหน้าจะเดาว่าเปิดใช้ได้แล้ว

**A2 · หน้าจัดการเป็น "รายกลุ่ม" ตาม mockup §07 เป๊ะ**
⇒ เส้นทาง (mapping ที่ตามมาโดยตรง — ไม่ใช่การตีความใหม่):

| หน้า | route | ที่มา |
|---|---|---|
| คลังคำถามของกลุ่มหนึ่ง | `/settings/auto-reply/[id]/qna` | mockup §07 (พาดหัว "คลังข้อมูลของกลุ่ม X") |
| คิวคำถามที่ตอบไม่ได้ | `/settings/auto-reply/unanswered` | mockup §05 — **ระดับร้าน ไม่ใช่รายกลุ่ม** เพราะคำถามที่ยังตอบไม่ได้ยังไม่มีกลุ่ม (กลุ่มถูกเลือกตอนกรอกคำตอบ ตาม mockup §05 มือถือ) |

`[id]/qna/**` เป็น **โฟลเดอร์ใหม่** ใต้ `[id]/` — ไม่มีไฟล์เดิม ไม่ชนกับ v3 ที่ถือ `[id]/KeywordEditorClient.tsx` (ยืนยันด้วย Acceptance ข้อ 7)
"ย้ายไปกลุ่มอื่น" ทำในหน้าเดิมผ่าน modal เลือกกลุ่มปลายทาง (ไม่ต้องเห็นข้ามกลุ่ม)

**A3 · ไฟล์นำเข้า/ส่งออก = CSV UTF-8 พร้อม BOM**
คอลัมน์: `คำถาม, คำตอบ, เปิดใช้งาน` (กลุ่มปลายทางเลือกจาก UI ไม่ใช่จากไฟล์ — เพราะหน้าเป็นรายกลุ่มอยู่แล้ว)
ไม่เพิ่ม dependency ใหม่ · BOM เพื่อให้ Excel ไทยเปิดแล้วไม่เป็นภาษาต่างดาว

**A5 · ช่องใส่รูปใน modal แก้ไขกฎคำตอบ = รอ v3 ปิดก่อน** (user ตัดสิน 2026-07-31)
รอบนี้ทำ **คอลัมน์ + เส้นทางส่ง + ช่องอัปโหลดในหน้าคลังคำถามใหม่** ให้ครบ · ช่องใส่รูปใน `KeywordEditorClient.tsx` เติมทีหลังเมื่อ v3 ปิด
⇒ **ไม่ต้อง migrate ซ้ำ** เพราะคอลัมน์ `AutoReplyRule.imageFileIds` ลงไปพร้อมรอบนี้แล้ว งานที่เหลือคือ UI ล้วน

**A6 · รูปสูงสุด 5 รูปต่อคำตอบ 1 ชุด · ส่งรูปก่อน แล้วข้อความตามหลัง**
ตรงกับ `QuickMessage.imageFileIds` ที่ใช้อยู่แล้ว (จำกัด 5 ที่ Valibot) และตรงกับพฤติกรรมปัจจุบันของ `sendOutboundMessage`
⚠️ ผลที่ตามมาซึ่งต้องบอกร้านให้รู้ใน UI: คำตอบ 1 ชุดที่มี 5 รูป = **ลูกค้าได้รับ 6 ข้อความรวด** — ต้องมีคำเตือนตอนใส่รูปเกิน 2-3 รูป ไม่ใช่ปล่อยให้รู้ตอนลูกค้าบ่น

**A4 · ตัวกรองคิว = ตายตัวในโค้ด + ตัดความยาว ≤ 3 ตัวอักษร**
บวกตัวกรอง PII ตาม D5 · ร้านไม่ต้องตั้งอะไร (ถ้าภายหลังพบว่ากรองเกิน ค่อยเปิดให้แก้ — ไม่ทำใน phase นี้)

### S-21 — คำตอบอัตโนมัติต้องแนบรูปได้ (user สั่ง 2026-07-31 กลาง phase)

### S-20 — ป้าย "DeepBot" ในรายการแชท (user สั่ง 2026-07-31 กลาง phase)

**ที่มา:** user ส่งภาพ 2 รูป — รูปแรกคือแถวในรายการแชทจริง (ชื่อ + preview + ชิป `ad_id.…` + badge `สำเร็จ` + ชิปกลุ่ม `ทดสอบ`) รูปที่สองคือรูปแบบป้ายที่ต้องการ: **pill ขอบมน พื้นอ่อนโทนเขียวมิ้นต์ + ไอคอนหุ่นยนต์ + ข้อความ** (ในภาพเขียนว่า "บอทตอบไว้")
**คำสั่ง:** ให้ใช้ **คำว่า `DeepBot`** แทนข้อความในภาพ

**ไฟล์:** `src/app/(paces)/seller/(chat)/inbox/components/InboxList.tsx` (+ backend ที่ประกอบ payload ของรายการแชท) — **ไม่แตะ `[id]/KeywordEditorClient.tsx`** จึงไม่ชนงาน v3

**เงื่อนไขที่ป้ายขึ้น (ต้องล็อกก่อนเขียนโค้ด):**
ข้อความ **ล่าสุด** ของเธรดเป็นข้อความฝั่งร้านที่มี `ChatMessage.autoReplyKind != null` — คือ "คำตอบล่าสุดในห้องนี้มาจากบอท ไม่ใช่คน"
🛑 **ไม่ใช่** "เธรดนี้เคยถูกบอทตอบ" (`autoReplyCount > 0`) — ถ้าใช้เกณฑ์นั้น ป้ายจะติดค้างตลอดกาลแม้พนักงานเข้ามารับช่วงไปนานแล้ว ซึ่งกลับหัวกับคุณค่าของป้าย (บอกว่า "ห้องนี้ยังไม่มีคนดู")
`autoReplyKind = 'AUTO_TEST'` ต้องแยกให้เห็น (ป้ายบอกโหมดทดสอบ) — สอดคล้องกับ `AutoReplyTag.tsx` ที่ใช้ label `DeepBot · ทดสอบ` อยู่แล้ว

**ไอคอน:** `robot` — **ยืนยันแล้วว่ามีใช้อยู่จริงใน prod** ที่ `AutoReplyTag.tsx:130` (`<Icon icon="robot" className="text-xs" />`)
~~เดิมผมบันทึกว่า `AutoReplyTag.tsx` ไม่มีไอคอน~~ — ผิด ux ตรวจโค้ดแล้วพบว่ามี ⇒ **ไม่มีคำถามเรื่องไอคอนเหลือ** ใช้ตัวเดียวกันทั้ง 2 ที่

**สี — เปลี่ยนจากที่ผมเสนอไว้แรก:** ux แย้งว่า **ห้ามใช้เขียว** แม้ภาพอ้างอิงจะเป็นเขียวมิ้นต์ เพราะ:
1. แถวนี้มี badge `สำเร็จ` สีเขียวอยู่แล้วจริง (เห็นในภาพที่ user ส่ง) — เขียว 2 ก้อนติดกันที่คนละความหมาย
2. Verified-Means-Green ของ Impeccable สงวนเขียวไว้ให้ "ยืนยันแล้ว/สำเร็จ" — "บอทตอบ" ไม่ใช่ทั้งสองอย่าง
⇒ ใช้ `text-primary` / `bg-primary/15 text-primary` ซึ่งตรงกับ `AutoReplyTag.tsx` ที่ shipped แล้ว (Hard Rule 6: skin ตาม theme ปัจจุบัน แม้ ref จะเป็นสีอื่น)

**⚠️ ช่องว่างที่ ux จับได้ — ต้องมีงาน backend เพิ่ม:** `autoReplyKind` ของ **ข้อความล่าสุด** ยังไม่มีใน payload ของรายการแชท (`ConversationListItem`) ⇒ S-20 ต้องรวมงาน enrich ฝั่ง backend ด้วย ไม่ใช่งาน UI ล้วน
