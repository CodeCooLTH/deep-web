# Sibling-surface parity — สร้างหน้าใหม่ ต้องอ่านหน้าพี่น้องก่อนเขียนบรรทัดแรก

> ที่มา: retro `docs/retro/2026-08-04-facebook-comments-00029-retrospective.md` §P5 — หน้าแท็บความคิดเห็นถูกรื้อ 4 รอบ
> รอบสุดท้าย user ถามตรง ๆ ว่า **"ตรงตัวกรองและสถานะทำไมไม่ทำเหมือน ตรงข้อความ"** ทั้งที่ตัวกรองชุดนั้นอยู่ใน
> `InboxList.tsx` โฟลเดอร์เดียวกัน ห่างกัน 2 ระดับ

---

## กฎ

**ก่อนสร้าง page / panel / tab ใหม่ใต้ route group ที่มีหน้าอื่นอยู่แล้ว ต้องทำ 3 ข้อนี้ก่อนเขียนโค้ด:**

1. `ls` โฟลเดอร์พี่น้องทั้งชั้น — ดูว่ามีหน้าไหนทำงานตระกูลเดียวกันอยู่
2. **เปิดอ่านจริง** ไฟล์ที่มี element ประเภทเดียวกับที่กำลังจะทำ:
   ตัวกรอง · แท็บสถานะ · แถบหัวข้อ · empty state · skeleton · ปุ่มโหลดเพิ่ม · ตัวนับ/badge
3. **ยกของนั้นมาใช้ซ้ำ** (import component เดิม หรือ copy โครงเดียวกันเป๊ะแล้วเปลี่ยนแค่ data)

**ถ้าเลือกไม่ยกมา** ต้องเขียนเหตุผลลง commit body ว่าทำไมหน้านี้ต้องต่างจากพี่น้อง — "อยากลองแบบใหม่" ไม่ใช่เหตุผล

---

## ตัวชี้วัดว่าละเมิดแล้ว

- user ต้องเป็นคนบอกว่า **"ทำไมไม่ทำเหมือนหน้า X"** → ละเมิดไปแล้ว ไม่ต้องเถียง
- หน้าใหม่มีปุ่มตัวกรองคนละทรงกับหน้าข้าง ๆ ในเมนูเดียวกัน
- ตัวเลข/สถานะเดียวกันคำนวณคนละที่ (ดู §"ตัวเลขต้องมาจาก symbol เดียว" ด้านล่าง)

---

## ทำไมกฎนี้ไม่ซ้ำกับ Hard Rule 1 (theme-copy)

| กฎ | ตอบคำถามว่า | แหล่งที่มา |
|---|---|---|
| Hard Rule 1 (theme-copy) | markup/สกินของ component มาจากไหน | `theme/paces/**`, `theme/vuexy/**` |
| **Sibling-surface parity (อันนี้)** | **หน้านี้ควรมีของอะไรบ้าง และวางเรียงยังไง** | หน้าพี่น้องในโปรดักต์เราเอง |

theme บอกว่าปุ่มหน้าตายังไง — **พี่น้องบอกว่าหน้านี้ควรมีปุ่มอะไรบ้าง** ผ่าน theme-copy แต่ประดิษฐ์ IA เองยังพังได้ (และพังจริงมาแล้ว 4 รอบ)

## ตัวเลขต้องมาจาก symbol เดียว

ต่อยอดบทเรียน `src/lib/shipping-address-status.ts` (2026-08-02) และ `countUnansweredForShop` (2026-08-03):

**นิยามที่ผู้ใช้เห็นเป็นตัวเลขหรือสถานะ ห้ามเขียน where/condition ซ้ำในสองไฟล์**
— ยกเป็นฟังก์ชันหรือ constant ตัวเดียวแล้ว import ไปใช้ทุกที่

เคสจริงที่พัง: จอเดียวกันโชว์ "ยังไม่ตอบ" 7 ที่รายการซ้าย และ 8 ที่แผงขวา เพราะนิยามถูกเขียนซ้ำ 2 ที่แล้วนับไม่เหมือนกัน

**เช็คก่อน commit:** จอเดียวที่โชว์ตัวเลขเดียวกัน 2 จุด → grep ให้เจอว่าทั้งสองจุดเรียก symbol เดียวกัน

## ปุ่ม/ชิปใหม่ต้องพูดภาษาเดียวกับ "แถวที่มันไปอยู่"

หลักเดียวกับหน้าพี่น้อง แต่ลงมาที่ระดับ container: **ก่อนตั้ง class ให้ของใหม่ ให้อ่าน class ของ
เพื่อนบ้านในคอนเทนเนอร์เดียวกันก่อนเสมอ** แล้วถามว่า "แถวนี้ใช้ภาษาไหน"

เคสจริง (2026-08-04, `4cb7cbcc` → แก้ที่ `d0f9f949`): เพิ่มปุ่ม "สร้างออเดอร์" ลงแถบเครื่องมือของ
ช่องพิมพ์ในแชท แล้วให้เป็น `bg-primary/15` (พิลล์ทึบ) เพราะคิดว่า "ปุ่มนี้สำคัญ ต้องเด่น" — user ทักว่า
"ไม่เข้าพวกเลย" เพราะทุกปุ่มในแถวนั้นเป็น `btn btn-icon` **พื้นใส สีบอกบทบาท ติดสีเฉพาะตอน hover**
(AI = `text-success`, เลือกสินค้า = `text-info`) พิลล์ทึบเป็นภาษาของ "ปุ่มหลักในการ์ด" คนละที่กัน

**ความเด่นมาจากตำแหน่งและป้ายกำกับ ไม่ใช่จากการเปลี่ยนภาษาของตัวเอง** — ปุ่มนั้นเด่นพอแล้วด้วยการ
เป็นตัวเดียวในแถวที่มีข้อความกำกับ (ตัวอื่นเป็นไอคอนเปล่า) โดยไม่ต้องเปลี่ยนพื้น

## จุดที่เกี่ยวข้อง

- Hard Rule 8 — `safepay-ux` เป็น mandatory gate ของงาน frontend ทุกชิ้น. **ด่านนี้มีหน้าที่ตรง ๆ คือไปเปิดหน้าพี่น้อง + theme มาแมปให้** ข้ามด่านนี้เมื่อไหร่กฎข้างบนก็ไม่มีใครบังคับ
- `feedback_ux_gate_every_round` (memory) — รอบแก้ก็ต้องผ่าน ux ไม่ใช่แค่รอบแรก
- `feedback_reuse_existing_shared_assets` (memory) — asset กลาง (โลโก้ช่องทาง/สีสถานะ) ก็ใช้หลักเดียวกัน
- `docs/conventions/reference-vs-theme-source.md` — ref จาก user ให้เอา IA/asset, สกินตามธีมเรา
