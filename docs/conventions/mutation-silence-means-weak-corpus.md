# "mutation แล้วเทสยังเขียว" = ชุดข้อมูลทดสอบอ่อน ไม่ใช่ mutation ไม่เกี่ยว

> ที่มา: `docs/retro/2026-08-21-phone-format-chip-retrospective.md` §1.3 — เกิด **2 ครั้งใน session เดียว**
> กับเทสที่ติดป้าย `[blocker]` ทั้งคู่

---

## กฎ

เมื่อทำ mutation (จงใจทำโค้ดให้ผิด) แล้ว **เทสยังเขียว** ห้ามสรุปว่า
*"mutation ตัวนี้ไม่เกี่ยวกับเทสตัวนี้"* แล้วข้ามไป

**mutation ทำหน้าที่ของมันสมบูรณ์แล้ว** — มันเพิ่งบอกว่า **โค้ดที่ผิดกับโค้ดที่ถูก ให้ผลลัพธ์
เหมือนกันบนทุก input ที่คุณป้อน** ซึ่งแปลว่าเทสนั้นไม่ได้กันสิ่งที่มันอ้างว่ากัน

ต้อง **เติม input ที่ทำให้ความต่างโผล่** แล้วรัน mutation เดิมซ้ำจนแดง ถึงจะถือว่าเทสใช้ได้

---

## ทำไมผลนี้หลอกที่สุด

ผลลัพธ์ทั้งสามแบบของ mutation อ่านต่างกันคนละเรื่อง:

| ผล | แปลว่า |
|---|---|
| เทส **แดง** | ✅ เทสกันได้จริง |
| เทส **พังตอน compile** | ต้องเลือก mutation ใหม่ที่ยัง type-check ผ่าน |
| เทส **ยังเขียว** | 🛑 **เทสไม่ได้กันอะไรเลย** — แต่หน้าตาเหมือนความสำเร็จ |

แถวสุดท้ายคืออันตราย เพราะมันมาในรูปของ "เขียวหมด" ซึ่งเป็นสิ่งที่เรากำลังอยากเห็นพอดี

## เคสจริง 2 ตัว (2026-08-21)

### 1. ไม่มี input ไหนผลิตค่าที่ผิดออกมาได้เลย

สัญญา: *"เบอร์ที่ chip เสนอ ต้องผ่านด่านบันทึกได้เสมอ"*
เทสป้อน output ของ chip เข้า `CreateOrderSchema` **ตัวจริง** (หลบ tautology สำเร็จแล้ว)

mutation: ผ่อนเกณฑ์ของ chip ให้รับเบอร์ 9 หลัก → **เขียว 42/42**

เพราะชุด input ทั้ง 17 ตัวไม่มีตัวไหนที่ตัดแล้วได้ **9 หลัก** เลย ⇒ ต่อให้ผ่อนกฎ
โค้ดก็ยังไม่มีโอกาสผลิตค่าที่ผิดออกมา · เติม `092079164` เข้าไปแล้วถึงแดง

### 2. ข้อมูลทดสอบวางของไว้คนละที่กับที่บั๊กจะโผล่

สัญญา: *"เบอร์ที่ลบไม่ออก ต้องไม่ค้างอยู่ในที่อยู่"*
เทส: `expect(r.addressLine).not.toMatch(/0_9_2/)`

mutation: ให้ `stripPhone` กลับไปใช้ regex เก่า → **เขียว 17/17**

เพราะข้อมูลทดสอบวางเบอร์ไว้ **คนละบรรทัด** กับที่อยู่ ⇒ ตัวที่ค้างไม่มีทางโผล่ใน `addressLine`
ย้ายมาบรรทัดเดียวกัน (ซึ่งเป็นรูปที่คอมเมนต์ในโค้ดบอกเองว่าเจอบ่อยที่สุด) ถึงเห็นว่า
**เบอร์ที่ลบไม่ออกกลายเป็น `addressLine` ทั้งดุ้น**

## วิธีเติม input ให้ตรงจุด

ถามคำถามเดียว: **"ถ้าโค้ดผิดแบบนี้ ค่าที่ผิดจะออกมาหน้าตายังไง — และมี input ตัวไหน
ในชุดที่พาไปถึงตรงนั้นได้"** ถ้าตอบไม่ได้ แปลว่ายังไม่มี ต้องแต่งขึ้นมา

- ผ่อนเกณฑ์ **ความยาว** → ต้องมี input ที่ยาวผิดพอดีกับที่ผ่อน
- ผ่อนเกณฑ์ **คำนำหน้า** → ต้องมี input ที่คำนำหน้าผิดแต่ส่วนอื่นถูกหมด
- ถอด **การลบ/ตัด** ค่าออกจากข้อความ → ต้องมี input ที่ค่านั้นอยู่ **ในตำแหน่งที่ผลลัพธ์จะหยิบไปใช้**
- ถอด **ด่านที่ลำดับสำคัญ** → ต้องมีเทสที่ยืนยัน *ลำดับ* ไม่ใช่แค่ *การมีอยู่*
  (ดู `src/services/__tests__/iship-import-phone-guard.test.ts` — เช็คว่า guard อยู่ก่อน `createOrder(`)

เขียนคอมเมนต์กำกับ input ที่เติมเข้าไปเพื่อ mutation โดยเฉพาะเสมอ ไม่งั้นคนถัดไปจะเห็นว่า
"ซ้ำกับเคสอื่น" แล้วลบทิ้ง — ตัวอย่าง `src/lib/phone-suggest.test.ts`:

```ts
// 🛑 3 บรรทัดนี้มีไว้ให้ mutation จับได้ — ถ้าใครผ่อนเกณฑ์ของ chip ให้รับ 9 หลัก
// อินพุตพวกนี้จะผลิต suggestion ที่บันทึกไม่ผ่านทันที
// ก่อนมีบรรทัดพวกนี้ เทสทั้งไฟล์เขียวแม้ผ่อนเกณฑ์
'092079164',
'0920791649 092079164',
'021234567',
```
