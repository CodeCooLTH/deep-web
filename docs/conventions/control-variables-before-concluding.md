# ก่อนสรุปผลการทดลองกับระบบภายนอก ต้องลิสต์ตัวแปรก่อนว่าคุมได้กี่ตัว

> เหตุการณ์ 2026-08-11 (feature 00043) — ทดสอบสิทธิ์ `HUMAN_AGENT` บน prod แล้ว Meta ตอบ
> `(#100) Cannot tag messages with 'HUMAN_AGENT' without prior approval.`
> สรุปทันทีว่า **"Standard Access ไม่พอ ต้องผ่าน App Review"** และรายงานหัวหน้าไปแล้ว
> หัวหน้าถามกลับสั้น ๆ ว่า *"มั่นใจแล้วใช่ไหม ลองเช็ค mcp + official document"*
> → ตรวจแล้วพบว่า **ฟีเจอร์นั้นไม่เคยถูกเพิ่มเข้า use case ของแอปเลยสักครั้ง**

## สิ่งที่เกิดขึ้น

การทดลองมีตัวแปร **2 ตัว** ที่ต่างก็ทำให้ Meta ปฏิเสธได้เหมือนกัน:

| ตัวแปร | สถานะจริงตอนทดลอง | ตรวจแล้วหรือยัง |
|---|---|---|
| ฟีเจอร์ถูกเพิ่มเข้า use case ของแอปแล้วหรือยัง | **ยังไม่เคยเพิ่ม** | ❌ ไม่ได้ตรวจ |
| ผ่าน App Review แล้วหรือยัง | ยังไม่ผ่าน | ✅ ตรวจ |

สิ่งที่พิสูจน์ได้จริงคือ **"ไม่เคยขอสิทธิ์ = ถูกปฏิเสธ"**
สิ่งที่รายงานออกไปคือ **"ขอแล้วแต่ยังไม่อนุมัติ = ถูกปฏิเสธ"** — คนละประโยค คนละความหมาย
และประโยคหลังคือ open question ตัวจริงที่ยังไม่ถูกตอบจนถึงตอนนี้

## กฎ

🛑 **ก่อนสรุปผลการทดลองกับระบบภายนอก ต้องตอบให้ได้ก่อนว่า "ถ้าผลออกมาแบบนี้ มีสาเหตุอื่นอีกกี่อย่าง
ที่ให้ผลเหมือนกัน"** — ตอบไม่ได้ = ยังสรุปไม่ได้ ให้รายงานเป็น "ยังไม่รู้" แทนการเดาที่ฟังดูมีเหตุผล

🛑 **error ที่ระบุชื่อสิ่งที่เราส่งไป (tag / field / scope / parameter) พิสูจน์แค่ว่า "เราส่งไปจริง"**
ไม่ได้พิสูจน์ว่าเงื่อนไขที่เราคิดว่าขาด คือเงื่อนไขที่ขาดจริง — มันบอกว่าปลายทางได้ยินเรา ไม่ได้บอกว่า
ทำไมปลายทางถึงปฏิเสธ

🛑 **ก่อนบอกว่า "X ไม่พอ" ต้องยืนยันว่า X ถูกตั้งค่าครบแล้ว ไม่ใช่ว่า X ไม่เคยมีอยู่เลย** — นี่คือรูปแบบ
ที่พลาดซ้ำได้ง่ายที่สุด เพราะทั้งสองกรณีให้ error เดียวกันเป๊ะ

🛑 **ผลที่ "ตรงกับสิ่งที่เราคาดไว้" ต้องถูกตรวจมากกว่าผลที่ขัดความคาดหมาย ไม่ใช่น้อยกว่า** — ผลที่ขัด
ความคาดหมายบังคับให้เราสืบต่ออยู่แล้วโดยธรรมชาติ ส่วนผลที่ตรงใจทำให้เราหยุด และถ้ามันปิด "รายการ
ค้าง" ที่เราเขียนไว้เองด้วย แรงจูงใจที่จะไม่ตรวจซ้ำจะยิ่งสูง

## วิธีปฏิบัติ

1. **ลิสต์ตัวแปรก่อนตีความผล** เขียนออกมาเป็นข้อ ๆ ว่ามีอะไรบ้างที่ทำให้ผลนี้เกิดได้
2. **ตรวจสถานะของทุกตัวแปรด้วยแหล่งที่เป็นอิสระจากการทดลอง** — MCP / dashboard / API ที่อ่าน
   config ตรง ๆ ไม่ใช่การอนุมานจากผลลัพธ์เดียวกัน
3. **แยกให้ชัดในรายงานว่าอะไรคือ "พิสูจน์แล้ว" อะไรคือ "ยังไม่รู้"** — อย่ารวบเป็นข้อสรุปเดียว
4. **ถ้าคุมตัวแปรไม่ครบ ให้ระบุการทดลองที่เหลือ** ว่าต้องทำอะไรเพิ่มจึงจะได้คำตอบจริง

## ญาติกัน (คลาสเดียวกัน เคยเกิดมาแล้ว)

- `docs/conventions/graph-access-depends-on-subject.md` — สรุปว่า endpoint "ยิงไม่ได้" หลังทดสอบกับ
  subject ชนิดเดียว (ลูกค้า 30 คน) โดยไม่ลอง subject ที่มี role บนแอป → คำอธิบายผิดนั้นปิดทาง
  สืบสวนไป 6 วัน · **กฎเดิมคือ "ทดสอบ ≥2 subject" — กฎนี้ขยายเป็น "ทดสอบ ≥2 สถานะของตัวแปร
  ที่กำลังสรุปถึง"**
- `docs/conventions/domain-term-single-definition.md` (ทิศกลับ) — ข้อความที่อ้างพฤติกรรมของระบบ
  ต้องยืนยันก่อนใช้เป็นเหตุผลที่จะ "ไม่ทำ" อะไร
- `feedback_status_field_is_not_an_event` — `REJECTED` ในตาราง privileges ของ Meta อาจแปลว่า
  "ยังไม่ได้ขอ" ไม่ใช่ "ขอแล้วถูกปฏิเสธ"
