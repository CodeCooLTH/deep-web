# 🛑 ค่าที่ตั้งจาก id ของผู้ให้บริการ คงที่ตลอดกาล — และแถวที่ถูกปิดยังถือมันไว้

> เกิดจริง 2026-08-15 บน prod · แก้ 2 รอบเพราะรอบแรกไล่ constraint ไม่ครบ
> `docs/20 - Features/00040 - App Store Compliance/EXTENSIONS-2026-08-10-signin-with-apple.md`

## อาการ

ผู้ใช้กด "เข้าสู่ระบบด้วย Apple" → **ค้างที่หน้าล็อกอิน มีวงกลมหมุน แต่ไม่พาไปไหนเลย**
ไม่มี error ให้ผู้ใช้เห็น ไม่มีอะไรบอกว่าเกิดอะไรขึ้น

## กลไก

`upsertOAuthUser()` ตั้งค่า 2 อย่างจากข้อมูลที่ผู้ให้บริการส่งมา:

```
username = `${prefix}${account.providerAccountId}`   // apple001680.9ea8bb…
email    = user.email                                // baaza06@icloud.com
```

ทั้งคู่ **คงที่ตลอดกาลต่อบัญชีหนึ่งใบของผู้ให้บริการ** — Apple/Facebook/LINE ส่งค่าเดิมมาทุกครั้ง

และ `User` มีคอลัมน์ `@unique` **3 ตัว**: `username` · `email` · `phone`

⇒ ถ้ามีแถวเก่าถือค่าใดค่าหนึ่งไว้ **จะชนทุกครั้งไป ไม่ใช่ครั้งเดียว** และ soft delete
**ไม่ปล่อยคอลัมน์ unique คืน** จนกว่าจะถึงรอบล้างข้อมูลจริง (30 วัน) ⇒ ชนได้แม้ไม่มีใครล็อกอินอยู่

เส้นทางที่พาไปถึง: เชื่อม OAuth → ถอดการเชื่อม (แถว `AuthAccount` ถูกลบ) → ออกจากระบบ →
ล็อกอินด้วย id เดิม ⇒ ไม่เจอ `AuthAccount` จึงไปสร้าง user ใหม่ ⇒ ชน

## ทำไมไม่มีอะไรฟ้อง

ตัวดักเดิมเหมาว่า **P2002 = race ตอนล็อกอินครั้งแรกเสมอ**:

```ts
catch (P2002) {
  const existing = await findUserByAuthAccount(...)
  if (existing) return existing.id
  throw err            // ← ตกมาที่นี่เมื่อชนคอลัมน์อื่น
}
```

พอชนที่ `username`/`email` (ไม่ใช่ที่ `AuthAccount`) ก็หา `existing` ไม่เจอ → `throw` →
NextAuth ตายกลางทาง → **หน้าล็อกอินค้าง** โดยไม่มี log ที่ผู้ใช้หรือเราเห็น

`tsc` / build / เทส / grep เขียวหมด เพราะโค้ดถูกทุกตัวอักษร — มันแค่รับมือไม่ครบ

## กติกา

**1. P2002 มีหลายสาเหตุ ห้ามเหมาเป็นอย่างเดียว** — อ่าน `err.meta.target` ว่าชนคอลัมน์ไหน
แล้วจัดการตามชนิด (Prisma ส่งมาเป็น `string[]` หรือ `string` แล้วแต่ไดรเวอร์ ⇒ แปลงเป็นสตริง
เดียวแล้วค้นคำ ปลอดภัยกว่าเดารูปแบบ)

| ชนที่ | ทำอะไร | เหตุผล |
|---|---|---|
| `AuthAccount` | คืน user ที่อีก request สร้างไปแล้ว | race จริง |
| `username` | ตั้งชื่อใหม่ | เป็นแค่ค่าตั้งต้น ผู้ใช้เปลี่ยนเองได้ทีหลัง |
| `email` | ไม่เก็บอีเมล | อีเมลเป็นของแถวอื่น เราไปยึดมาไม่ได้ · nullable · ระบบนี้ยึด "เบอร์" เป็นตัวตนหลัก |
| อื่น ๆ | `throw` | unique ตัวใหม่ที่ยังไม่มีใครคิดถึง ต้องดังออกมา ห้ามกลืน |

**2. ไล่ constraint ให้ครบก่อนแก้ ไม่ใช่ปะทีละอาการ** — รอบแรกผมแก้แค่ `username` แล้วประกาศ
ว่าจบ user ทดสอบแล้วยังค้างเหมือนเดิมเพราะชนต่อที่ `email` ซึ่งอยู่ในสคีมาเดียวกัน
**ดูสคีมา 5 วินาทีก็เห็นครบทั้ง 3 ตัว**

**3. ด่านต้องผูกกับสคีมาจริง ไม่ใช่รายชื่อที่พิมพ์ไว้ในเทส**

```ts
const uniqueCols = [...userModel.matchAll(/^\s+(\w+)\s+\S+\s+@unique/gm)].map((m) => m[1])
expect(uniqueCols.sort()).toEqual(['email', 'phone', 'username'])
```

เพิ่มคอลัมน์ unique ใหม่เมื่อไหร่ เทสแดงทันที บังคับให้มาทบทวนว่าเส้นทางสมัคร OAuth ต้องรับมือไหม

**4. ด่านต้องเช็ค "ทำอะไรกับสิ่งที่ตรวจเจอ" ไม่ใช่แค่ "ตรวจเจอ"** — ร่างแรกของเทสเช็คแค่
`target.includes("email")` ซึ่งเป็นแค่การ *ตรวจจับ* พิสูจน์ด้วย mutation แล้วพบว่าลบบรรทัด
ที่ *แก้ปัญหา* ทิ้ง (`trustedEmail = undefined`) เทสยังเขียว — **ด่านที่ผ่านตลอดคือด่านที่ไม่มีอยู่จริง**

## เรื่องที่ยังไม่ได้ทำ

soft delete ยังไม่ปล่อยคอลัมน์ unique คืนตอนปิดบัญชี (ปล่อยตอน purge เท่านั้น ผ่าน
`purgedUsername()`) — จงใจไม่แก้ เพราะการเปลี่ยนความหมายของ "ปิดบัญชี" ควรเป็นการตัดสินใจ
ของตัวมันเอง ไม่ใช่ผลข้างเคียงของการแก้บั๊กล็อกอิน · การรับมือที่ `upsertOAuthUser`
ครอบทุกสาเหตุอยู่แล้วไม่ว่าแถวเก่าจะมาจากทางไหน
