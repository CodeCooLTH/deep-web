# ฟีเจอร์ที่พึ่งการสื่อสารข้าม context ต้อง fail-loud และต้องยืนยันในเบราว์เซอร์

**ที่มา:** feature 00035 ตัวจัดหน้าร้าน — คอลัมน์กลาง 40% ของหน้า **ไม่ทำงานเลยตั้งแต่ deploy แรก** โดย `tsc` และ `next build` ผ่านหมดทุกรอบ และไม่มี error สักตัวทั้งใน console และ log
(retro: `docs/retro/2026-08-07-feature-00035-shop-page-builder-retrospective.md`)

---

## ครอบอะไรบ้าง

ฟีเจอร์ที่ความถูกต้องขึ้นกับ **สองฝ่ายที่รันคนละ context แล้วต้องคุยกันติด**:

- `iframe` + `postMessage` (คนละ document)
- session/cookie ข้าม subdomain (`seller.*` ↔ main domain — โปรเจกต์นี้ **แยก session ตาม subdomain**)
- webhook ที่ต้องมี echo กลับมา (Meta, iShip)
- worker/cron ที่ต้องรายงานผลกลับ
- Broadcast/realtime ที่ต้องมี subscriber ฝั่งตรงข้าม

ลักษณะร่วม: **ถ้าอีกฝ่ายเงียบ โค้ดฝั่งเราไม่ผิดอะไรเลย** — ไม่ throw ไม่ compile error มันแค่ไม่มีอะไรเกิดขึ้น

---

## กฎ

### 1. ต้อง fail-loud บนหน้าจอ ห้ามค้างเงียบ

ถ้าไม่ได้รับสัญญาณที่คาดไว้ภายในเวลาที่กำหนด (แนะนำ ~2 วินาทีสำหรับ UI) **ต้องแสดงให้ผู้ใช้เห็น** ว่าเชื่อมไม่ติด และบอกว่าอะไรยังใช้ได้อยู่

```
"ตัวอย่างสดใช้ไม่ได้ตอนนี้ — สิ่งที่คุณจัดยังบันทึกได้ปกติ"
```

ห้ามใช้ `console.error` อย่างเดียว ผู้ใช้ไม่เปิด devtools
(บทเรียนเดียวกับ iShip `unwrap` ที่ทำ quote ราคาพังเงียบบน prod หลายเดือน)

### 2. ป้ายบน UI ที่สัญญาความสามารถ ต้องผูกกับสถานะจริง

หน้า builder เขียนหัวคอลัมน์ว่า **"ลากเพื่อสลับลำดับ"** เป็นข้อความคงที่ ขณะที่ไม่มีอะไรลากได้ทั้งจอ — ป้ายที่โกหกแย่กว่าไม่มีป้าย เพราะผู้ใช้จะโทษตัวเองว่าทำไม่เป็น

ข้อความที่บรรยายสิ่งที่ทำได้ ต้อง render ตามสถานะจริง ไม่ใช่ hardcode

### 3. `tsc` + `build` ไม่นับเป็นการยืนยันสำหรับฟีเจอร์กลุ่มนี้

ทั้งสองอย่างตรวจได้แค่ว่า **โค้ดคอมไพล์ผ่าน** ไม่ได้ตรวจว่า runtime สองฝั่งคุยกันติด
ต้องมีหลักฐานจากเบราว์เซอร์จริง — วิธีที่ใช้ได้ในโปรเจกต์นี้คือ `browser-harness`
(ดู memory `project_browser_qa_via_browser_harness`)

หลักฐานที่ยอมรับได้คือ **ตัวเลขก่อน/หลัง** ไม่ใช่ screenshot ที่ "ดูโอเค":

```python
# ตัวอย่างจริงจาก 00035 — พิสูจน์ว่าลากวางได้
cdp("Input.dispatchMouseEvent", type="mousePressed", x=sx, y=sy, button="left", clickCount=1, buttons=1)
# ...mouseMoved หลายจุด...
cdp("Input.dispatchMouseEvent", type="mouseReleased", x=tx, y=ty, button="left", buttons=0)
# แล้ววัด childCount ของ droppable ก่อน/หลัง
```

หมายเหตุ: `cdp()` ของ harness มี signature `cdp(method, session_id=None, **params)` — **params เป็น kwargs ไม่ใช่ dict**

### 4. เมื่อ user รายงานอาการ ให้ไปวัดก่อนอธิบาย

ถ้ารายงานขัดกับสิ่งที่เราเชื่อว่าจริง **หลักฐานอยู่ฝั่ง user** — ใน 00035 user บอกว่า "ไม่เห็นจะ drag & drop ได้เลย" **3 ครั้ง** และทุกครั้งได้คำอธิบายข้อจำกัดทางสถาปัตยกรรมกลับไป (ซึ่งถูกต้อง แต่ไม่ใช่คำตอบ) แทนที่จะมีใครไปเปิดหน้าดู

คำอธิบายที่ถูกต้องแต่ไม่ตรงคำถาม = การเถียงกับหลักฐาน

## ทางเลือกที่ควรพิจารณาก่อนเลือกสถาปัตยกรรมข้าม context

ก่อนตัดสินใจใช้ `iframe`/`postMessage` เพื่อความ "แม่นยำ 100%" ให้ชั่งกับต้นทุนจริง:

| | iframe ของหน้าจริง | วาดเองในหน้าเดียวกัน |
|---|---|---|
| ความตรงกับของจริง | 100% ถ้าทำงาน | เพี้ยนได้ ต้อง sync มือ |
| ลาก/โต้ตอบข้ามคอลัมน์ | **ทำไม่ได้** (pointer event ไม่ข้าม document) | ทำได้ |
| จุดที่พังเงียบได้ | session · origin · rect sync · scroll sync | ไม่มี |
| ตรวจด้วย static check | ไม่ได้เลย | ได้บางส่วน |

00035 เลือก iframe ก่อนแล้วต้องรื้อทิ้ง — ถ้า interaction หลักของหน้าคือการลาก/เลือกข้ามพื้นที่ **อย่าเลือก iframe**
