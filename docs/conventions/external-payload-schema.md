# Payload จากระบบภายนอก — กติกาที่ต้องยึด

> ครอบ webhook และ response ของบริการภายนอกทุกเจ้า (Meta Graph, iShip, apitel, …)
> ไฟล์นี้ถูกอ้างจาก `CLAUDE.md` และจาก spec/plan หลายใบมาตั้งแต่ 2026-08-04 แต่เพิ่งถูกเขียนจริง
> 2026-08-07 — ระหว่างนั้นกติกาอยู่ในหัวคนกับในคอมเมนต์กระจัดกระจาย

---

## 1. ทุก field เป็น optional เป็นค่าตั้งต้น

**กฎ:** schema ของ payload ภายนอกประกาศ field เป็น optional ทั้งหมด ยกเว้น field ที่ **จำเป็นต่อการตัดสินความหมาย** จริง ๆ

**ทำไม:** field ที่ประกาศเป็น "บังคับ" ทั้งที่ปลายทางไม่ได้ส่งมาทุกครั้ง = validator ตี event ตกทั้งก้อน แล้วข้อมูลหายเงียบ ๆ ไม่มี error ให้ใครเห็น

**เคสจริง 2026-08-04:** `AttachmentSchema.type` ถูกประกาศบังคับ แต่ Meta ไม่ได้ส่ง `type` มาทุกครั้ง → Valibot ตีทั้ง event ตก → **รูป 6 ใบหายทั้งชุด** ตัวตัดสินความหมายที่ถูกต้องคือ `payload.url` (ไม่มี url = ไม่มีไฟล์แนบจริง) ไม่ใช่ `type`

**ตัวช่วย:** เก็บ payload ดิบไว้ก่อนเข้า validator เสมอ (`rawMessage`) — ของที่ผ่าน Valibot แล้วสืบย้อนอะไรไม่ได้เลย

## 2. ชื่อฟิลด์เดียวกัน "คนละทิศทาง" อาจแปลคนละอย่าง — ต้องพิสูจน์ด้วย payload จริง

**กฎ:** ก่อนแมป field ของ response เข้าโครงข้อมูลของเรา ต้องมีหลักฐานจาก **payload จริงของปลายทาง** ว่าฟิลด์นั้นแปลว่าอะไร — เอกสาร ความสมมาตรของชื่อ และ "ฝั่งขาออกเป็นแบบนี้" ไม่นับเป็นหลักฐาน

**เคสจริง 2026-08-07 (iShip):**

| | ตำบล | อำเภอ |
|---|---|---|
| ขาออก `create_order` | `dst_district` | `dst_amphure` |
| ขาเข้า `query_orders`/`get_order` | **`dst_area`** | **`dst_district`** |

`dst_district` แปลว่าคนละระดับการปกครองในสองทิศทางของ API เดียวกัน โค้ดเดาว่าขาเข้าสมมาตรกับขาออก ผลคือทุกออเดอร์ที่ผูกพัสดุมาจาก iShip ถูกบันทึก **ตำบลกับอำเภอสลับกัน** — 23 ใบบน prod ระหว่าง 08-01 ถึง 08-07

**ทำไมไม่มีอะไรฟ้อง:** ค่าที่สลับกันยังเป็นสตริงไทยที่ดูสมเหตุสมผลทุกประการ `tsc` เขียว validator ผ่าน หน้าจอแสดงผลสวย — มันไปพังตอนเปิดพัสดุ **ใบถัดไป** ของลูกค้าคนเดิม (ที่อยู่ลูกค้าเก่าถูกหยิบมาใช้ซ้ำ) เป็นข้อความว่า "ที่อยู่ผู้รับไม่ผ่านการตรวจสอบของขนส่ง" คนละหน้าจอ คนละสัปดาห์ กับต้นเหตุ

**วิธีพิสูจน์ที่ใช้ได้จริง:** ยิง endpoint จริงด้วย token จริงกับข้อมูลที่ **ค่าสองช่องต่างกัน** แล้วเทียบกับชุดข้อมูลอ้างอิงที่ผู้ให้บริการกำหนด (ที่นี่คือ `public/data/iship-address.json`) — ตัวอย่างในเอกสารของ iShip ใส่ค่า "สายไหม" ไว้ทั้งสองช่อง จึงพิสูจน์อะไรไม่ได้เลย และ fixture ของเราก็ลอกความกำกวมนั้นมาเป็นค่าที่แต่งเอง

## 3. "ให้คนตรวจด้วยตา" ไม่ใช่ด่านกันข้อมูลเพี้ยน

**กฎ:** ถ้ายอมรับความไม่แน่นอนของ mapping ไว้ ห้ามอ้างขั้นตอนที่พึ่งสายตาผู้ใช้เป็นตัวกัน — ต้องกันด้วยเทสที่ยึดค่าจริง หรือด้วยการตรวจกับชุดข้อมูลอ้างอิงตอนเขียนลงฐาน

**เคสจริง:** หัวไฟล์ `src/lib/iship/unlinked.ts` เขียนไว้ตรง ๆ ว่าคู่ตำบล/อำเภอขาเข้า "พิสูจน์จากเอกสารไม่ได้" แล้วรับความเสี่ยงด้วยเหตุผลว่า *"การผูกพัสดุมีขั้นเทียบที่อยู่สองคอลัมน์ให้ร้านตรวจด้วยตาเสมอ ถ้าจับคู่กลับหัวจริง ร้านจะเห็นทันที"* — ผ่านไป 23 ใบไม่มีใครทักสักใบ เพราะคนที่กดผูกกำลังทำงานอื่นอยู่ (ยืนยันว่าเป็นพัสดุใบที่ตั้งใจ) ไม่ได้กำลังตรวจ mapping ของ API

**ผลที่ตามมาที่ต้องจำ:** การรู้ตัวว่าเดา + เขียนคอมเมนต์ยอมรับไว้ **ไม่ได้ลดความเสียหาย** มันแค่ทำให้ตอนสืบสวนใช้เวลาน้อยลง

## 4. คอลัมน์ที่มีผู้เขียนสองราย ต้องแยก "ไม่รู้" ออกจาก "ถูกลบ"

**กฎ:** คอลัมน์ที่ทั้งเราและ echo ของระบบภายนอกเขียนได้ ต้องตอบให้ได้ว่า "ค่าที่หายไปจาก payload = ปลายทางไม่ได้ส่งมา (ไม่รู้) หรือ ปลายทางบอกว่าถูกลบแล้ว" — **ถ้าไม่รู้ ห้ามเขียน null ทับ**

**เคสจริง 2026-08-04:** รีแอ็กชันบนข้อความโผล่ประมาณ 1 วินาทีแล้วหาย เพราะ echo ของ Meta ที่ไม่มี field รีแอ็กชันติดมาถูกตีความว่า "ถูก unreact" แล้วเขียน null ทับของที่เพิ่งบันทึกไป

---

## 5. ค่าที่ผู้ใช้กรอกแล้วส่งต่อให้ระบบภายนอกตรวจ ต้องตรงกับชุดข้อมูลของระบบนั้น

**กฎ:** เมื่อผู้ให้บริการกำหนดชุดข้อมูลอ้างอิงมาให้ (ที่อยู่/รหัสสินค้า/ชื่อขนส่ง) ให้ยึดชุดนั้นเป็น SSOT ของค่าที่กรอกได้ ไม่ใช่ชุดข้อมูลมาตรฐานทั่วไป

**เคสจริง:** ไฟล์ที่อยู่ของ iShip (`public/data/iship-address.json`, 7,662 แถว) เขียน กทม. ว่า `"กรุงเทพ"` และ **ไม่มีอำเภอชื่อ "เมือง" เดี่ยว ๆ เลยสักแถว** มีแต่ `"เมืองสมุทรปราการ"`/`"เมืองชุมพร"` — ที่อยู่ที่ผู้ใช้พิมพ์ "อ.เมือง" จึงถูกขนส่งตีตกเหมือนกันกับกรณีสลับตำบล/อำเภอ (เจอ 3 ใบบน prod รอบเดียวกัน)

**วิธีตรวจทั้งฐานในนาทีเดียว** (ใช้ตอนสงสัยว่ามีข้อมูลเพี้ยนเป็นคลาส ไม่ใช่ไล่ทีละใบ):
1. ดึงคู่ `(subdistrict, district, province, postcode)` ของทุกแถวออกมา
2. เช็คว่าคู่นั้นมีในไฟล์อ้างอิงไหม
3. ถ้าไม่มี → เช็คว่า **คู่ที่สลับกัน** มีไหม (เจอ = สลับทั้งคลาส ไม่ใช่คนกรอกผิดรายใบ)
4. ที่เหลือค่อยดูด้วยตา

## 6. UI ที่ผูกกับ error ของระบบภายนอก ต้องแยก "กดซ้ำแล้วมีโอกาสผ่าน" ออกจาก "กดกี่ครั้งก็เหมือนเดิม"

**กฎ:** เกณฑ์ retryable อยู่ที่เดียว (`IShipError.retryable` + `classifyRetryUX` ใน `src/lib/iship/errors.ts`) และหน้าจอต้องให้ **ปุ่มทึบใบเดียว** ชี้ไปที่ทางที่แก้ปัญหาได้จริงตามชนิด error

**ทำไม:** การจัดประเภทผิดฝั่ง "ชวนให้กด" แพงกว่าฝั่งตรงข้ามเสมอ — มันสั่งให้ผู้ใช้ทำสิ่งที่ไร้ผลซ้ำ ๆ (เคสจริง prod 2026-08-06 ร้านกด "ลองใหม่" 3-4 ครั้งกับเครดิตไม่พอ · 2026-08-07 กับที่อยู่ไม่ผ่าน) และห้ามซ่อนปุ่มที่ถูกลดตำแหน่ง เพราะการแยกชนิด error จากข้อความพลาดได้ — จัดหมวดผิดแล้วซ่อนปุ่ม = ผู้ใช้ออกจากทางตันไม่ได้เลย

**ข้อความประกอบท้ายจอต้องผูกกับชนิด error ด้วย** — ประโยคให้กำลังใจแบบเดียวใช้ทุกเคส ("กดลองใหม่ได้เรื่อย ๆ") จะกลายเป็นคำเชิญให้กดสิ่งที่ไม่มีวันผ่าน ทั้งที่ทั้งจอพยายามห้าม
