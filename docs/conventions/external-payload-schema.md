## กฎรวบยอด

**ข้อมูลจากระบบภายนอกไม่หายแบบเสียงดัง มันหายแบบ HTTP 200** ทั้งสองเคสจริงด้านล่างไม่มี error
ไม่มี exception ไม่มี log สีแดง — `tsc` / build / grep / hook มองไม่เห็นทั้งหมด เพราะโค้ดถูกตาม
ไวยากรณ์ทุกบรรทัด รู้ตัวอีกทีคือผู้ใช้ทักว่า "ทำไมมันขึ้นแบบนี้"

## 1. ขาเข้า (webhook) — ทุก field เป็น optional เป็นค่าตั้งต้น

**กฎ:** ใน Valibot schema ของ payload ภายนอก ประกาศทุก field เป็น optional ไว้ก่อน แล้วค่อยเลือก
บังคับเฉพาะ field ที่ **จำเป็นต่อการตัดสินความหมาย** จริง ๆ

**เหตุผล:** field ที่ประกาศเป็น "บังคับ" ทั้งที่ต้นทางไม่ได้ส่งมาเสมอ ทำให้ Valibot **ตี event ตก
ทั้งก้อน** ไม่ใช่แค่ field นั้นเป็น undefined — ข้อความทั้งข้อความหายไปเงียบ ๆ

**เคสจริง 2026-08-04:** `AttachmentSchema.type` ถูกประกาศเป็น required → รูป 6 ใบหายทั้งชุด
ตัวที่ควรบังคับคือ `payload.url` (ไม่มี url = แสดงอะไรไม่ได้จริง) ไม่ใช่ `type`
(ซึ่งเป็นแค่ป้ายกำกับที่ Meta ส่งบ้างไม่ส่งบ้าง)

**เช็คลิสต์เวลาเขียน schema ใหม่:**
- field ไหนที่ "ถ้าไม่มี = ทำอะไรต่อไม่ได้เลย" → บังคับได้
- field ไหนที่ "ถ้าไม่มี = แสดงผลได้แต่ข้อมูลน้อยลง" → optional เสมอ
- เก็บ payload ดิบไว้ก่อนเข้า validator (`ChatMessage.rawMessage`) — สิ่งที่ผ่าน validator แล้ว
  สืบย้อนอะไรไม่ได้อีก

## 2. ขาออก (field selection) — ขอชื่อฟิลด์ผิด = ข้อมูลหายเงียบ ไม่ใช่ error

**กฎ:** เวลาขอข้อมูลด้วย field expansion / sparse fieldset (Graph `fields=`, JSON:API `fields[]`,
GraphQL selection) **อย่าเดาชื่อซับฟิลด์** — เปิดเอกสารของ node นั้นก่อน หรือ **ขอแบบไม่ระบุ
ซับฟิลด์ไปเลย**

**เหตุผล:** Graph API ตอบ HTTP 200 พร้อม **ตัดคีย์นั้นทิ้งทั้งก้อน** เมื่อซับฟิลด์ที่ขอไม่มีอยู่จริง
ผลลัพธ์หน้าตาเหมือน "ต้นทางไม่มีข้อมูล" เป๊ะ ๆ ทั้งที่จริงคือเราถามผิด

**เคสจริง 2026-07-30 → 08-07 (542 แถวบน prod):** `fetchThreadMessages` ขอ `attachments{type}`
แต่ message attachment **ไม่มีฟิลด์ `type`** (มีเฉพาะใน webhook payload ซึ่งเป็นคนละโครงสร้าง —
ชื่อพ้องกันพอดีเลยไม่มีใครเอะใจ) ฟิลด์จริงคือ `generic_template` / `image_data` / `video_data` /
`file_url` การ์ดโฆษณาและการ์ดปุ่มโทรจึงกลายเป็น placeholder
`[ข้อความจากระบบของ Facebook — เปิดดูใน Messenger]` มาตลอด 8 วัน

```
GET /{message-id}?fields=attachments{type}   → {"id":"m_SVa01…"}                    ← ไม่มี attachments เลย
GET /{message-id}?fields=attachments         → {"attachments":{"data":[{"generic_template":{…}}]}}
```

**สิ่งที่ทำให้เสียเวลาซ้ำสอง:** ตอนสืบสวน probe รอบแรกระบุซับฟิลด์ครบทุกตัว **ยกเว้น
`generic_template`** แล้วได้ก้อนว่างเหมือนเดิม จนเกือบสรุปผิดว่า "Meta ไม่เปิดเผยเนื้อหาการ์ด" —
คลาสความผิดพลาดเดียวกัน ลึกลงไปอีกหนึ่งชั้น

**วิธีที่ปลอดภัยกว่า:** ขอ `attachments` เปล่า ๆ — ต้นทางตัดฟิลด์ที่ไม่มีข้อมูลออกให้อยู่แล้ว
การระบุเองไม่ประหยัด bandwidth ที่วัดได้ แต่เปิดโอกาสพลาดคลาสนี้ทุกครั้งที่มีคนแก้

**วิธีตรวจว่าเคยพลาดมาก่อนหรือเปล่า:** อย่าดูแค่โค้ด ให้ query การกระจายค่าจริงจากฐาน —
ถ้า field หนึ่ง "มีค่าเดียวตลอดกาล" (`unknown` 45 ครั้ง ไม่มีค่าอื่นเลย) นั่นไม่ใช่ข้อมูลจริง
นั่นคือ default ที่ไม่มีใครเคยเขียนทับ

## 3. คอลัมน์ที่มีผู้เขียน 2 ราย

**กฎ:** คอลัมน์ที่ทั้งเราและ echo/webhook ของต้นทางเขียนได้ ต้องตอบให้ได้ว่า
**"ค่าที่หายไปจาก payload แปลว่า *ไม่รู้* หรือ *ถูกลบ*"** — ถ้าตอบไม่ได้ **ห้ามเขียน `null` ทับ**

**เคสจริง:** รีแอ็กชันบนข้อความโผล่ 1 วินาทีแล้วหาย เพราะ event ถัดมาที่ไม่มี field รีแอ็กชัน
ถูกตีความว่า "ถูกถอดรีแอ็กชัน" แล้วเขียน null ทับของที่เพิ่งเขียนไป

ดูเพิ่ม: `docs/conventions/stored-flag-vs-owner-truth.md` (ธงที่เก็บไว้ ≠ ความจริงปัจจุบัน)
และ memory `feedback_trace_feed_is_not_state`

## 4. ฟีเจอร์ที่ fail เงียบต้องมีเสียง

ทั้งสองเคสข้างบนอยู่ในโค้ดที่ออกแบบให้ **ล้มแล้วไม่ล้มทั้งระบบ** (backfill ล้ม = เห็นเท่าที่
webhook ให้, quote ล้ม = ไม่โชว์ราคา) ซึ่งถูกต้อง — แต่ "ไม่ล้มทั้งระบบ" ต้องไม่แปลว่า "ไม่มีใครรู้"

- ทางที่ fallback ไป placeholder / ค่าว่าง → `console.warn` พร้อม key ที่ได้รับจริง
- ตัวเลขที่ควรจะไม่เป็นศูนย์ (จำนวน attachment ที่ mirror ได้) → เก็บให้ query ย้อนหลังได้
- เทียบกับหน้าจอของต้นทางเอง (Business Suite / เว็บ iShip) เป็นระยะ — ผู้ใช้ทำแบบนี้อยู่แล้ว
  และเป็นคนเจอทั้งสองเคส
