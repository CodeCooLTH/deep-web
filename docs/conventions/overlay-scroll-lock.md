# Overlay ที่ประกอบเอง ต้องตรึง scroll เอง

> เหตุการณ์ 2026-08-07 — user รายงานพร้อมภาพ: เปิดแผงกดค้างในกล่องแชทบนมือถือแล้ว
> "มัน pull หรือ เลื่อนจอได้เฉยเลย" ฉากเบลอถูกดึงลงจนเห็นแถบขาวเหนือหัวแชท

## กฎ

**โมดัล/ชีต/เมนูเต็มจอที่เราประกอบเองด้วย React state ต้องเรียก `useLockBodyScroll`
(`src/hooks/useLockBodyScroll.ts`) เสมอ** — ตัวที่ขับด้วย Preline (`hs-overlay` + `data-hs-overlay`)
ไม่ต้อง เพราะ `HSOverlay.open()` สั่ง `document.body.style.overflow = 'hidden'` ให้อยู่แล้ว

```tsx
useLockBodyScroll(open)   // มี prop/state `open` และ component ถูก render ค้างไว้
useLockBodyScroll(true)   // parent render ใต้ `{open && <Sheet/>}` — mount = เปิดอยู่แล้ว
```

และ **ทุกกล่องที่มี `overflow-y-auto` ภายใน overlay ต้องมี `overscroll-contain` ติดไปด้วย**

## ทำไมถึงหายไปทั้งคลาสโดยไม่มีใครเห็น

โปรเจกต์นี้ "แปลง hs-overlay เป็น controlled div" เป็นแพตเทิร์นมาตรฐาน — เพราะ Preline พังเมื่อ
component re-render (ดู `feedback_filterdropdown_reusable`) คอมเมนต์ที่หัวไฟล์หลายใบเขียนเหตุผลนี้ไว้ตรง ๆ
แต่ **ไม่มีใบไหนสังเกตว่าการแปลงนั้นทิ้งการล็อก scroll ที่ Preline เคยให้ฟรีไปด้วย** ผลคือ overlay
ที่ประกอบเองทุกใบเกิดมาพร้อมช่องโหว่เดียวกันตั้งแต่วันแรก ไม่ใช่ของที่เคยทำงานแล้วพัง

ที่ไม่มีใครเห็นนานขนาดนี้เพราะบนเดสก์ท็อปแทบไม่มีอาการ: ล้อเมาส์เลื่อนพื้นหลังนิดหน่อยแล้วจบ
ส่วนบนมือถือมันคือการลากทั้งหน้าจนเนื้อหาหลุดกรอบ

## ทำไมต้องสั่ง 3 อย่าง ไม่ใช่อย่างเดียว

| สั่งอะไร | กันอะไร |
|---|---|
| `overflow:hidden` ที่ `<body>` | ท่ามาตรฐาน (และเป็นท่าที่ Preline ใช้) |
| `overflow:hidden` ที่ `<html>` ด้วย | iOS Safari เอาไม่อยู่ถ้าสั่งที่ `body` อย่างเดียว |
| `overscroll-behavior-y:none` ที่ `<html>` | iOS เด้งเอกสาร (rubber-band) ได้แม้หน้าไม่มีอะไรให้เลื่อน — **คนละกลไกกับ scroll chaining** จึงต้องสั่งแยก |

ไม่ใช้ท่า `position:fixed` ที่ `body` เพราะมันรีเซ็ตตำแหน่ง scroll ของหน้าเมื่อปิด overlay

## กับดักที่เจอจริงระหว่างแก้

- 🛑 **`touch-none` ที่ฉากเบลอกันได้เฉพาะนิ้วที่แตะฉากเบลอ** — นิ้วที่ลากอยู่บน "แผ่นคำสั่ง" ไม่ถูกกันเลย
  คอมเมนต์เดิมใน `ChatContextMenu.tsx` อธิบายไว้ถูกแล้วว่าทำไมต้องวาง `touch-none` ที่ฉากเบลอไม่ใช่ที่ตัวครอบ
  (เพื่อให้เลื่อน *ในแผง* ได้) แต่ไม่มีใครถามต่อว่า "แล้วอะไรกันการเลื่อนที่มาจากในแผง"
- 🛑 **overlay ที่ `createPortal` ไป `document.body` มีบรรพบุรุษที่รับ scroll ต่อเป็น `document` เอง**
  ไม่ใช่คอลัมน์ที่มันลอยทับอยู่ — คอลัมน์รายการแชทมี `overscroll-contain` มาตั้งแต่ 2026-07-23 แล้ว
  แต่ไม่เกี่ยวกันเลย เพราะ scroll chaining เดินตาม DOM tree ไม่ใช่ตำแหน่งบนจอ
- 🛑 **กล่อง `overflow-y-auto` ที่เนื้อหายังไม่ล้น ก็ยัง chain ออกไปข้างนอก** — บั๊กจึงเห็นชัดที่สุด
  ตอนเนื้อหา *สั้น* ซึ่งเป็นกรณีปกติ (ตรงข้ามกับที่คนมักเดา)
- 🛑 **`useLockBodyScroll(true)` ห้ามใช้กับ overlay ที่ซ่อนด้วย CSS breakpoint** (เช่น `sm:hidden`
  ใน `ExpenseCategoryFilterSheet.tsx`) — เปิดบนมือถือแล้วหมุนจอเป็นแนวนอน จะเหลือหน้าที่เลื่อนไม่ได้
  โดยไม่มีแผ่นให้เห็น = แย่กว่าบั๊กเดิม ให้ผูกกับ `matchMedia` แทน (idiom เดียวกับ `isSheet` ใน `EmojiPicker.tsx`)

## ที่ยกเว้นโดยตั้งใจ

- **โหมด popover/คลิกขวาบนเดสก์ท็อป** (`ChatContextMenu`, `MessageActionBubble` โหมด `point`) —
  ตั้งใจให้เลื่อนหน้าแล้ว *ปิดเมนู* ไม่ใช่ตรึงหน้า
- **`DraftOrderProvider`** — บนเดสก์ท็อปเป็นหน้าต่าง dock ขวาที่จงใจไม่บล็อกทั้งจอ (user request
  2026-07-24: "ให้อ่านแชทที่อยู่ข้างหลังได้") การตรึง scroll จะขัดเจตนานั้น
- **overlay ที่ขับด้วย Preline** — ได้จาก `HSOverlay.open()` อยู่แล้ว ใส่ซ้ำไม่ผิดแต่ไม่จำเป็น
