# "ข้อจำกัดที่รู้ตัว" กับ "ฟีเจอร์ที่ยังไม่เสร็จ" — แยกให้ออกก่อนบันทึกเป็นหนี้

> เคสจริง 2026-08-09→10: ทำให้ป้าย "ไม่สำเร็จ" ในหน้าประวัติตอบกลับคอมเมนต์บอกเหตุผลได้ (`6fdd85fd`)
> รายงานว่าเสร็จ พร้อมบันทึกข้อจำกัดไว้ท้ายรายงานเอง แล้ว user ถามกลับมาประโยคเดียวว่า
> *"มันต้องเก็บเหตุผลแยกกันป่าว — เพราะ reply ไม่ผ่าน อาจจะทักแชทได้ก็ได้"*
> ตรวจแล้วพบว่านั่นคือเคสที่ทำให้ฟีเจอร์ที่เพิ่ง ship **ไม่ทำงานเลย** ต้องแก้ตามใน `31c7053a`

---

## กฎ

🛑 **ก่อนบันทึกอะไรเป็น "ข้อจำกัดที่รู้ตัว / หนี้" ต้องไล่เคสของฟีเจอร์ที่เพิ่งทำทีละเคส แล้วตอบให้ได้
ว่าข้อจำกัดนั้นกินเคสไหนไปบ้าง**

- ถ้ามันกินเคสที่ **พบบ่อย** หรือกินเคสที่ฟีเจอร์นี้ถูกสร้างมาเพื่อแก้ → **นั่นไม่ใช่หนี้ นั่นคือ
  ฟีเจอร์ที่ยังไม่เสร็จ** ห้าม ship แล้วบอกว่าเสร็จ
- ถ้ามันกินเคสขอบที่เกิดยากและผู้ใช้ยังได้ประโยชน์เต็มในเส้นทางหลัก → เป็นหนี้ได้ บันทึกให้ชัดว่า
  **กินเคสไหน** ไม่ใช่แค่บอกว่า "มีข้อจำกัด"

🛑 **ห้ามใช้เหตุผล "ควรแยกรอบ / เป็นการเปลี่ยนพฤติกรรมฝั่งเขียน" กับข้อจำกัดที่ทำให้ของที่เพิ่ง ship
ไม่ทำงาน** — เหตุผลพวกนี้ฟังดูมีวินัย แต่มันตอบคำถามว่า *"งานนี้ใหญ่แค่ไหน"* ไม่ได้ตอบว่า
*"ของที่เพิ่งส่งมอบใช้ได้จริงไหม"*

## ทำไมการ "รู้ตัว" ไม่ช่วยอะไรเลย

ในเคสจริงข้างบน ผมเขียนข้อจำกัดนั้นไว้เองท้ายรายงาน คำต่อคำว่า

> "ถ้า 'ตอบใต้คอมเมนต์' ล้มเหลวแต่ 'ทักแชท' สำเร็จ โค้ดเดิมจะเขียน `errorMessage` เป็น null ทับ —
> เหตุผลของฝั่งสาธารณะหายไป ผมยังไม่แตะเพราะเป็นการเปลี่ยนพฤติกรรมฝั่งเขียนซึ่งควรแยกรอบ"

ข้อความนั้น **ถูกทุกตัวอักษร** แต่ไม่มีตรงไหนบอกว่าเคสนั้นเกิดบ่อยแค่ไหน และไม่มีตรงไหนเชื่อมกลับไป
ว่า *"แปลว่าฟีเจอร์ที่เพิ่งทำจะไม่แสดงอะไรเลยในเคสนั้น"* — การรู้ตัวโดยไม่ประเมินผลกระทบ
มีค่าเท่ากับการไม่รู้ ต่างกันแค่มีบรรทัดให้อ้างอิงตอนสืบย้อนหลัง

คลาสเดียวกับบทเรียนที่รีโปนี้เจอมาแล้ว: `external-payload-schema.md` — หัวไฟล์ `unlinked.ts` เขียน
ยอมรับเองว่าเดาการแมปฟิลด์ แล้วรับความเสี่ยงไว้ด้วยเหตุผลว่าผู้ใช้จะตรวจเอง ผลคือ 23 ออเดอร์บน prod
ถูกบันทึกที่อยู่สลับกันโดยไม่มีใครทัก

## เช็คลิสต์ก่อนเขียนคำว่า "หนี้" ในรายงาน

1. ฟีเจอร์นี้ถูกสร้างเพื่อแก้ปัญหาอะไร — ข้อจำกัดนี้กินปัญหานั้นไปกี่ %
2. เคสที่ข้อจำกัดกิน เกิดบ่อยแค่ไหนในข้อมูลจริง (ถ้าตอบไม่ได้ ให้ query ก่อน อย่าเดา)
3. ผู้ใช้ที่ตกอยู่ในเคสนั้น เห็นอะไรบนหน้าจอ — **เห็นของที่ผิด/ว่างเปล่า หรือแค่เห็นน้อยกว่าที่ควร**
   (เห็นว่างเปล่าโดยไม่มีคำอธิบาย = พอ ๆ กับก่อนทำฟีเจอร์)
4. ถ้าตอบข้อ 1-3 แล้วยังคิดว่าเป็นหนี้ ให้เขียนคำตอบทั้งสามข้อลงไปในรายงานด้วย ไม่ใช่เขียนแค่
   "มีข้อจำกัดเรื่อง X"
