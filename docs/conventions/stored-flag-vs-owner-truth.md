# ธงที่เก็บในแถวข้อมูล ≠ ความจริงปัจจุบันของเจ้าของแถว

> ที่มา: `docs/retro/2026-08-07-service-shipping-guard-and-chat-ui-retrospective.md`
> (ร้านบริการโดนบังคับกรอกที่อยู่จัดส่ง 2 รอบในวันเดียว)

## 1. กฎ

**คอลัมน์ที่เป็น "ธง" (`fulfillmentMode`, `isActive`, `requiresSlip`, …) คือภาพนิ่ง ณ เวลาที่มัน
ถูกเขียน ไม่ใช่ข้อเท็จจริงปัจจุบันของเจ้าของแถว** ก่อนใช้ธงเป็นเงื่อนไข ให้ถามว่า:

1. ธงนี้ถูกเขียนตอนไหน และ **เจ้าของแถวเปลี่ยนสถานะหลังจากนั้นได้ไหม**
   (ร้านเปลี่ยน `vertical` · แพ็กเกจหมดอายุ · ฟีเจอร์ถูกปิด)
2. มี **ตัวเขียนกี่ราย** และทุกรายเดินผ่าน SSOT เดียวกันหรือเปล่า

ถ้าคำตอบข้อ 1 คือ "เปลี่ยนได้" → ตัวตัดสินต้องเป็นสถานะปัจจุบันของเจ้าของ **ไม่ใช่ธงบนแถวลูก**

### เคสจริง (2026-08-07)

`Product.fulfillmentMode = 'SHIPPED'` ถูกใช้เป็นหลักฐานว่า "ออเดอร์นี้ต้องจัดส่ง" แต่ร้าน
`SERVICE_QUEUE` มีสินค้าติดธงนี้ได้ 2 ทาง — สร้างไว้ตอนยังเป็น `ONLINE_SALES` แล้วเปลี่ยนประเภท
ทีหลัง และ Quick-Create ที่เขียนคอลัมน์เอง — ผลคือร้านที่ไม่มีการจัดส่งเลยถูกบังคับกรอกที่อยู่
จนต้องเอาช่อง "บ้านเลขที่" ไปกรอกข้อความอื่นเพื่อให้ผ่าน validate

ตัวตัดสินที่ถูกคือ `shopShipsGoods(Shop.vertical)` (`src/lib/shipping-address-status.ts`) —
สถานะปัจจุบันของร้าน ไม่ใช่ธงบนสินค้า

## 2. กฎที่เป็น OR: ต้องกั้นที่ผลลัพธ์ ไม่ใช่ที่ operand เดียว

```ts
// เกณฑ์จริง
SHIPPED  ⟸  (รายการพิมพ์เอง ∧ type=PHYSICAL)  ∨  (มีสินค้าที่ธง=SHIPPED)
```

แพตช์รอบเช้าเติมด่านให้ operand ซ้ายอย่างเดียว → repro ที่ user รายงานหายจริง แต่ผลลัพธ์รวม
ไม่เปลี่ยนเลยเมื่อ operand ขวายิงแทน ผู้ใช้จึงเจอ **อาการเดิมเป๊ะ** อีกครั้งใน 2 ชั่วโมงครึ่ง

> **repro หาย ≠ กฎถูก** — หลังปิด operand หนึ่ง ให้ไล่ทุก operand ที่ประกอบเป็นค่าเดียวกัน
> และไล่ทุกทางเข้าที่คำนวณค่านั้น (`createOrder`, `updateOrder`, import, ฟอร์มฝั่งจอ)

## 3. ประกาศ SSOT ของคอลัมน์แล้ว ต้อง grep "ชื่อคอลัมน์" ไม่ใช่ "ชื่อฟังก์ชัน"

`resolveFulfillmentMode()` ถูกประกาศไว้ตั้งแต่ feature 00030 (BR-BKU-13) ว่าเป็นที่เดียวที่ตัดสิน
ค่านี้ พร้อมคอมเมนต์ว่า "ร้าน SERVICE_QUEUE → NO_SHIPPING เสมอ ไม่ว่า caller ส่งอะไรมา"

แต่ `order.service.ts` มี `tx.product.create({ … fulfillmentMode: … })` เขียนคอลัมน์ตรง ๆ 2 ที่
ซึ่ง **ไม่โผล่ในผลค้นหา `resolveFulfillmentMode`** เพราะไม่ได้เรียกมัน ตัวล็อกจึงล็อกได้เฉพาะคนที่
เดินผ่านประตู

**เช็คลิสต์เมื่อประกาศ SSOT ของคอลัมน์ใด:**

```bash
# ไม่ใช่แค่นี้
rg "resolveFulfillmentMode"
# ต้องอันนี้ด้วย — หาคนที่เขียนคอลัมน์ตรง ๆ
rg "fulfillmentMode:" src/ --glob '!*.test.*'
```

ทำครั้งเดียวตอนสร้าง SSOT และทำซ้ำทุกครั้งที่แก้กฎในนั้น

## 4. ข้อมูลที่ค้างอยู่แล้วต้องล้าง ไม่ใช่แค่ปิดทางเขียนใหม่

โค้ดที่แก้แล้วกันของใหม่ได้ แต่แถวที่ติดธงผิดอยู่แล้วยังเป็นกับดักรอเส้นทางอื่นที่อ่านคอลัมน์นั้น
ตรง ๆ (ฟอร์มแก้สินค้า, ปุ่มเปิดพัสดุ) → เขียน migration ล้างแบบ scope แคบและ idempotent
(`prisma/migrations/20260807150000_service_shop_products_no_shipping/`) และ **ไม่แตะข้อมูลประวัติ**
(ออเดอร์ที่ปิดไปแล้วคือหลักฐาน ไม่เขียนทับ)
