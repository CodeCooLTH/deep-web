# ชะตากรรมของค่าถูกตัดสินที่ "จุดเขียน" ไม่ใช่ "จุดส่ง"

> 🛑 **การเห็นว่าโค้ด *ส่ง* ค่าเข้าไป ไม่ใช่หลักฐานว่าค่านั้น *ถูกเก็บ*** — ตัวที่ตัดสินคือบรรทัดที่เขียนลงฐาน
> ซึ่งมักอยู่คนละฟังก์ชัน คนละไฟล์ และมักมีเงื่อนไขของตัวเองที่ทิ้งค่านั้นทันที
>
> และ 🛑 **ห้ามเขียนคำอ้างเรื่องพฤติกรรมของโค้ดลงเอกสาร/คอมมิต ก่อนเปิดดูบรรทัดที่บังคับมันจริง**

## เหตุการณ์ที่ทำให้เกิดกฎนี้ (2026-08-11 → user จับได้ 2026-08-12)

งาน "ส่งสรุปนัดหมายเข้าแชท" (ส่วนขยาย 00024) เขียน route ให้ส่งข้อความสรุปเข้าไปเป็น `body`:

```ts
// src/app/api/chat/conversations/[id]/messages/route.ts — จุดส่ง
body: type === "APPOINTMENT" ? (appointmentSummary?.text ?? null) : …
```

แล้วผมเขียนลงเอกสาร **3 ที่** (`AC-APS-20` ใน feature docs · `docs/SRS.md §7.14` · commit message) ว่า

> *"`text` ส่งเสมอทุกกรณี — เป็นทั้ง `ChatMessage.body` ที่ร้านเห็นและ**ค้นหาเจอ**ในประวัติ และทางถอย…"*

**ครึ่งหลังไม่จริงเลย** ตัวที่เขียนลงฐานทิ้งค่านั้นทันที ทั้งสองเส้นทาง:

```ts
// src/services/chat.service.ts (DEEP)
body: params.type === 'PRODUCT' || params.type === 'ORDER' ? null : (params.body ?? null),

// src/services/channel-chat.service.ts (LINE/Meta)
body: isOrder || isProductCard || attachment ? null : …
```

การ์ดสรุปนัดถูกเก็บเป็น `type='ORDER'` (มติที่ถูกและตั้งใจ — ไม่มี migration) ⇒ ตกเข้าเงื่อนไขนี้พอดี
**`body` เป็น `null` ทุกใบ ร้านค้นหาไม่เจอ** — และ `lastMessagePreview` ก็ตกไปใช้คำของออเดอร์
(`[ใบเสนอราคา]` / `[คำสั่งซื้อ]`) ซึ่งเป็นคำที่ผิดเรื่องสำหรับร้านคิวงาน

### ทำไมถึงหลุด

| ด่าน | ทำไมมองไม่เห็น |
|---|---|
| `tsc` / `build` | `body` เป็น `string \| null` ทั้งคู่ — ส่งค่าไปแล้วถูกทิ้งคือโปรแกรมที่ถูกต้องตามชนิดทุกตัวอักษร |
| เทส | เทสของงานนี้ตรวจ "route ส่ง `text` ออกไป" ซึ่ง**จริง** — ไม่มีตัวไหนตรวจ "แถวที่บันทึกมี `body`" |
| grep | คำว่า `body:` มีเป็นสิบจุดในไฟล์เดียว การเห็นว่ามีไม่ได้แปลว่าเห็นว่าอันไหนชนะ |
| การอ่านโค้ด | **ผมอ่านคอมเมนต์ที่อธิบาย *เจตนา* แล้วเชื่อ** — คอมเมนต์เหนือบรรทัดที่ทิ้งค่าเขียนว่า "กันร้านเห็นการ์ดซ้อนข้อความดิบ" ซึ่งอ่านเหมือนคำอธิบาย ไม่ใช่คำเตือนว่าค่าจะหาย |

**ที่แพงที่สุดคือเอกสาร** — โค้ดที่ผิดมีวันถูกจับได้ตอนใครสักคนใช้งาน แต่เอกสารที่โกหกจะถูกอ่านเป็นข้อเท็จจริง
โดยคนถัดไปที่ไม่มีเหตุผลจะสงสัย แล้วเขาจะสร้างของบนสมมติฐานนั้นต่อ (คลาสเดียวกับ
`docs-claimed-constraint-verify-in-code.md` แต่ **ทิศกลับ**: อันนั้นคือ *เชื่อเอกสารที่คนอื่นเขียน*
อันนี้คือ *ผลิตเอกสารที่โกหกด้วยตัวเอง*)

## กฎ

**1. ก่อนเขียนว่า "ค่านี้ถูกเก็บ / ถูกส่ง / ถูกแสดง" — ตามไปที่บรรทัดที่ทำสิ่งนั้นจริง**

```bash
# ไล่จาก "จุดส่ง" ไปหา "จุดเขียน" — ตัวที่ตัดสินคือ create/update ไม่ใช่ตัวที่ประกอบ params
rg -n "prisma\.<model>\.(create|update|upsert)" -A 25 src/services/ | rg -n "<ชื่อฟิลด์>:"
```

ดูให้ครบ **ทุกเส้นทาง** — ในรีโปนี้ข้อความมี 2 เส้นทางที่ไม่เรียกหากัน (`chat.service.sendMessage`
สำหรับ DEEP · `channel-chat.service.sendOutboundMessage` สำหรับช่องทางนอก) การตรวจเส้นเดียวแล้ว
สรุปทั้งระบบคือความผิดพลาดที่เกิดซ้ำได้ง่ายที่สุด

**2. `type` ที่ reuse ของเดิม = สืบทอดกฎของเดิมทั้งชุด ไม่ใช่แค่ตัวเรนเดอร์**

การเลือกเก็บของใหม่ทับชนิดเดิม (ที่นี่: สรุปนัด → `type='ORDER'`) เป็นมติที่ดี แต่มันแปลว่า
**ทุกเงื่อนไขที่เขียนว่า `type === 'ORDER'` ทั่วทั้งโปรเจกต์กลายเป็นกฎของของใหม่ทันที** —
ต้องไล่ให้ครบก่อนตัดสิน ไม่ใช่แค่จุดที่เราตั้งใจใช้ประโยชน์

```bash
rg -n "=== 'ORDER'|=== \"ORDER\"|isOrder" src/services/ src/app/
```

**3. คำที่ควรจุดชนวนให้ไปเช็คก่อนเขียนลงเอกสาร**

**"ถูกเก็บ" · "ค้นหาเจอ" · "แสดงใน…" · "ส่งเสมอ" · "อัปเดตตามเอง"** — ทุกคำนี้เป็นคำอ้าง
เกี่ยวกับพฤติกรรมที่มีบรรทัดใดบรรทัดหนึ่งบังคับอยู่ ถ้าชี้บรรทัดนั้นไม่ได้ ห้ามเขียน

**4. ถ้าจะอ้างในคอมมิต ให้เทสอ้างด้วย**

คำอ้างที่ไม่มีเทสผูกคือคำอ้างที่จะกลายเป็นเท็จวันไหนก็ได้โดยไม่มีใครรู้ — เทสไม่ต้องใหญ่
แค่ยืนยัน "แถวที่ถูกสร้างมีค่านั้นจริง" ก็พอ
