# ศัพท์ธุรกิจต้องมีนิยามเดียว — และนิยามที่ชนกันมักอยู่ในไฟล์ที่คุณเพิ่ง import

> เหตุการณ์จริง 2026-08-08 (feature 00016 ส่วนขยาย) — `/impeccable critique` จัดเป็น **P0**
> ดู `docs/retro/2026-08-08-product-cost-00016-ext-retrospective.md` §P-1

## สิ่งที่เกิดขึ้น

การ์ดกำไรรายออเดอร์คำนวณ `totalAmount − Σ(cost×qty)` แล้วเรียกตัวเองว่า **"กำไรจากใบนี้"**

ปัญหา: `totalAmount` **รวม VAT** และสูตรนี้ **ไม่หักค่าใช้จ่ายเลย** ขณะที่ระบบมีนิยามของคำว่า "กำไร" อยู่แล้ว

```ts
// src/lib/format-money.ts:50
export const NET_PROFIT_FORMULA = 'กำไรสุทธิ = ยอดขายที่ยืนยันแล้ว − ต้นทุนสินค้า − ค่าใช้จ่าย'
```

และไฟล์นั้นคือ **ไฟล์เดียวกับที่การ์ดนี้ `import { formatBaht }` มาใช้** — ระยะห่างทางสายตาเป็นศูนย์ แต่ไม่มีใครมอง

**ผลกับผู้ใช้:** ผู้ขายที่บวก "กำไรรายใบ" ทั้งเดือนแล้วเทียบกับ "กำไรสุทธิ" ที่ `/sales` จะได้เลขไม่ตรงเสมอ และไม่มีทางรู้ว่าใครผิด · ร้านที่จด VAT เห็นกำไรพองตาม VAT ที่ไม่ใช่เงินตัวเอง

🛑 **คนที่จะเจอปัญหานี้ก่อน คือคนที่เริ่มเชื่อฟีเจอร์มากพอจะเอาไปตรวจสอบ** — เป็นการทำลายความเชื่อถือในจังหวะที่แย่ที่สุด

## ทำไมไม่มีชั้นไหนจับได้

| ชั้น | ทำไมมองไม่เห็น |
|---|---|
| `tsc` | ทั้งสองฝั่งเป็น `number`/`string` ถูกต้อง |
| `next build` | ไม่เกี่ยวกับความหมาย |
| impeccable detector | ตรวจ class/markup ไม่ตรวจ semantics |
| `theme-guard.sh` | ตรวจ pattern ของ Tailwind |
| grep | ไม่มีสตริงผิดให้ค้น — ทั้งสองนิยาม "ถูก" ในตัวเอง |

**ทุก gate ของโปรเจกต์ตรวจ "รูปแบบ" ไม่มีอันไหนตรวจ "ความหมาย"** — คำถามว่า *"คำนี้แปลว่าอะไรในระบบนี้"* ไม่ใช่สิ่งที่ regex ตอบได้

## กฎ

### ก่อนนิยามสูตร/ค่าคงที่ที่เป็นศัพท์ธุรกิจ ต้องทำ 2 อย่าง

ครอบคำเหล่านี้เป็นอย่างน้อย: **กำไร · ยอดขาย · รายได้ · ต้นทุน · ส่วนลด · ค่าธรรมเนียม · ยอดรวม · คงเหลือ · ยอดค้าง**

```bash
# 1. หานิยามเดิมทั้งโปรเจกต์
rg -n "FORMULA|_TOTAL|_AMOUNT" src/lib/ src/services/
rg -n "กำไร|ยอดขาย|ต้นทุน" src/lib/ --glob '*.ts'

# 2. เปิดไฟล์ที่กำลังจะ import อ่านให้จบ ไม่ใช่แค่ดูว่ามีฟังก์ชันที่ต้องการไหม
```

### ถ้ามีนิยามเดิมอยู่แล้ว และของใหม่ต่างจริง

1. **ตั้งชื่อที่ต่างกันชัดในตัวเอง** — `GROSS_PROFIT_FORMULA` vs `NET_PROFIT_FORMULA` ไม่ใช่ `PROFIT_FORMULA` กับ `PROFIT_FORMULA_2`
2. **วางไว้ติดกันในไฟล์เดียวกัน** — คนที่มาแก้ทีหลังต้องเห็นทั้งคู่พร้อมกันโดยไม่ต้องหา
3. **เขียนคอมเมนต์บอกว่าต่างกันตรงไหน และผลรวมของสองอันจะไม่เท่ากันเพราะอะไร**
4. **หน้าจอต้องบอกผู้ใช้ด้วย** — ไม่ใช่แค่คอมเมนต์ในโค้ด ผู้ใช้ที่เอาไปบวกเทียบต้องเห็นเองว่าคนละตัว

ตัวอย่างที่ทำแล้ว (`src/lib/format-money.ts` หลัง `a247cf0a`):

```ts
export const NET_PROFIT_FORMULA = 'กำไรสุทธิ = ยอดขายที่ยืนยันแล้ว − ต้นทุนสินค้า − ค่าใช้จ่าย'

/**
 * นิยามของกำไร **ขั้นต้น** — คนละตัวกับกำไรสุทธิข้างบน วางติดกันโดยตั้งใจ
 * ต่างกัน 2 อย่าง: (1) คิดจากยอดที่ลูกค้าจ่ายจริงของใบนั้น (มี VAT ก็รวมอยู่)
 * (2) ยังไม่หักค่าใช้จ่ายร้านเลยสักบาท
 * ผลคือเอากำไรขั้นต้นรายใบมาบวกกันทั้งเดือน จะ **ไม่เท่า** กำไรสุทธิที่ /sales เสมอ
 * และนั่นถูกต้องแล้ว — แต่ต้องบอกผู้ใช้ ไม่ใช่ปล่อยให้เขาไปเจอเองแล้วสรุปว่าระบบคิดผิด
 */
export const GROSS_PROFIT_FORMULA = 'กำไรขั้นต้น = ยอดที่ลูกค้าจ่าย − ต้นทุนสินค้า · ยังไม่หักค่าใช้จ่ายร้าน'
```

### สำหรับคนเขียน SRS/SDS

**ห้ามนิยามสูตรใน SRS โดยไม่เปิดโค้ดที่มีอยู่ก่อน** — รอบนี้สูตรถูกเขียนลง SRS §11.2 อย่างละเอียด (รวมถึงเรื่องปัดเศษและการข้าม `cost=null`) แต่ไม่มีบรรทัดไหนถามว่า *"ระบบเรียกสิ่งนี้ว่าอะไรอยู่แล้ว"*

## ทิศกลับ — เอกสารประกาศข้อจำกัดที่โค้ดไม่เคยมี

> เหตุการณ์จริง 2026-08-08 รอบสอง · `docs/retro/2026-08-08-line-cost-at-order-entry-retrospective.md` §P-2

หัวข้อข้างบนคือ "โค้ดนิยามศัพท์ชนกับนิยามที่มีอยู่" — ทิศกลับอันตรายกว่าเพราะจับไม่ได้เลย:

`safepay-product` ล็อกมติว่า *"ห้ามให้กรอกต้นทุนตอนแก้ไขออเดอร์ เพราะขัด D-5 ที่ว่า snapshot เกิดตอนสร้างเท่านั้น"* โดยอ้าง FR-EXP-02 ที่เขียนคำว่า **"เท่านั้น"** ไว้จริง

แต่ `updateOrder` **re-snapshot อยู่แล้ว** — คอมเมนต์ในโค้ดเขียนเองว่า `// 5) cost snapshot (เหมือน createOrder)` และ `PATCH /api/orders/[token]` ก็ validate ด้วย `CreateOrderSchema` ตัวเดียวกับตอนสร้าง

**เอกสารบันทึก *เจตนา* ตอนออกแบบ แล้วถูกอ่านเป็น *ข้อเท็จจริง* ตอน implement** — ไม่มีใครกลับมาแก้คำว่า "เท่านั้น" เมื่อโค้ดถูกเขียนต่างออกไปในรอบเดียวกัน

### ทำไมคลาสนี้อันตรายกว่า

**ข้อจำกัดปลอมทำให้เรา *ไม่* เขียนโค้ด — จึงไม่มีอะไรให้เทสจับ ไม่มีอะไรพัง ไม่มีใครรายงาน** มันอยู่ต่อไปเรื่อย ๆ จนกว่าจะมีคนบังเอิญเปิดโค้ดดู (รอบนี้เจอเพราะบังเอิญไปแตะ ไม่ได้ไล่หา)

ผลถ้าไม่จับได้: ซ่อนช่องกรอกในหน้าแก้ไข ทั้งที่ระบบเขียนทับค่าอยู่ดี = ผู้ขายแก้ไม่ได้โดยไม่ได้ป้องกันอะไรเลย · และพลาดทางแก้ที่ใช้ได้ทันที (ออเดอร์ PENDING เปิดแล้วบันทึกใหม่ ได้ต้นทุนเลย)

### กฎ

🛑 **ข้อความในเอกสารที่อ้างพฤติกรรมของโค้ด ต้องยืนยันกับโค้ดก่อนใช้ตัดสินใจ — โดยเฉพาะเมื่อถูกใช้เป็นเหตุผลที่จะ "ไม่ทำ" อะไร**

```bash
# เอกสาร/agent อ้างว่า "ระบบทำ X เท่านั้น / ห้าม Y" → เปิดฟังก์ชันที่เกี่ยวข้องอ่านจริงก่อนเชื่อ
rg -n "ชื่อฟังก์ชันที่เกี่ยวข้อง" src/services/ src/app/api/
```

คำที่ควรจุดชนวนให้ไปเช็ค: **"เท่านั้น" · "ห้าม" · "ไม่สามารถ" · "โดยธรรมชาติ" · "อยู่แล้ว"** — คำพวกนี้เป็นการอ้างข้อเท็จจริงเกี่ยวกับระบบ ไม่ใช่การอธิบายเจตนา

**สำหรับ prompt ที่ส่งให้ agent เขียนเอกสาร:** สั่งให้ยืนยันข้อจำกัดที่เอกสารอ้างกับโค้ดก่อนล็อกเป็นมติเสมอ — agent ที่ถูกส่งไปเขียนเอกสารจะอ่านเอกสารเป็นแหล่งความจริงโดยธรรมชาติ

## หนี้ที่รู้ตัวแล้วยังไม่แก้ (ห้ามลบออกจนกว่าจะปิด)

### D-1 · คำเรียกการ์ดออเดอร์ในรายการแชท ไม่ตรงกัน 2 เส้นทาง (พบ 2026-08-12)

ของสิ่งเดียวกัน — ข้อความ `type='ORDER'` — ขึ้นในกล่องขาเข้าคนละคำตามว่าถูกส่งทางไหน:

| เส้นทาง | ไฟล์ | คำที่ขึ้น |
|---|---|---|
| DEEP | `src/services/chat.service.ts` (`const preview`) | `[ใบเสนอราคา]` |
| LINE / Messenger / IG | `src/services/channel-chat.service.ts` (`const preview = isOrder ? …`) | `[คำสั่งซื้อ]` |

ผู้ขายที่ดูรายการแชทรวมทุกช่องทางจะเห็นสองคำนี้ปนกันในจอเดียว โดยที่มันคือของชนิดเดียวกัน

**ทำไมยังไม่แก้ (user เคาะ 2026-08-12):** เป็นหนี้ที่มีอยู่ก่อนงานที่กำลังทำ และการรวมคำกระทบ
ร้านที่ขายของทุกร้าน ควรเป็นรอบของตัวเอง ไม่ใช่แถมมากับงานอื่น

🛑 **ก่อนแก้ต้องตอบให้ได้ก่อนว่าคำไหนถูก** — `[ใบเสนอราคา]` กับ `[คำสั่งซื้อ]` ไม่ใช่คำพ้อง:
ใบเสนอราคาคือของที่ยังไม่ตกลง ส่วนคำสั่งซื้อคือตกลงแล้ว การ์ดใบเดียวกันถูกใช้ทั้งสองความหมาย
(ดู `ORDER_VOCAB` ซึ่งผันคำตาม `Shop.vertical` อยู่แล้ว — คำตอบน่าจะอยู่ตรงนั้น ไม่ใช่การเลือกคำใดคำหนึ่งมาใช้ทั้งระบบ)

**ที่เกี่ยวข้อง:** ตั้งแต่ 2026-08-11 การ์ด "สรุปนัดหมาย" ของร้านคิวงานก็ถูกเก็บเป็น `type='ORDER'`
ด้วย ⇒ ตกเข้าคำทั้งสองนี้เหมือนกัน (กำลังแก้แยกให้ได้คำของตัวเอง — ดู retro 2026-08-12)
