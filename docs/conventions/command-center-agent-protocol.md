> SSOT ของ **ป้ายและ comment ส่งต่อ** ระหว่าง subagent 6 ขั้น
> ผูกกับ `docs/20 - Features/00049 - AI Command Center/` (FR-CC-03/04/05, TFR-CC-03/04/05, SDS TD-002)

## 1. 🛑 ใครเป็นคนเขียน GitHub — ข้อเท็จจริงที่กำหนดทั้งโปรโตคอล

**ไม่มี subagent ตัวไหนยิง `gh` เลย — Controller เป็นคนโพสต์ comment และย้ายป้ายทั้งหมด**

เหตุผลไม่ใช่ความชอบ แต่มาจากสิ่งที่ตรวจได้จาก `.claude/agents/*.md` เอง:

| ขั้น | ป้าย | agent | มี `Bash` ไหม |
|---|---|---|---|
| ① วางแผน | `stage:plan` | `safepay-planner` | ❌ **ไม่มี** |
| ② ออกแบบ UX | `stage:ux` | `safepay-ux` | ❌ **ไม่มี** |
| ③ เขียนโค้ด | `stage:build` | `safepay-developer` | ✅ มี |
| ④ รีวิว | `stage:review` | `safepay-reviewer` | ✅ มี |
| ⑤ QA | `stage:qa` | `safepay-qa` | ✅ มี |
| ⑥ sync เอกสาร | `stage:docs` | `safepay-docs` | ❌ **ไม่มี** |
| ⑦ รอเคาะ | `stage:ready` | — (ไม่มี agent · รอ user) | — |

**3 ใน 6 ตัวเขียน GitHub ไม่ได้อยู่แล้ว** (ไม่มี Bash ⇒ เรียก `gh` ไม่ได้) ถ้าปล่อยให้อีก 3 ตัวที่มี Bash
ทำเอง จะได้ระบบที่ป้ายถูกเขียนจาก **2 เส้นทางที่ไม่รู้จักกัน** — คลาสเดียวกับ HR16 และ
`value-fate-decided-at-write-site.md` และยังเปิดช่องให้ agent แตะ GitHub state ตรง ๆ ซึ่งขัดเจตนา
ของ D-1/FR-CC-06 (agent เปิด PR ได้อย่างเดียว)

⇒ **agent ทุกตัวมีหน้าที่เดียว: คืน "บล็อกส่งต่อ" ในรายงานของตัวเอง** Controller อ่านแล้วเขียนให้

🛑 กฎนี้ครอบ `gh` ด้วย ไม่ใช่แค่ `git` — ข้อ 4 ของ `safepay-developer` (git scope ban) และข้อห้าม
เดียวกันใน `safepay-reviewer`/`safepay-qa` ให้อ่านว่าครอบ **ทุกคำสั่งที่เปลี่ยนสถานะบน GitHub**

## 2. บล็อกส่งต่อ (handoff block)

ทุก agent ต้องปิดรายงานด้วยบล็อกนี้ **ตัวอักษรตรงเป๊ะ** เพื่อให้ Controller ตัดออกมาได้โดยไม่ต้องเดา:

```
=== DEEP-HANDOFF ===
ใบงาน: #41
ขั้นนี้: stage:review
ผลลัพธ์: ผ่าน
ป้ายถัดไป: stage:qa
สรุปผล:
- <สิ่งที่ทำ/ตรวจ จริง ไม่ใช่สิ่งที่ตั้งใจจะทำ>
ไฟล์ที่ต้องแตะ:
- src/services/command-center.service.ts
ข้อควรระวังสำหรับขั้นถัดไป:
- <กับดักที่ขั้นถัดไปจะเจอ ถ้าไม่มีให้เขียน "ไม่มี">
=== จบ ===
```

**4 หัวข้อบังคับ** (`สรุปผล` · `ไฟล์ที่ต้องแตะ` · `ข้อควรระวังสำหรับขั้นถัดไป` · `ป้ายถัดไป`)
มาจาก FR-CC-03 AC-03-1 ตรงตัว — ขาดหัวข้อไหน Controller ต้องตีกลับให้เขียนใหม่ ไม่ใช่เติมให้เอง

`ผลลัพธ์` มี 3 ค่าเท่านั้น: **`ผ่าน`** (ส่งต่อขั้นถัดไป) · **`ตีกลับ`** (กลับ `stage:build`) ·
**`ติดขัด`** (ทำต่อไม่ได้ ต้องให้คนตัดสิน — Controller คงป้ายเดิมไว้แล้วรายงาน user)

### หัวข้อเพิ่มตามขั้น

| ขั้น | หัวข้อบังคับเพิ่ม | ผูกกับ |
|---|---|---|
| ① วางแผน | `ต้องผ่านขั้น UX:` `ใช่`/`ไม่` + **รายการ path ที่ใช้ตัดสิน** | FR-CC-04 AC-04-1 |
| ② UX | `Theme Source:` ชี้ `theme/...` ที่ copy | FR-CC-03 AC-03-2 · HR1/HR3 |
| ③ เขียนโค้ด | `PR:` เลข PR ที่เปิด | SDS TD-002 |
| ④⑤ ตีกลับ | `เหตุผลที่ตีกลับ:` (ห้ามว่าง) | FR-CC-05 AC-05-1 |

## 3. 🛑 ลำดับที่ห้ามสลับ — comment ก่อน ป้ายทีหลัง

FR-CC-03 AC-03-3 เขียนว่า *"ป้ายเปลี่ยนไปขั้นถัดไปได้ก็ต่อเมื่อ comment สรุปผลถูกเขียนแล้วเท่านั้น"*

Controller ทำตามลำดับนี้เสมอ:

1. อ่านบล็อกส่งต่อจากรายงานของ agent — **ไม่ครบ 4 หัวข้อ → หยุด ไม่ย้ายป้าย**
2. `gh issue comment <n> --body-file -` (หรือ `gh pr comment`) — **ต้องสำเร็จก่อน**
3. ลบป้าย `stage:*` ทุกตัวออก แล้วค่อยเพิ่มป้ายถัดไป

🛑 **comment ล้ม = ไม่ย้ายป้าย** ใบงานค้างอยู่ขั้นเดิมและยังเห็นบนบอร์ด
ซึ่งดีกว่าใบงานที่ป้ายเดินหน้าไปแล้วแต่ไม่มีหลักฐานว่าขั้นก่อนทำอะไร (ขั้นถัดไปจะเริ่มด้วยการเดา)

🛑 **1 ใบมีป้าย `stage:*` ได้ตัวเดียวเสมอ** — ต้อง *ลบของเดิมออกก่อน* ไม่ใช่เพิ่มทับ
ไม่งั้นใบเดียวจะโผล่ 2 คอลัมน์บนบอร์ด (bucket ของ `GET /board` วนจาก `.labels[]` ทุกตัว)

## 4. 🛑 ป้ายย้ายจาก Issue ไป PR ตอนขั้น ③ (SDS TD-002)

- ใบงานเกิดเป็น **Issue** พร้อม `stage:plan` (`POST /tasks`)
- ขั้น ①→② อยู่ที่ Issue
- **ขั้น ③ เมื่อ developer เปิด PR:** Controller **ลบ `stage:*` ออกจาก Issue** แล้ว **เพิ่ม `stage:build` ที่ PR**
- ขั้น ④⑤⑥⑦ อยู่ที่ PR ทั้งหมด
- PR body **ต้องมี `Closes #NN`** — เป็นเส้นเดียวที่ผูก PR กลับไปหา Issue ต้นทาง

**เหตุผล:** `auto-merge.yml` อ่านป้าย `พร้อมขึ้น` จาก **PR เท่านั้น** (`gh pr list --json labels`)
ไม่เคยอ่านจาก issue เลย ⇒ ให้ป้ายอยู่กับ artifact จริงของขั้นนั้น และไม่ต้องเก็บ mapping แยก

## 5. ขั้น ⑥ จบแล้วไปไหน — `stage:ready`

`safepay-docs` เสร็จ → Controller ย้ายป้ายเป็น **`stage:ready`** แล้ว**หยุด**

🛑 **ห้าม agent หรือ Controller ติดป้าย `พร้อมขึ้น` เด็ดขาด** (FR-CC-11/BR-CC-06) — ป้ายนั้นปรากฏได้
2 ทางเท่านั้น: ปุ่มบนจอ Command Center หรือ user ติดเองบน GitHub **นี่คือประตูอนุมัติเดียวของทั้งระบบ**
และเป็นสิ่งเดียวที่กั้นระหว่าง "โค้ดที่ agent เขียน" กับ "prod"

`stage:ready` มีอยู่เพราะถ้าไม่มี ใบที่จบขั้น docs จะ **หายจากบอร์ด** (ไม่มี `stage:*` = ไม่ถูก bucket)
หรือค้างคอลัมน์ "เอกสาร" ทั้งที่ทำเสร็จแล้ว — user จะไม่มีทางรู้ว่ามีอะไรรอตัวเองอยู่

คอลัมน์ "รอเคาะ" บนบอร์ดจึงถือ **2 สถานะ**: `stage:ready` (รอ user กด) และ `พร้อมขึ้น` (กดแล้ว รอ merge)

## 6. ขั้น ② ข้ามได้เมื่อไหร่ (FR-CC-04)

**`safepay-planner` เป็นคนตัดสินคนเดียว** ตอนเขียนบล็อกส่งต่อของขั้น ① — ขั้นเขียนโค้ดไม่มีสิทธิ์ตัดสินเอง

🛑 **ต้องผ่านขั้น UX เสมอ ถ้างานแตะ path ใดต่อไปนี้แม้แต่ไฟล์เดียว** (HR8 — ไม่มีข้อยกเว้น):

```
src/app/(marketing)/**   src/app/(paces)/**   src/components/**   src/views/**
src/@core/**   src/@layouts/**   *.css
```

งาน backend ล้วน (`src/services/**`, `src/lib/**`, `src/app/api/**`, `prisma/**`, `docs/**`) ข้ามได้

⚠️ **ยังไม่มีด่านอัตโนมัติบังคับข้อนี้** (SRS §8 R-3) — ถ้า planner ตัดสินผิด ระบบจะไม่ฟ้อง
ผู้ที่เห็นก่อนคือ `safepay-reviewer` ขั้น ④ ซึ่งต้องตีกลับเมื่อเจองาน UI ที่ไม่เคยผ่านขั้น ②

## 7. ตีกลับ (FR-CC-05)

`safepay-reviewer` (④) และ `safepay-qa` (⑤) ตีกลับได้ → ป้ายกลับไป **`stage:build`**

- ต้องมี `เหตุผลที่ตีกลับ:` ในบล็อกส่งต่อ **ห้ามว่าง** และต้องบอก *สิ่งที่ต้องแก้* ไม่ใช่แค่ *สิ่งที่ผิด*
- Controller โพสต์ comment ก่อน แล้วค่อยย้ายป้าย (ข้อ 3)
- ใบที่ถูกตีกลับแล้วไม่มีใครรับต่อ **ค้างที่ `stage:build` — ห้ามลบป้ายทิ้ง** (AC-05-2)
  งานที่หายจากบอร์ดคืองานที่ไม่มีใครรู้ว่ายังไม่เสร็จ
