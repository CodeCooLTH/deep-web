# ดักซ้ำด้วยการปล่อยให้ชน = ERROR ใน log ทุกใบ

> เหตุการณ์จริง 2026-08-10 — `2ca467dd`
> user ส่งภาพ log Supabase มาถามว่า "มัน error อะไร"

## สิ่งที่เกิดขึ้น

log ของ Supabase มีบรรทัดนี้ไหลทุก 10–30 วินาที:

```
23505  duplicate key value violates unique constraint "ChatMessage_externalMessageId_key"
```

หน้าตาเหมือนระบบแชทพังหนัก แต่ความจริงคือ **ตัวกันข้อความซ้ำที่ทำงานถูกต้อง 100%**

`ChatMessage.externalMessageId` เป็น `@unique` เพื่อ idempotency ของข้อความจาก Meta และโค้ดใช้วิธี
**insert ไปก่อน แล้วดักตอนชน** (`isUniqueViolationOn` ใน `channel-chat.service.ts`) ไม่ได้ SELECT
เช็คก่อน

ลำดับของขาออกคือ **ส่งก่อน → ได้ `mid` → ค่อยเขียน DB** (จงใจ ไม่งั้นจะได้ 2 แถว) แปลว่า
**ทุกข้อความที่ร้านส่งจาก Deep จะมี echo ที่ `mid` เดียวกันเด้งกลับเข้า `ingestInboundMessage` แน่นอน
ทุกใบ** → ชน → 23505 หนึ่งบรรทัด ต่อข้อความหนึ่งใบ

## ทำไมไม่มีอะไรฟ้อง (และทำไมมันดังตลอด)

**Postgres เขียน ERROR ลง log ทุก constraint violation ไม่สนว่าแอปดักด้วย try/catch แล้ว** — ฝั่งแอป
คืน `{status:'DUPLICATE'}` ตอบ 200 ให้ Meta เรียบร้อย ไม่มี 500 ไม่มีข้อความหาย แต่ฝั่งฐานข้อมูล
บันทึกว่าเป็น error ทุกครั้ง

จำนวนบรรทัดใน log จึงเท่ากับ **ปริมาณงานที่สำเร็จ** ไม่ใช่ปริมาณงานที่ล้ม

## "ไม่ใช่บั๊ก" ไม่ได้แปลว่า "ไม่ต้องแก้"

ทางเดิมจ่ายของจริงทุกใบก่อนจะไปล้ม:

| | ก่อน | หลัง |
|---|---|---|
| echo ที่ชน | `externalContact.upsert` (**write**) + ทรานแซกชัน + INSERT ที่ล้ม + ROLLBACK + **dead tuple ให้ autovacuum ตามเก็บ** + 1 บรรทัดใน log | **1 SELECT** |
| ข้อความใหม่จริง | — | **+1 SELECT** บน unique index ที่มีอยู่แล้ว |

INSERT ที่ล้มด้วย unique violation **เขียน tuple + index entry ลงไปจริงก่อนถูก rollback** — กลายเป็น
dead tuple ที่ autovacuum ต้องตามเก็บทีหลัง ต้นทุนนี้ไม่โผล่ในกราฟตอนเกิด แต่มาโผล่เป็นงาน vacuum
และ index ที่บวมขึ้น

หลังแก้ log เงียบสนิท (user ยืนยันเอง: "หายไปหมดเลย")

## กติกา

**1. เห็น ERROR ไหลใน log ฐานข้อมูล → ถามก่อนว่า "โค้ดดักมันไว้หรือเปล่า"**
ถ้ามี catch ครอบอยู่ = กลไกทำงาน ให้ย้ายไปประเมินที่ **ต้นทุน** แทน **ความถูกต้อง** อย่ารีบสรุปว่าพัง
แล้วไล่แก้สิ่งที่ไม่ได้เสีย

**2. เพิ่ม pre-check ได้ แต่ห้ามถอดตัวดักเดิม**
race ระหว่าง SELECT กับ INSERT ยังเกิดได้จริง — **ความถูกต้องต้องอยู่ที่ `@unique` เสมอ** pre-check
เป็นแค่ทางลัดของเคสที่รู้ผลล่วงหน้าอยู่แล้ว ไม่ใช่ตัวกันซ้ำตัวใหม่ ถ้าถอด catch ทิ้งเมื่อไหร่ =
เปลี่ยนจาก log รก เป็น 500 ตอนคนทักรัว ๆ

**3. จุดวาง pre-check สำคัญกว่าตัว pre-check**
ต้องอยู่ **หลัง** ทุก branch ที่ใช้ id เดิมโดยตั้งใจ — `is_deleted` (unsend) ส่ง `mid` ของข้อความที่
**มีอยู่แล้ว** มาเป็นเรื่องปกติ ถ้าวาง pre-check ไว้ก่อนสาขานั้น ข้อความที่ลูกค้ากดลบจะค้างในเธรด
ตลอดไปโดยไม่มีอะไรฟ้องเลย (ตรึงด้วยเทสไว้แล้วใน `channel-chat-ingest.test.ts`)

**4. อย่าไล่แก้ทุกที่ที่มีแพตเทิร์นเดียวกัน — ดูอัตราการชนจริงก่อน**
LINE ใช้ insert-then-catch เหมือนกันเป๊ะ แต่ `capabilities.echo=false` (LINE ไม่ echo ข้อความที่เรา
ยิงออก) การชนจึงเกิดเฉพาะตอน redelivery ซึ่งนาน ๆ ครั้ง — ไม่ใช่ต้นเหตุของ log ที่เห็น และไม่คุ้ม
ที่จะจ่าย SELECT เพิ่มให้ทุก event

## ที่มาของอาการแบบนี้โดยทั่วไป

แพตเทิร์น "ให้ฐานข้อมูลเป็นคนตัดสินว่าซ้ำ" ถูกและปลอดภัยกว่าเช็คเองเสมอในแง่ correctness — แต่มันแลก
มาด้วยการที่ **ทุกครั้งที่มันทำงาน จะถูกบันทึกเป็นความล้มเหลว** ซึ่งกลบสัญญาณของ error จริงใน log
จนหาไม่เจอ ถ้าอัตราการชนสูงพอที่จะกลบ ให้เติม pre-check; ถ้าต่ำ ปล่อยไว้แบบเดิมดีกว่า
