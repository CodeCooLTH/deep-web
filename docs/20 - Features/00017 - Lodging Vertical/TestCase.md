## 2. Test Scenarios

### 2.1 Phase 1 — ประเภทกิจการ

#### TC-001: เลือกประเภทกิจการตอนสร้างธุรกิจ
- **Linked to:** FR-LODG-01, BR-LODG-01
- **Precondition:** ผู้ใช้มีแพ็กเกจที่สร้าง Business ได้
- **Steps:** เข้าหน้าสร้างธุรกิจ → ตรวจว่ามีช่อง "ประเภทกิจการ" 2 ตัวเลือกและค่าเริ่มต้นคือ *สินค้าและบริการ* → เลือก *บ้านพักตากอากาศ* → บันทึก
- **Expected:** สร้างสำเร็จ, DB: `Shop.vertical = 'LODGING'`, ช่องเดิมแสดงป้าย **"ประเภทผู้ประกอบการ"** (ไม่ใช่ "ประเภทธุรกิจ") และยังส่งค่า `businessType` เหมือนเดิม

#### TC-002: 🛑 ประเภทกิจการเปลี่ยนภายหลังไม่ได้
- **Linked to:** BR-LODG-30, D-01
- **Steps:** เปิดหน้าตั้งค่าธุรกิจ → ยืนยันว่าไม่มีช่องแก้ประเภทกิจการ → ยิง `PATCH` ไปยัง endpoint แก้ข้อมูลร้านพร้อม `vertical: 'GENERAL'` ตรง ๆ
- **Expected:** ค่าใน DB **ไม่เปลี่ยน** (ไม่ว่าจะตอบ 200 หรือ 400) — field ถูกละเว้นที่ service ไม่ใช่แค่ซ่อนใน UI

#### TC-003: 🛑 เมนูและสิทธิ์แยกตามประเภท
- **Linked to:** FR-LODG-02, BR-LODG-03
- **Steps:** เข้าร้าน `LODGING` ตรวจเมนู → เข้าร้าน `GENERAL` ตรวจเมนู → จากร้าน `GENERAL` เปิด URL `/rooms` และยิง `GET /api/shops/current/rooms` ตรง ๆ
- **Expected:** `LODGING` เห็นเมนูห้องพัก/ปฏิทิน/การจอง/แม่บ้าน และไม่เห็นเมนูสินค้า/สต็อก/ปักหมุด; `GENERAL` ตรงข้าม; **ร้าน `GENERAL` ที่เข้าตรงได้ `403 NOT_LODGING_SHOP` ทั้งหน้าและ API — ไม่ใช่แค่ไม่เห็นเมนู**

#### TC-004: 🛑 ธุรกิจเดิมทั้งหมดเป็น GENERAL (zero-regression)
- **Linked to:** FR-LODG-03, BR-LODG-27
- **Steps:** หลัง migration M1 → query `SELECT vertical, COUNT(*) FROM "Shop" GROUP BY vertical` → เข้าหน้า seller เดิมทุกหน้าด้วยบัญชีที่มีอยู่ก่อน
- **Expected:** ทุกแถวเดิม = `'GENERAL'`, ไม่มีหน้าจอบังคับให้เลือกประเภท, ทุกหน้าเดิมทำงานเหมือนเดิม

#### TC-005: สร้าง / แก้ไข / ปิดการใช้งานห้องพัก
- **Linked to:** FR-LODG-04
- **Expected:** สร้างได้ด้วยชื่อ+ราคา; แก้ได้ทุกช่อง; ปิดการใช้งานแล้วไม่ปรากฏในตัวเลือกตอนสร้างการจอง แต่การจองเดิมยังเปิดดูได้

#### TC-006: ราคาต่อคืนต้องมากกว่า 0
- **Linked to:** BR-LODG-05
- **Steps:** สร้างห้องด้วย `pricePerNight = 0` และ `-100`
- **Expected:** `400 VALIDATION_ERROR` ทั้งสองกรณี และถ้าเลี่ยง validation ยิงตรง DB ต้องติด CHECK `Room_price_positive`

#### TC-007: 🛑 ห้ามลบห้องที่มีการจอง
- **Linked to:** BR-LODG-06
- **Steps:** สร้างห้อง → สร้างการจองบนห้องนั้น → พยายามลบห้อง (ทั้งผ่าน API และ `DELETE` ตรงที่ DB)
- **Expected:** ลบไม่ได้ทั้งสองทาง — DB ติด FK `ON DELETE RESTRICT`; ข้อความแนะนำให้ใช้การปิดการใช้งานแทน

#### TC-008: จำกัดรูป 10 รูปต่อห้อง
- **Linked to:** BR-LODG-34, D-05
- **Steps:** อัปโหลด 10 รูป → อัปโหลดรูปที่ 11
- **Expected:** 10 รูปแรกสำเร็จ, รูปที่ 11 ถูกปฏิเสธพร้อมข้อความบอกเพดานชัดเจน

#### TC-009: ห้องที่ปิดการใช้งานไม่ปรากฏบนหน้าสาธารณะ
- **Linked to:** FR-LODG-07, BR-LODG-07

- **Linked to:** FR-LODG-08, FR-LODG-10, BR-LODG-09
- **Steps:** สร้างการจอง 5–8 ก.ย. → เปิดปฏิทินทันทีโดยยังไม่แนบสลิป

#### TC-014: 🛑🛑 กดสร้างพร้อมกัน → สำเร็จรายการเดียว
- **Linked to:** BR-LODG-11, TFR-005, TD-002

- **Steps:** ยิง `POST /bookings` พร้อมกัน 2 คำขอ (ช่วงวันเดียวกัน ห้องเดียวกัน) ด้วย `Promise.all`

- **หมายเหตุ:** นี่คือเคสที่พิสูจน์ว่า EXCLUDE constraint ทำงานจริง ไม่ใช่แค่การตรวจก่อนบันทึก — **ห้ามข้าม**

- **Expected:** **B สำเร็จ** (เช็คอินวันเดียวกับที่ A เช็คเอาท์), **C ได้ 409** (ทับวันที่ 7); ปฏิทินแสดงวันที่ 8 เป็นวันที่มีทั้งเช็คเอาท์และเช็คอิน

## 6. สรุป

แผนทดสอบมี **43 เคส** ครอบ FR-LODG-01..22 และ BR-LODG-01..40 ครบทุกข้อ แบ่งเป็น unit (สูตรคำนวณ), integration ที่ต่อฐานข้อมูลจริง (constraint และการกดพร้อมกัน), E2E ด้วย Playwright และ regression ของร้านเดิม

เคสที่สำคัญที่สุดสองข้อคือ **TC-023** (ผู้จองยืนยันการจองเองไม่ได้) และ **TC-014** (กดพร้อมกันแล้วสำเร็จรายการเดียว) — ข้อแรกกันช่องได้ใบจองฟรี ข้อหลังพิสูจน์ว่ากลไกกันจองทับทำงานจริงที่ระดับฐานข้อมูล ไม่ใช่แค่การตรวจก่อนบันทึกที่มีช่องว่างเสมอ

**TC-036** เป็นเคสที่ตั้งขึ้นเพราะความไม่แน่ใจโดยเจตนา — โค้ดปัจจุบันเรียก `restockFromCancelledOrder` ทุกครั้งที่ยกเลิก และแม้การอ่านโค้ดจะบอกว่าการจองไม่น่ากระทบสต็อก แต่ข้อสรุปแบบนั้นต้องมาจากการทดสอบ ไม่ใช่การอ่าน
