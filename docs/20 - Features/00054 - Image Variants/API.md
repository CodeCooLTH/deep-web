# API Contract: รูปย่อสำหรับหน้าจอ

---

## 1. Overview

🛑 **ไม่มี endpoint ใหม่ และไม่มี response ไหนเปลี่ยนรูปร่าง**

ฟีเจอร์นี้จงใจไม่เพิ่ม API เลย — variant ถูกเสิร์ฟผ่าน `GET /api/files/[...fileId]` เดิม โดยที่ client **คำนวณคีย์เอง** จาก `fileId` ที่มีอยู่แล้ว (สูตรใน SRS TFR-001)

เหตุผล: การเพิ่ม field `thumbUrl` ลงใน response ของ commit จะบังคับให้ทุกจุดที่เก็บรูป (Product/Room/Shop/User + แอปมือถือ) ต้องรู้จัก field ใหม่และเก็บมันไว้ ทั้งที่ค่านั้น derive ได้จากสิ่งที่มีอยู่แล้ว — และรูปเก่าหลายพันใบจะไม่มี field นั้นอยู่ดี

## 2. Authentication
ไม่เปลี่ยน — `POST /api/uploads/commit` ยังต้องมี session + ticket ที่ผูก `userId` เหมือนเดิม

## 4. Endpoint Detail

### 4.1 `POST /api/uploads/commit`

**Request / Response: ไม่เปลี่ยน**

**พฤติกรรมที่เพิ่มเข้ามา (มองไม่เห็นจากฝั่ง client):**
หลังไฟล์ผ่านด่านทั้งหมดแล้ว ถ้า `purpose === 'IMAGE'` และนามสกุลอยู่ใน `{jpg, jpeg, png, webp}`:
1. อ่านต้นฉบับจาก storage
2. สร้าง `thumb` และ `lg`
3. เขียนที่คีย์ `<คีย์ต้นฉบับไม่รวมนามสกุล>.<variant>.webp`

🛑 ทุกความล้มเหลวในขั้นตอนนี้ถูกกลืน — response ยังเป็น 200 เหมือนเดิม (BR-IMG-04)
🛑 **ไม่มีการลบหรือเขียนทับต้นฉบับ**

**Error:** ไม่มี error code ใหม่

### 4.2 `GET /api/files/[...fileId]`

**ไม่แก้ไขไฟล์นี้เลย** — บันทึกไว้เพื่อให้ชัดว่าทำไมมันใช้ได้กับ variant:

| ประเด็น | สถานะ |
|---------|-------|
| รับคีย์ที่มี slash หลายชั้น | ได้อยู่แล้ว (catch-all, 2026-07-25) |
| content-type ของ `.webp` | มีใน `EXT_TO_MIME` อยู่แล้ว |
| cache | `public, max-age=86400` เหมือนไฟล์รูปทั่วไป |
| ไม่พบไฟล์ | 404 → `<img>` ยิง `onError` → หน้าจอตกไปต้นฉบับ |

🛑 **ด่านสิทธิ์ทั้ง 5 ชั้นในไฟล์นี้ (KYC · สลิปเติมเงิน · สลิปออเดอร์ · หลักฐานมิจฉาชีพ · เอกสารแนบแชท) ตรวจจาก "คีย์ต้นฉบับ" เท่านั้น** — คีย์ของ variant จะไม่ตรงกับค่าใดในฐานข้อมูล จึงเดินผ่านทุกด่านและถูกเสิร์ฟเป็นไฟล์สาธารณะ
นี่คือเหตุผลทั้งหมดที่การสร้าง variant ต้องเป็น allow-list ที่ `purpose === 'IMAGE'` (SDS TD-004) ไม่ใช่ deny-list — และเป็นเหตุผลที่ backfill ต้องดึงรายชื่อจากคอลัมน์รูปสาธารณะเท่านั้น
