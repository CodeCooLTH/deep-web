# PRD: รูปย่อสำหรับหน้าจอ (Image Variants)

---

## Executive Summary

ทุกวันนี้รูปที่ผู้ขายอัปโหลด **ถูกเสิร์ฟกลับไปเป็นไฟล์ต้นฉบับขนาดเต็มทุกจุด** ไม่ว่าจะเอาไปวางในกรอบใหญ่แค่ไหน วัดจากรูปจริงบน prod (ร้านอะไหล่มอเตอร์ไซค์ 2026-08-23): ไฟล์หนึ่ง **1080×1920 px หนัก 210 KB** ขณะที่การ์ดสินค้าในกริดหน้าร้านกว้างจริงเพียง ~180–240 px — เท่ากับส่งข้อมูลไปมากกว่าที่จอใช้จริงหลายเท่าทุกใบ

ร้านนั้นมีสินค้าที่มีรูป 22 ชิ้น ⇒ การเปิดแท็บสินค้าหนึ่งครั้งดึงข้อมูล **~4.6 MB** ซึ่งบนเน็ตมือถือคือความช้าที่ผู้ซื้อรู้สึกได้ตั้งแต่วินาทีแรก และเป็นความช้าที่เกิด**ทุกครั้ง**ที่มีผู้ชมคนใหม่เปิดหน้าร้าน — ไม่ใช่แค่ครั้งแรกของแต่ละเครื่อง

ฟีเจอร์นี้สร้าง **รูปย่อสองขนาด** ควบคู่กับไฟล์ต้นฉบับตอนอัปโหลด แล้วให้หน้าจอเลือกใช้ขนาดที่ตรงกับกรอบจริง:

| variant | ขนาด | ใช้ที่ไหน | วัดจากรูปจริง |
|---------|------|-----------|----------------|
| `thumb` | กว้างไม่เกิน 480 px, WebP | กริดการ์ดสินค้า/ห้องพัก, รูปย่อในรายการหลังร้าน | 210 KB → **33 KB** |
| `lg` | ด้านยาวไม่เกิน 1280 px, WebP | ป๊อปอัปดูรูปเต็ม | 210 KB → **97 KB** |
| ต้นฉบับ | ไม่แตะ | เก็บไว้เป็นต้นทาง — ไม่ถูกลบ ไม่ถูกเขียนทับ | 210 KB |

ผลที่คาดหวังกับหน้าที่ user รายงาน: กริด 22 ใบ **4.6 MB → ~0.7 MB (ลดลง ~85%)**

🛑 **ไฟล์ต้นฉบับไม่ถูกแตะเลยแม้แต่ไบต์เดียว** ทั้งตอนอัปโหลดใหม่และตอน backfill — variant เป็นไฟล์ที่ *เพิ่มเข้ามา* ไม่ใช่ไฟล์ที่ *แทนที่* (ผู้ใช้สั่งไว้เป็นกฎถาวรว่าห้ามลบ/ทับอะไรโดยไม่บอกก่อน) แลกกับพื้นที่เก็บที่โตขึ้นราว 60% ต่อรูปหนึ่งใบ ซึ่งเป็นราคาที่ถูกกว่าความเสี่ยงของการทำลายต้นฉบับที่กู้คืนไม่ได้

## 2. User Personas

### 2.1 ผู้ซื้อที่เปิดหน้าร้านจากลิงก์ในแชท
- **บริบท:** เน็ตมือถือ ไม่รู้จักร้าน กำลังตัดสินใจว่าจะคุยต่อไหม
- **สิ่งที่ต้องการ:** เห็นสินค้าเร็ว
- **ความสำเร็จ:** กริดขึ้นครบก่อนที่จะเบื่อจนปิดทิ้ง

### 2.2 ผู้ขายที่อัปรูปจากมือถือ
- **บริบท:** ถ่ายด้วยกล้องมือถือ ไฟล์ 2–8 MB ต่อใบ อัปทีละหลายใบ
- **สิ่งที่ต้องการ:** อัปแล้วจบ ไม่ต้องย่อเอง และรูปที่ลูกค้าเห็นต้องยังคมชัด
- **ความสำเร็จ:** ไม่รู้สึกว่ามีอะไรเปลี่ยน นอกจากหน้าร้านเร็วขึ้น

## 3. Business Requirements

### 3.1 การสร้าง variant

| # | ความต้องการ | ระดับ |
|---|-------------|-------|
| BR-3.1.1 | รูปที่อัปโหลดใหม่ต้องได้ `thumb` และ `lg` อัตโนมัติ โดยผู้ใช้ไม่ต้องทำอะไร | ต้องมี |
| BR-3.1.2 | สร้าง variant เฉพาะรูปที่เอาไปโชว์บนหน้าจอ (สินค้า/ห้องพัก/โลโก้/ปก/อวาตาร์) | ต้องมี |
| BR-3.1.3 | **ห้าม**สร้าง variant ให้เอกสารยืนยันตัวตน สลิปโอนเงิน และไฟล์แนบในแชท | ต้องมี |
| BR-3.1.4 | สร้าง variant ไม่สำเร็จต้องไม่ทำให้การอัปโหลดล้ม — ตกกลับไปใช้ต้นฉบับเงียบ ๆ | ต้องมี |
| BR-3.1.5 | ไม่สร้าง variant ให้ GIF (จะทำลายภาพเคลื่อนไหว) | ต้องมี |

### 3.2 การแสดงผล

| # | ความต้องการ | ระดับ |
|---|-------------|-------|
| BR-3.2.1 | กริดการ์ดใช้ `thumb` · ป๊อปอัปดูรูปเต็มใช้ `lg` | ต้องมี |
| BR-3.2.2 | รูปที่ยังไม่มี variant (ของเก่าที่ยังไม่ backfill / สร้างไม่สำเร็จ) ต้องแสดงต้นฉบับแทนโดยอัตโนมัติ ไม่ใช่รูปแตก | ต้องมี |
| BR-3.2.3 | คุณภาพที่ผู้ซื้อเห็นต้องไม่แย่ลงจนสังเกตได้ | ต้องมี |

### 3.3 ของเก่า (backfill)

| # | ความต้องการ | ระดับ |
|---|-------------|-------|
| BR-3.3.1 | รูปสินค้า/ห้องพัก/ร้าน ที่มีอยู่แล้วต้องได้ variant ย้อนหลัง | ต้องมี |
| BR-3.3.2 | สคริปต์ต้องมีโหมด dry-run ที่รายงานว่าจะแตะอะไรบ้างก่อนลงมือจริง | ต้องมี |
| BR-3.3.3 | สคริปต์ต้อง resume ได้ (ข้ามไฟล์ที่มี variant แล้ว) | ต้องมี |
| BR-3.3.4 | **สคริปต์ต้องไม่มีคำสั่งลบหรือเขียนทับไฟล์ต้นฉบับเลยแม้แต่บรรทัดเดียว** | ต้องมี |

## 4. Business Rules & Constraints

### 4.1 กฎทางธุรกิจหลัก

- **BR-IMG-01** — ต้นฉบับเป็นของผู้ใช้ ระบบมีสิทธิ์ *เพิ่ม* ไฟล์ข้าง ๆ เท่านั้น ห้ามลบ/เขียนทับ
- **BR-IMG-02** — variant ของไฟล์ `k.ext` อยู่ที่คีย์ `k.<variant>.webp` ในที่เดียวกัน (เดาได้จากคีย์ต้นฉบับ ไม่ต้องมีคอลัมน์ใหม่ใน DB)
- **BR-IMG-03** — 🛑 **ห้ามสร้าง variant ให้ไฟล์ที่มีด่านสิทธิ์** (KYC/สลิป/หลักฐานมิจฉาชีพ/เอกสารแนบแชท) เพราะด่านใน `/api/files/*` ตรวจจาก **คีย์ต้นฉบับ** เท่านั้น — คีย์ variant จะเล็ดลอดด่านทั้งหมดและถูกเสิร์ฟเป็นไฟล์สาธารณะ
- **BR-IMG-04** — variant สร้างไม่สำเร็จ = เรื่องปกติ ไม่ใช่ error ที่ต้องบอกผู้ใช้ (หน้าจอตกไปใช้ต้นฉบับ)
- **BR-IMG-05** — variant ไม่มีวันใหญ่กว่าต้นฉบับ ถ้าย่อแล้วได้ไฟล์ใหญ่กว่าเดิม ให้ทิ้งผลนั้นและไม่สร้าง variant

### 4.2 ข้อจำกัด

- พื้นที่เก็บโตขึ้นราว 60% ต่อรูปหนึ่งใบ (33 + 97 = 130 KB ต่อต้นฉบับ 210 KB) — ยอมรับเพื่อไม่แตะต้นฉบับ
- WebP ไม่รองรับบนเบราว์เซอร์เก่ามาก (IE, Safari < 14) — กลุ่มนี้จะเห็นรูปแตกเฉพาะกรณีที่ `<img>` ตกไปหา variant ⇒ ต้องมี fallback ไปต้นฉบับด้วย `onError` เสมอ

## 5. Out of Scope

| # | ไม่ทำในเฟสนี้ | เหตุผล |
|---|--------------|--------|
| OOS-1 | `next/image` / Vercel Image Optimization | ผู้ใช้เลือกทางย่อตอนอัปโหลดแทนโดยตรง (2026-08-23) เพราะไม่อยากมีค่าใช้จ่ายต่อการแปลงรูป |
| OOS-2 | ย่อ/แปลงรูปในแชท | มีไปป์ไลน์ของตัวเอง (mirror + dedup 00051) และเป็นไฟล์ที่มีด่านสิทธิ์ |
| OOS-3 | `srcSet` หลายความละเอียดตามจอ (1x/2x/3x) | thumb 480 px ครอบกรอบ 240 px ที่ 2x อยู่แล้ว เพิ่มขั้นทีหลังได้โดยไม่ต้องรื้อ |
| OOS-4 | ลบ/บีบไฟล์ต้นฉบับเพื่อประหยัดพื้นที่ | ผู้ใช้สั่งห้ามลบโดยไม่บอกก่อน — ถ้าจะทำต้องเป็นรอบแยกที่ขออนุมัติเฉพาะ |
| OOS-5 | AVIF | เบราว์เซอร์รองรับน้อยกว่า WebP และ encode ช้ากว่ามาก |

## 6. Risks & Mitigation

| # | ความเสี่ยง | ผลกระทบ | การรับมือ |
|---|-----------|---------|-----------|
| R-1 | สร้าง variant ให้ไฟล์ที่มีด่านสิทธิ์ | เอกสาร KYC/สลิปกลายเป็น URL สาธารณะ | allow-list ที่ purpose (`IMAGE` เท่านั้น) + เทส `[blocker]` + backfill ดึงรายชื่อจากคอลัมน์รูปที่เป็นสาธารณะอยู่แล้วเท่านั้น |
| R-2 | รูปแตกบนเบราว์เซอร์ที่ไม่รองรับ WebP | ผู้ซื้อเห็นการ์ดเปล่า | `onError` ตกไปต้นฉบับทุกจุด (ทดสอบด้วยการชี้ไป key ที่ไม่มีจริง) |
| R-3 | คุณภาพตกจนผู้ขายทัก | เสียความเชื่อมั่น | q72/q80 + ไม่ขยายรูปเล็กให้ใหญ่ขึ้น (`withoutEnlargement`) |
| R-4 | backfill ทำงานนานแล้วหลุดกลางทาง | ทำซ้ำเสียเวลา | ข้ามไฟล์ที่มี variant แล้ว (resume ได้ในตัว) + dry-run ก่อน |
| R-5 | สร้าง variant ทำให้ commit ช้าลง | อัปโหลดรู้สึกหน่วง | ทำหลังจากตอบ client ไม่ได้ / ถ้าทำ inline ต้องวัดเวลาจริงก่อน (ดู SRS NFR) |

## 9. Dependencies & Assumptions

### 9.1 Dependencies
- `sharp` (เป็น dependency ตรงอยู่แล้วตั้งแต่ feature 00045 — `src/lib/line/preview-image.ts`)
- ไปป์ไลน์อัปโหลด direct-to-storage (2026-08-10) — `POST /api/uploads/commit` คือจุดเดียวที่ server เห็นไฟล์หลังอัปโหลด
- `/api/files/[...fileId]` เสิร์ฟคีย์อะไรก็ได้ในบัคเก็ต พร้อม `public, max-age=86400`

### 9.2 Assumptions
- รูปสินค้าส่วนใหญ่เป็น JPEG/PNG จากมือถือ (ยืนยันจาก prod: นามสกุล `.jpg` เป็นส่วนใหญ่)
- ผู้ชมหน้าร้านใช้เบราว์เซอร์ที่รองรับ WebP (Safari 14+ ปี 2020 ขึ้นไป) — ที่เหลือมี fallback

## 10. Appendix

### 10.1 ตัวเลขที่วัดจริง (2026-08-23)

ไฟล์ `2026/08/11/090806bb-….jpg` ของร้านอะไหล่มอเตอร์ไซค์บน prod:

```
ต้นฉบับ  1080x1920  210 KB
thumb     480x853    33 KB   (-84%)
lg       1080x1920   97 KB   (-54%, ไม่ขยาย เพราะด้านยาว 1920 > 1280 จึงย่อเหลือ 720x1280 ในโค้ดจริง)
```

> หมายเหตุ: ตัวเลข `lg` ด้านบนมาจากการทดลองที่ตั้ง `width:1280` ซึ่งไม่ย่อรูปแนวตั้งใบนี้ —
> สเปกจริงใช้ "ด้านยาวไม่เกิน 1280" (ดู SRS TFR-002) จึงได้ไฟล์เล็กกว่าที่แสดงไว้ตรงนี้อีก

### 10.2 ทำไมไม่แตะต้นฉบับ

ผู้ใช้สั่งเป็นกฎถาวรเมื่อ 2026-08-21 ว่า **ห้ามลบอะไรโดยไม่บอกก่อน รวมถึงสคริปต์ที่มีการลบซ่อนอยู่** การเขียนทับต้นฉบับด้วยไฟล์ที่ย่อแล้วคือการลบข้อมูลที่กู้ไม่ได้ ต่อให้ผลลัพธ์ "ดูเหมือนเดิม" — ถ้าวันหนึ่งต้องการรูปความละเอียดสูงกลับมา (พิมพ์แคตตาล็อก/ขายผ่านแพลตฟอร์มอื่น) จะไม่มีทางได้คืน พื้นที่เก็บที่ประหยัดได้ไม่คุ้มกับความเสี่ยงนั้น
