# PRD: บัญชีส่วนตัวและการเชื่อมต่อบัญชี (Personal Account & Connections)

---

## Executive Summary

user ที่เข้าระบบ Deep ผ่าน **invite link** (feature 00012 Shop Staff Invite Links) กลายเป็นแอดมินของร้านธุรกิจ (BUSINESS shop) ของคนอื่นได้ทันที แต่ **สร้างร้านส่วนตัวของตัวเองไม่ได้เลย** แม้ backend (`POST /api/shops/open-personal`) และ business rule ("เปิดร้านของฉันได้ทุกเมื่อ" — FR-STAFF-10 ของ feature 00012) จะรองรับไว้อยู่แล้ว สาเหตุคือ UI ที่เรียกความสามารถนี้มีอยู่จุดเดียวคือหน้า `/choose-shop` ซึ่งผู้ถูกเชิญที่มี business membership แล้วไม่ถูกพาไปอีกเลย — กลายเป็น "ทางตัน" ที่ไม่มีใครสังเกตเห็นจนกว่าจะมี user จริงมาเจอ

ผู้ใช้กลุ่มนี้ยังพ่วงปัญหาที่เกี่ยวข้องกันมาด้วย: ไม่มีหน้าแก้ **ข้อมูลส่วนตัวของ user** แยกจากข้อมูลร้าน (หน้า `/shop` ที่มีอยู่แก้ `Shop` ที่ active อยู่เท่านั้น ไม่ใช่ `User`) ทำให้คนที่ login ด้วย LINE/Facebook เปลี่ยนรูปโปรไฟล์ที่ติดมาจาก provider ไม่ได้ และรู้สึกว่าไม่มีทาง "เชื่อมบัญชี" ให้ user ที่สมัครด้วยเบอร์โทรไป login ด้วย LINE ในภายหลังโดยไม่กลายเป็นบัญชีใหม่คนละใบ

feature นี้แก้ทั้ง 3 เรื่องภายใต้หลักการเดียวกันที่ user ย้ำชัด — **"หน้านี้เป็นการตั้งค่าของ user คนนั้น ไม่ใช่การตั้งค่าร้าน"**: (ส่วน A) เพิ่มทางเข้าจริงให้ผู้ถูกเชิญกดสร้างร้านส่วนตัวได้จาก account switcher พร้อมแก้กับดัก onboarding ที่จะบังคับ setup ร้านส่วนตัวทับร้านธุรกิจที่กำลังทำงานอยู่ (ตรวจโค้ดพบว่าตรรกะแก้กับดักนี้ถูกแยกออกมาเป็นฟังก์ชันล้วน `resolveOnboardingGate` ใน `src/lib/onboarding-gate.ts` และมี Vitest ครอบไว้แล้ว 7 เคส — งาน backend ของส่วนนี้จึงมีความคืบหน้าไปก่อนเอกสารนี้แล้วบางส่วน) และ (ส่วน B) หน้าใหม่ `/account` แก้ข้อมูลส่วนตัว (ชื่อ/username/รูป/อีเมล) ที่ **ไม่ผูกกับร้าน active** — อยู่ร้านไหนก็เห็นหน้าเดียวกัน

**ส่วน C แก้ไขความเข้าใจ (สำคัญ):** ตอนวิเคราะห์ปัญหารอบแรก ทีมเข้าใจผิดว่า "เชื่อมต่อบัญชี" (ตั้งรหัสผ่าน / เชื่อม LINE-Facebook เพิ่ม) เป็นความสามารถที่ยังไม่มีในระบบ ต้องเขียน OAuth link flow ขึ้นใหม่ทั้งเส้น — **ตรวจโค้ดจริงพบว่าความสามารถนี้ถูกสร้างเสร็จและอยู่บน `origin/main` แล้ว** ตั้งแต่ commit `e69513c4` (feature 00001 FR-LO-16: เชื่อม/ยกเลิก LINE·Facebook·Instagram พร้อม guard เหลือวิธี login ≥1 เสมอ, หน้า `/settings`) รวมกับ FR-LO-04 (ตั้ง/รีเซ็ตรหัสผ่านผ่าน OTP ที่มีอยู่ก่อนแล้ว) **ปัญหาจริงของ user จึงเป็นปัญหา discoverability (หาไม่เจอ) ไม่ใช่ปัญหา capability (ทำไม่ได้)** — เมนู "บัญชีที่เชื่อมต่อ" ถูกจัดไว้ในกลุ่มเมนู "STORE"/"ร้านค้า" (`_seller-menu.ts:151`) ปนกับเมนูที่เป็นเรื่องร้านล้วน ๆ ทั้งที่เนื้อในผูกกับตัวคน ไม่ผูกร้าน (D6 — งาน console ที่เดิมคิดว่าต้องให้ user ไปเพิ่ม redirect URI เอง — **ยกเลิกไปด้วย เพราะไม่มี flow ใหม่ถูกสร้าง**)

รอบนี้ implement **ส่วน A + B + ครึ่งหนึ่งของ C** — การเชื่อม OAuth (LINE/Facebook/Instagram) ไม่ต้องสร้างใหม่เพราะมีอยู่แล้ว (feature 00001 FR-LO-16) เอกสารนี้จึงบันทึกความสามารถที่มีอยู่ให้ถูกต้อง พร้อมยกธงประเด็นที่ต้องให้ user ตัดสิน 2 เรื่อง: (1) จะย้าย/เพิ่มทางเข้า "บัญชีที่เชื่อมต่อ" ให้เข้าถึงจาก `/account` อย่างไร และ (2) พฤติกรรมการเจอบัญชีซ้ำที่ระบบมีอยู่จริง **2 แบบต่างกัน** ขึ้นกับ entry point ควรรวมเป็นแบบเดียวหรือไม่ (มติ D2 เดิม "บล็อกเสมอ" ใช้ได้จริงเฉพาะ entry point เดียว — ดู §4.3)

> **แก้ไข 2026-08-02 (หลัง implement):** เอกสารฉบับก่อนสรุปว่า "ส่วน C ไม่ต้องสร้าง capability ใหม่ใด ๆ" ซึ่ง**ผิด** — ที่มีอยู่แล้วคือการเชื่อม OAuth เท่านั้น ส่วน **username/password ที่ user ขอมาตั้งแต่ข้อความแรก ("สำหรับคนที่อยากสร้าง account username/password สำหรับ login ตรง") ไม่เคยมี**: การ์ด `ConnectedAccountsClient` ใช้ `hasPassword` แค่ขึ้นข้อความเตือน ไม่มีปุ่มให้ตั้งรหัสผ่าน ทางเดียวคือออกจากระบบแล้วใช้ "ลืมรหัสผ่าน" ที่หน้า login ซึ่งบัญชีที่เข้ามาด้วย FB/LINE ไปไม่ถึงถ้ายังไม่มีเบอร์ — สร้างเพิ่มแล้วในรอบนี้ ดู **FR-PAC-10** และ `API.md`

## 1. Business Goals & KPIs

### 1.1 เป้าหมายทางธุรกิจ

| เป้าหมาย | รายละเอียด |
|----------|-----------|
| **ปิดทางตันของผู้ถูกเชิญที่อยากขายของเอง** | ผู้ถูกเชิญเข้าร้านธุรกิจต้องมีทางกดสร้างร้านส่วนตัวได้จริง ไม่ใช่แค่มี backend รองรับเฉย ๆ — ทำให้ FR-STAFF-10 ของ feature 00012 ใช้งานได้จริงเป็นครั้งแรก |
| **แยกตัวตนออกจากร้าน** | user ต้องแก้ไขข้อมูลของตัวเอง (ชื่อ/รูป/username) ได้โดยไม่ขึ้นกับว่ากำลัง active อยู่ร้านไหน — สอดคล้องกับสถาปัตยกรรม Profile-Centric ของ Deep ที่ trust profile เป็นของ "คน" ไม่ใช่ของ "ร้าน" |
| **ไม่สร้างช่องโหว่ trust score ผ่านการเปิดร้านใหม่** | ร้านส่วนตัวที่สร้างใหม่ต้องแสดงคะแนนความน่าเชื่อถือเดียวกับที่ user มีอยู่แล้ว (`User.trustScore`) ไม่ใช่คะแนนเริ่มต้นใหม่ — กันไม่ให้เป็นช่องทาง "ล้างคะแนน" โดยเปิดร้านใหม่ |
| **ทำให้ความสามารถที่มีอยู่แล้วหาเจอ** | "เชื่อมต่อบัญชี" (ตั้งรหัสผ่าน/เชื่อม LINE-Facebook) implement เสร็จแล้วบน prod แต่ user หาไม่เจอเพราะเมนูจัดวางผิดกลุ่ม — เอกสารนี้บันทึกปัญหานี้ให้ถูกต้องเป็นปัญหา IA ไม่ใช่ปัญหา build ใหม่ |
| **ลดความเสี่ยงด้านความปลอดภัยของ API บัญชีตัวเอง** | ระหว่างสำรวจฟีเจอร์นี้พบช่องโหว่ privilege-escalation บน `PATCH /api/users/me` — ปิดแล้วเป็น hotfix แยกต่างหาก (commit `eb32a937`) ก่อนเริ่มงานนี้ ส่วน B ของฟีเจอร์นี้สร้างต่อบนฐานที่ปลอดภัยแล้ว |

## 2. User Personas (กลุ่มผู้ใช้งาน)

### 2.1 ผู้ถูกเชิญเข้าร้านธุรกิจ (Invited Business Admin)

**ข้อมูลพื้นฐาน:**
- ถูกเชิญเข้าร้านธุรกิจของคนอื่นผ่าน invite link (`/i/<slug>`) กลายเป็น `ShopMember(role=ADMIN)` ของร้านนั้น — role ADMIN หรือ OWNER ไม่มีผลต่อสิทธิ์ที่ฟีเจอร์นี้เพิ่ม (ดู §4.4)
- ไม่มี PERSONAL shop เป็นของตัวเอง — active shop ปัจจุบันคือร้านธุรกิจที่ถูกเชิญเข้ามา
- อาจ login ด้วยเบอร์โทร หรือ LINE/Facebook ก็ได้ (ไม่จำเป็นต้องมีเบอร์มาก่อน)

**เป้าหมาย:**
- อยากขายของในนามตัวเองเพิ่ม โดยไม่กระทบงานที่ทำอยู่ในร้าน BUSINESS

**ความต้องการ:**
- เห็นทางเลือก "สร้างร้านส่วนตัวของฉัน" อยู่ในที่ที่กำลังใช้งานอยู่แล้ว (account switcher) ไม่ต้องไปหาหน้าลับ
- สร้างเสร็จแล้วไม่ถูกล็อกอยู่ที่ setup ของร้านส่วนตัวจนออกไปทำงานร้านเดิมไม่ได้

**จุดปวด (Pain Points):**
- กดหาปุ่ม "เปิดร้านของฉัน" ทั่วเมนูไม่เจอ ทั้งที่ระบบบอกว่าทำได้ (backend มีจริง)
- ถ้าสร้างร้านส่วนตัวได้ กลัวว่าจะถูกบังคับ setup จนออกจากร้านธุรกิจที่ทำงานอยู่ไม่ได้

### 2.2 ผู้ใช้ที่ login ด้วย LINE/Facebook (Social-Login User)

**ข้อมูลพื้นฐาน:**
- สมัคร/login ด้วย LINE หรือ Facebook OAuth — รูปโปรไฟล์ถูกดึงมาจาก provider อัตโนมัติตอน login ครั้งแรก
- อาจมีหรือไม่มีเบอร์โทรผูกกับบัญชีก็ได้

**เป้าหมาย:**
- แก้รูป/ชื่อที่แสดงใน Deep ให้ไม่ต้องเหมือนรูปที่ใช้ใน LINE/Facebook
- (ถ้าจำเป็น) เชื่อมช่องทาง login เพิ่ม หรือตั้งรหัสผ่านสำรอง — ความสามารถนี้ **มีอยู่แล้ว** แต่หาทางเข้าไม่เจอ

**ความต้องการ:**
- อัปโหลด/เปลี่ยน/ลบรูปโปรไฟล์ได้เอง โดยไม่ต้องพึ่งการเปลี่ยนรูปที่ต้นทาง provider

**จุดปวด (Pain Points):**
- รูปโปรไฟล์ติดมาจาก provider แก้ไม่ได้เลยในตอนนี้ — ไม่มีเมนูไหนให้แก้ `User.avatar` โดยตรง
- (บริบทเพิ่มจากการตรวจโค้ด) แม้ระบบมีหน้า "บัญชีที่เชื่อมต่อ" อยู่แล้ว แต่ซ่อนอยู่ในเมนู "ตั้งค่าร้านค้า" — persona กลุ่มนี้ไม่มีทางเดาได้ว่าการตั้งค่า login ของตัวเองอยู่ตรงนั้น

### 2.3 เจ้าของร้านที่ต้องการแยกตัวตนออกจากร้าน (Existing Seller)

**ข้อมูลพื้นฐาน:**
- อาจมีทั้งร้านส่วนตัวและร้านธุรกิจ สลับไปมาระหว่างร้านผ่าน account switcher เป็นประจำ

**เป้าหมาย:**
- ตั้งค่าที่เป็น "ของตัวเอง" (ชื่อ, username, รูป) ได้จากที่เดียว ไม่ต้องสลับร้านไปมาเพื่อหาว่าตั้งค่าได้จากร้านไหน

**ความต้องการ:**
- หน้าตั้งค่าบัญชีที่แสดงผลเหมือนกันไม่ว่าจะ active อยู่ร้านไหน

**จุดปวด (Pain Points):**
- ปัจจุบันหน้า `/shop`/`/settings` ปนข้อมูล "ร้าน" กับสิ่งที่ควรเป็น "ของ user" เข้าด้วยกัน — ยืนยันแล้วว่าหน้า `/settings` เองก็ปนการ์ดตั้งค่าจัดส่ง (ผูกกับ active shop) กับการ์ด "บัญชีที่เชื่อมต่อ" (ผูกกับตัว user) อยู่ในหน้าเดียวกัน

### 2.4 ผู้ดูแลแพลตฟอร์ม Deep (Platform Admin)

**ข้อมูลพื้นฐาน:**
- ดูแลภาพรวมความปลอดภัยและความถูกต้องของระบบบน `admin.*`

**เป้าหมาย:**
- มั่นใจว่าไม่มี API ที่ user ทั่วไปใช้ยกระดับสิทธิ์ตัวเองได้ และการเพิ่มทางสร้างร้านส่วนตัวไม่กระทบ onboarding gate เดิม
- มั่นใจว่าเปิดร้านส่วนตัวใหม่ไม่ใช่ช่องทางล้าง/ปลอมคะแนนความน่าเชื่อถือ
- อยากให้พฤติกรรมของระบบเมื่อเจอบัญชีซ้ำสอดคล้องกันไม่ว่าจะเข้าทางไหน (ปัจจุบันไม่สอดคล้อง — ดู §4.3)

**ความต้องการ:**
- เห็นว่าช่องโหว่ที่พบระหว่างสำรวจฟีเจอร์นี้ (`PATCH /api/users/me`) ถูกปิดจริงและมี regression test คุมไว้

**จุดปวด (Pain Points):**
- ฟีเจอร์ที่แก้ auth callback (`jwt`/`session` ใน `lib/auth.ts`) มีความเสี่ยงสูงถ้า mirror ไม่ตรงกัน 2 จุด — เคยมีบทเรียนเรื่องนี้มาก่อนในไฟล์เดียวกัน

## 3. Business Requirements

### 3.1 ส่วน A — สร้างร้านส่วนตัวจาก account switcher

**ความต้องการ:**
- user ที่มี business membership แต่ไม่มี PERSONAL shop ต้องเห็นทางเลือก "สร้างร้านส่วนตัวของฉัน" อยู่ใน account switcher ทั้ง 2 จุดที่มีอยู่ (desktop dropdown, มือถือ sheet)
- สร้างสำเร็จแล้วต้องพาเข้า onboarding wizard ของร้านส่วนตัวทันที และต้องมีทางกลับไปร้านธุรกิจเดิมโดยไม่ต้อง setup ให้เสร็จก่อน

**Business Rules:**
- ร้านส่วนตัวสร้างได้คนละ **1 ร้านเท่านั้น** ต่อ user — บังคับด้วย partial unique index ระดับฐานข้อมูลที่มีอยู่แล้ว (`Shop_userId_personal_key` บน `Shop.userId` เมื่อ `kind = 'PERSONAL'`) ไม่ต้องเขียนกลไกกันซ้ำเพิ่ม
- การสร้างร้านส่วนตัวเป็นการกระทำที่ **idempotent** — กดซ้ำไม่สร้างร้านซ้ำ คืนร้านเดิมที่มีอยู่แล้วเสมอ
- ทันทีที่ร้านส่วนตัวถูกสร้าง ระบบต้องบังคับ setup (ตั้ง slug) **เฉพาะตอนที่ user เลือกอยู่ในร้านส่วนตัวนั้นจริง ๆ** เท่านั้น — ต้องไม่ล็อกทุกหน้าจอของ user คนนั้นไม่ว่าจะ active shop ไหนอยู่
- user ที่มีร้านส่วนตัวอยู่แล้ว (ไม่ว่าจะ setup เสร็จหรือยัง) ต้องไม่เห็นทางเลือก "สร้างร้านส่วนตัว" อีก
- role ของ user บนร้านธุรกิจ (`OWNER` หรือ `ADMIN`) **ไม่มีผลต่อสิทธิ์การสร้างร้านส่วนตัว** — ทั้งสอง role นับเป็น "มี business membership" เหมือนกัน (ดู §4.4)
- ร้านส่วนตัวที่สร้างใหม่ **ไม่รีเซ็ตคะแนนความน่าเชื่อถือ** — แสดงคะแนนเดียวกับ `User.trustScore` ที่มีอยู่แล้วของ user คนนั้น ไม่ใช่คะแนนเริ่มต้นที่ 0 (ดู §4.5)

**เหตุผล:**
- backend ของความสามารถนี้ (`POST /api/shops/open-personal`) มีอยู่แล้วตั้งแต่ feature 00012 และเป็น idempotent อยู่แล้ว — สิ่งที่ขาดคือ UI entry point เท่านั้น ทำให้ต้นทุนของส่วนนี้ต่ำมากเทียบกับคุณค่าที่ปิดทางตันได้จริง
- ถ้าไม่แก้กับดักการบังคับ setup ให้ผูกกับ "ร้านที่ active อยู่จริง" การเพิ่มทางเข้านี้จะสร้างปัญหาใหม่ที่หนักกว่าเดิม — user ที่กำลังทำงานอยู่ในร้านธุรกิจจะถูกล็อกออกจากทุกหน้าจอทันทีที่ร้านส่วนตัวถูกสร้างขึ้น (เพราะร้านส่วนตัวใหม่ยังไม่มี slug)
- ถ้าไม่ยืนยันว่าไม่มีผลต่อ trust score จะเปิดช่องให้ตีความว่าเปิดร้านใหม่ = คะแนนใหม่ ซึ่งขัดกับสถาปัตยกรรม Profile-Centric ที่คะแนนเป็นของคนไม่ใช่ของร้าน (schema มีคอมเมนต์ยืนยันชัดว่า `Shop.trustScore` ไม่ถูกใช้กับ PERSONAL shop)

### 3.2 ส่วน B — หน้าตั้งค่าบัญชีส่วนตัว (`/account`)

**ความต้องการ:**
- ต้องมีหน้าใหม่ที่แก้ไข **ข้อมูลของ user** (ชื่อที่แสดง, username, รูปโปรไฟล์, อีเมล) แยกออกจากหน้า `/shop` ที่แก้ข้อมูลร้านที่ active อยู่
- หน้านี้ต้องแสดงผลเหมือนกันไม่ว่า user จะ active อยู่ร้านไหน (ร้านธุรกิจใดก็ตาม หรือร้านส่วนตัวของตัวเอง)
- เบอร์โทรแสดงเป็นข้อมูลอ่านอย่างเดียว — ถ้ายังไม่มีเบอร์ ต้องมีทางไปสู่ flow เพิ่มเบอร์ที่มีอยู่แล้วในระบบ

**Business Rules:**
- เบอร์โทรเป็นข้อมูล **immutable** ตามกติกาเดิมของระบบ (ตั้งได้ครั้งเดียวผ่าน flow ยืนยัน OTP เท่านั้น เปลี่ยนไม่ได้ในภายหลัง เพราะมีผลต่อ Trust Score) — หน้านี้ต้องไม่มีทางแก้เบอร์โทรได้ไม่ว่าทางใด
- `username` ต้องไม่ซ้ำกับ user คนอื่นในระบบทั้งหมด (unique ระดับ global ไม่ใช่ต่อร้าน) — ต้องเช็คซ้ำทั้งฝั่งหน้าจอ (realtime) และฝั่งหลังบ้าน (กัน race condition ตอนสองคนแย่งชื่อเดียวกันพร้อมกัน)
- การแก้ไขข้อมูลส่วนตัวต้องผ่าน allow-list ของ field ที่ user แก้ไขได้เองเท่านั้น — field ที่กระทบสิทธิ์หรือคะแนนของระบบ (สิทธิ์แอดมิน, คะแนนความน่าเชื่อถือ, รหัสผ่าน, เบอร์โทร) ต้องแก้ผ่าน endpoint นี้ไม่ได้แม้แต่ทางเทคนิค
- การเพิ่มเบอร์โทรจากหน้านี้ (ผ่าน flow `set-phone` เดิม) **มีผลข้างเคียงต่อ Trust Score** — สร้าง verification ระดับ L1 (`PHONE_OTP`) ให้อัตโนมัติ ซึ่งเป็นส่วนหนึ่งของสูตรคะแนน "Verification 35%" ที่มีอยู่แล้ว ไม่ใช่ผลข้างเคียงใหม่ที่ฟีเจอร์นี้สร้าง

**เหตุผล:**
- หลักการ Profile-Centric ของ Deep ถือว่า trust profile เป็นของ "คน" ไม่ใช่ของ "ร้าน" — การปนข้อมูลส่วนตัวไว้ในหน้าตั้งค่าร้านขัดกับสถาปัตยกรรมนี้โดยตรง และสร้างความสับสนให้ user ที่มีหลายร้าน
- ระหว่างสำรวจงานนี้พบว่า API ที่ต้องต่อยอด (`PATCH /api/users/me`) เคยรับ body ดิบเข้า Prisma ตรง ๆ โดยไม่กรอง ทำให้ user คนไหนก็ยกระดับตัวเองเป็นแอดมินระบบได้ — ต้องปิดก่อนต่อยอด ไม่ปล่อยให้ฟีเจอร์ใหม่ยืนอยู่บนฐานที่ไม่ปลอดภัย (ปิดแล้วเป็น hotfix ก่อนเริ่มงานนี้ ดู §9.1)

### 3.3 ส่วน C — การเชื่อมต่อบัญชี (มีอยู่แล้วบน production — ไม่ใช่ requirement ใหม่)

> **แก้ไขจาก v1.0:** เดิมเอกสารนี้เขียน §3.3 เป็นข้อกำหนดสำหรับ implement ใหม่ทั้งหมด (ตั้งรหัสผ่าน, เชื่อม/ยกเลิก LINE·Facebook) — **ผิด**. หลังตรวจโค้ดจริงพบว่าความสามารถทั้งหมดนี้ implement เสร็จและอยู่บน `origin/main` แล้ว เป็นส่วนหนึ่งของ feature 00001 (FR-LO-16 + FR-LO-04) หัวข้อนี้จึงเปลี่ยนจาก "requirement ที่ต้องสร้าง" เป็น "ของที่มีอยู่แล้ว + ปัญหาที่แท้จริงที่ต้องแก้"

**ความสามารถที่มีอยู่แล้ว (อย่าสร้างซ้ำ):**

| ความสามารถ | อยู่ที่ | อ้างอิง |
|-----------|---------|---------|
| เชื่อม/ยกเลิกเชื่อมบัญชี LINE, Facebook, Instagram (flag-off) | หน้า `/settings` (`ConnectedAccountsClient.tsx`) | feature 00001 FR-LO-16 |
| guard "ต้องเหลือวิธี login อย่างน้อย 1 ทาง" | `POST /api/account/link/remove` | FR-LO-16-AC-09 |
| ยืนยันตัวตนด้วย OTP ก่อนยกเลิกการเชื่อมต่อ | `POST /api/account/link/send-otp` | FR-LO-16-AC-08 |
| บล็อกการเชื่อมบัญชี provider ที่ผูกกับ user อื่นอยู่แล้ว (ไม่ merge) | `signIn` callback ใน `lib/auth.ts` | FR-LO-16-AC-03/04, D2 เดิม (เฉพาะ entry point นี้ — ดู §4.3) |
| ตั้ง/รีเซ็ตรหัสผ่านผ่านการยืนยันเบอร์ด้วย OTP | `POST /api/account/set-phone` + `POST /api/account/set-password` | feature 00001 FR-LO-04 |

**ความต้องการที่แท้จริง (discoverability):**
- user ต้องหา "การตั้งค่าวิธี login ของตัวเอง" เจอจากหน้าที่ว่าด้วยตัวเอง — ปัจจุบันเมนู "บัญชีที่เชื่อมต่อ" อยู่ในกลุ่ม "STORE" (ตั้งค่าร้านค้า) ปนกับเมนูที่เป็นของร้านล้วน ๆ ทั้งที่เนื้อในผูกกับตัวคน (`AuthAccount` ผูกกับ `User.id` ไม่ใช่ `Shop.id`)
- ยืนยันเพิ่มจากการอ่าน `settings/page.tsx` จริง: หน้า `/settings` เดียวกันนี้ยังปนการ์ด "ตั้งค่าการจัดส่ง" (ผูกกับ active shop) ไว้ด้วย — ตอกย้ำว่าเป็นหน้าที่ผสมของร้านกับของคนเข้าด้วยกัน
- ไม่มีทางเข้า UI ที่พา user ที่ login อยู่แล้วไปสู่ flow "ตั้งรหัสผ่าน" เลย (`ConnectedAccountsClient.tsx` แสดงแค่ข้อความเตือนว่ายังไม่มีรหัสผ่าน ไม่มีปุ่มกดตั้ง) — ทางเดียวที่ตั้งรหัสผ่านได้จริงตอนนี้คือ flow "ลืมรหัสผ่าน" ที่ `/auth/reset-pass` ซึ่งไม่มีลิงก์จากภายในแอปที่ login แล้วเลย

**Business Rules ที่ยืนยันแล้วว่าใช้งานจริง:**
- การเชื่อมบัญชีสำเร็จต้องไม่แตะ session ที่ login อยู่ปัจจุบัน — ยืนยันจากโค้ด (`signIn` callback ผูก `AuthAccount` เข้ากับ `intent.userId` ไม่ใช่ user ที่ OAuth ส่งมา)
- ยกเลิกการเชื่อมต่อวิธี login สุดท้ายที่เหลืออยู่ต้องถูกปฏิเสธ — ยืนยันจากโค้ด (`methodsAfterRemoval < 1` → 400)

**ประเด็นที่ต้องให้ user ตัดสิน (ห้ามเขียนทับด้วยมติเดิม — ดู §4.3):**
- พฤติกรรมเมื่อเจอบัญชีซ้ำที่ระบบมีจริงตอนนี้มี **2 แบบต่างกัน** ขึ้นกับ entry point — ต้องให้ user ตัดสินว่าจะรวมเป็นแบบเดียวหรือปล่อยให้ต่างกันตามบริบทต่อไป

**เหตุผลที่ต้องแก้เอกสารส่วนนี้:**
- เอกสาร v1.0 อ้างอิงจากการอ่าน `authOptions.providers` เพียงจุดเดียวแล้วสรุปว่า "NextAuth v4 JWT strategy ไม่มี adapter → เชื่อมบัญชีไม่ได้" โดยไม่ได้ไล่ดู import ทั้งไฟล์ (`lib/auth.ts` บรรทัด 9 import `verifyLinkIntent` อยู่แล้ว) — เป็นบทเรียนเรื่อง verify-don't-assume ที่ต้องบันทึกไว้ไม่ให้เกิดซ้ำ

## 4. Business Rules & Constraints

### 4.1 กฎทางธุรกิจหลัก

| กฎ | คำอธิบาย |
|----|----------|
| **ร้านส่วนตัว 1 ต่อ user** | user หนึ่งคนมีร้านที่ `kind = PERSONAL` ได้สูงสุด 1 ร้าน บังคับที่ระดับฐานข้อมูล |
| **หน้าบัญชีส่วนตัวไม่ผูกกับร้าน active** | `/account` resolve ข้อมูลจาก identity ของ user เท่านั้น ไม่อ่าน/ไม่ผูกกับ active shop ไม่ว่ากรณีใด |
| **เบอร์โทร immutable** | ตั้งได้ครั้งเดียวผ่านการยืนยัน OTP เท่านั้น เปลี่ยนไม่ได้ตลอดชีพของบัญชี |
| **บังคับ onboarding เฉพาะร้านที่ active อยู่จริง** | การเข้า mandatory `/onboarding` (เพราะไม่มี slug) ต้องพิจารณาจาก active shop ปัจจุบันเท่านั้น ไม่ใช่จากการมีร้านส่วนตัวอยู่เฉย ๆ — สูตรถูกแยกเป็น pure function `resolveOnboardingGate()` แล้ว (`src/lib/onboarding-gate.ts`) เพื่อกันไม่ให้ `jwt`/`session` callback คำนวณไม่ตรงกัน |
| **username unique ระดับระบบ** | ไม่ซ้ำกับ user คนอื่นทั้งระบบ ไม่ใช่แค่ในร้านเดียวกัน |
| **แก้ไขข้อมูลส่วนตัวผ่าน allow-list เท่านั้น** | field ที่แก้ได้ผ่าน API ต้องประกาศไว้ชัดเจนล่วงหน้า ห้ามรับ body ดิบเข้าฐานข้อมูลโดยไม่กรอง |
| **การเชื่อม/ยกเลิกเชื่อมบัญชี provider (feature 00001 FR-LO-16)** | มีอยู่แล้ว ใช้งานได้จริง — ฟีเจอร์นี้ไม่แก้ไข ไม่สร้างซ้ำ อ้างอิงเป็น dependency เท่านั้น |
| **สิทธิ์ไม่ขึ้นกับ role บนร้านธุรกิจ** | `ShopMember.role` (OWNER/ADMIN) ไม่มีผลต่อการสร้างร้านส่วนตัว การแก้ไขข้อมูล `/account` หรือปุ่ม "กลับไปร้านเดิม" — ทั้งหมดเป็นสิทธิ์ระดับ user ไม่ใช่ระดับ role บนร้าน (ดู §4.4) |
| **ร้านส่วนตัวไม่มีคะแนนความน่าเชื่อถือของตัวเอง** | `Shop.trustScore` ถูกกำหนดไว้ในระดับ schema ว่าไม่ใช้กับ `kind = PERSONAL` (คงค่า default 0 เสมอ) — ร้านส่วนตัวแสดงคะแนนผ่าน `User.trustScore` เดิมเท่านั้น (ดู §4.5) |

### 4.2 ข้อจำกัดทางธุรกิจ

| ข้อจำกัด | รายละเอียด |
|---------|-----------|
| **ไม่ implement/แก้ไขความสามารถของส่วน C ในรอบนี้** | ความสามารถมีอยู่แล้วบน prod — งานที่เหลือ (ย้าย/เพิ่มทางเข้าจาก `/account`) เป็นการตัดสินใจ IA ที่รอ user เคาะ ไม่อยู่ใน scope การ implement รอบนี้ |
| **ไม่มี username cooldown ในรอบนี้** | หนี้ที่ค้างมาตั้งแต่ seller auth (2026-06-17) ไม่รวมอยู่ในขอบเขตของฟีเจอร์นี้ |
| **ไม่มี redirect อัตโนมัติจาก `/u/{username}` เดิมไปใหม่** | เมื่อ user เปลี่ยน username ลิงก์เก่าที่แชร์ไว้จะใช้ไม่ได้ทันที |

### 4.3 ประเด็นเปิด — พฤติกรรมเมื่อเจอบัญชีซ้ำไม่สอดคล้องกันตาม entry point (ต้องให้ user ตัดสิน)

ระบบมี **2 กลไกที่ต่างกัน** สำหรับสถานการณ์ "เจอบัญชีซ้ำ" ขึ้นกับว่าผู้ใช้เข้าทางไหน — ไม่ใช่ข้อขัดแย้งที่เกิดจากบั๊ก แต่เป็นการตัดสินใจ 2 ครั้งแยกกันในบริบทที่ต่างกัน (2026-06-18 กับ 2026-07-25) ที่ยังไม่เคยถูกเทียบกันตรง ๆ:

| Entry point | สัญญาณที่ตรวจ | พฤติกรรมจริง | อ้างอิงโค้ด |
|-------------|---------------|---------------|-------------|
| หน้า `/settings` "บัญชีที่เชื่อมต่อ" — user กด "เชื่อม" provider เอง | provider account (FB/LINE/IG) ผูกกับ Deep user อื่นอยู่แล้ว | **บล็อกเสมอ** ไม่ย้าย ไม่ลบ ไม่ merge — redirect กลับพร้อม error | `signIn` callback, `lib/auth.ts:508-514` (FR-LO-16-AC-03) |
| หน้า `/o/{token}` ตอนยืนยันเบอร์คำสั่งซื้อ — user เพิ่ง login ด้วย OAuth ใหม่ | เบอร์ที่ยืนยันตรงกับเบอร์ของ Deep user คนอื่นที่มีอยู่แล้ว | **เสนอย้าย** OAuth provider จากบัญชีใหม่ไปผูกกับบัญชีที่ถือเบอร์ — ทำได้เฉพาะเมื่อบัญชีใหม่นั้น **ไม่มีข้อมูลใด ๆ เลย** (ไม่มีออเดอร์/ร้าน/รีวิว/เบอร์อื่น) มิฉะนั้นบล็อกเช่นกัน | `verify-phone/route.ts:90-108`, `link-account/route.ts:91-104` (feature 00015 S-5) |

**สิ่งที่ต้องให้ user ตัดสิน:**
1. พฤติกรรมทั้ง 2 แบบนี้ควรคงแยกกันต่อไปตามบริบท (order-claim ต้องลดแรงเสียดทานเพราะกำลังจะบล็อกการซื้อของ vs การตั้งค่าบัญชีเป็นการกระทำที่ตั้งใจ ไม่รีบ) **หรือ** ควรรวมพฤติกรรมให้เหมือนกันทั้งระบบ
2. ถ้าจะรวม — ฝั่งไหนควรเป็นมาตรฐาน: บล็อกเสมอแบบ `/settings` (ปลอดภัยกว่า แต่ order-claim จะฝืดขึ้น) หรือเปิดทาง "ย้ายบัญชีว่างเปล่า" แบบ order-claim ให้ `/settings` ด้วย (ผู้ใช้สะดวกขึ้น แต่เพิ่ม attack surface ที่ `/settings` ซึ่งไม่มี guard "บัญชีต้นทางต้องว่างเปล่า" อยู่ในปัจจุบัน)

**ฟีเจอร์นี้ไม่ตัดสินแทน** — บันทึกไว้เป็นประเด็นเปิดเพื่อรอ user เคาะ ไม่ใช่ default เป็นแบบใดแบบหนึ่ง

### 4.4 สิทธิ์และบทบาท (Authorization)

| การกระทำ | ต้องมีสิทธิ์อะไร | ยืนยันจากโค้ด |
|----------|-------------------|----------------|
| เห็นแถว "สร้างร้านส่วนตัวของฉัน" ใน switcher | มี `ShopMember` อย่างน้อย 1 แถวบนร้าน `kind=BUSINESS` (role ใดก็ได้) **และ** ไม่มีร้าน `kind=PERSONAL` | `GET /api/business/context` (`personal: null`) + `hasBusinessMembership` ใน `lib/auth.ts` ไม่ filter role |
| สร้างร้านส่วนตัว | login แล้วเท่านั้น (ไม่ต้องมี business membership ด้วยซ้ำ — ใครก็เรียกได้ แต่ปุ่มใน UI จะโผล่เฉพาะเคส A) | `POST /api/shops/open-personal` เช็คแค่ session |

| แก้ไขข้อมูล `/account` | เจ้าของบัญชีเท่านั้น (`session.user.id`) — ไม่เกี่ยวกับ role บนร้านใด ๆ | ตาม design spec §3 "resolve จาก session.user.id อย่างเดียว" |

**สมมติฐานที่ต้องยืนยัน (A-6):** เมื่อ user มี business membership มากกว่า 1 ร้าน ปุ่ม "กลับไปร้านเดิม" จะสลับไปร้านไหน — design spec ระบุแค่ "ร้านธุรกิจแรกที่ user เป็นสมาชิก" โดยไม่นิยามลำดับ "แรก" ไว้ชัดเจน (เรียงตาม `ShopMember.createdAt` หรือลำดับอื่น) สมมติฐานของ PM คือ **เรียงตาม `ShopMember.createdAt` ascending (ร้านที่เข้าร่วมก่อน)** — ต้องยืนยันกับ user/ทีมพัฒนาก่อน implement เพราะกระทบ QA ของ user ที่มีหลายร้านธุรกิจ

### 4.6 เคสที่ระบบต้องปฏิเสธ (ส่วน A/B ที่ implement รอบนี้เท่านั้น)

- user ที่มีร้านส่วนตัวอยู่แล้วพยายามสร้างร้านส่วนตัวซ้ำ (ระบบต้อง idempotent คืนร้านเดิม ไม่ error และไม่สร้างซ้ำ)
- คำขอแก้ไข `PATCH /api/users/me` ที่มี field นอก allow-list (เช่น `isAdmin`, `trustScore`, `passwordHash`, `phone`, `successfulBidCount`) — ต้องถูกกรองทิ้งโดยไม่กระทบ field ที่อนุญาต
- `username` ที่ซ้ำกับ user อื่น (รวมถึงกรณี race condition สองคนตั้งชื่อเดียวกันพร้อมกัน)
- user ที่ไม่มี business membership เลยพยายามกดปุ่ม "กลับไปร้านเดิม" (ต้องไม่ปรากฏปุ่มนี้ให้กดตั้งแต่แรก)

### FR-PAC-10 — ตั้ง/เปลี่ยนรหัสผ่านจากหน้า `/account` (เพิ่ม 2026-08-02)

**ที่มา:** user ถามระหว่างทดสอบว่า "สร้าง user password ยังไง" แล้วพบว่าทำจากในระบบไม่ได้เลย

| # | ข้อกำหนด |
|---|----------|
| 10.1 | การ์ด "วิธีเข้าสู่ระบบ" ต้องมีแถว **รหัสผ่าน** อยู่บนสุด แสดงสถานะ `ตั้งแล้ว` / `ยังไม่ได้ตั้ง` / `ต้องเพิ่มเบอร์โทรก่อน` |
| 10.2 | บัญชีที่**ยังไม่มีเบอร์โทร** ตั้งรหัสผ่านไม่ได้ (ปุ่ม disabled) — ต้องเพิ่มเบอร์ที่การ์ด "ข้อมูลส่วนตัว" ก่อน (มติ D3) |
| 10.3 | การตั้ง/เปลี่ยนรหัสผ่านต้องยืนยันด้วย **OTP ทางเบอร์เสมอ** แม้ผู้ใช้จะล็อกอินอยู่แล้ว — session อย่างเดียวไม่พอ เพราะเครื่องที่เปิดทิ้งไว้จะถูกยึดบัญชีได้ทันที |
| 10.4 | client **ห้ามรู้เบอร์จริง** — endpoint resolve เบอร์จาก session และคืนกลับเฉพาะรูปแบบที่ปิดบังแล้ว (`081xxxx678`) |
| 10.5 | รหัสผ่านต้องผ่าน `isStrongPassword` (≥8 ตัว มีตัวอักษร + ตัวเลข + อักขระพิเศษ) — SSOT เดียวกับ seller auth เดิม |
| 10.6 | หลังตั้งรหัสผ่านแล้ว login ตรงได้ด้วย **username + password** (provider `seller-credentials`) — ไม่ใช่เบอร์ + password |

**Acceptance**
- บัญชีที่ไม่มีเบอร์ → ปุ่ม "ตั้งรหัสผ่าน" กดไม่ได้ และ badge บอกว่าต้องเพิ่มเบอร์ก่อน
- เพิ่มเบอร์แล้ว → ปุ่มกดได้ → ได้ OTP → ตั้งรหัสผ่านสำเร็จ → badge เปลี่ยนเป็น "ตั้งแล้ว"
- ใส่รหัสผ่านที่อ่อนเกิน (ไม่มีอักขระพิเศษ) → ขึ้น error ในโมดัล ไม่บันทึก และ **ไม่เผา OTP ทิ้ง**
- ใส่ OTP ผิด → ขึ้น error ไม่บันทึก
- ขอ OTP เกินโควตา (3 ครั้ง/10 นาที ต่อเบอร์) → 429

### FR-PAC-11 — เตือนบัญชีที่กู้คืนไม่ได้ (เพิ่ม 2026-08-02)

บัญชีที่**ไม่มีทั้งเบอร์และรหัสผ่าน** (login ได้ทางเดียวคือ OAuth) ต้องเห็นแถบเตือนบนหน้า `/account` ว่าถ้าเข้า provider นั้นไม่ได้จะกู้บัญชีไม่ได้เลย พร้อมชี้ทางไปเพิ่มเบอร์

**ทำไมเตือนไม่บังคับ (user ตัดสิน 2026-08-02):** การบังคับเพิ่มเบอร์ตอน login OAuth ครั้งแรกจะเพิ่มแรงเสียดทานให้ผู้ถูกเชิญ ซึ่งเป็นกลุ่มเดียวกับที่ feature นี้เพิ่งลดให้

**ขนาดของปัญหา ณ วันที่บันทึก:** 5 จาก 10 บัญชีบน prod อยู่ในสถานะนี้

## 5. Out of Scope (นอกขอบเขต)

| หัวข้อ | คำอธิบาย |
|--------|----------|
| **สร้าง/แก้ไข capability ของส่วน C** | มีอยู่แล้วบน prod (feature 00001 FR-LO-16 + FR-LO-04) — ฟีเจอร์นี้ไม่แก้โค้ดของ `ConnectedAccountsClient.tsx`, `/api/account/link/*`, `signIn` callback, `account-merge-ticket.ts`/`link-account` เลย |
| **ย้าย/เพิ่มทางเข้า "บัญชีที่เชื่อมต่อ" จาก `/account`** | เป็นงาน IA ที่รอ user ตัดสิน (ดู §3.3) และรอข้อเสนอจาก `safepay-ux` — ไม่อยู่ใน scope การ implement รอบนี้ |
| **รวมพฤติกรรมการจัดการบัญชีซ้ำให้เหมือนกันทั้งระบบ** | ประเด็นเปิดตาม §4.3 — รอ user ตัดสินก่อนว่าจะรวมหรือคงแยก |
| **Merge บัญชีซ้ำที่มีข้อมูลจริง** | ทั้ง 2 flow ที่มีอยู่ (`/settings` และ `/o/{token}`) ปฏิเสธการ merge บัญชีที่มีข้อมูลอยู่แล้วเหมือนกัน — ไม่มีแผนเปลี่ยนพฤติกรรมนี้ |
| **Username cooldown 30 วัน** | หนี้เดิมที่ค้างมาตั้งแต่ feature seller auth (2026-06-17) ไม่รวมในขอบเขตนี้ |
| **Instagram linking แบบเปิดใช้งานจริง** | provider ปิด flag อยู่ (`NEXT_PUBLIC_ENABLE_IG_LOGIN`) — ไม่เปิดในฟีเจอร์นี้ (ไม่เกี่ยวกับฟีเจอร์นี้อยู่แล้ว เพราะเป็นเรื่องของ feature 00001) |
| **แก้เบอร์โทร** | ยึดตามกฎ immutable เดิมของระบบ ไม่มีทางแก้เบอร์แม้แต่ในหน้า `/account` |
| **Redirect `/u/{username}` เก่า → ใหม่** | เมื่อเปลี่ยน username ลิงก์เก่าใช้ไม่ได้ทันที ไม่มีกลไก redirect ในรอบนี้ |
| **ปรับสูตร Trust Score / Tier mapping** | ฟีเจอร์นี้ไม่แตะสูตรคะแนนหรือ mapping tier ใด ๆ — อ้างอิงพฤติกรรมเดิมทั้งหมด (ดู §4.5) |

## 6. Risks & Mitigation (ความเสี่ยงและแนวทางแก้ไข)

### 6.1 ความเสี่ยงทางธุรกิจ

|-----------|---------|-----------------|-------------|
| **user สับสนระหว่างร้านส่วนตัวกับร้านธุรกิจที่ตัวเองเป็นแอดมิน** | กดสร้างร้านส่วนตัวโดยไม่ตั้งใจ หรือกลัวว่าจะเสียสิทธิ์ในร้านธุรกิจเดิม | กลาง | Swal confirm อธิบายชัดก่อนสร้างจริง + มีปุ่ม "กลับไปร้านเดิม" ที่หน้า onboarding เสมอ |

| **user คาดหวังว่าปัญหา discoverability ของ C ถูกแก้ในรอบนี้** | ผิดหวังถ้าเข้าใจผิดว่าเมนูจะถูกจัดใหม่ทันที | กลาง | ระบุชัดว่า C "มีอยู่แล้วแต่ยังไม่ย้าย/เพิ่มทางเข้า — รอการตัดสินใจ" ทั้งใน PRD/BRD |

### 6.2 ความเสี่ยงทางเทคนิค

| ความเสี่ยง | ผลกระทบ | แนวทางแก้ไข |
|-----------|---------|-------------|
| **แก้สูตร `resolveOnboardingGate`/`needsOnboarding`/`needsRegistration` ผิด** | seller ปกติ (ไม่เกี่ยวกับฟีเจอร์นี้) หลุด onboarding gate เดิม หรือถูกล็อกผิดจังหวะ | Vitest ครอบสูตรครบ 7 เคสแล้วที่ `src/lib/onboarding-gate.test.ts` (ยืนยันจากโค้ดจริง — มากกว่า 4 เคสที่ design spec เดิมระบุ) + E2E เคส "มีร้านแล้วไม่มี slug ต้องยังโดนบังคับ" |

| **หน้า `/account` เผลอผูกกับ active shop** | ทำลายหลักการ "ตั้งค่าของคน ไม่ใช่ของร้าน" ที่เป็นแกนของฟีเจอร์นี้ | reviewer gate: grep `requireActiveShop`/`activeShopId` ในไฟล์ใหม่ของหน้านี้ต้องเป็น 0 |
| **RSC serialize ข้อมูลส่วนตัวเกินจำเป็น** | หน้า `/account` อยู่ใต้ client layout (`VerticalLayout`) เหมือนหน้า seller อื่นที่เคยพบปัญหา PII รั่วผ่าน flight payload มาก่อน | ตรวจ field ที่ serialize ลง client เฉพาะที่ UI ใช้จริง ไม่ pass ทั้ง object ของ user ไปดิบ ๆ |
| **B0 (`PATCH /api/users/me`) เป็น API ที่ buyer app ใช้อยู่ด้วย** | แก้ allow-list ผิดอาจกระทบฝั่ง buyer ที่เรียก endpoint เดียวกัน | เช็ค call-site ทั้งโปรเจกต์ก่อนแก้ (ทำไปแล้วในหมัดฟิกซ์ `eb32a937`) — ฟีเจอร์นี้ต่อยอดบน schema เดิมโดยเพิ่ม field ที่จำเป็น (เช่น email) ไม่แก้ field ที่มีอยู่แล้ว |
| **มีคนแก้เมนู `_seller-menu.ts` ย้าย "บัญชีที่เชื่อมต่อ" กลับไปกลุ่ม auto-reply โดยไม่อ่านประวัติ** | คอมเมนต์ในไฟล์ (`_seller-menu.ts:111-114`) เตือนไว้แล้วว่า "ห้ามย้ายกลับมาอีก" หลังเคยย้ายแล้วพบว่าไม่ถูก — ความเสี่ยงนี้มีอยู่ก่อนฟีเจอร์นี้ ไม่ใช่ risk ใหม่ที่ฟีเจอร์นี้สร้าง แต่ทีมที่จะมาแก้ IA ของ C ในอนาคตต้องอ่าน comment นี้ก่อนเสนอย้าย | บันทึกไว้ใน §3.3 ให้ทีมถัดไปอ่านก่อน |
| **โค้ดบางส่วนของ A (`onboarding-gate.ts`) implement ไปก่อนเอกสารนี้ผ่าน review** | อาจขัด Hard Rule 11 (Documentation-First) ถ้าไม่ใช่การตัดสินใจของ Controller โดยตรง | รายงานให้ Controller ทราบ (ดู Executive Summary) — เป็นการ refactor ที่แยก logic ที่มีอยู่แล้วออกมาเป็น pure function พร้อม test ไม่ใช่การเพิ่มพฤติกรรมใหม่ที่ยังไม่ผ่าน review ความเสี่ยงจึงต่ำ แต่ต้องบันทึกไว้เพื่อความโปร่งใส |

## 7. Glossary (อภิธานศัพท์)

| คำศัพท์ | ความหมาย |
|---------|----------|
| **ร้านส่วนตัว (PERSONAL shop)** | ร้านที่ `Shop.kind = PERSONAL` ผูกกับตัวตนของ user โดยตรง สร้างได้สูงสุด 1 ร้านต่อคน ไม่มีคะแนนความน่าเชื่อถือของตัวเอง |
| **ร้านธุรกิจ (BUSINESS shop)** | ร้านที่ `Shop.kind = BUSINESS` มีสมาชิกได้หลายคนผ่าน `ShopMember` มีคะแนนความน่าเชื่อถือแยกของตัวเอง (`Shop.trustScore`) |
| **Account switcher** | ส่วน UI (desktop dropdown + มือถือ sheet) ให้ user สลับ active shop ระหว่างร้านที่ตัวเองเข้าถึงได้ |
| **Onboarding wizard** | หน้า `/onboarding` แบบ mandatory ที่บังคับ setup ร้าน (หมวดหมู่ → slug → ที่อยู่ → สินค้าแรก) เมื่อร้านที่ active อยู่ยังไม่มี slug |
| **Invite link** | ลิงก์เชิญ (`/i/<slug>`) จาก feature 00012 ที่พา user เข้าเป็น `ShopMember(role=ADMIN)` ของร้านธุรกิจ |
| **AuthAccount** | ตารางที่เก็บการผูกบัญชี Deep user เข้ากับ provider ภายนอก (LINE/Facebook) หนึ่งแถวต่อหนึ่ง provider account |
| **Allow-list** | รายการ field ที่อนุญาตให้แก้ไขผ่าน API หนึ่ง ๆ อย่างชัดเจน — ตรงข้ามกับการรับ body ดิบทั้งก้อนเข้าฐานข้อมูล |
| **FR-LO-16** | Functional Requirement ของ feature 00001 (Login & Onboarding) — "Account Linking: เชื่อมหลาย provider เข้าบัญชีเดียว" ความสามารถของส่วน C ของฟีเจอร์นี้ |
| **บล็อก (block)** | เมื่อเจอบัญชี/provider ซ้ำ — ปฏิเสธการกระทำ ไม่แก้ไขข้อมูลใด ๆ ทั้งสองฝั่ง |
| **ย้าย (move)** | เมื่อเจอบัญชีซ้ำในบริบทเฉพาะของ order-claim — ย้ายเฉพาะแถว `AuthAccount` (วิธี login) จากบัญชีว่างเปล่าไปอีกบัญชี ไม่ใช่การรวมข้อมูลธุรกิจ (order/review/trust score) |
| **`resolveOnboardingGate`** | pure function ใน `src/lib/onboarding-gate.ts` — SSOT เดียวของสูตร "ต้องบังคับ user ไปลงทะเบียน/ตั้งค่าร้านก่อนใช้งานไหม" ที่ทั้ง `jwt` และ `session` callback เรียกใช้ร่วมกัน |

### 9.2 สมมติฐาน (Assumptions)

- **A-1:** ทางเข้าหน้า `/account` มี 2 จุดตามที่ design spec ระบุ — `UserDropdownDetailed.tsx` (desktop) และ `AccountSwitcherSheet.tsx` (มือถือ) เท่านั้น ไม่ต้องเพิ่มทางเข้าอื่น
- **A-2 (แก้ 2 รอบ):** v1.0 บอกว่าต้องเขียน OAuth link flow ใหม่ทั้งเส้น (ผิด — มีอยู่แล้ว); v1.1 แก้เป็น "ส่วน C ไม่ต้อง implement ใหม่เลย" (**ผิดอีกครั้ง** — ส่วน OAuth มีอยู่แล้วจริง แต่ส่วนรหัสผ่านไม่เคยมี). ข้อสรุปที่ถูก: **OAuth linking = มีอยู่แล้ว ไม่แตะ; username/password = สร้างใหม่ในรอบนี้ (FR-PAC-10)**. บทเรียน: อ่านว่าไฟล์/โฟลเดอร์ *ทำอะไร* ก่อนสรุปว่าฟีเจอร์มีอยู่แล้ว — การเห็นชื่อ `/api/account/link/*` กับ `ConnectedAccountsClient.tsx` ไม่ได้แปลว่าครบทุกวิธี login
- **A-3:** ไม่มี migration ฐานข้อมูลใหม่สำหรับส่วน A และ B — schema ที่มีอยู่ (`Shop.kind`, partial unique index, `User.username/avatar/email/passwordHash`, `AuthAccount`) รองรับครบแล้ว
- **A-4 (ยกเลิกจาก v1.0):** ~~งาน console ฝั่ง LINE Developers/Meta App เป็นความรับผิดชอบของ user เอง~~ — ไม่จำเป็นแล้ว เพราะไม่มี OAuth flow ใหม่ถูกสร้าง (flow ที่ใช้จริงคือ callback ของ NextAuth ที่ลงทะเบียนไว้อยู่แล้วตั้งแต่ feature 00001)
- **A-5:** ผู้ถูกเชิญที่จะได้ประโยชน์จากส่วน A มี business membership อยู่แล้วเสมอ (`AccountSwitcherLauncher.tsx` ไม่ mount sheet เลยถ้า `!hasBusinessMembership` — ไม่กระทบ persona เป้าหมายของฟีเจอร์นี้)
- **A-6 (ใหม่ — ต้องยืนยัน):** ปุ่ม "กลับไปร้านเดิม" เมื่อ user มีร้านธุรกิจมากกว่า 1 ร้าน จะสลับไปร้านที่มี `ShopMember.createdAt` เก่าที่สุด (เข้าร่วมก่อน) — design spec ไม่ได้นิยามลำดับไว้ชัดเจน สมมติฐานนี้ต้องยืนยันก่อน implement
- **A-7 (ใหม่):** โค้ดส่วน `resolveOnboardingGate()` ที่พบว่ามีอยู่แล้วในสาขานี้ ถือเป็นงานเตรียมการ (prep refactor) ที่ Controller อนุมัติไว้ล่วงหน้า ไม่ใช่การข้าม Documentation-First — สมมติฐานนี้ต้อง Controller ยืนยัน

## 10. Appendix

### 10.1 ตัวอย่าง User Journey

**Scenario A: ผู้ถูกเชิญกดสร้างร้านส่วนตัวจาก account switcher**

1. ผู้ถูกเชิญกดลิงก์เชิญ (`/i/<slug>`) → login → accept → กลายเป็น `ShopMember(role=ADMIN)` ของร้าน BT ธนภัทร ตามปกติของ feature 00012
2. วันหนึ่งอยากขายของเอง เปิด account switcher (มือถือหรือ desktop) เห็นแถวใหม่ "สร้างร้านส่วนตัวของฉัน"
3. กด → เห็น Swal confirm อธิบายว่าจะพาไปตั้งค่าร้านต่อ → กดยืนยัน
4. ระบบเรียก `POST /api/shops/open-personal` → สลับ active shop เป็นร้านส่วนตัวที่สร้างใหม่ → พาเข้า `/onboarding`
5. ระหว่างทำ onboarding เห็นปุ่ม "กลับไปร้านเดิม" — กดแล้วสลับกลับไปร้าน BT ธนภัทรได้ทันทีโดยไม่ต้องตั้งค่าร้านส่วนตัวให้เสร็จก่อน
6. กลับมาทำต่อภายหลัง ตั้ง slug/หมวดหมู่/สินค้าแรกจนจบ → เข้า dashboard ร้านส่วนตัว — เห็นคะแนนความน่าเชื่อถือเป็นค่าเดิมที่มีอยู่แล้ว ไม่ใช่ 0

**Scenario B: ผู้ใช้ LINE login แก้รูปโปรไฟล์**

1. user login ด้วย LINE ครั้งแรก — รูปโปรไฟล์ถูกดึงมาจาก LINE อัตโนมัติ
2. เปิด account switcher → กดเข้าเมนู "บัญชีของฉัน" (`/account`)
3. เห็นการ์ด "ข้อมูลส่วนตัว" กดอัปโหลดรูปใหม่ → บันทึก
4. topbar อัปเดตรูปทันทีโดยไม่ต้อง re-login (ผ่าน `session.update()`)

**Scenario C (อ้างอิงพฤติกรรมปัจจุบัน — ไม่ใช่ของฟีเจอร์นี้): user ต้องการตั้งรหัสผ่านสำรอง**

1. user login ด้วย Facebook เท่านั้น ต้องการตั้งรหัสผ่านสำรองไว้กันบัญชี Facebook เข้าไม่ได้
2. **ปัจจุบัน:** ทางเดียวที่ทำได้คือไปที่ `/auth/reset-pass` เอง (ไม่มีลิงก์จากในแอปพาไป) → กรอกเบอร์ → OTP → ตั้งรหัสผ่านใหม่
3. เชื่อมโยงกับฟีเจอร์นี้: ถ้าในอนาคตมีการเพิ่มทางเข้าจาก `/account` (ตาม §3.3) user จะกดจากในแอปได้ตรง ๆ — แต่ **ไม่ใช่ scope ของรอบนี้**

### 10.2 ร่าง Scope Baseline — phase นี้

**อยู่ในขอบเขต (A + B — implement รอบนี้):**

| รายการ | หมายเหตุ |
|--------|---------|
| แถว "สร้างร้านส่วนตัวของฉัน" ใน account switcher ทั้ง 2 จุด | render เมื่อ `context.personal === null` |
| แก้สูตร `needsOnboarding`/`needsRegistration` ให้ผูกกับ active shop | ผ่าน `resolveOnboardingGate()` — logic มีอยู่แล้ว เหลือแค่ต่อสาย UI (A1/A3) |

| หน้า `/account` การ์ดข้อมูลส่วนตัว (avatar/displayName/username/email แก้ได้, phone read-only) | ไม่ผูกกับ active shop |
