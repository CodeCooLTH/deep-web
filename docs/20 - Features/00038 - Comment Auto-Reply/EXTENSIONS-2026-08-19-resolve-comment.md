# 00038 — Extension (2026-08-19): ปิดคิว "ยังไม่ตอบ" ที่ตอบไม่ได้แล้ว (Resolve / Mark Done)

> เอกสารนี้ต่อท้าย `BRD.md` / `SRS.md` / `DATABASE.md` ของ 00038 — เขียนก่อนแตะโค้ดตาม Hard Rule 11

## 0. ปัญหาที่ยืนยันจากข้อมูลจริงบน prod (ไม่ใช่การประมาณ)

### 0.1 คิว "ยังไม่ตอบ" ไม่มีทางลดลงสำหรับคอมเมนต์ที่ตอบไม่ได้แล้วหรือถูกข้ามโดยตั้งใจ

สถานะทั้งหมดของคอมเมนต์ (`CommentAnswerState`) ถูก derive จาก "คำตอบที่ระบบเรามองเห็น" เท่านั้น
(`deriveCommentState()` ใน `src/services/page-comment.service.ts`) — คอมเมนต์ที่พ้นหน้าต่างทักแชท
7 วันไปแล้ว หรือที่แอดมินตั้งใจข้าม (ไม่ใช่คำถามจริง/ไม่เกี่ยวกับสินค้า) ไม่มีทางถูกทำเครื่องหมาย
ว่า "จัดการแล้ว" เลย ตัวเลขบนแท็บจึงโตขึ้นเรื่อย ๆ จนเลิกเป็นสัญญาณที่เชื่อได้ — จอจริงตอนนี้
**"ยังไม่ตอบ 56"**

### 0.2 กด "ทักแชท" ซ้ำแล้วเจอ error เดิมไม่รู้จบ — `#10900 Activity already replied to`

error นี้แปลว่าเพจเคยทัก private reply คอมเมนต์นั้นไปแล้ว **จาก Business Suite/Page Inbox โดยตรง**
(Meta ให้ทักได้ครั้งเดียวต่อคอมเมนต์ ไม่สนว่าใครเป็นคนกด) ฝั่ง Deep ไม่มี log ของการทักจากนอกระบบ
จึงยังโชว์ปุ่ม "ทักแชท" กดได้ + นับถอยหลังต่อไปเหมือนไม่มีอะไรเกิดขึ้น

ยืนยันแล้ว **25 ครั้ง** บน prod ล่าสุด 2026-08-19 สองครั้งติดกัน (คอมเมนต์ของ Ming Mingnon 15 ส.ค.
และ สมชาย หมึกแดง 17 ส.ค. บนเพจ "ธนภัทร์ อะไหล่มอเตอร์ไซค์ สายซิ่ง") — มีห้องแชทอยู่จริง ข้อความใบแรก
คือ "สวัสดีค่า" ส่งหลังคอมเมนต์ 6-11 นาที และมาทาง **webhook echo** (ส่งจากนอก Deep ไม่ใช่ระบบเรา)

### 0.3 ข้อความ error ปัจจุบันเชิญให้กดสิ่งที่ไม่มีวันสำเร็จ

route แมป `SEND_FAILED` → `502 UPSTREAM_ERROR` → ข้อความหน้าจอ **"ส่งไม่สำเร็จ ลองใหม่อีกครั้ง"**
เป็นข้อความเดียวกันไม่ว่าสาเหตุจริงจะเป็นอะไร — คลาสความผิดพลาดเดียวกับที่โปรเจกต์นี้เคยพลาดมาแล้ว
ฝั่ง iShip (ดู §8): จัด error ถาวรให้เป็น retryable แล้วชวนผู้ใช้กดวนซ้ำสิ่งที่พังแน่นอน 100%

## 1. Goal

ให้ผู้ขายปิดคิว "ยังไม่ตอบ" ของคอมเมนต์ที่ตอบไม่ได้แล้วหรือตั้งใจข้ามได้ด้วยตัวเอง (ด้วยมือหรือ
อัตโนมัติเมื่อ Facebook ยืนยันว่าทักไปแล้วจากที่อื่น) โดยไม่เพิ่มสถานะ/แท็บใหม่ และไม่ปิดกั้นการ
ตอบจริงที่ยังทำได้อยู่

## 2. User Stories

> ในฐานะแอดมินร้านที่มีคิวคอมเมนต์ค้าง 56 รายการ ฉันต้องการปิดรายการที่รู้อยู่แล้วว่าตอบไม่ได้
> (เกิน 7 วัน / ไม่ใช่คำถามจริง) ออกจากคิว เพื่อให้ตัวเลขที่เหลือเป็นงานที่ต้องทำจริง ๆ

> ในฐานะแอดมินร้าน ฉันไม่ต้องการกดปุ่ม "ทักแชท" ซ้ำแล้วเจอ error เดิม ทั้งที่ Facebook บอกชัดแล้ว
> ว่ามีคนทักคอมเมนต์นี้ไปแล้ว เพื่อไม่ให้เสียเวลากับสิ่งที่ไม่มีวันสำเร็จ

> ในฐานะแอดมินร้าน ฉันต้องกดยกเลิกการปิดคิวได้ถ้าปิดผิด เพราะการข้ามงานเป็นการตัดสินใจของคน
> ต้องแก้ไขได้เหมือนการกระทำอื่น ๆ ในระบบ

| **D-1** | เพิ่ม `PageComment.resolvedAt` (`DateTime?`) + `resolvedByUserId` (`String?`) + `resolvedReason` (`String?` — `'MANUAL'` \| `'ALREADY_REPLIED_EXTERNALLY'`) **additive ล้วน ไม่มี backfill** | แถวเดิมทั้งหมด = `NULL` ทั้ง 3 คอลัมน์ ถูกต้องอยู่แล้ว เพราะปุ่มนี้ไม่เคยมีมาก่อนวันนี้ ไม่มีใครเคย mark done จริง |

| **D-4** | กลับคำได้ (unresolve) | การข้ามเป็นการตัดสินใจของคน ต้องถอยได้เหมือนการกระทำอื่นในระบบ |
| **D-5** | สิทธิ์ = คนที่เข้าถึงร้านนั้นได้ (`canAccessShop`) เหมือนปุ่มทักแชท ไม่ใช่ owner-only | งานจัดการคิวประจำวัน ไม่ใช่การตั้งค่าระดับร้าน |
| **D-6** | `resolvedByUserId` เป็น **plain String ไม่ผูก FK** | ตามแพตเทิร์นเดิมของตารางเดียวกัน (`PageComment.repliedByUserId` และ `ShopChannel.connectedByUserId`) — คอมเมนต์ต้องไม่ถูกลากหายไปกับ user ที่ถูกลบ และคอลัมน์นี้เป็นบันทึกว่า "ใครกด" ไม่ใช่ความสัมพันธ์ที่ต้อง join |

| **D-7** | บังคับความถูกต้องของคู่ค่าที่ **ชั้นฐานข้อมูล** ด้วย CHECK 2 ตัว | `PageComment_resolvedReason_check` (ค่าที่ไม่รู้จักเขียนไม่ลง — แพตเทิร์นเดียวกับ `Shop_vertical_check`) และ `PageComment_resolved_pair_check` (`resolvedAt IS NULL` ต้องเท่ากับ `resolvedReason IS NULL`) เพราะแถวที่มีเวลาแต่ไม่มีเหตุผลอ่านได้สองแบบตลอดไปโดยไม่มีใครรู้ว่าอันไหนถูก |

## 4. Functional Requirements (ต่อ BRD §2.4 — เลขต่อจาก FR-CR-14)

### FR-CR-15 — "ทำเครื่องหมายว่าจัดการแล้ว" (mark done ด้วยมือ)

- ทางเข้าอยู่ที่แถวคอมเมนต์ในคอลัมน์ซ้าย **เฉพาะคอมเมนต์ที่สถานะปัจจุบันคือ "ยังไม่ตอบ"** (คอมเมนต์
  ที่ตอบแล้วไม่มีทางเข้านี้ — ไม่มีอะไรต้องปิด)
- กดแล้วปิดทันที **ไม่มีกล่องยืนยัน** (ต่างจาก FR-CR-10 ของ private reply เพราะย้อนกลับได้เสมอผ่าน
  FR-CR-17 — ไม่ใช่การส่งข้อความจริงออกไปหาลูกค้าที่ย้อนไม่ได้)
- คอมเมนต์ที่ mark done หลุดจากชิป/แท็บ "ยังไม่ตอบ" **และ** "หมดอายุ" ทันที ไม่ต้องรีเฟรชหน้า
- ไม่ลบคอมเมนต์ ไม่แตะปุ่มตอบ/ทักแชทเดิม — ถ้ายังอยู่ในหน้าต่าง 7 วัน ยังกดตอบ/ทักได้ตามปกติ
  (mark done ไม่ใช่การปิดกั้นความสามารถของระบบ เป็นแค่การบอกว่า "ไม่ต้องนับเป็นงานค้างอีกต่อไป")

### FR-CR-16 — ปิดคิวอัตโนมัติเมื่อ Facebook ปฏิเสธเพราะเคยทักไปแล้วนอกระบบ

- เมื่อ Graph ตอบรหัส **`#10900` (Activity already replied to)** ตอนกด "ทักแชท" (ทั้ง AUTO และ
  MANUAL) ระบบตั้งคอมเมนต์นั้นเป็น resolved อัตโนมัติทันที โดยไม่ต้องมีคนกด
- ปุ่ม "ทักแชท" ของคอมเมนต์นั้นกดไม่ได้อีก — ข้อความอธิบายต้องบอกว่ามาจากที่อื่น ไม่ใช่จากระบบเรา
- ข้อความ error ที่ร้านเห็น **ต้องไม่ใช่ข้อความที่ชวนให้กดลองใหม่** (ดู §8)

### FR-CR-18 — "ทำเครื่องหมายทั้งหมด" ของแท็บ "หมดอายุ" (รอบสอง 2026-08-19)

> user: "พวก หมดอายุ ให้ทำ mark all ด้วยได้ไหม"

- ปุ่มโผล่ **เฉพาะแท็บ "หมดอายุ" และเฉพาะเมื่อมี ≥1 รายการ** (count = 0 → ซ่อนทั้งแถว ไม่ใช่ปุ่มตายที่ขึ้น "(0)")
- ทำงานตาม **เกณฑ์** (ทุกใบที่เข้าเงื่อนไขในขอบเขตที่กรองอยู่) ไม่ใช่ตาม "แถวที่โหลดมาแล้ว" —
  ไม่งั้นกดแล้วตัวเลขไม่ลงเป็น 0 ผู้ใช้จะกดวนไม่รู้จบ
- มีกล่องยืนยันเสมอ (ต่างจาก FR-CR-15 ที่กดแล้วจบทันที) บอก **จำนวน** + **ขอบเขต** (เพจไหน/ช่องทางไหน)
  + บอกว่ายกเลิกทีละรายการได้ทีหลัง — ต้องอยู่ในกล่องยืนยัน ไม่ใช่หลังทำเสร็จ (ผิดเวลาช่วยอะไรไม่ได้)
  โฟกัสเริ่มต้นที่ปุ่ม "ยกเลิก" (`focusCancel`) เพราะกระทบหลายสิบแถวพร้อมกัน
- toast บอก **จำนวนที่แตะจริง** จาก response ไม่ใช่ตัวเลขที่ค้างอยู่ตอนกด (ระหว่างอ่านกล่องยืนยัน
  เพื่อนร่วมทีมอาจปิดไปแล้วบางใบ)
- แท็บว่างหลังกด → empty state เฉพาะ ("ไม่มีคอมเมนต์ที่หมดอายุ") **ห้ามใช้ "ไม่พบตามตัวกรอง"** ซึ่งชวนให้
  ผู้ใช้ไปงมตัวกรองหาของที่ไม่มีอยู่จริง — แย่ที่สุดตอนเพิ่งเคลียร์เองกับมือ

### FR-CR-17 — ยกเลิกการทำเครื่องหมาย (unresolve)

- ใช้ได้ **ไม่ว่า `resolvedReason` เป็นค่าไหน** — ให้ผู้ใช้เป็นคนตัดสินว่าจะกลับคำ ไม่ใช่ระบบตัดสิน
  แทนว่าเคสไหนแก้ไม่ได้ (เผื่อกรณี Graph ตอบผิดพลาด)
- กดแล้วคอมเมนต์กลับเข้าคิว **ด้วยสถานะที่คำนวณจริง ณ ตอนนั้น** ไม่ใช่ค่าตายตัวว่าต้องเป็น
  "ยังไม่ตอบ" เสมอ (BR-CR-R2)

## 5. Business Rules (ต่อ BRD §8 — กลุ่มใหม่ §8.4)

| รหัส | กฎ |
|---|---|
| **BR-CR-R1** | resolved **ไม่ใช่สถานะที่ 4** — คอมเมนต์ resolved ที่ยังไม่มีคำตอบสาธารณะ/private reply สำเร็จ ถูกนับเป็น **HUMAN_ANSWERED** ในตัวนับ/ตัวกรอง/badge เดิมทั้งหมด (D-2) หน้าจอแยกแยะด้วยป้ายเสริมที่อ่าน `resolvedReason` แทน |
| **BR-CR-R2** | **ลำดับความสำคัญเมื่อคำนวณสถานะ** (ห้ามสลับ): (1) มีคำตอบสาธารณะ → ตามเดิม (BR-CR-S1) (2) ไม่มีคำตอบสาธารณะแต่ private reply สำเร็จ → ตามเดิม (3) ไม่เข้า (1)-(2) แต่ `resolvedAt IS NOT NULL` → HUMAN_ANSWERED **(ใหม่)** (4) ไม่เข้าเงื่อนไขไหนเลย → UNANSWERED. เหตุผลที่ resolved อยู่ท้ายสุดก่อน UNANSWERED: คำตอบจริงที่มองเห็นได้บอกได้ด้วยว่า "ใครตอบ" (คน/บอท) ส่วน resolved บอกได้แค่ว่า "ไม่ต้องทำอะไรต่อ" — สลับลำดับเมื่อไหร่ คอมเมนต์ที่บอทตอบแล้วและถูกกดข้ามด้วยจะเปลี่ยนจาก BOT_ANSWERED เป็น HUMAN_ANSWERED โดยไม่มีใครสั่ง |
| **BR-CR-R3** | 🛑 **SQL CASE ของ `countCommentStatesByShop()`/`countCommentPostStatesByShop()` ต้องเรียงตรงกับ `deriveCommentState()` บรรทัดต่อบรรทัด** — ไฟล์นั้นเขียนคำเตือนนี้ไว้เองแล้ว และเคยทำให้จอขึ้น "ยังไม่ตอบ 7 กับ 8" มาแล้ว ต้องผูกเทส `[blocker]` ในชุดเดิม |
| **BR-CR-R4** | `resolvedReason` มี 2 ค่าเท่านั้น (`MANUAL` / `ALREADY_REPLIED_EXTERNALLY`) บังคับด้วย CHECK ที่ชั้นฐาน (D-7) และตัวแปลงฝั่ง TS ต้อง fail-closed (ค่าที่ไม่รู้จัก → `null` ไม่ใช่ตกไปเป็นค่าใดค่าหนึ่ง) |
| **BR-CR-R5** | unresolve ล้าง `resolvedAt`/`resolvedByUserId`/`resolvedReason` **ทั้ง 3 คอลัมน์พร้อมกันเสมอ** — บังคับด้วย CHECK คู่ (D-7) |
| **BR-CR-R6** | สิทธิ์ mark done / unresolve = `canAccessShop` ระดับเดียวกับปุ่ม "ทักแชท" ไม่ใช่ owner-only |
| **BR-CR-R7** | `ALREADY_REPLIED_EXTERNALLY` **สงวนให้ระบบตั้งเองเท่านั้น** — route ที่รับคำสั่งจากผู้ใช้ต้องส่ง `MANUAL` เสมอ ไม่งั้นผู้ใช้ปลอมข้อเท็จจริงที่ควรมาจาก Meta ได้ แล้วจอจะบอกว่า "เพจทักไปแล้ว" ทั้งที่ไม่เคยทัก |
| **BR-CR-R10** | 🛑 **"ทำเครื่องหมายทั้งหมด" มีได้เฉพาะเกณฑ์ "หมดอายุ" เท่านั้น และด่านต้องอยู่ใน *รูปร่างของ API* ไม่ใช่ใน *วินัยของผู้เรียก*** — `resolveAllExpiredComments()` เขียนเงื่อนไขตายไว้ในตัวเอง **ไม่รับพารามิเตอร์ `state`** และ route ก็ไม่มีทางส่งเข้ามาได้ ถ้าเปิดให้ส่งได้ วันหนึ่งจะมีคนส่ง `UNANSWERED` แล้วคำขอเดียวจะล้าง **คิวงานจริงทั้งกอง** ซึ่งกู้คืนได้ทีละแถวเท่านั้น (การซ่อนปุ่มที่ UI ไม่ใช่ด่าน) |
| **BR-CR-R11** | ขอบเขตของ bulk (เพจ/ช่องทาง) ต้องตรงกับที่ `listComments`/`countCommentStatesByShop` ใช้เป๊ะ — กดจากจอที่กรองเพจ A ต้องไม่โดนของเพจ B และกดแล้วตัวเลขต้องลงเป็น 0 จริง · ต้องกัน `resolvedAt IS NULL` **ทั้งตอน SELECT และตอน UPDATE** เพราะระหว่างสองคำสั่งนั้นเพื่อนร่วมทีม/webhook อาจปิดใบเดียวกันไปแล้ว การเขียนทับจะกลืนเหตุผลเดิม (BR-CR-R8) |
| **BR-CR-R9** | ป้ายที่ผู้ใช้เห็นสำหรับคอมเมนต์ที่ resolved คือ **"จัดการแล้ว" คำเดียว สไตล์เดียว** ไม่ว่า `resolvedReason` เป็นค่าไหน (D-8) — แต่ **พฤติกรรมของปุ่ม "ทักแชท" ยังแยกตาม reason**: `ALREADY_REPLIED_EXTERNALLY` = กดไม่ได้ถาวร (Meta ปฏิเสธแน่นอน) · `MANUAL` = ยังกดได้ถ้ายังอยู่ในหน้าต่าง 7 วัน (คนเปลี่ยนใจได้). 🛑 อย่าเผลอยุบ `resolvedReason` เหลือ boolean เพราะเห็นว่าป้ายเหมือนกัน — ป้ายเหมือนกันเพราะผู้ใช้ไม่ต้องการรายละเอียดตอนกวาดตา ไม่ใช่เพราะสองอย่างนี้เหมือนกัน |
| **BR-CR-R8** | การตั้ง resolved อัตโนมัติของ #10900 **ห้ามทับแถวที่ resolved อยู่แล้ว** — คอมเมนต์ที่ถูกกดข้ามด้วยมือต้องคงเหตุผล `MANUAL` ไว้ (คนเป็นคนตัดสินใจ ระบบไม่ควรเขียนทับความตั้งใจนั้น) |

## 6. Data Model (additive ล้วน — D-1)

`PageComment` — เพิ่ม 3 คอลัมน์:

| Column | Type | Null | Default | หมายเหตุ |
|---|---|---|---|---|
| `resolvedAt` | `TIMESTAMP(3)` | YES | `NULL` | `NULL` = ยังไม่จบงาน |
| `resolvedByUserId` | `TEXT` | YES | `NULL` | plain String ไม่ผูก FK (D-6) · `NULL` เมื่อระบบเป็นคนตั้ง |
| `resolvedReason` | `TEXT` | YES | `NULL` | `MANUAL` \| `ALREADY_REPLIED_EXTERNALLY` (BR-CR-R4) |

CHECK ที่ไปด้วยกัน (D-7):
- `PageComment_resolvedReason_check` — `resolvedReason IS NULL OR resolvedReason IN ('MANUAL','ALREADY_REPLIED_EXTERNALLY')`
- `PageComment_resolved_pair_check` — `(resolvedAt IS NULL) = (resolvedReason IS NULL)`

🛑 วันที่ต้องเพิ่มเหตุผลใหม่ ต้อง DROP แล้ว ADD ใหม่โดย **อ่านรายชื่อเดิมมาต่อท้าย** ห้าม hardcode
เฉพาะค่าใหม่ (`docs/conventions/migration-check-constraint-additive.md` — บทเรียน 00033)

**ไม่มี backfill** — แถวเดิมทั้งหมด `NULL` ทั้ง 3 คอลัมน์ ซึ่งแปลว่า "ยังไม่ resolved" ถูกต้องสำหรับ
ทุกแถวที่มีอยู่ก่อนวันนี้

## 7. API Surface

| Method | Path | คำอธิบาย | Auth |
|---|---|---|---|
| `POST` | `/api/chat/comments/[commentId]/resolve` | mark done (FR-CR-15) → `resolvedReason='MANUAL'` | `canAccessShop` ผ่าน comment→post→channel→shop |
| `POST` | `/api/chat/comments/resolve-expired` | "ทำเครื่องหมายทั้งหมด" (FR-CR-18) — body `{ channelId?, provider? }` ชื่อพารามิเตอร์ตรงกับ query param ของ `/list` (HR16) → `{ resolved: number }`. 🛑 **ไม่มีพารามิเตอร์ `state`** (BR-CR-R10) | `canAccessShop` ผ่าน `resolveChatScope` เหมือน `/list` |
| `DELETE` | `/api/chat/comments/[commentId]/resolve` | unresolve (FR-CR-17) → ล้างทั้ง 3 คอลัมน์ | เหมือนข้างต้น |

🛑 ห้ามอ่าน `session.activeShopId` ในสองเส้นทางนี้ — อยู่ใต้ `src/app/api/chat/**` ซึ่งเป็นขอบเขตแชท
ตาม `src/lib/chat-scope.ts` (คอมเมนต์ใบหนึ่งอาจเป็นของร้านที่ไม่ใช่ร้าน active ของผู้ใช้)

**ภายใน (ไม่ผ่าน route ข้างบน):** `sendPrivateReplyToCommentById()` จับ `#10900` แล้วเรียกเส้นทาง
resolve ภายในด้วย system actor — ต้องเขียน `CommentReplyLog` (หลักฐานเดิม) **ก่อน** แล้วจึงตั้ง
`PageComment.resolvedAt` เหตุผลที่ Facebook ให้มาคือหลักฐาน ต้องไม่หายไปกับการปิดงาน และการตั้ง
resolved ที่ล้มเหลวต้องไม่ทำให้การจัดประเภท error หายไปด้วย

## 8. การจัดประเภท error ของ Graph — ทำไม "ลองใหม่อีกครั้ง" เป็นข้อความที่ผิด

อ้างอิง `docs/retro/2026-08-06-iship-retry-and-credit-retrospective.md` — โปรเจกต์นี้เคยพลาดคลาส
เดียวกันมาแล้วฝั่ง iShip: จัด error ที่ไม่มีวันสำเร็จให้เป็น retryable แล้วจอเชิญผู้ใช้กดวนซ้ำ

`#10900` เป็น error **ถาวรระดับคอมเมนต์** — กด "ลองใหม่" กี่ครั้งก็ได้ผลเดิมเสมอ เพราะสิทธิ์
private reply ของคอมเมนต์นั้นถูกใช้ไปแล้วจริง ไม่ใช่ความผิดพลาดชั่วคราวของเครือข่าย/rate limit

- 🛑 **ต้องจับที่รหัส (`GraphApiError.code === 10900`) ไม่ใช่จับข้อความภาษาอังกฤษ** — Meta เปลี่ยน
  ถ้อยคำได้โดยไม่แจ้ง รหัสเป็นสัญญาที่คงที่ (คลาสเดียวกับ regex "ไม่พอ" ที่ไม่ match "ไม่เพียงพอ"
  ของ iShip) · คง string fallback ไว้เฉพาะรูปแบบ `(#10900)` เผื่อ error ถูก wrap จนไม่เหลือ instance
  เดิม **ห้ามขยายไปจับคำว่า "already replied" เปล่า ๆ**
- จับได้แล้ว → มีเส้นทางแยกที่ตั้ง resolved อัตโนมัติ (FR-CR-16) และคืนข้อความว่า **"มีคนทักแชท
  คอมเมนต์นี้ไปแล้วจาก Facebook โดยตรง"** ไม่ใช่คำที่ชวนกดซ้ำ
- ปุ่ม "ทักแชท" หลังเจอ #10900 กดไม่ได้อีก ไม่ใช่กลับไปเป็น "ทักได้" รอบหน้า

## 9. Acceptance Criteria (ต่อ BRD §3.4 — เลขต่อจาก AC-CR-30)

| รหัส | เกณฑ์ |
|---|---|
| **AC-CR-31** | กด "ทำเครื่องหมายว่าจัดการแล้ว" บนคอมเมนต์ที่ยังไม่ตอบ → หลุดจากทั้งชิป/แท็บ "ยังไม่ตอบ" **และ** "หมดอายุ" ทันที ไม่ต้องรีเฟรชหน้า |
| **AC-CR-32** | กด "ยกเลิก" (unresolve) → กลับเข้าคิวด้วยสถานะที่คำนวณจริง ณ ตอนนั้น |
| **AC-CR-33** | คอมเมนต์ที่มีคำตอบสาธารณะอยู่แล้ว กด mark done → ไม่มีอะไรเปลี่ยนที่มองเห็นได้ (คำตอบสาธารณะชนะเสมอ BR-CR-R2) |
| **AC-CR-34** | กด "ทักแชท" แล้ว Graph ตอบ `#10900` → ระบบตั้ง `resolvedReason='ALREADY_REPLIED_EXTERNALLY'` อัตโนมัติ + บันทึกลง log + จอบอกว่ามีคนทักไปแล้วจาก Facebook โดยตรง (ไม่ใช่ "ลองใหม่อีกครั้ง") |
| **AC-CR-35** | คอมเมนต์เดียวกันที่เคยเจอ `#10900` → กด "ทักแชท" ไม่ได้อีก |
| **AC-CR-36** | ผู้ใช้ที่เข้าถึงร้านไม่ได้ กด mark done/unresolve ผ่าน API ตรงไม่ได้ (`403`) |
| **AC-CR-37** | ตัวเลขบนชิป/แท็บ/ผลกรองยังตรงกันเสมอหลังมี resolved เข้ามา (สืบเนื่อง BR-CR-S4/FR-CR-13) |
| **AC-CR-38** | ยิง `POST /resolve` ด้วย body ที่พยายามตั้ง `reason='ALREADY_REPLIED_EXTERNALLY'` → ต้องได้ `MANUAL` เสมอ (BR-CR-R7) |
| **AC-CR-40** | ปุ่ม "ทำเครื่องหมายทั้งหมด" ไม่ปรากฏในแท็บ "ทั้งหมด"/"ยังไม่ตอบ" และหายไปเองเมื่อ count = 0 |
| **AC-CR-41** | ยิง `POST /resolve-expired` โดยพยายามแนบ `state` ใด ๆ → ต้องไม่มีผลต่อเกณฑ์ (ยังแตะเฉพาะใบที่หมดอายุ) |
| **AC-CR-42** | กด "ทำเครื่องหมายทั้งหมด" ขณะกรองเพจเดียว → แตะเฉพาะใบของเพจนั้น เพจอื่นไม่ขยับ |
| **AC-CR-43** | ใบที่ระบบเคยปิดเองด้วย `ALREADY_REPLIED_EXTERNALLY` ต้องคงเหตุผลเดิมหลัง bulk (ไม่ถูกเขียนทับเป็น `MANUAL`) |
| **AC-CR-39** | คอมเมนต์ที่ถูกกดข้ามด้วยมือแล้ว ต่อมาเจอ `#10900` → `resolvedReason` ต้องยังเป็น `MANUAL` ไม่ถูกเขียนทับ (BR-CR-R8) |

## 10. Known gaps / ความเสี่ยง

- **ไม่มี API จาก Meta ที่บอกล่วงหน้าว่า "คอมเมนต์นี้เคยถูกทักแชทไปแล้วหรือยัง"** — รู้ได้ก็ต่อเมื่อ
  ลองยิงแล้วโดนปฏิเสธด้วย `#10900` เท่านั้น เพราะฉะนั้นคิวที่มีอยู่ก่อนส่วนขยายนี้ (ที่จริงตอบไม่ได้
  แล้วเพราะถูกทักจากที่อื่นไปนานแล้ว) จะยังค้างอยู่จนกว่าจะมีใครกด "ทักแชท" ของมันสักครั้งแล้วเจอ
  `#10900` หรือกด mark done ด้วยมือ — **ไม่มี backfill อัตโนมัติ และไม่มีทางตรวจแบบ batch ได้เลย**
- **การหาห้องแชทเดิมของคนคอมเมนต์ใช้การเทียบ id ตรง ๆ ในเพจเดียวกัน** (`ExternalContact.externalUserId`
  = `PageComment.fromExternalId`) — บน prod จับคู่ได้ **430 จาก 469** โดยหลักการ PSID กับ ASID เป็น
  คนละ id space และ **แปลงกันไม่ได้** (`reference_fb_psid_asid_cannot_map.md`) เราจึงใช้ได้แค่กรณีที่
  **ค่าเท่ากันเป๊ะทั้งสตริงภายในเพจเดียวกัน** เท่านั้น ห้ามทำ heuristic/แปลงค่าใด ๆ. โหมดล้มเหลวของ
  วิธีนี้คือ "หาไม่เจอ" (39 เคส → ไม่แสดงปุ่มไปที่ห้องแชท) ไม่ใช่ "เจอผิดคน" — ถ้าวันหน้าพบว่ามีเคส
  เจอผิดคนแม้แต่เคสเดียว ต้องถอดการเชื่อมนี้ออกทันที ไม่ใช่ปรับเกณฑ์
- **Instagram ไม่อยู่ในขอบเขตรอบนี้** — ยังไม่ยืนยันว่า Private Replies ของ IG ใช้รหัส error เดียวกัน
  หรือคนละรหัส ห้ามเดา (`docs/conventions/known-limitation-vs-unfinished.md`)
- **เอกสารที่ต้อง sync เมื่อ implement ครบ:** `BRD.md` §2.4/§3.4/§8 · `SRS.md` §5 + Traceability +
  TFR ของ resolve endpoint · `DATABASE.md` §3.2 · `API.md` · `TestCase.md` (AC-CR-31..39)
