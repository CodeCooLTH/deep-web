# 00038 — Extension (2026-08-15): คอลัมน์ซ้ายของ `/inbox/comments` เป็น **1 แถว = 1 คอมเมนต์**

## คำสั่งของผู้ใช้

> *"ผมอยากให้ทางซ้าย มัน lists ต่อ 1 comment ครับ ต่อให้จะมี 10 comments ใน post เดียวก็ต้องขึ้น
> lists 10 อัน"*
> *"แต่ layout ต้องเหมือนเดิมนะ"*

เดิมคอลัมน์ซ้ายเป็น **1 แถว = 1 โพสต์** (`listCommentPosts`) โพสต์ที่มีลูกค้าถาม 10 คนจึงยุบเหลือ
แถวเดียว แล้วผู้ขายต้องเปิดเข้าไปถึงจะเห็นว่ามีงานค้างกี่ใบ — คิวงานที่แท้จริงคือ "คอมเมนต์"
ไม่ใช่ "โพสต์"

## มติ

| # | มติ | เหตุผล |
|---|---|---|
| D-RC-1 | คอลัมน์ซ้ายเป็นรายการ **คอมเมนต์ของลูกค้า** เรียง `createdTime DESC` | หน่วยของแถว = หน่วยของงาน |
| D-RC-2 | **คงโครง 3 คอลัมน์เดิม** — กลาง (เธรดของโพสต์) และขวา (สื่อ/สถิติของโพสต์) ยังทำงานระดับโพสต์ | ผู้ใช้สั่งไว้; และเธรดคือที่ที่ตอบจริง |
| D-RC-3 | **คำตอบของลูกค้าใต้คอมเมนต์อื่นได้แถวของตัวเอง** (`isReply=true`) | มันคือคำถามที่รอคำตอบเหมือนกัน |
| D-RC-4 | คอมเมนต์ที่เพจเขียนเอง (`isFromPage=true`) และที่ถูกลบ **ไม่เป็นแถว** | รายการนี้คือ "สิ่งที่ต้องตอบ" ไม่ใช่ประวัติทั้งหมด — กติกาเดียวกับที่ตัวนับใช้มาตลอด |
| D-RC-5 | **layout ของแถวไม่เปลี่ยนสักคลาส** | คำสั่งตรงของผู้ใช้ — เปลี่ยนแค่ว่าแต่ละช่องพูดเรื่องอะไร |

### D-RC-5 แปลว่าอะไรบนหน้าจอ

โครงเดิม (รูปปกโพสต์ + ป้ายเพจมุมล่างขวา · สองบรรทัด · ป้ายสถานะ · เวลาชิดขวา) อยู่ครบ
สลับความหมายดังนี้:

| ช่อง | เดิม (แถว = โพสต์) | ใหม่ (แถว = คอมเมนต์) |
|---|---|---|
| บรรทัดที่ 1 | ข้อความโพสต์ | **`ชื่อผู้คอมเมนต์: ข้อความคอมเมนต์`** |
| บรรทัดที่ 2 | คอมเมนต์ล่าสุด (หรือ "N ความคิดเห็น") | **ข้อความโพสต์** (บริบทว่าอยู่ใต้โพสต์ไหน) |
| ป้ายสถานะ | สถานะรวมของโพสต์ (แย่ที่สุดชนะ, BR-CR-S2) | **สถานะของคอมเมนต์ใบนี้** (BR-CR-S1) |
| นับถอยหลัง 7 วัน | จากคอมเมนต์ที่ยังไม่ตอบ *ที่เก่าที่สุดในโพสต์* | **จาก `createdTime` ของใบนี้เอง** |
| เวลาชิดขวา | คอมเมนต์ล่าสุดของโพสต์ | `createdTime` ของใบนี้ |

บรรทัดที่ 1 ต้องเป็นคอมเมนต์ เพราะเมื่อ 1 แถว = 1 คอมเมนต์ **ข้อความโพสต์จะซ้ำกันทุกแถวของ
โพสต์เดียวกัน** — ถ้าปล่อยไว้ที่บรรทัดเด่น ผู้ขายจะเห็น 10 แถวหน้าตาเหมือนกันเป๊ะ

คอมเมนต์ที่เป็นการตอบกลับ (D-RC-3) ได้ไอคอน `corner-down-right` นำหน้า **ในบรรทัดข้อความ**
ไม่ใช่การเยื้องแถว — การเยื้องคือการเปลี่ยน layout ซึ่งผู้ใช้ห้ามไว้

## กฎที่ถูกแก้

### BR-CR-S4 (แก้) — หน่วยของตัวนับต้องเท่ากับหน่วยของแถว

TFR-010 เดิมเขียนว่า badge แท็บ "ความคิดเห็น" นับ **จำนวนโพสต์** โดยให้เหตุผลว่าต้องเป็นหน่วย
เดียวกับ badge แท็บ "ข้อความ" (ซึ่งนับเธรด) — เหตุผลนั้นถูก *ตอนที่แถวเป็นโพสต์*
ตอนนี้แถวเป็นคอมเมนต์แล้ว **ถ้าไม่แก้ badge จะขึ้น "7" อยู่เหนือรายการ 12 แถว**

⇒ `countUnansweredForShops()` และตัวนับ 4 กลุ่มบนแท็บ เปลี่ยนไปใช้
`countCommentStatesByShop()` (นับคอมเมนต์) แทน `countCommentPostStatesByShop()`

🛑 **`countCommentPostStatesByShop()` ยังต้องอยู่** — ตัว CASE ข้างในคือ SSOT ของ 3 สถานะที่
`deriveCommentState()` ต้องเรียงตรงกันบรรทัดต่อบรรทัด และยังมีที่อื่นที่นับเป็นโพสต์จริง ๆ

### BR-CR-S2 (ขอบเขตแคบลง)

"ตัวที่แย่ที่สุดชนะ" ยังเป็นกฎที่ถูก แต่**ไม่มีผลกับแถวในคอลัมน์ซ้ายอีกต่อไป** — ใช้กับที่ที่ยัง
พูดถึงโพสต์ทั้งใบเท่านั้น

## สัญญา API

| เดิม | ใหม่ |
|---|---|
| `GET /api/chat/comments/posts` → `{ posts, counts, rawCount }` | **`GET /api/chat/comments/list`** → `{ comments, counts, rawCount }` |

- `posts/route.ts` (collection GET) **ถูกลบ** — เส้นทางลูก `posts/[postId]` (เธรด · เขียนคอมเมนต์ ·
  รีเฟรช) ไม่เปลี่ยนเลย เพราะคอลัมน์กลาง/ขวายังทำงานระดับโพสต์ (D-RC-2)
- query เดิมทั้งชุดใช้ได้เหมือนเดิม (`q` · `channelId` · `state` · `provider` · `skip`) —
  `q` ค้นได้ทั้งข้อความคอมเมนต์ · ชื่อผู้คอมเมนต์ · ข้อความโพสต์
- `counts` = **ทั้งร้าน นับเป็นคอมเมนต์** · `rawCount` = จำนวนแถวดิบก่อนกรองด้วย `state`
  (ใช้คำนวณ `skip`/`hasMore` เท่านั้น **ห้ามแสดง**)

### ขนาดหน้า

`COMMENT_LIST_PAGE_SIZE` (`src/lib/comment-list-page.ts`) = 25 — ตัวเลขเดียวที่ทั้งฝั่ง query และ
ฝั่งตัดสิน `hasMore` ใช้ร่วมกัน (HR16) ก่อนหน้านี้ service ใช้ 30 / client เทียบ 25 แล้วปุ่ม
"โหลดเพิ่ม" โผล่ในหน้าสุดท้ายโดยกดไปได้ศูนย์แถว โดยไม่มี `tsc`/เทสตัวไหนเห็น เพราะเลขทั้งสอง
"ถูก" ในตัวเอง สิ่งที่ผิดคือมันควรเป็นเลขเดียวกัน

## ผลข้างเคียงที่ต้องรู้

- **`selectedPost` derive จากแถว** — โพสต์ที่เปิดอยู่มาจากคอมเมนต์ใบแรกที่อยู่ใต้โพสต์นั้น
  snapshot ผ่าน `selectedPostRef` ยังทำงานเหมือนเดิม (โพสต์ที่เปิดอยู่ต้องไม่หายจากแผงขวาเพียงเพราะ
  แถวหลุดจากตัวกรอง)
- **"ยังไม่ตอบ N" ที่แถบสถิติของโพสต์** เดิมอ่านจาก `unansweredCount` ที่มากับแถว ตอนนี้ **นับจาก
  เธรดที่โหลดมาแล้ว** (`selectedUnanswered`) — ห้ามนับจากรายการซ้าย เพราะนั่นคือชุดที่ถูกกรอง/
  แบ่งหน้าแล้ว จะได้เลขต่ำกว่าจริงเสมอ
- **ไฮไลต์แถวแยกจาก "โพสต์ที่เปิดอยู่"** (`highlightCommentId`) — ใช้ `selectedId` ตัวเดียว
  ไม่ได้ ไม่งั้นทุกแถวของโพสต์เดียวกันจะสว่างพร้อมกัน
- **ไม่มี migration · ไม่แตะ schema · ไม่แตะกติกาการตอบ/ทักแชท**

## หนี้ที่รู้ตัว

- **ยังไม่เคยเปิดหน้าจริงสักครั้ง** — จุดเสี่ยงที่ static ตรวจไม่ได้: โพสต์ที่มีคอมเมนต์เยอะทำให้
  แถวซ้ำภาพปกเดียวกันติดกันหลายใบ (ตั้งใจ แต่ต้องดูว่าอ่านออกจริงไหม) · ปุ่ม "โหลดเพิ่ม" กับหน้า
  ที่กรองด้วย `state` · การไฮไลต์แถวเมื่อกดจากคนละโพสต์สลับไปมา
- **ไม่ได้ผ่าน `safepay-ux` (HR8) และไม่ได้รัน `/impeccable critique`** — session นี้ห้ามเรียก
  subagent (หนี้ก้อนเดียวกับหลายรอบก่อนหน้า)
- ยังไม่มีการเลื่อนเธรดไปหาคอมเมนต์ใบที่กด — กดแถวแล้วได้เธรดทั้งโพสต์ ผู้ขายต้องหาเอง
  (`highlightCommentId` ถูกเก็บไว้แล้ว เหลือแค่ผูกกับ scroll ในคอลัมน์กลาง)
- `TestCase.md` ยังไม่มีเคสของรายการแบบใหม่
