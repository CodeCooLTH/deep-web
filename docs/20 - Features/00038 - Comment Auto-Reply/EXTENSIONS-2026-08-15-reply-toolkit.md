## E1 — ตอบใต้คอมเมนต์อัตโนมัติ **พร้อมรูป**

### สิ่งที่มีอยู่แล้ว (ห้ามสร้างซ้ำ)
`replyToComment({ commentId, message, actorUserId, fileId })` รับ `fileId` มาตั้งแต่ 2026-08-03
แล้วแปลงเป็น presigned URL อายุ 1 ชม. ส่งเป็น `attachment_url` เข้า `POST /{comment-id}/comments`
พร้อม `message` **ในคำขอเดียว** (คอมเมนต์ส่งรูป+ข้อความพร้อมกันได้ ต่างจาก Send API ของแชทที่ต้อง
แยกเป็น 2 ข้อความ — ข้อแตกต่างนี้เขียนไว้แล้วใน docstring ของ `createCommentReply`)

โหมด "ตอบเอง" ใช้อยู่จริง (134 ใบ) — **โหมดอัตโนมัติส่ง `fileId` เป็น null ทุกครั้ง** เท่านั้นเอง

### สิ่งที่ต้องทำ
- `ShopChannel.commentPublicReplyFileId String?` (migration additive)
- หน้า `/settings/comment-reply` การ์ดสวิตช์ A เพิ่มช่องแนบรูป 1 ใบ (ลบได้ · พรีวิวได้)
- `processCommentAutoReply` ส่ง `fileId` ต่อเข้า `replyToComment`

### กติกาที่ต้องบังคับ
- 🛑 **เก็บ `fileId` ห้ามเก็บ URL** — presigned URL อายุ 1 ชม. เก็บ URL ไว้ในคอลัมน์ตั้งค่าคือของที่
  ตายภายในชั่วโมงเดียวโดยไม่มีอะไรฟ้อง (คลาสเดียวกับ `thumbnailUrl` ของโพสต์ที่หายใน 4 วัน)
  ตัว URL ต้องสร้างใหม่ทุกครั้งที่ยิง ซึ่ง `replyToComment` ทำให้อยู่แล้ว
- **รูปอย่างเดียวไม่มีข้อความ = ส่งได้** (Graph ต้องมีอย่างน้อยหนึ่งใน message/attachment_url)
  ⇒ เกณฑ์ "สวิตช์ A เปิดใช้งานได้ไหม" ต้องเปลี่ยนจาก *"มีข้อความ"* เป็น *"มีข้อความ **หรือ** มีรูป"*
  🛑 จุดนี้อยู่ 3 ที่ที่ต้องแก้พร้อมกัน: `evaluateCommentGate` (DISABLED) · Valibot
  `CommentReplyConfigSchema` (`commentPublicReplyEnabled !== true || !!text?.trim()`) · ปุ่มบันทึกใน UI
  — แก้ไม่ครบ = ร้านที่ตั้งรูปอย่างเดียวจะบันทึกไม่ได้ หรือบันทึกได้แล้วไม่ยิง
- อัปโหลดผ่าน `@/lib/upload-client` เท่านั้น (Hard Rule เพดาน 4.5MB ของ Vercel)
- ไฟล์ผูกกับร้าน: ตอนบันทึก config ต้องเช็คว่า `fileId` เป็นของ shop นั้นจริง ไม่งั้นเป็นช่องอ้างไฟล์ร้านอื่น

### ยังไม่ทำในรอบนี้
รูปในข้อความ **ทักแชท** — คนละท่อ (Send API attachment ต้องส่งแยกเป็นข้อความที่ 2) และชนกับ E3
ที่จะเปลี่ยนข้อความทักแชทเป็นการ์ดอยู่แล้ว

## E2 — ตอบต่างกันตามคีย์เวิร์ด  🔥 คุ้มที่สุด

### ปัญหา
ทุกคนได้ข้อความเดียวกันหมด ขณะที่ **35% ถามราคาตรง ๆ** — และคอมเมนต์สาธารณะคือที่ที่คำตอบ
ถูกอ่านซ้ำโดยคนที่เลื่อนผ่าน (ต่างจากแชทที่อ่านคนเดียว) การตอบราคาในคอมเมนต์จึงมีมูลค่าคูณ

### D-EXT2-1 — **ตารางกฎของตัวเอง ไม่ผูกกับ `AutoReplyKeyword` ของแชท (00023)**
ยกมาใช้ซ้ำเฉพาะ **`normalizeMessage()`** (`src/lib/auto-reply-normalize.ts`) ซึ่งเป็นส่วนที่ยาก
และต้องมีนิยามเดียวทั้งระบบ (HR16 — การ normalize ภาษาไทยที่ต่างกัน 2 ชุดคือของที่แตกเงียบ)

**เหตุผลที่ไม่ reuse `AutoReplyRule`:**
- `AutoReplyKeyword.status` มีโหมด `TEST` ที่ผูกกับ `AutoReplyKeywordTestThread` → **เป็นเธรดแชท**
  ไม่มีสิ่งเทียบเท่าในโลกของคอมเมนต์ ยัดเข้าไปจะได้ค่าที่ไม่มีความหมายในบริบทหนึ่งเสมอ
- `AutoReplyRule` มีมิติ `adId`/`productId` + `specificity` bitmask ที่ออกแบบมาเพื่อ 8 ระดับของแชท
  การเติม discriminator `scope='COMMENT'` เข้าไปในตารางที่ engine ตัวอื่นอ่านอยู่ = ความเสี่ยงที่
  กฎคอมเมนต์รั่วไปตอบในแชท ซึ่งเป็นคลาสบั๊กที่โปรเจกต์นี้เจอซ้ำ ๆ (fail-closed, guard ที่หายไป)
- ร้านแก้กลุ่มคำเพื่อแชท แล้วพฤติกรรมคอมเมนต์เปลี่ยนตามโดยไม่รู้ตัว = ผลข้างเคียงที่มองไม่เห็น

**เหตุผลที่รับได้:** เจตนาของคอมเมนต์มีไม่กี่แบบจริง ๆ (ราคา / สนใจ / ผ่อน-ติดตั้ง-สาขา) ตั้งเองใน
หน้าเดียวจบ ไม่ต้องข้ามไปหน้าตั้งค่าแชท

### โมเดล
```
CommentReplyRule
  id, shopId, shopChannelId?      // null = ใช้ทุกเพจของร้าน
  name                            // ชื่อกฎที่ร้านตั้งเอง เช่น "ถามราคา"
  phrases          String[]       // คำที่ร้านพิมพ์ (เก็บของเดิมไว้โชว์)
  normalizedPhrases String[]      // ผ่าน normalizeMessage() แล้ว — ตัวที่ใช้เทียบจริง
  publicReplyText  String?
  publicReplyFileId String?
  privateReplyText String?
  priority         Int            // มากกว่า = ชนะก่อน
  isActive         Boolean
```

### กติกาที่ต้องบังคับ
- 🛑 **ต้องมี fallback เสมอ** — ข้อความในหน้าตั้งค่าเดิม (`commentPublicReplyText`) กลายเป็น
  "คำตอบเมื่อไม่เข้ากฎไหนเลย" ห้ามให้คอมเมนต์ที่ไม่ match เงียบไป (นั่นคือถอยหลังจากวันนี้)
- 🛑 **กฎต้องเลือกได้ตัวเดียวและเลือกได้เหมือนเดิมทุกครั้ง** — เรียงด้วย `priority DESC, id ASC`
  ห้ามพึ่งลำดับที่ Postgres คืนมาเอง (เคสจริงของโปรเจกต์: ผลลัพธ์สลับกันเองระหว่างสองรอบ)
- 🛑 **คอมเมนต์ที่ไม่มีข้อความ (22 ใบ) ต้องไม่ match กฎไหน** — สตริงว่างหลัง normalize เข้าเงื่อนไข
  `CONTAINS` ของทุกกฎพร้อมกัน ต้องตัดทิ้งก่อนเข้าตัว match (เขียนเทส `[blocker]` ข้อนี้โดยเฉพาะ)
- คำที่ normalize แล้วซ้ำกันภายในกฎเดียว = unique ที่ DB ไม่ใช่แค่เช็คใน UI
- ตัวตัดสินต้องเป็น **ฟังก์ชันบริสุทธิ์** (`matchCommentRule(normalizedText, rules)`) ใน `src/lib/`
  พร้อมเทส `[blocker]` + พิสูจน์ด้วย mutation — ไม่ใช่เทอร์นารีกลาง service
  (`docs/conventions/ui-boolean-needs-a-testable-home.md`)

fallback ของเพจใช้เฉพาะตอน **ไม่มีกฎไหน match เลย** เท่านั้น

## E4 — รายงาน "คอมเมนต์ → ออเดอร์"

### ข้อมูลต่อกันครบอยู่แล้ว ไม่ต้องเก็บอะไรเพิ่ม
`CommentReplyLog.conversationId` → `Conversation` → `Order.conversationId`
ผลจริง 6 วัน: **127 ห้อง → ตอบกลับ 86 (68%) → ออเดอร์ 10 ใบ** — ไม่มีใครเห็นตัวเลขนี้เลยตอนนี้

### สิ่งที่ต้องแสดง
ต่อเพจ · ต่อช่วงเวลา · **ต่อโพสต์** (โพสต์ไหนทำเงิน = ข้อมูลที่ร้านเอาไปตัดสินใจยิงแอดต่อได้)

### กติกาที่ต้องบังคับ
- 🛑 **ตัวเลขบางส่วนต้องมีป้ายกำกับ** (`docs/conventions/partial-data-must-be-labeled-or-filled.md`)
  — ฟีเจอร์เพิ่งเริ่ม 9 ส.ค. ข้อมูลก่อนหน้านั้นไม่มีเลย ถ้าโชว์ "ทั้งหมด" โดยไม่บอก ร้านจะอ่านว่า
  ระบบทำงานได้แย่ · และห้องที่ยังไม่ปิดการขายไม่เท่ากับ "ไม่ได้ออเดอร์"
- 🛑 นิยาม "ออเดอร์ที่มาจากคอมเมนต์" ต้องมีนิยามเดียว (HR16) — ผูกด้วย `Order.conversationId`
  เท่านั้น ห้ามมีสูตรที่สองที่หน้าอื่น และต้องเขียนบนหน้าจอว่านับยังไง
- อ่านอย่างเดียว ไม่แตะ write path
