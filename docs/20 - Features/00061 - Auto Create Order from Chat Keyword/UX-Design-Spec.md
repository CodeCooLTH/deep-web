# Design Spec — feature 00061: สร้างออเดอร์อัตโนมัติจากคำสั่งในแชท

> ## 🔄 มติเปลี่ยน 2026-08-30 — ร่างเป็น `Order.status='DRAFTED'` · **หน้า C ถูกยุบ**
>
> *"ไม่อยากให้สร้างตารางแยกแล้ว · อยากให้สร้างออเดอร์ไว้รวมกันเลย แต่เป็น drafted แทน · ง่ายกว่า"* (user)
>
> **สิ่งที่หายไปทั้งก้อน:** หน้ารวมศูนย์ (หน้า C) · เมนูใหม่ · ปุ่ม "เปิดฟอร์มที่กรอกไว้ให้แล้ว"
> **แทนด้วย:** ชิปกรอง **"ร่าง"** ในแถบตัวกรองของ `/orders` เดิม · ปุ่มเปิดร่าง = **ฟอร์มแก้ไขออเดอร์ปกติ**
> **หน้า A / หน้า B / หน้า D ไม่เปลี่ยน** (ยกเว้นชื่อปุ่ม 1 จุดในหน้า B)


> อ่านตามลำดับ Hard Rule 8/9 แล้ว: `DESIGN.md` → `PRODUCT.md` → `.impeccable/design.json` →
> Impeccable playbook (`shape.md` + `operate.md` + `craft-floor.md`) →
> `docs/system/ui-guideline/README.md` + `paces-component-reference.md` → หน้าพี่น้องทั้งหมด

🛑 **ทิศทางของฟีเจอร์ (อ่านก่อนออกแบบ/แก้ไขทุกครั้ง):** ระบบนี้ดัก **ข้อความที่ร้าน (SHOP) พิมพ์เอง**
ในแชท **ไม่ใช่ดักข้อความลูกค้า** — วลีจุดชนวนและแม่แบบทั้งหมดคือสิ่งที่ **ผู้ขาย/พนักงานพิมพ์**
เพื่อสั่งให้ระบบสร้างออเดอร์ ไม่ใช่สิ่งที่บอกให้ลูกค้าพิมพ์.
ห้ามลอกถ้อยคำจาก `AutoReplyListing`/`KeywordEditorClient` มาใช้ตรง ๆ — ระบบนั้นคือการ *ตอบกลับลูกค้า*
ซึ่งทิศทางข้อความตรงข้ามกับฟีเจอร์นี้ (ลอกได้เฉพาะโครงสร้าง component ห้ามลอกความหมายของคำ)

### Impeccable compliance

- **Mode: Operate.** ทั้ง 4 กลุ่มจอเป็นเครื่องมือปฏิบัติงานของผู้ขาย (ฟอร์มตั้งค่า / รายการรอตรวจ /
  badge ในกล่องแชท) ไม่ใช่ surface แบรนด์ — ใช้เกณฑ์ `operate.md`: ความคุ้นเคยชนะการแสดงออก,
  ทุก interactive component ต้องมี default/hover/focus/active/disabled/loading/error ครบ,
  สีสงวนไว้กับ action หลัก/สถานะเท่านั้น, skeleton ไม่ใช่ spinner กลางเนื้อหา,
  ไม่มี choreography ตอนโหลดหน้า (ตรงกับ `DESIGN.md`)
- **One Voice Rule:** `bg-primary`/`text-primary` (Counter Blue `#236dc9`) ใช้เฉพาะ (1) ปุ่มหลัก
  "บันทึกการตั้งค่า"/"เพิ่มวลี" ในหน้า A (2) หัวการ์ดออเดอร์สถานะ CREATED ในหน้า B (ของเดิมในระบบอยู่แล้ว)
  (3) ปุ่ม "เปิดฟอร์มที่กรอกไว้ให้แล้ว" ในหน้า B/C. **ไม่ใช้น้ำเงินกับพื้นหลังการ์ด/หัวข้อ/badge สถานะ**
- 🛑 **Verified-Means-Green (จุดที่ต้องระวังที่สุดของงานนี้):**
  - `LIVE` (เปิดใช้จริงกับลูกค้าทุกคน) = `bg-success` / `text-success-ink` — ตรงกับ
    `AutoReplyListing.STATUS_META.LIVE` เดิม เพราะแปลว่า "ยืนยันแล้วว่าใช้งานจริง"
  - `DRAFT` (ร่างที่รอผู้ขายตรวจ) และ `TEST` (โหมดซ้อม) = `bg-warning` / `text-warning-ink`
    **ห้ามเขียวเด็ดขาด**
  - `CREATED` (ระบบสร้างออเดอร์สำเร็จ) = **น้ำเงิน primary ไม่ใช่เขียว** เพราะ "ระบบทำงานสำเร็จ"
    ไม่เท่ากับ "ลูกค้ายืนยันแล้ว" — ออเดอร์ที่เกิดยังเป็น `PENDING` การยืนยันจริงเกิดตอนลูกค้ากดที่
    `/o/{token}` (ตรงกับที่ `OrderCardView` ของจริงใช้หัวน้ำเงินกับออเดอร์ `PENDING` ทุกใบอยู่แล้ว)
- **Sentence-case** ทุกป้าย
- **Ink-Tinted Shadow:** ใช้ `.card`/`shadow` token ของ Paces (`0 1px 4px rgba(130,143,163,.15)`)
  ไม่มี custom shadow ใหม่
- **anti-slop:** ไม่มี hero-metric, ไม่มี eyebrow ตัวพิมพ์เล็ก, ไม่มีการ์ดซ้อนการ์ด (หน้า C ใช้การ์ด
  แยกใบแบบ `/orders`/`/products`), ไม่มี border ตกแต่ง >1px (ยกเว้น `border-s-3` ที่เป็น carve-out
  ขึ้นทะเบียนแล้วของ `(paces)`)
- **น้ำเสียง:** ทุกข้อความ error/empty บอกทางออก ไม่ใช่แค่บอกว่าผิด — โดยเฉพาะเหตุผลตกร่างที่ต้อง
  **บอกครบทุกข้อพร้อมกัน** ไม่ใช่เปิดเผยทีละข้อ (ตรงกับ `clarify.md`: บอกทางแก้ทั้งหมดในครั้งเดียว
  ไม่ปล่อยให้ผู้ใช้ชนกำแพงซ้ำ)
- **จุดที่ theme ขัดกับ Impeccable:** ไม่มีจุดขัดจริง — Paces primitive ครอบคลุมทุก component
  ที่ต้องการ (segmented toggle 3 ค่า, checkbox list, chip input, card, badge, DataTable)
  มี precedent ในโค้ดจริงครบทุกตัว **ไม่มีจุดไหนต้องใช้ arbitrary value ใหม่**

## หน้า A: ตั้งค่าสร้างออเดอร์อัตโนมัติ (`/seller/settings/auto-reply/order-agent`)

### User stories ที่ครอบ

- ในฐานะเจ้าของร้าน ฉันอยากพิมพ์สรุปคำสั่งซื้อในแชทแล้วให้ระบบสร้างคำสั่งซื้อให้อัตโนมัติ โดยไม่ต้องสลับไปกรอกฟอร์มแยก
- ในฐานะเจ้าของร้าน ฉันอยากมีแม่แบบข้อความที่พิมพ์ตามได้ทุกครั้ง เพื่อไม่ให้พิมพ์ผิดจนระบบอ่านไม่ออก
- ในฐานะเจ้าของร้าน ฉันอยากทดสอบรูปแบบข้อความของตัวเองก่อนเปิดใช้งานจริงกับลูกค้าทุกคน
- ในฐานะเจ้าของร้าน ฉันอยากรู้ทันทีถ้าเพจของฉันตั้งค่าไม่ครบจนฟีเจอร์นี้ทำงานไม่ได้
- ในฐานะพนักงานร้าน (ไม่ใช่ OWNER/ADMIN) ฉันอยากดูการตั้งค่านี้ได้แต่ไม่อยากพลาดกดแก้โดยไม่ได้ตั้งใจ

### Layout — <768px: ไม่ให้ตั้งค่าบนมือถือ (มติ user 2026-08-29)

🛑 **หน้าตั้งค่านี้ต้องใช้บนแท็บเล็ตขึ้นไป (≥768px)** — ต่ำกว่านั้นแสดงจอบอกทางแทนฟอร์ม
(แบบอย่างในระบบ: ตัวจัดหน้าร้าน 00035 ที่ gate ไว้ที่ `xl` — อันนี้ gate ที่ `md` เพราะแท็บเล็ตพอ)

เหตุผล: หน้านี้ต้องดู **แม่แบบข้อความ + รายชื่อเพจ + ผลการทดสอบ** พร้อมกันถึงจะตั้งค่าได้อย่างมั่นใจ
บนจอ 320px ต่อให้ยัดลงได้ก็เป็นการตั้งค่าที่ผู้ขายมองไม่เห็นภาพรวมของสิ่งที่ตัวเองกำลังเปิด

```
┌─────────────────────────────┐
│[icon:arrow-left] สร้างออเดอร์อัตโนมัติ│
├─────────────────────────────┤
│  ┌───────────────────────┐  │
│  │  [icon:device-desktop] │  │
│  │ ตั้งค่าหน้านี้บนแท็บเล็ต   │  │
│  │ หรือคอมพิวเตอร์          │  │
│  │ (เหตุผล 2 บรรทัด)        │  │
│  └───────────────────────┘  │
│  ┌───────────────────────┐  │
│  │[icon:check] ระบบยังทำงาน│  │  ← สำคัญที่สุดในจอนี้
│  │ บนมือถือตามปกติ         │  │

🛑 **จอนี้ต้องบอก 3 อย่าง ไม่ใช่แค่ไล่ผู้ใช้ไปที่อื่น:**
1. **ตั้งค่าที่ไหนได้** (แท็บเล็ต/คอม) และ **ทำไม** — ไม่ใช่ "จอเล็กเกินไป" ลอย ๆ
2. 🛑 **"ระบบยังทำงานบนมือถือตามปกติ"** — ถ้าไม่บอก ผู้ขายจะเข้าใจว่าฟีเจอร์ทั้งอันใช้บนมือถือไม่ได้
   ทั้งที่ความจริงคือ **ตั้งค่าไม่ได้เท่านั้น ส่วนการดักจับ/ผลลัพธ์ทำงานเต็มที่**
3. **ทางไปต่อที่ทำได้จริงบนมือถือ** — ห้องแชท (หน้า B) และ **ชิปกรอง "ร่าง" ในหน้า `/orders`** พร้อมตัวเลขค้าง

**ขอบเขตของประตูนี้: เฉพาะหน้า A เท่านั้น** — หน้า B (การ์ดในเธรด) และหน้า `/orders` (ที่ร่างไปปรากฏ)
**ต้องใช้ได้เต็มที่บนมือถือ** เพราะเป็นงานที่แอดมินทำระหว่างวันจากโทรศัพท์ ไม่ใช่งานตั้งค่า

**ผลพลอยได้:** ปัญหางบพื้นที่ของแถบสถานะที่ 320px (ดูหัวข้อถัดไป) **หมดไปสำหรับหน้านี้** —
แถบสถานะเป็นแนวนอนตลอด ไม่ต้องมีโหมดวางแนวตั้งอีก และ `aria-orientation` เป็น `horizontal` ค่าเดียว

### คำที่ใช้กับ 3 สถานะ — และเหตุผลที่ไม่ลอกของเดิมทั้งชุด

ทวนกับ `AutoReplyListing.STATUS_META` แล้ว ของเดิมคือ `OFFLINE: 'ไม่ใช้งาน'` · `TEST: 'ทดสอบ'` ·
`LIVE: 'ตอบลูกค้าจริง'`

- `ไม่ใช้งาน` / `ทดสอบ` — **ใช้คำเดิมตรงตัว** (เป็นคำกลาง ๆ ที่ข้ามฟีเจอร์ได้จริง)
- `ตอบลูกค้าจริง` — 🛑 **ใช้กับฟีเจอร์นี้ไม่ได้** เพราะมันแปลว่า "ตอบ" ซึ่งฟีเจอร์นี้ไม่เคยตอบใครเลย
  (มันสร้างออเดอร์). การใช้คำเดิมทั้งที่ความหมายผิด จะสับสนกว่าการใช้คำที่ต่างกันเล็กน้อยแต่ถูกต้อง
  ⇒ ใช้ **`สร้างออเดอร์จริง`** — คงโครง "[กริยา]จริง" เดียวกับต้นแบบ เปลี่ยนเฉพาะกริยาให้ตรงพฤติกรรม

#### งบพื้นที่ที่ 320px ของแถบสถานะ — เก็บไว้เป็นหลักฐาน (ไม่ใช้กับหน้านี้แล้ว)

> ⛔ **ล้าสมัยสำหรับหน้า A แล้ว** หลังมติ gate ที่ <768px — แถบสถานะเป็นแนวนอนตลอด
> **แต่เก็บหัวข้อนี้ไว้เพราะมันบันทึกหนี้ของหน้าอื่นที่ยังอยู่บน prod (ดู 🛑 ท้ายหัวข้อ)**

> ⚠️ ตัวเลขด้านล่างประมาณจาก font metrics (ux มีเครื่องมืออ่านไฟล์อย่างเดียว ไม่มีเบราว์เซอร์จริง)
> — **QA/dev ต้องวัดซ้ำในเบราว์เซอร์จริงก่อนปิดงาน** แต่ทิศทางฟันธงได้แล้ว

| รายการ | ความกว้าง |
|---|---|
| viewport | 320px |
| − `.card-header` padding `px-5` (20×2) | เหลือ **280px** |
| − group `rounded-lg p-0.5` (4px) | เหลือ **276px** |
| − padding ในปุ่ม `px-3` × 3 ปุ่ม (24×3) | เหลือให้ตัวหนังสือ **204px** |
| `ไม่ใช้งาน` (7 หน่วย × ~9px @ `text-xs`) | ~63px |
| `ทดสอบ` (5 หน่วย) | ~45px |
| `ตอบลูกค้าจริง` — คำเดิมของ auto-reply (10 หน่วย) | ~90px |
| `สร้างออเดอร์จริง` — คำใหม่ของฟีเจอร์นี้ (13 หน่วย) | ~117px |

- **ชุดคำเดิม** 63+45+90+72+4 = **274px จาก 280px** → พอดีแบบ **ไม่มีระยะเผื่อเลย (เหลือ 6px)**
- **ชุดคำใหม่** 63+45+117+72+4 = **301px** → **ล้น 21px ที่ 320px แน่นอน**

🛑 **ผลพลอยได้ที่สำคัญกว่าตัวฟีเจอร์:** แถบสถานะของ `KeywordEditorClient` (หน้าตอบกลับอัตโนมัติเดิม)
**อยู่ที่ขอบพอดีมาตั้งแต่แรกแล้ว** — 274/280px ไม่มีระยะปลอดภัย ⇒ มันจะพังทันทีที่ใครแตะคำ ปรับ padding
หรือเปลี่ยนขนาดฟอนต์ นี่คือบั๊กที่หลับอยู่ในหน้าที่ขึ้น prod แล้ว ไม่ใช่ของที่ฟีเจอร์นี้สร้างขึ้น
(ดู `docs/conventions/flex-header-truncation.md` — คลาสเดียวกับที่เคยเจอ)

**ทางแก้ที่เคยเลือกไว้ (ก่อนมติ gate): วางแนวตั้งต่ำกว่า `sm` (640px)** — ยกเลิกแล้วสำหรับหน้า A

- ไม่เลือก (ข) ย่อคำ — `สร้างออเดอร์จริง` ย่อเหลือ `จริง`/`สร้าง` แล้วเดาความหมายไม่ออก และ**ของเดิม
  ก็ไม่มีระยะเหลือให้ย่ออยู่แล้ว** (274/280)
- ไม่เลือก (ค) เปลี่ยนเป็น `form-select` — ทำลาย affordance "กดสลับทันที ไม่ต้องกดบันทึก" ซึ่งเป็น
  จุดขายของ toggle นี้
- (ก) **ไม่ใช่การประดิษฐ์ใหม่** — Paces มี pattern "Button Group แนวตั้ง" ขึ้นทะเบียนแล้วที่
  `paces-component-reference.md §2` (`inline-flex flex-col` + มุมโค้งแบ่งบน/กลาง/ล่าง)
- ที่ ≥`sm` (640px → เหลือ 560px) กลับเป็นแถวเดียวตามเดิม ไม่มีทางล้น

```
┌───────────────────────┐

### a11y — หน้า A

**1) แถบสถานะ 3 ค่า → `radiogroup` จริง ไม่ใช่ปุ่ม `aria-pressed`**

ของเดิมที่ `KeywordEditorClient` เป็น "ปุ่มอิสระ 3 ปุ่มที่ toggle กันเอง" ⇒ คีย์บอร์ดต้อง Tab ผ่านทีละปุ่ม
(3 stop) ซึ่งไม่ใช่พฤติกรรมที่ผู้ใช้ screen reader คาดหวังจาก radio (ลูกศรเปลี่ยนค่า · Tab แค่ 1 stop)

- container: `role="radiogroup"` + `aria-label="สถานะของระบบสร้างออเดอร์อัตโนมัติ"`
- แต่ละปุ่ม: `role="radio"` · `aria-checked={status===key}` · `tabIndex={status===key ? 0 : -1}`
  (roving tabindex — มีแค่ตัวที่เลือกอยู่ที่ Tab เข้าถึงได้)
- `onKeyDown`: ลูกศร **ขวา/ซ้าย** (แถวเดียวเสมอ — หน้านี้ไม่แสดงต่ำกว่า 768px แล้ว)
  `aria-orientation="horizontal"` ค่าเดียว **ไม่ต้องผันตาม breakpoint อีก** หลังมติ gate
  (ข้อควรระวังเดิมยังใช้ได้กับหน้าอื่นที่แถบสลับแนวจริง: ทิศลูกศรที่ประกาศต้องตรงกับที่ตาเห็น)
- `Home`/`End`: ไป `ไม่ใช้งาน` / `สร้างออเดอร์จริง` ทันที
- 🛑 **หนี้ที่พบระหว่างทาง (ไม่แก้ในรอบนี้):** `KeywordEditorClient.tsx` ต้นทางยังใช้ `aria-pressed`
  ซึ่งไม่ใช่ radiogroup ที่ถูกตาม APG เช่นกัน — **ไม่แก้เพราะไม่ใช่ไฟล์ที่ 00061 แตะ** ส่งต่อให้
  Controller ตัดสินว่าจะ backport หรือไม่

**2) การ์ดตรวจสุขภาพเพจ — live region ต่อ "แถว" ไม่ใช่ทั้งการ์ด**

ห่อ `aria-live` ที่การ์ดทั้งใบ ⇒ พอมีหลายเพจ แถวเดียวเปลี่ยนสถานะจะทำให้ screen reader อ่านซ้ำทุกแถวใหม่หมด

```jsx
<span role="status" aria-live="polite" aria-atomic="true">
  {/* ข้อความสถานะปัจจุบันของแถวนี้ เช่น "กำลังซ่อม..." / "ซ่อมสิทธิ์ของ ... แล้ว" */}
</span>
```

`aria-atomic="true"` เพราะข้อความสั้นและเปลี่ยนทั้งก้อน (ไม่ใช่ diff บางส่วน) — ประกาศ 4 ช่วง:
`ตรวจอยู่` → `ไม่ผ่าน...` → (กด) `กำลังซ่อม...` → `ซ่อมสิทธิ์ของ ... แล้ว` หรือ `ซ่อมให้ ... ไม่สำเร็จ`
ทุกช่วงเป็น **`polite` ไม่ใช่ `assertive`** เพราะไม่ใช่เหตุฉุกเฉินที่ต้องขัดจังหวะสิ่งที่ผู้ใช้กำลังอ่านอยู่

**3) แม่แบบสรุปคำสั่งซื้อ — ใช้ `<textarea readOnly>` ไม่ใช่ `<pre>`**

`<pre>` อ่านออกได้ (กับดัก "aria-label ไม่มีผลกับ `div`/`p`/`span` เปล่า" ไม่กระทบ `<pre>` เพราะเนื้อหา
เป็น text content จริง ไม่ใช่ label ลอย) **แต่ก็อปด้วยคีย์บอร์ดล้วนไม่ได้** — ถ้า clipboard API ใช้ไม่ได้
แล้วตกไปที่ข้อความ "กรุณาเลือกและคัดลอกด้วยตัวเอง" ผู้ใช้ที่ไม่มีเมาส์จะเลือกข้อความใน `<pre>` ไม่ได้เลย
(ไม่ใช่ focusable element)

```jsx
<textarea readOnly aria-label="ตัวอย่างข้อความแม่แบบสรุปคำสั่งซื้อ"
  className="form-textarea bg-default-50 border-dashed resize-none" rows={9} />
```

🛑 **`readOnly` ไม่ใช่ `disabled`** — `disabled` จะดึงออกจาก tab order ทำให้ Tab ไม่ถึงเลย ส่วน `readOnly`
ยัง focus ได้ + เลือกทั้งหมดด้วย Ctrl/Cmd+A ได้ แค่แก้ไขไม่ได้ · ปุ่ม `คัดลอกข้อความนี้` ยังเป็นทางลัดหลัก
(1 คลิก / 1 Enter) — `<textarea readOnly>` เป็น**ทางสำรอง** ไม่ใช่การถอดปุ่มออก

**4) ผลลัพธ์ "ลองพิมพ์ดู":** `role="status"` + `aria-live="polite"` ห่อผลลัพธ์ที่เปลี่ยนหลังกดทดสอบ

## หน้า B — การ์ดผลลัพธ์ในเธรดแชท

### User stories ที่ครอบ

- ในฐานะร้าน ฉันพิมพ์สรุปคำสั่งซื้อในแชทตามปกติ แล้วอยากเห็นทันทีว่าระบบกำลังอ่านอยู่ — ไม่ใช่เงียบจนไม่รู้ว่ามันทำงานหรือเปล่า
- ในฐานะร้าน เมื่อระบบสร้างออเดอร์ได้ ฉันอยากกดดูใบนั้นได้ทันทีจากในแชท และกดส่งสรุปให้ลูกค้าได้โดยไม่ต้องสลับจอ
- ในฐานะร้าน เมื่อข้อความของฉันไม่ครบ ฉันอยากเห็น **เหตุผลทุกข้อพร้อมกัน** จะได้แก้ทีเดียวจบ ไม่ใช่แก้ทีละรอบแล้วเจอปัญหาใหม่ทุกครั้ง
- ในฐานะร้าน ฉันอยากเปิดฟอร์มที่กรอกไว้ให้แล้วต่อจากร่างได้ในคลิกเดียว โดยไม่ต้องพิมพ์ข้อมูลที่ระบบแกะได้แล้วซ้ำ
- ในฐานะร้าน ถ้าฉันพิมพ์ข้อความจุดชนวนซ้ำสำหรับลูกค้าคนเดิม ฉันอยากรู้ว่าใบใหม่มาแทนใบไหน และยกเลิกใบเก่าได้จากตรงนั้นเลย
- ในฐานะร้าน ฉันอยากมั่นใจว่าการ์ดนี้ไม่มีวันหลุดไปหาลูกค้า และไม่มีวันไปรบกวนบอทตอบอัตโนมัติของห้องนั้นโดยที่ฉันไม่รู้ตัว

### การ์ดนี้ต้องไม่เหมือนบับเบิลข้อความของร้าน — แยกด้วยรูปทรงอะไร

**ยืนยันกับโค้ดจริงแล้ว (`ChatThread.tsx`):** บับเบิลข้อความปกติของร้านใช้ `rounded px-6 py-3 bg-primary text-white`
วางใน `<div className="my-* flex justify-end">` ชิดขวาเสมอ มี avatar + delivery-tick + เวลา — นี่คือ "ไวยากรณ์ภาพ"
ที่ผู้ขายอ่านเป็น **สิ่งที่ฉันพิมพ์ไปหาลูกค้า** มาตลอดทั้งระบบ

🛑 **มีต้นแบบอยู่แล้วในไฟล์เดียวกันสำหรับ "การ์ดของระบบที่ไม่ใช่ข้อความที่พิมพ์"** — ข้อความชนิด `CALL`
(`ChatThread.tsx:3166-3194`) แก้ปัญหาเดียวกันมาแล้ว: คอมเมนต์ในโค้ดเขียนไว้ตรง ๆ ว่าใช้ `bg-default-100`
(ไม่ใช่ `bg-primary`) + **ไม่มี avatar/สถานะส่ง** "เพื่อไม่ให้อ่านเป็นข้อความที่ร้านพิมพ์เอง"
แต่ `CALL` ยังคง **ตำแหน่งชิดขวาแบบบับเบิล** (`justify-end`, `max-w-xs`) เพราะมันยังมีทิศทาง
(สายเข้า/สายออก) ที่สื่อความหมาย

**การ์ดของฟีเจอร์นี้ไม่มีทิศทางแบบนั้น** — มันไม่ใช่ "สิ่งที่ฝั่งไหนพูด" แต่เป็น **ผลลัพธ์ของระบบที่แปะอยู่
ใต้ข้อความ** จึงตัดขาดจากไวยากรณ์บับเบิลไปอีกขั้นหนึ่งกว่า `CALL`:

| ลักษณะ | บับเบิลข้อความ (ปกติ / `CALL`) | การ์ดผลลัพธ์ (ใหม่) |
|---|---|---|
| ตำแหน่งแนวนอน | ชิดข้างใดข้างหนึ่งเสมอ (`justify-end/start`) | **เต็มความกว้างคอลัมน์แชท ไม่ชิดข้าง** — ตัดไวยากรณ์ซ้าย/ขวาทิ้ง |
| รูปทรงมุม | `rounded` (bubble ปัดมุมเบา) | `rounded-lg` เหมือน `.card` ของ Paces + `border` รอบเต็ม 1px |
| พื้น | `bg-primary`(ร้าน) / `bg-light`(ลูกค้า) / `bg-default-100`(`CALL`) | `bg-card` (ขาว) — เหมือนการ์ดออเดอร์ในแผงขวา ไม่เหมือนบับเบิลไหนเลย |
| ตัวบอกที่มา | ไม่มี (บับเบิลบอกทิศเอง) | **แถบซ้าย `border-s-3 border-{semantic}`** (carve-out ที่ขึ้นทะเบียนแล้วใน DESIGN.md เฉพาะ `(paces)`) + หัวการ์ดมีไอคอน `robot` + label `ผลจากข้อความนี้ · เห็นเฉพาะคุณ` **เสมอทุกสถานะ** |
| avatar / เวลาส่ง | มี (ยกเว้น `CALL` ไม่มี avatar) | ไม่มีทั้งคู่ — มีแค่เวลาแบบ meta เล็ก (`text-2xs text-default-500`) ไม่ใช่ timestamp สไตล์ข้อความ |

🛑 **เหตุผลที่ "เต็มความกว้าง ไม่ชิดข้าง" เป็นตัวตัดสินหลัก:** มันคือสิ่งเดียวที่มองจากระยะไกล/เหลือบตา
บนมือถือแล้วแยกออกได้ทันที **โดยไม่ต้องอ่านตัวหนังสือเลย** — ผู้ขายไล่สายตาลงมาเห็น "แถบเต็มแนวนอน"
สลับกับ "บับเบิลชิดข้าง" อ่านออกทันทีว่าอันไหนคือสิ่งที่ตัวเองพิมพ์ อันไหนคือระบบพูดกับตัวเอง —
ตรงกับความเสี่ยงจริงที่ BR-ACO-21a ยืนยันแล้ว (ระบบนับข้อความฝั่งร้านทุกชนิดเป็น "การตอบ")
⇒ **ต้องแยกที่ระดับสายตา ไม่ใช่แค่ระดับสี**

### ตัดสิน 3 ข้อ ก่อน anatomy

**1) "ใต้ข้อความที่ทำให้เกิด" = ระยะห่างต้องไม่เท่าข้อความอื่น**

ยืนยันจากโค้ด: gap ปกติระหว่างบับเบิลคือ `my-5` (20px) เหมือนกันทั้งไฟล์ (`ChatThread.tsx:3047,3179,3475`)
— นี่คือจังหวะที่ผู้ขายอ่านเป็น "ข้อความถัดไป" ทุกครั้ง ⇒ การ์ดผลลัพธ์ **ต้องใช้ระยะที่ต่างออกไปโดยตั้งใจ**

**ตัดสิน: `mt-1` (4px) เหนือการ์ด · `mb-5` (20px) ใต้การ์ด (asymmetric gap)**
- `mt` เล็กพอให้สายตาอ่านว่า "นี่คือผลของบรรทัดบน"
- `mb` เท่าปกติ เพื่อไม่ให้ข้อความ **ถัดไป** ดูเหมือนเป็นส่วนหนึ่งของการ์ดนี้ไปด้วย
- ถ้าทำแน่นเท่ากันทั้งสองด้าน จะไปกลืนกับข้อความของลูกค้าที่อาจแทรกมา (race กับ echo)

**2) `READING` ไม่เพิ่มสถานะที่ 5 — แต่ต้องมี "เหตุผลที่ 9" ที่เป็นระดับระบบ**

BR-ACO-19 บังคับอยู่แล้วว่า **ทุกความล้มเหลวต้องตกเป็นร่าง ไม่มีข้อยกเว้น** ⇒ timeout/crash ก็คือ
ความล้มเหลวแบบหนึ่ง ต้องจบที่ `DRAFT` เหมือนกัน **ไม่ต้องมีสถานะที่ 5**

🛑 **แต่ห้ามใช้ 8 เหตุผลใน PRD §4.3 กับเคสนี้** — 8 ข้อนั้นเป็นเหตุผล **เชิงเนื้อหา** ("ไม่พบเบอร์โทร" ฯลฯ)
ซึ่งทั้งหมดสื่อว่า *ระบบอ่านสำเร็จแต่ข้อมูลไม่ครบ* ส่วน timeout คือ *ระบบไม่ได้อ่านจบเลย*
⇒ ถ้าใช้เหตุผลผิดชุด (ขึ้น "ไม่พบเบอร์โทร" ทั้งที่จริงคือ crash) **ร้านจะไปแก้เบอร์ที่ถูกอยู่แล้ว
แล้วกดใหม่ไปเรื่อย ๆ โดยไม่มีวันหาย**

⇒ **เหตุผลที่ 9 = `ประมวลผลไม่สำเร็จ`** (ระดับระบบ ไม่ใช่ระดับธุรกิจ) และการ์ด `DRAFT` ที่มาจากเหตุนี้
🛑 **ไม่มีปุ่ม "เปิดฟอร์มที่กรอกไว้ให้แล้ว"** เพราะไม่มีอะไรถูกแกะเลย — ปุ่มนั้นจะเปิดฟอร์มเปล่าซึ่งเป็นการโกหก
มีแค่ปุ่ม **`ลองอ่านข้อความนี้อีกครั้ง`** แทน

> **ค้างให้ SRS ตัดสิน:** เพดานเวลาก่อนตัดสินว่า "ไม่สำเร็จ" — ux เสนอ **2 นาที** (สูงกว่ามัธยฐานเป้า 5 วิ
> มาก แต่ไม่ปล่อยหมุนตลอดกาล) เป็นค่าฝั่ง backend ไม่ใช่สิ่งที่ ux ตัดสินเอง

**3) งบพื้นที่หัวการ์ดที่ 320px — `เห็นเฉพาะคุณ` รอด แต่ต้องตัดวลีอื่นทิ้ง**

| รายการ | ความกว้าง |
|---|---|
| viewport | 320px |
| − padding thread (`px-4` ×2) | เหลือ **288px** |
| − border + card padding (`px-3` ×2) | เหลือ **264px** |
| − ไอคอน 16px + `gap-2` | เหลือ **240px** |
| − เวลา (`text-2xs` "10:32") + gap | เหลือ **194px** |
| `ผลจากข้อความนี้ · เห็นเฉพาะคุณ` (30 ตัวอักษร @ ~8.25px) | **ต้องการ ~247px** |

**ต้องการ 247px มีที่ให้ 194px → ล้น 53px** ⇒ **ตัดสิน: ตัด `ผลจากข้อความนี้` ทิ้งทั้งวลี ไม่ใช่ย่อคำ**

เหตุผลที่ตัดได้โดยไม่เสียความหมาย: "ผลจากข้อความนี้" **ถูกสื่อไปแล้วโดยตำแหน่ง** (`mt-1` ติดบับเบิล — ข้อ 1)
และ **โดยรูปทรง** (เต็มความกว้าง ไม่ชิดข้าง) ⇒ เป็นข้อมูลซ้ำ. ส่วน `เห็นเฉพาะคุณ` เป็นสิ่งเดียวที่
**ไม่มีช่องทางอื่นสื่อได้เลย** — ไม่มีสัญญาณภาพใดบอกว่า "สิ่งนี้ไม่ถูกส่งออก"

คำนวณใหม่: `เห็นเฉพาะคุณ` (~99px) + ไอคอน 24px + เวลา 46px = **169px จาก 264px** เหลือเผื่อ 95px ผ่านทุก breakpoint

**label เฉพาะสถานะ** ("กำลังอ่าน" / "สร้างคำสั่งซื้อแล้ว" / "ยังสร้างไม่ได้") **ย้ายไปเป็นหัวข้อใน body ของการ์ด**
(`text-sm font-semibold`) ไม่ใช่แถบ meta บนสุด — แถบบนสุดเป็น **meta คงที่ทุกสถานะ** โครงนี้ตรงกับ
`OrderCardView` เดิมที่แยก header ออกจาก meta อยู่แล้ว

### Anatomy — โครงร่วมทุกสถานะ

```jsx
<div
  role="status" /* READING เท่านั้น — สถานะอื่นนิ่งแล้วไม่ต้อง live-announce ซ้ำ */
  aria-live={state === 'READING' ? 'polite' : undefined}
  className="rounded-lg border border-default-200 border-s-3 ${accent} bg-card overflow-hidden"
>
  {/* แถบ meta — เหมือนกันทุกสถานะ = ตัวตัดขาดจากบับเบิลข้อความอย่างถาวร */}
  <div className="bg-default-50 border-default-200 flex items-center gap-2 border-b border-dashed px-3 py-1.5">
    <Icon icon="robot" className="text-default-500 shrink-0 text-sm" aria-hidden="true" />
    <span className="text-default-500 text-2xs font-medium">เห็นเฉพาะคุณ</span>
    <span className="text-default-400 ml-auto shrink-0 text-2xs">{formatTimeHM(createdAt)}</span>
  </div>
  <div className="px-3.5 py-3">{/* body ต่างกันตามสถานะ */}</div>
</div>
```

`accent`: `READING` = `border-default-300` (ยังไม่รู้ผล เป็นกลาง) · `CREATED` ทั้งสองแบบ = `border-primary`
· `DRAFT` = `border-warning` — ตรงกับ Impeccable compliance ที่ล็อกไว้ (`CREATED` น้ำเงินไม่ใช่เขียว)

### สถานะ `DRAFT`

**1) ลำดับเหตุผล — เดินตามลำดับช่องในฟอร์มสร้างออเดอร์**

เหตุผลผูกกับ **"ช่องที่ต้องแก้"** ไม่ใช่ "ความยาก" หรือ "ลำดับใน §4.3" เพราะพฤติกรรมจริงคือร้านกด
`แก้ไขคำสั่งซื้อ` แล้วไล่แก้จากบนลงล่างอยู่ดี ⇒ ให้รายการเหตุผลเดินลำดับเดียวกัน
ลดภาระ "แปลจากลิสต์นี้ไปหาตำแหน่งในฟอร์ม" ในหัวคนอ่าน

🛑 **ลำดับที่ยืนยันกับฟอร์มจริงแล้ว** (`QuickForm.tsx` = ฟอร์มที่ใช้จริงบนมือถือ/แท็บเล็ต `<lg`) —
ลำดับ block จริงคือ `CustomerQuickBlock` (ชื่อ/เบอร์/ที่อยู่) → `ChannelPaymentSelect` →
**`OrderDateRow` (วันที่)** → `QuickLineItem` (รายการสินค้า) → `MoreOptions` → `QuickSummaryPanel` (ยอดรวม)

**ลำดับเหตุผลที่ต้องใช้:**
1. เบอร์ (ไม่พบ → ไม่ถูกต้อง)
2. ที่อยู่ไม่ครบ
3. **เวลาเกินเพดานที่ยอมรับ**
4. รายการสินค้า (ไม่พบ → ไม่ระบุราคา → ไม่ตรงร้าน)
5. ยอดรวมไม่ตรง

> ⚠️ **แก้จากร่างแรกของ ux:** ร่างแรกวาง "เวลาเกินเพดาน" ไว้ **ท้ายสุด** ด้วยเหตุผลว่า *"วันที่มักอยู่ท้ายฟอร์ม"*
> — ux ติดป้ายไว้เองว่าเป็นสมมติฐานที่ยังไม่ได้เปิดฟอร์มดู. **Controller ตรวจแล้วพบว่าไม่จริง**: ช่องวันที่อยู่
> **ตำแหน่งที่ 3 ก่อนรายการสินค้า** ⇒ ถ้าใช้ลำดับเดิม ผู้ขายจะไล่แก้จากบนลงล่างแล้ว **ข้ามช่องวันที่ไปโดยไม่รู้ตัว
> แล้วต้องเลื่อนย้อนกลับขึ้นไป** ซึ่งทำลายเหตุผลทั้งหมดที่เลือกเรียงตามฟอร์มตั้งแต่แรก

**2) ค่าที่อ่านได้ — ใส่ได้แค่บางข้อ ไม่ใช่ทุกข้อ**

กติกา: **ค่าที่ยาว "คงที่" (ตัวเลข/ศัพท์ปิด) → ใส่ได้ · ค่าที่ผู้ใช้พิมพ์เองยาวไม่จำกัด (ชื่อสินค้า) → ไม่ใส่**
เพราะค่าที่ยาวไม่จำกัดทำให้ความสูงของการ์ดคาดเดาไม่ได้

| เหตุผล | ใส่ค่าเสริม | รูปแบบ |
|---|---|---|
| ไม่พบเบอร์โทร | ไม่ | ไม่มีอะไรให้อ้าง |
| เบอร์ไม่ถูกต้อง | **ใส่** | `เบอร์ไม่ถูกต้อง (081234567)` — ตัวเลขล้วน สั้นคงที่ |
| ที่อยู่ไม่ครบ | **ใส่** | `ที่อยู่ไม่ครบ — ขาดรหัสไปรษณีย์` (ขาด 1 ส่วน = ระบุชื่อ · ≥2 ส่วน = `ขาด 2 ส่วน` ไม่แจกแจง — ชื่อ 3 คำนี้เป็นศัพท์ปิด ไม่ใช่ข้อความอิสระ) |
| ไม่พบรายการสินค้า | ไม่ | ไม่มีอะไรให้อ้าง |
| มีรายการแต่ไม่ระบุราคา | **ไม่** | ชื่อสินค้าอิสระยาวไม่จำกัด — เสี่ยงพังเลย์เอาต์ |
| สินค้าไม่ตรงกับที่มีในร้าน | **ไม่** | เหตุผลเดียวกับข้อบน |
| ยอดรวมไม่ตรง | **ใส่ (บังคับโดย BR-ACO-17)** | ดูข้อ 3 |
| เวลาเกินเพดานที่ยอมรับ | **ใส่** | `(3 วันก่อน)` สั้นคงที่ |

**งบต่อแถว:** body content ≈256px − ไอคอน+gap (32px) = **224px/บรรทัด** (≈32 ตัวอักษรไทยที่ `text-xs`)
**สูง/แถว:** `py-1 gap-2` + icon 14px + `text-xs` ≈ **28px** · แถว "ยอดรวมไม่ตรง" ที่ตก 2 บรรทัด ≈ **46px**

**กางเลข 4 เหตุผลพร้อมกัน:**

| ส่วน | สูง |
|---|---|
| แถบ meta ("เห็นเฉพาะคุณ") | 32px |
| หัว `ยังสร้างไม่ได้ — ต้องแก้ N อย่าง` | 26px |
| 4 แถว (เบอร์+ที่อยู่+สินค้าไม่ตรง+ยอดรวม) = 28+28+28+46 | 130px |
| เส้นประ + ปุ่ม 2 ใบ (`min-h-11`) + padding | 68px |
| padding การ์ด (`py-3` ×2) | 24px |
| **รวมในการ์ด** | **≈280px** |
| + `mt-1` (4) + `mb-5` (20) | **≈304px** |

**เทียบพื้นที่เห็นจริงบนจอเล็กสุด (320×568):**
568 − หัวแอป (~56) − หัวห้องแชท (~60) − แถบพิมพ์+เครื่องมือ (~72) ≈ **380px ที่เห็นจริง**
⇒ **การ์ด 304px จาก 380px ≈ 80%** — สูงจริง **แต่ไม่ใช่ทั้งจอ** ยังเหลือ ~76px ให้เห็นขอบบับเบิลก่อน/หลัง
ว่ามีบทสนทนาต่อ (5 เหตุผลจะดันเป็น ~332px ≈ 87%)

เจอเหตุผลใหม่อีกรอบ** (กดวน ซึ่ง PRD ห้ามไว้ตรง ๆ)

`confirmButtonText:'ทิ้งร่างนี้'` · ปุ่ม `bg-danger text-white` ตาม pattern `SweetAlerts.tsx`

### สถานะที่ 4 — `CREATED` ที่เป็นใบแทนใบก่อนหน้า

**ยืนยันกับโค้ดจริงก่อนออกแบบปุ่มยกเลิก** (`order.service.ts::cancelOrder`):
- ด่านเดียวที่บล็อกคือ `assertTransition` — **ยกเลิกไม่ได้เมื่อ `status === CONFIRMED`** (ลูกค้ากดยืนยันที่
  `/o/{token}` แล้ว) ส่วน `PENDING`/`SHIPPED` **ยกเลิกได้เสมอ แม้เปิดพัสดุ iShip ไปแล้ว** — ไม่มี guard เรื่องพัสดุ
- `cancelOrder()` **คืนสต๊อกอัตโนมัติเสมอ** (`restockFromCancelledOrder`)
- 🛑 **แต่ไม่แตะ `OrderShipment`/iShip เลยแม้แต่บรรทัดเดียว** ⇒ ถ้าขนส่งเปิดพัสดุไปแล้ว **การยกเลิกออเดอร์
  ไม่ได้ยกเลิกพัสดุให้** ⇒ **ต้องเตือนในคำถามยืนยัน ไม่ใช่ปล่อยให้ร้านเดา**

> 🛑 **ค้างให้ product/user ตัดสิน:** ไม่มีค่าเหตุผลยกเลิกใดใน `CANCEL_REASONS_BY_VERTICAL.ONLINE_SALES`
> (`src/lib/cancel-reasons.ts`) ที่ตรงกับ "ถูกแทนที่ด้วยใบใหม่" — ux **ไม่ตัดสินเรื่อง enum เอง**

**บล็อก "ใบเก่า" = sub-notice เล็กในการ์ดเดียวกัน ไม่ใช่การ์ดซ้อนการ์ด:**

```
┌ (body ส่วนบนเหมือน CREATED ปกติ: ไอคอน/ยอด/เลขออเดอร์/รายการ) ────────┐
│ ...                                                                    │
│ ┌ bg-default-50 rounded-lg px-2.5 py-2 mt-2 ─────────────────────┐    │
│ │ [icon:repeat] แทนที่ DP2608A1C2 (ลิงก์ขีดเส้นใต้)                 │    │ ← text-xs
│ │ ลูกค้าพิมพ์คำสั่งซื้อซ้ำสำหรับคนเดียวกัน                          │    │ ← text-2xs text-default-500
│ │ [ยกเลิกใบเก่า]  (ghost text-danger · min-h-11)                   │    │
│ └───────────────────────────────────────────────────────────────┘    │
│ (แถบเตือน "ลูกค้ายังไม่เห็นสรุปนี้" + ปุ่ม ดูคำสั่งซื้อ/ส่งเข้าแชท เหมือน CREATED ปกติ) │
└─────────────────────────────────────────────────────────────────────┘
```

**3 สถานะของ sub-notice (ต้องมีครบ ไม่ใช่แค่ happy path):**

| สถานะใบเก่า | ปุ่ม/ข้อความ |
|---|---|
| **ยกเลิกได้** (`PENDING`/`SHIPPED`) | ปุ่ม `ยกเลิกใบเก่า` ใช้งานได้ → Swal |
| **ยกเลิกไม่ได้แล้ว** (`CONFIRMED`) | **ไม่มีปุ่ม** — แทนด้วยข้อความกลาง `text-default-500`: `ใบเก่ายืนยันแล้ว — ยกเลิกไม่ได้จากที่นี่ ถ้าเป็นการสั่งซ้ำจริง ให้ติดต่อลูกค้าโดยตรง` (**ไม่ใช้สีแดง/เตือน** เพราะไม่ใช่ข้อผิดพลาด เป็นข้อเท็จจริง) |
| **ถูกยกเลิกไปแล้ว** (ร้านกดจากที่อื่นคู่ขนาน) | ไอคอน `check` กลาง + `ใบเก่าถูกยกเลิกแล้ว` — ไม่มีปุ่มซ้ำ |

**Swal ยืนยันยกเลิกใบเก่า** (`icon:'warning'` · `showCancelButton:true`):
- หัวข้อ: `ยกเลิก {orderNo เก่า}?`
- บรรทัดคงที่: `สต๊อกที่ตัดไว้ของใบนี้จะถูกคืนอัตโนมัติ`
- 🛑 **บรรทัดเงื่อนไข — ต่อเมื่อใบเก่ามีพัสดุ iShip `status='CREATED'`:**
  `ใบนี้เปิดพัสดุกับขนส่งไว้แล้ว — การยกเลิกนี้ไม่ได้ยกเลิกพัสดุให้อัตโนมัติ ไปที่ใบเดิมเพื่อจัดการพัสดุด้วยตัวเอง`
  (ต้องมี icon `alert-triangle` + `bg-warning/10` **แยกกล่องจากบรรทัดบน** เพราะเป็นความเสี่ยงที่หนักกว่า "แค่คืนสต๊อก")
- ปุ่ม: `ยกเลิกใบเก่า` (`bg-danger text-white`) / `ไม่ยกเลิก`
- สำเร็จ → `pacesToast.success('ยกเลิก {orderNo เก่า} แล้ว')` + sub-notice เปลี่ยนเป็น "ถูกยกเลิกแล้ว" ทันที (optimistic)

### a11y รวม — หน้า B

- **การ์ดทั้ง 4 สถานะ:** `role="group"` + `aria-label` สรุปสั้นตามสถานะ (เช่น `aria-label="ผลจากข้อความนี้ — สร้างคำสั่งซื้อแล้ว ฿840"`) เพราะ `border-s-3`/สีเป็นสัญญาณภาพล้วนที่ screen reader อ่านไม่ได้
- **`READING` เท่านั้น** ที่ `role="status" aria-live="polite"` — สถานะอื่นนิ่งแล้ว ไม่ต้อง live-announce ซ้ำทุก re-render
- 🛑 **ปุ่ม `ยกเลิกใบเก่า` ที่กดไม่ได้:** ใช้ `aria-disabled="true"` + `title` เหตุผล **ไม่ใช่ `disabled` ล้วน**
  ที่ดึงออกจาก tab order เงียบ ๆ — ผู้ใช้ screen reader ควรได้ยินเหตุผลว่าทำไมกดไม่ได้ ไม่ใช่ถูกข้ามไปเฉย ๆ
- **ลิงก์ `แทนที่ {orderNo}`** ต้องเป็น `<a href="/orders/{token}">` จริง ไม่ใช่ `<span onClick>` — keyboard-reachable
- **tap target ≥44px ทุกปุ่มในการ์ด** (`min-h-11` เสมอ ไม่มีข้อยกเว้น แม้ในการ์ดที่แน่นที่สุด)

### ข้อตัดสินที่ยังใช้ได้ (ยกมาจากหัวข้อเดิม)

1. **เรียงลำดับ: ร่างที่ใกล้หมดอายุก่อน** — `expiresAt` เป็น timestamp คงที่ ⇒ **ลำดับไม่ขยับเองตามเวลา**
   ⇒ เมื่อชิป "ร่าง" ถูกเลือก ให้เรียง `expiresAt ASC` แทนค่าเริ่มต้นของหน้า (`createdAt DESC`)
   เพราะเหตุผลที่ชิปนี้มีอยู่คือ **"งานที่กำลังจะหาย"** ไม่ใช่ "ของใหม่ล่าสุด"
2. **ป้ายบอกอายุบนแถวร่าง** — `[icon:clock] หมดอายุใน N วัน` · เปลี่ยนเป็นโทน warning เมื่อเหลือ **≤24 ชม.**
   (นี่คือกลไก "แจ้งเตือนล่วงหน้า 1 ครั้ง" ของ v1 ตามมติ user)
3. 🛑 **empty state ต้องแตกสาขาเมื่อฟีเจอร์ปิดอยู่** — `ไม่มีร่างค้าง` สื่อว่า *"ทำงานอยู่แล้วไม่เจอปัญหา"*
   ซึ่ง **ผิดถ้าฟีเจอร์ปิด** (ความจริงคือ *"ไม่เคยทำงาน"*) ⇒ เมื่อ `status='OFFLINE'` และไม่เคยมีร่างเลย
   ใช้ข้อความ `ยังไม่ได้เปิดใช้งาน` + ปุ่ม `ไปตั้งค่า`
4. **ร่างที่ถูกกู้เป็นออเดอร์จริงแล้ว** — หายจากชิป "ร่าง" เองตามธรรมชาติ (สถานะเปลี่ยนเป็น `PENDING`)
   **ไม่ต้องมีกลไกยุบแถวชั่วคราวอีกแล้ว** เพราะแถวยังอยู่ในหน้าเดียวกัน แค่ย้ายไปอยู่ใต้ชิปอื่น
   ⇒ **ข้อดีที่ได้ฟรีจากมติใหม่** (เดิมต้องออกแบบแถบยืนยันชั่วคราวเพื่อไม่ให้ของหายวับ)

## Anti-slop self-check

1. **เฉพาะกับ Deep จริงไหม** — ใช่: ผูกกับ `createOrder()` เดียวกับทุกช่องทาง (BR-ACO-16) · เกณฑ์เบอร์ไทย 06/08/09 · `resolveOrderVocab` ผันคำตาม vertical · Sweet Alerts + Paces token · ปุ่ม "ส่งเข้าแชท" เรียก handler จริงที่มีอยู่แล้ว — **เอาไปแปะสินค้าอื่นไม่ได้โดยไม่แก้อะไรเลย**
2. **พระเอกต่อจอ** — หน้า B: การ์ดผลลัพธ์เต็มความกว้าง · หน้า C: การ์ดร่างแต่ละใบ (reuse หน้า B) · หน้า D: badge เดียว
3. **ตัดของซ้ำ** — ตัด "ผลจากข้อความนี้" ออกจากแถบ meta (ซ้ำกับตำแหน่ง+รูปทรง) · ไม่ nest `OrderCardView` เต็มใบ · ค่าเสริม "ที่อ่านได้" ใส่เฉพาะ 4/9 เหตุผลที่คุ้มจริง **ไม่ใส่ทุกข้อเพื่อความครบ**
4. **states ครบ** — 5 body variant · empty ×3 แบบ · skeleton · ชื่อเพจ 34 ตัวอักษร · 0 รายการ · **ยอดหลักล้าน (7 หลัก): ยอดเงิน `shrink-0` มีสิทธิ์เหนือ label เสมอ label ยาว truncate ก่อน** (ให้ QA ยืนยันด้วยเลขจริง)
5. **copy บอกผลลัพธ์จริง** — ทุกปุ่มไม่ใช่ท่าทาง และ error/empty ทุกจุดบอกทางออกเสมอ
6. **คำเดียวกัน = ของเดียวกัน** — "ร่าง"/"เห็นเฉพาะคุณ"/ปุ่มทั้งคู่ใช้คำเดียวกันซ้ำระหว่างหน้า B/C ทุกตัวอักษร · "ส่งเข้าแชท" ตรงกับปุ่มเดิมของระบบเป๊ะ · icon `flask` ตัวเดียวกับที่ `ChatThread.tsx` ใช้อยู่แล้ว
7. **สีถูกความหมาย** — `CREATED` น้ำเงินไม่ใช่เขียว · "ส่งแล้ว"/empty ที่ดีใช้กลาง (delivery/absence-of-problem ≠ verified) · `DRAFT` เนื้อหา = warning เสมอ · ระบบ-ล้มเหลว = กลางเสมอ (ไม่กล่าวหาร้าน)
8. **แตะได้จริงบนมือถือ** — `min-h-11` ทุกปุ่มไม่มีข้อยกเว้น · แถวหัวการ์ดหน้า C ทั้งแถวเป็น tap target · action หลักอยู่โซนล่างของการ์ด
9. **1440px ไม่มีคอลัมน์ว่าง** — **พบช่องโหว่จริงระหว่างเช็ค (หน้า C ไม่มีเดสก์ท็อป layout) แก้แล้วก่อนปิดสเปก** ไม่ปล่อยเป็นหมายเหตุลอย
