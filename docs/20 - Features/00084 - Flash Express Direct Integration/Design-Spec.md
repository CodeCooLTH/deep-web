## 2. Layout และพฤติกรรมร่วม

### 2.1 Breakpoint (Paces: เส้นเดียวที่ `lg` = 1024px)
- ต่ำกว่า 1024px (รวม 375 และ 768): โมดัลเป็น **bottom-sheet** (`IShipModalShell`) ไม่ใช่ modal กลางจอ ดังนั้นภาพ 768 ของโมดัลหน้าตาเหมือน 375 แต่กว้างกว่า
- 1024px ขึ้นไป: modal กลางจอ `lg:max-w-sm|md|2xl`
- เป้าที่กดได้ได้ 44px บนมือถือจากกฎกลางของ `.btn` (`safepay-overrides.css`) ส่วนปุ่มที่ประกอบเองใช้ `min-h-11 lg:min-h-0`

### 2.2 กฎการใช้สีที่ใช้ซ้ำทั้งสเปก
- ปุ่มทึบ `bg-primary text-white` มี **ได้ 1 ใบต่อหน้าจอ/โมดัล** ใบอื่นเป็น tint (`bg-primary/15 text-primary-ink`) หรือขอบ (`border border-default-300`)
- ป้ายสถานะใช้ `TONE_BADGE` / `NOTICE_BOX` จาก `src/components/safepay/iship/tone.ts` ตัวเดียว
- เขียว (success) ใช้เฉพาะ "ยืนยันแล้ว": เชื่อมต่อ ACTIVE, ส่งถึงแล้ว
- ต้องตรวจสอบมือ (NEEDS_REVIEW), ตั้งรับแจ้งสถานะไม่ครบ, ประมาณการ ใช้ warning หรือ neutral ไม่ใช่เขียว
- แดงใช้เฉพาะล้มเหลวจริง (FAILED, ต้องวางคีย์ใหม่ไม่ใช่แดง ใช้ warning เพราะแก้ได้ในหน้าเดียวและไม่ใช่ความล้มเหลวของพัสดุ)

### 2.3 ชนิดของกล่องโต้ตอบ (HR8/HR9)
| พฤติกรรม | เครื่องมือ | Base |
|---|---|---|
| ฟอร์มหลายช่อง (เชื่อมต่อ, ตั้งค่า, เรียกรถ, ฟอร์มสร้างพัสดุ) | `IShipModalShell` (precedent ในรีโพ) | `ui/modals/page.tsx` + `ui/offcanvas/page.tsx` |
| ยืนยัน/ผลลัพธ์ที่ต้องตอบ | Swal ผ่าน `@/lib/paces-swal` (`pacesConfirm.question/warning/danger`, `pacesAlert`) | `plugins/sweet-alerts/components/SweetAlerts.tsx` |
| แจ้งผลที่หายเอง | `pacesToast.*` | ไม่ใช้ `react-toastify` |

ข้อยกเว้นที่ต้องเขียนให้ชัด: โมดัลฟอร์มไม่ใช่ alert/confirm จึงไม่อยู่ใต้ HR8 และมี precedent เดิมในรีโพ (`ShippingSettingsRow`, `ShipmentEntryModal`) การยืนยันทุกชนิดภายในโมดัลเหล่านี้ใช้ Swal

### 2.4 Icon (tabler ผ่าน `components/wrappers/Icon`, ชื่อเปล่า = tabler)
ใช้เฉพาะชื่อที่มีใช้อยู่แล้วในรีโพนี้: `plug-connected`, `plug-off`, `truck`, `truck-delivery`, `settings`, `eye`, `eye-off`, `refresh`, `alert-triangle`, `alert-circle`, `circle-check`, `info-circle`, `lock`, `map-pin`, `chevron-right`, `chevron-down`, `device-floppy`, `copy`, `printer`, `dots-vertical`, `unlink`, `link`, `package`, `package-export`, `package-off`, `edit`, `x`, `loader-2`, `flask`, `phone`, `scale`, `key`, `clock`, `cash`, `receipt`, `photo-off`, `history`, `world`, `send`, `bolt`, `help-circle`, `player-pause`, `settings-automation`
สำหรับการรับแจ้งสถานะ (webhook) ใช้ `world` แทน (ไม่ใช้ชื่อ `webhook` เพราะยังไม่เคยใช้ในรีโพ)
ไม่มี emoji

### 2.5 ภาพโลโก้
`courierLogoUrl('FLASH', 'Flash Express')` ให้ `/images/logos/flash-express.jpeg` (จัตุรัส พื้นเหลืองเต็มกรอบ) ใช้ `object-cover` ไม่ใส่ขอบ/padding ในช่อง `size-9` (แถวตั้งค่า) เหมือน `IShipLogo` และ `object-contain ring-1 ring-default-200` ที่ `size-11` ในหัวสถานะพัสดุตามพี่น้อง ต้องมี fallback เมื่อไฟล์หาย (`useState` + `onError` แสดงไอคอน `truck-delivery`)

## 3. พื้นผิว 1: การ์ดตั้งค่า "Flash Express (บัญชีของร้านเอง)"

Route: `/settings` (ไฟล์ `src/app/(paces)/seller/(dashboard)/settings/page.tsx` + `FlashSettingsRow.tsx`)

### 3.1 User stories ที่ครอบ
FR-FLASH-001..004, 010, 051, 052 · ร้านที่มีสัญญา Flash วาง mchId+key ครั้งเดียวแล้วเห็นสถานะชัด · เจ้าของร้านตัดสินใจเรื่อง webhook ของระบบเดิมโดยไม่โดนเขียนทับเงียบ

### 3.2 การมองเห็น (ไม่ใช่ disabled)
| เงื่อนไข | ผล |
|---|---|
| `connection.available === false` | ไม่ render การ์ดเลย |
| `Shop.vertical !== ONLINE_SALES` | ไม่ render การ์ดเลย (เหมือนการ์ด iShip) |
| ผู้ใช้เป็นเจ้าของร้าน (OWNER) | เต็ม: เชื่อม/เปลี่ยน key/ถอน/ตั้งค่า/ตั้ง webhook |
| ไม่ใช่เจ้าของ (ผู้จัดการ ผ่านด่าน S2) | อ่านอย่างเดียว: เห็น mchId แบบปิดบัง, ทดสอบการเชื่อมต่อได้, เรียกรถได้, ดูค่าตั้งต้นแบบรายการ, **ไม่เห็น key และไม่มีปุ่มแก้** |

การ์ดวางเป็นใบที่สอง ต่อจากการ์ด "การจัดส่ง" (iShip) เรียงแนวตั้งเต็มความกว้าง (`mb-4`) ไม่ทำ 2 คอลัมน์ เพราะเนื้อในแต่ละใบคือ 1 แถว (ข้อความซ้าย ปุ่มขวา) ที่เต็มความกว้างอยู่แล้ว ที่ 1280px ไม่มีคอลัมน์ว่าง

### 3.4 Section breakdown (การ์ด)
- **หัวการ์ด**: `card-header` + `h5` ตามพี่น้อง (เส้นประ) ข้อความ "Flash Express (บัญชีของร้านเอง)"
- **แถวหลัก**: ตามโครง `ShippingSettingsRow` (โลโก้ `size-9` + ชื่อ + บรรทัดรอง + ป้าย | ปุ่มชุดขวา)
- **ป้ายสถานะ** (`TONE_BADGE` ตัวเดียว ไม่เขียนซ้ำ):
  - ยังไม่ได้เชื่อมต่อ: `secondary` + `plug-off`
  - เชื่อมต่อแล้ว: `success` + `circle-check`
  - ต้องตรวจรหัสร้านค้า/Key: `warning` + `alert-triangle`
- **บรรทัดรองแบบเปลี่ยนตามสถานะ**: เชื่อมแล้ว = `mchId AB••34 · ตรวจล่าสุด {formatRelativeDayTime}` (ใช้ `formatDateTime` ตามกฎวันที่ของโปรเจกต์)
- **ปุ่มขวา**:
  - ยังไม่เชื่อม: `เชื่อมต่อ` (tint primary)
  - ACTIVE: `เรียกรถ` (ขอบ) + `ตั้งค่า` (tint primary) ถ้าเจ้าของ, ไม่ใช่เจ้าของ: `ดูค่าที่ตั้งไว้` (ขอบ)
  - TOKEN_INVALID: `วางคีย์ใหม่` (tint warning, เฉพาะเจ้าของ; ผู้จัดการเห็นข้อความ "แจ้งเจ้าของร้านให้วางคีย์ใหม่") + `ตั้งค่า`/`ดูค่าที่ตั้งไว้` (ขอบ)
- **ไม่มีสถานะ loading ของการ์ด** (ข้อมูลมากับ server component) loading มีเฉพาะปุ่มทดสอบ/บันทึก

```
│  ระบบเก็บแบบเข้ารหัสและจะไม่แสดงให้เห็นอีก
│ ┌ (พื้นที่ข้อผิดพลาด role="alert" แสดงเมื่อมี) ┐
│ [        ทดสอบและบันทึก          ]   ← ปุ่มทึบ 1 ใบของโมดัล
```

พฤติกรรม:
- กด `ทดสอบและบันทึก`: ปุ่มเปลี่ยนเป็นสปินเนอร์ + ข้อความ "กำลังทดสอบกับ Flash…" ช่องทั้งหมด `disabled` และโมดัลปิดไม่ได้ (`busy`) เพราะเป็นคำขอที่ปิดกลางทางไม่ได้ (บทเรียน P0 ใน `IShipModalShell`)
- สำเร็จและ webhook ทุกชนิดเรียบร้อย: ปิดโมดัล + `pacesToast.success('เชื่อมต่อ Flash สำเร็จ')` + `router.refresh()`
- สำเร็จแต่ webhook มีชนิดที่ต้องตัดสินใจ (EXTERNAL) หรือลงทะเบียนล้ม: **ไม่ปิดโมดัล** สลับไปแสดงส่วน "การรับแจ้งสถานะ" ทันที พร้อมข้อความ "เชื่อมต่อสำเร็จแล้ว เหลือเรื่องการรับแจ้งสถานะ" เพื่อไม่ให้ข้อมูลการตัดสินใจหายไปกับ toast
- ข้อผิดพลาดแสดงเป็นกล่องในโมดัล (`NOTICE_BOX.danger`, `role="alert"`) ค้างจนกว่าจะแก้ ไม่ใช่ toast อย่างเดียว

ข้อความผิดพลาด (บอกทางออก ไม่ใช้ "ไม่สามารถ…"):

| กรณี | ข้อความ |

| ฟอร์มว่าง | "วางรหัสร้านค้า (mchId) และ Secret Key ให้ครบทั้งสองช่อง" |
| mchId ไม่ผ่านรูปแบบ | "รหัสร้านค้าเป็นตัวอักษรหรือตัวเลข 2–32 ตัว ตรวจว่าพิมพ์ตรงกับที่ Flash ให้มา" |
| key สั้น/มีช่องว่าง | "Secret Key สั้นเกินไป คัดลอกมาให้ครบทั้งชุด" / "Secret Key ต้องไม่มีช่องว่าง คัดลอกใหม่" |
| 1001 | "Flash ไม่พบรหัสร้านค้านี้ ตรวจว่า mchId ตรงกับที่ Flash ให้มา แล้วลองใหม่" |
| 1002 | "Secret Key ไม่ตรงกับรหัสร้านค้านี้ คัดลอก Secret Key จาก Flash มาวางใหม่ทั้งชุด (ระวังช่องว่างหน้า-หลัง)" |

| timeout/502 | "ติดต่อ Flash ไม่ได้ตอนนี้ จึงยังไม่ได้บันทึก ลองอีกครั้งในอีกสักครู่" |

ปุ่ม "ทดสอบการเชื่อมต่อ":
- สำเร็จ: toast "การเชื่อมต่อใช้งานได้ตามปกติ" อัปเดต "ตรวจล่าสุด"
- Flash ตอบ 1001/1002: โมดัลสลับเป็นสถานะ TOKEN_INVALID + toast warning "Flash ปฏิเสธรหัสร้านค้าหรือ Secret Key แล้ว วาง Secret Key ใหม่ด้านล่าง"
- timeout: toast error "ติดต่อ Flash ไม่ได้ตอนนี้ สถานะการเชื่อมต่อยังเป็นเดิม ลองอีกครั้งในอีกสักครู่"

### 3.6 บล็อก "การรับแจ้งสถานะจาก Flash" (webhook) ในโมดัล A

โครง: หัวข้อ `h6` + ป้ายสรุป + (ถ้ามี) รายชนิดแยก + ตัวเลือกของเจ้าของ

```
การรับแจ้งสถานะจาก Flash              [⚠ บางชนิดส่งไประบบอื่นอยู่]
 สถานะพัสดุ   ส่งไปที่ hooks.example.com อยู่แล้ว · ไม่ได้เปลี่ยน
 เส้นทาง      ส่งไปที่ hooks.example.com อยู่แล้ว · ไม่ได้เปลี่ยน
 น้ำหนัก      ส่งมาที่ Deep
 ราคา         ส่งมาที่ Deep
 ข้อมูลคนขับ   ส่งมาที่ Deep

 ระบบเช็คสถานะให้เองทุก 15 นาทีสำหรับชนิดที่ไม่ได้ส่งมาที่ Deep

 ( ◉ ) คงเดิม (เช็คอัตโนมัติทุก 15 นาที)
        ระบบเดิมของคุณรับแจ้งต่อได้เหมือนเดิม สถานะใน Deep อัปเดตช้ากว่าเล็กน้อย
 ( ○ ) เปลี่ยนมาใช้ Deep
        [เลือกแล้วแสดง] ☑ สถานะพัสดุ ☑ เส้นทาง
        ┌ ⚠ ระบบที่รับแจ้งสถานะอยู่ตอนนี้ (hooks.example.com) จะหยุดได้รับ
        │   ข้อมูลจาก Flash ทันที Flash ตั้งปลายทางได้ชนิดละ 1 ที่
        └
        [ เปลี่ยนมาใช้ Deep ]  → Swal warning ยืนยัน
```

กติกา:
- แสดงเฉพาะ **ชื่อโฮสต์** (`host`) ห้ามแสดง path/โทเคน/URL เต็ม
- ป้ายต่อชนิด: OURS/SET = `info` "ส่งมาที่ Deep" (ไม่ใช้เขียว เพราะเป็นการตั้งค่าที่เราทำ ไม่ใช่การยืนยันความเชื่อใจ), EXTERNAL = `warning`, FAILED = `warning` "ตั้งไม่สำเร็จ", UNKNOWN = `secondary` "อ่านค่าที่ตั้งไว้ไม่ได้ · ไม่ได้เปลี่ยน" (ทับไม่ได้ ไม่มี checkbox)
- ตัวเลือกคู่ ◉/○ ใช้โครง radio-card ของ `CREATE_MODES` (precedent) ค่าเริ่มต้น "คงเดิม" และ **ไม่มีปุ่มบันทึกจนกว่าจะเลือก "เปลี่ยนมาใช้ Deep"** (เลือก "คงเดิม" = ไม่ต้องทำอะไร)
- ปุ่ม `เปลี่ยนมาใช้ Deep` → `pacesConfirm.warning`:
  - หัวข้อ: "เปลี่ยนที่รับแจ้งสถานะมาใช้ Deep?"
  - เนื้อหา: "{ชนิดที่เลือก} จะส่งมาที่ Deep แทน {host} ระบบเดิมจะหยุดได้รับข้อมูลชนิดนี้จาก Flash ระบบจะบันทึกชื่อคุณและเวลาที่เปลี่ยน"
  - ปุ่ม: ยืนยัน "เปลี่ยนมาใช้ Deep" / ยกเลิก "คงเดิม"
- เมื่อทับสำเร็จ ชนิดนั้นกลายเป็น "ส่งมาที่ Deep" และบล็อกตัวเลือกหายเมื่อไม่เหลือชนิด EXTERNAL
- สถานะรวม `REGISTERED` (ทุกชนิดเป็นของ Deep): แสดงบรรทัดเดียว `info` "ตั้งรับแจ้งสถานะแล้ว Flash ส่งสถานะ เส้นทาง น้ำหนัก ราคา และข้อมูลคนขับมาที่ Deep ทันที" ไม่แสดงรายชนิด (ไม่มีอะไรให้ตัดสินใจ)
- สถานะรวม `NOT_SET`/`FAILED`: `warning` "ยังไม่ได้ตั้งรับแจ้งสถานะ ระบบจะเช็คเองทุก 15 นาที" + ปุ่ม `ลองตั้งใหม่` (ขอบ) → `POST /webhook/sync` ไม่ส่ง `overrideKinds` ระหว่างรอ: สปินเนอร์
- ผู้ที่ไม่ใช่เจ้าของ: เห็นสถานะ/รายชนิดแต่ไม่มีตัวเลือกและปุ่ม ใต้ข้อมูลมีบรรทัด `lock` "เจ้าของร้านเป็นผู้ตั้งค่านี้"
- โหลด: โครงเทา 3 แถว (`animate-pulse`) · ข้อผิดพลาดเครือข่าย: `warning` "อ่านสถานะการรับแจ้งจาก Flash ไม่ได้ตอนนี้" + `ลองใหม่`

### 3.8 โมดัล B: "ตั้งค่าการจัดส่ง Flash" (`size="2xl"`, 3 แท็บ ตามพี่น้อง)

แท็บ (นับแท็บเท่า iShip เพื่อให้จำง่าย): ที่อยู่ผู้ส่ง `map-pin` · ค่าตั้งต้นพัสดุ `package` · โหมดและใบปะหน้า `settings-automation` (โครงแท็บ ARIA + ลูกศรซ้ายขวา + จุดแดงเมื่อมี error ตามเดิม, ทุกแท็บ mount ค้างด้วย `hidden`)

แท็บ 1 "ที่อยู่ผู้ส่ง"
- ถ้า `senderComplete=false`: `NOTICE_BOX.warning` "กรอกที่อยู่ผู้ส่งให้ครบก่อน จึงจะเปิดพัสดุและเรียกรถได้"
- ปุ่ม `ใช้ที่อยู่ที่ตั้งไว้กับ iShip` (ขอบ, ไอคอน `copy`) **แสดงเฉพาะเมื่อร้านเชื่อม iShip และที่อยู่ผู้ส่งของ iShip ครบ** ไม่มีเงื่อนไข = ไม่วาด
  - ช่องที่กรอกไว้แล้วมีค่า: `pacesConfirm.question` "แทนที่ที่อยู่ผู้ส่งที่กรอกไว้?" ยืนยัน "แทนที่" ยกเลิก "เก็บของเดิม"
  - สำเร็จ: เติม 7 ช่องแล้ว `pacesToast.success('คัดลอกที่อยู่ผู้ส่งจาก iShip แล้ว ตรวจแล้วกดบันทึก')` (ยังไม่บันทึกจนกว่าจะกดบันทึก)
- ช่อง: ชื่อผู้ส่ง, เบอร์โทรผู้ส่ง, ที่อยู่ (บ้านเลขที่/ถนน), ตัวเลือกตำบล/อำเภอ/จังหวัด/รหัสไปรษณีย์ผ่าน `AddressSearchSheet` ตัวเดียวกับ iShip (เลือกครั้งเดียวเติม 4 ค่า ลดความเสี่ยงสลับตำบล/อำเภอ BR-FLASH ตำบล→DistrictName อำเภอ→CityName)

แท็บ 2 "ค่าตั้งต้นพัสดุ"
- ประเภทสินค้า: `form-select` (ชุด 0–11, 99 ตาม API) ที่มา `InputTextfieldType.tsx` (native select เพราะผูกค่ากับฟอร์ม HR6 ข้อ ก)
- น้ำหนัก (กก.), กว้าง/ยาว/สูง (ซม.) ป้ายกำกับ "(ไม่บังคับ)" สำหรับขนาด ข้อความช่วย "Flash ไม่บังคับขนาดกล่อง"
- หมายเหตุถึงคนส่งของ (≤200)
- กล่องข้อมูล `info`: "ขนาดและน้ำหนักที่กรอกเป็นค่าที่ร้านแจ้ง Flash อาจชั่งจริงแล้วคิดค่าส่งต่างจากนี้"
- กล่องข้อมูล `info`: "ยอดเก็บเงินปลายทางกำหนดจากวิธีชำระเงินของแต่ละคำสั่งซื้อตอนสร้างพัสดุ ไม่ต้องตั้งเป็นค่าเริ่มต้นที่นี่"
- ตัวเลือกเสริมแบบ checkbox: "ใช้บริการส่งตรงเวลา", "ประกันกล่องพัสดุ", "ประกันสินค้า" (เปิดแล้วต้องกรอก "มูลค่าสินค้าที่เอาประกัน (บาท)" ตรวจเหมือน iShip: "เปิดประกันสินค้าแล้วต้องระบุมูลค่าสินค้าที่ต้องการเอาประกัน")
- ไม่มี: เลือกขนส่ง, เลือกกล่อง, สวิตช์ COD เริ่มต้น (ตามสัญญา API)

แท็บ 3 "โหมดและใบปะหน้า"
- หัวย่อย "ขนาดใบปะหน้า": radio-card 2 ใบ
  - "100×180 มม. (ค่าเริ่มต้น)" คำอธิบาย "ขนาดมาตรฐานของ Flash เหมาะกับเครื่องพิมพ์ใบปะหน้าทั่วไป"
  - "100×75 มม." คำอธิบาย "ใบเล็ก สำหรับเครื่องพิมพ์สติกเกอร์ขนาดเล็ก"
- หัวย่อย "โหมดการสร้างพัสดุ": radio-card 3 ใบ (ไอคอน/ลำดับเท่า iShip)
  - "ปิดไว้ก่อน" · "ถามทุกครั้ง" · "สร้างพัสดุอัตโนมัติ" คำอธิบาย AUTO: "เปิดพัสดุที่ Flash ให้ทันทีที่บันทึกคำสั่งซื้อที่เข้าเงื่อนไข โดยไม่ถาม มีค่าใช้จ่ายจริงทุกครั้ง"
- ถ้าร้านเชื่อม iShip ด้วย: `NOTICE_BOX.info` "ร้านที่เชื่อมทั้ง iShip และ Flash จะถูกถามให้เลือกผู้ให้บริการทุกครั้ง แม้ตั้งเป็นอัตโนมัติ" (เป็นความจริงตาม `decideAfterCreate`)

ปุ่มท้ายโมดัล: `ปิด` (ขอบ) + `บันทึกการตั้งค่า` (ทึบ, `device-floppy`) · ปิดเมื่อ dirty → `pacesConfirm.warning` "ปิดโดยไม่บันทึก?" (ข้อความเดิมของ iShip)
การตรวจ: ข้อความและกฎเหมือน `validateSettings` ของ iShip ยกเว้นไม่มีกฎ box/courier; error ไม่ผ่านพาไปแท็บแรกที่ผิดแล้วโฟกัสช่องนั้น

ผู้ที่ไม่ใช่เจ้าของ: โมดัลชื่อ "ค่าที่ตั้งไว้ของ Flash" แสดงเป็นแถวอ่านค่า (โครง `StatRow` เส้นประของ `ShipmentStatusView`) ทุกแท็บ + `NOTICE_BOX.secondary` ไอคอน `lock` "เฉพาะเจ้าของร้านแก้ไขได้" ไม่มีปุ่มบันทึก (มีแค่ `ปิด`)

- หัวสถานะ: บรรทัดรองใช้ `shipmentSourceLabel(...)` แทน `courierName`
- **ป้าย COD ถาวร**: `NOTICE_BOX.info` + ไอคอน `cash` ข้อความ **ตรงตัวตาม BRD:** "Flash ไม่แจ้งการโอนเงิน COD — ตรวจยอดกับ Flash แล้วกดยืนยันรับเงินเอง" แสดงเมื่อ `isCodManualConfirmNotice(provider, codAmount)` ทุกสถานะ (รวมส่งถึงแล้ว) ไม่ปิดได้ ใช้ `info` ไม่ใช่เขียว/แดง เพราะเป็นข้อเท็จจริง ไม่ใช่ความล้มเหลว · ปุ่ม "ได้รับเงินปลายทางแล้ว" มีอยู่ในหน้าคำสั่งซื้อแล้ว (ข้อความของปุ่มปรากฏใน `BulkActionBar`) ป้ายจึงไม่ชี้ไปที่ปุ่มที่ไม่มี
- **ข้อความสาเหตุที่ค้าง (markerCategory)** อยู่ในกล่องเตือนเดียวกับ `progress.notice` (ไม่สร้างกล่องที่สอง): บรรทัดแรกคือข้อความเตือนเดิม บรรทัดสอง "Flash บันทึกว่า: …" + คำแนะนำสั้น:

| รหัส | ข้อความ | ขั้นต่อไปที่ทำได้จริงในหน้า |
|---|---|---|
| 14 | "ผู้รับขอเลื่อนวันรับ" | "รอ Flash นัดส่งใหม่" |

| 17 | "ผู้รับไม่รับพัสดุ" | "ติดต่อผู้รับเพื่อยืนยันว่าจะรับหรือไม่" |

  น้ำเสียงเป็นกลางต่อบุคคลที่สาม ("Flash บันทึกว่า…") ไม่กล่าวหาผู้รับ/ผู้ซื้อ
- แถวในส่วน "รายละเอียดพัสดุ": เพิ่ม "น้ำหนักที่ Flash ชั่งได้" เมื่อมีค่า (ไม่ใช่ข้อมูลเงิน จึงไม่ติดสิทธิ์การเงิน) · **ไม่เพิ่มแถวค่าส่ง/ค่าธรรมเนียม COD** ในหน้าสถานะ (เงินอยู่หน้ากำไรตามสิทธิ์ 00071) หาก dev พบจุดแสดงค่าส่งใหม่ ต้องติดป้าย "ประมาณการ" ตาม BR-FLASH-53
- **ใบปะหน้า**: ปุ่ม `printer` เปลี่ยนจาก `<a href>` เป็นปุ่มที่ดึง PDF เองแล้ว `window.open(blobUrl)` (วิธีเดียวกับ `BulkActionBar.handlePrintLabels`) เพราะเส้นทาง Flash มีผลลัพธ์ที่เป็น JSON error จริง (409 key ใช้ไม่ได้, ไม่ใช่ PDF) ถ้าเป็น `<a target=_blank>` ผู้ขายจะเจอแท็บ JSON · ข้อผิดพลาด → `pacesToast.error(ข้อความไทย)` · `aria-label` "พิมพ์ใบปะหน้า 100×180 มม." (ตามขนาดที่ตั้ง) · แถว "พิมพ์ใบปะหน้าแล้ว" เดิมใช้ต่อ
- เมนู `⋯` (`dropdown-item min-h-11`):
  - ใบปกติ: `ยกเลิกพัสดุ` → `pacesConfirm.danger` "ยกเลิกพัสดุที่ Flash?" เนื้อหา "ยกเลิกได้เฉพาะตอนที่ Flash ยังไม่รับของ ยกเลิกแล้วเปิดพัสดุใบใหม่สำหรับคำสั่งซื้อนี้ได้ ระบบจะบันทึกชื่อคุณและเวลา" ยืนยัน "ยกเลิกพัสดุ" ยกเลิก "ไม่ยกเลิก" · ถ้า Flash ตอบรับของแล้ว (1015): `pacesAlert` ไอคอน info หัวข้อ "Flash รับพัสดุไปแล้ว" เนื้อหา "ยกเลิกจาก Deep ไม่ได้ ต้องติดต่อ Flash โดยตรง สถานะพัสดุใน Deep ไม่เปลี่ยน" (ผลที่ต้องรับทราบ จึงเป็น Swal ไม่ใช่ toast)
  - ใบผูก (LINKED): `ยกเลิกการผูก` → `pacesConfirm.question` "พัสดุจริงที่ Flash จะไม่ถูกยกเลิก คุณเลือกผูกใบอื่นหรือสร้างใหม่ได้ทันที" (ข้อความเดิมของ iShip ผันผู้ให้บริการ)
- ใบ LINKED: กล่องข้อมูลใต้หัว `info` "ผูกจาก Flash พัสดุใบนี้ถูกสร้างไว้ก่อนแล้ว ไม่ได้เปิดจากคำสั่งซื้อนี้" ราคาประมาณการว่าง = **ไม่แสดง ฿0**
- ข้อความ iShip ที่ยังเขียนตายตัวในไฟล์นี้ ("เครดิต iShip ไม่พอ", "ผูกจาก iShip") ต้องผันตาม `provider`; กิ่ง `balance` ไม่ใช้กับ Flash (Deep ไม่รู้ยอดเครดิต Flash)
- Hook-order trap: กิ่ง `NEEDS_REVIEW` และ `FLASH` ใหม่ต้องวาง **ใต้ hook ทุกตัว** (เทส `shipment-status-view-hooks.test.ts`)

`ShippingCard` (สรุปบนหน้า): ป้ายหัวการ์ดแทน "เปิดพัสดุผ่าน iShip" ด้วย "เปิดพัสดุผ่าน Flash (บัญชีของร้านเอง)" + โลโก้ Flash · ปุ่มรีเฟรช/คำอธิบาย "ตรวจกับ Flash ล่าสุด" ผันตามผู้ให้บริการ · ดึงข้อมูลที่ `shipmentApiBase(provider)` ผ่าน `useIShipUrl()` · ป้าย COD ถาวรแสดงในการ์ดสรุปด้วย (เมื่อเข้าเงื่อนไข) · NEEDS_REVIEW ในการ์ดสรุป: แสดงเฉพาะป้าย `warning` "ต้องตรวจสอบพัสดุ" + ลิงก์ "จัดการพัสดุ ›" เปิดโมดัล (ไม่ดึงไทม์ไลน์ เพราะยังไม่มี pno)

### 4.6 ล้มเหลว (FAILED) ของ Flash

ใช้กิ่ง FAILED เดิมของ `ShipmentStatusView` โดยเลือกตัวจัดหมวดตามผู้ให้บริการ (`retryUxFor(provider, code)`):

| fix-data ผู้ส่ง | 1004, 1022 | "Flash ไม่รับที่อยู่ผู้ส่ง ตรวจตำบล อำเภอ จังหวัด และรหัสไปรษณีย์ในตั้งค่า" | `ตั้งที่อยู่ผู้ส่ง` | `ลองใหม่` (ghost) |
| fix-data ผู้รับ | 1005, 1021 | "Flash ไม่รับที่อยู่ผู้รับ ตรวจตำบล อำเภอ จังหวัด และรหัสไปรษณีย์" | `แก้ที่อยู่ผู้รับ` (ป้ายต่างจาก iShip: ไม่มีขนส่งให้แก้) | `ลองใหม่` (ghost) |

- กรณี 1008 ห้ามมีปุ่ม "เปิดแบบไม่เก็บเงิน" (BR-FLASH-27)
- ปุ่ม `ลองใหม่` เปลี่ยนป้ายเป็น "กำลังลองใหม่…" ระหว่างทำงาน (เหมือนเดิม) · สถานะ PENDING ค้าง: โครงเทา + "กำลังสร้างพัสดุกับ Flash…"

## 9. User flow (กดอะไร เห็นอะไร)

1. ตั้งค่า > "เชื่อมต่อ" > อ่านคำอธิบายว่าต้องขอ mchId+key จาก Flash > วาง > "ทดสอบและบันทึก" > สำเร็จ: toast + การ์ดเป็น "เชื่อมต่อแล้ว" / ถ้ามีชนิด webhook ไปที่อื่น: โมดัลค้างที่ส่วนการรับแจ้งสถานะ ให้เลือก "คงเดิม" (ค่าเริ่มต้น) หรือ "เปลี่ยนมาใช้ Deep" (Swal เตือน)
2. ตั้งค่า > "ตั้งค่า" > (ปุ่ม "ใช้ที่อยู่ที่ตั้งไว้กับ iShip") > กรอกผู้ส่ง/ค่าตั้งต้น/ขนาดใบปะหน้า/โหมด > "บันทึกการตั้งค่า"
3. สร้างคำสั่งซื้อ: ร้านสองเจ้า > Swal "เปิดพัสดุกับใคร" > เลือก > สร้าง · ร้าน Flash เดียว ASK > Swal พร้อมสรุปและราคาประมาณ
4. หน้าคำสั่งซื้อ > แจ้ง/จัดการพัสดุ > (สองเจ้า: เลือกผู้ให้บริการ ก่อน) > ฟอร์ม Flash > "สร้างพัสดุที่ Flash" > มุมมองสถานะ (เลข, ใบปะหน้า, ยกเลิก, ไทม์ไลน์)
5. ล้มเหลว: ข้อความบอกฝั่ง (ผู้ส่ง/ผู้รับ) + ปุ่มที่แก้ได้จริง · 1003: แผงตรวจสอบ ผูก pno หรือยืนยันเปิดใหม่
6. ส่งถึง: ป้าย COD ยังอยู่ · ส่วน "หลักฐานจากขนส่ง" มีหลักฐานการส่ง (ร้านเท่านั้น)
7. รายการคำสั่งซื้อ > เลือกหลายแถว > "พิมพ์ใบปะหน้า" > Swal รายการที่ถูกข้ามพร้อมลิงก์ทีละใบ

## 10. Content outline (ข้อความหลัก, ไทยทั้งหมด)

อยู่ในแต่ละหัวข้อข้างต้น ข้อความที่ต้องตรงตัว (BRD/API/PRD): 
- "Flash ไม่แจ้งการโอนเงิน COD — ตรวจยอดกับ Flash แล้วกดยืนยันรับเงินเอง"

- "ใบปะหน้า Flash พิมพ์ได้ทีละใบ"

- "ขนส่งรับของไปแล้ว ยกเลิกจาก Deep ไม่ได้ ต้องติดต่อ Flash" (ใช้ข้อความ API ใน Swal 1015)
- "คงเดิม (เช็คอัตโนมัติทุก 15 นาที)" · "เปลี่ยนมาใช้ Deep" · "ใช้ที่อยู่ที่ตั้งไว้กับ iShip" · "ประมาณการ" · "ราคาสัญญา" · "ราคามาตรฐาน"

## 12. Impeccable compliance

- **Mode: Operate** เหตุผล: คอนโซลผู้ขายที่ผู้ใช้อยู่ในงาน (ตั้งค่า, สร้างพัสดุ, ตัดสินใจเรื่องเงิน) ความคุ้นเคยและการสแกนง่ายสำคัญกว่าการแสดงออก แบรนด์อยู่ที่ความแม่นยำของข้อความและสีที่มีความหมาย (DESIGN.md: seller/admin override เป็น `product`)
- **The One Voice Rule:** accent น้ำเงิน `bg-primary` ใช้ที่: ปุ่มทึบ 1 ใบต่อโมดัล ("ทดสอบและบันทึก", "บันทึกการตั้งค่า", "เรียกรถ", "สร้างพัสดุที่ Flash", "ยืนยันผูกเลขนี้") + tint ของปุ่มรองและแท็บที่เลือก ไม่ใช้ตกแต่ง ไม่มี `#7367F0`
- **พระเอกของแต่ละหน้า:** การ์ดตั้งค่า = ป้ายสถานะ + บรรทัดที่ต้องทำ · ฟอร์มสร้างพัสดุ = ปุ่มสร้าง + แถวราคา · NEEDS_REVIEW = ทางเลือก ① ผูกเลข (ปุ่มทึบ) · รายการ = รายชื่อที่ถูกข้ามใน Swal
- **Verified-Means-Green:** เขียวเฉพาะ "เชื่อมต่อแล้ว (ACTIVE)" และสถานะส่งถึงที่มาจากตารางสถานะกลาง ส่วน "ส่งคำขอเรียกรถแล้ว", "ตั้งรับแจ้งสถานะแล้ว", "หลักฐานการส่ง (บันทึกไว้)", ราคาประมาณ, NEEDS_REVIEW ใช้ info/warning/secondary
- **Sentence-case / ไทย:** ไม่มี ALL CAPS กับข้อความไทย ศัพท์อังกฤษที่คงไว้เป็นชื่อของ Flash (mchId, Secret Key, pno) พร้อมคำไทยกำกับ
- **เงาผสมหมึก:** ใช้ `shadow`/`shadow-lg` ของ Paces เท่านั้น ไม่มีเงาใหม่
- **Anti-slop:** ไม่มี gradient/hero-metric/eyebrow/การ์ดซ้อนการ์ด (ตัวเลือกใน NEEDS_REVIEW เป็นแถวมีกรอบ 1px ไม่ใช่การ์ด ใช้ `.card` ครั้งเดียวที่ระดับหน้า) ไม่มีขอบสีหนากว่า 1px
- **น้ำเสียงข้อความ:** บอกทางออก ไม่ใช้รูปราชการ เป็นกลางต่อผู้รับ/ผู้ซื้อ ("Flash บันทึกว่า…") ไม่ไฮป์
- **จุดที่ theme ขัดกับ Impeccable และการตัดสิน:**
  1. ต้นแบบ `statusBadge` ของ iShip ใช้ `text-warning`/`text-success` บนพื้น `/15` (คอนทราสต์ตก) ตัดสิน: Flash ใช้ `-ink` ผ่าน `TONE_BADGE` (Impeccable ชนะเรื่องสี) ไม่แตะแถว iShip
  2. ต้นแบบรูปเสียของ `ReviewImageGallery` ใช้ `text-default-300` ไม่ผ่าน ตัดสิน: ใช้ `text-default-700` + ข้อความ
  3. `IShipModalShell` เป็นโมดัลฟอร์ม ไม่ใช่ Swal: ถือเป็นข้อยกเว้นของ HR8 เพราะไม่ใช่กล่องที่ต้องตอบ (มี precedent) และ operate.md เตือน "modal เป็นความคิดแรก" ตรวจแล้วว่าทุกโมดัลเป็นงานหลายช่องที่ต้องโฟกัส ส่วนการยืนยันทั้งหมดเป็น Swal
  4. ปุ่มพิมพ์ใบปะหน้าของ Flash เป็น fetch-blob แทน `<a>` ต่างจากพี่น้อง iShip โดยจงใจ เพราะเส้นทาง Flash มีผล JSON error จริง
  5. ไม่มีค่าดิบ/arbitrary: ทุกขนาดใช้ `text-2xs..text-lg`, `size-*`, `gap-*`, `rounded-lg`, `bg-{semantic}/15` ไม่มี hex, ไม่มี font อื่น (Anuphan เท่านั้น ไม่ใช้ `font-mono` กับเลขพัสดุ ใช้ `tabular-nums`)
- **จุดที่ Controller ควรเพ่งตอน critique:** (ก) โมดัล A ที่ซ้อนหลายบล็อก (สถานะ, webhook, ฟอร์ม) ที่ 375px ต้องไม่ยาวจนปุ่มหลักหลุดสายตา (ข) ชั้นผู้ให้บริการสองชั้นที่ 375px (ค) รายการ Swal ที่ถูกข้ามเมื่อยาว (ง) คอนทราสต์ป้าย `secondary` บน `bg-default-100`

## 13. Design decisions + rationale

1. **การ์ดแยกจาก iShip (ใบที่สอง)** ตาม PRD "แยกการ์ด" และเพื่อให้ร้านที่ไม่มี Flash ไม่เห็นอะไรเปลี่ยน
2. **Webhook อยู่ในโมดัลเชื่อมต่อ ไม่ใช่การ์ดหลัก** เพราะเป็นเรื่องที่ตัดสินครั้งเดียวหลังเชื่อม แต่ถ้ามีเรื่องค้าง (ไม่ครบ/ระบบอื่นรับอยู่) จะโผล่เป็นบรรทัดเตือนบนการ์ด จึงไม่ถูกฝังจนลืม
3. **"คงเดิม" เป็นค่าเริ่มต้นและไม่มีปุ่มบันทึก** เพื่อให้ท่าเริ่มต้นปลอดภัยจริง (ไม่ทับ) และไม่มีการคลิกที่ไม่ทำอะไร
4. **ไม่ preselect ผู้ให้บริการเมื่อมีสองเจ้า** ตาม DD-5/BR-FLASH-21 ยอมรับว่าเพิ่มหนึ่งคลิก แลกกับการไม่ให้ระบบเลือกแทนร้าน
5. **แถวราคา Flash แยกบล็อก ไม่ร่วมอันดับ "ถูกที่สุด"** เพราะเป็นค่าประมาณคนละบิล
6. **ลำดับใน NEEDS_REVIEW: ผูกก่อน เปิดใหม่ทีหลัง และเปิดใหม่ไม่ใช่ปุ่มทึบ** ลดโอกาสเสียเงินซ้ำ
7. **Swal เลือกผู้ให้บริการไม่ใส่ราคา iShip** เลี่ยงการหน่วงขั้นหลังสร้างคำสั่งซื้อ ราคาอยู่ที่แผงเทียบราคา
8. **ไม่เพิ่มแถวเงินในหน้าสถานะพัสดุ** เพื่อไม่ชนกฎสิทธิ์การเงินและ HR16 (ตัวเลขต้นทุนนิยามเดียวที่หน้ากำไร)

## 14. Open questions (สูงสุด 5)

1. **คำขอเรียกรถล่าสุดหลังรีโหลด:** API ไม่มี GET รายการ/สถานะคำขอรถ และ `FlashConnectionView` ไม่มี `lastPickup` ทำให้ปุ่ม "ยกเลิกคำขอรถ" และข้อมูลคนขับมีอยู่เฉพาะในเซสชันโมดัลที่เพิ่งเรียก (หลังรีโหลดหาย แม้ webhook คนขับจะอัปเดตข้อมูลแล้ว) ต้องการเพิ่มฟิลด์ `lastPickup` ใน view หรือยอมรับข้อจำกัดนี้ใน v1
2. **ความหมายของสถานะ webhook `OTHER_DEEP` และ `UNKNOWN`:** สเปกนี้ตั้งป้ายว่า "ส่งมาที่ Deep ด้วยลิงก์อื่น (ทับได้)" และ "อ่านค่าที่ตั้งไว้ไม่ได้ (ทับไม่ได้)" ขอให้ SA ยืนยันว่า `OTHER_DEEP` ควรให้ทับได้โดยไม่ต้องเตือนระบบเดิมหรือไม่ เพราะไม่มีระบบภายนอกถูกกระทบ
3. **การยืนยัน ASK ของ Flash มีสรุป (ผู้รับ ที่อยู่ น้ำหนัก COD ราคาประมาณ) ตาม FR-FLASH-020 แต่ Swal ของ iShip ไม่มี** ตัดสินใจให้ Flash มีสรุปโดยไม่แตะ iShip (ตามเงื่อนไขเจ้าเดียวพฤติกรรมเดิม) ขอให้ยืนยันว่ายอมรับความต่างนี้ หรือจะยกระดับ iShip ในรอบอื่น
4. **ปุ่ม "ได้รับเงินปลายทางแล้ว" ของใบ Flash COD หลังส่งถึง:** ป้าย COD ถาวรชี้ให้ "กดยืนยันรับเงินเอง" ขอให้ dev/QA ยืนยันว่าปุ่มนี้ปรากฏในหน้าคำสั่งซื้อสถานะ SHIPPED ที่ Flash แจ้งส่งถึง (สเปกนี้อนุมานจากข้อความใน `BulkActionBar` และ `NextAction` ไม่ได้เปิดดูโค้ดปุ่มโดยตรง)
5. **แหล่งข้อความสาเหตุที่ค้าง (markerCategory) บน `ShipmentViewJson`:** ยังไม่มีฟิลด์ที่ชัดเจนใน API (มีเฉพาะ `lastErrorMessage` และ `carrierStatusText`) ต้องมีฟิลด์ เช่น `markerReason` (ข้อความไทยจาก `describeMarker`) ใน view ที่ T7a/T4 ส่งให้ UI

## 15. Anti-slop self-check

1. **เฉพาะ Deep หรือไม่:** ใช่ ทุกส่วนผูกกับศัพท์/กฎของโปรเจกต์นี้ (HR16 สองป้าย Flash, DD-5 ห้ามเลือกเจ้าที่ถูกกว่า, 1003 ไม่เปิดใบใหม่เงียบ, ห้ามทับ webhook ของร้าน, ป้าย COD ตามกฎ BR-FLASH-49, `ShipmentRail`/`tone.ts` เดิม) เอาไปใช้กับสินค้าอื่นไม่ได้โดยไม่แก้
2. **พระเอก 1 อย่างต่อจอ:** ระบุไว้ในหัวข้อ 12 ทุกจอ และปุ่มทึบมีใบเดียวต่อโมดัล (ตรวจแล้ว: โมดัล A ฟอร์ม, B บันทึก, C เรียกรถ, ฟอร์มสร้าง, ผูกเลข)
3. **ตัดของซ้ำ/คงที่:** ไม่มีการ์ดตัวเลขหรือข้อมูลคงที่ ตัดแถวเงินในหน้าสถานะ (ซ้ำกับหน้ากำไร) ตัดรายการ webhook เมื่อทุกชนิดเป็นของ Deep (เหลือบรรทัดเดียว) ตัดแถวเตือนบนการ์ดเมื่อไม่มีเรื่องต้องทำ ตัดตัวเลือกตัวที่สองของ webhook เมื่อไม่มี EXTERNAL
4. **ครบทุก state:** ตารางหัวข้อ 11 + ข้อความผิดพลาดรายกรณี (3.5, 3.9, 4.6, 4.7) + ตัวเลขสุดโต่ง/ข้อความยาว + โหมดจำลอง
5. **copy บอกสิ่งที่ทำได้จริง:** ปุ่มบอกผลลัพธ์ ("สร้างพัสดุที่ Flash", "เรียกรถ") · ข้อผิดพลาดทุกข้อมีทางออก · กรณี 1008 และ 1010/1011 ไม่ชวนให้กดปุ่มที่ไม่ช่วย (ไม่มีปุ่มทึบ/บอกให้ติดต่อ Flash) · บรรทัด "ปุ่มลองใหม่ถูกปิดไว้" อธิบายว่าทำไมไม่มีปุ่ม · ป้าย COD ชี้ไปที่การกระทำที่มีอยู่แล้ว (ดู Open Q 4)
6. **คำเดียวกันเป็นของเดียวกัน:** หัวข้อ 1 ล็อกศัพท์ 7 คำ ใช้ `shipmentSourceLabel` เป็นแหล่งเดียวของป้ายผู้ให้บริการ
7. **สีสื่อความหมายถูก:** เขียวเฉพาะเชื่อมต่อ ACTIVE/ส่งถึง; ประมาณการ/ตรวจมือ/ตั้งรับแจ้งไม่ครบ = warning/neutral; แดงเฉพาะ FAILED/ข้อผิดพลาดจริง; TOKEN_INVALID เป็น warning (แก้ได้หน้าเดียว); สถานะเดียวกันสีเดียวทั้งการ์ด โมดัล แชท รายการ เพราะใช้ `TONE_BADGE` ตัวเดียว
8. **แตะได้จริงบนมือถือ:** ปุ่มหลักอยู่ footer ติดล่างของ bottom-sheet (โซนนิ้วโป้ง) · ช่องเลือกผู้ให้บริการ `min-h-11` · เมนู `⋯` item `min-h-11` · ลิงก์ในรายการ Swal ต้องมีพื้นที่แตะ ≥44px (`inline-flex min-h-11 items-center`)
9. **จอ 1440 คอลัมน์ว่างไหม:** การ์ดตั้งค่าเต็มความกว้างแต่ละแถวมีข้อความซ้าย ปุ่มขวา; โมดัล `lg:max-w-*` จำกัดความกว้างเอง (ไม่ลากเต็ม 1440); ฟอร์มสร้างพัสดุใช้ 2 คอลัมน์ที่ `@2xl`; ไม่มี 70/30 ที่ฝั่ง 30 เป็นเนื้อหาจริง
