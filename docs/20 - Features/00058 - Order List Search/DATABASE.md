# DATABASE: ค้นหาในหน้ารายการคำสั่งซื้อ

---

## 1. สรุป — ไม่มีการเปลี่ยนแปลงฐานข้อมูลในฟีเจอร์นี้

**ไม่มี migration · ไม่มีตารางใหม่ · ไม่มีคอลัมน์ใหม่ · ไม่มี index ใหม่ · ไม่มี enum ใหม่**

ฟีเจอร์นี้ทำงานบนข้อมูลที่ถูกส่งข้าม RSC boundary ลงมาที่เบราว์เซอร์อยู่แล้วทั้งหมด
การค้นหาเกิดขึ้นบนเครื่องผู้ใช้ ไม่มี query ใหม่วิ่งไปที่ฐานข้อมูลเลยแม้แต่ครั้งเดียว

🛑 **เอกสารนี้มีอยู่เพื่อบันทึกว่า "ตรวจแล้วไม่ต้องแตะฐาน" ไม่ใช่เพราะยังไม่ได้ตรวจ** —
การไม่มีไฟล์นี้กับการมีไฟล์ที่เขียนว่า "ไม่มีการเปลี่ยนแปลง" อ่านต่างกันคนละเรื่องสำหรับ
คนที่มาทำต่อ (Hard Rule 11)

---

## 2. ข้อมูลที่ฟีเจอร์นี้อ่าน (มีอยู่แล้วทั้งหมด)

ทุกฟิลด์มาจาก `getOrdersByShop()` (`src/services/order.service.ts`) ซึ่ง RSC ของหน้า
`/seller/orders` เรียกอยู่แล้วก่อนมีฟีเจอร์นี้

| ฟิลด์ที่ค้นหา | มาจาก | หมายเหตุ |
|---|---|---|
| เลขคำสั่งซื้อ | **derive สด** จาก `Order.publicToken` + `Order.createdAt` ผ่าน `formatOrderNo()` | ไม่ได้อ่านคอลัมน์ `Order.orderNo` — 🛑 คอลัมน์นั้นมี `@@index([orderNo])` อยู่จริงแต่ **ไม่ถูก select ลงมาเลย** ดู §4 |
| รหัสสั้น | `Order.shortCode` (`@unique`) | `null` = ออเดอร์ก่อน backfill |
| ชื่อผู้ซื้อ | `Order.buyerName` / `Order.buyerUsername` | |
| เบอร์โทร | `Order.buyerContact` | ส่งลงมาเป็น `OrderRow.buyerPhone` **ค่าดิบ ไม่ปิดบัง** ตั้งแต่ 2026-06-15 (ก่อนฟีเจอร์นี้) |
| เลขพัสดุ | `OrderShipment.trackingNo` **หรือ** `ShipmentTracking.trackingNo` | รวมเป็นฟิลด์เดียวที่ server โดยให้ iShip ชนะ (`docs/conventions/one-value-many-entry-points.md`) |
| ชื่อสินค้า | `OrderItem.name` | มาผ่าน `include: { items: … }` ที่มีอยู่แล้ว |

## 3. ผลของ D-13 (ถอดมาสก์เบอร์ฝั่งผู้ขาย) ต่อฐานข้อมูล

**ไม่มีเลย** — การปิดบังเป็นการแปลงค่า *ตอนแสดงผล* ทั้งหมด ไม่เคยมีการเก็บค่าที่ปิดบังแล้ว
ลงฐาน ค่าใน `Order.buyerContact` / `Customer.phone` เป็นค่าดิบมาตลอดและไม่ถูกแตะในรอบนี้

⇒ **ไม่ต้อง backfill · ไม่ต้อง migration · ย้อนมติได้โดยไม่กระทบข้อมูล**
(ถ้าวันหนึ่งกลับไปปิดบัง แค่เปลี่ยน `src/lib/seller-contact-display.ts` ที่เดียว)

## 4. สิ่งที่จะต้องแตะฐาน **ถ้า** ย้ายไปค้นฝั่ง server (ยังไม่ทำในรอบนี้)

บันทึกไว้เพื่อให้คนที่มาทำต่อไม่ต้องสำรวจซ้ำ:

- **ไม่มี index ตัวไหนในระบบช่วย `contains` / prefix บน `buyerName` / `buyerContact` /
  `OrderItem.name` เลย** — ทั้งรีโปไม่มี `pg_trgm`, ไม่มี `tsvector`, ไม่มี GIN
  ทุก index บน `Order` เป็น B-tree ธรรมดา
- ที่ปริมาณปัจจุบัน (มากสุด **421 ใบ/ร้าน** — ข้อมูล prod 2026-08-24) seq scan ต่อร้าน
  ยังไม่เจ็บ การเพิ่ม index จึงเป็นการจ่ายก่อนได้ใช้
- `Order.orderNo` มี index อยู่แล้วและตั้งใจให้ค้นได้ตั้งแต่แรก (คอมเมนต์ที่
  `src/lib/order-no.ts` เขียนไว้เอง) — **แต่หน้ารายการไม่เคย wire มาใช้** ถ้าย้ายไป
  ค้นฝั่ง server ตัวนี้คือฟิลด์แรกที่ควรใช้ เพราะได้ index ฟรีอยู่แล้ว
  🛑 ระวัง: `Order.createdAt` = "วันที่ลูกค้าสั่ง" ที่ผู้ขายแก้ได้ (feature 00033) ⇒ เลขคำสั่งซื้อ
  เปลี่ยนตามได้ คอลัมน์ `orderNo` ที่เก็บไว้ต้องถูก recompute ในทรานแซกชันเดียวกับการแก้วันที่
  **ก่อน**จะเชื่อถือมันเป็นแหล่งค้นหา ต้องยืนยันว่าไม่มีแถวไหน drift
- `internalNote` (prod: 38/541 ใบมีค่า) ไม่อยู่ใน `include` ปัจจุบัน — ถ้าจะให้ค้นได้
  ต้องเพิ่มที่ service **และ** ประเมิน PII ใหม่ เพราะเป็นข้อความอิสระที่ร้านพิมพ์เอง
