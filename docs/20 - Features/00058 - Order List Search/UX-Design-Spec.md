### Section breakdown (prose)

**1. `src/lib/order-search.ts` (ไฟล์ใหม่ — pure module, สถาปัตยกรรมก็อปจาก `order-date-filter.ts`)**
ห้าม import prisma/server-only, ห้ามผูกกับ `OrderRow` แบบ hard import ทั้งชนิด — ใช้ structural typing แคบ ๆ (pick เฉพาะฟิลด์ที่ต้องใช้) เพื่อให้ทั้งสองจอเรียกได้โดยไม่ผูก dependency แปลก ๆ

Export ที่ต้องมี:
- `ORDER_SEARCH_MIN_CHARS = 2`
- `matchesText(value, query): boolean` — trim+lowercase substring, ใช้กับ orderNo/buyerName/trackingNo/itemName
- `matchesPhone(phone, query): boolean` — strip ตัวที่ไม่ใช่ตัวเลขออกทั้งสองฝั่งก่อนเทียบ (พิมพ์ "081-234-5678" หรือ "0812345678" หรือแค่ "5678" ต้องเจอเหมือนกัน)
- `isExactIdentifierMatch(order, query): boolean` — เทียบเท่าเต็มค่า (ไม่ใช่ substring) กับ **เฉพาะ 3 ฟิลด์ที่เป็น "ตัวระบุเฉพาะ": เลขคำสั่งซื้อ (`formatOrderNo` เต็มสตริง) / เบอร์โทร (digits เต็ม) / เลขพัสดุ (เต็มสตริง case-insensitive)** — ชื่อผู้ซื้อและชื่อสินค้าไม่ใช่ตัวระบุเฉพาะ ไม่เข้าเกณฑ์นี้แม้พิมพ์ตรงเป๊ะ (เหตุผลใน Design decisions)
- `searchOrders(orders, query): { order; isExactMatch: boolean }[]` — กรอง (AND กับตัวกรองอื่นที่ caller ทำไว้ก่อนแล้ว เพราะฟังก์ชันนี้รับ list ที่กรองมาบางส่วนแล้วเข้ามาได้) + จัดเรียง exact match ขึ้นก่อน (stable partition — ที่เหลือคงลำดับเดิม)

**2. `OrdersList.tsx` (มือถือ) — แก้ 4 จุด**
- ค้นหา: แทนที่ ad-hoc match เดิม (บรรทัด ~427-436) ด้วยเรียก `searchOrders()` เป็นขั้นสุดท้ายของ pipeline `filtered` (หลัง stage/status/type/date เหมือนเดิม — ยังคง AND)
- `search` init จาก `searchParams.get('q') ?? ''`, sync กลับด้วย `window.history.replaceState` (ไม่ใช่ `router.replace`/`push`) ทุกครั้งที่พิมพ์ — เหตุผลเต็มใน Design decisions (กัน RSC refetch ทุกตัวอักษร)
- ช่องพิมพ์: เพิ่มปุ่ม × ล้างค่า (icon `circle-x` — ยืนยันแล้วว่ามีอยู่จริง เพราะ `OrdersTable.tsx` ใช้ชื่อนี้อยู่แล้ว) เฉพาะตอน `search.length>0`, ตำแหน่ง absolute right-3 ในกล่อง relative เดิม
- เพิ่มแถวใหม่ (เงื่อนไข `search.trim().length === 1`) ระหว่างแถว back/search/filter/bell กับแถว chip — ข้อความ "พิมพ์อีก 1 ตัวเพื่อค้นหา" `text-2xs text-default-500`
- empty state (เฉพาะ branch ที่ `search.trim().length >= 2` และผลว่าง — บรรทัด 771-777 เดิม) แทนที่ด้วย `title`+`description`+`action` ใหม่ (ดู Content outline) ผ่าน prop เดิมของ `SellerEmptyState` **ไม่แก้ component**
- `OrderCard` รับ prop ใหม่ `searchQuery?: string` + `isExactSearchMatch?: boolean` ส่งต่อ

**3. `OrderCard.tsx` — แก้เฉพาะจุดที่ query ตรง**
- ห่อการ์ดด้วย `ring-1 ring-primary/30` เพิ่มเข้าไปใน className เดิม (`card border-s-3 ${strip}`) เมื่อ `isExactSearchMatch`
- ชื่อผู้ซื้อ, displayId (order no): ห่อด้วย `<HighlightText>` (compose ใหม่ ดู Theme Source Mapping)
- เบอร์โทร: **การ์ดนี้ไม่เคยแสดงเบอร์เลยในทุกกรณี** (ยืนยันจากไฟล์ — ไม่มีบรรทัดไหน render `buyerPhone`) → ถ้า `matchesPhone(order.buyerPhone, searchQuery)` เป็น true ให้ insert แถวใหม่ (block แรกสุดหลัง header, ก่อน item list) แสดง "🔍 ตรงกับ: เบอร์โทร {highlight}" — นี่คือ **จุดเดียว** ที่ต้องมี meta line บนมือถือ เพราะฟิลด์อื่นทั้งหมดมีที่แสดงอยู่แล้วหรือ auto-expand ได้
- ชื่อสินค้า: ถ้า query ตรงกับ item ที่ไม่ใช่ `items[0]` (ตอนยังไม่ expand) → `useEffect` บังคับ `setExpanded(true)` (ทางเดียว: เปิด ไม่มีทางบังคับปิด — เคารพการกดย่อเองของผู้ใช้)
- เลขพัสดุ: แสดงอยู่แล้วเสมอเมื่อมี `shipment.trackingNo` (ไม่มีทางซ่อน) → highlight ตรงที่เดิม ไม่ต้องมี meta line

**4. `OrdersTable.tsx` (เดสก์ท็อป) — แก้ 5 จุด**
- ลบ `globalFilter`/`onGlobalFilterChange`/`globalFilterFn:'includesString'` ทั้งชุด (ของเดิมเป็น naive substring ทุกคอลัมน์ ไม่ตรงกับ 5-field spec)
- เพิ่ม prop ใหม่ `allOrders: OrderRow[]` (ชุดเต็มไม่กรองอะไรเลย — ส่งมาจาก `OrdersList` คู่กับ `orders={stageFiltered}` เดิม) ใช้เฉพาะคำนวณ "พบ N รายการในทั้งร้าน" ตอน empty state
- `query` state init จาก URL เดียวกับมือถือ (ต้อง sync กันเพราะเป็นหน้าเดียวกันคนละ breakpoint — คนละ component แต่ต้องอ่าน `?q=` เดียวกัน)
- `tableData = useMemo(() => query.trim().length>=2 ? searchOrders(orders, query).map(r=>r.order) : orders, [orders, query])` ป้อนเข้า `useReactTable({data: tableData, ...})` แทน `orders` ตรง ๆ — เก็บ `isExactMatch` แยกเป็น `Map<publicToken, boolean>` (จากผลเดียวกัน) ส่งเข้า cell renderer ของ groupRow
- คอลัมน์ "รายการสินค้า": ถ้า query ตรง item ที่อยู่ใน `rest` (เกิน 2 แรก) → `<details open={...}>` ตั้ง initial state ให้เปิด (⚠️ ระวัง React sync `open` ทุก render จน fight การกดปิดเอง — คำนวณแค่ตอน mount/ตอน query เปลี่ยนจริง ๆ ปล่อยให้ browser คุม toggle ต่อจากนั้น เป็นจุดที่ต้องระวังทางเทคนิค ไม่ใช่ตัดสินใจดีไซน์)
- empty state: `emptyMessage={<SellerEmptyState compact .../>}` (component เดียวกับมือถือ — `emptyMessage` รับ `React.ReactNode` ยืนยันแล้วจาก `DataTable.tsx:22`)

**5. `HighlightText` (component เล็กใหม่ — ไม่ผูกกับ theme file ไหนโดยตรง)**
```
<HighlightText text={value} query={query} exact={isExactMatch} inheritColor={boolean} />
```
- ปกติ: `<mark className="rounded bg-primary/15 px-0.5 font-semibold text-primary-ink">`
- `inheritColor` (ใช้ตอนข้อความแม่เป็นลิงก์สีอยู่แล้ว เช่นเลขคำสั่งซื้อบนตาราง `text-primary`): ตัด `text-primary-ink` ออก เหลือแค่พื้นหลัง ไม่งั้นได้สีน้ำเงิน 2 เฉดปนกันในลิงก์เดียว
- `exact`: เพิ่ม `ring-1 ring-primary/30` — เป็นสัญญาณเดียวที่บอกว่า "ใบนี้ถูกยกขึ้นมาเพราะตรงเป๊ะ"

### User flow
1. พิมพ์ 1 ตัวอักษร → ไม่กรอง, ขึ้นข้อความชั่วคราว "พิมพ์อีก 1 ตัวเพื่อค้นหา"
2. พิมพ์ตัวที่ 2 → เริ่มกรองทันที (client-side, ไม่มี loading overlay) — URL อัปเดตเป็น `?q=...` เงียบ ๆ (ไม่เพิ่ม browser history)
3. เจอผล → ใบที่ตรงเต็มค่าตัวระบุเฉพาะลอยขึ้นบนสุด มี ring จาง ๆ; ทุกใบไฮไลต์คำที่ตรงตรงตำแหน่งจริง; ถ้าตรงในฟิลด์ที่ไม่โชว์ (เบอร์บนมือถือ) มีบรรทัดเล็กอธิบาย; ถ้าตรงในสินค้าที่ยุบไว้ → เปิดอัตโนมัติ
4. ไม่เจอผลเพราะติดตัวกรองอื่น → ขึ้นบรรทัดรอง "พบ N รายการในทั้งร้าน" + ปุ่ม "ดูผลทั้งร้าน (N)" กดแล้วพาไป `/orders?q=...` (ล้างตัวกรองอื่นทั้งหมด คง query ค้นหาไว้)
5. ไม่เจอผลจริง ๆ (N=0) → บรรทัดเดียว ไม่มีปุ่มหลอกให้กด
6. กด × ในช่องค้นหา → กลับสู่รายการเดิมตามตัวกรองอื่นที่ยังค้างอยู่
7. กด "ล้างตัวกรอง" ในโมดัลมือถือ → **ไม่ล้างคำค้นหา**

### Content outline (ภาษาไทย)
- Placeholder มือถือ (เดิม, ไม่แก้): `ค้นหาเลข{vocab.noun} / ชื่อลูกค้า / เบอร์`
- Placeholder เดสก์ท็อป (เดิม `ค้นหา{vocab.noun}...`): เปลี่ยนเป็น `ค้นหาเลข{vocab.noun} / ชื่อลูกค้า / เบอร์ / เลขพัสดุ / สินค้า`
- คำใบ้ 1 ตัวอักษร: `พิมพ์อีก 1 ตัวเพื่อค้นหา`
- aria-label ปุ่มล้าง: `ล้างคำค้นหา`
- meta line มือถือ: `ตรงกับ: เบอร์โทร {เบอร์ดิบ}`
- Empty state title: `ไม่พบ{vocab.noun}ที่ตรงกับ "{query}"` (**สตริงนี้มีอยู่แล้วในโค้ดปัจจุบัน บรรทัด 777 — reuse คำเดิมเป๊ะ**)
- Empty state description (มีตัวกรองอื่นซ้อน + N>0): `ในตัวกรองที่เลือกไว้ · พบ {N} รายการในทั้งร้าน`
- Empty state action label: `ดูผลทั้งร้าน ({N})`
- badge "ตรงเป๊ะ": **ไม่ใช้** — แทนด้วย ring เข้ม (เหตุผล §6)

### Edge states ที่ต้องออกแบบ
- **0 ตัวอักษร:** ไม่เปลี่ยนจากปัจจุบัน
- **1 ตัวอักษร:** ไม่กรอง + คำใบ้ — ไม่ใช่ error
- **loading:** ไม่มี — client-side filter ล้วน
- **error:** ไม่มี (ไม่มี API call)
- **ผลว่างเพราะตัวกรองอื่น (N>0):** title+description+CTA
- **ผลว่างจริง (N=0):** title อย่างเดียว
- **query ยาวผิดปกติ:** substring ปกติ ไม่ crash, ไม่ต้อง cap ความยาว
- **ชื่อสินค้า/ที่อยู่ยาวมากที่มี match ลึก:** meta-line ตัดเป็นหน้าต่าง ~36 ตัวอักษรรอบตำแหน่งที่ตรง ใส่ `…`
- **N หลักล้าน:** ยังไม่มีความเสี่ยงในระบบนี้ (ร้านเล็ก) แต่ระบุ `.toLocaleString('th-TH')` ตามแพตเทิร์นเดิมถ้าต้องการ
- **ค้นหาพร้อม apptDay filter:** N "ทั้งร้าน" คำนวณจาก `orders` เต็ม **ไม่ใช่** `dayScoped` — เบี่ยงจาก convention เดิมของไฟล์นี้โดยตั้งใจ (ดู Design decisions #2)

### Impeccable compliance

- **Mode: Operate** — dashboard/table ของ seller (`(paces)/**`) เกณฑ์คือ scanability/consistency ชนะการแสดงออก ไม่มี hero เชิง marketing; ทุกองค์ประกอบใหม่ต้อง "หายไปในงาน" (PRODUCT.md Product Principle #4)
- **One Voice (≤10% จอ):** ไฮไลต์ใช้ `bg-primary/15` (โปร่ง 15%) ปรากฏเฉพาะช่วง active search (ชั่วคราว ไม่ใช่ของถาวร) — ไม่กระทบงบ
- **Verified-Means-Green:** ไม่แตะเลย — ไฮไลต์ใช้ primary (น้ำเงิน) ไม่ชนความหมาย "ยืนยันแล้ว" ของสถานะออเดอร์ในการ์ด/แถวเดียวกัน (จุดที่ user เตือนไว้ตรง ๆ — ตรวจแล้วไม่ชน)
- **Sentence case:** ข้อความทั้งหมดเป็นประโยคปกติ
- **Ink-tinted shadow:** ไม่เพิ่ม shadow ใหม่ (ring ≠ shadow)
- **anti-slop:** ไม่มี gradient, ไม่มี badge ใหม่ที่ไม่จำเป็น (ตัดสินใจใช้ ring แทน badge ข้อความโดยเจตนา), ไม่ซ้อนการ์ดในการ์ด
- **น้ำเสียง:** empty state บอกทางออกเสมอ ("พบ N รายการในทั้งร้าน" + ปุ่มพาไป) ไม่ใช่แค่บอกว่า "ไม่พบ"
- **จุดที่ใช้ accent สีธีม:** `bg-primary/15` ในไฮไลต์ทุกจุดที่ query ตรง + `ring-primary/30` (เฉพาะ exact match) + ปุ่ม "ดูผลทั้งร้าน" (`btn bg-primary` ตาม `SellerEmptyState` เดิม) — พระเอกของหน้าตอน active search คือ **ใบที่ตรงเป๊ะที่ลอยขึ้นบนสุด**
- **จุดที่ theme ขัดกับ Impeccable:** ไม่มีจุดขัดตรง ๆ — จุดเดียวที่ต้องรายงานคือ "ไม่พบ theme match สำหรับ text-highlight" (HR1) ซึ่งแก้ด้วยการ compose primitive เดิม

### Design decisions + rationale

1. **`window.history.replaceState` แทน `router.replace`/`push` สำหรับ sync `?q=`** — เลี่ยง Server Component re-render/refetch ทุกตัวอักษร เพราะข้อมูล order โหลดมาแล้วทั้งหมด ไม่ต้องขอใหม่ — ขยายหลักการเดิมของโค้ด (แยกช่องค้นหาออกจาก `busy.run()`/transition อยู่แล้ว) ไปอีกชั้น
2. **"ทั้งร้าน" = `orders` เต็มดิบ ไม่ใช่ `dayScoped`** — เบี่ยงจาก convention เดิมของไฟล์นี้โดยตั้งใจ เพราะงานของ search คือ "หาออเดอร์ใบนี้ให้เจอไม่ว่าจะอยู่กองไหน" ไม่ใช่ "อธิบายประชากรของกองนี้" — ต้องแจ้ง Controller ให้ชัดว่าเป็นข้อยกเว้นที่ตั้งใจ
3. **ไม่มี chip/badge แสดง query ที่ active** — ช่องค้นหาเองมองเห็นได้ตลอดเวลาอยู่แล้ว (ต่างจาก apptDay pill ที่ต้องมีสัญญาณเพราะซ่อนในโมดัล) — เพิ่ม chip จะพูดซ้ำสิ่งที่เห็นอยู่แล้ว
4. **"ล้างตัวกรอง" ในโมดัลมือถือไม่ล้างคำค้นหา** — สอดคล้องกับหลักการที่มีอยู่แล้วในคอมเมนต์ของโค้ดปัจจุบัน ("ล้างเฉพาะสิ่งที่โมดัลนี้คุม") ช่องค้นหาไม่ได้อยู่ในโมดัลเลย
5. **exact match float-to-top เฉพาะเมื่อไม่มีการเรียงคอลัมน์ด้วยมือ (เดสก์ท็อป)** — ไม่ขัดกับสิ่งที่ผู้ขายเพิ่งสั่งเอง (ยัง highlight/ring ปกติ แค่ไม่ลอยขึ้นบนสุด)
6. **สัญญาณ "ตรงเป๊ะ" ใช้ ring เข้มขึ้น ไม่ใช่ badge ข้อความใหม่** — ไฮไลต์ที่ตรงเป๊ะอยู่แล้วเป็นหลักฐานในตัวเอง, หน้านี้มีเสียง UI เยอะอยู่แล้ว (5 ตัวกรอง+ชิป+เช็กลิสต์สถานะ), แต่ยังต้อง "มีสัญญาณ" เพราะการเรียงลำดับที่เปลี่ยนไปเงียบ ๆ เสี่ยงให้ผู้ใช้คิดว่าแอปมีบั๊ก — ring คือจุดกึ่งกลาง
7. **field label "รายการ" ไม่ใช้ "ใบ"** — memory `feedback_vocab_substitution_needs_sentence_sets` เตือนตรง ๆ ว่าลักษณนาม "ใบ" ใช้กับ nominalized action (SERVICE_QUEUE noun="การเข้ารับบริการ") ไม่ได้ตามธรรมชาติ → เลี่ยงด้วยลักษณนามกลาง "รายการ" ที่ใช้ได้ทุก vertical โดยไม่ต้องแยกชุดประโยค
8. **description "ในตัวกรองที่เลือกไว้" เป็นวลี generic ไม่เอ่ยชื่อตัวกรองที่ active จริง** — เลี่ยงการประกอบประโยคอัตโนมัติแบบ `"ในสถานะ{label}"`/`"ใน{dateLabel}"` เพราะแต่ละแกนมีบทบาททางไวยากรณ์ต่างกัน (ความเสี่ยงเดียวกับข้อ 7 ที่ detector มองไม่เห็น จับได้เฉพาะ critique) — วลี generic ปลอดภัย 100%

### Open questions (ให้ Controller/developer)
1. **`impeccable/reference/*` ไม่มีอยู่จริงในเครื่อง agent นี้** — spec นี้อิงหลักการจาก CLAUDE.md/DESIGN.md ล้วน ไม่ได้อ่าน `operate.md`/`shape.md`/`craft-floor.md` ตัวจริง ถ้ามีรายละเอียดขัดกับ spec นี้ ต้องเทียบซ้ำหลัง build
2. `<details open>` auto-open ตอน match กับ items ที่ซ่อนบนตาราง — ความเสี่ยงทางเทคนิค (React sync attribute ทุก render จน fight การกดปิดของผู้ใช้) ส่งต่อให้ developer ตัดสินใจวิธี implement
3. ยืนยันกับ Controller ว่า "ทั้งร้าน" ควรนิยามกว้างสุด (`orders` เต็ม) ตามที่เลือก หรือควรแคบลงตาม apptDay เหมือน `stageCounts` เดิม (Design decision #2)

### Anti-slop self-check
1. **เฉพาะกับ Deep ตรงไหน:** field label/ข้อความผูกกับโดเมนออเดอร์ของ Deep จริง (เลข `DP{ปี}{เดือน}{code}`, `vocab.noun` ผันตาม vertical) — เอาไปแปะสินค้าอื่นตรง ๆ ไม่ได้
2. **1 อย่างเด่นที่สุด:** ใบที่ตรงเป๊ะคือจุดเด่นเดียวตอน active search — ที่เหลือเบากว่าเสมอ
3. **ตัดของซ้ำ:** ไม่เพิ่ม chip query (ซ้ำกับช่องค้นหา — §3), ไม่เพิ่ม badge "ตรงเป๊ะ" (ซ้ำกับไฮไลต์ — §6)

5. **copy บอกสิ่งที่ทำได้จริง:** ปุ่ม "ดูผลทั้งร้าน (N)" มี N จริงกำกับเสมอ ไม่โผล่ตอน N=0
6. **คำเดียวกันหมายถึงของเดียวกัน:** field label "เบอร์โทร" เดียวกับตารางเดสก์ท็อป; "ตรงกับ" ใช้ความหมายเดียวทั้งระบบ ไม่ชน HR16
7. **สีถูกความหมาย:** ตรวจแล้วในหัวข้อ Impeccable compliance
8. **แตะได้จริงบนมือถือ:** ปุ่ม × ต้องมี hit-area ≥44px แม้ icon เล็ก — flag ให้ developer เช็คบนเครื่องจริง

## Addendum: D-13 เบอร์ไม่ถูกปิดบัง — ผลต่อ Design Spec

### สิ่งที่พบระหว่างตรวจไฟล์จริง (สำคัญ — ต้องแจ้ง Controller)
`data.ts` มีคอมเมนต์ที่ `buyerPhone` เขียนไว้แล้วว่า `"เบอร์จริง (ไม่ mask) สำหรับ tap-to-call ... (user decision 2026-06-15)"` และ `OrdersTable.tsx` ก็ render ค่านี้แบบดิบอยู่แล้ว (`{row.original.buyerPhone ?? row.original.buyer}`) — เดสก์ท็อป**ไม่ได้ถูกปิดบังอยู่ก่อนแล้ว**ตามที่โค้ดบอก แต่ `OrderCard.tsx` ปัจจุบัน**ไม่ render เบอร์เลยสักบรรทัด** (คอมเมนต์บรรทัด 179 ในไฟล์นั้นเขียนว่า meta row ตอนนี้ "แทนเบอร์โทรเดิม" — แปลว่าการ์ด v11 (2026-07-06) เคยมีเบอร์แล้วถอดออกไปเพื่อเอาช่องทาง+วิธีชำระมาแทน) จุดนี้ขัดกับ "เบอร์ที่แสดงจะเปลี่ยนจาก `••••••5678`" ที่บอกมา — ผมตีความว่า **D-13 = ทั้งเอาเบอร์กลับมาแสดงบนการ์ดมือถือ (ที่หายไปตั้งแต่ v11) และยืนยันไม่ปิดบังทั้งสองจอ** ไม่ใช่แค่ "เปลี่ยนรูปแบบการ mask ที่มีอยู่แล้ว" — ถ้าตีความผิด ให้ Controller แก้ไขก่อน developer ลงมือ

### ผลกระทบต่อ spec เดิม (แทนที่ทั้งหมดที่เกี่ยวกับเบอร์)

**1. รูปแบบตัวเลข — แนะนำ: ตัวเลขล้วน `0812345678` ไม่ใส่ขีด**
เหตุผล:
- คงรูปแบบเดียวกับที่เดสก์ท็อปแสดงอยู่แล้ว (raw, ไม่ format) — sibling-parity ในหน้าเดียวกัน ไม่ต้องเปลี่ยน 2 จุด
- `select-all` ที่มีอยู่แล้วบนเดสก์ท็อปใช้ copy ไปวางในระบบอื่น (iShip/แชท) ตัวเลขล้วนปลอดภัยกว่าเพราะระบบปลายทางบางตัวไม่ strip ขีดให้เอง
- **แก้ปัญหาไฮไลต์ทั้งข้อ 2 ไปในตัว** (ดูข้างล่าง) — ถ้าไม่มีขีดในข้อความที่แสดง ตำแหน่งที่ตรงจาก digit-only compare จะ map ตรงกับข้อความบนจอ 1:1 ทันที ไม่ต้องคำนวณ offset จากขีดที่แทรกเข้ามา
- ถ้า Controller ยืนกรานอยากได้ `081-234-5678` เพื่ออ่านง่ายขึ้น: ยังทำได้ แต่ต้อง**ไฮไลต์ทั้งก้อนเบอร์แทนการไฮไลต์บางส่วน** ตามที่ทีมเสนอมา (เพราะตำแหน่งที่ตรงจาก digit-only ไม่ใช่ตำแหน่งเดียวกับสตริงที่มีขีดคั่น การ splice highlight range รอบขีดเสี่ยง off-by-one) — ผมยังแนะนำตัวเลขล้วนเป็นค่าเริ่มต้น

**2. ไฮไลต์บนเบอร์**
ใช้ `<HighlightText>` ตัวเดียวกับฟิลด์อื่นได้เลย เพราะเลือกไม่ใส่ขีด (ข้อ 1) — `matchesPhone()` เดิม (digit-only compare) คืน matchStart/matchLength ที่ใช้กับข้อความที่แสดงได้ตรง ๆ ไม่ต้องเขียน mapping function แยก. เคส query มีขีด (`081-234`) แต่ query ถูก strip ขีดออกก่อนเทียบอยู่แล้วตาม design เดิม (`matchesPhone` strip ทั้งสองฝั่ง) — ไม่มีปัญหา

**3. tel: link — แนะนำ: ไม่ทำ ให้เบอร์เป็นข้อความเปล่า (ไม่ใช่ `<a href="tel:">`)**
เหตุผล:
- มีปุ่มโทรเฉพาะอยู่แล้ว (ตามที่ทีมยืนยัน) — ไม่ต้องมี affordance ซ้ำสองจุดบนพื้นที่เดียวกัน (ข้อความ vs ปุ่ม) ที่ทำงานเหมือนกันแต่ทริกเกอร์คนละที่ ผู้ใช้จะสับสนว่า "แตะตรงไหนจะโทร"
- ต้นทุนทางเทคนิคจริง: การ์ดทั้งใบมี stretched-link (`<Link className="absolute inset-0">`) ทับอยู่แล้วเพื่อเปิดหน้ารายละเอียด — ถ้าจะให้ข้อความเบอร์เป็น `<a href="tel:">` ต้องยก `relative z-10` เฉพาะจุด (แพตเทิร์นเดียวกับปุ่ม "ดูเพิ่มเติม"/OrderActions) เพิ่มความซับซ้อนโดยไม่จำเป็นเมื่อมีปุ่มโทรอยู่แล้ว
- ผลคือ: แตะที่ตัวเลขเบอร์ = เหมือนแตะข้อความอื่นในการ์ด (เปิดหน้ารายละเอียด ผ่าน stretched-link เดิม) ซึ่งเป็นพฤติกรรมที่คาดเดาได้ ไม่ใช่ trap ที่ยิงโทรออกโดยไม่ตั้งใจ

**4. ลำดับชั้น/ตำแหน่ง — เบอร์ต้องเบากว่าชื่อเสมอ**
- **มือถือ:** เพิ่มเบอร์เข้าไปใน meta row ที่มีอยู่แล้ว (ช่องทาง+วิธีชำระ) ต่อท้ายด้วย `·` — ใช้คลาสเดียวกับ item อื่นในแถวนั้น (`text-xs text-default-500`) เติม `tabular-nums` (ตัวเลขต้องเรียงคอลัมน์) ไม่ใช้ `font-semibold`/สีเข้มขึ้นเด็ดขาด — ชื่อผู้ซื้อยังคงเป็น `text-sm font-bold text-default-900` เด่นกว่าเสมอตามลำดับเดิม
- **เดสก์ท็อป:** ไม่เปลี่ยน (`text-xs tabular-nums text-default-500` ใต้ชื่ออยู่แล้ว — เบากว่าชื่อซึ่งเป็น `text-sm font-semibold text-default-900` อยู่แล้วเช่นกัน)
- **🛑 ผลสำคัญ: ลบ "ตรงกับ: เบอร์โทร" meta-line ที่ออกแบบไว้ในสเปกฉบับก่อนหน้าทิ้งทั้งหมด** — เพราะเบอร์กลายเป็นฟิลด์ที่แสดงอยู่บนจอถาวรแล้วทั้งสองจอ ไม่ใช่ฟิลด์ที่ซ่อนอีกต่อไป → ใช้ inline `<HighlightText>` แบบเดียวกับ orderNo/buyerName/trackingNo ได้เลย **ผลคือมือถือไม่มีฟิลด์ "ซ่อน" เหลืออยู่เลยสักฟิลด์** (5 ฟิลด์ทั้งหมดมีที่แสดงถาวรหรือ auto-expand ได้) — ทำให้ meta-line pattern (icon `search` + "ตรงกับ:") **ไม่ถูกใช้งานจริงในงานนี้แล้ว** แต่ยังคงออกแบบ/export ไว้ใน `order-search.ts`/`HighlightText` เผื่ออนาคตมีฟิลด์ที่ 6 ที่ยังซ่อนอยู่ (ไม่ต้องรื้อ ไม่มีต้นทุนเพิ่ม)

### Anti-slop self-check (เพิ่มเติมจาก D-13)
- **ตัดของซ้ำ:** ลบ meta-line "ตรงกับ: เบอร์โทร" ที่เคยออกแบบไว้ทิ้ง เพราะกลายเป็นข้อมูลซ้ำซ้อนกับเบอร์ที่แสดงถาวรแล้ว — ตรงตามหลัก "การ์ด/element ที่ข้อมูลซ้ำต้องตัดทิ้ง"
- **สีถูกความหมาย:** เบอร์ไม่ใช้สี semantic ใด ๆ (ไม่ primary ไม่ success ฯลฯ) เป็น neutral gray เหมือนข้อมูล metadata อื่นในแถวเดียวกัน — ไม่เสี่ยงชนความหมายสถานะ
- **แตะได้จริงบนมือถือ:** เบอร์เป็นข้อความเปล่า ไม่ใช่ target ที่ต้องกดแม่นเป๊ะ (ไม่ต้องกังวลเรื่อง 44px เพราะไม่ใช่ interactive element ตามมติข้อ 3)

### Open question เพิ่ม
4. ยืนยันกับ Controller เรื่องการตีความ "การ์ดมือถือเคยปิดบังเบอร์" — จากไฟล์จริง การ์ดมือถือไม่เคยแสดงเบอร์เลย (ไม่ใช่ปิดบัง แต่ไม่มีเลย) ผมออกแบบให้ D-13 ครอบทั้ง "เอาเบอร์กลับมาแสดง" และ "ไม่ปิดบัง" พร้อมกัน — ถ้า Controller ต้องการแค่ยืนยัน "ไม่ปิดบังเดสก์ท็อป" (ซึ่งไม่ปิดบังอยู่แล้วในโค้ด) โดยไม่ต้องการให้มือถือมีเบอร์เพิ่มขึ้นมา ให้แจ้งกลับก่อน developer ลงมือ เพราะเป็นงานคนละขนาด (มือถือ: เพิ่ม UI ใหม่ / เดสก์ท็อป: ไม่มีอะไรต้องแก้เลย)

## (5) งบพื้นที่ sticky header ที่ 320px — กางเป็นตัวเลขจริง

แถว 1 ของ `OrdersList.tsx` (`data-orders-header` → `<div className="flex items-center gap-2">`) ที่มองเห็นได้จริงบนมือถือ (`lg:hidden` ตัว, `lg:inline-flex` ตัดออก):

| องค์ประกอบ | คลาส | กว้าง |
|---|---|---|
| ปุ่มย้อนกลับ | `size-10 shrink-0` | 40px |
| ช่องค้นหา | `relative flex-1` | **ตัวแปร (คำนวณด้านล่าง)** |
| ปุ่มตัวกรอง | `size-10 shrink-0` | 40px |
| กระดิ่ง | `size-10 shrink-0` | 40px |
| ปุ่มสร้าง (มือถือ, `lg:hidden`) | `size-11 shrink-0` | 44px |
| ~~ปุ่มดึงจาก iShip~~ | `hidden ... lg:inline-flex` | **0 — ซ่อนที่ 320px** |
| ~~ปุ่มสร้าง (เดสก์ท็อป)~~ | `hidden ... lg:inline-flex` | **0 — ซ่อนที่ 320px** |

คำนวณ: `40+40+40+44 = 164px` คงที่ + `gap-2` (8px) ×4 ช่อง = `32px` + padding container (`px-2` = 8px×2) = `16px`
**รวมของทุกอย่างยกเว้นช่องค้นหา = 164+32+16 = 212px**
**เหลือให้ช่องค้นหาที่ 320px = 320 − 212 = 108px**

108px คือพื้นที่ **ทั้งกล่อง** ของช่องค้นหา (รวม icon แว่นขยายซ้าย + padding + ตัวอักษรที่พิมพ์) — ของเดิมแคบขนาดนี้อยู่แล้วก่อนงานนี้ (ยืนยันจากโค้ด ไม่ใช่สิ่งที่งานนี้ทำให้แย่ลง)

**ปุ่ม × ที่จะเพิ่ม อยู่ *ภายใน* 108px นี้ ไม่ใช่แถวนอก** — ต้องกิน padding-right ของ `<input>` เพิ่ม (`!pr-8` ประมาณนั้น) เพื่อไม่ให้ตัวอักษรท้ายที่พิมพ์ไปซ้อนปุ่ม × พอดี เหลือพื้นที่ตัวอักษรจริง ~108−32(icon ซ้าย+padding)−32(ปุ่ม ×) ≈ **44px สำหรับตัวหนังสือที่พิมพ์** — แคบ แต่ input จริงรองรับ scroll ภายในตัวเองได้ตามปกติของ `<input type="text">` (เบราว์เซอร์เลื่อนให้เห็น cursor เอง) ไม่ใช่บั๊ก เป็นพฤติกรรมมาตรฐานของ mobile search bar ที่มี icon นำหน้า+ปุ่มล้างท้าย (เช่น iOS Safari/Search) — **ไม่ใช่การเพิ่มความแออัดสุทธิให้แถวนอก** (แถวนอกไม่มีอะไรเพิ่ม/หายเลย)

**768px / ≥1280px:** ไม่มีข้อจำกัดแบบนี้ — เดสก์ท็อปช่องค้นหาอยู่ใน toolbar แถวที่มีที่ว่างมาก (ไม่ต้องกางงบ)

## (3) Impeccable compliance

**Mode: Operate** — `(paces)/**` เป็น dashboard/table ของ seller เกณฑ์ตัดสินคือ scanability/consistency/native-expectation ชนะการแสดงออกทางภาพ ไม่มี hero เชิง marketing ในหน้านี้ — ทุกองค์ประกอบใหม่ต้อง "หายไปในงาน" (PRODUCT.md Product Principle #4 — "แบรนด์ที่ขอบ งานที่ทำให้หายไปตรงกลาง")

- **One Voice (≤10% จอ):** ไฮไลต์ใช้ `bg-primary/15` (โปร่ง 15%) เกิดขึ้นเฉพาะช่วง active search (state ชั่วคราว ไม่ใช่ของถาวรบนจอ) — ไม่กระทบงบ 10%
- **Verified-Means-Green:** ไม่แตะ — ไฮไลต์ใช้น้ำเงิน (primary) ไม่ใช่เขียว ไม่ชนความหมาย "ยืนยันแล้ว" ของสถานะออเดอร์ในการ์ด/แถวเดียวกัน — ตรวจแล้วไม่ชน (จุดที่ brief เตือนไว้ตรง ๆ)
- **Sentence case:** ข้อความใหม่ทั้งหมด (คำใบ้/empty state/aria-label) เป็นประโยคปกติ
- **Ink-tinted shadow:** ไม่เพิ่ม shadow ใหม่เลย (ring ≠ shadow)
- **anti-slop:** ไม่มี gradient, ไม่มี badge ข้อความใหม่ (ตัดสินใจใช้ ring แทน — ดูเหตุผลข้อ 6 ด้านล่าง), ไม่ซ้อนการ์ดในการ์ด, **ตัด meta-line "ตรงกับ: ..." ทิ้งทั้งกลไก** เพราะหลัง D-13 ไม่มีฟิลด์ไหนซ่อนอีกแล้ว (ดูหัวข้อ D-13 ด้านล่าง) — ของที่ไม่ทำงานจริงต้องไม่ถูกสร้าง
- **น้ำเสียง:** empty state บอกทางออกเสมอ ("พบ N รายการในทั้งร้าน" + ปุ่มพาไป) ไม่ใช่แค่บอกว่า "ไม่พบ"
- **จุดที่ใช้ accent สีธีม:** `bg-primary/15` ในไฮไลต์ทุกจุดที่ query ตรง + `ring-primary/30` (เฉพาะ exact match) + ปุ่ม "ดูผลทั้งร้าน" (`btn bg-primary`) — **พระเอกของหน้าตอน active search = ใบที่ตรงเป๊ะที่ลอยขึ้นบนสุด**; ตอนไม่ได้ค้นหา พระเอกยังเป็นของหน้าเดิม (ไม่เปลี่ยน)
- **จุดที่ theme ขัดกับ Impeccable:** ไม่มีจุดขัดตรง ๆ — จุดเดียวที่ต้องรายงานคือ "ไม่พบ theme match สำหรับ text-highlight" (ตาราง §2) ซึ่งแก้ด้วยการ compose primitive เดิม

## (4) คำตอบ 7 ประเด็นจาก brief แรก + 4 ประเด็นเบอร์เต็ม D-13

**Brief แรก:**

1. **ค้น 5 ฟิลด์:** `src/lib/order-search.ts` — `matchesText()` (orderNo/buyerName/trackingNo/itemName, trim+lowercase substring), `matchesPhone()` (digit-only substring ทั้งสองฝั่ง), `isExactIdentifierMatch()` (เทียบเต็มค่า เฉพาะ orderNo/phone/trackingNo — ไม่รวม buyerName/itemName เพราะไม่ใช่ "ตัวระบุเฉพาะ")
2. **ตรรกะเดียวกัน 2 จอ:** `searchOrders(orders, query)` เรียกอิสระจาก `OrdersList.tsx` และ `OrdersTable.tsx` คนละที่ แต่ input เดียวกัน→output เดียวกันเสมอ (สถาปัตยกรรมเดียวกับ `order-date-filter.ts` ที่พิสูจน์แล้วในโค้ด prod)
3. **AND กับตัวกรองอื่น:** ยืนยัน — `searchOrders()` เป็นขั้นสุดท้ายของ pipeline ที่กรอง stage/status/type/date มาก่อนแล้ว (มือถือ) และเป็น pre-filter ก่อนเข้า `useReactTable` (เดสก์ท็อป, คอลัมน์ filter ยังทำงาน AND ต่อได้ปกติ)
4. **≥2 ตัวอักษร + สื่อความหมายที่ 1 ตัว:** `ORDER_SEARCH_MIN_CHARS=2`; ที่ 1 ตัวอักษรไม่กรอง + ขึ้นแถวคำใบ้ "พิมพ์อีก 1 ตัวเพื่อค้นหา" (ดู wireframe §1)
5. **ไฮไลต์ + บอกฟิลด์ที่ซ่อน:** **หลัง D-13 ไม่มีฟิลด์ไหนซ่อนอีกแล้ว** (ดูหัวข้อ D-13) → ทุกฟิลด์ inline-highlight ตรงตำแหน่งจริง ไม่มี meta-line "ตรงกับ:" ในงานนี้
6. **สัญญาณ exact match:** **มี** — ใช้ `ring-1 ring-primary/30` ห่อการ์ด/แถบหัวกลุ่ม ไม่ใช้ badge ข้อความใหม่ (เหตุผล: ไฮไลต์เต็มค่าที่มีอยู่แล้วเป็นหลักฐานในตัว + หน้ามีเสียง UI เยอะอยู่แล้ว ไม่อยากเติม element ใหม่ที่ไม่จำเป็น — แต่ยังต้อง "มีสัญญาณ" เพราะการเรียงลำดับที่เปลี่ยนเงียบ ๆ เสี่ยงผู้ใช้คิดว่าแอปบั๊ก)
7. **`?q=` sync + ปุ่มล้างตัวกรอง + ชิป:**
   - sync ด้วย `window.history.replaceState` (ไม่ใช่ `router.replace`/`push`) กันจอกระตุกทุกตัวอักษร (เหตุผลเต็มใน §Design decisions)
   - "ล้างตัวกรอง" ในโมดัลมือถือ **ไม่ล้างคำค้นหา** — สอดคล้องกับหลักการที่มีอยู่แล้วในคอมเมนต์โค้ดปัจจุบัน ("ล้างเฉพาะสิ่งที่โมดัลนี้คุม")
   - **ไม่มี chip แสดง query** — ช่องค้นหาเองมองเห็นตลอดเวลาอยู่แล้ว ต่างจาก apptDay ที่ซ่อนในโมดัลจึงต้องมีสัญญาณแทน

**D-13 (เบอร์เต็ม):**

1. **รูปแบบตัวเลข:** แนะนำ **ไม่ใส่ขีด** (`0812345678`) — เหตุผล: (ก) sibling-parity กับเดสก์ท็อปที่แสดงดิบอยู่แล้ว (ข) `select-all`/copy ไปวางระบบอื่น (iShip) ปลอดภัยกว่าเป็นตัวเลขล้วน (ค) **แก้ปัญหาข้อ 2 ไปในตัว** — ถ้าไม่มีขีด ตำแหน่งที่ตรงจาก digit-only compare ตรงกับข้อความบนจอ 1:1 ไม่ต้องคำนวณ offset ข้ามอักขระคั่น. ถ้า Controller อยากได้ `081-234-5678` เพื่ออ่านง่าย ต้องไฮไลต์ทั้งก้อนแทนบางส่วนตามที่ทีมเสนอ (เสี่ยง off-by-one ถ้าทำ partial highlight)
2. **ไฮไลต์บนเบอร์:** ทำได้ตรง ๆ ด้วยเหตุผลข้อ 1 (ไม่มีขีดให้ชนกัน)
3. **tel: link:** แนะนำ **ไม่ทำ** — มีปุ่มโทรเฉพาะอยู่แล้ว (ตามที่ทีมยืนยัน), การ์ดทั้งใบมี stretched-link ทับอยู่แล้ว การทำเบอร์เป็นลิงก์ซ้อนต้องยก `relative z-10` เฉพาะจุดเพิ่มความซับซ้อนโดยไม่จำเป็น, และเลี่ยง double-affordance ที่คลุมเครือ (แตะแล้วโทร vs แตะแล้วเปิดรายละเอียด)
4. **น้ำหนัก/สี:** เบอร์อยู่ใน meta row เดียวกับช่องทาง/วิธีชำระ (`text-xs text-default-500 tabular-nums`) — เบากว่าชื่อผู้ซื้อ (`text-sm font-bold text-default-900`) เสมอทั้ง 2 จอ ไม่ใช้สี semantic ใด ๆ

## (6) จุดที่ควรมี icon แต่ยังไม่ระบุตัว — **ต้องถาม user ก่อน ห้ามเดา**

**1 จุดเดียว:** เบอร์โทรใน meta row ของการ์ดมือถือ (D-13) อยู่ถัดจากช่องทาง (มีโลโก้สี) และวิธีชำระ (มีไอคอน `PAYMENT_ICONS`) — ถ้าอยากให้แถวสม่ำเสมอ (ทุกไอเทมมี icon นำหน้า) เบอร์ควรมี icon โทรศัพท์นำหน้าด้วย **แต่ผมไม่ระบุชื่อ icon เอง** เพราะยังไม่ได้เปิด `theme/paces/Admin/TS/src/app/(admin)/icons/` ไปยืนยันว่าชื่อที่คิดในใจ (เช่น `phone`/`device-mobile`) มีอยู่จริงในชุดที่ Paces bundle ไว้จริงไหม (tabler/lucide/solar/boxicons/remix — ชุดไหนมีชื่อนี้)

**ค่า default ที่แนะนำถ้าไม่อยากเสียเวลาถาม:** ไม่ต้องมี icon เลย (plain text) — ตรงกับที่เดสก์ท็อปทำอยู่แล้ว (เบอร์ใต้ชื่อไม่มี icon นำหน้าเช่นกัน) ไม่ต้องเพิ่มความสม่ำเสมอในแถวนี้เป็นพิเศษ — **นี่คือทางเลือกที่ผมใช้เป็นค่าเริ่มต้นใน wireframe ข้างบน** ถ้า Controller/user อยากได้ icon ให้เจาะจงชื่อจากชุดที่ยืนยันแล้วก่อนส่งกลับมา

ไม่มีจุดอื่นในงานนี้ที่ต้องเลือก icon ใหม่ — icon ทั้งหมดที่ใช้ (`circle-x`, `search`, `shopping-cart-off`) **มีอยู่แล้วและถูกใช้จริงในไฟล์เดียวกันนี้** (ยืนยันด้วยการอ่านโค้ดตรง ๆ ไม่ได้เดา)

## (7) ข้อทักท้วง — ให้ user ตัดสิน

**🛑 D-13 เพิ่มพื้นที่ผิวที่เบอร์ลูกค้ารั่วไหลได้จากการกวาดตาดูจอเฉย ๆ** — ก่อนหน้านี้เบอร์ (แม้จะไม่ mask ตามคอมเมนต์ในโค้ดเดสก์ท็อป) ก็ยังต้องกดเข้าไปที่แถวนั้นถึงจะเห็น หรือบนมือถือไม่แสดงเลย ตอนนี้กลายเป็น**เห็นได้ทันทีจากการสแกนรายการทั้งจอ**ทั้งมือถือและเดสก์ท็อป — เพิ่มความเสี่ยงในสถานการณ์ที่หน้าจอถูกเห็นโดยคนอื่น (พนักงานร้านที่ไม่ควรรู้เบอร์ลูกค้าทั้งหมด, การแชร์สกรีน/อัดคลิปสอนใช้งาน, ลูกค้าคนอื่นแอบมองจอตอนพนักงานเช็คออเดอร์). ไม่ใช่เหตุผลให้ไม่ทำ (เป็นมติที่ล็อกแล้วและมีเหตุผลทางธุรกิจที่สมเหตุสมผล — seller เป็นเจ้าของข้อมูลลูกค้าตัวเอง) แต่ **อยากให้ user ยืนยันว่าประเมินความเสี่ยงนี้แล้วจริง ๆ** ก่อนขึ้น prod ไม่ใช่แค่มติที่มาจากมุมมอง "การปิดบังไม่จำเป็นเพราะ owner เห็นได้อยู่แล้ว" อย่างเดียว

ไม่มีข้อทักท้วงอื่นต่อ 7 ประเด็นจาก brief แรก — ทุกมติดูสมเหตุสมผลและออกแบบตามได้โดยไม่กระทบ UX ในทางลบ

### Edge states
0 ตัวอักษร (ไม่เปลี่ยน) / 1 ตัวอักษร (คำใบ้) / query ยาวผิดปกติ (substring ปกติ ไม่ crash) / ผลว่างมีตัวกรองอื่น N>0 (title+description+CTA) / ผลว่าง N=0 (title อย่างเดียว) / ค้นหาพร้อม apptDay (N ทั้งร้าน = `orders` เต็ม ไม่ใช่ `dayScoped` — ดู Design decisions #2) — ไม่มี loading/error (client-side ล้วน)

### Design decisions + rationale (สรุปเหตุผลหลัก)
1. `history.replaceState` ไม่ใช่ router — กัน RSC refetch ทุกตัวอักษร
2. "ทั้งร้าน" = `orders` เต็มดิบ ไม่ใช่ `dayScoped` — เบี่ยง convention เดิมโดยตั้งใจ (ต้องยืนยันกับ Controller — เป็น Open question)
3. ไม่มี chip query — ซ้ำกับช่องค้นหาที่เห็นอยู่แล้ว
4. "ล้างตัวกรอง" ไม่ล้างคำค้นหา — ตาม precedent ในโค้ดเดิม
5. exact-float-to-top เฉพาะไม่มี manual sort (เดสก์ท็อป) — ไม่ขัดสิ่งที่ผู้ขายเพิ่งสั่งเอง
6. ring ไม่ใช่ badge — เหตุผลใน §4 ข้อ 6
7. "รายการ" ไม่ใช่ "ใบ" — กัน grammar เพี้ยนข้าม vertical (memory `feedback_vocab_substitution_needs_sentence_sets`)
8. "ในตัวกรองที่เลือกไว้" เป็นวลี generic ไม่ประกอบ label เฉพาะ — กัน grammar เพี้ยนแบบเดียวกับข้อ 7
9. **ตัด meta-line "ตรงกับ:" ทิ้งทั้งกลไก** (ใหม่ในรอบนี้) — หลัง D-13 ไม่มีฟิลด์ไหนซ่อนจริงอีกแล้ว การสร้าง component ที่ไม่มีวันถูกเรียกขัด anti-slop โดยตรง

### Open questions
1. `impeccable/reference/*` ไม่มีในเครื่อง agent — ต้องเทียบซ้ำหลัง build
2. `<details open>` auto-open — ความเสี่ยงทางเทคนิค (React sync attribute ทุก render) ส่งต่อให้ developer ตัดสินวิธี implement
3. นิยาม "ทั้งร้าน" (Design decision #2) — ต้องยืนยันจาก Controller
4. การตีความ D-13 ว่าครอบทั้ง "เอาเบอร์กลับมาแสดงบนมือถือ" ด้วยไหม (ไฟล์เดิมไม่เคยแสดงเบอร์บนการ์ดเลย) — ยืนยันแล้วจาก brief นี้ว่าใช่ (ระบุ "ทั้งการ์ดมือถือ") ถือว่าปิดประเด็นนี้แล้ว

### Anti-slop self-check
1. เฉพาะ Deep: format เลข `DP{ปี}{เดือน}{code}`, `vocab.noun` ผันตาม vertical — เอาไปแปะสินค้าอื่นตรง ๆ ไม่ได้
2. 1 อย่างเด่นสุด: ใบตรงเป๊ะตอน active search
3. ตัดของซ้ำ: ไม่มี chip query, ไม่มี badge "ตรงเป๊ะ", ไม่มี meta-line ที่ไม่มีวันเรียก
4. state ครบ: ตามตารางข้างบน
5. copy บอกสิ่งที่ทำได้จริง: ปุ่ม "ดูผลทั้งร้าน (N)" มี N จริงเสมอ
6. คำเดียวกัน=ของเดียวกัน: "เบอร์โทร" ตรงกับตารางเดสก์ท็อป
7. สีถูกความหมาย: ตรวจแล้วใน §3
8. แตะได้จริง: ปุ่ม × ต้อง hit-area ≥44px — flag ให้ developer เช็คเครื่องจริง
9. จอ 1440 คอลัมน์ว่าง: ไม่เกี่ยว — แก้ toolbar/cell เดิมที่ใช้พื้นที่เต็มความกว้างอยู่แล้ว
