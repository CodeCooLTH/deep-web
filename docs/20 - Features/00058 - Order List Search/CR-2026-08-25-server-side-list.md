## 1. Performance analysis (ทำก่อนเขียนโค้ด ตามที่ user สั่งให้เป็นของขึ้นก่อนเสมอ)

### 1.1 ตัวเลขจริงจาก prod (2026-08-25, SELECT อย่างเดียว)

| ตัวชี้วัด | ค่า |
|---|---|
| `Order` ทั้งฐาน | 554 แถว |
| ร้านใหญ่สุด (ธนภัทร์ อะไหล่มอเตอร์ไซค์) | **431 ใบ** · ลูกค้าไม่ซ้ำ 415 |
| ร้านที่สอง | 104 ใบ |
| `OrderItem` ต่อออเดอร์ | avg **1.07** · max 6 (ร้านใหญ่รวม 460 แถว) |
| `pg_column_size` ของแถว `Order` | avg **625 B** · max 829 B |
| **ข้อมูลดิบทั้งร้านใหญ่** | **< 400 KB** |
| ออเดอร์ที่มีพัสดุ active | 417 / 431 (**97%**) |

### 1.2 🛑 ข้อค้นพบที่พลิกวิธีมองปัญหา — คอขวดไม่ได้อยู่ที่ฐานข้อมูล

ข้อมูลดิบทั้งร้าน **< 400 KB** แต่ payload ที่ข้าม RSC boundary อยู่ที่ **~500–800 KB**
เพราะ `page.tsx` **enrich ทุกแถว** ด้วยของอีก 6–7 ก้อน (shipment · appointment · money ·
shipTo · customerStats · conversationId · items + รูป) แล้ว serialize ลงไปทั้งหมด

⇒ **ต้นทุนอยู่ที่ "แปลงและส่งแถวที่ผู้ใช้ไม่มีวันเห็น" ไม่ใช่ที่ "ดึงแถวจากฐาน"**
การแก้จึงต้องลด **จำนวนแถวที่ถูก enrich** ไม่ใช่แค่ทำ query ให้เร็วขึ้น

### 1.3 🛑 หลักฐานที่ชัดที่สุดว่าเสียเปล่าตรงไหน

กระจายกองงานของร้านใหญ่ (จำลองสูตร `deriveShippingStage` เป็น SQL แล้วรันจริงบน prod):

| กอง | จำนวน | มีชิป/ไทล์พาไปไหม |
|---|---|---|
| **DONE** | **331 (77%)** | **ไม่มีเลย** |
| SHIPPING | 38 | ✅ |
| AWAITING_COD | 25 | ✅ |
| AWAITING_PICKUP | 19 | ✅ |
| RETURNED | 12 | ✅ |
| AWAITING_PARCEL | **5** | ✅ |
| PROBLEM | 1 | ✅ |

**77% ของแถวที่โหลดมาตกกองที่ไม่มีทางเข้าไปดู** และงานที่ร้านต้องทำจริงรวมกัน ~100 ใบ
กองที่เร่งด่วนที่สุด (`AWAITING_PARCEL` รอเลขพัสดุ) มีแค่ **5 ใบ** จาก 431

⇒ **แบ่งหน้าอย่างเดียวไม่พอ** — ถ้ากรอง stage ยังทำที่ client ผู้ใช้จะต้องเปิดหลายหน้ากว่าจะ
เจอ 5 ใบนั้น ต้องกรองใน SQL ให้ได้ด้วย

### 1.4 ที่พังก่อนตามลำดับ เมื่อออเดอร์เพิ่มขึ้น

| ออเดอร์/ร้าน | payload | ค้นหา (วัดจริง) | อาการ |
|---|---|---|---|
| 431 (วันนี้) | ~500–800 KB | 2.5 ms | ยังไหว |
| **~1,000** | **~1.5 MB** | 6 ms | **มือถือเริ่มหน่วงตอนเปิดหน้า** ← เส้นที่ต้องเริ่มทำ |
| 5,000 | ~7 MB | 29 ms | เปิดหน้าบน 4G รอหลายวินาที |
| 10,000 | **~12–19 MB** | 59 ms | **มือถือกิน RAM ไม่ไหว = พัง ไม่ใช่ช้า** |

🛑 **แก้เกณฑ์ที่เคยตั้งไว้ผิด:** SRS §10.14 เขียนว่า "ย้ายไป server ที่ 1,500 ใบ" ซึ่งมาจาก
ต้นทุน *การค้นหา* — เป็นข้อจำกัดที่ผิดตัว ตัวที่แคบกว่าคือ **ขนาด payload**
⇒ เกณฑ์จริงคือ **~1,000 ใบต่อร้าน** และตัวที่ต้องเฝ้าคือ **KB ไม่ใช่ ms**
ร้านใหญ่สุดโต ~500 ใบ/เดือนจาก 431 ⇒ **ชนเส้นราวต้นเดือนหน้า**

### 1.5 อีก 2 อย่างที่ต้องแก้ไปพร้อมกัน ไม่งั้นแก้ไม่จบ

1. **ทุกครั้งที่กดชิปกรอง `pushQuery()` ยิง `router.push`** ⇒ ดึง flight payload ทั้งก้อนใหม่
   (ไม่ใช่แค่ตอนเปิดหน้า — ตอนกดกรองด้วย)
2. **การ์ดสถิติ 4 ใบบนหัวหน้า** คำนวณด้วย `.filter()` บน array ทั้งร้านใน RSC (`page.tsx:440-486`)
   ⇒ ต่อให้แบ่งหน้าแล้ว ยังต้องดึงทั้งร้านมาอยู่ดีถ้าไม่ย้ายตัวนับไป SQL

## 2. Index ที่ต้องมี (user สั่ง: "ตรงไหนควรมี index ให้ทำตั้งแต่วันนี้")

### 2.1 สถานะปัจจุบัน
- `Order` มี 14 index แต่ **ตัวเดียวที่ใช้กับหน้านี้ได้คือ `@@index([shopId, status, createdAt])`**
- `OrderItem`: มีแค่ `@@index([orderId])` — **ไม่มี index บน `name`**
- `OrderShipment`: ไม่มี index บน `carrierStatus`/`direction`/`isDryRun` และไม่มี composite
  ที่รองรับ LATERAL join ที่ใช้อยู่
- `ShipmentTracking`: มีแค่ `orderId @unique` — **ไม่มี index บน `trackingNo`**
- 🛑 **ทั้งรีโปไม่มี `pg_trgm` / `tsvector` / GIN บน text เลยสักตัว** (GIN 2 ตัวที่มีเป็นบน
  `String[]` ของ `Shop`) ⇒ ค้นหาฝั่ง server ต้องเริ่มจากศูนย์

### 2.2 ที่ต้องเพิ่ม

| # | index | ทำไม | ชนิด |
|---|---|---|---|
| I-1 | `Order(shopId, createdAt DESC, id DESC)` | keyset pagination — ตัวหลักของทุก query ในหน้านี้ | B-tree |
| I-2 | `OrderShipment(orderId, status, isDryRun, createdAt DESC)` | LATERAL join หาพัสดุ active ใบล่าสุด — **97% ของแถวต้องทำ** | B-tree |
| I-3 | `ShipmentTracking(trackingNo)` | ค้นเลขพัสดุที่ร้านแจ้งเอง | B-tree |
| I-4 | `OrderShipment(trackingNo)` | ค้นเลขพัสดุ iShip (มี partial unique อยู่แล้วแต่ `WHERE NOT NULL`) | ตรวจว่าใช้ของเดิมได้ไหมก่อนเพิ่ม |
| I-5 | GIN trgm บน `Order.buyerName` | ค้นชื่อลูกค้าแบบ `contains` | GIN + `pg_trgm` |
| I-6 | GIN trgm บน `OrderItem.name` | ค้นชื่อสินค้า | GIN + `pg_trgm` |
| I-7 | `Order(shopId, "codReceivedAt")` หรือรวมใน I-1 | กอง `AWAITING_COD` | ประเมินหลังเขียน query จริง |

🛑 **I-5/I-6 ต้อง `CREATE EXTENSION IF NOT EXISTS pg_trgm` และเขียนเป็น unmanaged SQL**
เพราะ Prisma แสดง trgm operator class ไม่ได้ ⇒ ตกอยู่ใต้ข้อห้าม `prisma db pull` (HR15)
ต้องเขียนคอมเมนต์กำกับใน migration

🛑 **`Order.buyerContact` (เบอร์) ไม่ต้องใช้ trgm** — ค้นเบอร์เป็น digits-only prefix/substring
ควรใช้ **คอลัมน์ normalize + B-tree** หรือ trgm ตัวเดียวกัน ต้องวัดก่อนตัดสิน (ดู D-3)

## 3. จุดที่ยากจริง และตัวเลือก

### 3.1 ตัวนับ 13 จุดที่ต้องตรงกับตัวกรองเสมอ

หน้านี้ + Command Center มีตัวเลขที่ผู้ใช้กดแล้วต้องเจอจำนวนตรงกัน **13 จุด**
CLAUDE.md เตือนไว้เองว่า *"ห้ามนับด้วย SQL แล้วกรองด้วย TS (จะกดเลข 5 เข้าไปเจอ 4)"*

🛑 **`getShippingStageCounts()` (`order.service.ts:1776-1822`) จงใจนับใน TS อยู่แล้ว**
(ดึงแถวมา derive ด้วย `deriveShippingStage` ตัวเดียวกับหน้า `/orders`) และคอมเมนต์เขียน
เหตุผลไว้ตรง ๆ ว่ายอมช้าเพื่อให้เลขตรง
⇒ **ถ้าเราทำ stage เป็น SQL สำหรับ `/orders` แต่ปล่อยตัวนี้ไว้ = ได้นิยาม 2 ชุดทันที**
ไม่ว่าจะเลือกทางไหน **ต้องย้ายทั้งคู่พร้อมกัน**

### 3.2 ข่าวดี: ตรรกะทั้งสองแกนเป็นฟังก์ชันบริสุทธิ์

- `deriveShippingStage()` — ขึ้นกับ **5 ค่าเท่านั้น**: `Order.status` · มีพัสดุ active ไหม ·
  `carrierStatus` · `paymentMethod` · `codReceivedAt` · **ไม่มี `Date.now()` และไม่อ่านอะไรนอกแถว**
- `deriveAppointmentStage()` — ขึ้นกับ `serviceStart` + `appointmentStatus` (คอลัมน์บน `Order` ตรง ๆ)

⇒ **ไม่มีอะไรที่ "คำนวณที่ server ไม่ได้"** — และ agent สำรวจได้จำลองสูตรเป็น SQL รันจริงบน
prod สำเร็จแล้ว (ตาราง §1.3 มาจากตรงนั้น)

### 3.3 `Order.orderNo` ยังเชื่อเป็นแหล่งค้นหาไม่ได้

- มี `@@index([orderNo])` อยู่แล้วและตั้งใจให้ค้นได้ตั้งแต่แรก
- **แต่หน้าจอไม่เคยอ่านคอลัมน์นี้เลย** — `formatOrderNo()` derive สดทุกครั้ง
- เขียนแค่ 2 จุด (`createOrder`, `updateOrder`) แต่ **`prisma.order.create()` อีก 2 จุดไม่เขียนเลย**
  (`auction.service.ts:545`, `booking.service.ts:194`)
- prod: `orderNo IS NULL` = 0 แถว · **ไม่ตรงกับค่าที่คำนวณสด 3 แถว** (ทั้งหมดคือ seed `DEMO-000x`)
⇒ ถ้าจะค้นด้วย SQL บนคอลัมน์นี้ ต้อง **backfill + ปิดช่อง 2 เส้นทาง + เทสผูก** ก่อน
ไม่งั้นค้นเลขที่เห็นบนจอแล้วไม่เจอ = บั๊กที่ 00058 เพิ่งแก้ไปในทิศตรงข้าม

### 3.4 ของที่จะพังเงียบถ้าไม่จัดการ

| # | เรื่อง | อาการถ้าปล่อย |
|---|---|---|
| R-1 | **"เลือกทั้งหมด" ใน bulk bar** | กลายเป็น "เลือกทั้งหน้า" เงียบ ๆ — ผู้ขายกดพิมพ์ใบปะหน้า 200 ใบแล้วได้ 10 ใบโดยไม่มีอะไรบอก |
| R-2 | **ค้นหายังอยู่ที่ client ขณะที่แบ่งหน้าที่ server** | ค้นเจอเฉพาะหน้าที่เปิดอยู่ = regression ที่แย่กว่าก่อนทำ 00058 **⇒ ต้องย้ายพร้อมกัน ห้ามแยกเฟส** |
| R-3 | **ตัวกรอง 5 แกนไม่มี URL param** (ช่วงเวลา · ประเภท · ขนส่ง · sort · page) | ย้ายไป server แล้วต้องออกแบบ contract ใหม่ทั้งชุด |
| R-4 | **การ์ดสถิติ 4 ใบ** คำนวณจาก array ทั้งร้าน | ยังต้องดึงทั้งร้านต่อไปแม้แบ่งหน้าแล้ว |
| R-5 | lazy-load มือถือทีละ 8 vs "แถวละ N" เดสก์ท็อป | สอง breakpoint ต้องใช้ contract เดียวกันฝั่ง server |

## 4. จุดตัดสินใจ — ✅ เคาะแล้วทั้งหมด (ก) เมื่อ 2026-08-25

### D-1 — ตรรกะกองพัสดุจะอยู่ที่ไหน
- **(ก) เขียนเป็น SQL แล้วผูกด้วยเทสเทียบผลสองฝั่ง** — ดึงแถวดิบมารัน `deriveShippingStage`
  ใน TS แล้วเทียบกับคำตอบของ SQL บนข้อมูลชุดเดียวกัน ต้องตรงกันทุกแถว มิฉะนั้นเทสแดง
  (ปิดความเสี่ยง "สองที่ไม่ตรงกัน" ด้วย *ด่าน* ไม่ใช่ *คอมเมนต์*)
- **(ข) เก็บเป็นคอลัมน์ `Order.shippingStage`** ที่ maintain ตอนเขียน + backfill + index
  — index ง่ายกว่า แต่เข้ากับดัก `stored-flag-vs-owner-truth.md`: ต้องมีคนอัปเดตทุกจุดที่เขียน
  5 คอลัมน์นั้น (สร้าง/แก้ออเดอร์ · webhook iShip · ปิด COD · ยกเลิก · รับคืน) พลาดจุดเดียว
  = ข้อมูลเน่าเงียบ และ **ทดสอบล่วงหน้าไม่ได้ว่าคนในอนาคตจะเพิ่มจุดเขียนที่ 6 ไหม**

### D-2 — ขอบเขตของ CR นี้
- **(ก) ทำครบชุดรอบเดียว** — keyset pagination + ย้ายตัวกรองทุกแกน + ค้นหา + ตัวนับ 13 จุด + index
- (ข) แบ่ง 2 รอบ: รอบแรกทำเฉพาะที่ไม่กระทบ contract (index + ตัวนับไป SQL) รอบสองค่อยแบ่งหน้า
  🛑 **แต่ R-2 บังคับว่าแบ่งหน้ากับค้นหาต้องไปพร้อมกัน** จึงแยกได้ไม่มากอย่างที่คิด

### D-3 — ค้นหาชื่อสินค้า/ชื่อลูกค้า
- **(ก) GIN + `pg_trgm`** — `contains` เร็วจริง แต่ต้อง `CREATE EXTENSION` + unmanaged SQL
- (ข) ยังไม่ใส่ index รอบนี้ ยอม seq-scan ไปก่อน (ที่ 431 แถวยังไม่เจ็บ) แล้วเพิ่มเมื่อชน
  🛑 ขัดกับที่ user สั่งว่า *"ตรงไหนควรมี index ให้ทำตั้งแต่วันนี้"*

### D-4 — "เลือกทั้งหมด" หลังแบ่งหน้า (R-1)
- **(ก) เปลี่ยนคำเป็น "เลือกทั้งหน้า" + เพิ่มปุ่ม "เลือกทั้งหมด N ใบที่ตรงตัวกรอง"** (ยิง server)
- (ข) คงไว้แค่ "เลือกทั้งหน้า" อย่างเดียว
- (ค) ไม่แตะ — **ไม่แนะนำ** เพราะเป็นการเปลี่ยนความหมายของปุ่มเงียบ ๆ

### D-5 — การ์ดสถิติ 4 ใบ + ตัวนับชิปทุกตัว (R-4)
- **(ก) ย้ายไป SQL ทั้งหมด** (`groupBy`/`count`) พร้อมกับรอบนี้
- (ข) คงไว้ที่ RSC — **แปลว่ายังต้องดึงทั้งร้านอยู่ดี ⇒ CR นี้จะไม่ได้ผลตามที่ตั้งใจ**

## 5. Out of scope
- ไม่แตะ `/customers` (00057 มีแนวทางของตัวเองแล้ว — มติ Q18)
- ไม่แตะหน้ารายละเอียดออเดอร์
