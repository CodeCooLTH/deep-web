# BRD: ChatBot ปิดการขาย

## 1. บทนำ

แปลง [PRD-sales-closing](PRD-sales-closing.md) เป็น FR ที่ทดสอบได้ พร้อม Acceptance Criteria ระดับที่ QA เขียน test case ได้ตรง ๆ

**Namespace:** ใช้ `FR-SC-xxx` / `AC-SC-xxx` / `BR-SC-xx` แยกจาก `FR-001..030` / `AC-xxx` / `BR-AR-xx` ของเอกสารหลัก 00023 เพื่อกันชนกัน — ไม่ใช่การเขียนทับเอกสารเดิม

**ในขอบเขต:** จำแนกเจตนาซื้อ · สรุปสินค้า+จำนวนแล้ว validate กับ DB · เก็บข้อมูลผู้รับโหมด SHIPPING · ดึงคิวว่างโหมด APPOINTMENT · ตรวจสต็อก/ความจุซ้ำ · สร้างร่าง + การ์ดยืนยัน + เข้าระบบจริง
**นอกขอบเขต:** ดู PRD §10

## 2. Functional Requirements

### 2.1 ร่วมทุกโหมด

#### FR-SC-001: จำแนกเจตนาซื้อ
ต่อยอดจากการเรียก AI ที่มีอยู่แล้วใน `tryChatbotAnswer` — จำแนกในการเรียก **ครั้งเดียวกัน** ไม่เพิ่ม latency/ต้นทุน

- [ ] AC-SC-001-01: ข้อความที่สื่อเจตนาซื้อชัดเจน ("รับค่ะ", "เอาอันนี้", "สั่งซื้อยังไง", "โอนยังไง") → เข้าสถานะ `IntentDetected` ในคำตอบถัดไป
- [ ] AC-SC-001-02: ข้อความทั่วไป ("ขอบคุณค่ะ", "แพงจัง", คำถามข้อมูลสินค้า) → ไม่ทริกเกอร์โหมดปิดการขาย
- [ ] AC-SC-001-03: จำแนกเฉพาะเมื่ออยู่ในเส้นทาง `resolutionLevel=CHATBOT` — ไม่ตัดหน้า Keyword/QnA/Rule (คำตอบที่ร้านตั้งเองชนะเสมอ)
- [ ] AC-SC-001-04: ไม่มั่นใจ → ไม่เข้าโหมด ให้ตอบคำถามตามปกติ (BR-SC-04)
- [ ] AC-SC-001-05: ไม่เพิ่มจำนวนครั้งที่เรียก AI ต่อข้อความ (ตรวจด้วย log ก่อน/หลังเปิดฟีเจอร์เท่ากัน)

#### FR-SC-002: สรุปสินค้า+จำนวน
- [ ] AC-SC-002-01: AI คืน structured `{ productId, qty }[]` เท่านั้น ห้ามคืนราคาหรือชื่อสินค้าอิสระที่ไม่ map กับ productId จริง
- [ ] AC-SC-002-02: ทุก productId ต้องเป็นของร้านนั้นและ `isActive=true` — พบตัวที่ไม่ตรง → **ทั้งชุด**ถือว่าสรุปไม่สำเร็จ (fail-closed มิเรอร์ `ProductNotInShopError`)
- [ ] AC-SC-002-03: สรุปไม่ได้ (บริบทไม่พอ/หลายรุ่นไม่ชัด) → กลับ `Idle` ให้ ChatBot ถามให้ชัดก่อน ไม่เดา
- [ ] AC-SC-002-04: `qty` ต้องเป็นจำนวนเต็มบวก — ไม่ใช่ตัวเลข/ติดลบ/ศูนย์ = สรุปไม่สำเร็จ
- [ ] AC-SC-002-05: ราคาต่อหน่วยดึงจาก `Product.price` **ณ เวลาสร้างร่าง** เสมอ ไม่ใช่ค่าที่เคยพูดถึงในบทสนทนา

#### FR-SC-003: การเลือกโหมด
- [ ] AC-SC-003-01: ทุกชิ้น `SHIPPED` → โหมด SHIPPING
- [ ] AC-SC-003-02: ทุกชิ้น `NO_SHIPPING` **และ** ร้านผ่าน `canUseAppointments` (`kind=BUSINESS` + `vertical=GENERAL`) **และ** มี `ServiceResource` active ≥1 → โหมด APPOINTMENT
- [ ] AC-SC-003-03: ผสมโหมด หรือ `NO_SHIPPING` แต่ร้านไม่เข้าเงื่อนไข → ไม่เข้าโหมดใด กลับ `Idle`
- [ ] AC-SC-003-04: ผลการตัดสินโหมดต้องบันทึกตรวจย้อนหลังได้

#### FR-SC-004: ตรวจสต็อก/ความจุก่อนสร้างร่าง (final gate)
- [ ] AC-SC-004-01: **[SHIPPING]** สินค้าที่ติดตามสต็อก (`stockQty` ไม่ null) ต้องมี `stockQty >= qty` ณ เวลาตรวจ — ไม่พอ → `HandedOff` เหตุผล `OUT_OF_STOCK`
- [ ] AC-SC-004-02: สินค้า untracked (`stockQty = null`) ผ่านเสมอ (พฤติกรรมเดิมของระบบ)
- [ ] AC-SC-004-03: **[APPOINTMENT]** ช่วงที่เลือกต้องตรวจซ้ำว่ายังไม่เต็ม — เต็ม → `HandedOff` เหตุผล `SLOT_FULL` และเสนอช่วงใหม่ได้ถ้ามี
- [ ] AC-SC-004-04: ตรวจครั้งนี้เกิดก่อนสร้างร่างจริง ไม่ใช่ใช้ผลตอนเริ่มบทสนทนา (กันเคส "หมด/เต็มระหว่างคุย")

#### FR-SC-005: สร้างร่าง
- [ ] AC-SC-005-01: ก่อนร้านยืนยัน ต้อง**ไม่มีผลข้างเคียง**: ไม่มีแถวใน `/orders`, ไม่ตัดสต็อก, ไม่แจ้งเตือนลูกค้าว่าออเดอร์ถูกสร้าง
- [ ] AC-SC-005-02: ร่างเก็บข้อมูลครบพอสร้างออเดอร์จริงทันทีเมื่อยืนยัน: รายการ (productId+qty+ราคาจาก DB), ยอดรวม, และที่อยู่ครบ (SHIPPING) หรือช่วงเวลา+ทรัพยากร (APPOINTMENT)
- [ ] AC-SC-005-03: ร่างผูกกับ `conversationId` เพื่อ auto-link `ExternalContact`/`Customer` ตอนยืนยัน (กลไกที่ `createOrder()` รองรับอยู่แล้ว)

#### FR-SC-006: การ์ดยืนยันฝั่งร้าน
- [ ] AC-SC-006-01: การ์ดปรากฏใน `/inbox` ฝั่งร้านเท่านั้น — **ห้ามส่งออกให้ลูกค้าเห็นทาง Messenger/Instagram** (มิเรอร์ constraint เดิมของ `ChatMessage.type=ORDER` ที่ใช้ได้เฉพาะแชท DEEP)
- [ ] AC-SC-006-02: การ์ดแสดงพอให้ตรวจก่อนยืนยัน: รายการ+ราคา+ยอดรวม, ข้อมูลผู้รับ/ช่วงเวลานัด, ที่มา
- [ ] AC-SC-006-03: กดยืนยัน → สร้างออเดอร์จริงสถานะ `PENDING` ตาม state machine เดิม และปรากฏใน `/orders` ทันที
- [ ] AC-SC-006-04: OWNER/ADMIN กดยืนยันได้ — role อื่นตามสิทธิ์ auto-reply เดิม (ห้ามข้ามร้าน)
- [ ] AC-SC-006-05: ไม่กดยืนยัน → ร่างค้างเฉย ๆ ไม่มี auto-expire (A-5) ร้านคุยกับลูกค้าต่อได้ปกติ

#### FR-SC-007: ยกเลิก/เปลี่ยนใจ
- [ ] AC-SC-007-01: เจตนายกเลิก ("ไม่เอาแล้ว", "ขอคิดดูก่อน") → กลับ `Idle` ทันที ไม่สร้างร่าง
- [ ] AC-SC-007-02: ร่างที่สร้างไปแล้วก่อนรู้ว่าเปลี่ยนใจ ต้องไม่ถูกยืนยันอัตโนมัติ และควรทำเครื่องหมายว่ายกเลิกให้ร้านเห็นเหตุผล (ไม่ลบเงียบ)
- [ ] AC-SC-007-03: กลับมาสนใจใหม่ → เริ่มเก็บข้อมูลใหม่ได้ ไม่ผูกกับร่างเก่าที่ยกเลิกแล้ว

### 2.2 โหมด SHIPPING

#### FR-SC-010: ขอข้อมูลผู้รับ
- [ ] AC-SC-010-01: ฟิลด์ที่ต้องครบ: ชื่อผู้รับ, เบอร์โทร, ที่อยู่ (รายละเอียด + ตำบล + อำเภอ + จังหวัด + รหัสไปรษณีย์)
- [ ] AC-SC-010-02: คำถามแรกถามรวมทุกฟิลด์ในครั้งเดียวได้ แต่ต้องรองรับการให้ทีละส่วนเสมอ
- [ ] AC-SC-010-03: ข้อความขอข้อมูลต้องไม่มีข้อมูลลูกค้าคนอื่นปน (เช่น placeholder ที่เป็นชื่อ/เบอร์จริงของคนอื่น)

#### FR-SC-011: ตรวจความครบถ้วนด้วยโค้ด
- [ ] AC-SC-011-01: เบอร์โทรดึงด้วย regex เบอร์ไทย (มิเรอร์ `PHONE_RE` ใน `pii-redact.ts`) — ไม่ส่งข้อความดิบที่มีเบอร์เข้า AI ให้ AI อ่านเอง
- [ ] AC-SC-011-02: ที่อยู่แยกด้วย `splitAddress()` — ต้องมีรหัสไปรษณีย์ 5 หลักในข้อความจึงแยกได้ (ข้อจำกัดของ library)
- [ ] AC-SC-011-03: `splitAddress()` คืน `null` → ถือว่ายังไม่ครบ ไม่เดาค่าใด
- [ ] AC-SC-011-04: ส่งให้ AI **เฉพาะรายชื่อฟิลด์ที่ขาด** (เช่น `["postcode"]`) เพื่อแต่งคำถามถัดไป ไม่ส่งค่าที่ตรวจแล้วหรือข้อความดิบซ้ำ
- [ ] AC-SC-011-05: ครบทุกฟิลด์ → เข้า `ValidatingBeforeDraft` ในรอบถัดไป ไม่ต้องรอ AI ยืนยันซ้ำ

#### FR-SC-012: รองรับข้อมูลทีละส่วน
- [ ] AC-SC-012-01: ชื่อ→เบอร์→ที่อยู่ คนละข้อความ (3 turn) → สะสมทั้ง 3 รวมกัน ไม่ตัดสินจากข้อความล่าสุดเดียว
- [ ] AC-SC-012-02: ให้ซ้ำ/แก้ฟิลด์เดิม (เช่น เปลี่ยนเบอร์) → ค่าล่าสุดชนะเสมอ
- [ ] AC-SC-012-03: ขอบเขตสะสม = ตั้งแต่เข้า `CollectingShippingInfo` จนครบหรือยกเลิก — ไม่ปนกับคำสั่งซื้อครั้งก่อนของลูกค้าคนเดิม

### 2.3 โหมด APPOINTMENT

#### FR-SC-020: ดึงคิวว่างจริง
- [ ] AC-SC-020-01: ช่วงที่เสนอมาจากความจุจริงของ `ServiceResource` ที่เกี่ยวข้อง (ตรรกะเดียวกับ `AppointmentSlotFullError` ของ 00024)
- [ ] AC-SC-020-02: ช่วงที่เต็มแล้วต้องไม่ถูกเสนอตั้งแต่แรก
- [ ] AC-SC-020-03: ร้านไม่มี `ServiceResource` active เลย → ไม่เข้าโหมดนี้ (ตกตาม AC-SC-003-03)
- [ ] AC-SC-020-04: จำนวนตัวเลือกในข้อความเดียวต้องอ่านได้จริงในแชท (ไม่ยัดตารางยาวสิบกว่าช่วง)

#### FR-SC-021: ลูกค้าเลือกช่วงเวลา
- [ ] AC-SC-021-01: AI จับคู่กับ slot ที่ระบบเสนอไปแล้วเท่านั้น — ห้ามสร้างช่วงเวลาใหม่ที่ไม่เคยเสนอ
- [ ] AC-SC-021-02: ตอบกำกวม/เลือกช่วงนอกตัวเลือก → ย้อนถามให้เลือกใหม่จากตัวเลือกเดิม ไม่เดา
- [ ] AC-SC-021-03: หลังเลือกต้องตรวจซ้ำว่ายังว่างจริงก่อนเข้า `ValidatingBeforeDraft`

## 3. Edge Cases

| # | Edge Case | พฤติกรรมที่ต้องการ | AC |
|---|---|---|---|
| 1 | ที่อยู่ไม่ครบ (ขาดรหัสไปรษณีย์) | ระบุเฉพาะฟิลด์ที่ขาด ไม่ขอที่อยู่ใหม่ทั้งหมด | AC-SC-011-03/04 |
| 2 | ให้ข้อมูลทีละส่วนคนละข้อความ | สะสมข้าม turn | AC-SC-012-01 |
| 3 | เปลี่ยนใจกลางทาง | กลับ `Idle`; ร่างที่สร้างแล้วต้องไม่ถูกยืนยันอัตโนมัติ | AC-SC-007-01/02 |
| 4 | ตำบล/อำเภอสะกดผิด | `splitAddress()` ใช้รหัสไปรษณีย์เป็นหลัก จับคู่ไม่ครบ 3 จุด → คืน `null` → ขอยืนยัน/พิมพ์ใหม่ ไม่เดา | AC-SC-011-03 |
| 5 | สินค้าหมดระหว่างคุย | ตรวจสต็อกซ้ำที่ final gate เสมอ | AC-SC-004-01/04 |
| 6 | สั่งหลายรายการ | validate ครบทุกชิ้นจึงสร้างร่าง — ชิ้นใดไม่ผ่าน = ทั้งชุดไม่ผ่าน | AC-SC-002-01/02 |
| 7 | สั่งสินค้าจัดส่ง + บริการนัดพร้อมกัน | ไม่เข้าโหมดอัตโนมัติ (โหมดผสม) | AC-SC-003-03 |
| 8 | ช่วงนัดเต็มระหว่างคุย | ตรวจความจุซ้ำก่อนสร้างร่าง ไม่พอ → handoff | AC-SC-004-03, AC-SC-021-03 |

## 4. NFR — PII (AC ที่ตรวจได้)

- [ ] AC-SC-NFR-01: ทุกข้อความที่ส่งเข้า AI ผ่าน `redactPii()` ก่อนเสมอ — ตรวจได้โดยยิงข้อความทดสอบที่มีเบอร์/ที่อยู่จริงแล้วดู payload ที่ส่งจริง
- [ ] AC-SC-NFR-02: การตัดสิน "ที่อยู่ครบหรือยัง"/"เบอร์ถูกไหม" มาจากโค้ดเท่านั้น — ไม่มี path ที่ AI ตัดสินสองฟิลด์นี้โดยตรง
- [ ] AC-SC-NFR-03: log ของฟีเจอร์นี้ไม่เก็บที่อยู่/เบอร์ดิบเกินความจำเป็น — มาตรฐานเดียวกับ AC-024-04 ของเอกสารหลัก

## 5. Acceptance Criteria สรุป

- [ ] เจตนาซื้อจำแนกได้โดยไม่เพิ่มการเรียก AI และ "ไม่มั่นใจ = ไม่เข้าโหมด"
- [ ] สินค้า/จำนวนมาจาก AI แต่ validate กับ DB เสมอ — หลอน = ไม่ใช้
- [ ] ราคาที่ใช้คำนวณมาจาก `Product.price` ไม่ใช่ตัวเลขจาก AI
- [ ] ที่อยู่/เบอร์ไม่ถูกส่งเข้า AI แบบดิบ — ส่งแค่ชื่อฟิลด์ที่ขาด
- [ ] ก่อนร้านยืนยัน ไม่มีผลข้างเคียงต่อระบบจริง
- [ ] การ์ดร่างอยู่ฝั่งร้านเท่านั้น ไม่ถูกส่งออกช่องทางนอก
- [ ] สต็อก/ความจุตรวจซ้ำ ณ เวลาสร้างร่าง
- [ ] ยกเลิกกลางทางไม่ทิ้งร่างที่ยืนยันได้เองโดยไม่มีใครสั่ง
- [ ] ข้อมูลที่ให้ทีละส่วนสะสมข้าม turn ถูกต้อง
- [ ] ตำบล/อำเภอสะกดผิดหรือขาดรหัสไปรษณีย์ ไม่ถูกเดา
