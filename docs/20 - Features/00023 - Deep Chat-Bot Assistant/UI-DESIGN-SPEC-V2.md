# UI Design Spec V2 — ตอบแชทอัตโนมัติ

## 0. ทำไมต้องมี V2

user ลองใช้จริงบน prod แล้วสะท้อน 3 ข้อ (2026-07-29) — ทุกข้อถูกต้อง:

| ข้อสะท้อน | สาเหตุที่แท้จริง |
|---|---|
| "UX/UI แย่มาก" | การ์ดแยกส่วนที่มีปุ่มบันทึกคนละที่ ผู้ใช้ไม่รู้ว่าอะไรบันทึกแล้วบ้าง |
| "ตอนเลือกสินค้าก็เชย อยากได้ card + รูป" | ใช้ `<select>` ทั้งที่ระบบมีรูปสินค้าอยู่แล้ว — ให้ผู้ใช้จำชื่อสินค้าแทนที่จะให้ดู |
| **"ไหน การเลือก keyword เป็นชั้น ๆ ตาม PRD"** | **ทำแค่คำตอบกลาง ส่วนแยกตามเพจ/โฆษณา/สินค้า มีแต่ตารางแสดงผล เพิ่มไม่ได้เลย** = ขาดคุณค่าหลักของฟีเจอร์ |

**และบั๊กที่เจอพร้อมกัน:** กลุ่มคำ `isActive=false` แต่แผงทดสอบบอกว่า *"ไม่ตรงกลุ่มคำใด"*
→ โยนความผิดให้ผู้ใช้ทั้งที่ระบบรู้คำตอบอยู่แล้วว่า "กลุ่มนี้ปิดอยู่"

---

## 1. ความเข้าใจผิดที่เป็นต้นตอ

V1 มองการตั้งค่าเป็น **"ตาราง 9 ระดับ"** ตามที่ PRD §8 เขียนไว้

แต่ 9 ระดับนั้นคือ **สเปกของ resolver** ไม่ใช่แบบจำลองในหัวของเจ้าของร้าน
ในหัวร้านมันคือประโยคเดียว:

> **"ปกติตอบแบบนี้ — ยกเว้นถ้ามาจากโฆษณาตัวนั้น ให้ตอบอีกแบบ"**

V2 จึงเปลี่ยนคำเรียกทั้งหน้า:

| V1 (ศัพท์ระบบ) | V2 (ภาษาคน) |
|---|---|
| คำตอบกลาง | **คำตอบหลัก** |
| คำตอบเฉพาะ / override | **ข้อยกเว้น** |
| resolution level `KEYWORD_PAGE_AD` | "เมื่อมาจากเพจ X และโฆษณา Y" |
| specificity 6 | ลำดับในบันได (เฉพาะเจาะจงกว่า = อยู่บนกว่า) |

## 2. โครงหน้าใหม่ — บันไดข้อยกเว้น

```
┌──────────────────────────────────────────────────────────────────┐
│  ทดสอบ1                          [○ ปิดอยู่]  ← สวิตช์มีผลทันที  │
│  ตรงเมื่อ: มีคำว่า "ทดสอบ1" หรือ "ทดสอบ2" อยู่ในข้อความ         │
│  [แก้คำตรวจจับ]                                                  │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  คำตอบหลัก                                                        │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ ระบบ Auto-Reply ตอบจ้า                                    │    │
│  └──────────────────────────────────────────────────────────┘    │
│  ใช้เมื่อไม่เข้าข้อยกเว้นด้านล่าง                        22/1000 │
│                                                                   │
│  ─────────────────────────────────────────────────────────────   │
│                                                                   │
│  ข้อยกเว้น (2)                              [+ เพิ่มข้อยกเว้น]   │
│  เฉพาะเจาะจงกว่าอยู่บน — ระบบเลือกอันบนสุดที่เข้าเงื่อนไข        │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ เมื่อมาจาก  [เพจ โช๊คแต่ง] + [โฆษณา โช๊ค 590]            │    │
│  │ ตอบ  "รุ่นนี้มีขนาดเดียว ราคา 590 บาท เก็บปลายทางได้ค่ะ"  │    │
│  │                                          [แก้ไข]  [ลบ]    │    │
│  ├──────────────────────────────────────────────────────────┤    │
│  │ เมื่อมาจาก  [เพจ โช๊คแต่ง]                                │    │
│  │ ตอบ  "รับโช๊ครุ่นไหนดีคะ แจ้งรุ่นรถและปีรถได้เลยค่ะ"      │    │
│  │                                          [แก้ไข]  [ลบ]    │    │
│  └──────────────────────────────────────────────────────────┘    │
│         ↓ ไม่เข้าข้อไหนเลย → ใช้คำตอบหลัก                        │
└──────────────────────────────────────────────────────────────────┘
```

**ทำไมเรียงจากเฉพาะเจาะจงมากลงมาน้อย:** เพราะนั่นคือลำดับที่ระบบตัดสินจริง
ผู้ใช้อ่านจากบนลงล่างแล้วเห็น "ทางเดินของการตัดสิน" ตรงกับสิ่งที่เกิดขึ้น ไม่ต้องจำกฎ

**ท้ายบันไดมีลูกศรชี้กลับไปคำตอบหลัก** — ทำให้ fallback เป็นสิ่งที่ *เห็น* ไม่ใช่สิ่งที่ต้องรู้

### ทำไมไม่ใส่เลข 1/2/3
เลขจะสื่อว่า "ทำตามลำดับ" แต่ความจริงคือ "เลือกอันแรกที่เข้าเงื่อนไข"
ตำแหน่งบน-ล่าง + ลูกศรท้ายบันได สื่อความหมายนี้ได้ตรงกว่าโดยไม่ต้องมีตัวเลข

## 3. เพิ่มข้อยกเว้น — sheet เดียวจบ

```
┌────────────────────────────────────────────┐
│ เพิ่มข้อยกเว้น                         [×] │
├────────────────────────────────────────────┤
│ ใช้ข้อยกเว้นนี้เมื่อลูกค้า...              │
│                                             │
│ ☐ มาจากเพจ                                  │
│   └ [โช๊คแต่ง ▾]                            │
│                                             │
│ ☐ กดมาจากโฆษณา                              │
│   └ ┌────────────────────────────────────┐  │
│     │ ◉ โช๊ค 590 · ทัก 24 ครั้ง          │  │
│     │ ○ สายยาง 390 · ทัก 8 ครั้ง         │  │
│     └────────────────────────────────────┘  │
│     เลือกจากโฆษณาที่เคยมีลูกค้าทักเข้ามาจริง │
│                                             │
│ ☐ สนใจสินค้า                                │
│   └ ┌──────────┬──────────┬──────────┐     │
│     │ [รูป]    │ [รูป]    │ [รูป]    │     │
│     │ โช๊ค 320 │ โช๊ค 350 │ สายยาง   │     │
│     │ ฿390     │ ฿590     │ ฿250     │     │
│     └──────────┴──────────┴──────────┘     │
│     [ค้นหาสินค้า...]                        │
│                                             │
│ ─────────────────────────────────────────  │
│ ตอบว่า                                      │
│ ┌────────────────────────────────────────┐ │
│ │                                         │ │
│ └────────────────────────────────────────┘ │
│                                             │
│ 💬 ข้อยกเว้นนี้จะถูกใช้เมื่อลูกค้าทักจาก    │
│    เพจ "โช๊คแต่ง" และกดมาจากโฆษณา          │
│    "โช๊ค 590" — จะอยู่เหนือข้อยกเว้นอื่น   │
│    ทั้งหมด                                  │
│                                             │
│              [ยกเลิก]   [เพิ่มข้อยกเว้น]   │
└────────────────────────────────────────────┘
```

**หัวใจคือบรรทัดสรุปก่อนกดยืนยัน** — บอกเป็นประโยคภาษาคนว่าข้อยกเว้นนี้จะทำงานเมื่อไหร่
และจะไปอยู่ตำแหน่งไหนในบันได ผู้ใช้ไม่ต้องเข้าใจคำว่า specificity เลย

**เลือกสินค้าเป็นการ์ดมีรูป + ราคา** (user request) — เพราะร้านจำสินค้าจากรูป ไม่ใช่จากชื่อ
โดยเฉพาะร้านอะไหล่ที่ชื่อสินค้าคล้ายกันหมด

**เลือกโฆษณาแสดงจำนวนครั้งที่มีคนทัก** — ช่วยให้ร้านรู้ว่าตัวไหนคุ้มค่าตั้งค่าก่อน

## 4. แก้เรื่องการบันทึก

**V1:** แต่ละการ์ดมีปุ่ม "บันทึก" ของตัวเอง — ไม่รู้ว่าอะไรบันทึกแล้ว
**V2:** แถบบันทึกลอยด้านล่าง โผล่เมื่อมีการแก้ และบอกว่าแก้อะไรไปบ้าง

```
        ┌──────────────────────────────────────────────┐
        │ แก้ไข 2 อย่าง: ชื่อกลุ่ม, คำตอบหลัก           │
        │                    [ยกเลิก]  [บันทึก]        │
        └──────────────────────────────────────────────┘
```

**ยกเว้นสวิตช์เปิด/ปิด — มีผลทันทีไม่ต้องกดบันทึก** เพราะไม่มีใครคาดหวังว่าสวิตช์จะต้องยืนยัน
(นี่คือต้นเหตุที่ user เจอว่า "ตั้งค่าแล้วไม่ตอบ")

## 5. แผงทดสอบต้องบอกความจริง

**V1 บอก:** "ไม่ตรงกลุ่มคำใด" ← โกหก คำตรงทุกตัวอักษร
**V2 ต้องบอก:**

```
┌────────────────────────────────────────┐
│ ⚠ กลุ่มคำนี้ปิดอยู่                    │
│ คำที่ตั้งไว้ตรงกับข้อความนี้ แต่ระบบ   │
│ ยังไม่นำมาใช้เพราะกลุ่มยังไม่เปิด      │
│                    [เปิดใช้งานเลย]     │
└────────────────────────────────────────┘
```

หลักการ: **ถ้าระบบรู้สาเหตุ ต้องบอกสาเหตุ ไม่ใช่บอกอาการ** — และถ้าแก้ได้ในคลิกเดียว ให้ปุ่มไปเลย

เคสอื่นที่ต้องบอกให้ตรงเช่นกัน:
| สถานการณ์ | ต้องบอกว่า |
|---|---|
| ร้านปิดสวิตช์ใหญ่ | "ระบบตอบอัตโนมัติปิดอยู่ทั้งร้าน" + ปุ่มเปิด |
| ยังไม่มีคำตอบหลักและไม่เข้าข้อยกเว้น | "ยังไม่ได้ตั้งคำตอบหลัก — ระบบจะส่งต่อพนักงาน" |
| เข้าข้อยกเว้น | บอกว่าเข้าข้อไหน และทำไมข้ออื่นแพ้ |

---

## 6. สิ่งที่ไม่เปลี่ยนจาก V1

- สี/component = Paces ล้วน (`#236dc9`) ห้าม arbitrary value
- ห้าม emoji ใน UI (ที่เห็นในเอกสารนี้เป็น marker ของเอกสาร ไม่ใช่ของ UI)
- toast = `pacesToast` · dialog ยืนยัน = Sweet Alerts
- ไม่มี AI ในเฟสนี้
- โครง 2 หน้า (รายการ → แก้ไข)

## 7. ลำดับการทำ

| ลำดับ | งาน | เหตุผล |
|---|---|---|
| 1 | สวิตช์มีผลทันที + แผงทดสอบบอกสาเหตุจริง | บั๊กที่ทำให้ user เข้าใจผิดว่าระบบพัง |
| 2 | บันไดข้อยกเว้น + sheet เพิ่มข้อยกเว้น | คุณค่าหลักที่ยังขาด |
| 3 | ตัวเลือกสินค้าเป็นการ์ดมีรูป | user request ตรง |
| 4 | แถบบันทึกลอย | เก็บงานเรื่องความสับสน |
