# PRD: ระบบนัดหมายวันเข้าใช้บริการ (Service Appointment Booking)

---

## Executive Summary

ร้านที่ขาย **บริการ** (นวด/สปา, ช่างซ่อมนอกสถานที่, สตูดิโอถ่ายรูป, จัดเลี้ยง, สอนพิเศษ, เช่าอุปกรณ์) ทุกวันนี้ใช้ Deep สร้างออเดอร์ได้ แต่ **ไม่มีที่เก็บ "วันไหน กี่โมง ใครให้บริการ"** — ร้านต้องจดใส่สมุด/Google Calendar/แชท แยกจากออเดอร์ ผลคือข้อมูลนัดหมายกับข้อมูลการเงินอยู่คนละที่ ลูกค้าจำวันผิด ร้านรับคิวชนกันเอง และประวัติการนัดไม่เคยกลายเป็นสินทรัพย์ของร้าน

ฟีเจอร์นี้เพิ่ม **วัน/ช่วงเวลาเข้าใช้บริการ ผูกติดกับออเดอร์โดยตรง** ให้ **บัญชีธุรกิจ (Business profile) ที่มีประเภทกิจการเป็น "สินค้าและบริการ"** พร้อมปฏิทินคิวที่ **กันจองเกินความจุได้จริงในระดับฐานข้อมูล** โดยยืมโครงสร้าง "การจอง = ออเดอร์" ที่พิสูจน์แล้วบน production จาก feature 00017 (Lodging Vertical) มาใช้ซ้ำแทนการสร้างระบบใหม่

ต่างจากบ้านพักตรงที่ **ร้านตั้งได้เองว่าทรัพยากรแต่ละหน่วยรับได้กี่คิวพร้อมกัน** — ห้องนวดรับทีละ 1 คน แต่คลาสโยคะรับได้ 8 คนในรอบเดียวกัน ระบบต้องนับที่ว่างให้ถูกต้องแม้ลูกค้าหลายคนกดจองพร้อมกันในเสี้ยววินาทีเดียว

รองรับ **2 รูปแบบการนัด** ตามที่ร้านต้องการ: **โหมด A** ร้านเลือกวันให้ลูกค้าเลยตอนสร้างออเดอร์ (เคส walk-in / นัดทางโทรศัพท์ / คุยจบในแชทแล้วร้านคีย์เอง) และ **โหมด B** ร้านส่งลิงก์ออเดอร์ให้ลูกค้า ลูกค้า login เข้ามาตรวจสอบและยืนยันนัดด้วยตัวเอง — โดยโหมด B **ไม่ต้องสร้างกลไก login ใหม่เลย** เพราะ feature 00015 (Order Claim & Forced Login) บังคับ login บนหน้า `/o/{token}` ไปแล้วทุกกรณี สิ่งที่เพิ่มคือส่วนแสดง/ยืนยันนัดหลังผ่าน login เท่านั้น

ผลลัพธ์ทางธุรกิจ: ร้านบริการเลิกใช้สมุดจดคู่ขนาน, ลดคิวชน/ลูกค้ามาผิดวัน, และทุกนัดกลายเป็นออเดอร์จริงที่ไหลเข้า Trust Score + ประวัติลูกค้า (feature 00014) โดยอัตโนมัติ

## 1. Business Goals & KPIs

### 1.1 เป้าหมายทางธุรกิจ

| เป้าหมาย | รายละเอียด |
|----------|-----------|
| **ปิดช่องว่างของร้านขายบริการ** | Deep รองรับร้านขายสินค้าและร้านบ้านพักได้ดีแล้ว แต่ร้านที่ขาย "เวลา" ยังไม่มีเครื่องมือ — ฟีเจอร์นี้ทำให้ Deep ใช้ได้จริงกับธุรกิจบริการโดยไม่ต้องแยกไปใช้แอปจองอื่น |
| **นัดหมายกับออเดอร์เป็นของชิ้นเดียวกัน** | วันนัดอยู่บนออเดอร์ ไม่ใช่ตารางแยก — ร้านเห็นเงิน/ลูกค้า/วันนัดในหน้าจอเดียว และนัดทุกครั้งกลายเป็นประวัติที่วัดผลได้ |
| **กันจองเกินความจุได้จริง ไม่ใช่แค่เตือน** | การจองที่เกินจำนวนคิวที่ร้านตั้งไว้ต้องถูกปฏิเสธในระดับฐานข้อมูล แม้กดพร้อมกัน — ต่อยอดจากกลไกกันช่วงเวลาซ้อนที่ใช้งานจริงบน production แล้วจาก feature 00017 |
| **ยืดหยุ่นพอที่ธุรกิจบริการหลากรูปแบบใช้ได้** | ร้านตั้งเองว่าแต่ละทรัพยากรรับได้กี่คิวพร้อมกัน — ครอบทั้งบริการตัวต่อตัว (1 คิว) และบริการแบบกลุ่ม/คลาส (หลายคิว) ด้วยระบบเดียว |
| **ลดต้นทุนพัฒนาโดยใช้ของเดิม** | reuse: ออเดอร์เป็นตัวเก็บการนัด (ไม่สร้างตารางจองแยก), forced login ของ 00015, ลูกค้ากลางของ 00014, แชทของ 00011/00018 เป็นช่องแจ้งเตือน — ลด surface ใหม่ให้เหลือน้อยที่สุด |
| **ไม่กระทบร้านเดิมแม้แต่น้อย** | ร้านขายสินค้าและร้าน `vertical = LODGING` ต้องไม่เห็นความเปลี่ยนแปลงใด ๆ (zero-regression) |

### 1.2 ตัวชี้วัดความสำเร็จ (KPIs)

| KPI | คำอธิบาย | เป้าหมาย |
|-----|----------|---------|
| **Service-Order Booking Attach Rate** | % ของออเดอร์ `type = SERVICE` ที่มีวันนัดผูกอยู่ (`serviceStart` ไม่ null) | ≥ 60% ภายใน 60 วันหลัง launch |
| **Over-Capacity Incidents** | จำนวนเคสที่ทรัพยากรหน่วยเดียวมีนัดในช่วงเวลาทับกันเกินจำนวนคิวที่ร้านตั้งไว้ | 0 (บังคับด้วย DB constraint) |
| **Buyer Confirm Rate (โหมด B)** | % ของนัดที่ส่งลิงก์ให้ลูกค้าแล้วลูกค้า login เข้ามายืนยันสำเร็จ | ≥ 70% ภายใน 60 วัน |
| **No-Show Rate** | % ของนัดที่ถูกทำเครื่องหมาย "ไม่มาตามนัด" ต่อนัดทั้งหมด | ติดตามเป็น baseline (ไม่ตั้งเป้าตายตัวรอบแรก) |
| **Reschedule Rate** | % ของนัดที่ถูกเลื่อนอย่างน้อย 1 ครั้ง | ติดตามเป็น baseline — ใช้ประเมินว่าโหมด B2 (ลูกค้าเลือกวันเอง) คุ้มลงทุนใน phase 2 หรือไม่ |

## 2. User Personas (กลุ่มผู้ใช้งาน)

### 2.1 เจ้าของร้านบริการรายเล็ก (Solo Service Owner)

**ข้อมูลพื้นฐาน:**
- ร้านนวด/ร้านทำเล็บ/ช่างซ่อมแอร์/ครูสอนพิเศษ ที่ทำเองคนเดียวหรือมีลูกน้อง 1-2 คน
- รับงานผ่านแชท Facebook/LINE เป็นหลัก (Deep Chat feature 00011/00018 รองรับอยู่แล้ว)
- ใช้มือถือเป็นเครื่องมือทำงานหลัก ไม่ค่อยเปิดคอมพิวเตอร์

**เป้าหมาย:**
- รู้ว่าวันนี้/พรุ่งนี้มีคิวอะไรบ้าง กี่โมง ลูกค้าคือใคร โดยไม่ต้องเปิดหลายแอป
- ไม่รับคิวชนกันเอง

**ความต้องการ:**
- คีย์นัดพร้อมออเดอร์ได้ในหน้าจอเดียว จบในไม่กี่วินาที ระหว่างคุยกับลูกค้าอยู่
- เห็นปฏิทินคิวแบบวัน/สัปดาห์บนมือถือ

**จุดปวด (Pain Points):**
- จดคิวในสมุด/โน้ตมือถือ แล้วลืมย้ายมาลงออเดอร์ → เก็บเงินตกหล่น
- รับคิวชนเพราะจำไม่ได้ว่ารับใครไว้แล้ว → ต้องโทรขอเลื่อน เสียความน่าเชื่อถือ
- ลูกค้าถามย้อนว่า "นัดวันไหนนะ" ต้องเลื่อนหาแชทเก่า

### 2.2 พนักงาน/แอดมินร้าน (Shop Staff)

**ข้อมูลพื้นฐาน:**
- พนักงานที่ถูกเชิญเข้าร้านผ่าน ShopMember (feature 00008/00012) ทำหน้าที่ตอบแชทและคีย์ออเดอร์
- ไม่ใช่เจ้าของ อาจไม่มีสิทธิ์ดูข้อมูลการเงิน (`staffCanViewFinance`)

**เป้าหมาย:**
- รับนัดแทนเจ้าของได้ถูกต้อง ไม่จองทับคิวที่มีอยู่

**ความต้องการ:**
- เห็นช่องว่างที่จองได้ทันทีตอนคีย์ ไม่ต้องเดาแล้วไปถามเจ้าของ

**จุดปวด (Pain Points):**
- ไม่รู้ว่าเจ้าของรับคิวอะไรไว้บ้าง ทำให้รับซ้อน
- ไม่กล้าเลื่อน/ยกเลิกนัดเพราะไม่รู้ว่ามีสิทธิ์หรือไม่

### 2.3 ลูกค้าผู้ใช้บริการ (Service Customer)

**ข้อมูลพื้นฐาน:**
- ได้ลิงก์ออเดอร์ `/o/{token}` จากร้านผ่านแชทหรือ SMS
- ต้อง login + ยืนยันตัวตนด้วย OTP เบอร์ตัวเองตามกติกา feature 00015

**เป้าหมาย:**
- รู้แน่ชัดว่านัดวันไหน กี่โมง ที่ไหน และมีหลักฐานยืนยันที่ย้อนกลับมาดูได้

**ความต้องการ:**
- เปิดลิงก์แล้วเห็นวันนัดชัดเจน กดยืนยันได้ในคลิกเดียว
- ถ้าติดธุระ ขอเลื่อนได้โดยไม่ต้องโทร

**จุดปวด (Pain Points):**
- นัดอยู่ในแชทที่ไหลหายไปแล้ว หาไม่เจอ
- ไม่แน่ใจว่าร้านจดนัดไว้จริงหรือเปล่า

### 2.4 ผู้ดูแลแพลตฟอร์ม Deep (Platform Admin)

**ข้อมูลพื้นฐาน:**
- ดูแลภาพรวมการใช้งานบน `admin.*`

**เป้าหมาย:**
- รู้ว่าฟีเจอร์นี้ถูกใช้จริงแค่ไหน และไม่ทำให้ข้อมูลออเดอร์เดิมเพี้ยน

**ความต้องการ:**
- ตัวเลข adoption + จำนวนเคสจองชน (ต้องเป็นศูนย์)

**จุดปวด (Pain Points):**
- ฟีเจอร์ที่เพิ่ม field ลงตารางกลางอย่าง Order มีความเสี่ยงกระทบร้านที่ไม่ได้ใช้

## 3. Business Requirements

### 3.1 ทรัพยากรที่จองได้ (Bookable Resource)

**ความต้องการ:**
- ร้านต้องนิยาม "สิ่งที่ลูกค้าจองเวลาเข้ามาใช้" ได้ก่อน เช่น ช่างแต่ละคน, เตียงนวดแต่ละเตียง, ห้องสตูดิโอ, คลาสเรียน, ชุดอุปกรณ์ที่ให้เช่า
- ตั้งชื่อ, คำอธิบาย, ระยะเวลาบริการมาตรฐาน (เช่น 60 นาที), **จำนวนคิวที่รับได้พร้อมกัน**, เปิด/ปิดการใช้งานได้

**Business Rules:**
- ร้านกำหนดได้เองว่าทรัพยากรแต่ละหน่วยรับได้กี่นัดที่ช่วงเวลาทับกัน — ค่าเริ่มต้นคือ 1
- จำนวนคิวต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป
- นัดที่ทำให้ช่วงเวลาใดก็ตามมีจำนวนนัดเกินค่าที่ตั้งไว้ ต้องถูกปฏิเสธ
- ลดจำนวนคิวลงต่ำกว่าจำนวนนัดที่จองไว้แล้วในบางช่วงเวลาไม่ได้ — ระบบต้องปฏิเสธพร้อมบอกว่าติดช่วงไหน
- ปิดการใช้งานทรัพยากร = ไม่รับนัดใหม่ แต่นัดเดิมยังอยู่ครบ
- ลบทรัพยากรที่มีนัดผูกอยู่ไม่ได้

**เหตุผล:**
- ธุรกิจบริการมีทั้งแบบตัวต่อตัว (นวด ซ่อม ถ่ายรูป) และแบบกลุ่ม (คลาสเรียน ทัวร์ จัดเลี้ยง) — บังคับให้ทุกอย่างเป็น 1 คิวจะทำให้ร้านกลุ่มหลังต้องสร้างทรัพยากรซ้ำ ๆ 8 หน่วยที่มีชื่อเหมือนกัน ซึ่งใช้งานจริงไม่ไหว
- ค่าเริ่มต้น 1 ทำให้ร้านที่ไม่สนใจเรื่องนี้ไม่ต้องตั้งค่าอะไรเลย
- แยก "หยุดรับคิว" ออกจาก "ลบประวัติ" ตามบทเรียนเดียวกับ `Room.isActive`

### 3.2 การนัดหมายผูกกับออเดอร์

**ความต้องการ:**
- ทุกการนัดต้องเป็น **ออเดอร์** ไม่ใช่ระเบียนแยก — ได้ลิงก์สาธารณะ, เลขออเดอร์, สลิป, รีวิว, Trust Score, ประวัติลูกค้า มาใช้ซ้ำทั้งหมด
- ออเดอร์เก็บ: ทรัพยากรที่จอง, เวลาเริ่ม, เวลาสิ้นสุด, สถานะการนัด

**Business Rules:**
- ใช้ `Order.type = "SERVICE"` ที่มีอยู่แล้วในระบบ — ไม่สร้างชนิดออเดอร์ใหม่
- ฟิลด์กลุ่มนัดหมายเป็น NULL เสมอสำหรับออเดอร์สินค้าปกติและออเดอร์ของร้านบ้านพัก
- เวลาเริ่มต้องมาก่อนเวลาสิ้นสุดเสมอ
- จำนวนนัดที่ช่วงเวลาทับกันของทรัพยากรหนึ่งหน่วย ต้องไม่เกินจำนวนคิวที่ร้านตั้งไว้ นับเฉพาะนัดที่ยังไม่ถูกยกเลิก

**เหตุผล:**
- feature 00017 พิสูจน์บน production แล้วว่ารูปแบบ "การจอง = ออเดอร์" ใช้ได้จริง และประหยัดงานมหาศาลเทียบกับการทำตารางจองแยกที่ต้องต่อท่อ Trust/รีวิว/ลูกค้าใหม่ทั้งหมด

### 3.3 โหมด A — ร้านเลือกวันให้เลย (Seller-assigned)

**ความต้องการ:**
- ร้านสร้างออเดอร์ที่หน้า POS แล้วเลือกทรัพยากร + วัน + เวลาได้ในฟอร์มเดียวกัน จบในครั้งเดียว
- ตอนเลือก ระบบต้องแสดงให้เห็นว่าช่วงไหนเต็มแล้ว

**Business Rules:**
- ร้านเลือกเวลาที่ทำให้ทรัพยากรนั้นเต็มเกินจำนวนคิวที่ตั้งไว้ไม่ได้ — ระบบปฏิเสธพร้อมบอกว่าเต็มที่ช่วงไหน
- ร้านนัดย้อนหลังได้ (เคสคีย์ตามหลังจากที่ให้บริการไปแล้ว) แต่ต้องมีคำเตือนให้เห็นชัด
- เจ้าของร้านและพนักงานที่มีสิทธิ์จัดการออเดอร์เป็นผู้ตั้ง/แก้วันนัดได้

**เหตุผล:**
- เป็นเคสที่เกิดบ่อยที่สุดของร้านไทย — ลูกค้าโทรมาหรือทักแชท ร้านตกลงวันจบแล้วค่อยคีย์
- ไม่เพิ่มขั้นตอนให้ร้านที่ทำงานเร็วอยู่แล้ว

### 3.4 โหมด B — ส่งลิงก์ให้ลูกค้า login เข้ามาตรวจ (Buyer-confirmed)

**ความต้องการ:**
- ร้านสร้างออเดอร์แล้วส่งลิงก์ `/o/{token}` ให้ลูกค้า
- ลูกค้า login แล้วเห็นวันนัดชัดเจน กดยืนยันหรือขอเลื่อนได้

**Business Rules:**
- การเข้าถึงหน้าออเดอร์ใช้กติกาของ feature 00015 ทั้งหมด **โดยไม่แก้ไข** — บังคับ login, ตัดสินสิทธิ์จากเจ้าของออเดอร์, OTP เบอร์ตัวเองให้ตรงกับเบอร์ในออเดอร์, ไม่มีการดูแบบ guest
- ลูกค้าเห็นและกระทำกับนัดได้เฉพาะออเดอร์ของตัวเองเท่านั้น
- การยืนยันนัดของลูกค้าเป็นการกระทำของบัญชีจริงเสมอ มีบันทึกว่าใครยืนยันเมื่อไร
- ลูกค้าขอเลื่อนได้ แต่ **ไม่ใช่การเลื่อนอัตโนมัติ** — เป็นคำขอที่ร้านต้องอนุมัติ

**เหตุผล:**
- forced login มีอยู่แล้วบน production ทำให้โหมดนี้ได้ความปลอดภัยระดับเดียวกับการยืนยันออเดอร์ฟรี ๆ
- ให้ร้านเป็นผู้ตัดสินใจสุดท้ายเรื่องคิว ป้องกันลูกค้าเลื่อนไปทับคิวคนอื่นหรือเลื่อนกระชั้นชิดจนร้านเสียหาย

**สถานะการนัดที่ต้องรองรับ:**

| สถานะ | ชื่อภาษาไทย | คำอธิบาย | การใช้งาน |
|-------|------------|----------|----------|
| **SCHEDULED** | นัดแล้ว | มีวันนัดผูกกับออเดอร์ ยังไม่ถึงวัน | ค่าเริ่มต้นเมื่อร้านตั้งวันนัด |
| **CONFIRMED_BY_BUYER** | ลูกค้ายืนยันแล้ว | ลูกค้า login เข้ามากดยืนยันนัดด้วยตัวเอง | โหมด B เท่านั้น |
| **RESCHEDULE_REQUESTED** | ลูกค้าขอเลื่อน | ลูกค้าส่งคำขอเลื่อน รอร้านตัดสิน | โหมด B เท่านั้น |
| **COMPLETED** | ให้บริการแล้ว | ร้านทำเครื่องหมายว่าให้บริการเสร็จสิ้น | ร้านกดหลังถึงวันนัด |
| **NO_SHOW** | ไม่มาตามนัด | ลูกค้าไม่มาและไม่แจ้งล่วงหน้า | ร้านกด — บันทึกไว้เป็นข้อมูล ไม่ตัดคะแนน |

### 3.5 การเลื่อนนัดและการยกเลิก

**ความต้องการ:**
- ร้านเลื่อนนัดได้ตลอดเวลาก่อนถึงวันนัด
- ลูกค้าขอเลื่อนได้ ร้านเป็นผู้อนุมัติ

**Business Rules:**
- การเลื่อนต้องผ่านการตรวจความจุของเวลาใหม่เช่นเดียวกับการสร้างนัด
- นัดที่ถูกยกเลิกไม่กันคิวอีกต่อไป — ช่องเวลานั้นกลับมาว่างทันที
- ประวัติการเลื่อนถูกบันทึกไว้ ไม่ทับของเดิม

**เหตุผล:**
- ธุรกิจบริการมีการเลื่อนเป็นเรื่องปกติ ระบบที่เลื่อนไม่ได้จะถูกเลิกใช้ทันที
- ประวัติการเลื่อนเป็นข้อมูลตั้งต้นสำหรับนโยบายลูกค้าประจำ/ลูกค้ามีปัญหาในอนาคต

### 3.6 การแจ้งเตือน

**ความต้องการ:**
- อีกฝ่ายต้องรู้เมื่อมีการตั้ง/ยืนยัน/เลื่อน/ยกเลิกนัด

**Business Rules:**
- ใช้ช่องทางแชทภายในของ Deep เป็นหลัก **ไม่ใช้ SMS โดยอัตโนมัติ**
- ถ้าร้านต้องการส่ง SMS ต้องเป็นการกดส่งเองและหักเครดิตตามกลไกเดิม (฿1/ครั้ง จาก SellerWallet)

**เหตุผล:**
- SMS อัตโนมัติทุกนัดจะกลายเป็นต้นทุนที่ร้านไม่ได้ตั้งใจจ่าย และเป็นเหตุให้ร้านเลิกใช้ฟีเจอร์

## 4. Business Rules & Constraints

### 4.1 กฎทางธุรกิจหลัก

| กฎ | คำอธิบาย |
|----|----------|
| **เฉพาะบัญชีธุรกิจ ประเภทสินค้าและบริการ** | ฟีเจอร์นี้เปิดให้ร้านที่เป็นบัญชีธุรกิจ (`kind = BUSINESS`) และมีประเภทกิจการ `vertical = GENERAL` เท่านั้น ร้าน `LODGING` ใช้ปฏิทินบ้านพักของ feature 00017 ต่อไป ห้ามมีสองระบบซ้อนกันในร้านเดียว |
| **การจอง = ออเดอร์** | ไม่มีตารางการจองแยก ทุกนัดคือออเดอร์ `type = SERVICE` |
| **ห้ามเกินความจุที่ร้านตั้งไว้** | จำนวนนัดที่ช่วงเวลาทับกันของทรัพยากรหนึ่งหน่วย ต้องไม่เกินจำนวนคิวที่ร้านกำหนด บังคับที่ระดับฐานข้อมูล ไม่ใช่แค่ตรวจในแอป |
| **นัดที่ยกเลิกไม่กันคิว** | เฉพาะนัดที่ยังไม่ถูกยกเลิกเท่านั้นที่นับเข้าความจุ |
| **ร้านเป็นผู้ตัดสินสุดท้าย** | ลูกค้า "ขอ" เลื่อนได้ แต่ไม่มีสิทธิ์เปลี่ยนวันนัดเองโดยตรง |
| **ไม่ตัดคะแนนความน่าเชื่อถือ** | การไม่มาตามนัดถูกบันทึกเป็นข้อมูล แต่ไม่หัก Trust Score ตามหลัก MVP ที่คะแนนมีแต่ขึ้น |
| **ไม่แตะกติกา login** | โหมด B ใช้กติกาการเข้าถึงของ feature 00015 ตามที่เป็นอยู่ ห้ามออกแบบ flow ยืนยันตัวตนใหม่ |
| **ไม่กระทบออเดอร์เดิม** | ออเดอร์ที่ไม่มีวันนัดต้องทำงานเหมือนเดิมทุกประการ ฟิลด์ใหม่ทั้งหมดยอมให้ว่างได้ |

### 4.2 ข้อจำกัดทางธุรกิจ

| ข้อจำกัด | รายละเอียด |
|---------|-----------|
| **ไม่มีการจองสาธารณะใน phase 1** | ลูกค้าที่ยังไม่มีออเดอร์ จองคิวเองจากหน้าร้านสาธารณะไม่ได้ — ต้องมีออเดอร์ที่ร้านสร้างก่อนเสมอ |
| **ความจุคงที่ต่อทรัพยากร** | จำนวนคิวที่รับได้เป็นค่าเดียวตลอด ไม่แปรตามวันหรือช่วงเวลา (เช่น ตั้ง "เสาร์-อาทิตย์รับ 10 คิว วันธรรมดารับ 5" ไม่ได้) |
| **มัดจำเป็นยอดที่บันทึก ไม่ใช่ระบบรับเงิน** | เก็บมัดจำได้ (FR-RSV-12 — ตั้งค่าเริ่มต้นที่ทรัพยากร แก้สดต่อออเดอร์ได้) แต่ระบบแค่บันทึกยอดและแสดงให้ลูกค้าเห็นว่าเหลือจ่ายหน้างานอีกเท่าไร **ไม่ติดตามสถานะการจ่าย ไม่มีการแนบสลิป และไม่กั้นการล็อกวัน** — ต่างจาก feature 00017 ที่การจองรอสลิปก่อนยืนยัน (ขอบเขตนี้แก้เมื่อ 2026-07-31 จากเดิมที่ระบุว่าไม่มีระบบมัดจำเลย) |
| 🛑 **Known Gap (บันทึกไว้ 2026-08-08) — ทรงเต็มของมัดจำต้องเพิ่มอะไร** | ทุก surface ที่แสดงมัดจำ (รวมแถบสถานะในห้องแชท — ดู `chat-service-progress.ts`) เขียนได้แค่ "มัดจำที่ตกลงไว้ ฿X" เพราะไม่มีคอลัมน์บอกว่าจ่ายแล้วหรือยัง — ถ้าจะทำให้เต็มรูปต้องเพิ่ม: (1) คอลัมน์ `depositReceivedAt` (มิเรอร์ `OrderShipment.codReceivedAt` ที่มีอยู่แล้ว) (2) ฟิลด์ผู้กดรับมัดจำ (3) ปุ่ม/action ยืนยันรับมัดจำที่หน้าออเดอร์ (4) ตัดสินใจว่าต้องแนบสลิปเหมือน feature 00017 หรือไม่ — ยังไม่มีข้อไหนถูกออกแบบ |
| 🛑 **Known Gap (บันทึกไว้ 2026-08-08) — การ์ดออเดอร์บริการในห้องแชทกดไม่ได้** | แถบสถานะออเดอร์ในห้องแชท (`OrderProgressBar.tsx`) แสดงการ์ดออเดอร์บริการเป็น**อ่านอย่างเดียว** (ไม่มี stretched-link/`onClick` เหมือนการ์ดออเดอร์ขนส่ง) เพราะระบบหน้าต่างร่างในแชท (`DraftOrderProvider`) รองรับแค่ `DraftKind: 'ORDER' | 'SHIPMENT'` — ยังไม่มีชนิดสำหรับเปิดดู/แก้นัด ต้องออกแบบ `DraftKind: 'APPOINTMENT'` ก่อน (ผ่าน `safepay-ux` ตาม Hard Rule 8) ถึงจะทำให้กดได้ |
| **เวลาไทยเท่านั้น** | ทุกวันเวลาอยู่บน timezone ไทย แสดงผลเป็น พ.ศ. ตาม convention ของโครงการ |

### 4.3 เคสที่ระบบต้องปฏิเสธ

- เวลาสิ้นสุดมาก่อนหรือเท่ากับเวลาเริ่ม
- ทรัพยากรที่เลือกไม่ใช่ของร้านตัวเอง
- ทรัพยากรที่ถูกปิดการใช้งาน
- ช่วงเวลาที่ทำให้ทรัพยากรนั้นมีนัดเกินจำนวนคิวที่ตั้งไว้ (ยกเว้นนัดที่ยกเลิกแล้ว ซึ่งไม่นับ)
- จำนวนคิวที่น้อยกว่า 1 หรือไม่ใช่จำนวนเต็ม
- การลดจำนวนคิวลงต่ำกว่าจำนวนนัดที่จองไว้แล้วในบางช่วงเวลา
- ร้านที่ไม่ใช่บัญชีธุรกิจ หรือร้าน `vertical = LODGING` พยายามใช้ฟีเจอร์นี้
- ลูกค้าพยายามกระทำกับนัดของออเดอร์ที่ไม่ใช่ของตน

## 5. Out of Scope (นอกขอบเขต)

| หัวข้อ | คำอธิบาย |
|--------|----------|
| **หน้าจองสาธารณะให้ลูกค้าจองเอง** | ลูกค้าเลือกวันจากปฏิทินของร้านโดยที่ยังไม่มีออเดอร์ = phase ถัดไป ต้องออกแบบ availability publishing + การกันช่องชั่วคราวเพิ่ม |
| **ความจุที่แปรตามวัน/ช่วงเวลา** | ตั้งได้ค่าเดียวต่อทรัพยากร — "เสาร์รับ 10 วันธรรมดารับ 5" ไม่รองรับใน phase 1 |
| **นัดซ้ำเป็นรอบ (recurring)** | เช่น "ทุกวันอังคาร 10 โมง 8 สัปดาห์" — ไม่ทำใน phase 1 |
| **เวลาทำการและวันหยุดร้าน** | phase 1 ยังไม่มีตารางเวลาทำการ ร้านเป็นผู้ควบคุมเองว่าจะรับนัดเวลาไหน |
| **ออกแบบ flow ยืนยันตัวตนใหม่** | ใช้ feature 00015 ตามที่เป็น ห้ามแตะ |
| **แจ้งเตือน SMS อัตโนมัติ** | มีต้นทุนต่อครั้ง — ร้านกดส่งเองผ่านกลไกเดิมเท่านั้น |
| **ซิงก์กับ Google Calendar / ปฏิทินภายนอก** | ไม่อยู่ในขอบเขต |
| **เปิดให้ร้านทั่วไปที่ไม่ใช่บัญชีธุรกิจ** | ฟีเจอร์นี้เป็นส่วนหนึ่งของ Business profile — ร้านบุคคลธรรมดา (`kind = PERSONAL`) ไม่ได้ใช้ |
| **เปลี่ยนพฤติกรรมร้านบ้านพัก** | feature 00017 ต้องทำงานเหมือนเดิมทุกประการ |

## 6. Risks & Mitigation (ความเสี่ยงและแนวทางแก้ไข)

### 6.1 ความเสี่ยงทางธุรกิจ

| ความเสี่ยง | ผลกระทบ | ระดับความรุนแรง | แนวทางแก้ไข |
|-----------|---------|-----------------|-------------|
| **ร้านมองว่าเพิ่มขั้นตอน** | ร้านไม่ใช้ กลับไปจดสมุด | สูง | วันนัดเป็นช่องเสริมในฟอร์มเดิม ไม่บังคับกรอก ร้านที่ไม่ใช้ต้องไม่รู้สึกว่ามีอะไรเปลี่ยน |
| **ลูกค้าไม่ยอม login เพื่อยืนยันนัด** | โหมด B มีอัตราการยืนยันต่ำ | กลาง | นัดยังคงมีผลแม้ลูกค้าไม่ยืนยัน — การยืนยันเป็นการเพิ่มความมั่นใจ ไม่ใช่เงื่อนไขให้นัดเกิดขึ้น |
| **ร้านตั้งจำนวนคิวสูงเกินจริง** | รับนัดล้นจนบริการไม่ทัน ลูกค้าเสียประสบการณ์ และโทษระบบ | กลาง | ค่าเริ่มต้นเป็น 1 และมีคำอธิบายชัดว่าตัวเลขนี้คือ "จำนวนลูกค้าที่ให้บริการพร้อมกันได้จริง" ไม่ใช่เป้าการขาย |
| **สับสนกับปฏิทินบ้านพัก** | ทีมหรือผู้ใช้เข้าใจผิดว่าเป็นระบบเดียวกัน | กลาง | แยกคำเรียกให้ชัด: บ้านพัก = "การจอง/ห้องพัก", บริการ = "นัดหมาย/ทรัพยากร" และไม่แสดงสองระบบในร้านเดียวกัน |

### 6.2 ความเสี่ยงทางเทคนิค

| ความเสี่ยง | ผลกระทบ | แนวทางแก้ไข |
|-----------|---------|-------------|
| **เพิ่มฟิลด์ลงตาราง Order ที่เป็นตารางกลาง** | กระทบทุกออเดอร์ในระบบถ้าพลาด | ฟิลด์ใหม่ทั้งหมดยอมให้ว่างได้และเป็น NULL เสมอสำหรับออเดอร์ที่ไม่ใช่การนัด — รูปแบบเดียวกับที่ feature 00017 ทำสำเร็จแล้ว |
| **กลไกกันจองซ้อนถูกลบโดยไม่ตั้งใจ** | เกิดการจองทับได้เงียบ ๆ | มีบทเรียนบันทึกไว้แล้วจาก feature 00017 ว่าเครื่องมือสร้าง schema อัตโนมัติมองไม่เห็นกลไกนี้และจะลบทิ้ง — ต้องกำกับไว้ในเอกสารระดับฐานข้อมูลและห้ามใช้คำสั่งดึง schema ย้อนกลับ |
| **การตรวจในแอปมีช่องว่างระหว่างตรวจกับบันทึก** | สองคนกดพร้อมกันแล้วจองทะลุความจุ | ไม่พึ่งการตรวจในแอปเป็นกลไกความถูกต้อง ใช้ constraint ระดับฐานข้อมูลเป็นตัวตัดสิน การตรวจในแอปมีไว้เพื่อประสบการณ์ใช้งานเท่านั้น |
| **ความจุ > 1 ทำให้กลไกกันช่วงเวลาซ้อนแบบเดิมใช้ตรง ๆ ไม่ได้** | ถ้าเปลี่ยนไปใช้การนับจำนวนแล้วบันทึก จะเกิดช่องว่างที่ทำให้จองเกินความจุได้ตอนกดพร้อมกัน | **ห้ามใช้วิธี "นับแล้วค่อยบันทึก" เป็นกลไกความถูกต้อง** — แนวทางที่แนะนำคือให้แต่ละนัดจับจอง "ที่นั่งลำดับที่ n" ของทรัพยากรนั้น แล้วบังคับด้วย constraint ระดับฐานข้อมูลว่าที่นั่งเดียวกันของทรัพยากรเดียวกันมีช่วงเวลาทับกันไม่ได้ ซึ่งเป็นกลไกเดียวกับที่ feature 00017 ใช้อยู่ ต่างแค่เพิ่มมิติที่นั่งเข้าไป การจองที่ชนกันจะถูกฐานข้อมูลปฏิเสธแล้วให้ระบบลองที่นั่งถัดไป จนครบความจุจึงแจ้งว่าเต็ม — **รายละเอียดการตัดสินใจนี้เป็นงานของ SDS/DATABASE ต้องพิสูจน์ด้วย spike ที่เรียกผ่านเส้นทางจริงก่อนลงมือ** |
| **เวลาเหลื่อมจาก timezone** | นัดเพี้ยนไปหนึ่งวัน | บ้านพักใช้ระดับ "วัน" แต่บริการต้องละเอียดถึง "เวลา" จึงต้องเก็บพร้อม timezone และแสดงผลผ่านเครื่องมือจัดรูปแบบวันที่กลางของโครงการเท่านั้น |

### 9.2 สมมติฐาน (Assumptions)

- **A-1 (user ยืนยันแล้ว 2026-07-30):** "business profile ประเภทสินค้าและบริการ" = ร้านที่เป็น **บัญชีธุรกิจ** (`Shop.kind = BUSINESS`) **และ** มีประเภทกิจการ `Shop.vertical = "GENERAL"` — ต้องเข้าเงื่อนไขทั้งสองอย่าง ฟีเจอร์นี้อยู่ใต้ Business profile
- **A-2 (ต้องให้ user ยืนยัน):** คำว่า "admin" หมายถึงฝั่งร้าน (เจ้าของร้าน/พนักงานร้าน) ไม่ใช่ผู้ดูแลแพลตฟอร์ม Deep

- **A-5:** ร้านยอมรับได้ว่าต้องสร้างทรัพยากรอย่างน้อย 1 หน่วยก่อนจึงจะนัดได้
- **A-6 (ต้องให้ user ยืนยัน):** บัญชีธุรกิจทุกระดับแพ็กเกจ (GROWTH/PRO/BUSINESS) ใช้ฟีเจอร์นี้ได้เท่ากัน ไม่แยกตามระดับ และไม่คิดเงินเพิ่มเป็น add-on

## 10. Appendix

### 10.1 ตัวอย่าง User Journey

**Scenario A: ร้านนวดรับนัดทางโทรศัพท์ (โหมด A)**

1. ลูกค้าโทรมาขอนัดนวดวันเสาร์บ่ายสองโมง
2. เจ้าของร้านเปิดหน้าสร้างออเดอร์บนมือถือ กรอกชื่อ+เบอร์ลูกค้า เลือกคอร์สนวด 90 นาที
3. ในฟอร์มเดียวกัน เลือกทรัพยากร "หมอนวด A" วันเสาร์ 14:00
4. ระบบแจ้งว่าช่วงนั้นหมอนวด A มีคิวอยู่แล้ว
5. เจ้าของเปลี่ยนเป็น "หมอนวด B" ระบบรับ บันทึกออเดอร์พร้อมนัด
6. เจ้าของกดคัดลอกลิงก์ออเดอร์ส่งให้ลูกค้าทางแชท
7. วันเสาร์ ลูกค้ามาตามนัด เจ้าของกด "ให้บริการแล้ว" ออเดอร์เดินต่อเข้าสู่การยืนยันและรีวิวตามปกติ

**Scenario B: ช่างซ่อมแอร์นัดผ่านลิงก์ (โหมด B)**

1. ลูกค้าทักแชทมาถามซ่อมแอร์ พนักงานร้านตอบและตกลงราคา
2. พนักงานสร้างออเดอร์ ระบุทรัพยากร "ช่างสมชาย" วันพุธ 09:00-11:00
3. พนักงานส่งลิงก์ออเดอร์ให้ลูกค้าในแชท
4. ลูกค้ากดลิงก์ ระบบบังคับให้ login และยืนยันเบอร์ด้วย OTP ตามกติกาเดิม
5. ลูกค้าเห็นรายละเอียดงาน ราคา และวันนัดชัดเจน กด "ยืนยันนัด"
6. ร้านเห็นสถานะเปลี่ยนเป็น "ลูกค้ายืนยันแล้ว" ในปฏิทินคิว
7. วันอังคารเย็น ลูกค้าติดธุระ กด "ขอเลื่อนนัด" พร้อมระบุเหตุผล
8. ร้านได้รับแจ้งในแชท เปิดออเดอร์ เลือกเวลาใหม่ที่ว่าง ระบบย้ายคิวให้ ช่วงเวลาเดิมกลับมาว่างทันที

**ข้อเสนอแนะ: เลือก B1 ใน phase 1** เพราะ (ก) คำว่า "ตรวจ" ในโจทย์เดิมสื่อถึงการตรวจสอบสิ่งที่ร้านกำหนดมาแล้ว มากกว่าการเลือกเอง (ข) ครอบคลุมพฤติกรรมจริงของร้านไทยที่มักตกลงวันจบในแชท/โทรศัพท์ก่อนแล้ว (ค) B2 พาปัญหาการแย่งช่องเวลาพร้อมกันเข้ามาด้วย ซึ่งเป็นงานออกแบบอีกก้อนหนึ่ง (ง) ตัว "ขอเลื่อนนัด" ของ B1 ทำหน้าที่แทน B2 ได้ 80% โดยที่ร้านยังคุมคิวอยู่ — และเราจะมีข้อมูลอัตราการขอเลื่อนไว้ตัดสินว่าควรลงทุนทำ B2 จริงไหม

**คำถามที่ 2 — ความจุต่อทรัพยากร (ตัดสินแล้ว: ร้านตั้งเอง)**

user เลือก **ให้ร้านตั้งจำนวนคิวที่รับพร้อมกันได้เอง** ซึ่งครอบคลุมธุรกิจได้กว้างกว่ามาก (คลาสเรียน ทัวร์ จัดเลี้ยง ที่รับได้หลายคนในรอบเดียว) แลกกับความเสี่ยงทางเทคนิคที่สูงขึ้น — ดู §6.2 สำหรับแนวทางที่แนะนำและข้อห้ามที่ต้องยึด

| **รายการอิสระที่ร้านตั้งเอง** | ร้านพิมพ์ชื่ออะไรก็ได้ เช่น "เตียง 1", "ห้องสตูดิโอ A", "ชุดกล้อง B" — ไม่ต้องมีบัญชี |
| **ไม่มีทรัพยากรเลย ใช้ทั้งร้านเป็นหน่วยเดียว** | ร้านรับได้ทีละ 1 นัดเท่านั้น |

**ข้อเสนอแนะ: รายการอิสระที่ร้านตั้งเอง** เพราะครอบคลุมทั้งคน สิ่งของ และสถานที่ และไม่บังคับให้ลูกน้องทุกคนต้องมีบัญชีในระบบ — ตรงกับรูปแบบที่ feature 00017 ใช้กับห้องพักและได้ผลดีแล้ว หากภายหลังต้องการผูกกับพนักงานจริงค่อยเพิ่มเป็นช่องเสริม

**คำถามที่ 3 — คิดเงินฟีเจอร์นี้หรือไม่ (ตัดสินแล้ว: อยู่ใต้ Business profile)**

user เลือกให้ฟีเจอร์นี้เป็นความสามารถของ **บัญชีธุรกิจ** — ร้านที่เป็น `kind = BUSINESS` และมีประเภทกิจการ `GENERAL` เท่านั้นที่ใช้ได้ ร้านบุคคลธรรมดาไม่เห็นฟีเจอร์นี้

ผลที่ตามมา: ตัวกั้นการเข้าถึงต้องตรวจ **สองเงื่อนไขพร้อมกัน** (`kind = BUSINESS` และ `vertical = GENERAL`) ทั้งที่ระดับเมนู หน้าจอ และการเรียกใช้งานฝั่งหลังบ้าน — ห้ามกั้นแค่ที่เมนู

ยังเหลือให้ยืนยัน (A-6): บัญชีธุรกิจทุกระดับแพ็กเกจใช้ได้เท่ากันหรือไม่ หรือจะจำกัดเฉพาะระดับสูง — ข้อเสนอคือให้ทุกระดับใช้ได้เท่ากัน เพราะการแยกตามระดับจะทำให้ต้องอธิบายเงื่อนไขซ้อนสามชั้น (บัญชีธุรกิจ + ประเภทกิจการ + ระดับแพ็กเกจ) ซึ่งผู้ใช้เข้าใจยาก

**คำถามที่ 4 — หน่วยเวลาที่ต้องรองรับ (ยังไม่ตอบ — ใช้ข้อเสนอไปก่อน)**

| ตัวเลือก | รายละเอียด |
|---------|-----------|
| **ช่วงเวลาเป็นชั่วโมง/นาที** | เช่น 14:00-15:30 |
| **ทั้งวัน** | เช่น จัดเลี้ยงวันที่ 5 ส.ค. |
| **รองรับทั้งคู่** | ร้านเลือกได้ว่านัดนี้เป็นแบบไหน |

**ข้อเสนอแนะ: รองรับทั้งคู่** โดยเก็บเป็นช่วงเวลาเสมอ และ "ทั้งวัน" คือช่วงเวลาที่ครอบทั้งวัน — ต้นทุนเพิ่มน้อยมากเพราะเป็นเรื่องการแสดงผล ไม่ใช่โครงสร้างข้อมูล แต่ครอบคลุมธุรกิจได้กว้างขึ้นมาก (ร้านนวดกับร้านจัดเลี้ยงใช้ระบบเดียวกันได้)

**คำถามที่ 5 — พนักงานร้านมีสิทธิ์แค่ไหน (ยังไม่ตอบ — ใช้ข้อเสนอไปก่อน)**

| ตัวเลือก | รายละเอียด |
|---------|-----------|
| **พนักงานที่สร้างออเดอร์ได้ = ตั้ง/แก้นัดได้** | สิทธิ์เดียวกับการจัดการออเดอร์ |
| **แยกสิทธิ์จัดการนัดออกมาต่างหาก** | ต้องเพิ่มการตั้งค่าสิทธิ์ใหม่ |

**ข้อเสนอแนะ: ใช้สิทธิ์เดียวกับการจัดการออเดอร์** — วันนัดเป็นส่วนหนึ่งของออเดอร์ การแยกสิทธิ์จะสร้างความซับซ้อนโดยไม่มีเหตุผลทางธุรกิจรองรับ

**คำถามที่ 6 — การไม่มาตามนัดกระทบคะแนนความน่าเชื่อถือหรือไม่ (ยังไม่ตอบ — ใช้ข้อเสนอไปก่อน)**

**ข้อเสนอแนะ: บันทึกไว้แต่ไม่หักคะแนน** ตามหลักการเดิมของระบบที่คะแนนความน่าเชื่อถือมีแต่ขึ้นในช่วง MVP — เก็บข้อมูลไว้ก่อน ค่อยตัดสินนโยบายเมื่อมีตัวเลขจริง
