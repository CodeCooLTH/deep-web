# ส่วนขยาย 2026-08-11 — ปุ่ม "ส่งสรุปนัด" เข้าแชท (การ์ดจริงทุกช่องทาง)

> คำสั่ง user (ตรงตัว): *"รายการนัดหมาย ลูกค้าอยากให้มีปุ่มส่งสรุป (คล้าย ๆ ส่งคำสั่งซื้อเข้า chat) … เป็นข้อความแบบนี้ (แต่ผมอยากให้ฝั่งระบบ มองเห็นเป็น Card)"* พร้อมภาพข้อความที่ร้าน BT Premium พิมพ์เองทุกใบ
>
> Design Spec: `docs/superpowers/specs/2026-08-11-chat-context-bar-and-appointment-summary-design.md` §3
> ม็อกอัพ: `docs/superpowers/specs/2026-08-11-chat-context-bar-and-appointment-summary-mockup.html`

## 1. ปัญหา

ท่อส่งการ์ดเข้าแชทมีอยู่ครบแล้ว — `CustomerPanel.tsx:333 sendToChat()` ยิง `POST /api/chat/conversations/[id]/messages` ด้วย `{ type:'ORDER', orderRefToken }` แล้ว route (`messages/route.ts:779`) ประกอบข้อความที่ใช้**ภาษาการซื้อของล้วน**:

```
คำสั่งซื้อ: {ชื่อรายการแรก}
ยอดสุทธิ ฿{ยอด}
https://deepthailand.app/o/{token}
```

ร้านคิวงานที่กดปุ่มนี้จึงส่ง **สิ่งที่ไม่มีวันนัด ไม่มีเวลา ไม่มีชื่อ ไม่มีเบอร์** ออกไป ทั้งที่ทุกค่านั้นอยู่บนออเดอร์ใบเดียวกัน (`serviceStart` / `serviceEnd` / `buyerName` / `buyerContact` / `depositAmount` / `serviceResourceId`) ร้านจึงพิมพ์เองทุกใบ

🛑 **ปุ่มเดิมไม่ได้พัง** — มันทำงานถูกต้องทุกบรรทัดสำหรับสิ่งที่มันถูกเขียนมาเพื่อทำ (ออเดอร์ขายของ) สิ่งที่ขาดคือ **ร้านคิวงานไม่เคยมีคำของตัวเอง** งานนี้คือการเติมสาขาที่หายไป ไม่ใช่การแก้บั๊ก

### 1.1 ของที่มีอยู่แล้วแต่ไม่มีทางเข้า

`src/app/(marketing)/o/[token]/AppointmentCard.tsx` ให้ลูกค้ากด **"ยืนยันนัด"** และ **"ขอเลื่อนนัด"** ได้จริงตั้งแต่ 00024 (เขียน `appointmentStatus = CONFIRMED_BY_BUYER` / `RESCHEDULE_REQUESTED` ซึ่งไหลกลับไปโผล่ในปฏิทิน `/queues` และชิปในห้องแชท) — **แต่ไม่มีเส้นทางไหนพาลูกค้าไปถึงหน้านั้นเลย** ปุ่มบนการ์ดสรุปคือทางเข้าตัวแรก

## 3. มติสถาปัตยกรรม: ไม่มี message type ใหม่ในฐานข้อมูล

ฝั่งเราเก็บเป็น **`type:'ORDER'` + `orderRefToken` ตัวเดิม**

- `OrderCardView` แสดง `serviceStart` / `serviceEnd` / `appointmentStatus` / `depositAmount` ได้อยู่แล้วตั้งแต่ 00024 (`CustomerPanel.tsx:381-387`)
- ⇒ **ไม่มี migration · ไม่มีคอลัมน์ใหม่ · ไม่ต้องแก้ตัวอ่านฝั่งเธรด** (`ChatThread.tsx:423 orderCard`) · การ์ดใบเก่าที่ส่งไปแล้วไม่เปลี่ยนหน้าตา
- สิ่งที่เปลี่ยนคือ **`body` ที่บันทึก** และ **payload ที่ยิงออกช่องทางนอก** เท่านั้น

🛑 **ห้ามเพิ่มค่าใหม่ใน `ChatMessage.type`** แล้วเขียนตัวอ่านคู่ขนาน — ประวัติเดิมจะแยกเป็นสองสายที่ต้อง render คนละทางตลอดไป และ `type` เป็นคอลัมน์ `String` ที่ TS จับไม่ได้ (`docs/conventions/enum-value-removal.md`)

**แต่ที่ระดับ API มี `type: "APPOINTMENT"`** — `type` ใน request คือ *"ผู้เรียกอยากให้ประกอบอะไร"* ส่วน `ChatMessage.type` คือ *"ของที่เก็บคือชนิดไหน"* สองอันนี้ไม่จำเป็นต้องเท่ากัน และ route นี้มี precedent อยู่แล้ว (`IMAGE_GRID` ก็ไม่มีในตาราง) การใช้ `type:'ORDER'` แล้วดูจาก `serviceStart` ว่าจะประกอบแบบไหน คือการซ่อนสาขาไว้ใน implicit condition ซึ่งจะพังเงียบวันที่ร้านขายของมีออเดอร์ที่บังเอิญมี `serviceStart`

## 4. Requirement

### FR-APS-01 — SSOT ของเนื้อหาและคำ

`src/lib/appointment-summary.ts` (**pure** — ห้าม import prisma/storage/component)

- **AC-APS-01** `when` ใช้ `formatDateTH` + `formatTimeHM` + `isAllDayAppointment` → `14 ส.ค. 2569 · 13:00–14:00` หรือ `… · ทั้งวัน` หรือวันที่อย่างเดียวเมื่อไม่มี `serviceEnd`
- **AC-APS-02** 🛑 **`appointmentText()` ที่ฝังอยู่ใน `OrderProgressBar.tsx:41` ต้องถูกย้ายมาไว้ที่นี่ แล้วให้ไฟล์นั้น import กลับ** — เวลานัดต้องมีสูตรเดียวทั้งระบบ (HR16) ตอนนี้มี 1 ที่ งานนี้กำลังจะทำให้เป็น 2
- **AC-APS-03** `deposit` เขียนว่า **"มัดจำที่ตกลงไว้"** ห้ามเขียน "มัดจำ" เปล่า — คำหลังอ่านได้ทั้ง "เก็บแล้ว" และ "ต้องเก็บ" แต่ระบบ**ไม่มี `depositReceivedAt`** จึงไม่รู้ว่าจ่ายหรือยัง (ตัดสินไปแล้วที่ `OrderProgressBar.tsx:188`)
- **AC-APS-04** ค่าที่เป็น `null`/ว่าง → **บรรทัดนั้นหายไปเลย** ไม่ใช่แสดง `—` (การ์ดนี้ออกไปหาลูกค้า ขีดกลางบนเอกสารยืนยันอ่านเป็น "ระบบพัง")
- **AC-APS-05** 🛑 **ห้าม emoji** ทั้งใน `lines` และ `text` (HR12) — ข้อความที่ร้านพิมพ์เองมี 📌🗓⏰👤📞✅ แต่ของเรามีไอคอนจริงบนการ์ด
- **AC-APS-06** ไม่ฟอร์แมตเงินเอง — รับ `totalText` / `depositText` ที่ผ่าน `formatBaht` มาแล้ว (HR16 กติกาเดียวกับ `flex-order-card.ts`)
- **AC-APS-07** `compact` = `{วันเวลา} · {บริการ}` ตัดที่ 80 ด้วย `truncateForMeta` (เกินแล้ว **Meta ตัดเองแบบไม่บอก**)

### FR-APS-02 — ชีตพรีวิว

`AppointmentSummarySheet.tsx` วางที่ `src/app/(paces)/seller/(chat)/_components/` (ถูกเรียกจากนอกห้องแชทด้วย)

- **AC-APS-08** 🛑 บรรทัด `when` **ติ๊กปิดไม่ได้** (checkbox disabled + คำว่า "ต้องมีเสมอ") — การ์ดชื่อ "ยืนยันนัดหมาย" ที่ไม่มีวันนัดคือการ์ดที่ไม่มีเหตุผลจะมีอยู่ และเปิดช่องให้ส่งของที่ทำให้ลูกค้ามาผิดวัน
- **AC-APS-09** บรรทัดที่ **ไม่มีข้อมูล** ไม่โผล่ในรายการติ๊กเลย (ไม่ใช่ติ๊กแล้วเทา) — ติ๊กที่กดไม่ได้โดยไม่บอกเหตุผลอ่านเป็นระบบพัง
- **AC-APS-10** จำค่าที่ติ๊กไว้ **ต่อร้าน** ที่ `localStorage['deep:appt-summary-lines:{shopId}']` — ร้านหนึ่งมีนโยบายเดียว (ร้านที่ไม่อยากส่งเบอร์ไม่ควรต้องติ๊กออกทุกใบ) · key ต้องมี `shopId` เพราะผู้ขายหลายร้านมีนโยบายต่างกัน
- **AC-APS-11** ข้อความท้าย **ไม่จำ** ค่าที่พิมพ์ครั้งก่อน ตั้งต้นที่ `DEFAULT_APPOINTMENT_CLOSING` เสมอ — ต่างจาก AC-APS-10 เพราะบรรทัดไหนแสดงคือ *นโยบาย* แต่ข้อความท้ายคือ *คำพูดกับลูกค้ารายนี้* จำค่าเดิม = คำที่เขียนให้ลูกค้าคนก่อนหลุดไปหาคนถัดไป
- **AC-APS-12** ปุ่มส่ง disabled ระหว่างยิง + spinner **บนปุ่ม** ไม่ใช่ overlay ทั้งชีต (ผู้ขายต้องยังอ่านสิ่งที่ตัวเองกำลังส่งได้)
- **AC-APS-13** `useLockBodyScroll` + `overscroll-contain` ที่ทุก `overflow-y-auto` (`docs/conventions/overlay-scroll-lock.md`)
- **AC-APS-14** **ไม่มี `pacesConfirm` ก่อนส่ง** — ชีตนี้**คือ**ขั้นยืนยันแล้ว (D-B3) ซ้อน Swal ทับอีกชั้นคือการถามคำถามเดิมสองครั้ง
- **AC-APS-15** ปิดชีตด้วย ✕ / ฉากหลัง / Esc ได้โดยไม่ถามยืนยัน (ยังไม่มีอะไรถูกส่ง)

### FR-APS-03 — ปลายทางและการเลือกห้องแชท

- **AC-APS-16** 🛑 หา conversation จาก `Conversation.customerId = Order.customerId` โดย **`shopId` ต้องอยู่ใน `WHERE`** — `Customer` เป็นตาราง global การ query ด้วย `customerId` เปล่าจะคืนห้องแชทของร้านอื่นที่ลูกค้าคนเดียวกันเคยคุยด้วย แล้วร้านจะส่งข้อมูลนัดของตัวเองเข้าห้องของร้านคู่แข่ง
- **AC-APS-17** 0 ห้อง → **ปุ่ม disabled + ข้อความ "ลูกค้ารายนี้ยังไม่มีห้องแชท"** ห้ามซ่อนปุ่ม (ซ่อนแล้วร้านจะคิดว่าฟีเจอร์ไม่มี แทนที่จะรู้ว่าติดอะไร) · `order.customerId = null` นับเป็นกรณีนี้
- **AC-APS-18** 1 ห้อง → เปิดชีตตรง ๆ ไม่มีแถวเลือก · >1 ห้อง → มีแถว "ส่งไปที่" ค่าตั้งต้น = `lastMessageAt` ใหม่สุด
- **AC-APS-19** ชื่อช่องทางในแถวเลือกมาจาก `src/lib/chat-channel.ts` **ห้ามพิมพ์คำเอง** (HR16)

### FR-APS-04 — การประกอบต่อช่องทาง

| ช่องทาง | ส่งอะไร | ผู้สร้าง |
|---|---|---|
| DEEP | ไม่ยิงออกนอก — บันทึกแถวอย่างเดียว | — |
| LINE | `flex` + ปุ่ม `uri` → `/o/{token}` | `src/lib/line/flex-appointment-card.ts` |
| Messenger / IG | `template` + ปุ่ม `web_url` → `/o/{token}` | `src/lib/meta/appointment-card.ts` |
| อื่น ๆ / ตกทุกกรณี | `text` | `appointment-summary.ts` |

- **AC-APS-20** `text` **ส่งเสมอทุกกรณี** — เป็นทั้ง `ChatMessage.body` ที่ร้านเห็นและค้นหาเจอในประวัติ และทางถอยเมื่อช่องทางไม่รองรับการ์ด
- **AC-APS-21** 🛑 `altText` ของ LINE ต้องมีทั้งวันนัดและเวลา (`ยืนยันนัดหมาย 14 ส.ค. 2569 · 13:00–14:00`) — เป็นสิ่งเดียวที่ลูกค้าเห็นในรายการแชทและ notification ไม่ใช่ "ข้อความจากร้าน"
- **AC-APS-22** `uri` action ของ LINE รับเฉพาะ `https` — base เป็น `http` (dev) ต้องถอยไปส่ง `text` ทั้งก้อน (กติกาเดิมที่ `messages/route.ts:802` ใช้อยู่ ยกมาใช้ซ้ำ)
- **AC-APS-23** Meta: `title` ≤80 · `subtitle` ≤80 · **ไม่มีรูป = ไม่ใส่คีย์ `image_url`** ไม่ใช่ค่าว่าง (ส่งค่าว่าง Meta ตกทั้งข้อความ)

### FR-APS-05 — ด่านฝั่ง server (fail-closed ทุกข้อ)

`POST /api/chat/conversations/{id}/messages` `{ type:"APPOINTMENT", orderRefToken, hiddenKeys[], closing }`

- **AC-APS-24** `order.publicToken = orderRefToken AND order.shopId = conv.shopId` — ownership อยู่ใน `WHERE` ไม่ใช่ดึงมาเทียบทีหลัง
- **AC-APS-25** `order.serviceStart = null` → `400 "คำสั่งซื้อนี้ไม่มีนัดหมาย"`
- **AC-APS-26** ร้านไม่ผ่าน `canUseAppointments` → `403`
- **AC-APS-27** `hiddenKeys` ผ่าน Valibot **allow-list** และ **ห้ามมี `'when'`** — ด่านที่สองของ AC-APS-08 (UI กันได้แค่คนที่เดินผ่านประตู)
- **AC-APS-28** `closing` ยาว ≤ `APPOINTMENT_CLOSING_MAX` (120) · trim แล้วว่าง → ไม่มีบรรทัดปิดท้าย
- **AC-APS-29** `isTerminalAppointmentStatus(order.appointmentStatus)` → `400 "นัดนี้จบแล้ว ส่งสรุปไม่ได้"` — ส่งใบยืนยันของนัดที่ให้บริการไปแล้ว/ไม่มาตามนัด คือการส่งข้อมูลที่ผิดออกไปหาลูกค้า

## 5. Edge cases

| # | เคส | พฤติกรรม |
|---|---|---|
| E-1 | นัดทั้งวัน | `when` = `… · ทั้งวัน` — เรียก `isAllDayAppointment` ห้ามเช็ค `00:00` เอง |
| E-2 | ไม่มี `serviceEnd` | วันที่อย่างเดียว (กติกาเดิมของ `appointmentText`) |
| E-3 | นัดอยู่ในอดีต | ยังส่งได้ (ร้านอาจส่งย้อนเป็นหลักฐาน) — แต่ `COMPLETED`/`NO_SHOW` ห้าม (AC-APS-29) |
| E-4 | ออเดอร์ `CANCELLED` | ปุ่มหายทุกจุด (กติกาเดิมของ footer `CustomerPanel:392`) |
| E-5 | ร้านเปลี่ยน `vertical` ทีหลัง | อ่านค่าปัจจุบันเสมอ ไม่อ่านธงที่เก็บบนแถว (`stored-flag-vs-owner-truth.md`) |
| E-6 | ส่งซ้ำใบเดิม | **อนุญาต ไม่กันซ้ำ** — ส่งเตือนซ้ำก่อนถึงวันนัดเป็นพฤติกรรมปกติ (ต่างจากการ์ดสินค้าที่ idempotent) |
| E-7 | นัดถูกเลื่อนหลังส่งการ์ดไปแล้ว | การ์ดในเธรด render จาก `orderRefToken` ⇒ **อัปเดตตามเอง** · ที่ลูกค้าได้บน Messenger/LINE เป็น snapshot ค้างไว้ — ปุ่ม `/o/{token}` พาไปหาค่าล่าสุดเสมอ |
| E-8 | ช่องทางส่งไม่ผ่าน | ตกไปเส้นทาง `SEND_FAILED` เดิม — บับเบิลแดงพร้อมเหตุผล ไม่ใช่หายเงียบ |

## 9. 🛑 จุดเรียกที่ 4 (ปฏิทิน `/queues`) — ยังไม่ได้ทำ และทำไม

สเปกเขียนไว้ว่าปุ่มจะอยู่ใน "popover ของนัด" ในปฏิทิน — **ข้อสันนิษฐานนั้นผิด ไม่มี popover อยู่จริง**

`AppointmentCalendar.tsx:285` ผูก `eventClick` ไว้กับ `router.push('/orders/{token}')` ตรง ๆ ⇒ แตะนัดในปฏิทิน = ไปหน้ารายละเอียดออเดอร์ทันที ไม่มีแผงกลางทางให้แขวนปุ่ม

ทางเลือกที่มี:

| ทาง | ผล |
|---|---|
| **(ที่เลือก) ไม่ทำ** | แตะนัด → หน้า `/orders/[token]` ซึ่ง **มีปุ่ม "ส่งสรุปนัด" แล้ว** (จุดที่ 3) = เพิ่ม 1 คลิก ไม่มีทางตัน |
| สร้าง popover ใหม่ในปฏิทิน | เป็น **interaction pattern ใหม่** ที่ยังไม่ผ่าน `safepay-ux` และเปลี่ยนพฤติกรรมของการแตะนัดทั้งปฏิทิน (ของเดิมคือไปหน้ารายละเอียด) — งานที่ควรตัดสินแยก ไม่ใช่แถมมากับรอบนี้ |

**ยังไม่ปิดประเด็น** — ถ้า user ยืนยันว่าต้องกดจากปฏิทินได้โดยไม่ต้องเปิดหน้าออเดอร์ ต้องออกแบบ popover ผ่าน ux ก่อน (รวมถึงกางเลขงบพื้นที่ที่ 390px ตาม `flex-header-truncation.md`)
