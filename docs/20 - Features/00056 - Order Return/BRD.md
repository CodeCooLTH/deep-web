# BRD — 00056 ระบบคืนของ

> คู่กับ `PRD.md` · กฎธุรกิจ + acceptance criteria ที่ทดสอบได้

## 1. นิยามศัพท์ (HR16)

| คำ | นิยามเดียวของระบบ |
|---|---|
| **คืนของ (return)** | ผู้ซื้อ **ได้รับของแล้ว** และส่งกลับมาหาร้าน — มี `OrderReturn` หนึ่งแถว |
| **ตีกลับ (parcel returned)** | ขนส่งส่งไม่สำเร็จ ของกลับต้นทางโดยผู้ซื้อ **ไม่เคยได้รับ** — `carrierStatus ∈ RETURNED_CARRIER_STATUSES` |
| **พัสดุขาไป (FORWARD)** | `OrderShipment.direction = 'FORWARD'` — พัสดุที่ร้านส่งให้ลูกค้า |
| **พัสดุขากลับ (RETURN)** | `OrderShipment.direction = 'RETURN'` — ผู้ส่ง = ลูกค้า · ผู้รับ = ร้าน |
| **ยอดที่คืน** | ผลรวม `OrderReturnItem.qty × OrderItem.price` ของใบคืนที่สถานะ `RECEIVED` |

🛑 **"คืนของ" กับ "ตีกลับ" ห้ามยุบเป็นคำเดียวกัน** — ต่างกันตรง *ผู้ซื้อเคยถือของไว้หรือไม่*
ซึ่งเปลี่ยนทั้งความรับผิด ค่าส่ง และการตีความสถิติผู้ซื้อ · ใบเดียวเป็นทั้งสองอย่างพร้อมกันไม่ได้

## 2. สถานะของใบคืน (`OrderReturn.status`)

```
REQUESTED ──► SHIPPING ──► RECEIVED
     │             │
     └─────────────┴──► CANCELLED
```

| สถานะ | ความหมาย | ผลต่อยอดขาย/สต็อก |
|---|---|---|
| `REQUESTED` | ร้านกดรับเรื่องแล้ว ยังไม่มีเลขพัสดุขากลับ | **ไม่มี** |
| `SHIPPING` | ออกเลขพัสดุขากลับแล้ว ของกำลังเดินทางกลับ | **ไม่มี** |
| `RECEIVED` | ของถึงร้านแล้ว ร้านกดยืนยันรับคืน | ✅ หักยอดขาย · ✅ คืนสต็อก · ✅ นับสถิติผู้ซื้อ |
| `CANCELLED` | ยกเลิกเรื่องคืน (ลูกค้าเปลี่ยนใจ/ตกลงกันได้) | **ไม่มี** |

🛑 **ผลทางบัญชีเกิดที่ `RECEIVED` เท่านั้น ไม่ใช่ตอนกดขอคืน** — ของที่ยังไม่กลับมาถึงร้านคือ
ของที่ยังอยู่กับลูกค้า การหักยอดตั้งแต่ตอนกดจะทำให้ร้านเห็นยอดหายไปทั้งที่ยังไม่ได้ของคืน
และถ้าลูกค้าเปลี่ยนใจ ต้องย้อนคืนซึ่งเป็นงานที่ไม่มีใครทำถูกทุกครั้ง

| **BR-RT-14** | ถ้อยคำใช้ **"คืนของ"** ห้ามใช้ "ตีกลับ" ในสิ่งที่ร้านเห็นบนใบคืน (คนละเหตุการณ์ · §1) |

## 4. ผลกระทบต่อของเดิมที่ต้องไล่ให้ครบ

### 4.1 `Order.status` ค่าที่ 5 — **60 จุดเทียบตรง ๆ**

ไม่มี CHECK ในฐาน (ตรวจ prod แล้ว) ⇒ **TypeScript เป็นด่านเดียว** · ตรรกะ binary
(`status === 'CANCELLED' ? A : B`) จะเงียบ ๆ ตีให้ `RETURNED` ตกเข้า branch "ยังไม่จบ"

กลุ่มที่ต้องไล่ก่อน (เรียงตามความเสียหาย):
1. **เงิน** — `countsAsRevenue()`, P&L, ยอดขายรายวัน
2. **สถิติ/คะแนน** — trust score, จำนวนออเดอร์บนโปรไฟล์สาธารณะ, badge
3. **กองงาน** — `deriveShippingStage()` ต้องคืน `DONE` ให้ `RETURNED`
4. **หน้าจอ** — ป้าย/ตัวกรอง/แท็บ

### 4.2 พัสดุ 2 ทิศ — **14 จุด**

`{ status: 'CREATED', isDryRun: false }` ปรากฏ 10 จุดใน Prisma + 4 จุดใน raw SQL
(`chat.service.ts` ×2, `order-stage.service.ts` ×2) — ทุกจุดต้องเติม `direction`

## 7. บันทึกจาก P1 (2026-08-24)

### 7.1 กับดักที่เจอจริงระหว่างทาง

| # | อาการ | ต้นเหตุ |
|---|---|---|
| 1 | ใส่ `as const` ที่ `ACTIVE_FORWARD_SHIPMENT` แล้ว `sales/page.tsx` ฟ้องว่า `shipments`/`items` **ไม่มีอยู่** ทั้งที่ไม่ได้แตะไฟล์นั้น | `revenueOrderWhere` spread ตัวนี้เข้า `where` ของ Prisma — readonly object ทำให้ Prisma assign ไม่ผ่านแล้ว **TS เลิก infer ทั้ง query** · ไฟล์ `order-revenue.ts` **เขียนเตือนเรื่องนี้ไว้เองอยู่แล้ว** แต่คำเตือนอยู่ที่ไฟล์ปลายทาง ไม่ใช่ที่ไฟล์ที่ผมกำลังเขียน |
| 2 | เติม `direction: true` ใน `select` แล้ว error ชุดเดียวกันโผล่อีก | **ลืม `prisma generate` หลังแก้ schema** — client ไม่รู้จักคอลัมน์ ⇒ `select` ไม่ถูกต้อง ⇒ Prisma ถอยไป type พื้นฐาน · เสียเวลาไล่ผิดทางไป 2 รอบ (กับดัก HR17 ตรง ๆ) |
| 3 | mutation 2 ตัวเขียวทั้งที่ควรแดง | ด่านเช็ค `toContain('ACTIVE_FORWARD_SHIPMENT')` ซึ่ง**บรรทัด `import` ก็ match** · และ slice ตัด `as const` ทิ้งพอดีเพราะมันอยู่ *หลัง* `}` — แก้เป็นจับ `...ACTIVE_FORWARD_SHIPMENT` (การใช้งาน) และกินบรรทัดปิดวงเล็บด้วย |

### 7.2 carve-out ที่ตั้งใจ

`backfillShipmentEvidence()` (00055) **ไม่กรอง `direction`** โดยเจตนา — หลักฐานข้อพิพาทเป็นของ
*พัสดุ* ไม่ใช่ของ *ทิศทาง* พัสดุขากลับที่หายระหว่างทางก็ต้องมีหลักฐานเหมือนกัน

### 7.3 ของที่ยังไม่แตะ (P3)

`Order.status` ยัง**ไม่มีค่า `RETURNED`** ในโค้ดเลย — เพิ่มค่าแล้วต้องไล่ 60 จุดพร้อมกัน
ไม่งั้นตรรกะ binary จะตีให้ตกเข้า branch "ยังไม่จบ" เงียบ ๆ (BRD §4.1) จึงแยกเป็นเฟสของตัวเอง

## 8. วิธีคืน (รอบ re-design 2026-08-25 · หัวหน้าเคาะ D-1)

SSOT = `RETURN_METHODS` ใน `src/lib/order-return.ts` (ลิสต์เดียวที่จอ render ตรง ๆ)

| # | key | พาดหัวบนจอ | badge เรื่องเงิน | ผู้ออกค่าส่ง (derive) | เป็นต้นทุนร้าน? |
|---|---|---|---|---|---|
| 1 | `ISHIP` | ส่งด้วย iShip | ตัดจากเครดิตร้าน | ร้าน | บังคับใช่ |
| 2 | `SHOP_SELF` | ร้านส่งเอง | เป็นต้นทุนร้าน | ร้าน | บังคับใช่ |
| 3 | `BUYER_SELF` | ลูกค้าส่งเอง | ลูกค้าออกค่าส่ง | ลูกค้า | **ร้านเลือก** |

🛑 **ตารางนี้เคยมี 5 แถว (`SHOP_ISHIP`/`SHOP_MANUAL`/`SHOP_NONE`/`BUYER_MANUAL`/`BUYER_NONE`)**
สองมิติ (payer × trackingSource) ถูกกางออกมาเป็นข้อ ๆ ทั้งตาราง ⇒ ร้านต้องอ่าน 5 ประโยคที่
ต่างกันทีละครึ่งท่อนเพื่อหาข้อของตัวเอง · หัวหน้าสั่งตรง 2026-08-25 ว่าเหลือ 3 เพราะ
**"ใครออกค่าส่ง" แต่ละข้อบอกในตัวอยู่แล้ว** (ข้อ 1 ตัดเครดิตร้าน ⇒ ร้านจ่ายแน่นอน)

**คู่ที่หายจากลิสต์ยังไปถึงได้ครบ — ไม่ได้ถอดความสามารถ:**

| วิธีที่เลือก | ช่องเลขพัสดุ | ผลลัพธ์ที่บันทึก |
|---|---|---|
| `ISHIP` | ไม่มีช่อง (ระบบออกให้) | `SHOP` + `ISHIP` |
| `SHOP_SELF` | เว้นว่าง | `SHOP` + `NONE` ← เดิมคือข้อ `SHOP_NONE` |
| `SHOP_SELF` | กรอกเลข | `SHOP` + `MANUAL` |
| `BUYER_SELF` | เว้นว่าง | `BUYER` + `NONE` ← เดิมคือข้อ `BUYER_NONE` |
| `BUYER_SELF` | กรอกเลข | `BUYER` + `MANUAL` |

เทส `[blocker]` เปลี่ยนเกณฑ์จาก "นับข้อในลิสต์" เป็น **"กาง 3 วิธี × มี/ไม่มีเลข แล้วต้อง
ครอบคู่ที่ valid ครบทั้ง 5 คู่ ไม่ขาดไม่เกิน"** — ใครแก้ให้คู่ไหนไปถึงไม่ได้ เทสแดงทันที

## 10. บันทึกจาก P2–P4

- **1 ออเดอร์ = 2 พัสดุที่ active พร้อมกันได้** (`FORWARD` 1 + `RETURN` 1) — ยืนยันตามที่หัวหน้าถาม
  นั่นคือเหตุผลทั้งหมดที่ต้องมีคอลัมน์ `direction`
- `OrderEvent.type` เพิ่ม 4 ค่า (`RETURN_REQUESTED`/`SHIPPED`/`RECEIVED`/`CANCELLED`) ผ่าน
  migration แบบ **อ่านของเดิมมาต่อท้าย** — ตรวจแล้วว่าค่าเดิม 17 ตัวยังอยู่ครบ (รวมเป็น 21)
- `Order.status = 'RETURNED'` ไหลเข้าชิป/ดรอปดาวน์/ป้ายทุกจอ **โดยไม่ต้องแก้ทีละจอ** เพราะ
  ทุกที่ derive จาก `ORDER_STATUS_META` อยู่แล้ว — จุดที่ต้องแก้ด้วยมือมีแค่ 3 ที่:
  `deriveShippingStage` (→ DONE) · `deriveOrderStage` (ชิปแถวแชท) · `countableOrderWhere`
- 🛑 `countableOrderWhere` เป็นจุดที่ **เกือบหลุด**: ใบที่คืนของครบมีพัสดุขาไป `delivered` จริง
  จึงผ่านสาขา OR ได้ ถ้าไม่ตัด `RETURNED` ออก ผลงานบนโปรไฟล์สาธารณะจะยังนับใบที่ยกเลิกการขาย
  ไปแล้ว = ปัญหาเดิมที่ฟีเจอร์นี้ตั้งใจแก้ กลับมาทางอื่น
- อัตราความสำเร็จ (`computeCompletionRate`) ไม่ต้องแก้ — `RETURNED` ไม่ใช่ทั้ง confirmed และ
  cancelled จึงหลุดจากทั้งตัวตั้งและตัวหาร = เป็นกลาง ตรงกับเจตนา BR-OSM-04 ที่ไม่ลงโทษร้าน
  จากเหตุการณ์ฝั่งผู้ซื้อ

**แม้ใบนั้นคืนไม่ได้** (โชว์ข้อความ "คืนของได้เมื่อของถึงมือลูกค้าแล้วเท่านั้น" ลอย ๆ) = เสียงรบกวนล้วน

`docs/conventions/seller-action-placement.md`

### 14.1 ด่านของโปรเจกต์จับได้ 2 อย่างที่ผมพลาด

1. **HR7 (theme-guard)** — ร่างแรกใช้ `z-[1090]` + `max-h-[85dvh]` (arbitrary value)
2. **เทส `[blocker]` `paces-sticky-z-index`** — หัวชีตใช้ `sticky z-10` ซึ่งจะถูก `.btn`
