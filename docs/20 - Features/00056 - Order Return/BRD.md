# BRD — 00056 ระบบคืนของ

> คู่กับ `PRD.md` · กฎธุรกิจ + acceptance criteria ที่ทดสอบได้

---

## 1. นิยามศัพท์ (HR16)

| คำ | นิยามเดียวของระบบ |
|---|---|
| **คืนของ (return)** | ผู้ซื้อ **ได้รับของแล้ว** และส่งกลับมาหาร้าน — มี `OrderReturn` หนึ่งแถว |
| **ตีกลับ (parcel returned)** | ขนส่งส่งไม่สำเร็จ ของกลับต้นทางโดยผู้ซื้อ **ไม่เคยได้รับ** — `carrierStatus ∈ RETURNED_CARRIER_STATUSES` |
| **พัสดุขาไป (FORWARD)** | `OrderShipment.direction = 'FORWARD'` — พัสดุที่ร้านส่งให้ลูกค้า |
| **พัสดุขากลับ (RETURN)** | `OrderShipment.direction = 'RETURN'` — ผู้ส่ง = ลูกค้า · ผู้รับ = ร้าน |
| **ยอดที่คืน** | ผลรวม `OrderReturnItem.qty × OrderItem.price` ของใบคืนที่สถานะ `RECEIVED` |

🛑 **"คืนของ" กับ "ตีกลับ" ห้ามยุบเป็นคำเดียวกัน** — ต่างกันตรง *ผู้ซื้อเคยถือของไว้หรือไม่*
ซึ่งเปลี่ยนทั้งความรับผิด ค่าส่ง และการตีความสถิติผู้ซื้อ · ใบเดียวเป็นทั้งสองอย่างพร้อมกันไม่ได้

## 2. สถานะของใบคืน (`OrderReturn.status`)

```
REQUESTED ──► SHIPPING ──► RECEIVED
     │             │
     └─────────────┴──► CANCELLED
```

| สถานะ | ความหมาย | ผลต่อยอดขาย/สต็อก |
|---|---|---|
| `REQUESTED` | ร้านกดรับเรื่องแล้ว ยังไม่มีเลขพัสดุขากลับ | **ไม่มี** |
| `SHIPPING` | ออกเลขพัสดุขากลับแล้ว ของกำลังเดินทางกลับ | **ไม่มี** |
| `RECEIVED` | ของถึงร้านแล้ว ร้านกดยืนยันรับคืน | ✅ หักยอดขาย · ✅ คืนสต็อก · ✅ นับสถิติผู้ซื้อ |
| `CANCELLED` | ยกเลิกเรื่องคืน (ลูกค้าเปลี่ยนใจ/ตกลงกันได้) | **ไม่มี** |

🛑 **ผลทางบัญชีเกิดที่ `RECEIVED` เท่านั้น ไม่ใช่ตอนกดขอคืน** — ของที่ยังไม่กลับมาถึงร้านคือ
ของที่ยังอยู่กับลูกค้า การหักยอดตั้งแต่ตอนกดจะทำให้ร้านเห็นยอดหายไปทั้งที่ยังไม่ได้ของคืน
และถ้าลูกค้าเปลี่ยนใจ ต้องย้อนคืนซึ่งเป็นงานที่ไม่มีใครทำถูกทุกครั้ง

## 3. กฎธุรกิจ

| # | กฎ |
|---|---|
| **BR-RT-01** | คืนของได้เฉพาะออเดอร์ที่ **ของถึงมือผู้ซื้อแล้ว** — `status ∈ {SHIPPED, CONFIRMED}` **หรือ** พัสดุขาไป `carrierStatus ∈ DELIVERED_CARRIER_STATUSES` · ใบ `PENDING`/`CANCELLED` คืนไม่ได้ (ยังไม่เคยส่ง = ให้ยกเลิกแทน) |
| **BR-RT-02** | 🛑 ห้ามสร้างใบคืนกับออเดอร์ที่พัสดุขาไป **ตีกลับ** — ผู้ซื้อไม่เคยได้ของ ไม่มีอะไรให้คืน (ใบพวกนั้นใช้ทางเดิม: ยกเลิกด้วย `PARCEL_RETURNED`) |
| **BR-RT-03** | 1 ออเดอร์มีใบคืนที่ยัง **ไม่จบ** (`REQUESTED`/`SHIPPING`) ได้ **ใบเดียว** — กันสองคนในร้านกดพร้อมกันแล้วออกเลขพัสดุขากลับ 2 ใบ · บังคับด้วย partial unique index ที่ระดับฐาน ไม่ใช่ find-then-insert |
| **BR-RT-04** | จำนวนที่คืนต่อรายการต้อง `≥1` และ **ไม่เกินจำนวนที่ยังไม่เคยถูกคืน** (`OrderItem.qty − ผลรวมที่คืนสำเร็จไปแล้ว`) |
| **BR-RT-05** | 🛑 **ห้ามสร้างออเดอร์ใบใหม่เพื่อการคืนของเด็ดขาด** — นี่คือทั้งหมดของฟีเจอร์นี้ · มีเทส `[blocker]` สแกนซอร์สว่า service ของ 00056 ไม่มี `order.create(` |
| **BR-RT-06** | `Order.status` เปลี่ยนเป็น `RETURNED` เมื่อ **ทุกรายการถูกคืนครบ** เท่านั้น · คืนบางส่วน = สถานะเดิมไม่เปลี่ยน (แต่ยอดขายหักตามจริง) |
| **BR-RT-07** | พัสดุขากลับต้อง `direction='RETURN'` เสมอ · **ทุก query ที่หา "พัสดุของออเดอร์นี้" ต้องระบุ direction** — ไม่ระบุ = พัสดุขากลับจะถูกอ่านเป็นพัสดุขาไป ⇒ ออเดอร์ที่คืนของแล้วกลับไปขึ้น "กำลังจัดส่ง" |
| **BR-RT-08** | ผู้ส่งของพัสดุขากลับ = **ที่อยู่ผู้ซื้อของออเดอร์นั้น** · ผู้รับ = **ที่อยู่ผู้ส่งของร้าน** (สลับกับขาไปเป๊ะ ๆ ไม่ให้ร้านกรอกใหม่) |
| **BR-RT-09** | ค่าส่งขากลับหักจากเครดิต iShip ของร้าน และบันทึกเป็น **ค่าใช้จ่าย** เหมือนค่าส่งขาไป (D-3c) |
| **BR-RT-10** | คืนสต็อกเฉพาะร้านที่เปิด Inventory Add-on และเฉพาะรายการที่ **เคยถูกตัดสต็อกจริง** (`OrderItem.stockDeducted` ไม่ null) — ตัดไปเท่าไรคืนเท่านั้น ห้ามคืนตาม `qty` ที่คืน (ใบเก่าที่ไม่เคยตัดจะกลายเป็นการเพิ่มสต็อกจากอากาศ) |
| **BR-RT-11** | ยอดขายหักด้วย `countsAsRevenue()` ที่เป็น SSOT อยู่แล้ว **ห้ามเขียนเกณฑ์ใหม่** |
| **BR-RT-12** | สถิติผู้ซื้อ (00055) ได้ถังใหม่ `returnedAfterDelivery` **แยกจาก `returned` (ตีกลับ)** — ถ้ายุบรวม ร้านจะอ่านว่าลูกค้าไม่ยอมรับของทั้งที่จริงคือรับแล้วขอคืน ซึ่งเป็นพฤติกรรมคนละแบบ |
| **BR-RT-13** | ทุกการเปลี่ยนสถานะของใบคืนต้องมี `OrderEvent` — ประวัติคือหลักฐาน |
| **BR-RT-14** | ถ้อยคำใช้ **"คืนของ"** ห้ามใช้ "ตีกลับ" ในสิ่งที่ร้านเห็นบนใบคืน (คนละเหตุการณ์ · §1) |

## 4. ผลกระทบต่อของเดิมที่ต้องไล่ให้ครบ

### 4.1 `Order.status` ค่าที่ 5 — **60 จุดเทียบตรง ๆ**

ไม่มี CHECK ในฐาน (ตรวจ prod แล้ว) ⇒ **TypeScript เป็นด่านเดียว** · ตรรกะ binary
(`status === 'CANCELLED' ? A : B`) จะเงียบ ๆ ตีให้ `RETURNED` ตกเข้า branch "ยังไม่จบ"

กลุ่มที่ต้องไล่ก่อน (เรียงตามความเสียหาย):
1. **เงิน** — `countsAsRevenue()`, P&L, ยอดขายรายวัน
2. **สถิติ/คะแนน** — trust score, จำนวนออเดอร์บนโปรไฟล์สาธารณะ, badge
3. **กองงาน** — `deriveShippingStage()` ต้องคืน `DONE` ให้ `RETURNED`
4. **หน้าจอ** — ป้าย/ตัวกรอง/แท็บ

### 4.2 พัสดุ 2 ทิศ — **14 จุด**

`{ status: 'CREATED', isDryRun: false }` ปรากฏ 10 จุดใน Prisma + 4 จุดใน raw SQL
(`chat.service.ts` ×2, `order-stage.service.ts` ×2) — ทุกจุดต้องเติม `direction`

## 5. Acceptance Criteria

| # | เกณฑ์ |
|---|---|
| AC-RT-01 | กดคืนของจากออเดอร์ `PENDING` ไม่ได้ · จากใบที่พัสดุตีกลับไม่ได้ |
| AC-RT-02 | สร้างใบคืนแล้ว **จำนวนออเดอร์ของร้านไม่เพิ่ม** |
| AC-RT-03 | คืน 1 จาก 3 ชิ้น → ยอดขายลดเท่าราคา 1 ชิ้น · `Order.status` ยังไม่เป็น `RETURNED` |
| AC-RT-04 | คืนครบทุกชิ้น → `Order.status = 'RETURNED'` · หลุดจากทุกกองงาน |
| AC-RT-05 | คืนเกินจำนวนที่ซื้อ / เกินที่เหลือ → ปฏิเสธ |
| AC-RT-06 | มีใบคืนที่ยังไม่จบอยู่แล้ว → สร้างใบที่สองไม่ได้ (บังคับที่ฐาน) |
| AC-RT-07 | พัสดุขากลับไม่ปรากฏในกองงานพัสดุขาไป และไม่เปลี่ยน `deriveShippingStage` ของออเดอร์ |
| AC-RT-08 | ผลทางบัญชีเกิดที่ `RECEIVED` เท่านั้น — `REQUESTED`/`SHIPPING` ไม่แตะยอดขาย/สต็อก |
| AC-RT-09 | ยกเลิกใบคืน → ไม่มีผลย้อนหลังใด ๆ |
| AC-RT-10 | คืนสต็อกเฉพาะรายการที่เคยถูกตัดสต็อกจริง |
| AC-RT-11 | service ของ 00056 **ไม่มี `order.create(`** |
| AC-RT-12 | สถิติผู้ซื้อแยก "คืนของ" ออกจาก "ตีกลับ" |
