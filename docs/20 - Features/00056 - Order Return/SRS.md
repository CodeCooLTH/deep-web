## 1. ขอบเขต

ผู้ขายบันทึกว่า "ลูกค้าได้รับของแล้วขอส่งคืน" โดย **ไม่สร้างออเดอร์ใบใหม่**

🛑 **นี่คือเหตุผลทั้งหมดที่ฟีเจอร์นี้มีอยู่** — ของเดิมร้านต้องสร้าง OD ปลอมเพื่อออกเลขพัสดุ
ขากลับ ทำให้จำนวนออเดอร์/ยอดขาย/Trust Score เฟ้อ ⇒ มีเทส `[blocker]` สแกนซอร์สห้าม
`prisma.order.create(` ปรากฏใน `order-return.service.ts` (BR-RT-05 · AC-RT-11)

**คืนของ ≠ ตีกลับ** — ตีกลับคือขนส่งส่งไม่สำเร็จ ผู้ซื้อ *ไม่เคยได้รับของ* ⇒ ใบนั้นต้องยกเลิก
คำสั่งซื้อ ไม่ใช่คืนของ · ต่างกันที่ความรับผิด ค่าส่ง และการตีความสถิติผู้ซื้อ

## 2. Functional requirements

| FR | ข้อกำหนด |
|---|---|
| FR-RT-01 | เปิดใบคืนได้เมื่อ **ของถึงมือลูกค้าแล้ว** — ผู้ซื้อกดยืนยันเอง (`CONFIRMED`) หรือขนส่งแจ้งส่งถึง · `SHIPPED` เฉย ๆ **ไม่พอ** เพราะร้านตั้งเองได้ |
| FR-RT-02 | 1 ออเดอร์มีใบคืนที่ยังไม่จบได้ **ใบเดียว** — บังคับที่ partial unique ระดับฐาน ไม่ใช่แค่ด่านในโค้ด |
| FR-RT-03 | เลือกคืนได้บางรายการ/บางจำนวน · เพดาน = จำนวนที่ยังไม่เคยถูกคืน · ใบที่ยกเลิก**คืนโควตา** |
| FR-RT-04 | ผู้ขายเลือก **วิธีส่งของกลับ 3 ข้อ**: `ส่งด้วย iShip` / `ร้านส่งเอง` / `ลูกค้าส่งเอง` — "ใครออกค่าส่ง" **ไม่ถามแยก** เพราะแต่ละข้อบอกในตัว |
| FR-RT-05 | เลขพัสดุขากลับ **เว้นว่างได้** = "ไม่มีเลข" ซึ่งไม่ใช่ข้อผิดพลาด |
| FR-RT-06 | ขากลับเป็น**พัสดุคนละใบ** มีขนส่งของตัวเอง — ขาไปไม่ถูกแตะ |
| FR-RT-07 | ขนส่งขากลับเลือกจาก**รายชื่อในระบบ** ห้ามพิมพ์อิสระ · ค่าตั้งต้น = เจ้าเดียวกับขาไป |
| FR-RT-08 | ขนาดกล่องขากลับตั้งต้นจากขาไป · แก้ได้ แต่ **ไม่บังคับกรอกใหม่** |
| FR-RT-09 | มี**หน้าสรุปก่อนยืนยัน** ที่บอก: ของที่คืน · 2 ขาคนละบรรทัด · ค่าส่งเข้าต้นทุนไหม · **ลูกค้าส่งกลับมาที่ไหน** · จะเกิดอะไรหลังกดยืนยัน |
| FR-RT-10 | **ที่อยู่ส่งกลับไม่มี UI ให้ตั้ง และต้องไม่มี** — ระบบสลับผู้ส่ง/ผู้รับกับขาไปเอง |
| FR-RT-11 | ผลทางบัญชีเกิดที่ **"ได้รับของคืนแล้ว" จุดเดียว** — ไม่ใช่ตอนเปิดใบ |
| FR-RT-12 | ค่าส่งขากลับเข้าระบบกำไรเมื่อร้านเป็นคนจ่าย · ร้านจ่ายเอง = **บังคับเป็นต้นทุน ห้ามปิด** |
| FR-RT-13 | ใบปะหน้าพัสดุขากลับต้องมี**เส้นทางสาธารณะ** — คนที่ต้องพิมพ์คือผู้ซื้อซึ่งส่วนใหญ่ไม่มีบัญชี |

## 3. Non-functional

| NFR | ข้อกำหนด |
|---|---|
| NFR-RT-01 | ชีตต้องล็อก scroll ของหน้า + `role="dialog"` คู่กับ `aria-modal` **และมีกับดักโฟกัสจริง** — `aria-modal` ที่ไม่มีกับดักคือคำสัญญาที่ผิด ไม่ใช่แค่ฟีเจอร์ที่ขาด |
| NFR-RT-02 | คอนทราสต์ทุกชั้นข้อความ ≥4.5:1 (วัดบนพื้นที่มันอยู่จริงหลัง composite) |
| NFR-RT-03 | tap target ≥44px — ยกเว้นที่เป็นหนี้ของธีม Paces ทั้งชุด ซึ่งต้องระบุเป็นหนี้ ไม่ใช่เงียบ |
| NFR-RT-04 | ไม่ล้นแนวนอนที่ 320px |
| NFR-RT-05 | **ไม่คืน PII เกินจำเป็น** — หน้านี้อยู่ใต้ client layout ทุกค่าที่ service คืนไหลเข้า flight payload · การประเมินค่าส่งอ่านที่อยู่ฝั่ง server เองและคืนเฉพาะราคา |
| NFR-RT-06 | การเปิดพัสดุจริงต้องไม่อยู่ใน transaction เดียวกับการสร้างใบคืน — iShip ล่มต้องไม่ทำให้บันทึกคำขอคืนไม่ได้ |

## 4. ข้อจำกัดที่รู้ตัว

| # | ข้อจำกัด |
|---|---|
| KG-RT-01 | ตัวประเมินค่าส่ง (`compareShippingPrices`) **ตรึงผู้ส่ง = ที่อยู่ร้านเสมอ** ⇒ ราคาที่ได้เป็นทิศ "ร้าน → ลูกค้า" ขณะที่ของจริงคือ "ลูกค้า → ร้าน" · ขนส่งไทยในประเทศคิดจาก (น้ำหนัก/ขนาด × คู่โซน) ซึ่งสมมาตร ⇒ ตรงกันในทางปฏิบัติ และจอเรียกมันว่า "โดยประมาณ" |
| KG-RT-02 | ค่าส่งขากลับของวิธีที่ไม่ใช่ iShip มาจาก**ที่ร้านกรอกเองเท่านั้น** — ไม่กรอก = ไม่ถูกนับในหน้ากำไร และ**หน้าจอต้องบอกเรื่องนี้** |
| KG-RT-03 | **สาขา iShip ยังไม่เคยถูกกดจริง** — จะทดสอบบน prod กับลูกค้าจริงเท่านั้น (หัวหน้าสั่ง 2026-08-26) เพราะการเปิดพัสดุตัดเครดิตร้านจริงทุกครั้ง |
| KG-RT-04 | คอลัมน์ `manualCourier` เลิกใช้แต่ไม่ลบ — DROP ทำให้ deployment เก่าที่ยังเสิร์ฟระหว่าง build พัง |
