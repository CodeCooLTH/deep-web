# PRD — 00056 ระบบคืนของ (Order Return)

> Draft · เริ่ม 2026-08-24 · ที่มา: หัวหน้าสั่งตรง
> "ตอนนี้เวลาคืนของ ลูกค้าจะไปสร้าง OD ใหม่ ซึ่งจริงๆ มันไม่ควรสร้างออเดอร์เพิ่ม
>  (เพราะมันจะนับเป็นออเดอร์เพิ่มขึ้นเกินมา) — อยากให้กดคืนของได้ และสร้างเลขแทรคขากลับ
>  จาก iShip ได้จากระบบเลย โดยกดจาก order detail + หน้าแชท"

---

## 1. ปัญหา

ระบบ **ไม่มีแนวคิด "คืนของ" เลย** ร้านจึงต้องสร้างออเดอร์ใบใหม่เพื่อออกเลขพัสดุขากลับ ผลคือ:

| ผลข้างเคียง | ทำไมมันแย่ |
|---|---|
| **จำนวนออเดอร์เกินจริง** | ใบคืนของถูกนับเป็นการขายอีกครั้ง — ตัวเลขบนแดชบอร์ด/โปรไฟล์สาธารณะเฟ้อ |
| **ยอดขายเฟ้อ** | ถ้าใบใหม่มียอด ก็ถูกนับซ้ำ; ถ้าใส่ยอด 0 ก็ทำให้ค่าเฉลี่ยเพี้ยน |
| **ประวัติขาดจากกัน** | ใบขายกับใบคืนไม่ผูกกัน — เปิดใบเดิมไม่รู้ว่าของถูกคืนไปแล้ว |
| **Trust Score เพี้ยน** | ออเดอร์ที่นับเข้า trust score เพิ่มขึ้นจากงานที่ไม่ใช่การขาย |

🛑 **`PARCEL_RETURNED` ที่มีอยู่แล้วไม่ใช่เรื่องเดียวกัน** — อันนั้นคือ *ขนส่งตีกลับก่อนถึงมือ
ผู้รับ* (ลูกค้าไม่เคยได้ของ) ส่วนฟีเจอร์นี้คือ *ลูกค้ารับของแล้วส่งคืน* คนละเหตุการณ์ คนละ
ผลทางบัญชี และเกิดพร้อมกันในใบเดียวไม่ได้

## 2. เป้าหมาย

ร้านกด **"คืนของ"** จากออเดอร์เดิมได้ทั้งในหน้ารายละเอียดและในห้องแชท → เลือกรายการที่คืน →
ระบบออก **เลขพัสดุขากลับจาก iShip** ให้ (ผู้ส่ง = ลูกค้า · ผู้รับ = ร้าน) **โดยไม่สร้าง
ออเดอร์ใบใหม่**

### ไม่ใช่เป้าหมายรอบนี้
- ให้ **ผู้ซื้อ** กดขอคืนเองจาก `/o/[token]` (รอบนี้ร้านเป็นคนกดให้)
- คืนเงินอัตโนมัติผ่านช่องทางชำระเงิน (ระบบไม่ได้ถือเงิน — บันทึกว่าคืนเท่าไรเท่านั้น)
- เปลี่ยน/เคลมสินค้า (exchange) — คนละ flow

## 4. ความเสี่ยงเชิงโครงสร้าง (วัดจริงก่อนเขียนโค้ด)

### 4.1 🛑 `Order.status` **ไม่มี CHECK constraint ในฐานเลย**

ตรวจ prod 2026-08-24 — `Order` มี CHECK 9 ตัว (`cancelReason`, `appointmentStatus`,
`booking_fields`, …) แต่ **ไม่มีตัวไหนคุม `status`** มันเป็น `String @default("PENDING")` เปล่า ๆ

⇒ เพิ่มค่าที่ 5 **ไม่ต้อง migrate คอลัมน์** แต่ก็แปลว่า **ไม่มีอะไรกันค่าใหม่หลุดไป branch ผิด
นอกจาก TypeScript** และในโค้ดมี **60 จุดที่เทียบ `status === 'CONFIRMED'/'CANCELLED'` ตรง ๆ**

นี่คือคลาสเดียวกับ `docs/conventions/enum-value-removal.md` แต่กลับทิศ: ตรรกะ binary
(`status === 'CANCELLED' ? A : B`) **ไม่พังเสียงดัง**เมื่อค่าที่ 5 มา มันเงียบ ๆ ตกเข้า branch
"ยังไม่จบ" ทั้งที่งานจบไปแล้ว

**วิธีกัน:** ยก `ORDER_STATUS_META` เป็น `Record<OrderStatus, …>` ที่ `tsc` บังคับให้ครบ
(มีอยู่แล้ว — เพิ่มคีย์แล้วจะฟ้องทันทีถ้าที่ไหนใช้ `Record` เดียวกัน) + ไล่ 60 จุดด้วยมือ
ทีละจุด แล้วเขียนเทส `[blocker]` ปักหมุดกลุ่มที่ตัดสินเรื่องเงิน/สถิติ

### 4.2 🛑 พัสดุขากลับจะปนกับพัสดุขาไปทุกจอ

มี **14 จุด** ที่กรอง "พัสดุของใบนี้" ด้วย `{ status: 'CREATED', isDryRun: false }`
(10 จุด Prisma + 4 จุด raw SQL) — ถ้าพัสดุขากลับถูกเก็บใน `OrderShipment` ตารางเดียวกัน
โดยไม่มีตัวแยก **ทุกจุดจะเห็นมันเป็นพัสดุของออเดอร์นั้น** ⇒ ออเดอร์ที่คืนของแล้วจะกลับไปขึ้น
"กำลังจัดส่ง" · ไทล์กองงานนับซ้ำ · หลักฐานข้อพิพาทของ 00055 ผูกผิดใบ

**วิธีกัน:** `OrderShipment.direction` (`FORWARD` ค่าตั้งต้น / `RETURN`) + **ค่ากลางตัวเดียว**
ให้ทุกจุดอ้าง + เทส `[blocker]` สแกนซอร์สว่าไม่มีจุดไหนกรองพัสดุโดยไม่ระบุ direction

ทำไมไม่แยกตารางใหม่: `createShipment()` ถือตรรกะทั้งหมดของการเปิดพัสดุ (ตรวจที่อยู่ · เครดิต ·
retry · เก็บหลักฐาน · ต้นทุนจริง) การก็อปไปอีกตารางคือการสร้างสำเนาที่จะเลื่อนออกจากกันแน่นอน

## 5. User story

| # | ในฐานะ | อยากจะ | เพื่อ |
|---|---|---|---|
| US-1 | ผู้ขาย | กด "คืนของ" จากออเดอร์เดิม | ไม่ต้องสร้างออเดอร์ปลอมอีกใบ |
| US-2 | ผู้ขาย | เลือกว่าคืนรายการไหนบ้าง | ลูกค้าซื้อ 3 คืน 1 ต้องบันทึกได้ตรง |
| US-3 | ผู้ขาย | ให้ระบบออกเลขพัสดุขากลับให้ | ลูกค้าเอาเลขไปส่งได้เลย ไม่ต้องคุยกันเอง |
| US-4 | ผู้ขาย | กดจากห้องแชทได้ | จังหวะที่ลูกค้าขอคืนคือระหว่างคุยกันอยู่ |
| US-5 | ผู้ขาย | เห็นว่าใบไหนคืนของแล้ว | ตัวเลขยอดขาย/สต็อกตรงกับความจริง |

## 6. Metrics

- จำนวนออเดอร์ที่ถูกสร้างเพื่อ "ออกเลขพัสดุขากลับ" = **0** หลังเปิดใช้
- ยอดขายรวมของเดือนที่มีการคืนของ ต้องเท่ากับ (ยอดเดิม − ยอดที่คืน)
- ไม่มีรายงานว่าออเดอร์ที่คืนของแล้วยังขึ้นในกองงาน "กำลังจัดส่ง"
