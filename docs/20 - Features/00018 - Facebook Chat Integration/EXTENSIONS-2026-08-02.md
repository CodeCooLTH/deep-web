## E10 — บอกเหตุผลที่ส่งข้อความไม่ออกเป็นภาษาไทย + ส่งใหม่ได้

### E10.1 ที่มา

user report 2026-08-02 พร้อมภาพหน้าจอ: บับเบิลที่ยิงไม่ออกขึ้นว่า

> ส่งไม่สำเร็จ — (#551) This person isn't available right now.

ร้านอ่านแล้วไม่รู้ว่าเกิดอะไรและต้องทำอะไรต่อ (ระบบเราพัง? กดส่งซ้ำได้ไหม? ต้องเชื่อมเพจใหม่?)
เพราะเราเก็บ `e.message` ของ Meta ดิบ ๆ ลง `ChatMessage.failureReason` ซึ่ง **Meta ตอบเป็น
ภาษาอังกฤษเสมอแม้เพจตั้งภาษาไทย**

การสืบสวนเคสนี้ (เธรด `c32b0ac3…`) ยืนยันว่าไม่ใช่บั๊กของระบบ: หน้าต่าง 24 ชม. เปิดอยู่
(`lastInboundAt` ห่างแค่ 5 นาที), token ใช้ได้, เพจเดียวกันส่งหาลูกค้าคนอื่นสำเร็จในนาทีเดียวกัน
และยิง `sender_action: mark_seen` (ไม่มีเนื้อหาถึงลูกค้า) ก็ยังโดนปฏิเสธด้วย error เดิม
→ เป็นสถานะฝั่งบัญชีลูกค้า (subcode `1545041`)

### E10.2 Business Rules

| BR | กฎ | เหตุผล |
|---|---|---|
| BR-FAIL-01 | **แปลตอนแสดงผล ไม่ใช่ตอนเขียน DB** — `failureReason` ยังเก็บข้อความดิบของ Meta | ซัพพอร์ตต้องใช้สืบสวน + แถวเก่าที่เก็บไว้แล้วได้คำแปลย้อนหลังฟรี |
| BR-FAIL-02 | แปลเฉพาะ error ที่ **ยืนยันได้จริง** เท่านั้น นอกนั้นคงข้อความดิบทั้งดุ้น | แปลผิด = ชี้ร้านไปผิดทาง เสียหายกว่าปล่อยอังกฤษไว้ (เอกสาร error code ของ Meta ตอบ HTTP 500 ตอนทำ ตรวจสอบไม่ได้) |

| BR-FAIL-04 | ส่งใหม่ = **สร้างข้อความใหม่** ไม่ใช่แก้แถวเดิมให้กลายเป็นสำเร็จ | `ChatMessage` เป็น append-only (`prisma/schema.prisma` ChatMessage) + ถ้าลบบับเบิลเก่าทิ้งฝั่ง client มันจะโผล่กลับตอนโหลดใหม่ ภาพก่อน/หลังรีเฟรชไม่ตรงกัน |
| BR-FAIL-05 | ส่งใหม่ได้เฉพาะชนิดที่ประกอบ payload กลับได้ครบจากแถวที่เก็บไว้ | TEXT ใช้ `body`, IMAGE ใช้ `imageUrl` (= fileId ที่ยังอยู่ใน storage); ORDER เก็บแค่ `orderRefToken` ส่วนข้อความลิงก์ประกอบตอนส่งและไม่ได้เก็บไว้ → ต้องส่งการ์ดใหม่จากออเดอร์ |

### E10.4 จุดที่แสดงผล

1. **บับเบิลในเธรด** — แถวเดียวใต้ข้อความ อยู่ **หน้าเวลา** (ไม่ใช่กล่องแดงเต็มบรรทัดแบบเดิม
   ซึ่งกินพื้นที่เท่าข้อความอีกอันทั้งที่เป็นสถานะของข้อความที่อยู่เหนือมันเอง):

   `[↻] ส่งไม่สำเร็จ (i) | ยกเลิกการส่งข้อความ`

   - `(i)` = เหตุผลเต็ม — hover เห็น (`title`) + แตะได้ (Swal) เพราะมือถือไม่มี hover
     ถ้าเป็น `title` อย่างเดียวคนใช้มือถือจะไม่มีทางรู้สาเหตุเลย
   - รวม 2 เส้นทางเป็นสถานะเดียวกัน เพราะสำหรับผู้ขายมันคือเรื่องเดียวกัน ("ข้อความไม่ถึงลูกค้า")
     ต่างแค่พลาดตรงไหน: `deliveryStatus='FAILED'` (ถึง server แล้ว Meta ปฏิเสธ) กับ
     `_status='failed'` (บับเบิล optimistic ที่ยังไม่เคยถึง server ของเรา)
2. **toast ตอนกดส่ง** — `POST .../messages` ตอบ 502 พร้อม `error` ที่แปลแล้ว
   (เดิมตอบ *"ส่งข้อความไปยังช่องทางภายนอกไม่สำเร็จ กรุณาลองใหม่"* ทุกกรณี ซึ่งเป็นคำแนะนำ
   ที่ **ผิด** กับ #551 — ร้านจะกดซ้ำเปล่า ๆ แล้วโทษระบบ)

### E10.5 Bug ที่เจอระหว่างทาง

บับเบิลที่ยิงไม่ออกขึ้นป้าย **"ส่งแล้ว"** ควบคู่กับแถบแดง เพราะเงื่อนไขป้ายสถานะดูแค่ `_status`
(ซึ่ง `undefined` สำหรับแถวที่บันทึกแล้ว) ไม่ได้ดู `deliveryStatus` — แก้แล้วในชุดเดียวกัน

### E11.2 ทำไมลบแถวจริง ไม่ใช่ `isDeleted`

`isDeleted` มีไว้สำหรับ **unsend ของข้อความที่ส่งถึงลูกค้าไปแล้ว** จึงต้องเหลือหลักฐานว่าเคยมี
ข้อความอยู่ตรงนั้น (บับเบิล "ข้อความถูกลบ") — แต่แถว `FAILED` **ลูกค้าไม่เคยเห็นอะไรเลย**
การทิ้ง tombstone ไว้จึงเป็นการโกหกผู้ขายว่า "มีข้อความถูกลบ" ทั้งที่ไม่เคยมีข้อความไปถึง

ข้อจำกัด FR-CANCEL-02 คือสิ่งเดียวที่ทำให้ยังปลอดภัยต่อ invariant append-only ของ `ChatMessage`
— **ห้ามผ่อนโดยไม่คิดเรื่อง unsend/หลักฐานในเธรดให้จบก่อน** (มี unit test ตรึงทั้งสองเงื่อนไข
ที่ `src/services/__tests__/channel-chat-cancel-failed.test.ts`)

## E12 — referral (คลิกโฆษณา/ปุ่ม CTA/ลิงก์ m.me) เปิดหน้าต่าง 24 ชม.

### E12.1 ที่มา

ตรวจสอบเอกสาร Messaging Policy ของ Meta เทียบโค้ดหลังเคส #551 พบว่า action ที่ **เปิดหรือรีเซ็ต
หน้าต่าง 24 ชม.** มีหลายอย่าง ไม่ใช่แค่ "ส่งข้อความ":

- ลูกค้าส่งข้อความ ✅ (มีอยู่แล้ว)
- ลูกค้า react ข้อความ ✅ (ทำไปแล้ว 2026-08-01)
- **คลิกโฆษณา Click-to-Messenger** ❌
- **กดปุ่ม CTA / Get Started** ❌
- **คลิกลิงก์ m.me ที่มี `ref`** ❌

สามอย่างหลังมาถึงเราเป็น **referral event** ซึ่ง `ingestAdReferral` บันทึกลง
`ConversationAdReferral` + `Conversation.referral*` เฉย ๆ ไม่แตะหน้าต่างเลย (คอมเมนต์ที่
`ingestInboundMessage` ระบุว่า referral ย้ายออกไป `ingestAdReferral` ตั้งแต่ E5 2026-07-26
แต่ตอนย้ายไม่ได้พาเรื่องหน้าต่างไปด้วย)

**ผลกระทบจริง:** ลูกค้าเก่ากดโฆษณาตัวใหม่แล้วยังไม่พิมพ์อะไร → ระบบขึ้นว่า "หมดเวลา" และ
บล็อกไม่ให้ร้านตอบ ทั้งที่ Meta เปิดหน้าต่างให้แล้ว = เสียโอกาสขายตรงจุดที่ร้านจ่ายค่าโฆษณาไปแล้ว
`syncInboundWindowFromMeta` กู้ไม่ได้เพราะมันถาม Meta หา "ข้อความล่าสุดของลูกค้า" เหมือนกัน
ไม่เห็นการคลิก

### E12.2 การแก้

`ingestAdReferral` รับ `customerActionAt?: number` เพิ่ม — ใส่มา = เปิดหน้าต่าง ณ เวลานั้น,
ไม่ใส่ = ไม่แตะหน้าต่างเลย

**ทำไมเป็นพารามิเตอร์ ไม่ให้ service อ่าน `event.timestamp` เอง:** `timestamp` มีค่าเสมอ
ถ้า service เดาเอง referral ที่ติดมากับ **echo ของข้อความฝั่งเพจ** จะเปิดหน้าต่างให้ตัวเอง —
webhook route จึงส่ง `undefined` เมื่อ `is_echo` และส่งเวลาจริงเมื่อเป็น action ของลูกค้า

เขียนด้วย `updateMany` + เงื่อนไข "ใหม่กว่าของเดิมเท่านั้น" แยกจาก `update` ของข้อมูล referral
(ที่ทับได้เสมอเพราะเป็นค่า "ล่าสุด") — กัน event ที่มาสลับลำดับดันหน้าต่างถอยหลัง ตรรกะเดียวกับ
react. **ไม่ขยับ `lastMessageAt`**: ไม่มีข้อความใหม่จริง การดันเธรดขึ้นหัวรายการเป็นคนละเรื่อง
กับสิทธิ์ในการส่ง

เทส: `src/services/__tests__/channel-chat-referral-window.test.ts` (4 เคส)

### E12.3 ยังไม่ครอบ (known gap)

**postback (ปุ่ม Get Started)** — `api/channels/facebook/webhook/route.ts` ยังไม่ handle
`event.postback` เลย ทั้ง event จึงตกไปทาง `ingestInboundMessage` แล้วถูกข้าม เป็นงานแยก

**ข้อความระบบของ Meta ที่ attribute เป็นฝั่งลูกค้า** — เช่น `You missed a call from …`
Meta ส่งมาโดย `from` = ผู้ใช้ เราจึงตั้ง `lastInboundAt` ตามนั้น แต่เอกสารไม่ได้ระบุว่า
"สายที่ไม่ได้รับ" เปิดหน้าต่าง → แบนเนอร์อาจบอกว่ายังส่งได้ทั้งที่จริงส่งไม่ได้

### E13.3 บทเรียนที่ฝังไว้ในโค้ด

## E14 — ชุดปุ่ม hover ในรายการแชท

user report 2026-08-02: *"ไอ shortcut 4 อันนี้กินพื้นที่มากเกินไป"* — ต้นเหตุไม่ใช่ขนาด
แต่เป็น **ตำแหน่ง**: ชุดปุ่มลอยอยู่ `top-1/2` คือกลางแถวพอดี จึงทับบรรทัดข้อความล่าสุด+แท็ก
ซึ่งเป็นบรรทัดที่ต้องอ่านเพื่อรู้ว่าห้องไหนเป็นห้องไหน ผลคือพอเมาส์กวาดผ่านรายการ เนื้อหาที่
กำลังหาหายไปพอดี

- ย้ายไป `top-2` = บรรทัดเดียวกับเวลา แล้วซ่อนเวลาด้วย `lg:group-hover:invisible`
  (ใช้ `invisible` ไม่ใช่ `hidden` — ต้องกันที่ไว้เท่าเดิม ไม่งั้นคอลัมน์ขวายุบแล้วเนื้อหา
  กระตุกทุกครั้งที่เมาส์ผ่าน) เวลาเป็นข้อมูลที่ยอมให้หายชั่วคราวได้ ต่างจากข้อความ/แท็ก
- เหลือ 2 ปุ่มที่ใช้บ่อยสุด (ปักหมุด/ปิดงาน) · ซ่อน+สแปม เข้าเมนู `⋯`
- เมนูเป็น custom React (`useState` + click-outside + Escape) **ไม่ใช่ Preline hs-dropdown**
  ด้วยเหตุผลเดียวกับ `OrderCardMenu`: รายการนี้ lazy-load + filter + realtime = re-render
  ตลอด ทำให้ inline-state ของ Preline หายแล้ว menu ค้าง `opacity: 0`
- state เก็บที่ระดับ list (`rowMenuId`) ไม่ใช่ในแต่ละแถว เพราะชุดปุ่มต้องรู้ว่าเมนูเปิดอยู่แล้ว
  ค้างตัวเองไว้แม้เมาส์ออกนอกแถว — ไม่งั้นเมนูที่ล้นนอกขอบแถวจะทำให้ hover หลุด ชุดปุ่มหาย
  เมนูหายตาม ระหว่างที่ผู้ใช้กำลังเลื่อนเมาส์ไปกดมันพอดี
