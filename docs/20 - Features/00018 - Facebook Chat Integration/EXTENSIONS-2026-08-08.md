## E1 — กด noti ของอีกร้านแล้ว "ไม่พบบทสนทนานี้"

> 🛑 หัวข้อนี้เป็นการ **บันทึกย้อนหลัง** งานที่ deploy ไปแล้ว (`90c1dc43`, `3ca3ba57` และฝั่งแอป
> `bb1f27f`) ทั้งสามคอมมิตไม่ได้แตะ `docs/` เลย — เขียนไว้ที่นี่เพื่อไม่ให้ตรรกะการสลับร้าน
> อัตโนมัติกลายเป็นของที่มีอยู่ในโค้ดโดยไม่มีใครรู้ที่มา

### E1.1 อาการที่ผู้ใช้เห็น

ผู้ขายที่ถือ **2 ร้าน และผูก Facebook Page คนละเพจไว้คนละร้าน** จะได้ push ของทั้งสองร้านลง
เครื่องเดียวกัน (ถูกต้องแล้ว — `shopAudience()` ส่งให้เจ้าของ+สมาชิกของร้านนั้น ซึ่งเป็นคนเดียวกัน)

แต่พอกด noti ของร้าน B ขณะที่ active อยู่ร้าน A ระบบขึ้น **"ไม่เจอช่องแชทนี้"** ทั้งที่เธรดมีอยู่จริง
และผู้ใช้มีสิทธิ์เต็ม — ไม่มีอะไรบอกว่าต้องไปสลับร้านก่อน ผู้ใช้ต้องเดาเอง

### E1.2 Root cause

payload ของ push มีแค่:

```json
{ "type": "chat", "url": "/inbox/{conversationId}", "conversationId": "…" }
```

**ไม่มี `shopId`** ขณะที่ ownership guard ของหน้าเธรด scope ด้วย `activeShopId`
(`WHERE { id, shopId: activeShopId }`) → เธรดของร้าน B หาไม่เจอเมื่อ active อยู่ร้าน A

### E1.3 ทางเลือกที่ไม่เลือก และเหตุผล

| ทางเลือก | ทำไมไม่เอา |
|---|---|
| เพิ่ม `shopId` ลง payload | ต้อง **build แอปใหม่ + ส่ง App Store ใหม่** ขณะที่ build 2 ยังอยู่ในคิวรีวิว · และเครื่องที่ยังไม่อัปเดตจะยังพังเหมือนเดิมตลอดไป |
| ให้ผู้ใช้สลับร้านเอง (ขึ้นข้อความบอก) | ผู้ใช้กด noti เพราะอยากอ่านข้อความ ไม่ได้อยากเรียนรู้เรื่องบริบทร้าน |

**ที่เลือก:** resolve ร้านเจ้าของเธรดจาก `conversationId` **ฝั่ง server** — payload เดิมใช้ได้
ทุกเวอร์ชันของแอปที่ปล่อยไปแล้ว ไม่ต้องแตะแอปเลย

### E1.4 กลไก

1. `listAccessibleShopIds(userId)` (`src/lib/shop-context.ts`) — ร้านที่ผู้ใช้เข้าถึงได้ทั้งหมด
   (เจ้าของ + สมาชิก) กรอง `deletedAt: null, purgedAt: null`
2. `findConversationShopForUser(conversationId, userId)` (`src/services/chat.service.ts`) —
   **scope สิทธิ์อยู่ใน `WHERE` (`shopId: { in: accessibleShopIds }`) ไม่ใช่ดึงมาแล้วเทียบทีหลัง**
   (กัน TOCTOU/IDOR ตามแบบเดียวกับ `getConversationToastPreview`)
3. `page.tsx` ของเธรด: เจอเธรด → render ปกติ · ไม่เจอ → ถามข้อ 2 ว่าเป็นของร้านไหนที่เข้าถึงได้
   → render `ChatShopAutoSwitch`
4. `ChatShopAutoSwitch.tsx` — สลับร้านผ่าน `useShopSwitcher` แล้ว hard-navigate กลับ
   `/inbox/{id}?switched=1`

🛑 **`?switched=1` คือตัวกันวน ห้ามเอาออก** — ถ้าสลับไม่สำเร็จจริง (session ไม่โปรพาเกต)
`page.tsx` เห็นค่านี้แล้วจะไม่ render ตัวสลับซ้ำ แต่ตกไปหน้า error ให้กดกลับได้

### E1.5 บั๊กที่เจอตอน self-review — overlay ค้างตลอดไป (`90c1dc43`)

เดิม `ChatShopAutoSwitch` hardcode `show={true}` — ถ้าสลับล้มเหลว (403 / เน็ตหลุด / 500)
ผู้ใช้จะ **ติดอยู่หน้าสปินเนอร์ ออกไปไหนไม่ได้เลย**

`useShopSwitcher` ไม่มี error state ให้อ่าน จึงต้องอนุมานจากพฤติกรรม:

| ผลลัพธ์ | `switching` |
|---|---|
| สำเร็จ | ค้าง `true` จน browser unload หน้า (ไม่เคยกลับเป็น false) |
| ล้มเหลว | เด้ง `pacesToast` แล้วตั้งกลับเป็น `false` |

→ **"เคยเป็น true แล้วกลับเป็น false" = ล้มเหลวเสมอ** → render `SellerErrorState`

### E1.6 Performance (`3ca3ba57`) — ~3.8 วิ → ~1.6 วิ

| ที่มาของเวลา | เดิม | ใหม่ |
|---|---|---|
| overlay ขั้นต่ำ | 3000ms (ค่าเดิมของการสลับร้านด้วยมือ) | **800ms** ผ่าน option `minOverlayMs` |
| query ตอนเธรดไม่ใช่ของร้านที่ active | 6 query (5 ตัวเสียเปล่า) | `conversation.findFirst` รันก่อน แล้วค่อย `Promise.all` ที่เหลือ |
| happy path | 3 รอบ round trip เรียงกัน | 2 รอบ |

**ทำไมลด 3000 → 800 ได้:** 3000ms เดิมมีไว้กันจอกระพริบตอนผู้ใช้ *กดสลับร้านเอง* — เขาเพิ่งเลือก
ร้านจากรายการ ต้องเห็นว่ากำลังไปร้านไหนสักพัก. แต่เส้นทางนี้ผู้ใช้ **ไม่ได้ตั้งใจสลับร้าน** เขากด
แจ้งเตือนเพื่ออ่านข้อความ การถ่วง 3 วินาทีอ่านเป็น "ระบบช้า" ทั้งที่งานจริงจบตั้งแต่ ~300ms

**ทำไมไม่ตัดเป็น 0:** ต้องเหลือเวลาให้ผู้ใช้อ่านทันว่าระบบกำลังสลับไปร้านไหน ไม่งั้นจอเปลี่ยนวูบเดียว
แล้วเขาจะงงว่าเมื่อกี้เกิดอะไรขึ้น — ปลอดภัยที่จะสั้นเพราะ `session.update()` เป็น `await`
(cookie ถูกตั้งเรียบร้อยแล้วตอน promise คืนค่า) เวลาที่เกินจากนั้นเป็นเรื่อง "ความรู้สึก" ไม่ใช่ความถูกต้อง

### E1.7 ฝั่งแอป — deep-link ที่พังคนละสาเหตุ (`bb1f27f` ใน deep-mobile-seller)

หลังแก้ E1.4 หัวหน้ารายงานว่า noti **ไม่พาไปแชทเลย** ซึ่งเป็นคนละบั๊ก 2 ตัวซ้อนกัน:

1. **`injectJavaScript` แข่งกับการโหลดแรกของ WebView** → แก้ด้วย `takePendingPath()` ที่ consume
   คิวมาใช้เป็น `initialUri` ตั้งแต่ render แรก (ได้ผลพลอยได้: ไม่ต้องโหลด `/dashboard` ทิ้งก่อน)
2. **cold start: response มาก่อน listener ถูก subscribe** → เพิ่ม
   `takeLaunchNotificationResponse()` อ่านค่าจาก native (`getLastNotificationResponse`)

🛑 **ลำดับสำคัญ: ต้องอ่าน launch response *หลัง* เช็ค OTA จบเท่านั้น** — ตัวอ่านนี้ล้างค่าฝั่ง native
ทิ้งหลังอ่าน ถ้าอ่านตอน mount แล้ว `applyPendingUpdate()` เจอ update ใหม่ →
`Updates.reloadAsync()` รีสตาร์ท JS context → คิวหายไปด้วย **และค่าฝั่ง native ก็ถูกล้างไปแล้ว**
= ปลายทางหายทั้งสองทาง (บั๊กที่ผมสร้างเองระหว่างแก้ แล้วจับได้ตอนตรวจซ้ำ)

dedupe ด้วย `responseId` เพราะบาง OS ยิงทั้งสองทางสำหรับการกดครั้งเดียว

## E2 — noti บอกด้วยว่ามาจากช่องทาง/เพจไหน

### E2.1 คำขอ

> user 2026-08-08: "ถ้าแจ้งเตือน noti อยากได้ page ว่าเป็น facebook หรือ ig อื่น ๆ ด้วย
> ทำได้มั้ยนะ ตอนนี้มีแต่ชื่อใช่ปะ"

ใช่ — เดิม `pushNewChatMessage` ส่งแค่ `title = preview.senderName` และ `body = ข้อความ`

**นี่คือคำขอเดียวกับที่ user เคยสั่งเมื่อ 2026-07-23 สำหรับ `ChannelBadge` ในกล่องแชท** —
*"ร้านที่มีหลายเพจ ต้องรู้ว่าลูกค้าคนนี้ทักมาจากเพจไหน คำว่า Messenger ซ้ำกันทุกเธรดจนไม่ให้ข้อมูลอะไร"*
แค่คนละพื้นผิว จึงยึดคำตัดสินเดิมเป็นฐาน: **ชื่อเพจคือตัวระบุ ส่วนช่องทางเป็นบริบท**

### E2.2 ข้อมูลมีอยู่แล้ว ไม่มี query เพิ่ม

`getConversationToastPreview()` ที่ push เรียกอยู่แล้ว **คืน `channel` และ `channelName`
(= `ShopChannel.name` ชื่อเพจ) มาทุกครั้งอยู่แล้ว** — เดิมทิ้งไปเปล่า ๆ

### E2.3 ทำไมใช้ `subtitle` ไม่ใช่ยัดรวมใน `title`

`title` คือชื่อผู้ส่ง ซึ่งเป็นชื่อไทยเต็ม ๆ อยู่แล้ว พอต่อ ` · ชื่อเพจ` ความยาวรวมเกินเพดาน
หัวเรื่องของ iOS เกือบทุกใบ แล้ว `…` **จะไปลงตรงชื่อเพจพอดี = ตัดทิ้งสิ่งที่เพิ่งเพิ่มเข้ามาเพื่อจะบอกเสียเอง**

```
┌────────────────────────────────┐
│ ▣  สมชาย ใจดี                  │  title    (เดิม)
│    Messenger · BT Premium      │  subtitle (ใหม่)
│    เสื้อยืดมีไซซ์ L ไหมคะ        │  body     (เดิม)
└────────────────────────────────┘
```

ยืนยันจากเอกสาร Expo Push API: `subtitle` (string) — Optional (**iOS Only**) — "The subtitle to
display in the notification below the title"

### E2.4 ทำไม *ไม่* ใส่ชื่อร้านคู่ไปด้วย

พิจารณาแล้วตัดออก — ชื่อเพจแยกได้ครบทุกกรณีที่มีเพจอยู่แล้ว:

| สถานการณ์ | ชื่อเพจพอไหม |
|---|---|
| 2 ร้าน คนละเพจ (เคสหัวหน้า) | พอ — และชื่อร้านจะกลายเป็นการพูดเรื่องเดิมสองรอบ |
| ร้านเดียว หลายเพจ | พอ — ชื่อร้านไม่ช่วยแยกอะไรเลย |

**เคสที่ชื่อเพจช่วยไม่ได้คือเธรด `DEEP`** (ลูกค้าทักผ่านแอป/เว็บของเราเอง ไม่มี `shopChannelId`
→ `channelName` เป็น `null`) — ตอนนี้เหลือคำว่า `Deep` ล้วน ถ้าวันหนึ่งพบว่าไม่พอ ให้เอาชื่อร้านมา
เสียบ *ตรงนี้ที่เดียว* ไม่ใช่ใส่คู่กันทุกใบ

🛑 หมายเหตุถ้าจะทำ: `ShopChannel.name` (ชื่อเพจบน Facebook ตอนกดเชื่อม) กับ `Shop.shopName`
(ผู้ขายพิมพ์เองในระบบเรา) **ตั้งคนละที่ ไม่การันตีว่าเหมือนกัน** — ใช้แทนกันไม่ได้

### E2.5 `src/lib/chat-channel.ts` (ใหม่) — ทำไมต้องแยกไฟล์
