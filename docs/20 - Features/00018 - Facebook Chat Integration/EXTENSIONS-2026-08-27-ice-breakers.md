# ส่วนขยาย 2026-08-27 — คำถามแนะนำก่อนเริ่มแชท (Ice Breakers)

> ต่อจาก `EXTENSIONS-2026-08-26-thread-control-api.md`
> ลำดับงานที่ user เคาะไว้: **3 (Sender Actions) → 2 (Ice Breakers) → 1 (IG Comments)** — ข้อนี้คือข้อ 2

---

## 1. ปัญหาที่แก้

ลูกค้าที่เปิดแชทกับเพจ/บัญชี IG **เป็นครั้งแรก** เจอกล่องเปล่า ต้องคิดเองว่าจะถามอะไร
คำถามที่เข้ามาจริงซ้ำกันแทบทุกใบ ("มีค่าส่งไหม" · "ของพร้อมส่งไหม" · "เปิดกี่โมง")
ผู้ขายพิมพ์คำตอบเดิมวันละหลายสิบครั้ง

Meta มี **Ice Breakers** ให้อยู่แล้ว — ปุ่มคำถามสำเร็จรูป ≤4 ข้อที่แสดงในกล่องแชทก่อนลูกค้าพิมพ์
ลูกค้าแตะแล้ว Meta ยิง `postback` มาหาเรา ⇒ เราตอบคำตอบที่ร้านตั้งไว้ให้อัตโนมัติ

**เงื่อนไขการมองเห็นของ Meta (ไม่ใช่ของเรา — เปลี่ยนไม่ได้):**
- เฉพาะเธรดที่ **ยังไม่เคยมีข้อความ** (ลูกค้าเดิมไม่เห็น)
- เฉพาะ **มือถือ**
- ตั้งแล้วมีผลทันที **ไม่มีสถานะร่าง**

## 3. มติที่ตัดสินระหว่างทาง

### D-IB-1 · `payload` ประกอบจาก **(ช่องทาง, ลำดับ)** ไม่ใช่ id ของแถว

ร่างแรกใช้ `ICEBREAKER:<row.id>` ซึ่ง **บังคับลำดับการทำงานที่ผิดกลับมาเอง**: id มีอยู่ก็ต่อเมื่อ
เขียน DB ไปแล้ว ⇒ ต้องเขียน DB ก่อนยิง Meta ⇒ **Meta ปฏิเสธเมื่อไหร่ ฐานเรามีคำถามชุดใหม่
ทั้งที่ลูกค้ายังเห็นชุดเก่า** แล้วหน้าจอรายงานว่า "ลูกค้าเห็นอยู่" ซึ่งไม่จริง — ย้อนกลับก็ไม่ได้
เพราะทรานแซกชันปิดไปแล้ว

`ICEBREAKER:<shopChannelId>:<order>` รู้ค่าล่วงหน้าได้ ⇒ สลับเป็น **ยิง Meta ก่อน สำเร็จแล้วจึง
เขียน DB** ⇒ ล้มแล้วไม่มีอะไรเปลี่ยนทั้งสองฝั่ง ผู้ขายแก้แล้วกดใหม่ได้

🛑 **แลกมาด้วยภาระใหม่: `payload` ระบุช่องทางมาเอง และมันมาจากภายนอกล้วน** ⇒ `answerIceBreaker()`
ต้องเทียบกับเพจที่ webhook มาจากจริง **ก่อน** เอาไปค้นฐานเสมอ ไม่งั้นใครก็ตามที่เดา payload ได้
จะสั่งให้เราส่งคำตอบของร้านอื่นออกไปได้ (มีเทส `[blocker]` ผูกลำดับ guard-ก่อน-lookup ไว้)

### D-IB-2 · เก็บคำตอบไว้ฝั่งเรา ไม่ฝากไว้กับ Meta

Meta เก็บเฉพาะ *คำถาม* + *payload* — คำตอบเป็นของเรา ⇒ ตาราง `ChannelIceBreaker` เก็บทั้งคู่
ทำให้แก้คำตอบได้โดยไม่ต้องแตะ Meta และค้นย้อนหลังได้ว่าคำถามไหนถูกแตะบ่อย (อนาคต)

### D-IB-3 · ลบทั้งชุดแล้วเขียนใหม่ ไม่ upsert รายข้อ

Meta ไม่มี partial update — ส่ง `ice_breakers` ไปคือแทนที่ทั้งก้อน
ถ้าฝั่งเราแก้ทีละแถว สถานะสองฝั่งจะเพี้ยนกันทันทีที่ผู้ขายลบข้อกลาง ๆ ออก
⇒ API มีแค่ `GET` + `PUT` (ส่ง `items: []` = ลบทั้งชุด) **ไม่มี POST/DELETE รายข้อโดยตั้งใจ**

### D-IB-4 · เพดานคำตอบ = **1,000** ไม่ใช่ 2,000

ux เสนอให้ reuse `QuickMessage.BODY_MAX` (2,000) โดยอ้าง HR16 — เหตุผลฟังขึ้นแต่ผิดในกรณีนี้
เพราะคำตอบถูกส่งเป็น **ข้อความแชทเข้า Instagram** ซึ่งเพดานจริงคือ 1,000 ตัวอักษร
ตั้ง 2,000 = ผู้ขายบันทึกผ่าน แล้ว Meta ปฏิเสธตอนลูกค้าแตะ ซึ่งเป็นเวลาที่ผู้ขายไม่อยู่ตรงนั้นแล้ว
(กฎที่ผิดจะเงียบจนถึงวินาทีที่แพงที่สุด)

### D-IB-5 · นับความยาวด้วย code point

ผู้ขายพิมพ์อิโมจิในคำถามได้จริง (HR12 ห้าม emoji ใน UI **ของเรา** ไม่ได้ห้ามข้อความของผู้ขาย)
🛑 **เหตุผลที่เขียนไว้รอบแรกว่า "เพราะภาษาไทย" ผิด** — ไทยอยู่ใน BMP ทั้งหมด `.length` เท่ากับ
จำนวน code point เป๊ะ · จับได้เพราะ **mutation ที่เปลี่ยนเป็น `.length` ยังเขียว** ⇒ เปลี่ยนตัวอย่าง
ในเทสเป็นอักขระนอก BMP แล้วจึงแดง (บันทึกไว้ที่ `mutation-silence-means-weak-corpus.md`)

## 5. เส้นทางตอนลูกค้าแตะคำถาม

```
ลูกค้าแตะปุ่ม
  └→ Meta ยิง webhook `postback` { title, payload, mid }   ← ไม่มี `message` มาด้วย
       ├→ ingestPostbackEvent()          — ต่ออายุหน้าต่างข้อความ (ของเดิม)
       ├→ ingestInboundMessage({ message: { mid, text: title } })
       │    บันทึก "คำถาม" เป็นข้อความของลูกค้า
       └→ after(() => answerIceBreaker()) — ส่งคำตอบที่ร้านตั้งไว้
```

🛑 **บันทึกคำถามผ่าน `ingestInboundMessage()` ตัวเดิม ไม่เขียนแถวเอง** — ingest ทำเรื่องที่ต้องถูก
อีกหลายอย่างให้ (กันซ้ำด้วย mid · อัปเดต preview · ปลุกเธรดที่ซ่อน · แจ้งเตือนผู้ขาย)
เขียนแถวเองคือก็อปตรรกะทั้งชุดมาไว้อีกที่แล้วรอวันที่มัน drift

🛑 **ไม่มี `mid` = ข้ามการบันทึกไปเลย** ยอมให้เธรดขาดคำถาม ดีกว่าประกอบ id เองแล้วชนกับ mid จริง
(`externalMessageId` เป็น `@unique` — ชนแล้ว **ข้อความจริงของลูกค้าจะเขียนไม่ลงทั้งใบ**)
เพิ่ม `mid` เข้า `postback` schema แล้ว (Meta ส่งมาตั้งแต่ v11 แต่ Valibot ของเราตัดทิ้งมาตลอด)

🛑 **ตอบใน `after()`** — Meta retry ทั้ง batch ถ้าเราตอบ webhook ช้า

## 6b. ชนกับที่ร้านตั้งเองบน Meta — และวิธีที่เราจัดการ (เพิ่ม 2026-08-27 รอบบ่าย)

user ถามเองว่า *"มันไม่ไปชนกันกับที่ตั้งค่าบน meta / ig เองหรอ"* — **ชนจริง และมีเอกสารรองรับ**

### สิ่งที่ Meta ประกาศไว้ (ฝั่ง Facebook เท่านั้น)

> **Page Profile Priority** — 1) API Ice Breakers · 2) Get Started button · 3) Custom Questions ที่ตั้งใน Page Inbox
> *"Editing Custom Questions from the Page Inbox UI is **disabled** when Ice Breakers are set via API"*

⇒ ของเรา **ทับ** ของร้าน **และล็อกไม่ให้ร้านแก้จากฝั่ง Facebook อีก** จนกว่าจะลบของเราออก

🛑 **ฝั่ง Instagram เอกสารไม่พูดถึงลำดับความสำคัญเลย** — copy บนหน้าจอจึงพูดต่างกัน:
FB เขียนตรง ๆ ว่าจะแก้จากฝั่งนั้นไม่ได้อีก · IG เขียนว่า *"ยังไม่ทราบแน่ชัด"*
**ห้ามเขียนแทน IG ว่าจะเกิดอะไร** จนกว่าจะยิงทดสอบกับบัญชีจริง

### ความผิดพลาดของ Controller ที่ทำให้เกิดช่องนี้

ผมสั่ง dev ตอนบรีฟว่า *"ไม่ต้องอ่านสถานะจาก Graph — ฐานเราตรงกับ Meta เสมอเพราะ service
ยิง Meta ก่อนแล้วจึงเขียน DB"* — **เหตุผลนั้นจริงเฉพาะกรณีที่เราเป็นคนตั้งเท่านั้น**
ร้านตั้งเองจากฝั่ง Meta ได้ตลอดเวลาโดยที่เราไม่รู้ ⇒ หน้าจอจะบอกว่า "ยังไม่ได้ตั้ง"
ทั้งที่ลูกค้าเห็นคำถามของร้านอยู่จริง แล้วร้านกดทับของตัวเองโดยไม่มีอะไรเตือน

### สิ่งที่ทำ

| ชิ้น | ราย
ละเอียด |
|---|---|
| `getIceBreakers()` + `parseIceBreakersResponse()` | อ่านค่าที่ Meta ถืออยู่จริง · **รับได้ 2 รูปแบบ** (`call_to_actions` ใหม่ / `ice_breakers` เก่า) เพราะ Meta คืนโครงตามที่ของเดิมถูกตั้งมา · **คืน `null` เมื่ออ่านไม่สำเร็จ ไม่ใช่ `[]`** |
| `classifyExternalIceBreakers()` | `OURS` / `NONE` / `FOREIGN` / `UNKNOWN` — เกณฑ์คือ **ทุกแถวต้องเป็นของเรา** ไม่ใช่มีของเราสักแถว (ปนกัน = FOREIGN ไม่งั้นแถวของร้านจะหายไปเงียบ ๆ) |
| แถบเตือนในหน้าแก้ไข | **โชว์คำถามเดิมให้เห็นทุกข้อ** ไม่ใช่แค่บอกว่ามี · ปุ่มไป Business Suite (เฉพาะ FB) · ปุ่มบันทึกเปลี่ยนคำเป็น **"แทนที่คำถามเดิมและบันทึก"** |
| `messenger-profile-rl.ts` | โควตา Meta **10 ครั้ง/10 นาที ต่อเพจ** — เราตั้งเพดาน **8** เผื่อคนอื่นในร้านกดพร้อมกัน · **จองก่อนยิงเสมอ** (คำขอที่ล้มก็กินโควตาไปแล้ว) · ข้อความบอก "อีกกี่นาที" |

### 🛑 อ่านจาก Meta **เฉพาะหน้าแก้ไข** ห้ามอ่านในหน้ารายการช่องทาง

Messenger Profile API จำกัด 10 ครั้ง/10 นาที **ต่อเพจ** ⇒ ถ้าแถวสถานะในหน้ารายการยิงถาม
ทุกครั้งที่โหลดหน้า ร้าน 3 เพจเปิดซ้ำ 4 รอบก็ทะลุ แล้วจะพังเป็น "ตรวจสอบสถานะไม่ได้" ทั้งหน้า
ซึ่งแย่กว่าไม่มีอะไรเลย — หน้าแก้ไขผู้ขายตั้งใจกดเข้ามา จึงคุ้มค่าเรียก
(หน้ารายการยังอ่านจากฐานเราเหมือนเดิม และยอมรับว่ามันอาจบอก "ยังไม่ได้ตั้ง" ผิด —
แต่จุดที่เกิดความเสียหายจริงคือตอน**กดบันทึก** ซึ่งอยู่ในหน้าแก้ไข และตรงนั้นเตือนแล้ว)

### ทำไมไม่บังคับกดยอมรับแบบ LINE Rich Menu

feature 00045 เจอปัญหาตระกูลเดียวกันเป๊ะ แล้วแก้ด้วย `consentAt` ที่บังคับใน service
**ต่างกันตรงที่ LINE อ่านของเดิมไม่ได้เลย** จึงต้องมีจุดยืนยันครั้งเดียวที่พูดครบทุกอย่าง
ส่วนที่นี่ของเดิมค้างอยู่บนจอตลอดเวลาที่ยังเป็น `FOREIGN` ⇒ แถบเตือนทำหน้าที่แทนได้แล้ว
เติมโมดัลอีกชั้น = เตือนซ้ำสิ่งที่อยู่ตรงหน้า
