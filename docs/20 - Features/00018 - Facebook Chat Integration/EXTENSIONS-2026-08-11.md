## 3. 🛑 ทำไม DEEP = 1 (ไม่ใช่ 10 ตามที่เสนอตอนแรก)

ตอนขออนุมัติผมเสนอ DEEP = 10 โดยให้เหตุผลว่า "ฝั่งเราไม่มีลิมิตจริง ตั้งเท่า Messenger เพื่อความคาดเดาได้"
**เหตุผลนั้นผิด** — พอไปอ่านโค้ดจริงพบว่าแอปผู้ซื้อ
(`src/app/(marketing)/(buyer-app)/messages/[shopId]/ChatThread.tsx`) วาดการ์ดสินค้าจาก `msg.productCard`
ซึ่งเป็น **ใบเดียว** ไม่มีตัวเรนเดอร์ carousel

ถ้าตั้ง 10 ตามที่เสนอไว้: ผู้ขายเลือก 5 ชิ้นในเธรด DEEP → ได้ 1 ข้อความ → **ลูกค้าเห็นสินค้าชิ้นแรก
ชิ้นเดียว อีก 4 ชิ้นหายเงียบ** ไม่มี error ไม่มี log — ซึ่งเข้าเกณฑ์ "ฟีเจอร์ที่ยังไม่เสร็จ" ไม่ใช่
"ข้อจำกัดที่รู้ตัว" ตาม `docs/conventions/known-limitation-vs-unfinished.md`

ตั้งเป็น 1 แล้วปล่อยให้กลไก "แบ่งเป็น N ข้อความ" (ซึ่งมีป้ายบอกผู้ขายก่อนกดส่งอยู่แล้วตาม D-2) ทำงานแทน
→ ลูกค้าได้ครบทุกชิ้นเสมอ · ผู้ขายรู้ล่วงหน้าว่าจะกลายเป็นกี่ข้อความ · ไม่ต้องแตะแอปผู้ซื้อรอบนี้

**หนี้ที่เปิดไว้:** วันที่แอปผู้ซื้อวาด carousel ได้ ให้ยกเลขนี้ขึ้น — แก้ที่ `CARDS_PER_MESSAGE.DEEP`
ที่เดียว ไม่มีที่อื่นต้องตาม (มีเทส `[blocker]` ล็อกค่านี้ไว้พร้อมเหตุผล)

## 4. Data model

```prisma
model ChatMessage {
  productRefId  String?    // ของเดิม — การ์ดใบเดียว (FK, onDelete SetNull)
  productRefIds String[]   // ใหม่ — การ์ดหลายใบ เรียงตามที่ผู้ขายเลือก
}
```

migration: `20260811130000_chat_message_product_refs` — additive ล้วน (`ADD COLUMN IF NOT EXISTS … DEFAULT '{}'`)
ไม่แตะ CHECK constraint ใด ๆ จึงไม่มีทางลบค่าของ migration สาขาอื่นที่รันคาบเกี่ยว
(`docs/conventions/migration-check-constraint-additive.md`)

**ทำไมคอลัมน์ใหม่ ไม่ใช้ `cards` (JSON) ที่มีอยู่แล้ว** — ระหว่างวางแผนผมตั้งใจจะ reuse `cards` เพื่อเลี่ยง
migration แล้วเปลี่ยนใจตอนลงมือ: `cards` เก็บ **snapshot** (title/subtitle/รูป) ของการ์ด carousel ที่มาจาก
Facebook ส่วนการ์ดสินค้าของเราต้อง **live-join** ถึงจะขึ้น "หยุดขายแล้ว"/"ไม่พบสินค้านี้แล้ว" ได้ตาม
BR-CTX-04 — ยัดสองความหมายลงคอลัมน์เดียวคือ HR16 ตรง ๆ

ไม่ทำ FK: Postgres ทำ FK บนคอลัมน์ array ไม่ได้ · id ที่ชี้สินค้าที่ถูกลบจะ resolve ไม่เจอตอน enrich แล้ว
การ์ดใบนั้นขึ้น "ไม่พบสินค้านี้แล้ว" — พฤติกรรมเดียวกับ `productRefId` ที่โดน `SET NULL`

**ไม่ backfill ของเก่า** — ว่าง = ข้อความการ์ดใบเดียว ใช้ `productRefId` เหมือนเดิมทุกประการ

## 5. API

### `POST /api/chat/conversations/[id]/messages`
เพิ่ม field `productRefIds?: string[]` (uuid, 1–36 ตัว) — ใช้แทน `productRefId` เมื่อส่งหลายชิ้น

- รวมสองทางเข้าเป็นรายการเดียวตั้งแต่บรรทัดแรก (`productRefIds ?? [productRefId]`) — ที่เหลือของ handler
  ไม่ต้องรู้ว่า client ส่งมาแบบไหน (สองเส้นทางขนานคือที่ที่ด่าน ownership จะหลุดไปข้างหนึ่ง)
- dedupe id ซ้ำ
- **ตรวจ ownership ทุก id** ด้วย `getProductsByIds` แล้วเทียบ `shopId` ทั้งชุด — ไม่ใช่ตรวจใบแรกแล้วเชื่อที่เหลือ
  (นั่นคือช่องส่งการ์ดสินค้าร้านอื่น)
- บังคับเพดานรวมที่ server ด้วย ตอบ 400 พร้อมตัวเลขจริง — ไม่ตัดทิ้งเงียบให้ร้านเข้าใจว่าส่งครบ
- แบ่งชุดด้วย `chunkProductCards` แล้ว **ส่งเรียงทีละชุด (ไม่ `Promise.all`)** — ยิงขนานแล้วปลายทาง
  จัดลำดับตามเวลาที่รับ ซึ่งสลับกันได้ ลำดับการ์ดคือสิ่งที่ผู้ขายตั้งใจ

**สถานะตอบกลับ**

| กรณี | สถานะ | เหตุผล |
|---|---|---|
| สำเร็จทุกชุด | 200 + ข้อความสุดท้าย | เหมือนเดิม |
| ชุดแรกล้ม | error เดิม (4xx/5xx) | ยังไม่มีอะไรถึงลูกค้า |
| ชุดที่ 2+ ล้ม | **207** + `{sentMessages, totalMessages}` | ลูกค้าได้ของบางส่วนไปแล้ว — ตอบ 500 เฉย ๆ จะทำให้ร้านกดส่งซ้ำทั้งชุดแล้วลูกค้าได้ของซ้ำ |

> 🛑 **แก้ 2026-08-11 (รอบสาม): `sentMessages` ถูกใช้จริงแล้ว — ก่อนหน้านี้ส่งมาแล้วไม่มีใครอ่าน**
> `sendProductCards` parse body ของ 207 อยู่แล้วแต่หยิบแค่ `error` ⇒ แผงคงติ๊กไว้ครบทุกใบ **รวมใบที่
> ถึงลูกค้าแล้ว** ขณะที่ข้อความ error สั่งว่า "เลือกเฉพาะรายการที่ยังไม่ได้ส่งแล้วลองใหม่" ซึ่งผู้ขาย
> ทำตามไม่ได้ (เห็นแค่ "1 จาก 3 ข้อความ" ไม่รู้ว่าข้อความที่ 1 บรรจุใบไหน ต้องรู้เพดานช่องทางแล้วหารเอง)
> → กดส่งซ้ำทั้งชุด = ลูกค้าได้การ์ดซ้ำ + บน LINE reply token ถูก claim ไปรอบแรก รอบสองตกไป push
> = โควตา = เงินร้าน
>
> ตอนนี้: `sentProductIds(ids, perMessage, sentMessages)` (SSOT ใน `lib/chat-product-card-batch.ts`)
> แปลงเลขกลับเป็นรายชื่อ id แล้วแผงติ๊กเฉพาะใบนั้นออกให้เอง คงที่เหลือไว้ให้กดส่งซ้ำได้ทันที ·
> `sendProductCards` คืน `{ok, sentMessages}` แทน `boolean` · **ข้อความ 207 เปลี่ยนตามเป็น "เอารายการ
> ที่ส่งแล้วออกให้แล้ว กดส่งอีกครั้งเพื่อส่งส่วนที่เหลือ"** (คำต้องขยับตามพฤติกรรม — HR16)
>
> 🛑 ความถูกต้องของ `sentProductIds` พิงข้อเท็จจริงเดียว: route **หยุดทันทีที่ชุดใดล้ม** (`return 207`
> ไม่ใช่ `continue`) จึงไม่มีทางเป็น "ชุด 1 กับ 3 สำเร็จ ข้าม 2" — วันไหนเปลี่ยนตรงนี้ **ต้องกลับมาแก้
> ฟังก์ชันนั้นด้วย** ไม่งั้นจะติ๊กของที่ยังไม่ถึงลูกค้าออกทิ้งเงียบ ๆ (มีเทส `[blocker]` ล็อกทั้งสองฝั่ง)
>
> ด่านกันซ้ำเดิม (`chat-product-resend.ts`, `8e030323`) **ครอบไม่ถึงเคสนี้โดยตั้งใจ** — มันเทียบ "ชุดเดิม
> ทั้งชุด" ส่วน 207 มีประวัติสั้นกว่า `batches` เลยคืน `false` ทันที ซึ่งถูกแล้ว ถ้ามันบล็อกตรงนั้นผู้ขาย
> จะกู้ส่วนที่เหลือไม่ได้เลย — สองด่านทำคนละหน้าที่

### `GET .../messages`
เพิ่ม `productCards: (ChatProductCard \| null)[] \| null` — `null` ทั้งก้อน = การ์ดใบเดียว (ใช้ `productCard` เดิม)
สมาชิกที่เป็น `null` = สินค้าถูกลบหลังส่ง **คงตำแหน่งไว้ ไม่ filter ทิ้ง** เพื่อให้ UI วาด "ไม่พบสินค้านี้แล้ว"
เป็นใบหนึ่งในแถว ไม่ใช่การ์ดหายไปเฉย ๆ แล้วผู้ขายนึกว่าส่งไม่ครบ

  (กฎ `docs/conventions/overlay-scroll-lock.md` ใช้กับของที่ประกอบเองแล้ว *ลอยทับ* เท่านั้น)
- ใบที่ติ๊กใช้ `ring-2 ring-info` **ไม่ใช่ `border-2`** — ความหนาขอบที่เปลี่ยนจะดันการ์ดทั้งแถวขยับ 1px
  ทุกครั้งที่ติ๊ก/เอาออก (ring วาดนอก layout box) · กล่องสไลด์ต้องมี `-mx-0.5 px-0.5` เผื่อที่ให้ ring
  ไม่งั้น `overflow-x-auto` ตัด ring ของใบซ้ายสุดหายไปข้างเดียวตอน `scrollLeft=0`
  มาฟรี (`docs/conventions/overlay-scroll-lock.md`)
- ส่งไม่สำเร็จ → ชีตเปิดค้าง ของที่เลือกยังอยู่ครบ กดใหม่ได้โดยไม่ต้องเลือกซ้ำ
