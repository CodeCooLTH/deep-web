# PRD — คิวงานใช้งานได้จริงครบวงจร (SERVICE_QUEUE End-to-End)

> feature 00050 · เริ่ม 2026-08-15 · ขอบเขต: **`Shop.vertical = SERVICE_QUEUE` เท่านั้น**
> ห้ามกระทบร้าน `ONLINE_SALES` / `LODGING` ซึ่งมีลูกค้าใช้งานจริงอยู่

## 1. ที่มา

หัวหน้าไล่ใช้งานจริงแล้วสรุปมา 5 ข้อ (บันทึกดิบเก็บไว้ที่ §7) ใจความคือ
**"ร้านบริการเปิดงาน เก็บมัดจำ ตามงาน แล้วปิดงานได้จบในที่เดียว"** ซึ่งวันนี้ยังทำไม่ได้

ร้านอ้างอิงที่ใช้ตรวจ: **BT Premium - สุขสวัสดิ์** (`btpremiumsuksawad`) —
8 ออเดอร์ · 7 ใบมีเวลานัด · 3 บริการ · 2 เพจ · 7 คนในทีม
🛑 เป็นร้านที่ลูกค้าใช้จริง — ห้ามแก้ข้อมูล ใช้ดูอย่างเดียว

## 2. ปัญหาแกนกลาง

ระบบรู้ว่า **ควรเก็บมัดจำเท่าไร** (`ServiceResource.depositMode/Value` → `Order.depositAmount`)
และเก็บ **รูปสลิป** ได้ (`Order.slipFileId`) — แต่ **ไม่มีที่ให้ร้านบันทึกว่า "ได้เงินแล้ว"**

โค้ดเขียนสารภาพไว้เองที่ `src/lib/appointment-summary.ts:34-40`:

> *"ระบบ **ไม่มีคอลัมน์ `depositReceivedAt`** จึงไม่รู้ว่าจ่ายหรือยัง"*

จึงต้องเลี่ยงไปใช้คำว่า **"มัดจำที่ตกลงไว้"** บนการ์ดที่ส่งให้ลูกค้า เพราะพูดไม่ได้ว่าเก็บแล้วหรือยัง

⇒ **รูโหว่เดียวนี้ทำให้ 4 ข้อที่เหลือของหัวหน้าทำไม่ได้ทั้งหมด** (แยกยอดมัดจำบน dashboard ·
ป้าย "รอยืนยัน/ชำระแล้ว" · ปุ่มในแชทกดแล้วไม่มีอะไรเปลี่ยน)

## 3. มติที่ user เคาะแล้ว (2026-08-15)

| # | คำถาม | มติ |
|---|---|---|
| D-1 | งานบริการ 1 ใบ เก็บเงินกี่ครั้ง | **2 ครั้ง — มัดจำ + ส่วนที่เหลือ** ระบบต้องรู้ทั้งสองก้อน และรู้ว่ายังค้างเท่าไร |
| D-2 | "จัดการสินค้าได้ด้วย" | **ทั้งสองอย่าง** — ขายของพ่วงบริการในบิลเดียว **และ** แก้/เพิ่มรายการหลังสร้างงานแล้ว |
| D-3 | มัดจำ 2 แบบในแชท | **ทั้งคู่** — (A) ร้านแจ้งยอดก่อนแล้วส่งการ์ดให้ลูกค้า (B) ลูกค้าส่งสลิปมาในแชท ร้านกดที่รูปนั้นแล้วเลือก "ใช้เป็นมัดจำของงาน…" |

## 4. เส้นทางที่ต้องใช้ได้จริง (Definition of Done)

| ขั้น | วันนี้ | ต้องเป็น |
|---|---|---|
| 1. ลูกค้าทักมาในแชท | ✅ | คงเดิม |
| 2. ร้านเปิดงาน + นัดคิว | ✅ | คงเดิม |
| 3. **แจ้งมัดจำ** | ❌ ไม่มีปุ่มในแชท · แก้ยอดทีหลังไม่ได้ | ปุ่มในแชท 2 ทาง (D-3) · แก้ยอดได้ |
| 4. ลูกค้าโอน + แนบสลิป | ⚠️ แนบได้ที่ `/o/[token]` แต่ส่งในแชทแล้วผูกกับงานไม่ได้ | ผูกสลิปจากแชทเข้างานได้ |
| 5. **ร้านยืนยัน "รับเงินแล้ว"** | ❌ **ไม่มีเลย** | ปุ่ม + บันทึกเวลา + ใครกด |
| 6. ถึงวันนัด → **เข้ารับบริการ** | ⚠️ กดได้ที่ตารางงาน/หน้าออเดอร์ ไม่ได้ที่แชท | กดได้จากแชทด้วย |
| 7. **walk-in (เดินเข้ามาเลย)** | ❌ โค้ดเขียนเองว่า *"ไม่อยู่ในแกนนี้เลย"* | มีที่ยืนในตารางงาน |
| 8. จบงาน → เก็บส่วนที่เหลือ | ❌ | บันทึกได้ รู้ว่าค้างเท่าไร |
| 9. ลูกค้ายืนยัน + รีวิว | ⚠️ ใช้ได้ แต่หน้าอ่านไม่รู้เรื่อง | จัดหน้าใหม่ + แสดงเพจต้นทาง |

## 5. ขอบเขต

**ทำ:** ทุกข้อใน §4 เฉพาะร้าน `SERVICE_QUEUE`

**ไม่ทำรอบนี้:** ระบบชำระเงินออนไลน์จริง (ยังเป็นโอน+สลิปเหมือนเดิม) · ใบเสร็จ/ภาษี ·
คืนเงินมัดจำอัตโนมัติ · แจ้งเตือนก่อนถึงนัด

**ห้ามกระทบ:** `ONLINE_SALES` (พัสดุ/สต็อก/ประมูล) · `LODGING` (มัดจำ+สลิปของบ้านพัก
ซึ่งเป็นคนละโดเมนโดยเจตนา — ดู `appointments.ts:53-58`)

## 6. ตัววัดว่าสำเร็จ

ร้าน BT Premium ทำครบ 9 ขั้นใน §4 ได้โดย **ไม่ต้องออกจากแชท** ยกเว้นขั้นที่ต้องดูตารางงาน
และหน้า `/o/[token]` ที่ส่งให้ลูกค้าต้องตอบได้ว่า *ใครนัด · เมื่อไร · จ่ายไปเท่าไร · ค้างเท่าไร*
โดยไม่ต้องถามร้านกลับ
