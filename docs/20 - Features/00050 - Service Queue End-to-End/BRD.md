# BRD — คิวงานใช้งานได้จริงครบวงจร (feature 00050)

> กฎธุรกิจ + เกณฑ์ยอมรับ · ขอบเขต `SERVICE_QUEUE` เท่านั้น

## §1 กฎเรื่องเงิน (แกนของฟีเจอร์)

| # | กฎ |
|---|---|
| BR-SQ-01 | งานบริการ 1 ใบเก็บเงินได้ **2 ก้อน**: **มัดจำ** (`depositAmount`) และ **ส่วนที่เหลือ** — ระบบต้องตอบได้เสมอว่า *ตกลงไว้เท่าไร · รับมาแล้วเท่าไร · ค้างเท่าไร* |
| BR-SQ-02 | 🛑 **"ยอดที่ตกลง" ≠ "ยอดที่ได้รับ"** — ห้ามใช้ `depositAmount > 0` แทนความหมายว่าเก็บแล้ว นี่คือความกำกวมที่ทำให้ต้องเลี่ยงไปใช้คำว่า "มัดจำที่ตกลงไว้" มาตลอด |
| BR-SQ-03 | ยอดค้าง = `totalAmount − (มัดจำที่รับแล้ว) − (ส่วนที่เหลือที่รับแล้ว)` · **ห้ามคำนวณจาก `depositAmount` ที่ยังไม่ได้รับ** |
| BR-SQ-04 | รับเงินแต่ละก้อนต้องบันทึก **เวลา + คนที่กด** — เป็นหลักฐานเรื่องเงิน ทีมมีหลายคน (ร้านอ้างอิงมี 7 คน) |
| BR-SQ-05 | มัดจำ **ไม่กั้นคิว** — จองได้โดยยังไม่จ่าย (คงกฎเดิม BR-RSV-49/50 ต่างจากบ้านพักที่มัดจำ > 0 บังคับแนบสลิปก่อนยืนยัน) |
| BR-SQ-06 | ยอดมัดจำ **แก้ได้หลังสร้างงาน** ตราบใดที่ยังไม่ได้รับเงิน · รับแล้วต้อง "ยกเลิกการรับ" ก่อน (มีบันทึกว่าใครยกเลิก) |
| BR-SQ-07 | `depositValue = 0` = ไม่เก็บมัดจำ → **ซ่อนส่วนมัดจำทุก surface** (คงกฎเดิม BR-RSV-44) |

## §2 กฎเรื่องสลิป

| # | กฎ |
|---|---|
| BR-SQ-10 | สลิปผูกกับ **ก้อนเงิน** ไม่ใช่ผูกกับออเดอร์ — 1 งานมีสลิปได้หลายใบ (มัดจำใบหนึ่ง ส่วนที่เหลืออีกใบ) |
| BR-SQ-11 | สลิปเข้าระบบได้ **2 ทาง**: ลูกค้าแนบเองที่ `/o/[token]` · ร้านกดจากรูปในแชทแล้วผูกเข้างาน (D-3 แบบ B) |
| BR-SQ-12 | 🛑 **การมีสลิป ≠ ได้รับเงิน** — ต้องมีคนกดยืนยันเสมอ สลิปปลอมมีจริง และรูปที่แนบผิดบิลก็มีจริง |
| BR-SQ-13 | เงินสด/โอนหน้าร้านต้องบันทึกได้โดย**ไม่ต้องมีสลิป** (หัวหน้า: *"เข้ามาหน้าร้านจ่ายเลย"*) |

## §3 กฎเรื่องการเข้ารับบริการ

| # | กฎ |
|---|---|
| BR-SQ-20 | มี **2 ทางเข้า**: จองล่วงหน้า (มี `serviceStart`) · **walk-in** (เดินเข้ามาเลย) — ทั้งคู่ต้องปรากฏในตารางงานของวันนั้น |
| BR-SQ-21 | 🛑 walk-in **ไม่ใช่ "นัดที่ไม่มีเวลา"** — มันคืองานที่เริ่ม ณ เวลาที่กด ต้องมีเวลาเริ่มจริง ไม่ใช่ปล่อย null แล้วหายจากทุกจอ (วันนี้ร้านอ้างอิงมี 1 ใบตกหล่นแบบนี้) |
| BR-SQ-22 | "เข้ารับบริการ" กดได้จาก **แชท · ตารางงาน · หน้าออเดอร์** — ทั้ง 3 ที่ต้องเปลี่ยนสถานะเดียวกัน (`appointmentStatus = COMPLETED`) |
| BR-SQ-23 | ปิดงานโดยยังค้างเงินได้ **แต่ต้องเตือน** — ห้ามบล็อก (ร้านบริการปิดงานก่อนเก็บเงินเป็นเรื่องปกติ) |

## §4 กฎเรื่องรายการในบิล

| # | กฎ |
|---|---|
| BR-SQ-30 | บิลเดียวมีได้ทั้ง **บริการ** และ **สินค้า** (D-2) |
| BR-SQ-31 | แก้/เพิ่มรายการหลังสร้างงานได้ → `totalAmount` เปลี่ยน → **ยอดค้างต้องคำนวณใหม่ทันที** |
| BR-SQ-32 | 🛑 มัดจำแบบ `PERCENT` คิดจากยอดรวม — ถ้ายอดรวมเปลี่ยนหลังรับมัดจำไปแล้ว **ห้ามคิดยอดมัดจำใหม่ย้อนหลัง** (เงินที่รับมาแล้วคือข้อเท็จจริง) ให้ไปโผล่ที่ยอดค้างแทน |

## §5 เกณฑ์ยอมรับ

| # | เกณฑ์ |
|---|---|
| AC-SQ-01 | ร้านเปิดงานจากแชท → แจ้งมัดจำ → ลูกค้าแนบสลิป → ร้านกดรับเงิน → ถึงวันนัดกดเข้ารับบริการ → เก็บส่วนที่เหลือ → ปิดงาน **ครบโดยไม่ออกจากแชท** (ยกเว้นดูตารางงาน) |
| AC-SQ-02 | ลูกค้าส่งสลิปในแชท → ร้านกดที่รูป → เลือกงาน → ผูกเป็นมัดจำได้ |
| AC-SQ-03 | walk-in กดจากแชทได้ และโผล่ในตารางงานวันนั้นทันที |
| AC-SQ-04 | Dashboard แสดง **ยอดเงินที่ได้รับจริงของวันนี้** แยก "มัดจำ" กับ "เต็มจำนวน" — ไม่ใช่ยอดขายตามบิล |
| AC-SQ-05 | ไทล์ "นัดวันนี้" พาไป **ตารางงาน** ไม่ใช่รายการออเดอร์ — 🛑 **เป็นการย้อนมติ 2026-08-10** ที่ user เคยสั่งให้เปลี่ยนจาก `/queues` มาเป็น `/orders?apptDay=today` (เหตุผลตอนนั้น: ไทล์ทั้ง 4 ในแถบควรไปที่เดียวกัน) · user ยืนยันกลับมติ 2026-08-15 · ตัวกรอง `?apptDay=` ของหน้า `/orders` **ยังอยู่ครบ** เข้าถึงจากชีตตารางงานรายวัน ไม่ได้ถอดฟีเจอร์ · เลขบนไทล์ตรงกับที่เห็นใน `/queues` เพราะ `serviceStart`/`serviceResourceId` ถูกเขียนคู่กันเสมอโดย `allocateSeat()` (ตรวจแล้วไม่มีเส้นทางไหนตั้งตัวเดียว) |
| AC-SQ-06 | `/o/[token]` ตอบได้ว่า *ใครนัด · เมื่อไร · จ่ายไปเท่าไร · ค้างเท่าไร · มาจากเพจไหน* โดยไม่ต้องถามร้าน |
| AC-SQ-07 | 🛑 ร้าน `ONLINE_SALES` และ `LODGING` **ไม่เห็นอะไรเปลี่ยนเลย** — ต้องมีเทสยืนยัน ไม่ใช่แค่ตั้งใจ |
