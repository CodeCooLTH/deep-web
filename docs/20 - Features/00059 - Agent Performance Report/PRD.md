# PRD: รายงานผลงานแอดมิน

---

## Executive Summary

ร้านที่มีพนักงานหลายคนตอบแชทอยู่ทุกวัน แต่ระบบไม่เคยตอบคำถามพื้นฐานของหัวหน้าได้เลยสักข้อ:
ใครตอบเร็ว · ใครรับงานเยอะ · ใครปิดการขายได้ · ยอดขายที่มาจากแชทเป็นของใคร

ข้อมูลดิบมีอยู่ครบแล้วในระบบ (`ChatMessage.senderUserId`, `Order.createdByUserId`,
`Order.conversationId`) แต่ไม่มีหน้าจอไหนรวมมันเข้าด้วยกัน — ฟีเจอร์นี้คือหน้ารายงานที่ทำสิ่งนั้น
**โดยไม่เพิ่มตารางใหม่ ไม่เพิ่มโครงสร้างพื้นฐานใหม่ และไม่แก้พฤติกรรมของหน้าอื่น**

---

## 1. Business Goals & KPIs

| # | เป้าหมายธุรกิจ | ตัวชี้วัด |
|---|---|---|
| G-1 | หัวหน้าประเมินทีมด้วยตัวเลขจริง ไม่ใช่ความรู้สึก | เปิดหน้ารายงานอย่างน้อย 1 ครั้ง/สัปดาห์ ต่อร้านที่มีพนักงาน ≥2 คน |
| G-2 | ลดเวลาตอบครั้งแรก | ค่ามัธยฐานของ "ตอบครั้งแรก" ระดับร้านลดลงเทียบกับ 4 สัปดาห์ก่อนเปิดใช้ |
| G-3 | เห็นว่ายอดขายจากแชทมาจากใคร | สัดส่วนออเดอร์ที่ยกเครดิตได้ (ไม่ตกกอง "ไม่ระบุ") ≥ 80% |

---

## 2. User Personas

| Persona | คือใคร | ต้องการอะไรจากหน้านี้ |
|---|---|---|
| **เจ้าของร้าน / หัวหน้าทีมแชท** | `Shop.userId` หรือ `ShopMember(role='OWNER')` | เทียบคนในทีมได้เร็ว ๆ ว่าใครควรได้รับคำชม/ควรได้รับการช่วยเหลือ |
| **พนักงานร้าน (แอดมิน)** | `ShopMember(role='ADMIN')` | เห็นตัวเลขของตัวเอง รู้ว่าตอบช้าไปไหม |

**ผู้ที่ไม่ใช่ผู้ใช้ของหน้านี้:** ผู้ซื้อ (ไม่เห็นอะไรเลย) และแอดมินของแพลตฟอร์ม (`admin.*` — คนละโดเมน)

## 3. Business Requirements

| ID | ความต้องการ | ที่มา |
|---|---|---|
| FR-AP-01 | มีหน้ารายงานที่กรองได้ด้วย ช่วงเวลา · ช่องทาง · ที่มาของแชท · เพจ/บัญชี | โจทย์ §1 |
| FR-AP-02 | ช่วงเวลาตั้งต้น = 7 วันล่าสุด และเทียบกับช่วงก่อนหน้าที่ยาวเท่ากัน | โจทย์ §1 |
| FR-AP-03 | การ์ดสรุป 7 ตัว: แชททั้งหมด · ตอบครั้งแรก · ตอบเฉลี่ย · คำสั่งซื้อ · ปิดการขาย · อัตราปิดการขาย · ยอดขาย | โจทย์ §2 |
| FR-AP-04 | ตารางจัดอันดับรายคน เรียงได้ทุกคอลัมน์ที่เป็นตัวเลข | โจทย์ §3 |
| FR-AP-05 | กดที่คนแล้วเห็นรายละเอียด + แนวโน้มรายวัน + รายการบทสนทนา | โจทย์ §4 |
| FR-AP-06 | มีเกณฑ์ SLA และแสดง % ที่ตอบทันเกณฑ์ | โจทย์ §7 |
| FR-AP-07 | สิทธิ์เข้าถึงใช้กลไกเดิมของระบบ ไม่สร้างระบบสิทธิ์ใหม่ | โจทย์ §12 |

## 4. Business Rules & Constraints

| ID | กฎ |
|---|---|
| BR-AP-01 | **"แอดมิน" = คนของร้าน** (เจ้าของ + `ShopMember`) — ระบบไม่มีตาราง Agent แยก และจะไม่สร้าง |
| BR-AP-02 | **นับเฉพาะคำตอบที่คนเป็นผู้ส่งและระบุตัวได้** — บอท/ข้อความระบบ/คำตอบจาก Business Suite ไม่นับเป็นผลงานของใคร |
| BR-AP-03 | คำตอบที่ระบุตัวไม่ได้ **ต้องถูกรายงานเป็นจำนวน** บนหน้าจอ ห้ามกลืนหาย |
| BR-AP-04 | ตัวหารของอัตราปิดการขายคือ "แชทที่เข้าเกณฑ์" ไม่ใช่แชททั้งหมด (นิยามใน SRS §3) |
| BR-AP-05 | "ยอดขาย" ใช้นิยามเดิมของระบบ (`src/lib/order-revenue.ts`) — ห้ามนิยามใหม่ |
| BR-AP-06 | หนึ่งแชทที่มีหลายออเดอร์ = ปิดการขายได้ **หนึ่ง** แชท |
| BR-AP-07 | ยังไม่มี "คะแนนรวม" — หัวหน้าต้องเห็นตัวเลขดิบก่อน |
| BR-AP-08 | ช่วงเวลาที่ขอได้ครั้งละไม่เกิน 92 วัน (เพดานเชิงเทคนิค ต้องบอกผู้ใช้เมื่อถูกหั่น) |

---

## 5. Out of Scope

- ระบบ "มอบหมายแชท" (assign/claim) — รายงานนี้ *อ่าน* ความเป็นเจ้าของจากร่องรอยที่มีอยู่ ไม่ได้สร้างกลไกใหม่
- ทีม/แผนก — ระบบยังไม่มีแนวคิดนี้ (`ShopMember.role` มีแค่ OWNER/ADMIN)
- เวลาทำการของร้าน (หักช่วงร้านปิดออกจากเวลาตอบ) — ยังไม่มีข้อมูลนี้ในระบบ
- ตั้งเกณฑ์ SLA เองต่อร้าน — โครงรองรับแล้ว แต่ยังไม่มีหน้าจอตั้งค่า
- ส่งออก CSV / ตั้งเวลาส่งรายงานเข้าอีเมล
- คะแนนรวม (composite score) และการจัดอันดับแบบให้รางวัล

## 6. Risks & Mitigation

| ความเสี่ยง | ผลกระทบ | การลด |
|---|---|---|
| ร้านที่ตอบแชทจาก Business Suite เป็นหลัก จะเห็นตัวเลขเป็น 0 | หัวหน้าสรุปว่า "ทีมไม่ได้ทำงาน" | แถบเตือนบอกจำนวนคำตอบที่ระบุตัวไม่ได้ + อธิบายสาเหตุ (BR-AP-03) |
| ตัวเลขถูกใช้ประเมินคน แล้วคนแข่งกันตอบเร็วโดยไม่สนคุณภาพ | คุณภาพบริการตก | ไม่มีคะแนนรวม · แสดงทั้งค่าเฉลี่ยและค่ากลาง · มีตารางให้กดดูของจริง |
| เวลาตอบข้ามคืนดันค่าเฉลี่ยจนอ่านไม่ได้ | ตัวเลขไม่มีความหมาย | แสดงค่ากลางคู่เสมอ (ค่ากลางทนต่อค่าสุดโต่ง) |
| แชทที่คนสองคนช่วยกันตอบถูกนับให้ทั้งคู่ | ผลรวมคอลัมน์ "แชท" มากกว่าภาพรวมร้าน | เขียนกำกับบนหน้าจอ + คอลัมน์ที่ผูกกับเงินยกให้คนเดียวเสมอ |

## 7. Glossary

| คำ | ความหมาย |
|---|---|
| แชท / เธรด | `Conversation` หนึ่งแถว |
| รอบการรอ | ช่วงตั้งแต่ข้อความลูกค้าใบแรกที่ยังไม่ถูกตอบ จนถึงคำตอบของคนใบถัดไป |
| เข้าเกณฑ์ | แชทที่มีสิทธิ์ถูกนับเป็นตัวหารของอัตราปิดการขาย (ดู SRS §3) |
| ปิดการขายได้ | แชทที่มีออเดอร์ซึ่งนับเป็นยอดขายอย่างน้อย 1 ใบ |
| ยกเครดิต | การตัดสินว่าออเดอร์ใบหนึ่งเป็นผลงานของใคร (ดู SRS §3.5) |

## 8. Success Metrics

1. เวลาโหลดหน้ารายงานช่วง 7 วัน < 1.5 วินาที (p95)
2. ตัวเลขบนการ์ดกับตัวเลขที่ได้จากการกดเข้าไปดูรายการ **ตรงกันเสมอ** (ไม่มีเคส "กด 12 เข้าไปเจอ 9")
3. สัดส่วนออเดอร์ที่ยกเครดิตได้ ≥ 80%

## 9. Dependencies & Assumptions

**พึ่งพา**
- `ChatMessage.senderUserId` / `autoReplyKind` — มีตั้งแต่ 00018 / 00023
- `Order.conversationId` — มีตั้งแต่ 2026-08-12 (**ไม่ backfill ย้อนหลังโดยตั้งใจ**)
- `Order.createdByUserId` — มีตั้งแต่ 2026-08-04
- `Shop.staffCanViewFinance` — กลไกสิทธิ์เดิมของ 00016

**ข้อสมมติ**
- A-1 ออเดอร์ที่เกิดก่อน 2026-08-12 ไม่มี `conversationId` ⇒ **ไม่ปรากฏในรายงานนี้** ช่วงเวลาย้อนหลังไกลกว่านั้นจะเห็นอัตราปิดการขายต่ำกว่าความจริง
- A-2 `Conversation.createdAt` ≈ เวลาที่ลูกค้าทักเข้ามาครั้งแรก (จริงสำหรับช่องทางนอกทุกช่องทาง)
- A-3 ปริมาณข้อมูลระดับร้านเล็กพอให้คำนวณสดได้ (ChatMessage ทั้งฐาน ~40,700 แถว ณ 2026-08-20)
