# PRD — 00044 คืนเงิน/คืนสินค้าหลังส่งถึงมือลูกค้า

> สถานะ: **ร่าง รอ user review** (HR11 — ห้าม implement ก่อน PRD+BRD ผ่านสายตา user)
> วันที่: 2026-08-11 · ผู้เขียน: Controller (ไม่ได้ผ่าน `safepay-product` — session นี้ตั้งไว้ว่าห้ามเรียก
> agent เว้นแต่ user ขอ; user อนุมัติเฉพาะ `safepay-ux` สำหรับงาน frontend เท่านั้น) หากต้องการให้
> product agent ตรวจซ้ำ สั่งได้

## 1. ปัญหา

**คำพูดของ user (ตรงตัว):**
> "เจอ usage ที่ว่า สถานะขนส่ง OK แล้วนะไม่คืน แต่ใช้ไป 1 วันต้องคืนเงิน เพราะของเสียหาย หรือไม่ดี
> แล้วร้านตัดสินใจต้องคืน อยากให้มีการ mark ได้ว่าคืน และนำยอดออกจาก ยอดขายด้วย"

วันนี้ระบบรองรับ "ของไม่ถึงมือ" อยู่แล้ว (พัสดุตีกลับ — `carrierStatus ∈ {return, return_success}`
ซึ่ง `order-revenue.ts` ตัดออกจากยอดขายให้เรียบร้อย) แต่ **ไม่มีอะไรรองรับ "ถึงมือแล้ว ใช้แล้ว
แล้วค่อยคืน"** เลย:

- ไม่มีที่บันทึกว่าออเดอร์ใบนี้ถูกคืนเงิน
- ยอดขาย/กำไรยังนับใบนั้นเต็มจำนวนตลอดไป ⇒ ร้านอ่านรายงานแล้วเห็นเงินที่จ่ายคืนไปแล้วเป็นรายได้
- ทางเดียวที่ร้านทำได้ตอนนี้คือ "ยกเลิก" ทั้งใบ ซึ่ง **ผิดความจริง**: ของถูกส่งไปแล้ว มีต้นทุนเกิดจริง
  มีค่าส่งจ่ายจริง และถ้าคืนแค่บางส่วนก็บันทึกไม่ได้เลย

## 2. เป้าหมาย

ให้ร้าน **บันทึกการคืนเงินบนออเดอร์ที่ส่งถึงแล้ว** ได้ พร้อมระบุยอดที่คืนจริง แล้วให้ตัวเลขทุกหน้าจอ
สะท้อนความจริงนั้นทันทีโดยไม่ต้องคำนวณเอง

**ไม่ใช่เป้าหมายรอบนี้ (out of scope):**
- ระบบ RMA/ใบคำร้องขอคืนจากฝั่งผู้ซื้อ (ผู้ซื้อกดขอคืนเอง) — รอบนี้ **ร้านเป็นคนบันทึกฝ่ายเดียว**
- การคืนเงินอัตโนมัติผ่านช่องทางชำระเงิน — ระบบไม่ได้ถือเงิน ร้านโอนคืนเอง เราแค่บันทึก
- คืนเงินบางส่วน "รายชิ้น" (ระบุว่าคืนสินค้าชิ้นไหน) — รอบนี้คืนเป็น **ยอดเงิน** ไม่ผูกรายชิ้น
- พัสดุตีกลับ (มีอยู่แล้ว คนละเรื่อง — ดู §7)

## 3. ผู้ใช้ + สถานการณ์

| ผู้ใช้ | สถานการณ์ | สิ่งที่ต้องทำได้ |
|---|---|---|
| ผู้ขาย | ลูกค้าได้ของแล้ว ใช้ไป 1 วัน ของเสีย → ตกลงคืนเงินเต็ม | mark ว่าคืน + ระบุยอดเต็ม + ระบุว่าของกลับมาไหม |
| ผู้ขาย | ของมีตำหนิเล็กน้อย ตกลงคืนบางส่วน 200 จาก 890 ลูกค้าเก็บของไว้ | mark คืนบางส่วน 200 · ของไม่กลับ |
| ผู้ขาย | ดูรายงานยอดขาย/กำไรสิ้นเดือน | ยอดที่คืนไปแล้วต้องถูกหักออก ไม่ต้องมาลบเอง |
| ผู้ขาย | เผลอกดผิด | ยกเลิกการ mark ได้ แล้วตัวเลขกลับเป็นเดิม |

## 4. มติที่ user เคาะแล้ว (2026-08-11)

| # | มติ | ผลที่ตามมา |
|---|---|---|
| D-1 | **คืนบางส่วนได้** — ร้านกรอกยอดเอง | ตัดยอดขายต้องหักเป็น "จำนวนเงิน" ไม่ใช่ตัดทั้งใบ ⇒ กระทบทุกจุดที่ SUM ยอด ไม่ใช่แค่ที่กรองแถว (ดู §6) |

## 5. FR (Functional Requirements)

| id | ข้อกำหนด | Acceptance |
|---|---|---|
| FR-RF-01 | ร้าน mark "คืนเงิน" ได้บนออเดอร์ที่ **ส่งถึงแล้ว** เท่านั้น | ใบที่ยังไม่ส่ง/ยกเลิกแล้ว ไม่มีปุ่มนี้ และ API ปฏิเสธ |
| FR-RF-02 | ระบุยอดคืนได้ตั้งแต่ >0 จนถึงยอดเต็มของใบนั้น | กรอก 0 / ติดลบ / เกินยอดใบ → 400 พร้อมข้อความบอกเพดาน |
| FR-RF-03 | ระบุได้ว่าของกลับเข้าสต็อกไหม (บังคับเลือก ไม่มีค่าตั้งต้น) | ไม่เลือก → กดบันทึกไม่ได้ (ไม่เดาแทนร้าน) |
| FR-RF-04 | บันทึกเหตุผล (เลือกจากรายการ + ข้อความเสริม) | เหตุผลปรากฏในไทม์ไลน์ของออเดอร์ |
| FR-RF-05 | **ยอดที่คืนถูกหักออกจากยอดขายทุกหน้าจอ** | ดู §6 — ต้องตรงกันทุกจุด ไม่มีจอไหนยังนับเต็ม |
| FR-RF-06 | กำไรสะท้อนความจริงตาม D-2 | ของกลับ → ต้นทุนกลับด้วย · ของเสียหาย → ต้นทุนยังอยู่ (ขาดทุนจริง) |
| FR-RF-07 | ยกเลิกการ mark ได้ | ตัวเลขทุกจอกลับเป็นก่อน mark · ไทม์ไลน์เก็บทั้งการ mark และการถอน |
| FR-RF-08 | **สถานะออเดอร์ไม่เปลี่ยน** (ยังเป็น CONFIRMED/SHIPPED เดิม) | ดู §8 เหตุผล |
| FR-RF-09 | เห็นได้ทันทีว่าใบไหนถูกคืน | ป้ายบนแถวในรายการออเดอร์ + บนหน้ารายละเอียด |
| FR-RF-10 | **ไม่กระทบ Trust Score / อัตราความสำเร็จ / จำนวนดีลสำเร็จที่ผู้ซื้อเห็น** | ดู §8 |

## 6. 🛑 ผลกระทบต่อตัวเลข — จุดที่พลาดแล้วทั้งระบบเพี้ยน

นี่คือความเสี่ยงหลักของฟีเจอร์นี้ และเป็นเหตุผลที่ต้องมี PRD ก่อนโค้ด (HR16)

`src/lib/order-revenue.ts` เป็น **SSOT ตัวเดียวของ "ใบนี้นับเป็นยอดขายหรือยัง"** ทั้งระบบ — แต่มันตอบ

จุดที่รวมยอดและต้องแก้ให้ครบ (สำรวจแล้ว 2026-08-11):

| `services/dashboard.service.ts` | sum `totalAmount` group by วัน | หัก refund ต่อใบ · **หมายเหตุ: คอมเมนต์หัวไฟล์บอกเกณฑ์เป็น `status != CANCELLED` ซึ่งอาจไม่ตรงกับ `revenueOrderWhere` อยู่แล้ว — ต้องยืนยันตอน SDS ว่าเป็นสองนิยามจริงไหม** |

## 7. ความต่างจาก "พัสดุตีกลับ" (ต้องไม่ปนกัน)

| | พัสดุตีกลับ (มีอยู่แล้ว) | คืนเงินหลังส่งถึง (00044) |
|---|---|---|
| ของถึงมือลูกค้าไหม | **ไม่ถึง** | **ถึงแล้ว ใช้แล้ว** |
| ใครเป็นคนบอก | ขนส่ง (`carrierStatus`) | ร้านบันทึกเอง |
| นับเป็นยอดขายไหม | ไม่นับอยู่แล้ว | นับตอนแรก แล้วถูกหักตอน mark |
| เป็นพฤติกรรมลูกค้าไหม | **ใช่** (ผู้รับไม่รับ/ติดต่อไม่ได้) | **ไม่ใช่** (D-3) |
| คำที่ใช้บนจอ | "พัสดุตีกลับ" | ต้องเป็นคำอื่น — **ห้ามใช้คำว่า "ตีกลับ" ซ้ำ** |

🛑 มีเทส `[blocker]` อยู่แล้วใน `chat-product-card-batch`/`customer-behavior` ที่ล็อกคำว่า "พัสดุตีกลับ"
ห้ามเขียนเป็น "คืนของ" — ฟีเจอร์นี้ต้องตั้งคำของตัวเองที่ไม่ชนกัน (เสนอ: **"คืนเงินแล้ว"**)

## 8. สิ่งที่ต้อง **ไม่** เปลี่ยน (และเหตุผล)

1. **`Order.status` ไม่เพิ่มค่าใหม่** — enum นี้มี 4 ค่าและมีตรรกะ `status === 'CANCELLED' ? A : B`
   กระจายอยู่ทั่วระบบ การเพิ่มค่าที่ 5 จะไม่พังเสียงดัง แต่ค่าใหม่จะตกเข้า branch ผิดเงียบ ๆ
   (บทเรียน `docs/conventions/enum-value-removal.md` + เคสจริง 00028) ⇒ ใช้คอลัมน์เพิ่มแทน
2. **Trust Score / อัตราความสำเร็จ / จำนวนดีลสำเร็จ ไม่ขยับ** — ค่าเหล่านี้เป็นสัญญาณที่ **ผู้ซื้อ**
   ใช้ตัดสินใจ และการคืนเงินเป็นสิ่งที่ **ร้านบันทึกเอง** (BR-OSM-05: ให้สิ่งที่ร้านกรอกเองมีอำนาจ
   เหนือคะแนนสาธารณะ = ให้ร้านให้คะแนนตัวเอง) ⇒ กระทบเฉพาะ **ยอดขาย/กำไร ซึ่งร้านดูเอง**
   เหมือนที่ `order-revenue.ts` เคยตัดสินไว้แล้วตอน 2026-08-05
3. **ป้ายพฤติกรรมลูกค้าไม่ขยับ** (D-3)

## 9. Metrics

- จำนวนใบที่ถูก mark คืนเงินต่อเดือน (ถ้าเป็น 0 ตลอด = ฟีเจอร์ไม่ถูกใช้ ต้องกลับมาดูว่าปุ่มหาไม่เจอไหม)
- อัตราการถอน mark (สูง = UI ทำให้กดผิดง่าย)

## 10. คำถามที่ยังเปิด (ต้องเคาะก่อนหรือระหว่าง SDS)

1. **ค่าส่งคืนด้วยไหม** — ยอดคืน 890 คือรวมค่าส่ง 50 หรือไม่ (เสนอ: ให้ร้านกรอกยอดรวมที่โอนคืนจริง
   ไปเลย ไม่ต้องแยก เพราะร้านรู้ว่าตัวเองโอนไปเท่าไร)
2. **ใบที่ COD และยังไม่ได้รับเงิน** แล้วคืน — เป็นไปได้ไหมในทางปฏิบัติ หรือกันไม่ให้ mark
3. **ต้องบันทึกวันที่คืนเงินจริง** (อาจไม่ใช่วันที่กด) ไหม — กระทบว่ายอดถูกหักออกจากเดือนไหน
4. ใครมีสิทธิ์ mark — เจ้าของร้านเท่านั้น หรือ staff (`ShopMember`) ด้วย
