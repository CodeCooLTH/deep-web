## กติกาการใช้ reference นี้ (Hard Rule 6)

reference นี้เป็น **แอปอื่น** ดังนั้น:

| ชั้น | เอามาใช้ |
|---|---|
| **IA / โครงหน้า / ลำดับการอ่าน** | **ตาม reference** — เป็นสิ่งที่ผู้ใช้คุ้นอยู่แล้วจากการตั้งค่าฝั่ง Facebook |
| **skin / สี / component / spacing** | **ตาม Paces เท่านั้น** — หน้านี้อยู่ใต้ `(paces)/**` (seller) ห้ามลอกสีน้ำเงิน Facebook ห้าม arbitrary Tailwind value (Hard Rule 7) |
| **ไอคอน** | ใช้ `@iconify/react` tabler เท่านั้น — **ห้าม emoji** (Hard Rule 12) แม้ reference จะมี |

## สิ่งที่สังเกตได้จาก reference

### โครงหน้า (บนลงล่าง)

1. **Breadcrumb** — `Inbox > Automations > Edit automation`
2. **หัวเรื่อง + สวิตช์เปิด/ปิด อยู่บรรทัดเดียวกัน** พร้อมคำอธิบายใต้หัวเรื่องว่าระบบนี้ทำอะไร
3. **การ์ดเรียงลงมาเป็นขั้น ๆ มีเส้นเชื่อมแนวตั้งทางซ้าย** สื่อว่าเป็นลำดับ if→then
   - `Channel` — เลือกช่องทาง (checkbox Messenger / Instagram)
   - `When this happens` — เงื่อนไข (อ่านอย่างเดียว บอกเป็นประโยค)
   - `Take this action` — การกระทำ + ช่องพิมพ์ข้อความ
4. **ช่องข้อความมีตัวนับอักษร** มุมขวาบนของกล่อง (`115/500`)
5. **แถวปุ่มเล็กใต้ช่องข้อความ** — ปุ่มช่วยเขียนด้วย AI + ปุ่มแทรก emoji
6. **`Media · Optional`** — ปุ่ม Add media แยกจากช่องข้อความ
7. **แผงพรีวิวด้านขวา** — จำลองหน้าตาแชทจริง แสดงบับเบิลข้อความที่กำลังพิมพ์แบบสด + ปุ่ม `Preview in Messenger`
8. **Footer ปุ่ม `Cancel` / `Save changes`** ชิดขวา — `Save changes` เป็น disabled จนกว่าจะมีการแก้

### สิ่งที่เอามาใช้ได้ทันที

| จาก reference | เอาไปใช้กับ |
|---|---|
| สวิตช์เปิด/ปิดอยู่บนสุดคู่กับหัวเรื่อง | สวิตช์ `AutoReplyConfig.isEnabled` ระดับร้าน (FR-015) |
| การ์ดเรียงเป็นขั้นมีเส้นเชื่อม | Keyword Editor ที่มีหลาย section (BRD §18.2 ระบุ 10 ส่วน) |
| ตัวนับอักษรในช่องข้อความ | `replyText` มีเพดานความยาว (AC-005-04 บังคับให้แสดงจำนวนอักษรปัจจุบัน) |
| **แผงพรีวิวสดด้านขวา** | **Rule Tester (FR-020)** — ของเราแรงกว่าตรงที่แสดง keyword ที่ match / ระดับกฎ / เหตุผลที่กฎอื่นแพ้ ไม่ใช่แค่บับเบิล |
| `Media · Optional` | ยังไม่ทำในเฟสนี้ — เฟสแรกตอบข้อความล้วน (บันทึกเป็นของเฟส 2) |

### สิ่งที่ **ต่างจากของเราอย่างมีนัยสำคัญ**

Facebook ทำแค่ **"ตอบข้อความแรกที่ใครก็ตามทักเข้ามา"** — ไม่มีการจับ keyword ไม่มีการแยกตามโฆษณา ไม่มีการถอยระดับ

ของเรามีมากกว่านั้นทั้งหมด:

| เรื่อง | Facebook | ของเรา |
|---|---|---|
| เงื่อนไขการตอบ | ข้อความแรกเท่านั้น | กลุ่มคำ + คำตรวจจับหลายคำ + 3 รูปแบบการจับ |
| ความละเอียดของคำตอบ | 1 ข้อความต่อ 1 automation | 9 ระดับ (เพจ/โฆษณา/สินค้า) + ถอยระดับอัตโนมัติ |
| โหมดทดสอบ | ไม่มี | allowlist เธรดจริง + หน้าทดสอบแบบกรอกเอง |
| บันทึกย้อนหลัง | ไม่มี | บันทึกทุกการตัดสินใจ รวมกรณีไม่ตอบ + เหตุผล |
| หยุดเมื่อพนักงานตอบ | ไม่มี | มี |

⇒ **ลอกโครง 1:1 ไม่ได้** หน้าของเราต้องมีที่ให้ตั้งกลุ่มคำและกฎหลายระดับ ซึ่ง reference ไม่มีให้ดู
⇒ แต่ **"ความรู้สึก" ของหน้าควรใกล้เคียง** — เรียบ เป็นขั้นตอน มีพรีวิวให้เห็นผลทันที ไม่ใช่ฟอร์มยาวเหยียดที่ต้องเดาว่ากรอกแล้วจะได้อะไร

### จุดที่ reference ทำแล้วเราต้อง **ไม่ทำตาม**

- **emoji ในข้อความตัวอย่างและปุ่มแทรก emoji** — ข้อความที่ *ร้านพิมพ์เอง* มี emoji ได้ (เป็น content ของผู้ใช้) แต่ **UI ของเราห้ามใช้ emoji เป็นไอคอน** (Hard Rule 12) ปุ่มแทรก emoji ในช่องพิมพ์ = ฟีเจอร์ ไม่ใช่ไอคอน ถ้าจะมีต้องใช้ไอคอน tabler เป็นหน้าปุ่ม
- **ปุ่มช่วยเขียนด้วย AI** (ไอคอนดาวในภาพ) — **เฟสนี้ไม่มี AI** ห้ามใส่ปุ่มนี้ ถ้าใส่แล้วกดไม่ได้จะยิ่งแย่กว่าไม่มี
- **สีน้ำเงิน Facebook** — ของเราใช้ `bg-primary` ของ Paces (`#236dc9`) ห้าม hardcode

## คำตัดสินของผู้ใช้ 2026-07-29 (FROZEN — `safepay-ux` ต้องยึดตามนี้)

| # | คำตัดสิน | ผล |
|---|---|---|
| 1 | **ขอบเขตที่เอามาจาก reference = "หน้าตั้งค่า" เท่านั้น** — ผู้ใช้ระบุชัด: *"ไม่ต้องทำสีตาม Facebook"*, *"สีตาม Paces แค่ให้ UI หน้าตั้งค่า"* | เอา **IA/โครง/ลำดับการอ่าน** มาใช้ · **สี/skin/component = Paces ล้วน** (`bg-primary` `#236dc9`, `.card`, `.btn`, token เท่านั้น) ห้ามมีร่องรอยสีหรือ component ของ Facebook |
| 2 | **โครงหน้า = 2 หน้า ตาม BRD §18.1 + §18.2** (ไม่ใช่หน้าเดียวยาวแบบ reference) | หน้า 1 = รายการกลุ่มคำ (ชื่อ / จำนวนคำตรวจจับ / จำนวนกฎ / สถานะเปิดปิด) + สวิตช์ระดับร้านอยู่บนสุด → คลิกเข้าหน้า 2 = แก้กลุ่มนั้น (คำตรวจจับ / คำตอบกลาง / แยกตามเพจ / แยกตามโฆษณา / แยกตามสินค้า / ทดสอบ). เหตุผล: ร้านที่มีหลายสิบกลุ่มคำจะเลื่อนยาวเกินไปถ้าอยู่หน้าเดียว |
| 3 | **แผงพรีวิว = ทั้งสองอย่างซ้อนกัน** — บับเบิลแชท **และ** เหตุผลการตัดสิน | บนสุดแสดงบับเบิลข้อความที่ลูกค้าจะได้รับจริง (แบบ reference) ใต้ลงมาแสดง: กลุ่มคำที่ match / คำตรวจจับที่ตรง / ระดับกฎที่ใช้ / **เหตุผลที่กฎอื่นไม่ถูกเลือก** — ข้อหลังคือสิ่งที่ AC-020-04 บังคับไว้ และเป็นสิ่งที่ reference ไม่มี |

### สิ่งที่คำตัดสินนี้ปิดไปแล้ว
- ไม่ต้องถามเรื่องสีอีก — Paces ล้วน ไม่มีข้อยกเว้น
- ไม่ต้องทำ accordion หน้าเดียว
- แผงพรีวิวไม่ใช่ของตกแต่ง แต่เป็นส่วนที่ปิด AC-020-03/04
