## Section breakdown

- **Header strip**: ไอคอน `tabler:shield-check` สี Signal Cyan (`#00BAD1`) + หัวข้อ **"Deep ตรวจสอบร้านนี้ต่อเนื่อง"** + บรรทัดขั้นปัจจุบันเป็นคำ (ไม่ใช่ตัวเลข) + จุดไล่ระดับ 4 จุด (decorative, `aria-hidden` — ข้อความข้างบนแบกความหมายอยู่แล้ว)
- **หลักฐานย่อ**: สูงสุด 2-3 ข้อเด่นของขั้นปัจจุบัน **ไม่ใช่ตัวหาร N/18** (เพื่อไม่ให้อ่านเป็นคะแนน)
- **รอบตรวจล่าสุด (preview)**: รอบล่าสุดเท่านั้น + ภาพย่อ 2-4 รูป + ปุ่มเปิดสมุดเต็ม
- **สถานะ LAPSED**: header ทั้งชุดถูกแทนที่ด้วยแถบสีเทากลาง (ไม่ใช่แดง) + "ไม่ได้อยู่ในแผนการตรวจสอบต่อเนื่องแล้ว" + วันที่ข้อมูลล่าสุด — **รอบตรวจ preview ยังอยู่เหมือนเดิม**
- **Full sheet**: checklist เต็ม (จัดกลุ่มตามชื่อขั้น แสดงเฉพาะขั้นไม่เกินขั้นปัจจุบันของร้าน) + room switcher (เฉพาะร้านมากกว่า 1 หลัง) + ไทม์ไลน์เต็มทุกรอบ + disclaimer ท้ายจอ

## User flow

1. ผู้ซื้อเปิด `/u/[username]` หรือ `/b/[slug]` ของร้าน LODGING ที่มีประวัติแผนการตรวจสอบ → เห็น `InspectionBlock` ในคอลัมน์ main เหนือแถบแท็บ
2. กด "ดูข้อตรวจทั้งหมด" → เปิด `ShopExtraPages` tab `inspection` (เต็มจอมือถือ / dialog กว้างเดสก์ท็อป ปิดด้วย x หรือ Esc ตาม pattern เดิม)
3. (ร้านหลายหลัง) กดชิปห้องพัก → เฉพาะส่วน "ผูกรายหลัง" เปลี่ยน ส่วน "ผูกร้าน" 7 ข้อไม่ขยับ
4. กด "ดูภาพจากคอล"/ภาพย่อ → เปิด lightbox (pattern เดิมของหน้านี้) — **ไม่ผูก query string ใหม่** เพราะสงวนไว้กับ deep-link สินค้า/คลิปที่มีอยู่แล้ว
5. ร้าน LAPSED → ผู้ซื้อยังเห็นบล็อกได้ แค่หัวเป็นสีเทากลาง กดดูรายละเอียดยังใช้งานได้ (ประวัติต้องดูได้เสมอ)

## Content outline

- หัวข้อบล็อก: **"Deep ตรวจสอบร้านนี้ต่อเนื่อง"**
- บรรทัดขั้น: **"กำลังอยู่ในขั้น: {ชื่อขั้น}"**
- สถานะ LAPSED: **"ไม่ได้อยู่ในแผนการตรวจสอบต่อเนื่องแล้ว"** + **"ข้อมูลล่าสุด: ตรวจเมื่อ {formatDateTH}"**
- ป้ายวันที่ต่อข้อ: **"ตรวจล่าสุด {formatDateTH}"**
- ป้ายรอตรวจซ้ำ: **"รอตรวจซ้ำ · ยืนยันล่าสุด {formatDateTH}"**
- ป้ายไม่เกี่ยวข้อง: **"ไม่เกี่ยวข้องกับที่พักประเภทนี้"**
- ป้ายยังไม่มีข้อมูล: **"ยังไม่มีข้อมูล"**
- CTA: **"ดูข้อตรวจทั้งหมด ({N} ข้อ) และรอบตรวจย้อนหลัง"**
- Disclaimer: **"Deep ยืนยันเฉพาะสิ่งที่ตรวจพบ ณ วันที่ตรวจเท่านั้น ไม่ได้รับประกันพฤติกรรมของร้านในอนาคตหรือคุณภาพการให้บริการ"**
- ป้ายรอบตรวจที่ผลไม่ผ่าน: **"รอบตรวจ {formatDateTH} · {ชื่อขั้น}"** (ไม่มีคำว่าผ่าน/ไม่ผ่านต่อท้าย)
- ห้ามใช้คำว่า **"ระดับ"/"คะแนน"/"เกรด"** ในบล็อกนี้ทั้งหมด (CONTEXT.md)

## Edge states

| State | พฤติกรรม |
|---|---|
| ร้าน LODGING ไม่เคยสมัครแผนเลย | **ไม่ render บล็อกทั้งก้อน** — กล่องเปล่าจะกลายเป็นเสียงรบกวนบนร้านส่วนใหญ่ (pattern เดียวกับ "ไม่มีเพจ = ไม่แสดงการ์ด" ของ `OfficialChannelsBlock`) |
| ร้านไม่ใช่ LODGING | ไม่ render (out of scope รอบแรก) |
| ขั้น 1 เท่านั้น | checklist แสดงเฉพาะกลุ่ม "ตรวจต่อเนื่องอัตโนมัติ" |
| ร้านหลายหลัง แต่หลัง B/C ยังไม่เคยตรวจ | ชิปหลัง B/C เป็น outline เลือกแล้วเห็นทุกข้อ "ยังไม่มีข้อมูล" ไม่ใช่ error |
| ทุกข้อของขั้นเป็น "รอตรวจซ้ำ" พร้อมกัน | แสดงตามปกติ ไม่มี state พิเศษ (แต่ละแถวพูดความจริงของตัวเอง) |
| ยังไม่มีรอบตรวจที่สมบูรณ์เลย | empty state: `tabler:calendar-time` + "ยังไม่มีรอบตรวจที่เสร็จสิ้น · Deep กำลังจัดคิวผู้ตรวจ" (ไม่ใช้คำว่า "รอผู้ตรวจเข้าตรวจ" ซึ่งสงวนไว้ฝั่งร้าน) |
| โหลดข้อมูล | render จาก server เสมอ — ไม่มี client loading spinner ที่ level นี้ |
| error ทาง data | ใช้ error boundary ของ Next ตามที่มีอยู่ — บล็อกนี้ไม่ query เอง |
| ข้อความยาวผิดปกติ | ทุก label ผ่าน `min-w-0`/`truncate` ตาม `flex-header-truncation.md` — ทดสอบด้วยชื่อหลังยาว 30+ ตัวอักษร |

## Section breakdown

- **`PlanStatusCard`**: การ์ดบนสุด — สถานะ (ไม่เคยสมัคร/ACTIVE/ค้างชำระ/LAPSED), ขั้นปัจจุบันเป็นคำ, ราคาต่อเดือน, วันที่ต่ออายุถัดไป, ปุ่ม `...` → "ยกเลิกแผน" → `pacesConfirm.warning` แสดงผลลัพธ์ล่วงหน้าตาม AC-INS-26-2
- **`StepLadder`**: 4 การ์ดต่อขั้น Base เดียวกับ `LevelCard.tsx` ของ `/verification`:
  - ต่ำกว่าขั้นปัจจุบัน → badge "รวมอยู่ในขั้นปัจจุบันแล้ว" ไม่มี CTA (muted)
  - เท่ากับขั้นปัจจุบัน → highlight + badge "ขั้นปัจจุบัน"
  - สูงกว่า → ปุ่ม "อัปเกรด" → เปิด `TermsConsentModal`
  - ยังไม่เคยสมัคร → ทุกการ์ดมีปุ่ม "เลือกขั้นนี้"

## Impeccable compliance

**Mode:** **A → Persuade** (register=`brand` หน้าตัดสินใจซื้อของผู้ซื้อ) · **B/C/D → Operate** (register=`product` ความคุ้นเคยชนะความสวยเดี่ยว ๆ)

- **The One Voice Rule**: ม่วง `#7367F0` ถูกใช้เต็มโควตาที่ `EvidencePanel` แล้ว (บล็อกเดียวที่มีพื้นสีในหน้า) — `InspectionBlock` **จงใจไม่ใช้ม่วง** เพื่อไม่แย่งโควตา 10% เดียวกัน และเพื่อให้อ่านออกว่าเป็นคนละแกน ใช้ Signal Cyan (`#00BAD1`) เป็น accent จุดเล็ก ๆ เท่านั้น พื้นบล็อกยังขาว — ตรงกับ role ที่ design.json ประกาศไว้ว่า Signal Cyan = ข้อมูล/สถานะกลาง ไม่ใช่ verified
- **The Verified-Means-Green Rule**: เขียวใช้ **เฉพาะไอคอน "ผ่าน" รายข้อ** เท่านั้น — ไม่ใช้เป็นสีกรอบบล็อกหรือสถานะ "กำลังตรวจ"/ACTIVE · **จุดที่ต้องระวังที่สุด: สถานะ ACTIVE ไม่ใช่ "ผ่าน" ห้ามใช้เขียวกับมันแม้จะรู้สึกว่าเป็นข่าวดี**
- **สีลงโทษสงวนให้มิจฉาชีพจริง**: LAPSED = เทากลาง (ไม่ใช่แดง/ส้ม) · "ไม่ผ่าน" ไม่มีจุดไหนแสดงคำหรือไอคอนต่อสาธารณะ
- **Sentence case**: ทุก label ไทยเป็นประโยคปกติ ไม่มี ALL CAPS
- **Ink-Tinted Shadow**: ยกจาก `SIDE_CARD_SX`/`TABS_CARD_SX` เดิม (`0 4px 18px rgba(40,34,76,.08)` = หมึกพลัม) ไม่ประดิษฐ์เงาใหม่ · ฝั่ง Paces ใช้ `--shadow`/`--shadow-lg` token เดิม
- **anti-slop**: ไม่มี gradient ตกแต่ง ไม่มี hero-metric ไม่มี eyebrow ตัวพิมพ์เล็ก ไม่มีบล็อกซ้อนบล็อก
- **น้ำเสียง**: บอกทางออกเสมอ (โควตาเต็ม→บอกเดือนถัดไป, เครดิตไม่พอ→ลิงก์เติมเงิน) เป็นกลางเมื่อพูดถึงร้านที่เลิกจ่าย

**จุดที่ theme ขัดกับ Impeccable และการตัดสิน:**
- `LevelCard.tsx` ใช้ `rounded-full` กับ CTA และ `!bg-primary` เป็น highlight เต็มการ์ด — "การ์ดเต็มสีทึบ" ขัดกับ Operate mode's "Restrained is the floor" เล็กน้อย **ยอมรับ pattern นี้ต่อ เพราะเป็น pattern ที่มีอยู่จริงบน prod ที่ `/verification`** (earned familiarity ชนะความสวยเดี่ยว ๆ) — ความสม่ำเสมอข้าม 2 หน้าที่ทำหน้าที่คล้ายกันสำคัญกว่าการคิดโทนใหม่
- `StatusBadge.tsx` เดิมใช้ `text-{semantic}` เปล่าบนพื้นจาง (ตกคอนทราสต์) — **ไม่ยกมาใช้** เบี่ยงจาก "หยิบของเดิมมาใช้ตรง ๆ" โดยตั้งใจ เพราะของเดิมมีหนี้คอนทราสต์ที่รู้อยู่แล้ว

## Design decisions + rationale

1. **"ไม่ผ่าน" (FAIL) เรนเดอร์เหมือน "ยังไม่มีข้อมูล" (NO_DATA) ทุกประการบนหน้าจอสาธารณะ** — BR §4.1/AC-INS-18-1/18-2 บังคับครบ (ไม่มีป้าย ไม่มีไอคอนยืนยัน ไม่มีคำว่า "ไม่ผ่าน") เลือกให้แสดงผล **เหมือนกันเป๊ะ** (icon `tabler:circle-dashed` สีเทา ไม่มีวันที่) เพราะผู้ซื้อไม่ควรแยกออกว่า "ยังไม่ตรวจ" กับ "ตรวจแล้วไม่ผ่าน" ต่างกันอย่างไร — สองอย่างนี้ควรดูเหมือนกันจากมุมมองสาธารณะโดยเจตนา · ฉ้อโกงจริงไปทางแยก (`/check`) ต่างหาก
2. **ไม่มีตัวเลข "N จาก 18 ข้อผ่าน"** — (ก) ทำให้อ่านเป็นคะแนน/เกรด ขัด BR "ตรวจข้อเท็จจริง ไม่ตัดสินคุณภาพ" (ข) หน้านี้เพิ่งถอด pattern เศษส่วนแบบเดียวกันออกไปเมื่อ 2026-08-23 ด้วยเหตุผลเดียวกันเป๊ะ — ทำซ้ำ pattern ที่เพิ่งถูกปฏิเสธจะเป็นการย้อนกลับโดยไม่มีเหตุผลใหม่
3. **บล็อกสาธารณะ = summary + full sheet** — แก้ปัญหา "ไทม์ไลน์ตัดหน้ากี่รอบ" ด้วยสถาปัตยกรรม ไม่ใช่ตัวเลข: sheet เต็มไม่ต้องจำกัดจำนวนรอบเพราะเป็นปลายทาง "อยากดูเพิ่ม" อยู่แล้ว ตรงตาม AC-INS-16 โดยไม่ทำให้หน้าหลักยาวเกิน
4. **Room-level checklist ต้องมี selector ฝั่งสาธารณะ** ซึ่ง SDS ตั้งชื่อไว้เฉพาะฝั่งร้าน — ออกแบบ variant สาธารณะ (MUI Chip, read-only) เพราะ AC-INS-29 บังคับให้แยกผลตามหลังอย่างชัดเจน เลี่ยงไม่ได้ถ้าร้านมีมากกว่า 1 หลัง
5. **ป้าย "รอผู้ตรวจเข้าตรวจ" อยู่ระดับรอบตรวจ ไม่ใช่ระดับข้อตรวจ** — ตีความจาก FR-INS-017 ว่าหมายถึงรอบทั้งรอบ เพราะรอบหนึ่งครอบหลายข้อพร้อมกัน (TD-017 ยืนยัน)

## Open questions

1. **จำนวนรอบใน timeline preview** — เสนอ **รอบล่าสุด 1 รอบ** + link ไปสมุดเต็ม เพื่อคุมความสูงของบล็อกไม่ให้แย่งพื้นที่จาก tabs — ต้องยืนยัน
2. **Badge บนการ์ดห้องพัก (`PublicRoomList`)** — ผู้ซื้อที่ดูแท็บ "ห้องพัก" อาจอยากเห็นสัญญาณ inspection ต่อการ์ดห้องทันที **นอกขอบเขตที่ SDS ระบุ** ไม่ได้ออกแบบเพื่อไม่ขยาย scope เอง — เสนอเป็น fast-follow
3. **พิกัด/ที่อยู่ที่ผู้ตรวจเห็น** — ออกแบบให้หายไปหลัง `completedAt` ถูกตั้ง ต้องยืนยันมติจริงก่อน implement
4. **ชื่อขั้นที่ยาว** — "ตรวจต่อเนื่องอัตโนมัติ" ยาวกว่า label อื่นมาก บนจอไม่เกิน 360px อาจต้อง wrap 2 บรรทัด · ยอมรับได้ (ไม่ตัดคำ) แต่ต้องทดสอบด้วยชื่อขั้นจริงทั้ง 4 ที่ 320px
5. **ไอคอนที่เสนอ** (`tabler:shield-check`, `tabler:circle-dashed`, `tabler:calendar-time`, `tabler:clipboard-off`) — อิงชื่อมาตรฐานของชุด tabler แต่ **developer ต้องเปิด iconify.design ยืนยันชื่อจริงก่อน implement ทีละตัว** ไม่ใช่เชื่อรายการนี้เฉย ๆ
6. **ราคา** — ต้องยืนยันว่าจะ **implement UI ครบแต่บล็อกการเปิดขายด้วย flag** หรือ **ไม่ทำ UI สมัคร-จ่ายเงินเลยจนกว่าจะมีมติราคา** (สอง scope ต่างกันมาก) — คำถามระดับ product ไม่ใช่ ux

## Anti-slop self-check

1. **เฉพาะกับ Deep จริงไหม** — ใช่ ทุกป้าย/สถานะ/สีอิง CONTEXT.md ที่ล็อกเฉพาะโปรเจกต์นี้ เอาไปใช้กับสินค้าอื่นตรง ๆ ไม่ได้
2. **พระเอกของแต่ละจอ** — A: ชื่อร้าน+ปกยังคงพระเอก `InspectionBlock` เป็นหลักฐานสนับสนุน · B: `PlanStatusCard` เด่นสุด · C: checklist ของรอบเดียวคือพระเอกทั้งจอ
3. **ตัดทิ้งแล้ว** — ตัวหาร N/18 · numeric step ladder แบบ "01/02/03" · ป้าย "รอผู้ตรวจเข้าตรวจ" ซ้ำสองที่ในจอเดียว
4. **State ครบ** — empty/loading/error/ข้อความยาว มีตารางทุก surface · ตั้งใจไม่มีตัวเลขรวมที่ต้องกัน edge 0/หลักล้าน
