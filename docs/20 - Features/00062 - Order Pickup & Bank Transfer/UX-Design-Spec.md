## A1. ตัวเลือกวิธีส่งมอบ "จัดส่ง | นัดรับ" (3 surface)

### User stories ที่ครอบ
FR-PKP-01 (BRD §2.1) — ร้าน ONLINE_SALES เลือก "นัดรับ" ได้ตอนสร้าง/แก้ไขออเดอร์ โดยไม่ผูกกับ salesChannel (D-4) และ override การคำนวณ fulfillmentMode อัตโนมัติเดิม

### ข้อสรุปจากการอ่านโค้ดจริง (ต้องรู้ก่อนอ่าน spec ข้างล่าง)
- **ไม่มีตัวเลือกวิธีส่งมอบอยู่ในระบบเลยตอนนี้** — `fulfillmentMode` ถูก **คำนวณ** จาก `toOrderItemShippingKind()` (จาก catalog ของสินค้าที่เลือก) ไม่ใช่ให้ผู้ใช้เลือกตรง ๆ นี่คือฟิลด์ใหม่ทั้งกระบิ ไม่ใช่ retheme ของที่มีอยู่
- 3 surface ที่ต้องแก้จริง ๆ มี **2 ไฟล์** (ไม่ใช่ 3 เพราะโมดัลแชทกับหน้า `/orders/new` มือถือใช้ component เดียวกัน):
  1. **`CustomerQuickBlock.tsx`** — ใช้ทั้งใน quick form โมดัลแชท (`compact=true`, w-96) และหน้า `/orders/new` มือถือ (`compact=false`) ผ่าน `QuickForm.tsx` ตัวเดียวกัน มีบล็อก "ที่อยู่ (ไม่ใช่ STOREFRONT)" อยู่แล้วที่บรรทัด ~346 กั้นด้วย `showAddress = needsShipping`
  2. **`CartPanel.tsx`** — ใช้เฉพาะ `/orders/new` ≥1024px (POS desktop) มี accordion "ที่อยู่จัดส่ง" กั้นด้วย `{needsShipping && (...)}`
- `needsShipping` มาจาก `orderNeedsShippingAddress()` (`src/lib/shipping-address-status.ts`) — ต้องเพิ่ม input ใหม่ `deliveryOverride?: 'PICKUP'` ที่ **short-circuit คืน `false` ทันที** เมื่อเลือกนัดรับ (เขียนไว้ก่อน `if (!input.shipsGoods) return false`) เพื่อให้ QuickForm/CartPanel/OrderCreateForm (submit) ยังเรียก SSOT ตัวเดียวกันเป๊ะเหมือนเดิม — **ห้ามเขียนเงื่อนไข "ถ้าเลือกนัดรับ" ซ้ำที่ 3 จุดเรียกเหมือนที่เคยพลาดมาก่อน (2026-08-07/08-10)**

### Section breakdown
- **แถว "วิธีส่งมอบ"** — label `text-sm font-semibold text-default-700` (ชุดเดียวกับ label แถว "ช่องทางการขาย"/"การชำระเงิน" ที่มีอยู่แล้ว) + ปุ่ม 2 ใบ `inline-flex` แบ่งครึ่งเท่ากัน (`flex-1`)
- ปุ่มที่เลือกอยู่: `btn bg-primary/15 text-primary` (soft-selected, ชุดเดียวกับ FilterDropdown active state) + icon tone primary
- ปุ่มที่ไม่ได้เลือก: `btn bg-light text-dark hover:text-primary`
- ปุ่มซ้าย (`จัดส่ง`) = `rounded-e-none`, ปุ่มขวา (`นัดรับ`) = `rounded-s-none` (Paces Button Group primitive §2)
- **แสดงเฉพาะร้าน `Shop.vertical === 'ONLINE_SALES'`** — ร้าน SERVICE_QUEUE/LODGING ไม่เห็นแถวนี้เลย (ไม่ใช่ disabled — ไม่มีอยู่ในหน้าเลย ตรงตาม FR-PKP-01 AC ข้อ 2)
- ค่าเริ่มต้น = "จัดส่ง" เสมอ (ไม่มีปุ่มดาวจำค่าเริ่มต้นแบบ channel/payment — ไม่ใช่สิ่งที่ PRD ขอ, หลีกเลี่ยง scope creep)

### User flow
1. ร้าน (ONLINE_SALES) เปิดฟอร์มสร้าง/แก้ไขออเดอร์ → ค่าเริ่มต้น "จัดส่ง" (พฤติกรรมเดิมทุกประการ ไม่มีอะไรเปลี่ยนถ้าไม่แตะ)
2. แตะ "นัดรับ" → บล็อกที่อยู่จัดส่งหายทันที (ไม่มี validation ที่อยู่อีกต่อไป) + ข้อความอธิบายสั้นโผล่แทน
3. บันทึกออเดอร์ → `Order.fulfillmentMode = 'PICKUP'`, ไม่มี `shippingAddress` ถูกส่ง
4. แก้ไขออเดอร์ภายหลัง (ยัง `PENDING`) → ตัวเลือกกลับมาแก้ได้เหมือนตอนสร้าง — สลับกลับ "จัดส่ง" ได้ บล็อกที่อยู่กลับมา (ค่าที่เคยกรอกไว้ก่อนสลับ **ไม่ถูกลบ** ถ้ามี — แค่ซ่อน/โชว์)

### Content outline (ไทย)
- Label แถว: `วิธีส่งมอบ`
- ปุ่ม: `จัดส่ง` / `นัดรับ`
- ข้อความอธิบายเมื่อเลือกนัดรับ: `ลูกค้ามารับเองที่ร้าน — ไม่ต้องกรอกที่อยู่จัดส่ง`

### Edge states
- **ร้านที่มีสินค้าติดธง `SHIPPED` ค้าง + เลือกนัดรับ**: ต้อง override ชนะเสมอ (FR-PKP-01 AC ข้อ 3 — "ไม่สนใจว่ารายการสินค้าจะเป็นชนิดที่ปกติคำนวณเป็น SHIPPED หรือไม่")
- **สลับจาก "นัดรับ" กลับเป็น "จัดส่ง" หลังเคยกรอกที่อยู่ไว้ก่อนสลับไปนัดรับ**: บล็อกที่อยู่กลับมาพร้อมค่าที่เคยกรอก (ฟอร์ม state ไม่ล้าง) — ไม่งั้นร้านต้องกรอกซ้ำและหงุดหงิด
- **แก้ไขออเดอร์ที่สถานะไม่ใช่ PENDING**: ทั้งแถวนี้ต้อง disabled/ไม่แสดงเลย — ไม่ต้องทำอะไรเพิ่ม เพราะหน้า edit ทั้งหน้าบล็อก non-PENDING อยู่แล้วในระดับ route

## A2 + A4. ปุ่ม "มอบสินค้าแล้ว" + การ์ด "การนัดรับ" (รวมเป็นการ์ดเดียว)

### เหตุผลที่รวม A2 กับ A4 เป็นการ์ดเดียว
`CodCard.tsx` (ต้นแบบ "mirror" ตาม PRD) **ไม่ใช่แค่ปุ่ม** — มันคือการ์ดที่รวม "สถานะ + ปุ่ม action" ไว้ด้วยกัน แล้วปุ่มบนการ์ดโชว์เฉพาะ ≥1024px (มือถือใช้แถบ action ล่างจอแทน — comment ในไฟล์บอกเหตุผลไว้แล้ว: "ไม่ให้ปุ่มหลักโผล่ 2 ที่พร้อมกันบนมือถือ") การแยก A2/A4 เป็น 2 การ์ดคนละใบจะทำให้ข้อมูล "ที่อยู่นัดรับ" กับ "ทำอะไรกับมันต่อ" ห่างกันโดยไม่มีเหตุผล — `ShippingAddress.tsx` เองก็ประกาศตัวเป็นไฟล์ที่ extend ได้อยู่แล้ว ("ที่เพิ่ม: สาขา NO_SHIPPING…ไม่ใช่การ์ดว่าง")

### ตำแหน่งจริงในหน้า (ยืนยันจาก `page.tsx`/`OrderDetailClient.tsx`)
คอลัมน์ขวาของหน้า order detail เรียงเป็น: `customerCard` → `CodCard` → `profitCard` → `sideCards` (= `[AppointmentCard ถ้ามีนัด] → ShippingAddressCard → ShippingCard`) — **การ์ด "การนัดรับ" นี้คือ `ShippingAddressCard` ที่เพิ่มสาขาใหม่** ไม่ใช่การ์ดแยก จึงอยู่ตำแหน่งเดิมเป๊ะ (แทนที่ `return null` เดิมของ `fulfillmentMode='PICKUP'`)

### Section breakdown
- **Badge หัวการ์ด (3 สถานะ)**: `รอมอบของ` (warning) → `รอผู้ซื้อยืนยัน` (info — **ไม่ใช่ success** เพราะยังไม่ปิดงานจริง) → `เสร็จสิ้น` (success เมื่อ `status === 'CONFIRMED'`) — **ห้ามเขียว badge ตอนยัง PENDING**
- **แถวจุดนัดรับ** — icon `building-store` + ชื่อร้าน + `Shop.address` (มติ D-5 assumption) + ปุ่มคัดลอกที่อยู่ (reuse pattern จาก `ShippingAddress.tsx` เดิมทุกอย่าง — icon `copy`, ปุ่มกลม 32px มุมขวาบน)
- **แถวสถานะมอบของ** — ก่อนกด: ไม่มีแถวนี้ (แค่ปุ่ม) · หลังกด: icon `circle-check` เขียว + เวลา + ผู้กด (pattern เดียวกับ `CodCard`'s "รับเมื่อ...")
- **บรรทัด grace period** — บอกเวลาที่ระบบจะปิดงานอัตโนมัติเป็นวันเวลาจริง (`formatDateTimeTH(handedOverAt + 48h)`) **ไม่ใช่นับถอยหลังแบบวินาที** (Paces "ไม่มี choreography" + ตัวเลขนิ่งอ่านง่ายกว่าเลขวิ่ง)
- **ปุ่ม "มอบสินค้าแล้ว"** — `btn bg-primary hover:bg-primary-hover` เต็มความกว้าง, icon `tabler:package-check`
- **ปุ่ม "ยกเลิกการยืนยัน"** (undo) — `btn border-default-300 text-default-700 border` (outline, เบากว่า primary — mirror CodCard undo เป๊ะ), icon `arrow-back-up`

### ตำแหน่งปุ่มบนแถบ action (มือถือ <1024, ผ่าน `order-action-set.ts`)
ต้องขยาย `GetOrderActionSetInput` ด้วย flag ใหม่ (คู่กับ `isCodUnpaid` ที่มีอยู่แล้ว) — **ไม่ทับ `isCodUnpaid` เดิม เพราะ COD กับ PICKUP+TRANSFER เป็นคนละ paymentMethod เสมอ ไม่มีวันชนกัน**:

🛑 **แก้ 2026-08-29:** ฉบับแรกเขียนว่า "ไม่ต้องมี confirm modal — mirror CodCard undo ซึ่งไม่มีเช่นกัน" — **คำอ้างเรื่อง CodCard นั้นผิด** เปิดโค้ดดูแล้ว `handleCodReceived`/`handleCodUndo` มี `pacesConfirm.question` ทั้งคู่ ⇒ เหตุผลที่ใช้ตัดสินไม่มีอยู่จริง (`docs/conventions/docs-claimed-constraint-verify-in-code.md`)

ของจริงที่ implement: **มี confirm ทั้ง "มอบสินค้าแล้ว" และ "ได้รับเงินแล้ว" รวมถึง undo ของทั้งคู่** — เหตุผล: (1) "ได้รับเงินแล้ว" เป็นคำยืนยันเรื่องเงิน กดพลาดแล้วตัวเลขในระบบผิด (2) "มอบสินค้าแล้ว" **เริ่มนับนาฬิกาปิดงานอัตโนมัติ 48 ชม.** กดพลาดแล้วออเดอร์ถูกปิดเองทั้งที่ลูกค้ายังไม่ได้ของ และไปนับเป็นออเดอร์สำเร็จของร้าน (3) การ์ดสองใบที่นั่งข้างกันในคอลัมน์เดียวกันไม่ควรมีพฤติกรรมต่างกันโดยไม่มีเหตุผลที่ผู้ใช้เดาได้ (`sibling-surface-parity.md`)
4. ผ่าน 48 ชม. ไม่มีข้อพิพาท → ระบบปิดงานเอง → badge เป็น "เสร็จสิ้น" (success)

- **`Shop.address` ว่างเปล่า**: แถวจุดนัดรับแสดง `ยังไม่ได้ตั้งที่อยู่ร้าน — ตั้งค่าได้ที่หน้าร้านค้า` พร้อมลิงก์ไป `/shop` (**ไม่ใช่ error สีแดง** — เป็นข้อมูลที่ขาดหายแบบไม่บล็อกอะไร)

- **ผู้ซื้อกดยืนยันเองก่อนร้านกด "มอบสินค้าแล้ว"**: การ์ดเปลี่ยนเป็น "เสร็จสิ้น" ทันทีโดยไม่มีขั้น "รอผู้ซื้อยืนยัน" คั่น (ข้าม state)
- **ออเดอร์ถูกยกเลิก**: การ์ดหายทั้งใบหรือ read-only แบบจาง — ให้เหมือนพฤติกรรมของการ์ดอื่นเมื่อ CANCELLED (ไม่มี action ใด ๆ)

**คำตอบของ ux: ไม่ควร** — เหตุผล:
1. BRD บอกตรง ๆ ว่าออเดอร์นัดรับ **"ต้องไม่ปรากฏในตัวนับ...ต้องมีตัวกรอง/หมวดของตัวเอง"** — คนละคำถาม คนละหมวดจริง ๆ (พัสดุตอบว่า "ของอยู่ไหนในเส้นทางขนส่ง" ส่วนนัดรับตอบว่า "ลูกค้ามารับหรือยัง")

### ตัดสินใจตำแหน่งหน้า (ตอบคำถาม "หน้านี้เป็นของใคร")
- `/settings` — **ตัด**: comment ในโค้ดปัจจุบันเขียนไว้ตรง ๆ ว่า "หน้านี้จึงเหลือเฉพาะเรื่องของร้าน = **การจัดส่ง**" (title metadata ก็เป็น "การจัดส่ง") — ยัดบัญชีธนาคารเข้าไปจะทำให้หน้าที่เพิ่งถูกทำให้โฟกัสเรื่องเดียวกลับไปปนอีก

- 🛑 **ร้านยังไม่ได้ตั้งบัญชีรับเงินเลย แต่ออเดอร์เป็น TRANSFER/PROMPTPAY** (ข้อมูลเก่าก่อนฟีเจอร์นี้ หรือร้านลืมตั้ง): ต้องมี fallback ที่ไม่ใช่การ์ดว่าง/พัง — แสดง `ร้านยังไม่ได้แจ้งเลขบัญชี — ทักแชทกับร้านเพื่อสอบถามวิธีโอนเงินได้เลย` + ปุ่ม "ติดต่อร้านค้า" (reuse `AuthPingLink` ที่มีอยู่ในหน้าเดียวกัน) — **ห้ามไม่แสดงอะไรเลย** เพราะผู้ซื้อจะไม่รู้ว่าเป็นปัญหาของร้านหรือของเว็บ
- **ตั้งบัญชีธนาคารแต่ไม่ตั้งพร้อมเพย์**: แสดงเฉพาะแถวธนาคาร+เลขบัญชี **ไม่มี QR block เลย** (ไม่ใช่กล่องเทาว่างที่บอก "ไม่มี QR")
- **ยอดออเดอร์ถูกแก้ไขหลังสร้าง**: QR คำนวณจากยอดปัจจุบันเสมอ (FR-BANK-05 AC) — ไม่ cache payload เก่า
- **เบอร์พร้อมเพย์ผิดรูปแบบ/EMVCo encode ล้มเหลว**: fallback เหมือนกรณี "ไม่ได้ตั้งพร้อมเพย์" (ซ่อน QR เงียบ ๆ ไม่ใช่โชว์ QR เสีย) แต่ยังต้องมีแถวเลขบัญชีธนาคารเป็น fallback ที่ใช้งานได้จริงเสมอ

## B8. ป้ายสถานะการชำระเงิน 3 สถานะ (`getPaymentBadge` — SSOT)

### ต้องขยาย SSOT เดียว ไม่ใช่คำนวณใหม่ที่ใดที่หนึ่ง
`getPaymentBadge(status, paymentMethod, slipFileId)` ใน `src/lib/order-display.ts` ต้องรับ parameter ใหม่ `paymentConfirmedAt: Date | string | null | undefined` — และเพิ่ม 1 เงื่อนไขก่อนกิ่ง `slipFileId`:

| สถานะ | Label | Tone |
|---|---|---|
| `status === CONFIRMED` | ชำระแล้ว | success (คงเดิม) |
| `status === CANCELLED` | ยกเลิก | neutral (คงเดิม) |
| `isCODPayment` | รอเก็บปลายทาง | info (คงเดิม) |
| TRANSFER/PROMPTPAY/CASH + `paymentConfirmedAt` | **ร้านยืนยันรับเงินแล้ว** | **info (ใหม่)** |
| TRANSFER/PROMPTPAY + `slipFileId` (ยังไม่ confirm) | รอตรวจสอบสลิป | info (คงเดิม) |
| TRANSFER/PROMPTPAY (ไม่มีทั้งคู่) | รอชำระ | warning (คงเดิม) |
| อื่น ๆ (ไม่รู้จัก paymentMethod) | ยังไม่ยืนยันการชำระ | warning (คงเดิม) |

🛑 **ต้องเช็ค `paymentConfirmedAt` ก่อน `slipFileId` เสมอ** (ลำดับ if-else) — เมื่อร้านกดยืนยันรับเงินแล้ว สถานะนั้นชนะ "รอตรวจสอบสลิป" เสมอ (ร้านยืนยันเองคือสัญญาณที่แน่นอนกว่าสลิปที่ยังไม่ตรวจ)

### ทำไมเลือก tone `info` ไม่ใช่ `success`
BRD FR-PAY-02 AC เขียนชัดว่า "ไม่ใช้สีเขียวของ 'ชำระแล้ว' เดิม" เพราะ Verified-Means-Green สงวนไว้เฉพาะ `status===CONFIRMED` — "ร้านยืนยันรับเงินแล้ว" เป็น **self-report ของร้านเอง ไม่มีบุคคลที่สามยืนยัน** (PRD §4.2 ยอมรับตรง ๆ) — ให้เขียวจะทำให้สัญญาณเขียวเฟ้อและสับสนกับ "ปิดงานแล้วจริง"

เลือก `info` เพราะไม่ต้องแก้ type `OrderStatusTone` (คงที่ 4 ค่า) ลด blast radius ของ `ORDER_STATUS_TONE_TO_MUI` bridge — แม้ label "รอตรวจสอบสลิป" กับ "ร้านยืนยันรับเงินแล้ว" ใช้สีเดียวกัน แต่ **ไม่มีวันแสดงพร้อมกันในช่องเดียว** (mutually exclusive ตามลำดับ if-else)

🛑 **ข้อสังเกตที่ต้องส่งต่อ SDS**: `getPaymentBadge()` วันนี้ **ยังไม่มีใครเรียกใช้ในฝั่งผู้ซื้อเลย** (`OrderDetailMobile.tsx`/`GuestOrderView.tsx` ใช้ `resolveOrderStatusBadge`/`ORDER_STATUS_TONE_TO_MUI` คนละฟังก์ชัน) — FR-PAY-02 บังคับว่า "ทุกจอ...ต้องได้ป้ายชุดเดียวกันจากฟังก์ชันเดียวกัน" หมายความว่า **B7 ต้องเริ่มเรียก `getPaymentBadge()` เป็นครั้งแรกบนฝั่งผู้ซื้อ** — `cls` ที่คืนมาเป็น Tailwind/Paces class ใช้กับ MUI ไม่ได้ตรง ๆ จึงต้อง **คืน `tone` เพิ่มด้วย** (คู่กับ `cls`) ให้ผ่าน `ORDER_STATUS_TONE_TO_MUI[tone]` ได้ — **เป็นการเปลี่ยน return shape ของ SSOT ที่ทั้ง Paces (A3) และ Vuexy (B7) import ตัวเดียวกัน ไม่ใช่แค่งาน UI**

## Impeccable compliance

**Mode: Operate** สำหรับ A1–A6 ทั้งหมด (seller console — app UI ที่ผู้ใช้อยู่ในงาน ต้อง earned-familiarity ไม่ใช่ความแปลกใหม่) · **B7–B8 ยึด Operate เป็นหลักเช่นกัน** (`/o/[token]` เป็นจอตัดสินใจของผู้ซื้อ แต่เป็น transactional utility ที่ต้องการความชัดเจนเหนือทุกอย่าง ไม่ใช่ landing page)

- **One Voice Rule**: ทั้งฟีเจอร์แทบไม่แตะม่วง/น้ำเงินเลย — primary จริงมีแค่ "มอบสินค้าแล้ว"/"ได้รับเงินแล้ว"/"บันทึกการเปลี่ยนแปลง" การ์ดข้อมูลอื่นใช้ semantic tone ไม่ใช่ primary
- **Verified-Means-Green**: บังคับตรงจุดที่สุดที่ B8 — **ห้าม** ใช้เขียวกับ "ร้านยืนยันรับเงินแล้ว" แม้ `CodCard` เดิม (ที่ PRD สั่งให้ mirror) จะใช้เขียวกับ "ได้รับเงินปลายทางแล้ว" — 🛑 **นี่คือจุดที่ precedent เดิมขัดกับ Impeccable และ ux เลือกทำตาม Impeccable + BRD** ⇒ mirror เฉพาะ "โครง/ตำแหน่ง" **ไม่ mirror "สี"**
- **Sentence case**: ทุกปุ่ม/label เป็นประโยคปกติ ไม่มี ALL CAPS
- **Ink-tinted shadow**: การ์ดใหม่ใช้ `.card`/MUI `Card` มาตรฐานของสกินเดิม ไม่ประดิษฐ์เงาใหม่
- **Anti-slop**: ไม่มี gradient ตกแต่ง · ไม่มี hero-metric template (ยอดเงินมี label กำกับเสมอ = Strong ไม่ใช่ Metric) · ไม่มี eyebrow ตัวเล็ก · ไม่ซ้อนการ์ดในการ์ด
- **น้ำเสียง**: ทุก error/empty state บอกทางออก ไม่ใช่แค่บอกว่าผิด — "ร้านยังไม่ได้แจ้งเลขบัญชี — **ทักแชทกับร้าน**เพื่อสอบถาม" · "ยังไม่ได้ตั้งที่อยู่ร้าน — **ตั้งค่าได้ที่**หน้าร้านค้า" — ไม่มีประโยคราชการแบบ "ไม่สามารถดำเนินการได้"

## Design decisions + rationale

1. **A2+A4 รวมเป็นการ์ดเดียว** — `ShippingAddress.tsx` เป็นไฟล์ extensible อยู่แล้ว และการแยกจะทำให้ "ที่อยู่นัดรับ" กับ "ปุ่มมอบของ" ห่างกันโดยไม่มีเหตุผลเชิงข้อมูล (มันคือเรื่องเดียวกัน)
2. **ไม่เพิ่มไทล์ที่ 7 ใน Command Center** — ปริมาณน้อย + กริดเต็มพอดี + คนละคำถามกับพัสดุ ⇒ ทำ facet filter แยกใน `/orders` แทน
3. **ปุ่ม "ได้รับเงินแล้ว" เป็น primary ก่อน "มอบสินค้าแล้ว" เมื่อทั้งคู่ยังไม่เสร็จ** — จำลองลำดับพฤติกรรมจริงจาก user journey ของ PRD (โอนเงินก่อน → มารับของทีหลัง) ให้แถบ action พาไปทีละขั้นแทนที่จะแข่งกัน 2 ปุ่มพร้อมกัน
4. **A6 วางที่ `/shop`** — อิงหลัก "หน้านี้เป็นของใคร" ที่ระบบยึดมาตลอด + ต่อยอด prop pattern ที่มีอยู่แล้ว
5. **badge "ร้านยืนยันรับเงินแล้ว" ใช้ tone `info`** — ไม่ต้องขยาย type `OrderStatusTone` (ลด blast radius) แม้ซ้ำสีกับ "รอตรวจสอบสลิป" แต่ไม่ชนกันจริงเพราะ mutually exclusive — ทางเลือกสำรอง (เพิ่ม tone ใหม่) ถูกปัดตกเพราะเพิ่มความเสี่ยงเกินจำเป็นสำหรับ MVP

## Anti-slop self-check

1. **เฉพาะกับ Deep จริงไหม** — ผ่าน: ทุกจุดผูกกับข้อมูลจริงของระบบนี้ (Trust Score, `ScamReportIdentifier`, guest-first flow ที่มาจากเลขจริง 0/504) ไม่ใช่ generic "add payment method"
2. **มีพระเอก 1 อย่างต่อจอไหม** — ผ่าน: A2/A3/A4 มีปุ่ม primary เดียวต่อสถานะ (จัดลำดับไว้แล้วในตาราง A2); B7 พระเอกคือเลขบัญชี+QR
3. **มีอะไรซ้ำ/ไม่ทำงานควรตัดไหม** — ตัดแล้ว: ไม่เพิ่มไทล์ Command Center ที่ 7 · ไม่แสดง QR block ว่างเมื่อร้านไม่ตั้งพร้อมเพย์
4. **state ครบไหม** — ครบ: empty (ร้านไม่ตั้งบัญชี/ไม่ตั้ง `Shop.address`), error inline, loading (`useListBusy()` เดิม), เนื้อหายาวผิดปกติ (ชื่อธนาคาร/ชื่อบัญชียาว — `truncate`+`min-w-0` ตามกฎ flex เดิม), ตัวเลข 0/หลักล้าน
5. **copy บอกสิ่งที่ระบบทำได้จริงไหม** — ผ่าน: ปุ่มบอกผลลัพธ์ตรง ๆ ไม่ใช่ท่าทาง; error ทุกจุดบอกทางออก
6. **คำเดียวกัน = ของเดียวกันไหม** — ผ่าน: badge สถานะนัดรับใช้คำเดียวกันทั้งการ์ด (A2/A4) และคอลัมน์ตาราง (A5); "นัดรับ" ไม่ชนกับ "รอรับเข้า" ของกองพัสดุเดิม
7. **สีสื่อความหมายถูกไหม** — ผ่าน (บังคับที่สุดในสเปกนี้): เขียวสงวนเฉพาะ `CONFIRMED` เท่านั้น
8. **แตะได้จริงบนมือถือไหม** — ผ่าน โดยมีข้อบังคับเพิ่ม: ปุ่มคัดลอกเลขบัญชี/บันทึก QR ใน B7 **ต้องไม่ใช้ `size='small'`** (ต่ำกว่า 44px)
9. **จอกว้าง 1440 มีคอลัมน์ว่างไหม** — ตรวจแล้ว: B7 คอลัมน์เดียวกึ่งกลางจอ ไม่ขยายเป็น 70/30; A1-A5 ใช้ grid ที่มีอยู่แล้วซึ่งเนื้อหาเต็มทั้งสองฝั่ง
