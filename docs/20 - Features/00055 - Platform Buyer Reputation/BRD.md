## 1. นิยามศัพท์ (HR16 — ห้ามนิยามซ้ำที่อื่น)

| คำ | นิยามเดียวของระบบ | อยู่ที่ |
|---|---|---|
| **ผู้ซื้อ (คนเดียวกัน)** | แถว `Customer` หนึ่งแถว — ระบุด้วย `phone` ที่ `@unique` **ระดับทั้งระบบ ไม่ผูกร้าน** | `prisma/schema.prisma:935` |
| **รับของแล้ว** | ออเดอร์ที่ `carrierStatus ∈ DELIVERED_CARRIER_STATUSES` **หรือ** `Order.status = 'CONFIRMED'` | `lib/iship/status.ts` |
| **พัสดุตีกลับ** | `carrierStatus ∈ RETURNED_CARRIER_STATUSES` (`return`, `return_success`) | `lib/iship/status.ts` |
| **ยกเลิกโดยฝั่งลูกค้า** | `cancelInitiator='buyer'` **หรือ** `cancelReason` ที่ `countsAgainstGuest` | §3 |
| **อัตราพัสดุตีกลับ** | `ตีกลับ ÷ (ออเดอร์ที่มีพัสดุจริงทั้งหมด)` — ตัวหารต้องเป็นใบที่มีโอกาสตีกลับได้เท่านั้น | BR-BR-05 |

🛑 **ตัวหารต้องมาจากแถวชุดเดียวกับตัวตั้ง** — ใบที่ไม่เคยเปิดพัสดุ (รับหน้าร้าน/ดิจิทัล/บริการ)
ไม่มีทางตีกลับได้ ถ้าเอาไปหารด้วยจะได้อัตราที่ต่ำกว่าความจริงเสมอ
(`feedback_subtrahend_must_match_minuend_scope`)

## 2. กฎธุรกิจ

| # | กฎ |
|---|---|
| **BR-BR-01** | สถิติผูกกับ `Customer.id` **ห้ามกรองด้วย `shopId`** — ถ้ามี `shopId` ในเงื่อนไข แปลว่ากลายเป็นสถิติรายร้านอีกครั้ง (มีอยู่แล้วที่ `customer-behavior.service.ts` และเป็นคนละตัว) |
| **BR-BR-02** | ผลลัพธ์ที่ส่งออกจาก service **ต้องเป็นตัวเลขรวมเท่านั้น** ห้ามมี `shopId`/`shopName`/`orderId` ติดไปด้วย (D-2) — บังคับที่ชนิดข้อมูลที่ `select` ไม่ใช่ที่การ render |
| **BR-BR-03** | ใบเดียวนับได้ครั้งเดียว · **ตีกลับชนะยกเลิก** (กติกาเดียวกับ `customer-behavior.ts` — ห้ามเขียนใหม่ให้ต่างกัน) |
| **BR-BR-04** | ใบที่ **ร้าน**เป็นต้นเหตุ (`SHOP_ISSUE`, `MUTUAL`) ห้ามเข้าประวัติลูกค้าเด็ดขาด |
| **BR-BR-05** | ตัวหารของอัตราตีกลับ = ออเดอร์ที่ **มีพัสดุจริง** (มีแถว `OrderShipment` ที่ `status='CREATED'`, `isDryRun=false`) เท่านั้น |
| **BR-BR-06** | ไม่แสดง "อัตรา" เมื่อฐาน < **3 ใบ** — แสดงจำนวนดิบแทน (R-2) |
| **BR-BR-07** | ระดับความเสี่ยงมี 3 ขั้น: `NONE` (ไม่เคยตีกลับ) · `WATCH` (ตีกลับ ≥1) · `HIGH` (ตีกลับ ≥2 **และ** อัตรา ≥ 30% บนฐาน ≥3) |
| **BR-BR-08** | การเตือนก่อนเปิดพัสดุ COD **ห้ามบล็อก** — เป็นข้อความ + ปุ่มยืนยันเท่านั้น (D-3) |
| **BR-BR-09** | ถ้อยคำต้องเป็น **"พัสดุตีกลับ"** ห้ามใช้ "ปฏิเสธรับของ"/"ลูกค้าโกง"/"เสี่ยง" ในสิ่งที่ร้านเห็น — เราไม่รู้ว่าใครผิด (R-1) |
| **BR-BR-10** | `BUYER_NO_PAYMENT` · `BUYER_NO_SHOW` · `BUYER_NO_TRANSFER` · `BUYER_REQUESTED` = เข้าประวัติลูกค้า · `PARCEL_RETURNED` = **ไม่**เข้าผ่านเหตุผล (นับจาก `carrierStatus` ไปแล้ว — BR-BR-03) |
| **BR-BR-11** | คะแนนผลกระทบต่อผู้ซื้อ (D-4) รอบนี้ **คำนวณสดเท่านั้น ห้ามเขียนทับ `User.trustScore`** จนกว่าจะมีมติเปิดใช้ (R-3) |
| **BR-BR-12** | ผู้ซื้อที่ยังไม่มี `Customer` (ออเดอร์ที่ไม่มีเบอร์) = ไม่มีสถิติ → UI ต้องไม่แสดงแถบเปล่า ต้องไม่แสดงเลย |

## 3. เหตุผลยกเลิกที่เข้าประวัติลูกค้า — SSOT ใหม่

ปัจจุบัน `cancelReasonCountsAgainstGuest()` อ่านจาก `CANCEL_REASONS` ใน `lib/lodging.ts`
ซึ่งมีแค่ 4 ค่าของโดเมนที่พัก ⇒ เหตุผลของร้านขายออนไลน์/บริการ **ไม่เคยถูกนับเลย**

| เหตุผล | vertical | เข้าประวัติลูกค้า | หมายเหตุ |
|---|---|---|---|
| `BUYER_NO_TRANSFER` | LODGING | ✅ | เดิมมีอยู่แล้ว |
| `BUYER_REQUESTED` | ทุก vertical | ✅ | เดิมมีอยู่แล้ว |
| `BUYER_NO_PAYMENT` | ONLINE_SALES | ✅ **ใหม่** | บน prod มี 1 ใบที่หายไปเงียบ ๆ |
| `BUYER_NO_SHOW` | SERVICE_QUEUE | ✅ **ใหม่** | |
| `PARCEL_RETURNED` | ONLINE_SALES | ❌ ตั้งใจ | นับจาก `carrierStatus` แล้ว (BR-BR-03) |
| `SHOP_ISSUE` | ทุก vertical | ❌ | ความผิดร้าน (BR-BR-04) |
| `MUTUAL` | ทุก vertical | ❌ | ตกลงกันได้ |

🛑 ต้องเป็น **allow-list** ไม่ใช่ deny-list — เหตุผลใหม่ที่ใครเพิ่มทีหลังต้อง "ไม่นับ" เป็นค่าตั้งต้น
การเดาผิดฝั่งนี้แปลว่าติดตราลูกค้าจากเหตุที่เขาไม่ได้ก่อ

## 5. D-4 · ผลกระทบต่อ Trust Score (ทำแล้ว 2026-08-24 — สวิตช์ยังปิด)

### 5.1 ข้อเท็จจริงที่เปลี่ยนความหมายของ D-4

สำรวจ prod ก่อนลงมือ:

| | จำนวน |
|---|---|
| `Customer` ทั้งหมด | **477** |
| ที่ผูกกับ `User` (มีบัญชีจริง) | **36 (7.5%)** |
| ลูกค้าที่มีพัสดุตีกลับ | 12 |
| **ในนั้นมีบัญชี** | **0** |

🛑 `Trust Score` ผูกกับ `User` แต่ผู้ซื้อ **92.5% ไม่มีบัญชี** ⇒ ถ้าทำ D-4 เป็น "หักคะแนน
`User.trustScore`" อย่างเดียว **วันที่ ship จะไม่กระทบใครเลยแม้แต่คนเดียว** แล้วเราจะบันทึกว่า
"ทำ D-4 แล้ว" ซึ่งเป็นคลาสเดียวกับ `docs/conventions/known-limitation-vs-unfinished.md`

ดังนั้นคะแนนคำนวณจาก **`BuyerReputation` ของ `Customer`** (ครบ 477 คน) แล้วค่อยไหลไป
`User.trustScore` เฉพาะคนที่ผูกบัญชี — ไม่ใช่กลับกัน · ตัวเลขที่ *ทุกคน* มีผลจริงคือแถบใน
แผงลูกค้าและคำเตือนก่อนเปิด COD ซึ่ง ship ไปแล้วในรอบก่อน

### 5.2 สูตร (`src/lib/buyer-trust.ts`)

| ค่า | ตัวเลข | เหตุผล |
|---|---|---|
| `PENALTY_PER_RETURNED` | 3 / ใบ | ของเดินทางไป-กลับจริง ร้านจ่ายค่าส่งสองขา |
| `PENALTY_PER_BUYER_CANCEL` | 1.5 / ใบ | ยังไม่มีของเดินทาง เบากว่าครึ่งหนึ่ง |
| `BUYER_CONDUCT_PENALTY_MAX` | **15** | ≈ "อายุบัญชี 10 + เหรียญตรา 10" · **ต้องน้อยกว่า 35 (verification เต็ม)** เสมอ — คนที่พิสูจน์ตัวตนแล้วต้องยังอยู่เหนือคนที่ไม่เคยพิสูจน์อะไรเลย ไม่งั้นการยืนยันตัวตนไร้ความหมาย (มีเทสบังคับ) |

ไม่มีข้อมูล = **หัก 0** ห้ามเดา — ผู้ซื้อที่ยังไม่เคยสั่งอะไรไม่ใช่ผู้ซื้อที่แย่

### 5.3 สถานะการเปิดใช้

`BUYER_CONDUCT_PENALTY_ENABLED = false` — รอบนี้ **คำนวณและบันทึกลง
`TrustScoreHistory.breakdown` (`buyerConduct` + `base`) แต่ยังไม่หักจริง** ตาม BR-BR-11

เหตุผล: D-4 คือการกลับหลักการ "มีแต่ขึ้น ไม่มีหัก" (PRD FR-3.5) ที่ประกาศไว้แต่แรก —
บันทึกก่อนเปิดทำให้มีข้อมูลย้อนหลังเทียบได้ว่า "ถ้าเปิดวันนี้ ใครเปลี่ยนไปเท่าไร"

**เปิดใช้ยังไง:** แก้ค่าคงที่ตัวเดียว → เทส `[blocker]` ข้อ "สวิตช์ต้องยังปิดอยู่" จะแดงทันที
โดยตั้งใจ เพื่อบังคับให้อ่าน R-3 ก่อน · ต้องอัปเดตหัวข้อนี้ในคอมมิตเดียวกัน

🛑 ตัวกันคะแนนตกของเดิม (`Math.max(user.trustScore, computed)`) **ยังอยู่และต้องอยู่ต่อ** —
แม้เปิดสวิตช์ ผู้ใช้ที่เคยได้คะแนนแล้วจะไม่เห็นคะแนนลดลงเอง การหักมีผลกับ *การขึ้นในอนาคต*
เท่านั้น (มีเทสบังคับ)

### 5.4 AC เพิ่ม

| # | เกณฑ์ |
|---|---|
| AC-BR-11 | สวิตช์ปิด → คะแนนเท่าเดิมทุกกรณี ไม่ว่าประวัติแย่แค่ไหน |
| AC-BR-12 | `buyerConduct` + `base` ถูกบันทึกลงประวัติเสมอ แม้สวิตช์ปิด |
| AC-BR-13 | เพดานการหัก < คะแนนยืนยันตัวตนเต็ม (35) |
| AC-BR-14 | ไม่มีข้อมูล → หัก 0 (ห้ามเดาว่าหักเต็ม) |
| AC-BR-15 | การหักต้องเดินผ่าน `applyBuyerConductPenalty` ห้ามลบเองที่จุดเรียก (ข้ามสวิตช์) |

## 6. หลักฐานสำหรับข้อพิพาท (หัวหน้าสั่ง 2026-08-24)

> "ควรจะบันทึกหลักฐานกรณีตีกลับ (เช่น logs จากขนส่ง) ไว้ด้วย กรณีมีการยื่นพิพาทไหม —
> เก็บกรณีมีปัญหาเท่านั้น"

### 6.1 ทำไมของเดิมใช้เป็นหลักฐานไม่ได้ (วัดจาก prod 2026-08-24)

| | ค่า |
|---|---|
| `ShipmentEvent` ทั้งหมด | 1,015 แถว |
| **ที่มี `payload` ดิบจากขนส่ง** | **0 แถว** |
| แหล่งที่มา | `POLL` 100% — **webhook ของ iShip ไม่เคยยิงเลยสักครั้ง** |
| พัสดุ active ทั้งหมด | 399 ใบ |
| **ที่ไม่มี event เลย** | **255 ใบ (64%)** |
| พัสดุมีปัญหา/ตีกลับที่ไม่มี event | 1 / 15 |

🛑 `ShipmentEvent` ถูกเขียนจาก 2 ทางเท่านั้น: `getTraces()` (ตอน **มีคนเปิดดู**) และ
`handleStatusWebhook()` (ซึ่งไม่เคยทำงาน) ⇒ หลักฐานที่มีอยู่คือ "ภาพตอนที่บังเอิญมีคนเอาเมาส์
ไปวาง" ไม่ใช่ "ภาพตอนเกิดเหตุ" และไม่มี payload ดิบให้ยืนยันอะไรได้เลย

### 6.2 ตาราง `ShipmentEvidence` (append-only)

| กฎ | รายละเอียด |
|---|---|
| **BR-BR-16** | เก็บ **เฉพาะ** `carrierStatus ∈ EVIDENCE_CARRIER_STATUSES` (= ชุดมีปัญหา + ชุดตีกลับ + `cancelled`) — เส้นทางปกติ (delivered/in_transit/payment_success/close) **ห้ามเก็บ** |
| **BR-BR-17** | จุดจุดชนวนคือ `applyCarrierStatus()` — **จุดเดียวในระบบที่รู้ว่าสถานะ *เพิ่งเปลี่ยน*** เก็บที่อื่นจะได้ภาพผิดเวลา |
| **BR-BR-18** | เก็บ **payload ดิบทั้งก้อน** (`traces` + `parcel`) ห้าม normalize ทิ้ง — นั่นคือประเด็นของหลักฐาน |
| **BR-BR-19** | กันซ้ำด้วย `@@unique([shipmentId, reason])` ที่ระดับฐาน ไม่ใช่ find-then-insert (poller หลายรอบทับกันได้) · สถานะใหม่ของใบเดิมเก็บเพิ่มได้ (`return` → `return_success` = 2 แถว) |
| **BR-BR-20** | ตัวเก็บ **ห้าม throw ออกไปหาลูป sync** — ใบเดียวล้มต้องไม่ลากทั้งรอบตาย · ดึงไม่ได้ = **บันทึกแถวที่มี `error`** ไม่ใช่ไม่บันทึกอะไรเลย ("ไม่มีแถว" = ไม่เคยพยายาม ซึ่งคนละเรื่องกับ "พยายามแล้วขนส่งไม่ตอบ" และวันที่ต้องใช้หลักฐานสองอันนี้ต่างกันมาก) |
| **BR-BR-21** | `traceCount = 0` เป็นหลักฐานในตัวมันเอง (ขนส่งไม่มีบันทึกอะไรเลย) ไม่ใช่ค่าที่แปลว่า "เก็บไม่สำเร็จ" |
| **BR-BR-22** | 🛑 **PDPA** — `parcel` มีชื่อ/เบอร์/ที่อยู่ผู้รับดิบ ๆ **ห้ามมี API ไหน serve คอลัมน์นี้ออกไปตรง ๆ** ใช้ตอนสืบสวนข้อพิพาทเท่านั้น |

### 6.3 กับดักที่เกือบหลุดตอนเขียนรอบนี้

ร่างแรกรับ `shopId` เป็น **optional** บนอ็อบเจกต์ `s` ของ `applyCarrierStatus()` แต่ `select`
ของชุด tracking **ไม่ได้ดึง `shopId` มา** ⇒ `if (s.shopId && …)` เป็นเท็จตลอดกาล
**ฟีเจอร์ตายเงียบสนิทโดยทุก gate เขียว** (`tsc` ไม่ฟ้องเพราะ optional แปลว่า "ไม่ส่งก็ได้")
→ เปลี่ยนเป็น positional บังคับ ลืมส่งเมื่อไร compile ไม่ผ่าน + เทส `[blocker]` ปักหมุด
(คลาสเดียวกับ `docs/conventions/rule-must-be-enforced-not-described.md`)

| AC-BR-20 | สคีมามี `@@unique([shipmentId, reason])` |

### 6.5 ยังไม่ทำ

- **ไม่มีหน้าจอให้ดูหลักฐาน** — รอบนี้เก็บอย่างเดียว (ตั้งใจ: เก็บก่อนถึงจะมีของให้ดู
  ถ้าทำจอก่อนจะได้จอเปล่า) การอ่านตอนนี้ทำผ่าน SQL ตอนสืบสวน
- ไม่มีตัวเก็บย้อนหลังสำหรับ 15 ใบที่มีปัญหาอยู่แล้ววันนี้ — สถานะไม่เปลี่ยนอีกแล้วจึงไม่มี
  อะไรจุดชนวน ต้องทำเป็นสคริปต์แยกถ้าต้องการ
