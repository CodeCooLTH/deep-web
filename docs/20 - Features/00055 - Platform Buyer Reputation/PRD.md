# PRD — 00055 สถิติผู้ซื้อระดับแพลตฟอร์ม (Platform Buyer Reputation)

> สถานะ: Draft · เริ่ม 2026-08-24 · ที่มา: หัวหน้าสั่งตรง ("ทำสถิติ buyer ระดับ platform ให้หน่อย")
> ต่อยอดจากคำถาม "แล้วเราบันทึกสถิติผู้ซื้อไหม ว่าเค้ารับของกี่ครั้ง ปฏิเสธรับกี่ครั้ง"

---

## 1. ปัญหา

ร้านตัดสินใจ **"จะเปิดพัสดุเก็บเงินปลายทางให้ลูกค้าคนนี้ไหม"** โดยไม่มีข้อมูลเลยว่าลูกค้าคนนี้
เคยปฏิเสธรับของมาก่อนหรือเปล่า — ค่าเสียหายต่อครั้งคือ **ค่าส่งไป-กลับ + ของที่หมุนไม่ได้ 5–10 วัน**
และเป็นต้นทุนที่ร้านจ่ายเต็มจำนวนโดยไม่ได้อะไรกลับมา

ระบบมีสถิติอยู่แล้ว (`src/lib/customer-behavior.ts` → ชิป "ตีกลับ N รายการ") แต่
**scope ผูกกับร้าน** (`customer-behavior.service.ts:37` — `where: { shopId: { in: shopIds } }`)
⇒ ลูกค้าที่ปฏิเสธรับของมาแล้ว 5 ร้าน จะขึ้นว่า "ตีกลับ 1 รายการ" ในสายตาของทุกร้าน
ไม่มีร้านไหนเห็นภาพรวม และร้านที่ 6 ก็จะโดนเป็นรายต่อไป

### 1.1 ข้อมูลจริงบน prod (2026-08-24)

| ตัวชี้วัด | ค่า |
|---|---|
| ออเดอร์ที่พัสดุตีกลับ (`return`/`return_success`) | 12 ใบ |
| ลูกค้าที่เกี่ยวข้อง | **12 คน — ไม่ซ้ำกันเลย** |
| ร้านที่เจอ | 1 ร้าน |

🛑 **แปลว่าฟีเจอร์นี้จะยัง "ไม่มีอะไรให้ดู" ในระยะสั้น** — ไม่มีเคสลูกค้าปฏิเสธซ้ำแม้แต่คนเดียว
เหตุผลที่ยังทำตอนนี้คือ **ข้อมูลต้องเริ่มสะสมก่อนถึงจะมีประวัติให้ใช้** ไม่ใช่เพราะมีปัญหาเฉพาะหน้า
เอกสารนี้บันทึกไว้เพื่อไม่ให้ใครอ่านตัวเลข "0 คนซ้ำ" ในอีก 3 เดือนแล้วสรุปว่าฟีเจอร์พัง

## 2. เป้าหมาย

ให้ร้าน **เห็นพฤติกรรมการรับของของลูกค้าในระดับทั้งระบบ** ก่อนตัดสินใจเปิดพัสดุ COD
โดยไม่เปิดเผยว่าเหตุการณ์นั้นเกิดที่ร้านไหน

### ไม่ใช่เป้าหมาย (Out of scope รอบนี้)
- แบนลูกค้า / บล็อกการสั่งซื้ออัตโนมัติ — ระบบ **เตือน** เท่านั้น ร้านตัดสินใจเอง
- ให้ร้านเห็นรายชื่อร้านอื่นที่ลูกค้าเคยสั่ง (ดู D-2)
- ให้ผู้ซื้อเห็นสถิติของตัวเอง (ดู D-2 ทางเลือกที่ไม่ถูกเลือก)
- ตัวชี้วัดฝั่งร้าน (มีอยู่แล้วที่ `shop.service.ts` อัตราความสำเร็จ)

## 3. ผู้ใช้และ user story

| # | ในฐานะ | ฉันอยากจะ | เพื่อ |
|---|---|---|---|
| US-1 | ผู้ขาย | เห็นว่าลูกค้าคนนี้ทั้งระบบสั่งกี่ครั้ง รับของกี่ครั้ง ปฏิเสธกี่ครั้ง | ประเมินความเสี่ยงก่อนรับออเดอร์ |
| US-2 | ผู้ขาย | ถูกเตือนตอนกำลังจะเปิดพัสดุ COD ให้ลูกค้าที่มีประวัติปฏิเสธรับ | ไม่จ่ายค่าส่งไป-กลับฟรี |
| US-3 | ผู้ขาย | รู้ว่าตัวเลขนี้ไม่ได้มาจากร้านฉันร้านเดียว | เชื่อถือได้มากกว่าประวัติในร้านตัวเอง |
| US-4 | แพลตฟอร์ม | สะท้อนพฤติกรรมผู้ซื้อลงคะแนนความน่าเชื่อถือ | ให้ Trust Score มีความหมายกับผู้ซื้อด้วย ไม่ใช่แค่ผู้ขาย |

## 4. มติที่หัวหน้าเคาะแล้ว (2026-08-24)

| # | มติ | ทางเลือกที่ไม่ถูกเลือก + เหตุผลที่ต้องรู้ |
|---|---|---|
| **D-1** | **ทุกร้านเห็นตัวเลขรวมทั้งระบบ** | "เฉพาะแอดมิน" (ปลอดภัยกว่าแต่ร้านไม่ได้ประโยชน์เลย) · "ผู้ซื้อเห็นของตัวเองด้วย" (ต้องมีหน้าโปรไฟล์ + สิทธิ์แก้ไข/โต้แย้ง = งานอีกก้อน) |
| **D-2** | **เห็นเฉพาะ "ตัวเลขรวม" ห้ามเห็นว่าเกิดที่ร้านไหน** | บังคับที่ชั้น query ไม่ใช่แค่ไม่แสดงบนจอ (DAL pattern) — ชื่อร้านอื่นคือข้อมูลธุรกิจของร้านนั้น ไม่ใช่ของเรา |
| **D-3** | **เตือนตอนเปิดพัสดุ COD** | เตือนเฉย ๆ กดต่อได้ **ห้ามบล็อก** — เราไม่รู้บริบท (อาจเป็นลูกค้าประจำที่บ้านเลขที่ผิดครั้งเดียว) |
| **D-4** | **กระทบ Trust Score ผู้ซื้อ** | 🛑 นี่คือการ**กลับหลักการเดิมของ MVP** ที่ระบุว่า "มีแต่ขึ้น ไม่มีหัก" — ดู §6 ความเสี่ยง |
| **D-5** | **นับ `BUYER_NO_PAYMENT` เข้าประวัติลูกค้าด้วย** | ตอนนี้ยังไม่ถูกนับเลย (ดู §5) |

## 5. ช่องโหว่ที่เจอระหว่างสำรวจ (แก้ไปกับรอบนี้)

🛑 **`cancelReasonCountsAgainstGuest()` รู้จักเหตุผลแค่ 4 ตัวของ "ที่พัก" เท่านั้น**
(`CANCEL_REASONS` ใน `src/lib/lodging.ts:180` = `BUYER_NO_TRANSFER` / `BUYER_REQUESTED` /
`SHOP_ISSUE` / `MUTUAL`) แต่ร้านขายออนไลน์กับร้านบริการใช้ชุดของตัวเองใน
`src/lib/cancel-reasons.ts` ซึ่งมี **`BUYER_NO_PAYMENT` · `BUYER_NO_SHOW` · `PARCEL_RETURNED`**
สามตัวนี้ **ไม่อยู่ในแมปที่มี `countsAgainstGuest` เลย** ⇒ `isCancelReason()` คืน false
⇒ **ไม่เคยถูกนับเข้าประวัติลูกค้าสักครั้ง**

ผลจริง: "ลูกค้าไม่โอนเงิน" กับ "ลูกค้าไม่มาตามนัด" — สองพฤติกรรมที่ชี้ตัวคนทำชัดที่สุด —
เป็นสองอันที่ระบบมองไม่เห็น ขณะที่ `SHOP_ISSUE` (ความผิดร้าน) ถูกประกาศไว้ว่าไม่นับ ซึ่งถูกแล้ว
บน prod มี `BUYER_NO_PAYMENT` 1 ใบที่หายไปจากประวัติลูกค้าโดยไม่มีอะไรฟ้อง

`PARCEL_RETURNED` เป็นข้อยกเว้นที่ **ตั้งใจให้ไม่นับผ่านเหตุผล** — เพราะ `customer-behavior.ts`
นับใบนั้นจาก `carrierStatus` ไปแล้ว (ตีกลับชนะยกเลิกเสมอ ใบเดียวนับครั้งเดียว) ถ้านับผ่านเหตุผลอีก
จะกลายเป็น 2 ครั้งจากใบเดียว

## 6. ความเสี่ยงที่ต้องรับรู้ก่อนอนุมัติ

| # | ความเสี่ยง | การจัดการ |
|---|---|---|
| R-1 | **ติดตราลูกค้าที่ไม่ผิด** — พัสดุตีกลับเกิดจากที่อยู่ผิด/ขนส่งส่งไม่ถึงได้ ไม่ใช่ลูกค้าปฏิเสธเสมอ | ใช้คำว่า "พัสดุตีกลับ" ไม่ใช่ "ปฏิเสธรับของ" · แสดงเป็น **จำนวน + อัตรา** ไม่ตัดสินว่าใครผิด · เคยพลาดคลาสนี้มาแล้ว 2026-08-11 (ป้าย "เคยยกเลิก N ครั้ง" นับการยกเลิกของร้านเองไปโทษลูกค้า) |
| R-2 | **ฐานน้อยแล้วอัตราหลอก** — สั่ง 1 ตีกลับ 1 = 100% ซึ่งอ่านว่าเลวร้ายที่สุดในระบบ | ไม่แสดงอัตราเมื่อออเดอร์ < `MIN_ORDERS_FOR_RATE` · แสดงจำนวนดิบแทน |
| R-3 | 🛑 **D-4 กลับหลักการ "Trust Score มีแต่ขึ้น"** — ผู้ซื้อที่เคยได้คะแนนแล้วอาจเห็นคะแนนตัวเองลดลงโดยไม่เคยถูกบอกล่วงหน้า | รอบนี้ทำเป็น **ตัวเลขที่คำนวณสด แยกจาก `User.trustScore` ที่เก็บในฐาน** ยังไม่เขียนทับค่าเดิม — ให้หัวหน้าเห็นผลจริงก่อนตัดสินใจเปิดใช้ (ดู SRS FR-BR-08) |
| R-4 | **PDPA** — ตัวเลขรวมไม่ระบุร้าน ถือเป็นข้อมูลพฤติกรรมของบุคคล | D-2 บังคับไม่ให้ระบุแหล่ง · ไม่มีการส่งออกนอกระบบ · ผู้ซื้อขอลบบัญชีแล้วประวัติหายตาม (soft delete เดิม) |
| R-5 | **ลูกค้าคนเดียวมีหลาย `Customer` ได้** ถ้าใช้คนละเบอร์ | ยอมรับ — `Customer.phone` เป็น `@unique` ระดับระบบอยู่แล้ว ไม่มีตัวรวมที่ดีกว่านี้ในตอนนี้ |

## 7. Metrics ความสำเร็จ

- ร้านเห็นแถบ "ทั้งระบบ" ในแผงลูกค้า ≥1 ครั้ง/วันทำการ (proxy: มีการเปิดแผง)
- จำนวนใบที่ตีกลับต่อ 100 ออเดอร์ COD **ลดลง** หลังเปิดใช้การเตือน (วัดหลัง 60 วัน)
- ไม่มีรายงานจากร้านว่า "ป้ายบอกว่าลูกค้าแย่ทั้งที่ไม่จริง" (R-1)

## 8. ขอบเขตรอบนี้

ปิดช่องโหว่ §5 · Trust Score แบบคำนวณสดที่ยังไม่เขียนทับ
