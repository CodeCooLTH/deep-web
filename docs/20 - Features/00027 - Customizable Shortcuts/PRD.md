# PRD: เมนูลัดที่ตั้งค่าเองได้ (Customizable Shortcuts)

---

## Executive Summary

วันนี้ "เมนูลัด" บน Command Center ของ seller (การ์ดที่อยู่บนสุดของ `/dashboard` เวอร์ชันมือถือ) เป็น **array คงที่ 8 ช่อง** (`SHORTCUT_TILES` ใน `dashboard/_constants/command-center.ts`) ที่เหมือนกันทุกคนทุกร้าน ไม่ผูกกับสิทธิ์ใด ๆ เลย — ปัญหาคือร้านแต่ละแบบใช้เมนูไม่เหมือนกัน (ร้านบ้านพักไม่มีสินค้า ไม่มีประมูล; พนักงานร้านอยากได้ทางลัดคนละชุดกับเจ้าของ) และเมนูจริงของระบบมีมากกว่าที่การ์ดนี้แสดงมาก (23-25 รายการใน `_seller-menu.ts` ซึ่งเป็น SSOT ของเมนูจริง เทียบกับ 7 รายการที่ใช้งานได้จริงใน `SHORTCUT_TILES` ปัจจุบัน)

ฟีเจอร์นี้เปลี่ยนเมนูลัดจาก **static ทุกคนเหมือนกัน** เป็น **ตั้งค่าได้ต่อคน × ต่อร้าน** — คนคนเดียวเปิดหลายร้าน ตั้งเมนูลัดแยกกันต่อร้านได้; หลายคนในร้านเดียวกัน (เจ้าของ/พนักงาน) ตั้งของตัวเองแยกกันได้ โดยเลือกจาก **แคตตาล็อกเมนูจริงที่ตัวเองมีสิทธิ์เห็น** เท่านั้น (SSOT เดียวกับ sidebar `_seller-menu.ts` — reuse ตัวกรองสิทธิ์ที่มีอยู่แล้วทั้งหมด ไม่สร้างกฎสิทธิ์คู่ขนาน) จำกัดไม่เกิน **8 ช่องพอดี** (ไม่ต้องมี carousel หลายหน้า — บังคับให้ผู้ใช้เลือกว่าอะไรสำคัญจริง) และแก้ไขได้ผ่าน **ปุ่มแก้ไขบนการ์ดเมนูลัดเอง** ไม่มีหน้าตั้งค่าแยก

ขอบเขตทางเทคนิคที่สำคัญที่ค้นพบระหว่างสำรวจโค้ด: เมนูลัดนี้ปัจจุบัน **render เฉพาะมือถือ** (`lg:hidden` ใน `dashboard/page.tsx`) — เดสก์ท็อปไม่มี widget เมนูลัดเลย ใช้ layout อื่นทั้งหมด ฟีเจอร์นี้จึงมีขอบเขต MVP = มือถือเท่านั้น (ดู §3.9/§9.2 Q7)

## 1. Business Goals & KPIs

### 1.1 เป้าหมายทางธุรกิจ

| เป้าหมาย | รายละเอียด |
|----------|-----------|
| **ลดความไม่เกี่ยวข้องของเมนูลัด** | เมนูลัดคงที่วันนี้ไม่รู้จัก vertical/role — ร้านบ้านพัก, พนักงานร้าน, ร้าน personal เห็นชุดเดียวกันหมดทั้งที่ใช้งานคนละแบบ |
| **เปิดทางเข้าถึงฟีเจอร์จริงทั้งระบบ ไม่ใช่แค่ 7 รายการเดิม** | Catalog ใหม่อ้างอิง SSOT เมนูจริง (23-25 รายการ) แทนลิสต์แยกที่ไม่เคยอัปเดตตามเมนูจริง (เช่น ไม่มี "ข้อความ"/"ค่าใช้จ่าย"/"ChatBot" ในเมนูลัดปัจจุบันทั้งที่เป็นเมนูจริงมานานแล้ว) |
| **เพิ่ม efficiency การเข้าถึงฟีเจอร์ที่ใช้บ่อยของแต่ละคน** | Owner กับพนักงานใช้ฟีเจอร์ต่างกัน — ให้แต่ละคนตั้งของตัวเองแทนบังคับชุดเดียวกัน |
| **ไม่เพิ่มความซับซ้อนของหน้าจอ (No New Page)** | แก้ไขผ่านปุ่มบนการ์ดเดิม ไม่สร้างหน้าตั้งค่าใหม่ที่ต้องเรียนรู้เพิ่ม |

### 1.2 ตัวชี้วัดความสำเร็จ (KPIs)

| KPI | คำอธิบาย | เป้าหมาย |
|-----|----------|---------|
| **Customization Adoption Rate** | % ของ seller ที่ active (login ใน 30 วัน) ที่เคยแก้เมนูลัดอย่างน้อย 1 ครั้ง | วัด baseline เดือนแรกหลัง launch |
| **Shortcut Click-Through Rate เทียบ baseline** | จำนวนคลิกเมนูลัดต่อ session เทียบกับก่อนมีฟีเจอร์นี้ (ควรเพิ่มขึ้นถ้าเมนูลัดตรงความต้องการมากขึ้น) | เพิ่มขึ้นจาก baseline |
| **Zero Dead-Tile Rate** | % ของการ render เมนูลัดที่มี tile ที่ผู้ใช้ไม่มีสิทธิ์เข้าถึงจริง (ต้อง = 0 เสมอ) | 0% เสมอ (correctness, ไม่ใช่ adoption metric) |
| **Reset Usage** | % ของผู้ใช้ที่เคยกด "รีเซ็ตเป็นค่าเริ่มต้น" | ติดตามเป็น baseline (สัญญาณว่า custom UX สับสนไหม) |

## 2. User Personas (กลุ่มผู้ใช้งาน)

### 2.1 Seller เจ้าของร้าน (Owner) — Primary

**ข้อมูลพื้นฐาน:**
- Owner ของ Shop อย่างน้อย 1 ร้าน (PERSONAL หรือ BUSINESS) — อาจเป็นเจ้าของหลายร้านพร้อมกัน (feature 00008)
- เปิด `/dashboard` บนมือถือเป็นหน้าแรกที่เจอบ่อยที่สุด

**เป้าหมาย:**
- เข้าฟีเจอร์ที่ใช้บ่อยที่สุดของร้านตัวเองได้เร็วที่สุด โดยไม่ต้องไล่เมนู sidebar ทุกครั้ง

**ความต้องการ:**
- เลือกเมนูลัดจากฟีเจอร์จริงที่ร้านตัวเองมีสิทธิ์ใช้ (ไม่ใช่ลิสต์ตายตัวที่ไม่ตรงกับร้านตัวเอง)
- ถ้ามีหลายร้าน ตั้งเมนูลัดแยกกันตามความสำคัญของแต่ละร้าน

**จุดปวด (Pain Points):**
- เมนูลัดเดิมมีเมนูที่ตัวเองไม่เคยใช้ (เช่น "คูปอง" ที่ปิดใช้งานอยู่) แต่ไม่มีเมนูที่อยากได้ (เช่น "ข้อความ"/"ค่าใช้จ่าย")

### 2.2 พนักงานร้าน (ShopMember role=ADMIN) — Secondary

**ข้อมูลพื้นฐาน:**
- ถูก owner invite เข้ามาช่วยบริหาร Business shop (feature 00008/00012, live แล้ว)
- ใช้ฟีเจอร์คนละชุดกับ owner (เช่น เน้นดูออเดอร์/ลูกค้า ไม่เน้นแพ็กเกจ/พนักงาน)

**เป้าหมาย:**
- ตั้งเมนูลัดของตัวเองแยกจาก owner โดยไม่ไปแตะของ owner

**ความต้องการ:**
- เห็นเฉพาะเมนูที่ตัวเองมีสิทธิ์จริง (เช่น ถ้า owner ไม่เปิด `staffCanViewFinance` ต้องไม่เห็น "ค่าใช้จ่าย" เป็นตัวเลือกในแคตตาล็อกด้วย)

**จุดปวด (Pain Points):**
- ถ้าเผลอปักหมุดเมนูที่ตัวเองไม่มีสิทธิ์ (เพราะยังไม่ได้กรองตอนเลือก) จะเจอ tile ที่กดแล้วพัง/โดนบล็อกทันที

### 2.3 Seller ร้านบ้านพัก (LODGING vertical) — Boundary Persona

**ข้อมูลพื้นฐาน:**
- ร้าน `Shop.vertical = 'LODGING'` (feature 00017) — ไม่มีสินค้า/ประมูล/สต็อก แต่มีห้องพัก/ปฏิทิน/การจอง/แม่บ้าน

**เป้าหมาย:**
- เห็นเฉพาะเมนูลัดที่เกี่ยวกับธุรกิจบ้านพักจริง

**ความต้องการ:**
- แคตตาล็อกต้องกรองเมนูตาม vertical เหมือนที่ sidebar ทำอยู่แล้ว (`applyVerticalMenu`) — ห้ามเห็น "สินค้า"/"ประมูล"/"จัดการสต็อก" เป็นตัวเลือก

**จุดปวด (Pain Points):**
- ถ้าแคตตาล็อกไม่กรอง vertical จะเห็นเมนูที่กดไปแล้วไม่มีความหมายกับธุรกิจตัวเองเลย

### 2.4 Seller ที่ยังไม่เคยตั้งค่าเมนูลัด (Never-Customized) — Boundary Persona

**ข้อมูลพื้นฐาน:**
- ผู้ใช้ใหม่ทุกคน (100% ของ user ก่อนฟีเจอร์นี้ launch) อยู่ในสถานะนี้ตั้งแต่วันแรก

**เป้าหมาย:**
- ใช้งาน `/dashboard` ได้ทันทีโดยไม่ต้องตั้งค่าอะไรก่อน

**ความต้องการ:**
- เห็นเมนูลัด "ค่าเริ่มต้น" ที่สมเหตุสมผลตั้งแต่ครั้งแรก ไม่ใช่การ์ดว่างเปล่าที่บังคับให้ตั้งค่าก่อนใช้

**จุดปวด (Pain Points):**
- ถ้า default ไม่ดี/ว่างเปล่า จะรู้สึกว่าฟีเจอร์พัง ไม่ใช่ฟีเจอร์ personalization

## 3. Business Requirements

### 3.1 ขอบเขตการเก็บค่า: ต่อคน × ต่อร้าน (ล็อกแล้วโดย user)

**ความต้องการ:**
- การตั้งค่าเมนูลัดต้องแยกกันตามคู่ (ผู้ใช้, ร้าน) เสมอ — ไม่ใช่ต่อ user เฉย ๆ และไม่ใช่ต่อ shop เฉย ๆ

**Business Rules:**
- คนคนเดียวที่เป็นสมาชิกหลายร้าน (owner ของหลายร้าน หรือเป็น staff ของร้านอื่นด้วย) ตั้งเมนูลัดแยกกันได้ทุกร้าน
- หลายคนในร้านเดียวกัน (owner + staff หลายคน) ตั้งเมนูลัดของตัวเองแยกกันได้ทั้งหมด ไม่มีใครเห็น/แก้ของคนอื่นได้
- Preference ผูกกับ "ร้านที่กำลังดูอยู่ (active shop)" เสมอ — สลับร้าน (shop switcher) = เห็นเมนูลัดของร้านนั้นตามที่ตัวเองเคยตั้งไว้

**เหตุผล:**
- ตรงกับ decision ที่ user เคาะแล้ว — สะท้อนพฤติกรรมจริงที่คนคนเดียวมีหลายร้าน และร้านเดียวกันมีหลายคนใช้งานคนละสไตล์

### 3.2 แคตตาล็อกเมนูลัด = SSOT เดียวกับ Sidebar

**ความต้องการ:**
- รายการเมนูให้เลือกปักหมุดต้องดึงจากแหล่งเดียวกับเมนู sidebar จริง (`_seller-menu.ts`) ไม่ใช่ลิสต์แยกต่างหาก

**Business Rules:**
- Catalog ที่ผู้ใช้คนหนึ่งเห็นตอนแก้ไขเมนูลัด = ผลลัพธ์หลัง apply ตัวกรองสิทธิ์ชุดเดียวกับที่ sidebar ใช้อยู่แล้วทั้งหมด (`applyStaffMenu`, `applyVerticalMenu`, `applyAppointmentMenu`, `applyExpenseMenu`) — รายการที่ถูกกรองออกจาก sidebar (เช่น "พนักงาน" สำหรับ staff, "ค่าใช้จ่าย" สำหรับ staff ที่ toggle ปิด, เมนูบ้านพักสำหรับร้าน GENERAL) ต้องไม่ปรากฏเป็นตัวเลือกในแคตตาล็อกด้วยเช่นกัน
- รายการที่ยังเห็นได้แต่ถูก "แต่งเป็น badge/disabled" (`applyInventoryGate`, `applyChatBadge` — เช่น "จัดการสต็อก" ที่ยังไม่ได้สมัคร) ยังคง**เป็นตัวเลือกได้** เพราะ sidebar เองก็ยังพาไปหน้านั้นได้ (แค่หน้าเป้าหมายจะโชว์ upsell/locked state เอง — สอดคล้องพฤติกรรมเดิมของ sidebar ไม่เพิ่มความสามารถใหม่)
- เมนูที่ href เป็น `null`/ยังไม่เปิดใช้งานจริง (ไม่มีอยู่ใน `_seller-menu.ts` เลย เช่น "คูปอง" เดิม) **ไม่อยู่ในแคตตาล็อก** — เพราะไม่มีปลายทางจริงให้ไป (การปักหมุดสิ่งที่กดแล้วไม่ไปไหนคือ dead tile)
- เมนูลิงก์กลับไปหน้า `/dashboard` เอง (`seller:dashboard`) ไม่อยู่ในแคตตาล็อก — เพราะเมนูลัดนี้อยู่บนหน้า dashboard อยู่แล้ว ปักหมุดกลับมาที่เดิมไม่มีประโยชน์

**เหตุผล:**
- การใช้ SSOT เดียวกันตัดปัญหา "เมนูลัดไม่ sync กับเมนูจริง" ที่เกิดกับ `SHORTCUT_TILES` เดิม (ไม่เคยอัปเดตตามเมนูจริงที่เพิ่มมาเรื่อย ๆ) และลดความเสี่ยงเรื่อง permission-drift เพราะ reuse ตัวกรองที่ผ่านการทดสอบแล้วแทนเขียนกฎสิทธิ์ใหม่คู่ขนาน

### 3.3 จำกัด 8 ช่องพอดี (ล็อกแล้วโดย user)

**ความต้องการ:**
- ปักหมุดได้สูงสุด **8 รายการ** ต่อคู่ (ผู้ใช้, ร้าน) — ไม่มี carousel หลายหน้าให้เลื่อนดูเพิ่ม

**Business Rules:**
- เลือกได้ตั้งแต่ 1 ถึง 8 รายการ (ดู §3.6 สำหรับขั้นต่ำ)
- ครบ 8 แล้วพยายามเพิ่มรายการที่ 9 → ระบบบล็อก พร้อมข้อความให้ถอดรายการเดิมออกก่อน (ไม่ auto-ถอดรายการที่เก่าที่สุดแทน — ต้องเป็นการตัดสินใจของผู้ใช้เอง)

**เหตุผล:**
- ตรงกับ decision ที่ user เคาะแล้ว — บังคับให้ผู้ใช้เลือกสิ่งที่สำคัญจริงแทนยัดทุกอย่างเข้ามา และเลี่ยงความซับซ้อนของ UI แบบ pagination/carousel ที่ `CarouselGrid.tsx` (v10) เคยรองรับไว้แต่ตอนนี้ไม่จำเป็นแล้วเมื่อ cap อยู่ที่ 8 เสมอ

### 3.4 จุดตั้งค่า = ปุ่มแก้ไขบนการ์ดเมนูลัดเอง (ล็อกแล้วโดย user)

**ความต้องการ:**
- ไม่มีหน้าตั้งค่าแยกสำหรับฟีเจอร์นี้ — แก้ไขผ่านปุ่ม/action ที่อยู่บนการ์ด "เมนูลัด" บน Command Center โดยตรง

**Business Rules:**
- การ์ดเมนูลัดต้องมีทางเข้าสู่โหมดแก้ไข (เช่น ปุ่มแก้ไขที่ card-header) โดยไม่ navigate ออกจากหน้า `/dashboard` ไปหน้าอื่นในระบบเมนู/sidebar
- Layout/interaction ของโหมดแก้ไข (bottom sheet/modal/inline expand) เป็น decision ของ `safepay-ux` ตอนออก Design Spec (Hard Rule 8) — เอกสารนี้กำหนดแค่ business constraint ว่าต้อง "อยู่บนการ์ดเดิม" เท่านั้น

**เหตุผล:**
- ตรงกับ decision ที่ user เคาะแล้ว — ลดจำนวนหน้าที่ผู้ใช้ต้องเรียนรู้ ทำให้การปรับแต่งเป็นเรื่อง in-context ไม่ใช่ "ไปตั้งค่า" แยกต่างหาก

### 3.5 ค่าเริ่มต้น (Default Shortcut Set) สำหรับผู้ที่ยังไม่เคยตั้งค่า

**ความต้องการ:**
- ผู้ใช้ที่ไม่เคยแก้ไขเมนูลัดมาก่อน ต้องเห็นชุดเมนูลัดที่สมเหตุสมผลตั้งแต่ครั้งแรก ไม่ใช่การ์ดว่าง

**Business Rules:**
- ค่าเริ่มต้น = **8 รายการแรกตามลำดับที่ปรากฏใน sidebar (`_seller-menu.ts`) ของแคตตาล็อกที่ผู้ใช้คนนั้นเห็นจริง ณ ขณะนั้น** (หลัง apply ตัวกรองสิทธิ์ตาม §3.2) ไม่นับ `seller:dashboard`
- ถ้าแคตตาล็อกของผู้ใช้คนนั้นมีน้อยกว่า 8 รายการ (เช่น staff ที่ถูกกรองสิทธิ์ออกเยอะ) → ค่าเริ่มต้น = ทุกรายการที่มี (ไม่เติมของหลอกให้ครบ 8)
- กฎนี้ทำให้ default "ปรับตาม vertical/role อัตโนมัติ" โดยไม่ต้องมีลิสต์ default แยกสำหรับ LODGING/GENERAL/staff — เพราะแคตตาล็อกถูกกรองไว้แล้วตั้งแต่ต้นทาง

**เหตุผล:**
- Default ที่คำนวณจาก SSOT order เดียวกันกับสิทธิ์จริง เป็นกฎเดียวที่ดูแลรักษาง่าย (ไม่ต้อง sync ลิสต์ default แยกต่างหากทุกครั้งที่เมนูจริงเปลี่ยน) และรับประกันว่า default ไม่มีวันมี dead tile ตั้งแต่ต้น — ดู §9.2 Q1 สำหรับการยืนยันขั้นสุดท้าย

### 3.6 พฤติกรรมเมื่อเมนูที่เคยปักไว้ "หมดสิทธิ์" ภายหลัง (Entitlement Drift)

**ความต้องการ:**
- เมนูที่ผู้ใช้เคยปักหมุดไว้ แต่ภายหลังหมดสิทธิ์เข้าถึง (แพ็กเกจหมดอายุ, ถูกลดสิทธิ์จาก OWNER เป็นพนักงาน, ร้านเปลี่ยน vertical, `staffCanViewFinance` ถูกปิด ฯลฯ) ต้องไม่กลายเป็น dead tile ที่กดแล้วพัง

**Business Rules:**
- ทุกครั้งที่ render เมนูลัด ระบบต้อง intersect รายการที่ปักหมุดไว้กับแคตตาล็อกปัจจุบันที่ผู้ใช้มีสิทธิ์เห็น ณ ขณะนั้น (คำนวณสด ไม่ cache สิทธิ์เก่า) — รายการที่หมดสิทธิ์แล้ว **ซ่อนทันทีจากการ์ด** ไม่แสดง (ไม่ใช่โชว์แบบเทา/disabled ค้างไว้) สอดคล้องกับ pattern ที่ sidebar ใช้อยู่แล้ว (`applyStaffMenu`/`applyVerticalMenu`/`applyExpenseMenu` = ซ่อนทั้งรายการเช่นกัน)
- Preference ที่บันทึกไว้ (รายการที่เคยเลือก) **ไม่ถูกลบทิ้งอัตโนมัติ** เมื่อหมดสิทธิ์ชั่วคราว — ถ้าสิทธิ์กลับมา (เช่น ต่อแพ็กเกจใหม่) รายการนั้นกลับมาแสดงเองโดยผู้ใช้ไม่ต้องปักหมุดซ้ำ
- ระบบ **ไม่ auto-เติม** รายการอื่นมาแทนที่ช่องที่หายไปกลางคัน (เช่น รายการที่ 8 ที่หายไปเหลือ 7 ช่อง แสดง 7 ช่องเฉย ๆ) — การเติมอัตโนมัติจะทำให้เมนูลัดขยับตำแหน่งโดยผู้ใช้ไม่คาดคิด
- เมื่อผู้ใช้เปิดโหมดแก้ไข (§3.4) รายการที่ปักหมุดไว้แต่ตอนนี้ใช้ไม่ได้แล้ว ต้องแสดงเป็นสถานะ "ใช้ไม่ได้แล้ว" ให้ผู้ใช้เห็นและเลือกถอด/แทนที่ได้ (ไม่ใช่หายไปเงียบ ๆ จากทั้งการ์ดและหน้าแก้ไข)

**เหตุผล:**
- ป้องกัน information disclosure ผ่าน UI (tile ที่ชี้ไปหน้าที่ไม่มีสิทธิ์เข้า) และตรงกับ convention ที่มีอยู่แล้วของระบบ (menu-hiding ไม่ใช่ disable) — การไม่ auto-เติมป้องกันเมนูลัด "สลับตำแหน่งเอง" ที่ทำให้ผู้ใช้กดผิดปุ่มเพราะจำตำแหน่งเดิม

### 3.7 ลำดับการแสดงผล — ไม่มี Manual Reorder ใน MVP

**ความต้องการ:**
- รายการที่ปักหมุดไว้ต้องแสดงผลในลำดับที่คาดเดาได้ ไม่ต้องมี UI ลากจัดเรียงเอง

**Business Rules:**
- ลำดับการแสดงผล = ลำดับเดียวกับที่ปรากฏใน sidebar (`_seller-menu.ts`) เสมอ ไม่ใช่ลำดับที่ผู้ใช้กดเลือก
- ไม่มีการลากสลับตำแหน่ง (drag-to-reorder) ใน MVP

**เหตุผล:**
- ลดความซับซ้อนของ UI/state management ในรอบแรก (เทียบ precedent Pin Products ที่ตัดสินใจไม่มี manual reorder เช่นกัน) — ลำดับตาม SSOT ยังคาดเดาได้และสม่ำเสมอทุกจุดของระบบที่อ้างอิงเมนูเดียวกัน — ดู §9.2 Q4 สำหรับการยืนยัน

### 3.8 รีเซ็ตกลับค่าเริ่มต้น

**ความต้องการ:**
- ผู้ใช้กดรีเซ็ตเมนูลัดกลับเป็นค่าเริ่มต้น (§3.5) ได้ทุกเมื่อ

**Business Rules:**
- ปุ่มรีเซ็ตอยู่ในโหมดแก้ไข (§3.4) — กดแล้วแทนที่ preference ปัจจุบันด้วยค่าเริ่มต้นที่คำนวณสดตามสิทธิ์ล่าสุด
- มีการยืนยันก่อนรีเซ็ต (ป้องกันกดพลาดแล้วเสียการตั้งค่าที่ตั้งใจไว้)

**เหตุผล:**
- เป็นทางออกฉุกเฉินเมื่อผู้ใช้ตั้งค่าจนงงหรือไม่พอใจ ป้องกันไม่ให้ผู้ใช้ต้องเลือกใหม่ทีละอันจนครบ — ต้นทุนพัฒนาต่ำเทียบกับคุณค่าที่ป้องกัน dead-end UX

### 3.9 ขอบเขตมือถือ vs เดสก์ท็อป

**ความต้องการ:**
- ระบุชัดเจนว่าฟีเจอร์นี้ครอบคลุมพื้นผิว (surface) ไหนของแอป

**Business Rules:**
- MVP ครอบคลุมเฉพาะ **การ์ดเมนูลัดบน Command Center มือถือ** (`CarouselGrid`/`ShortcutGrid` ที่ render เฉพาะ `<lg`) — ตรงกับพื้นผิวที่ฟีเจอร์เมนูลัดมีอยู่จริงในปัจจุบัน
- เดสก์ท็อป (`≥lg`) **ไม่มี** widget เมนูลัดเทียบเท่าอยู่ก่อนแล้ว (ใช้ UserCard/StatisticCard/AchievementLevel/SalesReport/RecentOrder แทน) — การสร้าง widget เมนูลัดใหม่บนเดสก์ท็อปเป็น scope เพิ่มเติมที่ใหญ่กว่าคำขอเดิม ("ไปแก้เมนูลัด") จึงจัดเป็น Out of Scope ของรอบนี้ (ดู §5, §9.2 Q7)

**เหตุผล:**
- คำขอต้นทางของ user พูดถึง "เมนูลัด" ซึ่งมีอยู่แล้วเฉพาะบนมือถือเท่านั้น — ขยายไป desktop โดยไม่ถามก่อนจะเป็นการเดา scope เกินคำขอ

## 4. Business Rules & Constraints

### 4.1 กฎทางธุรกิจหลัก

| กฎ | คำอธิบาย |
|----|----------|
| **Scope ต่อคน × ต่อร้าน** | Preference คีย์ด้วย (userId, shopId) เสมอ — ไม่มี preference ระดับ user เดี่ยว ๆ หรือ shop เดี่ยว ๆ |
| **Catalog = SSOT sidebar เดียวกัน** | ไม่มีลิสต์เมนูลัดแยกต่างหากที่ดูแลคู่ขนานกับ `_seller-menu.ts` |
| **Cap 8 ช่องเสมอ** | เลือกได้ 1-8 รายการ ไม่มี carousel หลายหน้า |

## 5. Out of Scope (นอกขอบเขต)

| หัวข้อ | คำอธิบาย |
|--------|----------|
| **เมนูลัดบนเดสก์ท็อป** | ไม่มี widget เทียบเท่าอยู่ก่อนแล้ว — สร้างใหม่ = scope เกินคำขอเดิม (ดู §3.9, §9.2 Q7) — Phase 2 ถ้า user ต้องการ |
| **Manual Reorder (ลากจัดเรียง)** | ลำดับตาม SSOT sidebar order เสมอใน MVP (§3.7) — Phase 2 |
| **Custom label/icon ต่อ tile** | เลือกได้แค่เปิด/ปิดรายการจาก catalog — Phase 2 |
| **Custom/external link เป็นเมนูลัด** | จำกัดเฉพาะเมนูจริงในระบบ (`_seller-menu.ts`) เท่านั้น |
| **Owner ตั้งเมนูลัดแทนพนักงาน** | แต่ละคนตั้งของตัวเองเท่านั้น (ตรงกับ decision §3.1) |
| **เปลี่ยนชื่อเมนู "เครดิต SMS" → "กระเป๋าเงิน"** | ทำไปแล้วแยกต่างหาก (commit `fc186e8b`, 56 ไฟล์) ก่อนฟีเจอร์นี้เริ่ม — แคตตาล็อกจึงได้ชื่อใหม่มาเองจาก `_seller-menu.ts` ไม่ต้องทำอะไรเพิ่ม |
| **เปลี่ยนชื่อ "ChatBot" → "Deep Bot" ในเมนูลัด/sidebar** | ขัดกับ decision ที่ user เคาะไปแล้วเมื่อ 2026-08-01 ว่าเมนูใช้คำว่า "ChatBot" (แยกจาก "DeepBot" ที่เป็นชื่อ customer-facing ในแชท) — ดู §9.2 Q9 |
| **Analytics เจาะลึกว่า tile ไหนถูกกดบ่อยสุด** | ไม่มี tracking ระดับ per-tile click ใน MVP — Phase 2 |
| **Bulk import/export preference ข้ามร้าน** | ไม่มีการ copy ชุดเมนูลัดจากร้านหนึ่งไปอีกร้านหนึ่งใน MVP |

## 6. Risks & Mitigation

### 6.1 ความเสี่ยงทางธุรกิจ

| ความเสี่ยง | ผลกระทบ | ระดับความรุนแรง | แนวทางแก้ไข |
|-----------|---------|-----------------|-------------|
| **Default ไม่ตรงใจผู้ใช้ส่วนใหญ่** | Adoption ต่ำ เพราะไม่รู้สึกว่าต้องแก้ | ต่ำ | Default คำนวณจาก sidebar order จริงของแต่ละ vertical/role อยู่แล้ว (§3.5) — ลดโอกาสที่ default จะดูสุ่ม |
| **ผู้ใช้สับสนว่าทำไมเมนูที่เคยปักหายไป (entitlement drift)** | Support ticket / ความไม่พอใจ | กลาง | หน้าแก้ไขต้องโชว์สถานะ "ใช้ไม่ได้แล้ว" ให้เห็นชัด (§3.6) ไม่ใช่หายเงียบทั้งสองที่ |
| **พนักงานคาดหวังว่า owner ตั้งเมนูลัดให้ได้** | ความคาดหวังผิดจาก mental model ของ `staffCanViewFinance` toggle ที่มีอยู่แล้ว | ต่ำ | Copy ในหน้าแก้ไขต้องสื่อชัดว่าเป็นการตั้งค่าส่วนตัว (safepay-ux รับผิดชอบ) |

### 6.2 ความเสี่ยงทางเทคนิค

| ความเสี่ยง | ผลกระทบ | แนวทางแก้ไข |
|-----------|---------|-------------|
| **Catalog permission-drift ถ้าไม่ reuse ตัวกรองเดิม** | เมนูลัดเห็นสิ่งที่ sidebar ไม่เห็น (หรือกลับกัน) — security/consistency bug | บังคับ reuse `applyStaffMenu`/`applyVerticalMenu`/`applyAppointmentMenu`/`applyExpenseMenu`/`applyInventoryGate` ตัวเดิมเป๊ะ ไม่เขียนกฎสิทธิ์ใหม่ (§3.2, §6.2 ของ SRS ต้องพิสูจน์ด้วย test) |
| **Migration model ใหม่บน DB ที่แชร์กับ prod** | เสี่ยงกระทบข้อมูลจริง (dev/prod share Supabase — ดู memory `project_shared_db_drift_no_migrate_dev`) | Additive migration เท่านั้น (ตาราง/field ใหม่) — ไม่แตะ `ShopMember`/`Shop` เดิม, กำหนดใน DATABASE.md โดย `safepay-database` |
| **Race condition ตอนแก้ไข preference พร้อมกันหลาย tab/device** | ข้อมูลชนกัน | Last-write-wins ยอมรับได้ใน MVP (preference ส่วนตัว ความเสี่ยงต่ำ ไม่ต้อง optimistic lock) — ยืนยันที่ SRS |
| **Performance — query catalog + gate ทุกครั้งที่เปิด dashboard** | หน้าโหลดช้าลง | Reuse ตัวกรองเดิมที่ query เบาอยู่แล้ว (ข้อมูล shop/role ถูก fetch อยู่แล้วใน `requireActiveShop`) — ไม่เพิ่ม query หนักใหม่ |

## 7. Glossary

| คำศัพท์ | ความหมาย |
|---------|----------|
| **Shortcut / เมนูลัด** | Tile บนการ์ด Command Center มือถือที่ลิงก์ไปหน้าเมนูอื่นในระบบ |
| **Catalog (แคตตาล็อก)** | รายการเมนูทั้งหมดที่ผู้ใช้คนหนึ่งมีสิทธิ์เลือกมาปักหมุด ณ ขณะนั้น (สด, อิง SSOT sidebar) |
| **Preference (การตั้งค่า)** | ชุดรายการที่ผู้ใช้คนหนึ่งปักหมุดไว้สำหรับร้านหนึ่ง (key = userId + shopId) |
| **SSOT (`_seller-menu.ts`)** | แหล่งความจริงเดียวของเมนู sidebar — แคตตาล็อกเมนูลัดต้อง derive จากที่นี่ |
| **Entitlement Drift** | สถานการณ์ที่รายการที่เคยปักหมุดไว้หมดสิทธิ์เข้าถึงภายหลัง (เช่น แพ็กเกจหมดอายุ) |
| **Dead Tile** | Tile ที่กดแล้วพัง/ไม่มีปลายทางจริง หรือพาไปหน้าที่ผู้ใช้ไม่มีสิทธิ์เข้า |
| **Command Center** | ชื่อการ์ดรวม header+wallet+เมนูลัด+activity บน `/dashboard` เวอร์ชันมือถือ |

## 10. Appendix

### 10.1 User Journey — ผู้ใช้ใหม่เห็นเมนูลัด default ครั้งแรก

**Scenario: Owner ร้านบ้านพัก (LODGING) เปิด `/dashboard` ครั้งแรกหลังฟีเจอร์นี้ launch**

1. Owner login เข้า `/dashboard` บนมือถือ (ไม่เคยตั้งค่าเมนูลัดมาก่อน)
2. ระบบคำนวณแคตตาล็อกของ owner คนนี้ ณ ร้านนี้ — กรอง vertical=LODGING ออก ทำให้เห็นเฉพาะ "ห้องพัก/ปฏิทินการจอง/การจอง/แม่บ้าน" แทน "สินค้า/ประมูล/จัดการสต็อก"
3. ระบบสร้าง default = 8 รายการแรกตามลำดับ sidebar ของแคตตาล็อกนี้ (ไม่มี "สินค้า"/"ประมูล" ปนมาแน่นอน)
4. Owner เห็นเมนูลัดที่ตรงกับธุรกิจบ้านพักตั้งแต่ครั้งแรก โดยไม่ต้องตั้งค่าอะไรเอง
