# BRD: ซื้อ Business Package ผ่าน In-App Purchase (iOS)

---

## 1. กติกาธุรกิจ (Business Rules)

### 1.1 แหล่งที่มาของสิทธิ์

| # | กติกา |
|---|---|
| **BR-IAP-01** | subscription ทุกใบต้องรู้ว่ามาจากไหน — `WALLET` (จ่ายด้วยเครดิตในระบบ) หรือ `APPLE_IAP` (จ่ายผ่าน Apple) แถวที่มีอยู่ก่อนฟีเจอร์นี้ทั้งหมดคือ `WALLET` |
| **BR-IAP-02** | 🛑 **cron ต่ออายุแตะเฉพาะ `source='WALLET'`** — ใบที่เป็น `APPLE_IAP` ห้ามถูก `deductCredit` ไม่ว่ากรณีใด เพราะ Apple เก็บเงินไปแล้ว การหักซ้ำคือการเก็บเงินลูกค้าสองต่อ |
| **BR-IAP-03** | ใบที่เป็น `APPLE_IAP` ให้ **Apple เป็นเจ้าของวันหมดอายุ** — `nextRenewalAt` มาจาก `expiresDate` ที่ Apple แจ้ง ห้ามคำนวณ +30 วันเอง (รอบของ Apple ไม่ตรง 30 วันเสมอ และเปลี่ยนได้จาก billing retry / grace period) |
| **BR-IAP-04** | 1 `originalTransactionId` ผูกได้กับ **1 เจ้าของบัญชี** เท่านั้น — ถ้ามีคนพยายามใช้ซ้ำกับอีกบัญชี ต้องปฏิเสธและบอกเหตุผล ไม่ใช่เงียบ |
| **BR-IAP-05** | เจ้าของบัญชีหนึ่งคนมี subscription ได้ใบเดียว (คงกติกาเดิมของ 00008 `ownerId @unique`) ไม่ว่าจะมาจากทางไหน |

### 1.2 วงจรชีวิต

| # | กติกา |
|---|---|
| **BR-IAP-10** | ซื้อสำเร็จ = ได้รับ **ธุรกรรมที่ผ่านการตรวจลายเซ็นแล้ว** ไม่ใช่แค่ SDK ฝั่งเครื่องบอกว่าสำเร็จ |
| **BR-IAP-11** | ห้ามปิดธุรกรรม (`finishTransaction`) จนกว่า server จะบันทึกสิทธิ์เสร็จ — ถ้าปิดก่อนแล้ว server ล่ม ผู้ใช้จะจ่ายเงินแล้วไม่ได้ของ และไม่มีทางกู้ |
| **BR-IAP-12** | ยกเลิกกับ Apple → สิทธิ์ยังอยู่จนถึง `expiresDate` แล้วค่อยหมด (ไม่ใช่หมดทันที) — ผู้ใช้จ่ายค่ารอบนี้ไปแล้ว |
| **BR-IAP-13** | Apple แจ้งคืนเงิน (`REFUND`) → ถอนสิทธิ์ทันที และล็อกร้านตามกติกาเดิม |
| **BR-IAP-14** | Apple เก็บเงินไม่สำเร็จ (`DID_FAIL_TO_RENEW`) → เข้าสถานะเดียวกับ "ต่ออายุไม่สำเร็จ" ของเดิม (`LOCKED_RENEWAL_FAILED`) เมื่อพ้น grace period ที่ Apple ให้ |
| **BR-IAP-15** | นอกจาก webhook ต้องมีตัวเดินตรวจซ้ำ — webhook หายได้ (Apple ยิงแล้วเราล่ม/ตอบช้า) การพึ่ง webhook อย่างเดียวแปลว่าวันหนึ่งจะมีคนใช้ฟรีตลอดไปโดยไม่มีใครรู้ |

### 1.3 สิ่งที่แสดงบนจอ

| # | กติกา |
|---|---|
| **BR-IAP-20** | ราคาที่แสดงในแอปต้องมาจาก **StoreKit** เท่านั้น ห้ามเอาเลขจากฝั่งเราไปแสดง — ราคาจริงขึ้นกับประเทศ/สกุลเงิน/ภาษีของบัญชี Apple ผู้ใช้ ถ้าเราเดาเลขเองจะมีวันที่จอบอกเลขหนึ่งแต่ถูกตัดอีกเลขหนึ่ง |
| **BR-IAP-21** | คนที่มีสิทธิ์อยู่แล้ว (ไม่ว่าทางไหน) ต้อง **ไม่เห็นปุ่มซื้อ** |
| **BR-IAP-22** | ในแอป iOS ห้ามมีลิงก์/ข้อความชี้ไปช่องทางจ่ายเงินนอกแอป (คงกติกาเดิมของ 00040) |
| **BR-IAP-23** | บนเว็บต้องไม่มีอะไรของ IAP โผล่เลย — คนเปิดเว็บบน Safari ของ iPhone ก็ยังต้องซื้อด้วยกระเป๋าเงินได้ตามปกติ |
| **BR-IAP-24** | ฟีเจอร์ Deep Stock ต้องไม่ปรากฏในแอป iOS ทั้งปุ่มซื้อและตัวฟีเจอร์ (Guideline 3.1.3(b)) |

## 2. Acceptance Criteria

### 2.1 การซื้อ

| # | เงื่อนไข | ผลที่ต้องได้ |
|---|---|---|
| AC-IAP-01-1 | เปิดหน้าแพ็กเกจในแอป iOS โดยยังไม่มีสิทธิ์ | เห็น 3 tier พร้อมราคาที่ StoreKit คืนมา |
| AC-IAP-01-2 | กดซื้อ → ยืนยันกับ Apple สำเร็จ | สิทธิ์เปิดใช้ทันที · หน้าจอเปลี่ยนเป็น "ใช้งานอยู่" |
| AC-IAP-01-3 | กดซื้อแล้วยกเลิกกลางทาง | ไม่มีอะไรเปลี่ยน ไม่มี error ค้างบนจอ |
| AC-IAP-01-4 | ซื้อสำเร็จกับ Apple แต่ server ตอบไม่สำเร็จ | ธุรกรรมไม่ถูกปิด · เปิดแอปใหม่แล้วระบบพยายามยืนยันซ้ำเองจนสำเร็จ |
| AC-IAP-01-5 | มีสิทธิ์จากกระเป๋าเงินอยู่แล้ว | ไม่เห็นปุ่มซื้อ |

### 2.2 กัน cron เก็บเงินซ้ำ (ข้อสำคัญที่สุด)

| # | เงื่อนไข | ผลที่ต้องได้ |
|---|---|---|
| AC-IAP-03-1 | มี subscription `source='APPLE_IAP'` ที่ `nextRenewalAt` เลยกำหนด | cron **ไม่หยิบมาทำอะไรเลย** |
| AC-IAP-03-2 | รัน cron ในวันที่มีทั้งใบ WALLET และ APPLE_IAP ครบกำหนดพร้อมกัน | ใบ WALLET ถูกต่ออายุตามปกติ · ใบ APPLE_IAP ไม่มี `WalletTransaction` เกิดขึ้นแม้แต่แถวเดียว |
| AC-IAP-03-3 | ใบ APPLE_IAP ที่เงินในกระเป๋าเป็น 0 | ต้องไม่ถูก `LOCKED` — เพราะกระเป๋าเงินไม่เกี่ยวกับใบนี้ |

### 2.3 การต่ออายุ / ยกเลิก / คืนเงิน

| # | เงื่อนไข | ผลที่ต้องได้ |
|---|---|---|
| AC-IAP-04-1 | Apple แจ้ง `DID_RENEW` | `nextRenewalAt` = `expiresDate` ที่ Apple ส่งมา · สถานะยัง `ACTIVE` |
| AC-IAP-05-1 | ผู้ใช้ยกเลิกใน Settings | ยังใช้ได้จนถึงสิ้นรอบ · พ้นรอบแล้วล็อกร้านตามกติกา 00008 |
| AC-IAP-06-1 | Apple แจ้ง `REFUND` | ถอนสิทธิ์ · ล็อกร้าน · บันทึกเหตุผลไว้ตรวจสอบได้ |
| AC-IAP-07-1 | ลงแอปใหม่แล้วกด "กู้คืนการซื้อ" | สิทธิ์กลับมาโดยไม่ต้องจ่ายซ้ำ |
| AC-IAP-15-1 | webhook ของรอบใดรอบหนึ่งหายไป | ตัวเดินตรวจซ้ำต้องพบและแก้สถานะให้ตรงภายในรอบถัดไป |

### 2.4 ไม่กระทบของเดิม

| # | เงื่อนไข | ผลที่ต้องได้ |
|---|---|---|
| AC-IAP-09-1 | ใช้งานบนเว็บทั้งหมด | ไม่มีพฤติกรรมใดเปลี่ยนจากก่อนฟีเจอร์นี้ |
| AC-IAP-08-1 | ผู้ใช้เดิม (WALLET) ครบกำหนดต่ออายุ | ถูกหักกระเป๋าเงินและต่ออายุเหมือนเดิมทุกประการ |
| AC-IAP-10-1 | เปิดหน้าสินค้าในแอป iOS | ไม่เห็นทั้งฟิลด์สต็อกและข้อความชวนสมัคร Deep Stock |

## 3. ผลกระทบต่อผู้ใช้เดิม

> นับจากฐาน prod จริง 2026-09-01 (อ่านอย่างเดียว) — ฐานมีผู้ใช้ 71 คน ร้าน 23 ร้าน

| กลุ่ม | จำนวนจริง | ผลกระทบ |
|---|---|---|
| จ่าย Business Package ผ่านกระเป๋าเงิน | **1 ราย** (tier BUSINESS · ACTIVE) | **ไม่มี** — ทำงานเหมือนเดิมทุกอย่าง (มติ D-3) |
| จ่าย Deep Stock อยู่ | **0 ราย — ไม่เคยมีใครสมัครเลยสักคน** (`InventoryEntitlement` ว่างเปล่า) | **ไม่มีใครได้รับผลกระทบ** |
| ใช้เว็บอย่างเดียว | — | ไม่มี |

### 3.1 ผลของตัวเลขนี้ต่อการตัดสินใจ

🛑 **R-2 หมดฤทธิ์ไปเอง** — ความเสี่ยง "ลูกค้าที่จ่าย Deep Stock อยู่จะเสียฟีเจอร์ในแอป" ที่ PRD §6
เขียนไว้ **ไม่มีตัวตนจริง** เพราะไม่มีใครสมัคร Deep Stock เลยแม้แต่รายเดียวนับตั้งแต่เปิดฟีเจอร์
⇒ การซ่อน Deep Stock ในแอป iOS **ไม่มีต้นทุนกับลูกค้าปัจจุบันเลย** เป็นทางเลือกที่ถูกที่สุดจริง

🛑 **แต่ก็แปลว่าความเร่งด่วนของทั้งฟีเจอร์นี้คือ "ผ่านรีวิว" ไม่ใช่ "รายได้"** — ฐานลูกค้าที่จ่ายเงิน
มี 1 รายและซื้อผ่านเว็บ ⇒ อย่าลงทุนเกินความจำเป็นกับ edge case ของ IAP ให้เน้นความถูกต้อง
ของด่านกันเก็บเงินซ้ำ (BR-IAP-02) และความครบของ webhook ก่อน แล้วค่อยขยายทีหลัง

## 4. สิ่งที่ต้องมีก่อนเริ่มเขียนโค้ดฝั่งแอป

| # | ของ | ทำไมขาดไม่ได้ |
|---|---|---|
| 1 | Paid Apps Agreement + ข้อมูลภาษี/ธนาคารครบ | ถ้าไม่ครบ StoreKit จะไม่คืนสินค้าเลยสักตัว และจะดีบักไม่ออกว่าทำไม |
| 2 | 3 subscription products อยู่ใน **กลุ่มเดียวกัน** | คนละกลุ่ม = เปลี่ยน tier ไม่ได้ ต้องยกเลิกแล้วซื้อใหม่ |
| 3 | In-App Purchase Key (.p8) + Key ID + Issuer ID | ใช้เรียก App Store Server API สำหรับตัวเดินตรวจซ้ำ (BR-IAP-15) |
| 4 | URL webhook ทั้ง Production และ Sandbox | Sandbox ยิงคนละ URL — ตั้งแต่ตัวเดียวจะทดสอบไม่ได้ |

## 5. ช่องโหว่ที่มีอยู่ก่อน ซึ่งเจอระหว่างทำเฟสนี้

> ทั้งสองข้อ **ไม่ได้เกิดจากงานนี้** แต่เป็นของเดิมที่จะทำให้ Apple ตีกลับซ้ำถ้าไม่แก้ไปพร้อมกัน

| # | ช่องโหว่ | ทำไมถึงหลุดมาได้ |
|---|---|---|
| **L-1** | **แคตตาล็อกทางลัดโชว์ "แพ็กเกจ" ในแอป iOS** — `shortcut.service.ts` สร้างรายการจาก `resolveVisibleSellerMenu` ตัวเดียวกับ sidebar แต่ **ไม่เคยส่ง `hidePayments` เลย** ⇒ ผู้ใช้ปักหมุดทางลัดไปหน้าจ่ายเงินได้ ทั้งที่ sidebar ซ่อนไปแล้ว | ตัวกรองถูกวางไว้ที่ sidebar ที่เดียว จอที่ประกอบรายการเมนูด้วยวิธีอื่นจึงหลุดตามไปหมด — **คลาสเดียวกับบั๊ก `ShopQuickLinks.tsx` ที่เคยเจอและแก้ไปแล้วครั้งหนึ่ง** แต่ไม่มีด่านกันการเกิดซ้ำ |
| **L-2** | **หน้า `/inventory/movements/[productId]` ไม่มีด่านเปลือกแอปเลย** — กันด้วยการซ่อนเมนูอย่างเดียว | โปรเจกต์เขียนกติกาไว้เองว่า "ซ่อนเมนู = UX ไม่ใช่การควบคุมสิทธิ์ ต้องกันที่หน้าเองด้วย" แต่หน้านี้ตกสำรวจ |

### 5.1 ด่านที่วางไว้กันการเกิดซ้ำ

เทส `[blocker]` สแกน **ทั้ง `src/`** (ไม่ใช่รายชื่อไฟล์ที่รู้จัก) — ทุกจุดที่เรียก
`resolveVisibleSellerMenu(` ต้องส่งทั้ง `hidePayments` และ `hidePaidFeatures` เข้าไป
มิฉะนั้นแดง ⇒ ผู้เรียกรายถัดไปที่ยังไม่มีใครเขียน ก็จะถูกจับด้วย

🛑 ด่านนี้จับงานของตัวเองได้จริงระหว่างทาง — ตอนเพิ่ม `hidePaidFeatures` ผมลืมต่อสาย
`seller-menu-server.ts` (ตัวที่สร้าง sidebar จริง) เทสแดงทันที
