### Section breakdown (ตามข้อ 1-6 ที่ขอ)

#### 1. หัวร้าน (FR-BOP-01/02, D-1, D-8)

**โครง:** `<header>` พื้น `background.paper` เต็มความกว้าง เส้นล่างบาง ไม่ sticky (D-9). ข้างในจัดตามกรอบเนื้อหา: โลโก้ | บล็อกชื่อ+บรรทัดย่อ (`min-width:0; flex:1`) | ปุ่มแชท.

**D-8: ขนาดชื่อร้าน.** ชื่อร้านใช้ **Title 1.125rem / weight 700 (Strong)** บนมือถือ และ **h4 1.5rem / 700** ที่ ≥861. ม็อกอัพใช้ 17.5px ซึ่งไม่อยู่บน ramp. `DESIGN.md` ระบุชื่อร้านไว้ที่ Title และอยู่ใน Strong step ตรงตัว.
- `lineHeight` ต้องไม่ต่ำกว่า **1.4**. ม็อกอัพใช้ 1.3 แต่กล่องมี `overflow:hidden` + line-clamp. สระและวรรณยุกต์ไทยของ Anuphan จะถูกตัดที่ 1.3.
- ใช้ `-webkit-line-clamp: 2` บนจอ ≥360 และ **3 บรรทัดที่ <360** (เหตุผลดู fixture ด้านล่าง). ใส่ `title` หรือ `aria-label` เป็นชื่อเต็มเสมอ.
- เป็น `<h1>`. ชื่อร้านคือหัวเรื่องแรกของหน้า ตรงกับ `SmsAutoEnter` และ `GuestOrderView`. AC-BOP-01-6.

**โลโก้:** วงกลม 52px (มือถือ), 64px (≥861). ลำดับ `Shop.logo` -> รูปเจ้าของ -> อักษรตัวแรกของชื่อร้าน. ตัวอักษรย่อใช้ `bgcolor: primary.lightOpacity`, `color: primary.main`, น้ำหนัก 800 (มีเหตุผลเดิมในโค้ดว่าเป็น "ภาพ"). มุมขวาล่างวางตราระดับ 20px จาก **`resolveVerifyLevelImage(maxVerifyLevel)`** (SSOT ที่มีอยู่แล้ว, `alt` มีคำว่า "ระดับ N"). ระดับ 0 ไม่มีตรา. **ห้ามใช้ติ๊กถูกเขียวแบบเดิม** (F3).

**D-8: ถ้อยคำบรรทัดย่อ.** ตัดสินใช้ **"{คะแนน} ดาว · ออเดอร์สำเร็จ {N} ครั้ง"** ตามม็อกอัพ.
- ระบบใช้ "คะแนนรีวิว" เป็น *ชื่อ* ของตัวเลข และใช้ "ดาว" เป็น *หน่วย* (`badge-labels.ts`: "คะแนนรีวิวเฉลี่ยไม่ต่ำกว่า {n} ดาว").
- บรรทัดย่อมีที่แคบ จึงโชว์แค่ค่า + หน่วย. การ์ดข้อมูลร้านโชว์ *ชื่อ* "คะแนนรีวิว". คำสองคำนี้ไม่ขัดกัน (HR16).
- ใส่ `<span class="sr-only">คะแนนรีวิวเฉลี่ย </span>` นำหน้าสำหรับ screen reader.
- ตัวเลขใช้ `tabular-nums` และ `formatBaht`-คู่กับ `toLocaleString('th-TH')` ตามที่ `ShopStats` ทำ.

| `avg` และ `completed` มีทั้งคู่ | `4.7 ดาว · ออเดอร์สำเร็จ 38 ครั้ง` |

#### 2. กล่องสิ่งที่ต้องทำ (FR-BOP-04..09)

**ตัวเลือกกล่องเป็นฟังก์ชันบริสุทธิ์** `resolveOrderActionBox(input)` ใน `src/lib/order-action-box.ts` พร้อมเทส `[blocker]` และ mutation (BR-BOP-13, ui-boolean-needs-a-testable-home). ห้ามเทอร์นารีใน JSX. คืน `{ primary: Kind | null, followUps: Kind[] }`.

ลำดับความสำคัญ (ตาม FR-BOP-04 และเพิ่มข้อที่ BRD เว้นไว้):
```
status ∈ {CONFIRMED, CANCELLED, RETURNED}                   -> primary = null
isServiceShop && appointment != null                        -> APPOINTMENT   (+ followUps: TRANSFER* ถ้า needsTransfer)
needsTransfer && payoutSnapshot != null                     -> TRANSFER      (+ followUps: PICKUP_INFO ถ้า pickup, DIGITAL_LINK ถ้ามี)
needsTransfer && payoutSnapshot == null                     -> TRANSFER_NO_ACCOUNT
isPickupOrder                                               -> PICKUP
มีพัสดุ (tracking != null || status === 'SHIPPED')          -> SHIPMENT
อื่น ๆ                                                      -> STATUS        (+ followUps: DIGITAL_LINK ถ้ามี)
```
`needsTransfer = status==='PENDING' && needsPayoutAccount(paymentMethod) && !paymentConfirmedAt && amountDue > 0`
`amountDue = serviceMoney ? serviceMoney.outstanding : totalAmount`

**D-5 (เงินสดตอน PENDING):** ซ่อนช่องแนบสลิปให้ตรงกับ `needsPayoutAccount` (CASH ไม่ต้องโอน). `showSlipZone()` เดิมซ่อนแค่ COD ต้องถูกแทนที่ด้วยเงื่อนไขเดียวกับ `needsTransfer`. เทสต้องครอบ `paymentMethod = null` ด้วย. `needsPayoutAccount(null)` คืน true ตามโค้ดปัจจุบัน.

#### 3. สลิปคำสั่งซื้อ (FR-BOP-10)

**โครงสร้าง 2 ชั้น (แก้ F6):**
```
Box ชั้นนอก   filter: drop-shadow(0 2px 6px rgb(47 43 61 / 0.14))   <- ink-tinted, ตามขอบฉีก
  Card ชั้นใน  borderRadius: 12px 12px 0 0 ; mask: radial-gradient(circle at 8px 100%, transparent 6.5px, #000 7px) 0 0 / 16px 100% repeat-x
```
ใช้ `Card` ของธีมโดยไม่ใส่คลาสรัศมีทับ. `drop-shadow` และ `mask` เป็นค่าพิเศษที่ธีมไม่มี token. ต้องเขียนคอมเมนต์กำกับบรรทัด (ดู Impeccable compliance). **ขอบฉีกมีเฉพาะสลิปใบเดียวของหน้า.** การ์ดหลักฐานร้านใช้หัวเส้นประ + รายการแบบ ledger เหมือน `SmsAutoEnter` แต่ขอบล่างตรง เพื่อให้ขอบฉีกยังเป็นลายเซ็นของ "ใบนี้ = เอกสาร".

**หัวสลิป:**
```
คำสั่งซื้อ (h2, 15px/500, ORDER_VOCAB[noun])                         04 ต.ค. 2569 19:30 (13px)
DP256910A6E2C3B9 (18px/700 tabular, break-all)             [copy 44] [share 44] [พิลสถานะ*]
- - - - - - เส้นประ 1.5px divider - - - - - -
```
- ชื่อเอกสารมาจาก `resolveOrderVocab(isServiceShop ? 'SERVICE_QUEUE' : 'ONLINE_SALES').noun` เท่านั้น. ห้ามต่อสตริง ห้าม "ใบสั่งซื้อ" (BR-BOP-03). โค้ดเดิมพิมพ์ "รายละเอียดคำสั่งซื้อ" / "รายละเอียดคำสั่งบริการ" เองซึ่งไม่ตรง ORDER_VOCAB ("การเข้ารับบริการ") ต้องเปลี่ยน.
- เลขจาก `formatOrderNo()` เต็มเสมอ. toast และ `aria-label` ของปุ่มคัดลอก/แชร์ผันตาม noun เดียวกัน.
- ***พิลสถานะ** ขึ้นเมื่อ **ไม่มี hero เท่านั้น** (ใบที่ปิดแล้ว). ตอนมี hero หัวเรื่อง hero คือสถานะอยู่แล้ว การขึ้นซ้ำคือข้อมูลซ้ำ. ที่มา: `resolveOrderStatusBadge` / `resolveServiceOrderBadge`.
- ลิงก์ `ดูคำสั่งซื้อทั้งหมด` (`/orders`) แสดงเฉพาะ ≥861 ตามเดิม ปุ่มข้อความ 44px ชิดขวาแถวบน.
- โทนสีป้ายอ่านจาก `ORDER_STATUS_TONE_TO_MUI` ผ่าน `TrustPill` เหมือนเดิม.

**รายการ:**
- รูป 56px รัศมี 8px (ม็อกอัพ 10px ไม่อยู่บนบันได). ไม่มีรูปใช้ placeholder `tabler-package` เดิม. ใบที่ยกเลิกใช้ `grayscale(.4)` + opacity เดิม.
- ชื่อ 15px/500, คำอธิบายรายการ 13px ตัดที่ 2 บรรทัด (AC-BOP-10-2), `จำนวน x ราคา` 13px, ยอดต่อรายการ 15px/700 ชิดขวา.
- ตัวนับ `(N รายการ)` ต่อท้ายคำ "ยอดรวม" เมื่อ N ≥ 2 เท่านั้น. ตัวนับ "1 รายการ" คือสัญญาณที่ไม่บอกอะไร จึงตัดทิ้ง. ข้อมูลไม่หาย.
- รายการ 0 ชิ้น: แสดงหัวสลิปและแถวยอดรวม ไม่มีข้อความ "ไม่มีรายการ".

**แถวยอด ร้านขายของ:**
```
ยอดรวม (3 รายการ) ...............  [ร้านยืนยันรับเงินแล้ว]  ฿2,400
```
- ป้าย `ยอดที่ต้องชำระ` ใช้เมื่อ `status==='PENDING' && !money && !paymentConfirmedAt` เท่านั้น. **ต้องเติม `!paymentConfirmedAt`**. ตามโค้ดเดิมใบที่ร้านยืนยันรับเงินแล้วแต่ยัง PENDING จะขึ้น "ยอดที่ต้องชำระ" คู่กับพิล "ร้านยืนยันรับเงินแล้ว" ซึ่งขัดกันเอง. ย้ายตรรกะนี้ไปเป็นฟังก์ชันบริสุทธิ์พร้อมเทส.
- ตัวเลขยอดรวมเป็น **ink 18px/700** ไม่ใช่ม่วง (โค้ดเดิมทาม่วง). ม่วงสงวนไว้ให้การกระทำ.
- พิล "ร้านยืนยันรับเงินแล้ว" (AC-BOP-10-5) แสดงเมื่อ `paymentConfirmedAt != null` และไม่ใช่ CANCELLED. คำและโทน (info) มาจาก `getPaymentBadge()` ห้ามเขียนใหม่. ห้ามคำว่า "ชำระแล้ว".

**บรรทัดเงินร้านบริการ 3 บรรทัด (AC-BOP-10-6/7, `order.money != null`):**
```
ยอดรวม ......................................... ฿12,900
ร้านยืนยันรับแล้ว .............................. ฿2,000     <- เมื่อ totalReceived > 0
(หรือ) มัดจำที่ตกลงไว้ ......................... ฿2,000     <- เมื่อ hasDeposit และยังไม่รับ
ยังค้างชำระ ................................... ฿10,900    <- ป้าย 700 · เลข 18px/700
```
- เมื่อ `fullyPaid` บรรทัดที่ 3 เปลี่ยนเป็น `ชำระเงินแล้ว` (`PAYMENT_STATE_LABEL.paid`) พร้อมไอคอนติ๊ก และไม่มีตัวเลข ฿0.
- **ตั้งใจเบี่ยงจากม็อกอัพ 1 จุด:** ม็อกอัพเขียน "มัดจำ [พิล] ฿2,000". ผมใช้ป้ายที่ระบบมีอยู่แล้วใน `PaymentSummaryCard` คือ "ร้านยืนยันรับแล้ว" (เมื่อรับแล้ว) หรือ "มัดจำที่ตกลงไว้" (เมื่อยังไม่รับ). เหตุผล: ตัวเลขข้างพิลต้องเป็นยอดที่ร้านรับจริง ไม่ใช่ยอดที่ตกลงไว้ (ถ้าลูกค้าโอนมา 1,000 จากมัดจำ 2,000 พิลข้าง 2,000 จะโกหก). และ HR16: ข้อเท็จจริงเดียวกันใช้คำเดียวกันทุกการ์ด. ดู Q9.
- ตัวเลขทั้ง 3 มาจากชุด `money` ชุดเดียวกับการ์ดประวัติ.

**ตราประทับ (`ConfirmStamp`):**
- ตราอยู่ **ในสลิป** เหนือขอบฉีก ภายในโซนเว้นที่ความสูงขั้นต่ำ 96px ที่จองเฉพาะเมื่อมี `confirmation`. ตัวตราหมุน -8deg ชิดขวา **ไม่ใช้ `position:absolute` ทับเนื้อหา**. ต่างจากตอนนี้ที่เป็นแถบท้ายการ์ด. ฝั่งซ้ายของโซนเว้นว่างโดยตั้งใจ เหมือนกระดาษสลิปที่ยังไม่ได้ประทับ.
- คำตามคนปิด: ผู้ซื้อกดเอง = `ได้รับแล้ว` (ขายของ) หรือ `รับบริการแล้ว` (บริการ), ปิดโดยทางอื่น = `สำเร็จ`. วันที่จาก `formatDateTH`.
- ตรา 18px/700 วันที่ 12px. สีเขียว `VERIFIED_INK` ใช้ได้เพราะเป็นสถานะที่ยืนยันแล้วจริง.
- หลังกดยืนยัน: ตราขึ้นทันทีโดยไม่รีโหลด (AC-BOP-10-8). ให้ตัว container ของตรามี `role="status"` เพื่อประกาศ "{label} {วันที่}" ให้ screen reader.

#### 4. การ์ดข้อมูลร้าน (D-1) และการ์ดที่คงไว้ (D-6)

**การ์ดหลักฐานของร้าน** (`Card` เงา sm, padding 20, ขอบล่างตรง):
```
[ตรา Deep (ลิงก์ /, 44)]                        หลักฐานของร้าน
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
(ร้านใหม่) [ร้านใหม่ · ยังไม่มีประวัติเพียงพอ]              <- เฉพาะ completed == null
[icon] ยืนยันเบอร์แล้ว ........................ [ระดับ 1]   <- resolveVerifyBadge (ระดับ 0 ไม่มีแถว)
[icon] ออเดอร์สำเร็จ ......................... 38 ครั้ง
[icon] คะแนนรีวิว ............................ 4.7 · 3 รีวิว
[icon] ชั้นความน่าเชื่อถือ ................... [Deep Gold]   <- TrustPill tier
       ชื่อผู้ใช้ ............................ @btpremium
ช่องทางที่เชื่อมต่อ (ShopChannels variant 'rows')
(จากการคุยที่ {เพจ})                                         <- shouldShowOrderOrigin เดิม
ตัวเลขจากระบบ Deep ร้านแก้เองไม่ได้
[ ดูโปรไฟล์ร้าน  > ]   outlined 44 เต็มกว้าง
```
- โครง `<dl>` + เส้นจุดนำสายตา ยกจาก `SmsAutoEnter.tsx` ตรง ๆ (ป้ายซ้าย · เส้นจุด · ค่าขวา). ผู้ซื้อเห็นภาษาเดียวกันตั้งแต่จอเปลี่ยนผ่าน.
- แถวที่ไม่มีข้อมูลไม่แสดง (BR-BOP-14). ไม่มีเลข 0.
- คำสามคำต้องตรง SSOT: ป้ายยืนยันจาก `verify-badge.ts`, "ออเดอร์สำเร็จ" ตรงกับบรรทัดย่อบนหัว, ชื่อ tier จาก `getTierLabel` (`Tier Lists.md`).
- ป้ายแถว tier "ชั้นความน่าเชื่อถือ" เป็นคำที่ผมตั้งเอง `Tier Lists.md` ไม่ได้กำหนดป้ายแถว (ดู Q10).
- payload ช่องทางส่ง 5 คีย์เท่านั้น (AC-BOP-03-4) ตามเดิม.

**การ์ดความช่วยเหลือ** ("ต้องการความช่วยเหลือ?", `HelpActionRow` ตัวเดิม):
1. ติดต่อร้านค้า: `คุยกับร้านโดยตรงในแชทของ Deep`. มีเสมอทุกสถานะ (BR-BOE-16).
2. แจ้งปัญหาคำสั่งซื้อ: `ให้ Deep ตรวจสอบ — ร้านจะเห็นเรื่องนี้ด้วย`. ซ่อนเมื่อ CONFIRMED / CANCELLED. เมื่อมี dispute แล้วถูกแทนด้วยแถบ "แจ้งปัญหาแล้ว เมื่อ ..." (คงเดิม).
3. **ใหม่:** ศูนย์ช่วยเหลือของ Deep: `วิธีใช้งานและคำถามที่พบบ่อย · เปิดในแท็บใหม่` (ไอคอน `tabler-lifebuoy`, ลูกศรออกนอก).

**รางสถานะ (D-6):** การ์ดเดิม (`HorizontalTimeline`, 3 ขั้น / 4 ขั้นร้านบริการ) อยู่ใต้สลิป. ตัดกล่องกันพลาดออก (ย้ายไป hero แล้ว). ตัวหนังสือ "อัปเดตตามการดำเนินงานจริง" คงไว้. หมายเหตุ: ร้านขายของที่ hero เป็น SHIPMENT จะเห็นรางสถานะกับแถบพัสดุ 4 จุดบนจอเดียว สองแกนที่ใกล้กันมาก (Q7).

**ประวัติการรับเงิน (D-6, ร้านบริการที่มี `order.money`):** `PaymentSummaryCard` คงอยู่ แต่ต้องตัดตัวเลขที่ซ้ำกับสลิป. ดูเหตุผลที่ Design decisions D-D. เหลือ: `SectionTitle` "ประวัติการรับเงิน" แทน `overline` เดิม + วงแหวน + ประโยค "ร้านยืนยันรับแล้ว {p}% ของยอดรวม" + รายการ + แถวช่องทางจ่าย. ตัดข้อความ 9px ในวงแหวน (นอก ramp, ต่ำกว่า 11px). กรณีไม่มีรายการเลยยังขึ้นประโยค "ยอดนี้จะอัปเดตเมื่อร้านกดยืนยันว่าได้รับเงินแล้ว — แนบสลิปไว้ได้เลย ร้านจะเห็นทันที" (ข้อความระบบ ไม่ใช่คำสัญญา).

**โซนรีวิว:** การ์ดทั้ง 5 สถานะคงเดิม. ปรับ 2 จุด:
1. สถานะล็อก (ยังไม่ถึงเวลารีวิว) ลดเหลือ **แถวเดียวในการ์ด**: ไอคอน `tabler-star` สีรอง + `เขียนรีวิวได้หลังกด “{ctaLabel}”`. ตัดดาวเทา 5 ดวงที่ตกแต่งอย่างเดียว และตัดป้าย "ยังไม่เปิดให้รีวิว" ที่ซ้ำกับประโยค.
2. การ์ดเขียนรีวิว (หลังยืนยัน) ตัดบรรทัด `สินค้าถึงมือคุณแล้ว` / `รับบริการเรียบร้อยแล้ว` เพราะตราบนสลิปพูดไปแล้ว. เหลือ `ให้คะแนนร้านนี้เพื่อช่วยผู้ซื้อคนอื่น`.
- เมื่อ CONFIRMED และยังไม่รีวิว การ์ดเขียนรีวิวขึ้น **ถัดจากสลิปทันที** (ก่อนแถวอื่นทั้งหมด) เพราะเป็นงานถัดไปของผู้ซื้อ.

**การ์ด "ซื้อผ่าน Deep มั่นใจได้":** ย้ายเป็น aside / ท้ายหน้า. เปลี่ยนพื้นจาก `primary.lightOpacity` เป็นพื้น `background.paper` ปกติ และเปลี่ยนติ๊กจากเขียนเป็นสีรองของข้อความ. 3 บรรทัดเป็นกฎของระบบ ไม่ใช่ผลการยืนยัน (เหตุผลที่ Impeccable compliance ข้อ 2).

#### 5. แถบล่างจอ + ปุ่มยกเลิก (FR-BOP-11, D-2, D-9)

**แถบ:** `position: fixed` ล่างสุด พื้น `background.paper` เส้นบนบาง **ไม่ใส่ `backdrop-filter: blur`** (โค้ดเดิมใส่ แต่ไม่มีประโยชน์เมื่อพื้นทึบ). เว้น safe-area (`max(0px, env(safe-area-inset-bottom))`). เว้นที่ท้ายหน้าด้วยความสูงที่วัดจริง (`ResizeObserver` เดิม, AC-BOP-11-8). แสดงเมื่อ `status ∈ {PENDING, SHIPPED}` ทุกกรณี (D-2).

**มือถือ (ซ้าย → ขวา):**
```
[ ยกเลิก ]  [        ยืนยันรับสินค้า        ]     <- ปุ่ม 44px+, CTA 48px
        กดเมื่อได้ของครบแล้วเท่านั้น              <- 13px สีรอง กลางแถว
```
- **ยกเลิก:** `variant='text' color='secondary'`, ป้าย "ยกเลิก" (`aria-label` / tooltip "ยกเลิกคำสั่งซื้อ" ผันตาม noun). แสดงเมื่อ `status==='PENDING'` และมี `onCancel` (คงตามที่หัวหน้าเคาะ 2026-08-30). โค้ดเดิมเป็นปุ่มไอคอนถังขยะ 46px ซึ่งอ่านเป็น "ลบ" และอยู่ติดปุ่มหลัก. ผมเปลี่ยนเป็นปุ่มข้อความเบา ๆ มีคำ. กดแล้วยังมี dialog ยืนยันก่อนเสมอ (ดู Q14).
- **CTA:** `ctaLabel` เดิม (`ยืนยันรับสินค้า` / `ยืนยันว่าได้รับแล้ว` / `ยืนยันว่ารับบริการแล้ว`). คำกำกับ (AC-BOP-11-2/3): ขายของ `กดเมื่อได้ของครบแล้วเท่านั้น`, บริการ `กดเมื่อรับบริการเรียบร้อยแล้วเท่านั้น`, ดิจิทัล `กดเมื่อได้รับแล้วเท่านั้น` (คำใหม่ BRD ไม่ได้กำหนด ดู Q ท้ายเอกสาร).
- ระหว่างยืนยัน: `กำลังยืนยัน...` และปุ่ม disabled. กดแล้วเปิด dialog ถามซ้ำเสมอ ไม่ยิง API ตรง.

**น้ำหนักของ CTA (ข้อเสนอใหม่ ต้องผ่าน Q2):** ปุ่มนี้ย้อนกลับไม่ได้ ซ่อนปุ่ม "แจ้งปัญหา" และป้อน Trust Score. ตอน PENDING ที่ยังไม่โอน ปุ่มม่วงทึบ "ยืนยันรับสินค้า" จะเด่นเท่าหรือกว่า "แนบสลิป" ซึ่งคือสิ่งที่ผู้ซื้อต้องทำจริง. ขยาย `isFinalStepReady` (ร้านบริการใช้อยู่แล้ว) ให้ครอบทุก vertical เป็นฟังก์ชันบริสุทธิ์ `isConfirmReady(...)`:
- `contained` เมื่อ SHIPPED + ขนส่งแจ้งส่งถึง, หรือ PICKUP + `handedOverAt`, หรือดิจิทัลที่มี `accessUrl`, หรือร้านบริการถึงเวลาตามราง.
- `tonal` (ลดน้ำหนัก ไม่ disabled) ในกรณีอื่นทั้งหมด **และเมื่อมี dispute เปิดอยู่**.
- ห้าม `disabled` ด้วยเงื่อนไขนี้ (BR-RSV-18 และเทส `[blocker]` ที่มีอยู่ใน `public-order-timeline-a11y.test.ts`).
- ตัวอักษรของปุ่ม tonal ใช้ `primary.dark` (hue เดิม เข้มขึ้น). tonal ของธีมให้ตัวอักษร `primary.main` บนพื้นจาง คอนทราสต์ราว 3.7:1 ตก AA ที่ 15px. Controller ต้องวัดจริงตอน critique.

**เดสก์ท็อป ≥861:** แถบกว้างเท่า `orderDetailWidthSx`. ซ้ายสุดแสดง `{totalLabel}` (12-13px สีรอง) + ยอด 20px/700 ink. ขวาสุด `ยกเลิกคำสั่งซื้อ` (ข้อความเต็ม, `text`) + CTA `max-width 420`. มือถือซ่อนยอด (ตามม็อกอัพ).

### User flow

1. เปิดจาก SMS: `SmsAutoEnter` (เห็นสลิปหลักฐานร้าน) -> เข้าสู่ระบบอัตโนมัติ -> หน้านี้. header + hero ขึ้นในจอแรก.
2. **ร้านขายของ รอโอน:** คัดลอกเลขบัญชี (หรือสแกน QR ใต้ปุ่ม) -> ไปแอปธนาคาร -> กลับมากด `แนบสลิป` -> เลือกไฟล์ -> hero เปลี่ยนเป็น `แนบสลิปแล้ว` + ปุ่ม `เปลี่ยนสลิป`. สลิปบนหน้ายังไม่มีพิล "ร้านยืนยันรับเงินแล้ว" จนกว่าร้านจะกด.
3. **ร้านส่งของ:** hero เปลี่ยนเป็น `กำลังจัดส่ง` + เลขพัสดุ + 4 จุด. ได้ของ -> ปุ่มล่างจอเปลี่ยนจาก tonal เป็นทึบ -> กด -> dialog ถามซ้ำ -> `ได้รับแล้ว` -> hero และแถบล่างหาย ตราประทับขึ้นบนสลิป `ReviewSheet` เลื่อนขึ้น.
4. **ร้านบริการ:** hero คือวันนัด -> `ยืนยันนัดหมาย` (ย้อนได้) -> วันนัดผ่านไปและรับบริการแล้ว -> ปุ่มล่างจอเป็นทึบ -> `ยืนยันว่ารับบริการแล้ว` -> dialog -> ตรา "รับบริการแล้ว".
5. **มีปัญหา:** การ์ดช่วยเหลือ -> `แจ้งปัญหาคำสั่งซื้อ` -> dialog (ข้อความไม่บังคับ ≤500) -> แถบ "แจ้งปัญหาแล้ว" ขึ้นใน hero และแถวแจ้งปัญหาในการ์ดช่วยเหลือเปลี่ยนเป็นแถบสถานะ; ปุ่มล่างจอลดน้ำหนักเป็น tonal.
6. **ยกเลิก (PENDING):** ปุ่ม `ยกเลิก` ในแถบล่าง -> dialog `ยืนยันการยกเลิก?` -> สถานะ CANCELLED ทันที (hero, แถบล่างหาย; ขึ้นแถวเหตุผล).

### a11y, dark mode, ฟอนต์

- **Heading:** `h1` ชื่อร้าน -> `h2` ของ hero -> `h2` ของสลิป (noun) -> `h2` การ์ดหลักฐาน / ช่วยเหลือ / รีวิว. เลขคำสั่งซื้อเป็นข้อความธรรมดา (ปัจจุบันเป็น `h1`). เทสสแกนซอร์สใน BRD §7.2 (`buyer-order-guardrails`, `buyer-order-typography`, `public-order-timeline-a11y`, `error-copy-consistency`, `sms-link-one-time`) ผูกกับไฟล์เดิม ถ้าย้ายโค้ดต้องย้ายเทสและพิสูจน์ด้วย mutation.
- **tap target ≥44:** ปุ่มแชท 52x48 (<360: 44x44), คัดลอก/แชร์ 44, ปุ่มข้อความ 44, `ยกเลิก` 44, CTA 48, ลิงก์ footer 44 (มีอยู่แล้ว), แถวช่วยเหลือ 56.
- **focus:** วงโฟกัส 2px ม่วงของธีมทุกตัวที่กดได้. ตัวหนังสือรอบคัดลอกเลขพัสดุเป็น `ButtonBase` ที่มี label "คัดลอกเลขพัสดุ {เลข}" อยู่แล้ว.
- **aria-label** ต้องอยู่บน element ที่ role รองรับชื่อเท่านั้น (ปุ่ม/ลิงก์/`role=group|list`). บรรทัดย่อใช้ข้อความ sr-only ไม่ใช่ `aria-label` บน `<div>`. ตรา `role="status"`. ราง `role="list"` + ข้อความสถานะต่อขั้น (เดิม).
- **สีไม่เป็นตัวสื่อเพียงอย่างเดียว:** ทุกสถานะมีข้อความ + ไอคอนรูปร่างต่างกัน.
- **motion:** วงกระเพื่อมที่ขั้นปัจจุบันของรางหยุดเมื่อ `prefers-reduced-motion` (เดิมมีแล้ว). ไม่เพิ่ม animation ใหม่นอกจากที่ถาม user ในข้อ S1.
- **Dark mode:** ต้องตรวจจริงถ้าฝั่ง buyer สลับ dark ได้ (ไม่ทราบ). จุดเสี่ยง: `VERIFY_BADGE_PALETTE` เป็น hex/rgba ตายตัว (`#18804A` บนพื้นมืดน่าจะราว 3:1) กับตราประทับและพิล; เงา `drop-shadow` หมึกพลัมบนพื้นมืดแทบมองไม่เห็น (ยอมรับได้ เพราะ Flat-At-Rest); พื้นสลิปและเส้นประใช้ token `background.paper` / `divider` จึงตามธีม. AC-BOP-14-6 ต้องวัดคอนทราสต์จริง.
- **ฟอนต์:** Anuphan เท่านั้น. ตัวเลขเรียงใช้ `tabular-nums` ไม่ใช้ monospace. ไม่มี emoji ทั้งสเปก (ไอคอนจาก tabler).

### Impeccable compliance

**Mode: Operate** (ภายใต้ register `brand` ตาม PRODUCT.md สำหรับ `/o/[token]`). เหตุผล: งานของหน้านี้คือทำให้เสร็จสามอย่าง (โอน/แนบสลิป, เช็กสถานะ, กดยืนยันรับที่ย้อนไม่ได้) โดยคนที่ระแวงและอาจอายุ 50+. เกณฑ์ตัดสินจึงเป็น scanability, consistency ระหว่างสองจอ (guest / ล็อกอิน) และความคุ้นมือ (สลิปโอนเงินที่คนไทยรู้จัก). ลายเซ็นแบบแบรนด์ (ขอบฉีก, ตรา) ถูกจำกัดอยู่ที่สลิปใบเดียว เพื่อให้เป็นรายละเอียดที่แม่น ไม่ใช่การตกแต่งที่ขวางงานหลัก.

**จุดใช้ accent สีธีม (ม่วง `#7367F0`) ทั้งหมด:**
1. ปุ่มทึบใน hero **1 ปุ่มต่อจอ** (`แนบสลิป` / `ยืนยันนัดหมาย` / `ติดต่อร้านค้า` / `แชทกับร้านเพื่อนัดรับ`).
2. ปุ่มแชทใน header (tonal).
3. ปุ่ม CTA ล่างจอ: ทึบเฉพาะเมื่อถึงเวลาควรกดจริง นอกนั้น tonal.
4. ปุ่ม `ดูโปรไฟล์ร้าน` (outlined), ลิงก์ในข้อความ, วงโฟกัส.

ไม่ใช้ม่วงกับ: ยอดรวมในสลิป (เดิมทาม่วง -> ink), พื้นการ์ด "ซื้อผ่าน Deep" (เดิม `primary.lightOpacity` -> เรียบ), ไล่สีพื้นหลังหน้า (F4). **พระเอกของหน้า:** หัวเรื่อง hero 24px/700 และปุ่มทึบม่วงใบเดียวใต้มัน. ที่เหลือถอยลงทั้งหมด.

**จุดที่ theme หรือม็อกอัพขัดกับ Impeccable และการตัดสิน:**
1. **Verified-Means-Green (จุดที่พลาดบ่อยสุด).** ผมตรวจทุกจุดสีเขียวของหน้า:
   - ถูก (คงเขียว): ตราประทับ (ผู้ซื้อกดเอง/ระบบปิดแล้ว), ขั้น `fin` ของราง (ต่อเมื่อ CONFIRMED), "ส่งสำเร็จ" ของ `ParcelTimeline` (ขนส่งยืนยัน), `ชำระเงินแล้ว` (ร้านบริการรับครบ, SSOT ให้ success), ป้ายยืนยัน L2 (SSOT).
   - **ผิดในโค้ดเดิม แก้แล้วในสเปก:** "แนบสลิปแล้ว" สีเขียว -> สีกลาง (การแนบไม่ใช่การยืนยันของใคร); ตราติ๊กเขียวบนโลโก้ร้านทุกระดับ -> `resolveVerifyLevelImage`; ติ๊ก 3 บรรทัดในการ์ด "ซื้อผ่าน Deep" -> สีรอง (เป็นกฎของระบบ ไม่ใช่ผลการยืนยัน).
   - **ม็อกอัพขัดกับ SSOT:** พิล "ร้านยืนยันรับเงินแล้ว" ม็อกอัพวาดเขียว แต่ `getPaymentBadge` ให้ info และเหตุผลเดียวกับ BR-BOP-12 (คำบอกเล่าฝั่งร้านฝ่ายเดียว). **ตัดสินตาม SSOT (info)**. ถ้า user ต้องการเขียวตามภาพที่อนุมัติ ต้องแก้ SSOT ก่อน ไม่ใช่แก้ที่หน้าจอ (Q1).
2. **Sentence case / ไม่มี ALL CAPS / ไม่มี eyebrow:** ไม่มีป้ายเล็กเหนือหัวเรื่อง. `overline` ใน `PaymentSummaryCard` เปลี่ยนเป็น `SectionTitle`. ป้ายใน hero เป็นหัวเรื่องจริง ไม่ใช่ kicker.
3. **เงา:** ink-tinted ทั้งหมด. `drop-shadow` ของสลิปใช้ `rgb(47 43 61 / .14)` ไม่ใช่ `#000`. ไม่ใช้ `box-shadow` ผสมกับ `mask` (F6).
4. **รัศมี:** การ์ด 12 / รูป 8 / ปุ่ม 6 / ชิป pill ตาม DESIGN.md ไม่ใช้ 10px ของม็อกอัพ. ไม่ใส่คลาสรัศมีทับ `<Card>`.
5. **ค่าพิเศษที่ธีมไม่มี (ให้ Controller ตัดสิน):** (ก) `mask` + `filter: drop-shadow` ของสลิป, (ข) สี `primary.dark` ทับตัวอักษรของปุ่ม tonal เพื่อคอนทราสต์. ทั้งสองต้องมีคอมเมนต์กำกับบรรทัด.
6. **น้ำเสียงข้อความ:** ปุ่มบอกผลลัพธ์ ("แนบสลิป", "ยืนยันนัดหมาย"). error มีทางออก (ข้อความจาก `uploadFileId`, "กดค้างที่เลข ... เพื่อคัดลอกเอง"). **ไม่มีประโยคสัญญาแทนร้าน** ("ร้านยังไม่ได้ยืนยันรับเงิน" แทน "ร้านจะตรวจสลิป"). ไม่ใช้ "ไม่สามารถ...ได้" ในข้อความใหม่. ไม่ไฮป์.
7. **Anti-slop (`narrative.donts`):** ไม่มี gradient ตกแต่ง (ตัดไล่สีพื้นหลังเดิม), ไม่มี hero-metric template (บรรทัดย่อเป็นประโยค ไม่ใช่การ์ดตัวเลข), ไม่มีการ์ดซ้อนการ์ด (กล่องบัญชีในรัศมี 12 อยู่ใน hero ใช้ `infoBoxSx` พื้นต่างระดับ ไม่ใช่ `Card` ซ้อน), ไม่มี border-left สี.
8. **ที่เสี่ยงโดน critique ตีกลับ:** ปุ่ม tonal ถ้า `primary.dark` ยังต่ำกว่า 4.5:1; ลำดับ ซ้ำของรางสถานะกับแถบพัสดุ (Q7); ขอบฉีกที่ยังไม่ได้ดูบนจอจริง; สองจุดที่ผมเบี่ยงจากม็อกอัพ (บรรทัดเงินร้านบริการ, ปุ่มยกเลิกเป็นข้อความ).

**ความขัดกันระหว่างกฎ (ลำดับ HR 1/5/7 > Impeccable > frontend-design):** ขอบฉีกขัด HR1 (ไม่มีใน Vuexy) แต่เป็นส่วนของ "asset ตาม ref" ที่ user อนุมัติและมีโค้ดใช้อยู่แล้ว (HR6) จึงเลือกคงไว้และให้ Controller ยืนยัน. ม็อกอัพขัดกับ Impeccable เรื่องไล่สีและเขียว: เลือก Impeccable.

### Design decisions + rationale

- **D-A: เดสก์ท็อปใส่ hero + สลิปในคอลัมน์หลัก, หลักฐานร้านอยู่ aside.** โค้ดเดิมวางเงิน/หลักฐาน/รีวิวไว้ aside ซึ่งทำให้งานหลักไปอยู่คอลัมน์รอง (ขัด AC-BOP-14-2). คอลัมน์ aside ใหม่มีแต่ของอ้างอิง (หลักฐาน, ช่วยเหลือ, ความมั่นใจ) ความสูงราว 780px เทียบคอลัมน์หลัก ~940px จึงไม่มีคอลัมน์ว่างเปล่าเมื่อจอ 1440 (ว่างท้ายราว 17%). ไม่ทำ sticky เพราะ aside ที่สูงกว่าจอจะมีส่วนล่างเข้าไม่ถึง.
- **D-B: ชื่อร้านใหญ่ขึ้นด้วย Strong ไม่ใช่ขนาดนอก ramp.** user สั่งให้ชื่อเด่น. `DESIGN.md` มีขั้นนี้ (ชื่อร้านอยู่ใน Strong ตรงตัว). ความเด่นมาจากน้ำหนัก + ตำแหน่งบนสุด + โลโก้ 52px ไม่ใช่การขยับฟอนต์.
- **D-C: ปุ่มล่างจอหนักเบาตามความพร้อม ไม่ใช่ปิดปุ่ม.** เหตุผลเดียวกับที่ร้านบริการทำอยู่แล้ว (ลืมกดปิดผลนัดต้องไม่ทำให้ปิดงานไม่ได้). ลดความเสี่ยงที่ผู้ซื้อกดยืนยันก่อนได้ของเพราะปุ่มม่วงเต็มจอ.
- **D-D: ตัดตัวเลขซ้ำใน `PaymentSummaryCard`.** สลิปมีสามบรรทัดอยู่แล้ว (ยอดรวม / รับแล้ว / ค้าง). การ์ดเดิมมี 4 แถวเดียวกัน ซึ่งเป็นรูปแบบที่ BRD §8.2 เองเตือนว่า "ตัวเลขทั้งสองต้องมาจากชุดเดียวกัน" ทางที่ปลอดภัยที่สุดคือไม่ให้ตัวเลขอยู่สองที่. เหลือสิ่งที่ไม่ซ้ำ: ประวัติรายครั้ง + สัดส่วน + ช่องทางจ่าย.
- **D-E: การ์ดหลักฐานเป็นภาษาเดียวกับ `SmsAutoEnter`.** ผู้ซื้อเพิ่งเห็นสลิปหลักฐานนั้นก่อนเข้าหน้านี้ ต่อเนื่องกว่าการ์ดตัวเลขแบบใหม่. ขอบล่างตรง เพื่อให้ขอบฉีกเป็นของสลิปคำสั่งซื้อใบเดียว.
- **D-F: ตราแบรนด์อยู่หัวการ์ดหลักฐาน.** ตราที่รับรองควรอยู่บนสิ่งที่มันรับรอง และไม่แย่งที่จาก header.
- **D-G: ปุ่มแชทมีคำ.** PRODUCT.md ผูกกลุ่มผู้สูงวัย/ความคล่องต่ำไว้ ไอคอนล้วนเสี่ยงมากกว่าที่ประหยัดได้ 8-12px.

### Anti-slop self-check

1. **ใช้กับสินค้าอื่นได้ทันทีไหม?** ไม่. สิ่งที่เฉพาะกับ Deep: สลิปที่ประทับตราตาม *คนที่ปิดใบจริง* (ผู้ซื้อกดเอง / ระบบปิดเอง); คำว่า "ร้านยืนยันรับเงินแล้ว" ที่แยก "แนบสลิป" ออกจาก "ได้รับเงิน"; หลักฐานร้านที่ร้านเขียนเองไม่ได้ ("ตัวเลขจากระบบ Deep ร้านแก้เองไม่ได้"); กล่องกันพลาด "ยืนยันนัด vs ปิดงาน".
2. **เด่นที่สุด 1 อย่างต่อจอ?** ใช่. หัวเรื่อง hero 24px/700 และปุ่มทึบม่วงใบเดียวใต้มัน. การ์ดอื่นลดเงาเป็น sm และหัวข้อ 15px. ตัวเลขยอดรวมในสลิปเปลี่ยนจากม่วงเป็น ink.
3. **การ์ด/element ซ้ำหรือคงที่ที่ตัดทิ้ง?** ตัดแล้ว: ดาวเทา 5 ดวงและป้าย "ยังไม่เปิดให้รีวิว" (ซ้ำประโยค); บรรทัด "สินค้าถึงมือคุณแล้ว" (ซ้ำตรา); ตัวเลขซ้ำ 4 แถวใน `PaymentSummaryCard` (ซ้ำสลิป); พิลสถานะในหัวสลิปตอนมี hero (ซ้ำหัวเรื่อง); ตัวนับ "1 รายการ"; ข้อความ 9px ในวงแหวน; ติ๊กเขียวบนโลโก้ (ซ้ำป้ายระดับและผิดกฎสี); `backdrop-filter` บนพื้นทึบ; ไล่สีพื้นหลัง. ที่ยังซ้ำโดยมติ: ปุ่มแชทกับแถว "ติดต่อร้านค้า", ลิงก์ช่วยเหลือกับ footer, รางสถานะกับแถบพัสดุ (Q7).
4. **ทุก state ครบไหม?** ครบตามตาราง Edge states และตาราง variant. empty (0 รายการ, ไม่มีบัญชี, ไม่มี QR, ไม่มีโลโก้, ร้านใหม่), error (อัปโหลด, clipboard, share, 409), ข้อความยาว (ชื่อร้าน 38 ตัว ที่ 320/360/390), ตัวเลข 0 และล้าน. loading ไม่มี skeleton เพราะ RSC. **ที่ยังพิสูจน์ไม่ได้:** ตัวเลขความกว้างชื่อร้านที่ 320/360 เป็นการประมาณ ไม่ได้วัดจริง.
5. **copy บอกสิ่งที่ระบบทำได้จริงไหม?** ใช่. ปุ่มบอกผลลัพธ์; "ร้านยังไม่ได้ยืนยันรับเงิน" เป็นข้อเท็จจริงที่ระบบรู้ ไม่ใช่คำสัญญา; "ถ้ามีเลขพัสดุ สถานะการจัดส่งจะขึ้นที่นี่" บอกพฤติกรรมของหน้านี้แบบมีเงื่อนไข; คำเตือนใน hero การ์ดนัดโผล่เฉพาะตอนที่ปุ่ม "ยืนยันนัดหมาย" ยังมีอยู่จริง. **จุดเสี่ยง:** บรรทัดสุดท้ายของ STATUS และ "ตรวจของให้ครบแล้วกด ..." ต้องตรวจว่าปุ่มนั้นมีจริงในสถานะนั้น (มีทั้งคู่ตาม D-2).
6. **คำเดียวกันหมายถึงของเดียวกันไหม?** ตรวจแล้ว: "คะแนนรีวิว" = ชื่อ / "ดาว" = หน่วย (ทั้งบรรทัดย่อและการ์ดหลักฐาน); "ออเดอร์สำเร็จ" ตรงทุกที่; "ร้านยืนยันรับเงินแล้ว/รับแล้ว" ใช้กับสิ่งที่ร้านบันทึกเท่านั้น; noun ผ่าน `ORDER_VOCAB` (เดิมหัวสลิปพิมพ์ "รายละเอียดคำสั่งซื้อ/คำสั่งบริการ" เอง ซึ่งไม่ตรง). ยังไม่แน่: ป้ายแถว tier (Q10).
7. **สีสื่อความหมายถูกไหม?** ตรวจทุกจุดเขียวแล้ว (Impeccable compliance ข้อ 1). แดงใช้กับ CANCELLED, พัสดุมีปัญหา และ dialog ยกเลิกเท่านั้น. ค้างชำระ/แนบสลิปแล้ว/มอบสินค้า = warning หรือกลาง ไม่ใช่เขียว ไม่ใช่แดง. สถานะเดียวกันคือสีเดียวกันเพราะอ่านจาก `ORDER_STATUS_TONE_TO_MUI` ตัวเดียว.
8. **แตะได้จริงบนมือถือไหม?** ปุ่มทุกตัว ≥44px (ตารางใน a11y). ปุ่มหลัก (CTA ล่างจอ) อยู่ในโซนนิ้วโป้ง; "แนบสลิป" อยู่ในจอแรกที่ 360x740 (ราว 420px จากบน เหนือแถบล่าง ~130px). ปุ่ม `ยกเลิก` อยู่ติด CTA ห่าง 12px: มี dialog กันกดพลาด และเป็นปุ่มข้อความเบาเพื่อไม่แข่งกับ CTA.
9. **จอ 1440 คอลัมน์ไหนว่าง?** aside สั้นกว่า main ราว 17% (ว่างท้ายเล็กน้อย) และมีแต่ของที่ผู้ซื้อต้องการเมื่อต้องการ ไม่ใช่ที่ว่างที่ผู้ใช้เลื่อนผ่าน. งานหลัก (hero + สลิป) อยู่คอลัมน์หลัก. ฝั่ง 30% ไม่ได้เก็บเนื้อหาที่ผู้ใช้ต้องใช้ทุกครั้ง.
