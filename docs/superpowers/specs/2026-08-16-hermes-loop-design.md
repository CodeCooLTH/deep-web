## 4. สถาปัตยกรรม

### 4.1 ทำไมเป็น Node script (D-14)

**ตัดทิ้ง — ให้ `claude` เป็น Controller เอง:** เอาโมเดลไปวางในเส้นทางตัดสิน ขัดเจตนา D-4
(*"ด่านรันบน Actions เชลล์ล้วน ไม่มีโมเดลในเส้นทางตัดสิน"*) และไม่มีอะไรกันมันย้ายป้ายไป `พร้อมขึ้น`
นอกจากคำสั่งใน prompt — เป็นการกันชนิดเดียวกับที่ `unlinked.ts` เคยพึ่งแล้วผิดไป 23 ออเดอร์

**ตัดทิ้ง — shell script:** ต้อง `grep`/`sed` หาป้ายเอง = **นิยามที่ 2 ของ "ใบนี้อยู่ขั้นไหน"** (HR16)
และ **ไม่มีด่านไหนในโปรเจกต์นี้เทสเชลล์ได้เลย** (`theme-guard.sh` ยังไม่มีเทสของตัวเองมาถึงวันนี้)

**เลือก Node เพราะ** import `stageFromLabels()` จาก `src/lib/command-center.ts` **ตัวเดียวกับที่จอใช้**
⇒ จอกับลูปไม่มีวันตอบคนละอย่าง · และไฟล์ `.ts` ใต้ `src/` **ถูกด่าน 2 (`vitest src/`) เทสให้ทุก PR**

### 4.2 ไฟล์

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/hermes-loop.ts` | **ตรรกะบริสุทธิ์** — `pickNextItem` · `agentForStage` · `parseHandoff` · `isAllowedNextLabel` · `isInsideWindow` |
| `scripts/hermes-loop.ts` | **เปลือก I/O** — ยิง `gh` · spawn `claude` · เขียน log · บางที่สุดเท่าที่ทำได้ |

ของที่เทสไม่ได้ต้องมีให้น้อยที่สุด — ตรรกะทั้งหมดอยู่ฝั่งซ้าย

### 4.3 ตั้งเวลา

```cron
*/5 * * * * cd /home/coder/deep-web && flock -n /tmp/hermes-loop.lock \
  npx tsx scripts/hermes-loop.ts >> /home/coder/hermes-loop.log 2>&1
```

🛑 **cron รันทุก 5 นาทีตลอด 24 ชม. แล้วสคริปต์เช็คหน้าต่างเวลาเอง** ด้วย `TZ=Asia/Bangkok`
ไม่ใช้ `CRON_TZ=` — ยกท่าที่พิสูจน์แล้วในรีโปนี้มาใช้ซ้ำ (`auto-merge.yml` ด่าน 0 ก็เช็คชั่วโมงในสคริปต์
ไม่เชื่อ trigger) ทนต่อการที่ใครไปแก้ TZ ของเครื่องทีหลัง — ซึ่ง **TZ ตอนนี้เป็น UTC** ถ้าเขียน
cron `8-21` ตรง ๆ ลูปจะทำงาน 15:00–04:55 เวลาไทย คือกลางดึกพอดี

**`flock -n`** = รอบก่อนยังไม่จบ → รอบใหม่ออกทันทีเงียบ ๆ ไม่ต่อคิว
จำเป็นเพราะขั้น `build` ต้องรัน `next build` (บน CI 2.5 นาที เครื่องนี้น่าจะนานกว่า)

## 5. Data flow

### 5.1 เลือกใบงาน

```
GET /issues?state=open&per_page=100
  → stageFromLabels()                 ← symbol เดียวกับจอ (src/lib/command-center.ts)
  → เก็บเฉพาะ 6 ขั้นที่มี agent        ← ตัด ready / พร้อมขึ้น
  → ตัดใบที่มีป้าย `รอคำตอบ`           ← มันรอ user ไม่ได้รอ agent
  → เรียง stageEnteredAt เก่า → ใหม่
  → เอาใบแรก 1 ใบ
```

**เรียง "ค้างขั้นนี้นานสุดก่อน" ให้ผลเป็น round-robin โดยอัตโนมัติและกันใบงานอดตาย** — ถ้าเรียงตามเลขใบ
ใบ #7 จะถูกหยิบซ้ำทุกรอบจนจบ ส่วนใบ #8 ไม่มีวันได้เริ่ม

**ขั้น → agent อ่านจาก `STAGE_COLUMNS`** ที่มีฟิลด์ `agent` อยู่แล้ว ไม่สร้างตารางที่ 2

### 5.2 รัน agent

```bash
GH_TOKEN=<PAT ของ Hermes> claude -p "<prompt ของขั้นนั้น>" --permission-mode acceptEdits
```

**เทมเพลต prompt (ตายตัว — ประกอบจากตัวแปร 4 ตัวเท่านั้น):**

```
คุณคือ Controller ของสายพาน AI Command Center (00049)
อ่าน docs/conventions/command-center-agent-protocol.md ก่อนเริ่ม

ใบงาน #{number}: {title}
{body}

ขั้นปัจจุบัน: {stageLabel}
ให้ใช้ subagent `{agentName}` ทำขั้นนี้จนจบ แล้วปิดคำตอบของคุณด้วย
"บล็อกส่งต่อ" ตามโครงในเอกสารนั้น ตัวอักษรตรงเป๊ะ

ห้ามติดป้าย/โพสต์ comment/merge เอง — ผมเป็นคนทำให้จากบล็อกที่คุณคืนมา
```

ตัวแปร 4 ตัว: `{number}` `{title}` `{body}` `{stageLabel}`+`{agentName}` (คู่หลังมาจาก `STAGE_COLUMNS`)
**ไม่มีส่วนไหนของ prompt ที่ประกอบขึ้นแบบไดนามิกนอกจากนี้** — prompt ที่เดาไม่ได้คือ prompt ที่ทดสอบไม่ได้

🛑 **ลูปไม่แตะฐานข้อมูลเลย** — ใช้แค่ `gh` + `claude` และ import เฉพาะฟังก์ชันบริสุทธิ์จาก
`src/lib/command-center.ts` ⇒ ไม่ต้องมี `DATABASE_URL` บนเครื่อง Hermes **และไม่ควรมี**
(HR13/HR14 — เครื่องที่ไม่มี connection string คือเครื่องที่ล้างฐานผิดใบไม่ได้)

### 5.3 🛑 อ่านผลกลับ — สคริปต์ตรวจก่อนทำตาม (D-15)

| ตรวจ | ไม่ผ่าน → |
|---|---|
| มีบล็อก `=== DEEP-HANDOFF ===` ครบ 4 หัวข้อ | ไม่ย้ายป้าย · โพสต์ comment ว่าคืนบล็อกไม่ครบ |
| `ป้ายถัดไป` อยู่ใน allow-list | **ไม่ย้ายป้าย** |
| `ป้ายถัดไป` เป็น `พร้อมขึ้น` | 🛑 **ปฏิเสธเสมอ ไม่มีเงื่อนไข** |

ข้อสุดท้ายคือสิ่งที่ทำให้ D-1 เป็นจริง — **ต่อให้โมเดลเขียน `ป้ายถัดไป: พร้อมขึ้น` สคริปต์ก็ไม่ทำตาม**
prompt เป็นการ *ขอ* สคริปต์เป็นตัว *บังคับ* (`rule-must-be-enforced-not-described.md`)

ลำดับเขียน GitHub ตาม P3: **comment สำเร็จก่อน → ค่อยย้ายป้าย** · comment ล้ม = ไม่ย้ายป้าย

### 5.4 เมื่อ `ผลลัพธ์: ติดขัด`

โพสต์คำถามเป็น comment → เพิ่มป้าย `รอคำตอบ` → **คงป้ายขั้นเดิมไว้** → รอบหน้าข้ามใบนี้

ต้องเพิ่มฝั่งจอด้วย ไม่งั้น user ต้องไปลบป้ายเองบน GitHub:
- `POST /api/admin/command-center/items/{n}/answer` — โพสต์คำตอบ + ถอดป้าย `รอคำตอบ`
- ปุ่ม **"ตอบคำถาม"** บนการ์ด + ตัวบ่งชี้บนบอร์ดว่ามีใบรอ user อยู่

**ขอบเขต:** ส่วนนี้เป็น *ส่วนน้อยของ P4 ที่ต้องมาพร้อม P5* ไม่ใช่ฟีเจอร์ "คิวรอเคาะ" เต็มรูปแบบ
ตามภาพ 12tees (คำถามหลายตัวเลือก · แถบสี 3 ระดับ · แท็บคำขออนุญาต) — อันนั้นเป็นรอบแยกต่างหาก
ที่จะออกแบบได้ก็ต่อเมื่อเห็นแล้วว่า agent ถามอะไรบ้างจากการใช้งานจริง (ตอนนี้ยังเดาไม่ได้)

## 6. ชีพจร + สวิตช์หยุด

### 6.1 ชีพจร

ทุกรอบเขียน repo variable `HERMES_HEARTBEAT` เป็นเวลา ISO ปัจจุบัน — `watchdog.yml` อ่านค่านี้
เก่ากว่า 2 ชม. → เปิด issue → จอขึ้นแถบแดง (ทางอ่านมีแล้วใน `getHeartbeat()` จาก P4)

🛑 **เขียนชีพจร *ก่อน* เช็คหน้าต่างเวลา และเขียนแม้ไม่มีงานทำ**

ถ้าเขียนเฉพาะตอนทำงาน → ทุกคืนหลัง 22:00 ชีพจรหยุด → ตี 0 กว่า watchdog เปิด issue ทุกคืน
ทั้งที่เครื่องปกติ → อีกสองสัปดาห์ไม่มีใครสนใจแถบแดงนั้นอีก ซึ่งคือตอนที่เครื่องตายจริง
**ชีพจร = "เครื่องยังหายใจ" ไม่ใช่ "เครื่องกำลังทำงาน"**

⬜ ต้องสร้างตัวแปรนี้ครั้งแรกก่อน (ยิงแล้วได้ 404 = ยังไม่มี)

### 6.2 สวิตช์หยุด

repo variable **`HERMES_ENABLED`** — ไม่ใช่ `1` = ออกทันที

เป็น repo variable เพราะกดหยุดได้จากที่ไหนก็ได้ **ไม่ต้อง SSH** ต่างจาก `crontab -r`
**อ่านค่าไม่ได้ = หยุด (fail-closed)** — GitHub ล่มแล้วลูปไม่เดิน 5 นาทีไม่เสียหาย เพราะถึงทำเสร็จ
ก็โพสต์ผลกลับไม่ได้อยู่ดี

## 7. 🛑 สิทธิ์ — จุดที่ปิดไม่สนิทและรับความเสี่ยงไว้

### 7.1 ปัญหาที่ spike เจอ

`gh` บนเครื่อง login เป็น `shinobu22` = **admin ของ org** ⇒ agent ที่รันแบบ `acceptEdits`
เรียก `gh pr merge --admin` ได้ทันที = ละเมิด D-1 ตรง ๆ

### 7.2 ทางแก้ที่ทำได้

ลูป `export GH_TOKEN=<PAT ของ Hermes>` ก่อน spawn `claude` — `GH_TOKEN` ชนะ credential ที่เก็บไว้
⇒ ทุกคำสั่ง `gh` ที่ agent ยิงใช้ token ที่จำกัดสิทธิ์

PAT ของ Hermes (คนละใบกับของจอ): Issues RW · Pull requests RW · Contents RW · Variables RW ·
🛑 **ไม่มี Workflows**

### 7.3 🛑 ความเสี่ยงที่ยังเหลือ — เขียนไว้เพราะปิดไม่ได้ ไม่ใช่เพราะลืม

**fine-grained PAT แยก "เปิด PR ได้" ออกจาก "merge ได้" ไม่ได้ — ทั้งคู่อยู่ใต้ `Pull requests: write`**

⇒ agent ที่หลงทางยัง merge PR ที่ด่านเขียวได้ สิ่งที่กันจริงเหลือ 3 ชั้นที่ไม่มีชั้นไหนสมบูรณ์:

1. สคริปต์ลูปไม่มีคำสั่ง merge อยู่เลย
2. prompt สั่งห้าม (= การขอ ไม่ใช่การบังคับ)
3. `enforce_admins` — **ตอนนี้ `false`** ถ้าเปิด `true` อย่างน้อย PR ที่ด่านแดง merge ไม่ได้แม้เป็น admin

**ข้อเสนอ: เปิด `enforce_admins`** — แต่มีผลกับ user ด้วย (bypass ด่านเองไม่ได้อีก)
**ยังไม่ตัดสิน — ต้องถามก่อน implement**

## 8. ด่าน + สิ่งที่ยังพิสูจน์ไม่ได้

### 8.1 เทส `[blocker]` ที่ต้องมี (พิสูจน์ด้วย mutation ทุกตัว)

| เทส | mutation ที่ต้องทำให้แดง |
|---|---|
| `pickNextItem` | ถอดตัวกรอง `รอคำตอบ` ออก · เรียงกลับด้าน |
| `parseHandoff` | บล็อกขาดหัวข้อแล้วยังคืน valid |
| **`isAllowedNextLabel`** | 🛑 ลบบรรทัดที่ปฏิเสธ `พร้อมขึ้น` ออก |
| `isInsideWindow` | 22:01 เวลาไทยแล้วยังคืน true · TZ หลุดไปเป็น UTC |

### 8.2 ไม่ต้องแตะ `verify.yml`

เคยคิดจะเพิ่ม `scripts/hermes-loop.*` เข้า path คุ้มครอง — **คิดใหม่แล้วไม่ต้อง**

agent แก้ `src/lib/hermes-loop.ts` ให้ยอมรับ `พร้อมขึ้น` → เทส `[blocker]` แดง → ด่าน 2 แดง → merge ไม่ได้
ถ้ามันแก้ตัวเทสด้วยให้เขียว → **ด่าน 0 จับ** เพราะไฟล์เทสที่มี `[blocker]` เป็น path คุ้มครองอยู่แล้ว
→ ต้องมีคนติดป้าย `แตะด่าน` = user ได้เห็น

**กลไกที่มีอยู่ครอบเคสนี้พอดีโดยไม่ต้องแก้อะไร**

### 8.3 🛑 ยังพิสูจน์ไม่ได้จนกว่าจะรันใบงานจริง

3. **โควตา subscription หมดเร็วแค่ไหน** ที่ ~12 รอบ/ชม. × 14 ชม./วัน
4. **ขั้น `build` ใช้เวลาเท่าไรบน 2 core** — ถ้าเกิน 5 นาที `flock` จะกันรอบถัดไปเรื่อย ๆ
