4 · เรื่องที่ต้องตัดสินก่อนลงมือ

ก. ป้าย “นัดแล้ว” ที่ซ้ำ 9 ใบ — ผมเลือกเก็บไว้ ไม่ตัด

  • ทางที่สวยกว่าคือ ให้สถานะปกติไม่มีป้าย แล้วเหลือป้ายเฉพาะสถานะที่ต้องรู้ (ยืนยันแล้ว/ขอเลื่อน/ให้บริการแล้ว/ไม่มาตามนัด) — จอจะเงียบลงมาก
  • แต่นั่นแปลว่า “นัดแล้ว” จะถูกสื่อด้วยความว่างเปล่า ซึ่งอ่านไม่ออกว่าเป็นสถานะหนึ่งหรือระบบยังไม่รู้ — และมันจะสร้างนิยามที่สองของสีสถานะขึ้นมาในไฟล์นี้ ซึ่งชนกับ APPOINTMENT_STAGE_META ที่ประกาศตัวเองเป็น SSOT (HR16)
  • ต้องการให้ตัดจริงไหม — ถ้าเอา ผมจะทำโดยเพิ่มโหมดที่ ตัว SSOT ไม่ใช่ที่การ์ด

ข. ข้อมูลที่ยังไม่มีในลิสต์ — ต้องแตะ listAppointments

อยากได้ตอนนี้ทำได้ไหม
ชื่อบริการ (“ตัดผม”, “ล้างแอร์”)ไม่มีใน payload เลยได้ — เพิ่ม select items[0].title ไม่ใช่ PII · นี่คือสิ่งที่จะทำให้ 5 ใบเวลาเดียวกันต่างกันจริง แนะนำให้ทำพร้อมกัน
เบอร์โทร / ปุ่มโทรตั้งใจไม่ส่งไม่ทำ — คอมเมนต์ใน route เขียนห้ามไว้ตรงตัว (TFR-010: หน้านี้อยู่ใต้ client layout ทุก field ไหลเข้า flight payload) · อยากโทรให้กดเข้าออเดอร์ ซึ่งเป็นที่ที่เบอร์อยู่แล้ว
ยอดเงิน / มัดจำไม่มีได้ทางเทคนิค แต่ ผมไม่เสนอ — จอนี้ตอบคำถาม “วันนี้ใครมาบ้าง” ไม่ใช่ “เก็บเงินครบยัง” การใส่ตัวเลขเงินจะเปิดคำถามที่จอนี้ตอบไม่จบ
ชื่อคิวงาน (ช่างเอ/ช่างบี)มีแล้วใช้กฎเดิมไม่เปลี่ยน — โผล่เฉพาะตอนดู “ทุกคิวงาน” และร้านมีมากกว่า 1 คิว

ค. สิ่งที่ mockup นี้ยังไม่ได้พิสูจน์

  • ยังไม่ได้กดจริงสักครั้ง — นี่คือภาพนิ่ง ไม่ใช่ของที่รันได้ ตัวที่ static ตรวจไม่ได้คือ: เมนู ⋯ ของการ์ดใบล่างสุดจะเด้งทะลุขอบจอไหม, ปุ่ม “ให้บริการแล้ว” กับพื้นที่กดทั้งใบทับกันตรงไหน, หัวกลุ่มแบบ sticky จะชนกับหัว SellerMobileHeader ไหม
  • ยังไม่ผ่าน safepay-ux (HR8) — session นี้ตั้งค่าห้ามเรียก subagent ผมจึงอ่าน design.json + theme source เอง ควรให้ ux ตรวจย้อนหลังก่อนเขียนโค้ด
  • เลขที่อ้างถึงความกว้าง (78px ของราง, ชื่อเหลือ 150px ที่ 320px) คำนวณจาก padding ในโค้ดจริง แต่ยังไม่ได้วัดจากเบราว์เซอร์
