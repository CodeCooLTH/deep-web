A ซ่อมตามธีม — ไอคอน 2 ตัวเหมือนเดิม

ซ่อม 5 ข้อ ไม่เพิ่มไม่ลดอะไรเลย · บรรทัด 2 ใส่ ชื่อเพจ (ที่ที่ธีมเตรียมไว้ให้อยู่แล้ว) · ปุ่มขวายังเป็นไอคอน 2 ตัว แต่ห่อกลุ่ม gap-1.5 และมีกรอบเท่ากันทั้งคู่

ได้

  • แรงน้อยที่สุด — ทุกบรรทัดที่แก้มีต้นทางในธีมชี้ได้
  • ชื่อเพจอ่านได้บนมือถือครั้งแรก (เดิมมีแต่ title= ที่ iOS ไม่แสดง)
  • ปุ่มหน้าตาเดียวกันทั้งแถว · ตัวบอกปิดเสียงไม่ล้นแล้ว
  • ชื่อได้ 98px ที่ 320px (จาก 85)

ยังไม่แก้

  • ปุ่มยังเป็นไอคอนเปล่า — ข้อ 2 ที่ user ทัก ("ไม่รู้ว่าปุ่มไหนคืออะไร") ยังอยู่ครบ
  • ชื่อยาว ๆ ยังถูกตัดที่ 320px

B ปุ่มไฟล์มีคำ — btn btn-sm แทนไอคอนเปล่า

ซ่อม 5 ข้อเหมือน A แล้วเปลี่ยนปุ่มคลังไฟล์จากไอคอนเปล่าเป็นปุ่มมีคำ [ไอคอน] ไฟล์ 3 (btn btn-sm border-default-300) — ตัวเลขเป็น badge ในปุ่ม ไม่ใช่จุดลอยมุม · ⋯ คงเป็นไอคอน

ได้

  • แก้ข้อ 2 ตรง ๆ — คำว่า "ไฟล์" อยู่บนจอ ไม่ต้องเดา ไม่ต้อง hover
  • ตอบ report ต้นเรื่องที่ทำให้ปุ่มนี้เกิดขึ้น ("จะเข้าไปดูไฟล์ใช้ร่วมกันยากมาก")
  • ตัวนับอยู่ในปุ่มเป็น badge = pattern ที่ธีมใช้จริง แทน badge ลอยมุมที่ชนขอบ

เสีย

  • ปุ่มกว้าง ~76px แทน 37 ⇒ ชื่อเหลือ 59px ที่ 320px — แคบกว่าปัจจุบัน
  • ที่ 320px ชื่อจะเหลือ ~4 ตัวอักษร ต้องยอมให้ตัด หรือให้ปุ่มยุบเป็นไอคอนที่ <375px
  • ปุ่มเดียวมีคำ อีกปุ่มไม่มี — ต้องยอมรับว่าไม่สมมาตร (แลกกับการที่ ⋯ เป็นสัญลักษณ์สากลอยู่แล้ว)

C ตัวตนกดได้ — ปุ่มขวาเหลือ ⋯ ตัวเดียว

ซ่อม 5 ข้อ + ทั้งกลุ่ม รูป + ชื่อ + ชื่อเพจ เป็นปุ่มเดียวที่เปิดแผงข้อมูลลูกค้า (เป้าแตะ ~180×40) · ปุ่มขวาเหลือ ⋯ ตัวเดียว โดยคลังไฟล์ย้ายไปเป็นรายการแรกในเมนู พร้อมคำและตัวนับ

ได้

  • ชื่อได้ 141px ที่ 320px — กว้างสุดในทั้ง 3 แบบ
  • เป้าแตะใหญ่ที่สุด และตรงกับที่คนแตะโดยสัญชาตญาณอยู่แล้ว (ชื่อคู่สนทนา)
  • แถวหัวสะอาดที่สุด ปุ่มเดียวจบ

เสีย

  • 🛑 คลังไฟล์ลึกลง 1 ชั้น (1 แตะ → 2 แตะ) ซึ่งสวนทางกับ report ที่ทำให้ปุ่มนี้ถูกยกขึ้นมาเมื่อเช้า — แลกกับการที่ในเมนูมีคำว่า "คลังไฟล์" ให้อ่าน
  • "แตะชื่อ = เปิดแผง" ไม่มีสัญญาณในตัวเอง ต้องมี chevron-right จาง ๆ กำกับ
  • ตัวนับไฟล์ไม่เห็นจากภายนอกเมนู เว้นแต่ทำจุดบนปุ่ม ⋯ ซึ่งจะชนกับตัวบอกปิดเสียงที่อยู่มุมเดียวกัน

E ออเดอร์เป็นปุ่มหลัก · ไฟล์โผล่เฉพาะเมื่อมี จาก feedback ลูกค้าจริง

ลูกค้าบอกว่า ผู้ขายบนมือถือดูรายการออเดอร์ของลูกค้ามากกว่าดูไฟล์ — แต่ของจริงกลับกัน: ไฟล์ = 1 แตะ · ออเดอร์ = 2 แตะ (⋯ → คำสั่งซื้อ) และไม่มีตัวเลขบอกว่ามีกี่ใบ
แบบนี้จึง สลับลำดับความสำคัญ: ปุ่มออเดอร์เป็นปุ่มระดับหนึ่งเสมอพร้อมตัวนับ · ปุ่มไฟล์ยังอยู่ระดับหนึ่งเหมือนเดิม แต่โผล่เฉพาะเมื่อ savedFiles.size > 0

ได้

  • งานที่ทำบ่อยสุดเหลือ 1 แตะ และเห็นตัวเลขจากหน้าจอโดยไม่ต้องเปิดอะไร
  • ไม่มีอะไรถูกดันลึกลง — ไฟล์ยังเป็น 1 แตะเหมือนเดิมเมื่อมีไฟล์ (ไม่ย้อนงานเมื่อเช้า)
  • เธรดที่ยังไม่มีไฟล์ (ส่วนใหญ่) ได้ชื่อกว้างเท่าแบบ A — ปุ่มที่กดไปเจอความว่างเปล่าไม่ควรกินที่ตั้งแต่แรก
  • ตัวนับทั้งคู่มาจากข้อมูลที่ server ส่งมาแล้ว (customerPanelData.orders / savedFiles) — ไม่มี request เพิ่มแม้แต่ใบเดียว

ต้องตัดสินต่อ

  • 🛑 ตัวนับบนปุ่มออเดอร์นับอะไร — ถ้านับ "ที่ยังดำเนินอยู่" จะซ้ำกับชิปในแถวชิปที่นับเลขเดียวกัน (HR16 เลขเดียวกันต้องมาจาก symbol เดียว) ⇒ ม็อกอัพนี้นับ ทั้งหมดของลูกค้าคนนี้ = "เคยสั่งกี่ครั้ง" ซึ่งเป็นคนละคำถามกับชิป
  • ปุ่มโผล่/หายตามข้อมูล — ผู้ใช้อาจงงว่าปุ่มหายไปไหน (บรรเทาด้วยการที่ไฟล์ยังอยู่ใน ⋯ เสมอ)
  • ที่ 320px เมื่อมีไฟล์ ชื่อจะแคบกว่าทุกแบบ — วัดจริงในกรอบซ้าย

K สังเคราะห์: คำเตือนแบบ H + ข้อมูลแบบ G ที่แนะนำหลัง re-design

H กับ I ล้มด้วยเหตุผลเชิงเรขาคณิต ไม่ใช่เรื่องรสนิยม — ชื่อเพจกว้าง 104px แต่บรรทัดใต้ชื่อที่ 390px มีที่แค่ ~123px ⇒ ใส่ได้อย่างเดียวเท่านั้น ป้ายลูกค้าที่ตั้งใจจะโชว์เลยไม่โผล่เลยบนจอที่ต้องการมันที่สุด
แถบเต็มความกว้างมี 358px ที่ 390px — จุของได้เกือบ 3 เท่า ⇒ ข้อมูลลูกค้าต้องอยู่แถบเต็มกว้าง ไม่ใช่ใต้ชื่อ
K จึงหยิบของที่ดีที่สุดของแต่ละแบบมาประกอบ: หัวแบบ E (ชื่อ + ชื่อเพจใต้ชื่อ + 3 ปุ่ม) · คำเตือนแบบ H (แถบสีเต็มกว้าง มีปุ่มในตัว โผล่เฉพาะเมื่อมี) · ข้อมูลลูกค้าแบบ G (แถบจางเต็มกว้าง บรรทัดเดียว)

ได้

  • คำเตือนอ่านไม่พลาด — เต็มความกว้าง มีสี ปุ่มอยู่ในตัว ไม่ต้องเลื่อนหา (จุดที่ชิปเดิมทำได้แย่ที่สุด)
  • ป้ายลูกค้า + ที่มา อ่านได้ครบบนมือถือจริง เพราะได้ความกว้างเต็มจอ
  • ชื่อเพจยังอยู่ใต้ชื่อลูกค้า ไม่ต้องแย่งที่กับข้อมูลลูกค้า
  • เธรดปกติ (ไม่มีคำเตือน) = 66 + 26 = 92px (จาก 105) · มีคำเตือน = 123px

เสีย

  • คำเตือนหลายอันพร้อมกัน = หลายแถบซ้อน (ชิปเดิมเรียงในแถวเดียวได้) — ต้องจำกัดว่าโชว์กี่แถบ แล้วที่เหลือยุบ
  • ข้อมูลนิ่งกดกางดูรายละเอียดไม่ได้ (เหมือน G) — ที่มาของแชทเคยกดดูรูปโฆษณาต้นทางได้
  • เมื่อมีคำเตือน = 3 ชั้น (หัว + แถบเตือน + แถบจาง) สูงกว่าเดิม 18px

H หัวเดียวจบ — ข้อมูลลูกค้าอยู่ใต้ชื่อ · คำเตือนเป็นแถบแยก re-design

ทิ้งแนวคิด "แถวชิป" ทั้งดุ้น — ของ 2 ชนิดที่เคยปนกันในแถวเดียวถูกแยกตามธรรมชาติของมัน:
• ข้อมูลนิ่ง (เพจ · ลูกค้าเก่า · ตีกลับ · ที่มา) ขึ้นไปอยู่ บรรทัดที่ 2 ใต้ชื่อ เป็นข้อความ inline คั่นจุด ไม่มีกรอบ
• คำเตือน ลงมาเป็น แถบสีเต็มความกว้าง ที่โผล่เฉพาะเมื่อมี — เหมือนแถบแจ้งเตือนของระบบ ไม่ใช่ชิปที่ต้องไปหาในแถว

ได้

  • เธรดปกติเหลือชั้นเดียว 66px (จาก 105) — ไม่มีแถวว่างที่มีชิปเดียวอีกต่อไป
  • คำเตือนอ่านไม่พลาด — เต็มความกว้าง มีสี มีปุ่มในตัว ไม่ต้องเลื่อนหา
  • ข้อมูลลูกค้าอยู่ติดชื่อ = อ่านเป็นประโยคเดียวกับ "กำลังคุยกับใคร"
  • ไม่มีอะไรถูกดันพ้นขอบจอ เพราะบรรทัด 2 ตัดท้ายด้วย truncate ตามลำดับความสำคัญ

เสีย

  • ข้อมูลนิ่งกดกางดูรายละเอียดไม่ได้อีก (เดิมกดชิปกางดูรูปโฆษณา/คอมเมนต์ต้นทางได้) — ต้องเข้าแผงลูกค้าแทน
  • บรรทัด 2 มีที่จำกัด ~200px ที่ 390px ⇒ ใส่ได้ ~3 อย่าง ที่เหลือถูกตัด
  • คำเตือนหลายอันพร้อมกัน = หลายแถบซ้อน (เดิมเป็นชิปเรียงในแถวเดียว)

I แถบเดียวผสม — เรียงตามความสำคัญ ไม่แยกชั้น re-design

หัวสั้นเหลือ ชื่อบรรทัดเดียว (ไม่มีบรรทัดรอง) แล้วยุบทุกอย่างลง แถบเดียวใต้หัว ที่ ผสมทั้งของที่ต้องลงมือและของที่ควรรู้ในบรรทัดเดียวกัน — ต่างกันด้วยรูปทรง ไม่ใช่ตำแหน่ง: เรื่องต้องลงมือ = เม็ดยาพื้นสี · เรื่องควรรู้ = ข้อความเปล่าคั่นจุด · เรียงซ้าย→ขวาตามความสำคัญ

ได้

  • ยังเป็น 2 ชั้นเท่าเดิม แต่ชั้นล่างจุของได้มากกว่าเดิมมาก เพราะของที่ไม่ต้องลงมือไม่กินกรอบ
  • ลำดับความสำคัญอ่านได้จากซ้ายไปขวาเป็นเส้นเดียว ไม่ต้องกวาดตา 2 แถว
  • ใกล้โครงเดิมที่สุด — ThreadChipStrip แค่เพิ่มชนิด "ข้อความเปล่า" เข้าไป

เสีย

  • ชื่อเพจหลุดจากหัว (ไปอยู่ในแถบ) ⇒ "คุยกับใคร" กับ "เพจไหน" ไม่ได้อยู่ติดกันแล้ว
  • ของ 2 ชนิดในบรรทัดเดียว ถ้าคำเตือนยาว ข้อมูลลูกค้าจะถูกดันพ้นขอบทันที (โรคเดียวกับ F)
  • ยังต้องเลื่อนแนวนอนอยู่ดีเมื่อมีของเยอะ

J ชั้นเดียวล้วน — ตัวเลขอยู่บนปุ่ม ไม่มีแถวที่ 2 re-design

สุดขั้วอีกทาง: ไม่มีแถบใต้หัวเลย พื้นที่บนสุดเหลือ 61px ชั้นเดียว
ข้อมูลถูกบีบให้เหลือเฉพาะที่แสดงเป็นตัวเลขหรือจุดสีบนปุ่มได้: ออเดอร์ = ตัวเลขบนปุ่มรถเข็น · ไฟล์ = ตัวเลขบนโฟลเดอร์ · มีเรื่องต้องลงมือ = จุดส้มบนปุ่ม ⋯ · ที่เหลือทั้งหมด (ป้ายลูกค้า · ที่มา · รายละเอียดคำเตือน) อยู่หลังการแตะ

ได้

  • 61px — ประหยัดที่สุดในทุกแบบ คืนพื้นที่อ่านข้อความ 44px
  • จอสะอาดมาก ไม่มีอะไรแย่งความสนใจจากบทสนทนา
  • ชื่อลูกค้าได้ที่กว้างที่สุดเท่าที่เป็นไปได้

เสีย — หนักที่สุด

  • 🛑 คำเตือนกลายเป็นจุดสีจุดเดียว — "บอทหยุดตอบ" กับ "โควตาหมดส่งไม่ได้" หน้าตาเหมือนกันเป๊ะ ผู้ขายไม่รู้ว่าเรื่องด่วนแค่ไหนจนกว่าจะกด
  • ป้ายพฤติกรรมลูกค้ากลับไปซ่อนในแผงเหมือนเดิม = ย้อนสิ่งที่ feedback ลูกค้าเพิ่งบอกมา
  • ปุ่มที่เคยกดได้ทันที (เช่น "ให้บอทตอบต่อ") ลึกลง 1 ชั้น
  • ใส่ไว้เป็นขั้วเปรียบเทียบ ไม่ได้เสนอให้ใช้จริง — มีไว้ให้เห็นว่า "ประหยัดที่สุด" แลกอะไรไปบ้าง

F แถวชิป: เติมป้ายลูกค้าเข้าไป (โครงเดิม)

หัวใช้แบบ E · แถวชิปคงโครงเดิมทุกอย่าง (ยุบ/กาง · เลื่อนแนวนอน · โทนตามความสำคัญ) แต่เติมของที่มีข้อมูลพร้อมอยู่แล้วแต่ไม่เคยแสดงที่นี่ เข้าไปในลำดับที่ 3:
คำเตือน → สถานะออเดอร์ → ป้ายลูกค้า (ใหม่) → ที่มาของแชท

ได้

  • ป้าย "ตีกลับ 2 รายการ / ยกเลิก 1 รายการ" ที่สั่งทำไว้เมื่อ 11 ส.ค. โผล่ตอนที่มันมีประโยชน์ที่สุด — ตอนกำลังคุยกับลูกค้า ไม่ใช่ตอนเปิดแผงไปดู
  • ไม่ต้องแตะโครง ThreadChipStrip เลย — เพิ่มรายการเข้า array เท่านั้น
  • ข้อมูลมาถึงหน้านี้อยู่แล้ว (customerBehavior, customerStats) ไม่มี request เพิ่ม

เสีย

  • แถวยาวขึ้น ต้องเลื่อนบ่อยขึ้น — ของสำคัญ (คำเตือน) ยังอยู่ซ้ายสุดเสมอ แต่ที่มาของแชทจะถูกดันพ้นขอบจอบ่อย
  • ชิป 4 ชนิดหน้าตาใกล้กันมาก ต่างแค่สี — ผู้ใช้ต้องอ่านทุกใบเพื่อรู้ว่าอันไหนคืออะไร
  • ป้ายลูกค้าเป็น ข้อมูลนิ่ง (ไม่เปลี่ยนทั้งวัน) อยู่ปนกับคำเตือนที่ ต้องลงมือ

G แถวชิป: แยก 2 ระดับ — เรื่องที่ต้องลงมือ vs เรื่องที่ควรรู้

หัวใช้แบบ E · แถวชิป (พื้นขาว) เหลือเฉพาะสิ่งที่ต้องลงมือ — คำเตือน + สถานะออเดอร์ · ข้อมูลนิ่งย้ายลงแถบจางบรรทัดเดียว (พื้นเทา ตัวเล็ก ไม่มีกรอบชิป): ป้ายลูกค้า · ที่มาของแชท
ไม่มีคำเตือนเลย → แถวชิปหายทั้งแถว เหลือแค่แถบจาง 26px (จาก 44px)

ได้

  • อ่านออกใน 1 วินาทีว่ามีอะไรต้องทำไหม — ถ้าไม่มีชิปสี = ไม่มีอะไรค้าง
  • เธรดปกติ (ส่วนใหญ่) chrome ลดจาก 44px เหลือ 26px
  • ข้อมูลลูกค้าได้ที่อยู่ถาวรโดยไม่แย่งความสนใจกับคำเตือน

เสีย

  • เพิ่มรูปแบบใหม่ให้หน้าจอ (แถบจาง) — ไม่มี precedent ตรง ๆ ในธีม ต้องหา pattern รองรับก่อน
  • ที่มาของแชทเคยกดกางดูรายละเอียดได้ (รูปโฆษณา/คอมเมนต์ต้นทาง) พอเป็นแถบจางต้องตัดสินว่ายังกดได้ไหม
  • 2 แถบซ้อนกันเมื่อมีคำเตือน = 44 + 26 = 70px สูงกว่าเดิม

D A + คำเฉพาะจอที่มีที่พอ ที่ผมแนะนำ

ฐานคือ A (ซ่อม 5 ข้อตามธีม) แล้วปุ่มคลังไฟล์ ผันตามความกว้างจอ: <375px เป็นไอคอนเปล่าเหมือน A · ≥375px กางเป็นปุ่มมีคำ "ไฟล์" เหมือน B — ดู 3 กรอบข้างล่างเทียบกัน จะเห็นความต่างทันที

ได้

  • ได้คำกำกับบนจอที่ผู้ใช้จริงเกือบทั้งหมดใช้ (iPhone SE รุ่นเล็กสุดที่ยังขายอยู่ = 375px)
  • ที่ 320px ไม่ทำให้ชื่อพัง — ยังได้ 98px เท่า A
  • ไม่มีอะไรหาย ไม่มีอะไรลึกลง — ต่างจาก C ที่ดันไฟล์กลับเข้าเมนู
  • เขียนด้วย hidden min-[375px]:inline ครอบคำ ไม่ต้องมี component แยก

ต้องยอม

  • ปุ่มเปลี่ยนรูปร่างตามจอ — ผู้ใช้คนเดียวที่สลับ 320↔390 จะเห็นไม่เหมือนกัน (ในทางปฏิบัติแทบไม่เกิด เครื่องเดียวความกว้างคงที่)
  • ต้องใช้ arbitrary breakpoint min-[375px] — ธีมไม่มี xs ⇒ ต้องเขียนคอมเมนต์กำกับตาม HR7 หรือใช้ sm: (640px) แทนซึ่งกว้างไปมาก
  • ปุ่มเดียวมีคำ อีกปุ่มไม่มี (ยอมรับได้ — ⋯ เป็นสัญลักษณ์สากล)
