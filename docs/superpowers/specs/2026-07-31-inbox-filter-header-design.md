- **วันที่:** 2026-07-31
- **ขอบเขต:** เฉพาะส่วนหัวของรายการแชท seller `/inbox` (`InboxList.tsx` card-header) — ไม่แตะแถวรายการหรือหน้าเธรด
- **Mockup:** [`2026-07-31-inbox-filter-header-mockup.html`](./2026-07-31-inbox-filter-header-mockup.html) (Mobile 375 / Tablet 768 / Desktop rail 320)
- **สถานะ:** รอ user เลือกทาง — **ยังไม่ implement**

## 1. ปัญหา

บนคอลัมน์แคบ (ซึ่งเป็นความกว้างปกติของรายการแชท) ส่วนหัวกินไป **3 แถว** ก่อนถึงรายการแชทจริง:

```
[ค้นหา]
[ทั้งหมด][Deep][FB][IG]  [ตัวกรอง ▾]
[ทุกเพจ ▾]                     ← ตกลงมาแถวของตัวเองเกือบตลอด
[ทั้งหมด][ร้านอะไหล่][ทดสอบ][+]
```

ผลคือเห็นเธรดต่อหนึ่งจอน้อยลง ซึ่งเป็นสิ่งที่ผู้ใช้มาที่หน้านี้เพื่อดู

---

## 2. ข้อจำกัดที่เรียนรู้มาแล้ว (สำคัญกว่าตัวเลขจำนวนแถว)

รอบวันที่ 2026-07-31 เคยลอง **ยุบช่องทาง+เพจ+สถานะเข้าปุ่ม "ตัวกรอง" ปุ่มเดียว** แล้ว user ปฏิเสธ
และสั่งถอยกลับทั้งหมด (`07eb6aaa`, `db7352c8`) บทเรียนที่ต้องไม่ทำซ้ำ:

| สิ่งที่พลาด | ผลที่เกิด |
|---|---|
| ยุบ pill ช่องทางเข้าดรอปดาวน์ | สลับ FB/IG จาก **1 คลิก → 3 คลิก** ทั้งที่เป็น action ที่ใช้บ่อยที่สุดในหน้านี้ |
| ปุ่มรวมทุกอย่างวางไว้ท้ายแถว | เป็น **single point of access** แล้วถูกดันหลุดขอบเมื่อกลุ่มเยอะ → เข้าไม่ถึงตัวกรองเลย |
| popover ยาวขึ้น 2 หัวข้อ | ทะลุจอและ**เลื่อนข้างในไม่ได้** (ไม่มี `max-height`) |

> **กฎที่ได้:** การลดจำนวนแถวไม่คุ้ม ถ้าต้องแลกด้วยจำนวนคลิกของสิ่งที่ใช้บ่อยที่สุดในหน้านั้น

## 3. ทางเลือก

### ทาง A — ซ่อนสิ่งที่ไม่จำเป็นโดยอัตโนมัติ

ไม่ย้ายอะไรสักอย่าง แค่ไม่แสดงตัวเลือกที่กดไปก็ไม่เกิดผล:

- pill ช่องทาง แสดงเฉพาะช่องทางที่ร้าน**มีจริง** (ดูจาก `channels` ที่ SSR ส่งมาอยู่แล้ว + มีเธรด DEEP ไหม)
- ดรอปดาวน์ "เพจ" โผล่เฉพาะร้านที่มี **มากกว่า 1 เพจ**

| | |
|---|---|
| แถว | **2 แถว** สำหรับร้านส่วนใหญ่ (3 แถวถ้าใช้ครบทุกช่องทาง + หลายเพจ) |
| คลิกที่เสียไป | **ไม่มีเลย** |
| ความเสี่ยง | ต่ำสุด — ไม่มีอะไรย้ายที่ |
| ข้อควรระวัง | ต้องนิยาม "ร้านมีช่องทางนี้จริง" ให้ถูก ไม่งั้นปุ่มหายทั้งที่ควรมี |

### ทาง B — ยุบเฉพาะ "เพจ" เข้าปุ่มตัวกรอง

pill ช่องทางอยู่ที่เดิมครบ ยุบเฉพาะดรอปดาวน์เพจเข้าไปเป็นหัวข้อในปุ่มตัวกรอง (พร้อม badge นับ)

| | |
|---|---|
| แถว | **2 แถว เสมอ** |
| คลิกที่เสียไป | เลือกเพจ 1 → 3 คลิก (กระทบเฉพาะร้านหลายเพจ) |
| ความเสี่ยง | ปานกลาง — ต้องใส่ `max-h` + scroll ใน popover ตั้งแต่แรก |

### ทาง C — จัดแถวใหม่ ไม่ซ่อนอะไรเลย

สลับว่าอะไรอยู่แถวไหน ตามความหมาย:

```
[ค้นหา]
[ช่องทาง...][ทุกเพจ ▾]        ← "ดูจากที่ไหน"
[ตัวกรอง ▾][กลุ่ม...เลื่อนได้]  ← "กรองยังไง"
```

| | |
|---|---|
| แถว | **2 แถว เสมอ** |
| คลิกที่เสียไป | **ไม่มีเลย** |
| ความเสี่ยง | ปานกลาง — ย้ายตำแหน่งของที่ผู้ใช้คุ้นมือ; ปุ่มตัวกรอง**ต้องปักซ้าย** ให้กลุ่มเลื่อนแทน (บทเรียนข้อ 2) |

## 4. หมายเหตุ

- **A รวมกับ B หรือ C ได้** — A เป็นกฎการ "ซ่อนเมื่อไม่มีผล" ไม่ใช่การจัดวาง จึงไม่ขัดกัน
- ทุกทางเลือกใช้ Paces token เท่านั้น (`--color-primary: #236dc9`) — **ห้ามม่วง Vuexy `#7367F0`** ในหน้า `(paces)/**` ตาม DESIGN.md §1 "Overview" (Dual-skin reality) และ Hard Rule 7
- ไม่มี emoji ใน mockup — ไอคอนเป็น SVG ทั้งหมด (Hard Rule 12)
- ทุกทางเลือกต้องเพิ่ม `max-h` + `overflow-y-auto` ให้ popover ตัวกรอง (บั๊กที่เจอจริง: เนื้อหายาวทะลุจอแล้วเลื่อนไม่ได้)

## 6. ผลการเลือก (2026-07-31)

user เลือก **V1** จาก mockup v2 ([`…-v2-mockup.html`](./2026-07-31-inbox-filter-header-v2-mockup.html))
พร้อมสั่งเพิ่ม:

- แถวแท็บล่างต้องมี **"ปิดงาน" และ "สแปม" เป็นมุมมองพื้นฐาน** (ลบไม่ได้) ก่อนกลุ่มที่ร้านสร้างเอง
- **สแปมใช้สีแดง** → ใช้ token `--color-danger: #f7577e` ของ Paces (ไม่ใช่แดงสดที่คิดเอง)
- เมื่อสถานะ/สแปมขึ้นเป็นแท็บแล้ว ต้อง**ถอดออกจากดรอป** ไม่ให้คุมเรื่องเดียวกัน 2 ที่

### หนี้ที่จดไว้ ยังไม่ทำ (user สั่งพักไว้ 2026-07-31)

**ช่องค้นหาโฆษณาเกินจริง** — placeholder เขียนว่า *"ค้นหาชื่อ ลูกค้า เบอร์ หรือข้อความในแชท"*
แต่ `listConversationsForShop` ค้นแค่ 2 อย่าง:

```ts
lastMessagePreview   contains q   // ข้อความ "ล่าสุด" อันเดียว ไม่ใช่ทั้งประวัติ
externalContact.name contains q
```

ทำไม่ได้จริง: ค้นข้อความย้อนหลัง (ต้องค้น `ChatMessage.body`) · ค้นเบอร์โทร
(`ExternalContact.phones` / `Customer.phone` ไม่ถูกแตะ)

ทางเลือกตอนกลับมาทำ: (ก) ทำให้ค้นได้จริง — ต้องคิดเรื่อง index เพราะแชทเยอะจะช้า
หรือ (ข) แก้ placeholder ให้ตรงความจริงก่อน แล้วค่อยทำของจริงทีหลัง

### กรองด้วยแท็ก (เพิ่ม 2026-07-31)

**สถานะเดิม:** ร้านตั้งแท็กได้ (`ExternalContact.tags`, `TagInput`, `GET /api/chat/tags`) และเห็น
badge แท็กในแถว **แต่กรอง/ค้นด้วยแท็กไม่ได้เลย** — `listConversationsForShop` ไม่มี option `tag`
และ `q` เทียบแค่ `lastMessagePreview` + ชื่อผู้ติดต่อ ทำให้แท็กแทบไม่มีประโยชน์เมื่อแชทเยอะ

**ที่ตกลง:**
- แท็กเป็นหัวข้อชิปในดรอปตัวกรอง (อยู่ถัดจาก "เพจ")
- **เลือกได้หลายอัน แบบ "ติดอันใดก็ได้" (OR)** — ไม่ใช่ต้องครบทุกอัน
- **โชว์ทุกแท็กของร้าน พับหลายบรรทัด** ไม่ตัดจำนวน (ดรอปมี max-height + เลื่อนอยู่แล้ว)
- ดึงรายการจาก `GET /api/chat/tags` ที่มีอยู่แล้ว ไม่ต้องทำ endpoint ใหม่

**ฝั่ง service ที่ต้องเพิ่ม:**
```ts
tags?: string[]   // ใน opts ของ listConversationsForShop
→ { externalContact: { tags: { hasSome: opts.tags } } }
```
ใช้ array operator ของ Postgres ตรง ๆ — ขนาดข้อมูลระดับร้านทั่วไปยังไม่ต้องทำ GIN index
(ถ้าโตจนช้าค่อยเพิ่มทีหลัง)

### กรองด้วยสถานะพัสดุ iShip (เพิ่ม 2026-07-31)

**ที่ตกลง:**
- หัวข้อ **"พัสดุ (iShip)"** ในดรอป — **โผล่เฉพาะร้านที่เชื่อม iShip แล้ว**
  (`ShopShippingAccount` ของร้านนั้น `status = 'ACTIVE'`) ร้านที่ไม่ได้ใช้ต้องไม่เห็นหัวข้อที่ไม่มีความหมาย
- 3 ตัวเลือก: `ยังไม่สร้างพัสดุ` · `สร้างแล้ว ยังไม่พิมพ์` · `พิมพ์แล้ว`
- ยึด **ออเดอร์ล่าสุด** ของลูกค้าคนนั้น — เหตุผล: ชิปสถานะออเดอร์ในแถว (`deriveOrderStage`)
  ก็อ้างออเดอร์ล่าสุดเหมือนกัน ถ้าตัวกรองใช้คนละเกณฑ์ ผลลัพธ์จะขัดกับชิปที่ผู้ใช้เห็นตรงหน้า

**ฝั่ง service:**

ต่างจากตัวกรองอื่นตรงที่ข้ามหลายตาราง: `Conversation → ExternalContact.customerId →
Order (ล่าสุด) → OrderShipment.labelPrintedAt`

- `ยังไม่สร้างพัสดุ` = ออเดอร์ล่าสุดไม่มี `OrderShipment` ที่ยัง active
- `สร้างแล้ว ยังไม่พิมพ์` = มีพัสดุ แต่ `labelPrintedAt IS NULL`
- `พิมพ์แล้ว` = `labelPrintedAt IS NOT NULL`

⚠️ Prisma แสดง "ออเดอร์ล่าสุดต่อลูกค้า" ใน `where` ตรง ๆ ไม่ได้ — ตัวกรองนี้จะต้องใช้ raw SQL
(`DISTINCT ON` แบบเดียวกับ `enrichWithOrderStage` ใน `order-stage.service.ts`) แล้วเอา
`conversationId` ที่ผ่านเกณฑ์มา `id: { in: [...] }` ต่อ — pattern เดียวกับที่ `readState`
ทำอยู่แล้ว (ดึง id มาก่อนแล้วค่อยกรอง)
