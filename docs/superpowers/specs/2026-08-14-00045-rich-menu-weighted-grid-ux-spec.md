## หน้า: เมนูลัดใน LINE — โครงช่องแบบปรับสัดส่วนได้ (Weighted Grid) (`/settings/channels/line/[channelId]/rich-menu`)

> **สถานะ lib (ยืนยันจาก team-lead 2026-08-14, ผ่านเทส 82 ข้อ):** `RichMenuLayout = { h: number; cols: number[] }[]`
> `h` = น้ำหนักความสูงของแถว (สัมพัทธ์กับแถวอื่น), `cols[i]` = น้ำหนักความกว้างของช่องที่ i ในแถวนั้น
> **น้ำหนักเป็นจำนวนเต็ม 1–12** · **แถวสูงสุด 10 แถว** · **ช่องต่อแถวสูงสุด 10 ช่อง** · **รวมทุกช่องทั้งเมนูไม่เกิน 20** (เพดานจริงของ LINE, `RICH_MENU_MAX_AREAS`)
> `matchPresetKey(layout)` คืนคีย์เทมเพลตที่ตรงกับเลย์เอาต์ปัจจุบัน หรือ `null` ถ้าไม่ตรงกับ 6 แบบใดเลย — ใช้ไฮไลต์ชิปเทมเพลตแบบ **live**
> จำนวนปุ่มต้องเท่าจำนวนช่องเป๊ะเสมอ (`RICH_MENU_BUTTON_COUNT_MISMATCH`) → การเพิ่ม/ลบช่องกระทบรายการปุ่มโดยตรง สเปกนี้ออกแบบวิธีเตือน+กู้คืนไว้แล้ว (ดู §Section 3, flow ข้อ 5-6)

### User stories ที่ครอบ
- ในฐานะผู้ขาย ฉันอยากให้แถวบน (โปรโมชั่น) สูงกว่าแถวล่าง (ปุ่มย่อย) เพื่อให้ภาพเมนูตรงกับสิ่งที่อยากเน้น
- ในฐานะผู้ขายที่มีภาพแบนเนอร์ของตัวเอง (โหมด CUSTOM) ฉันอยากขยับสัดส่วนให้ตรงกับช่องในภาพที่กราฟิกออกแบบมาให้ ไม่ใช่ถูกบังคับให้แบ่งเท่า ๆ กัน
- ในฐานะผู้ขายที่ทำงานบนมือถือเป็นหลัก (PRODUCT.md) ฉันต้องปรับโครงช่องได้เต็มที่โดยไม่ต้องรอเปิดคอม
- ในฐานะผู้ขาย ฉันไม่อยากพลาดลบปุ่มที่ผูก action สำคัญ (เช่นลิงก์ร้าน) ไปแบบไม่รู้ตัวตอนลดจำนวนช่อง

### Layout (ASCII wireframe)

**หมายเหตุ breakpoint สำคัญ:** หน้านี้อยู่ใต้ `(paces)` — ใช้สเกล Tailwind มาตรฐาน **ไม่ remap** และ **seller mobile shell มีเส้นแบ่งเดียวคือ `lg` (1024px)** (DESIGN.md → "Seller mobile shell"). แปลว่า **768px ยังอยู่ในโหมดมือถือ/คอลัมน์เดียว** ไม่ใช่จุดขึ้น 2 คอลัมน์แบบฝั่ง buyer (900px, `md:`) — โครงหน้าที่ 768 กับ 375 จึงเหมือนกัน ต่างแค่ความกว้างที่มีให้ chip/steppers เท่านั้น (กับดัก "Two-Breakpoint-Systems Rule" ที่ DESIGN.md เตือนตรง ๆ)

### Section breakdown (prose)

**1. "โครงช่อง" (ใหม่) — แทนที่ "รูปแบบการวางช่อง" เดิม ใช้ได้ทั้ง AUTO และ CUSTOM**
เดิมตัวเลือกเลย์เอาต์ 6 แบบแสดงเฉพาะโหมด CUSTOM (บรรทัด 415-434 ของ `RichMenuEditor.tsx` เวอร์ชันก่อนงานนี้) โหมด AUTO ไม่มี UI ปรับโครงเลย — งานนี้ทำให้ "โครงช่อง" เป็น section เดียวใช้ร่วมกันทั้ง 2 โหมด: ทั้งคู่แก้จำนวนแถว/จำนวนช่อง/สัดส่วนได้ที่นี่ ต่างกันแค่สิ่งที่วาดทับ (AUTO = canvas เรนเดอร์ข้อความปุ่ม, CUSTOM = ภาพที่ร้านอัปโหลด)

**2. เทมเพลตสำเร็จ 6 แบบ — เปลี่ยนบทบาทจาก "ทางเลือกหลัก" เป็น "จุดเริ่มต้นที่ไฮไลต์แบบ live"**
กดแล้ว **เซต** `layout` เป็นเวอร์ชันน้ำหนักเท่ากันทันที (`h=1` ทุกแถว, `cols` เป็น `1` ซ้ำตามจำนวนช่องของแถวนั้น — คณิตเดียวกับพฤติกรรมเดิมทุกประการ เพราะน้ำหนักเท่ากันหมด = แบ่งเท่ากันแบบเดิม) ไม่ใช่ "ล็อกโหมด" อีกต่อไป — กดแล้วยังปรับสัดส่วน/เพิ่มลดช่องต่อได้เสมอ
🔑 **ใช้ `matchPresetKey(layout)` ไฮไลต์ชิปแบบ live** — ไม่ใช่แค่ตอนกด: ถ้าปรับสเต็ปเปอร์จนน้ำหนักไม่ตรงกับเทมเพลตไหนเลย ไฮไลต์หายไปเอง (คืน `null`) และถ้าบังเอิญปรับจนตรงกับอีกเทมเพลตพอดี ก็ไฮไลต์ชิปนั้นแทน — สื่อสารตรงกับความจริงตลอดเวลา ไม่ใช่ "จำ" ว่าผู้ใช้เคยกดอะไร

**3. Row card — หน่วยของการแก้คือ "แถว" + จุดที่ตอบโจทย์ "เพิ่ม/ลดช่อง = ปุ่มเปลี่ยนทันที"**
แถวละ 1 การ์ดยึด `sibling-surface-parity` (ภาษาการ์ดแยกใบแบบ `/orders`/`/products`) แต่ละใบมี: สเต็ปเปอร์ "ความสูงของแถวนี้" (คุม `h`) → เส้นคั่น → รายชื่อ "ช่อง" ในแถวนั้น แต่ละช่องมีสเต็ปเปอร์ "ความกว้าง" ของตัวเอง (คุม `cols[i]`) → ปุ่ม "+ เพิ่มช่องในแถวนี้" → ปุ่มลบทั้งแถว (ถังขยะ มุมขวาล่าง)
การซ้อนกันแบบนี้ (คุม `h` ที่หัวการ์ด, คุม `cols[i]` ในตัวช่องข้างใน) คือคำตอบของ "สื่อยังไงว่าอันนี้ทำกับแถวไม่ใช่ทั้งใบ" — ตำแหน่งใน DOM สื่อ scope เอง ตรงกับโครงข้อมูลจริง `{h, cols}[]` ที่แยกแกน Y/X อยู่แล้ว
ส่วนที่ตอบโจทย์ "จำนวนปุ่มต้องเท่าจำนวนช่องเป๊ะ": เพิ่ม/ลบช่องในการ์ดนี้แก้ `cellCount` โดยตรงและสะท้อนไปยัง section "แก้ข้อความบนปุ่ม" **ทันที** (ไม่ต้องกดบันทึกก่อน) — ผู้ขายเห็นผลจริงว่ารายการปุ่มเปลี่ยนพร้อมกับที่เขาเพิ่ม/ลดช่อง ไม่ใช่เห็นทีหลังตอน error ตอนกดบันทึก (กลไก confirm+undo อยู่ที่ flow ข้อ 5-6)

**4. สเต็ปเปอร์ — ไม่ใช่การลากเส้น**
ปุ่ม `−`/`+` ข้างตัวเลขเปอร์เซ็นต์ (คำนวณสดจาก `h / Σh` หรือ `cols[i] / Σcols` ไม่โชว์คำว่า "น้ำหนัก"/"หน่วย"/เลขดิบ 1–12 ให้เห็นเลย — พูดแค่ %) เป็นกลไก**หลักและใช้ได้ทุกจอเหมือนกันทุกประการ** แต่ละแตะ = `±1` หน่วยน้ำหนัก (ช่วง 1–12) `−` หยุดที่ 1, `+` หยุดที่ 12 — ดู Design decisions ข้อ 1 และ Open questions ข้อ 1 (long-press)

**5. ตัวนับช่อง + เพดาน 2 ชั้น**
หัว section โชว์ "N ช่อง" เสมอ (`text-xs tabular-nums`, ปกติ `text-default-400` — คัด pattern จากตัวนับ `chatBarLen` เดิมในไฟล์นี้) เพดานมี **2 ชั้นที่ต้องแยกกันสื่อสาร**: (ก) รวมทั้งเมนู ≤20 ช่อง (ข) แถว ≤10 และช่องต่อแถว ≤10 — ปุ่ม "+เพิ่มช่องในแถวนี้"/"+เพิ่มแถวใหม่" อาจถูก disable ด้วยเหตุผลคนละอย่าง ต้องมี caption แยกให้ชัด (ดู Content outline)

**6. ป้ายเตือนช่องเล็กเกินนิ้ว**
ช่องที่คำนวณแล้วสัดส่วน < ~12% ของแกนนั้น ได้ `ring-1 ring-warning` ที่ตัวสเต็ปเปอร์ + แคปชัน "ช่องนี้เล็กมาก ลูกค้าอาจกดพลาดบนมือถือ" — **เตือน ไม่บล็อก** ด้วยช่วงน้ำหนัก 1–12 ที่กว้าง เคสนี้เกิดได้ง่ายกว่าที่คิด (เช่นแถวเดียวมี 5 ช่อง น้ำหนัก 8/1/1/1/1 = ช่อง 2-5 เหลือ ~8% ต่อช่อง) — ยิ่งตอกย้ำว่าต้องมีจริง ไม่ใช่แค่ทฤษฎี

**7. โหมด CUSTOM — ภาพของร้านต้องอยู่ใต้เส้นแบ่งตลอดเวลา (ตอบโจทย์ข้อ 5)**
กลไกนี้**มีอยู่แล้วในโค้ดปัจจุบัน** ไม่ต้องสร้างใหม่: `customUrl` (ภาพที่อัปโหลด) วาดเป็น `<img>` ชั้นล่าง แล้ว overlay เส้นแบ่ง (`CELL_BOX`/`CELL_BOX_FOCUS`, `pointer-events-none absolute inset-0`) วาดทับด้วยพิกัดเปอร์เซ็นต์จาก `layoutBounds()` ชั้นบน — งานนี้แค่เปลี่ยนสิ่งที่ป้อนเข้า `layoutBounds()` จาก column-count มาเป็น weight object เท่านั้น ภาพต้นทางไม่ถูกแตะหรือซ่อนเลยไม่ว่าจะปรับสัดส่วนกี่ครั้ง — สวิตช์ "แสดงเส้นแบ่งช่อง" (`showGrid`) เดิมยังคงอยู่ และควรตั้ง `true` อัตโนมัติทุกครั้งที่โครงช่องถูกแก้ (ไม่ใช่แค่ตอนอัปโหลดครั้งแรกแบบเดิม) เพื่อให้ร้านเห็นผลทันทีว่าเส้นขยับตรงกับภาพตัวเองไหม

### User flow

1. ผู้ขายเปิดหน้าเดิม (AUTO หรือ CUSTOM) → เห็น section "โครงช่อง" ใหม่ต่อจาก "แหล่งภาพเมนู"
2. (ไม่บังคับ) กดชิปเทมเพลต → `layout` ถูกเซตเป็นน้ำหนักเท่ากันทันที (พฤติกรรมเดิม 100%) — ชิปนั้นไฮไลต์ (`matchPresetKey()` ตรง) — พรีวิวอัปเดตทันที
3. กด `+`/`−` ที่สเต็ปเปอร์ "ความสูงของแถวนี้"/"ความกว้างของช่องนี้" → % ที่แสดงขยับตามน้ำหนักใหม่ (แถว/ช่องอื่นในแกนเดียวกันหด/ขยายชดเชยอัตโนมัติ), ชิปเทมเพลตที่เคยไฮไลต์ดับลงทันทีถ้าไม่ตรงแล้ว, พรีวิวรีเฟรชสด
4. กด "+ เพิ่มช่องในแถวนี้" → ช่องใหม่เกิดในแถวนั้นด้วยน้ำหนัก `1`, ได้ปุ่ม default "คุยกับแอดมิน" (action ที่ทำงานได้จริงเสมอ), ป้ายข้อความว่าง → เห็น `is-invalid` แดงทันที (behavior เดิมของฟอร์ม label ที่มีอยู่แล้ว), section "แก้ข้อความบนปุ่ม" ได้แถวใหม่ทันทีในตำแหน่งที่ถูกต้อง (แทรกตาม global index ของช่องนั้น) — ปุ่มนี้ปิดเองถ้าแถวนั้นครบ 10 ช่อง หรือรวมทั้งเมนูครบ 20
5. กดถังขยะที่หัวแถว → ถ้าทุกช่องในแถวยังเป็น default ("คุยกับแอดมิน" ไม่เคยแก้ label) → ลบทันที ไม่มี confirm; ถ้ามีช่องไหนถูกแก้ label หรือมี action พิเศษ (uri/postback/ฯลฯ) → `pacesConfirm.warning` บอกรายการ action ที่จะหาย → ยืนยันแล้วลบ (label ในช่อง "แก้ข้อความบนปุ่ม" หายไปพร้อมกัน)
6. ลบไปแล้ว 6-10 วิ มีแถบ "ลบแถวที่ 2 แล้ว — เลิกทำ" ปักไว้เหนือรายการแถว (undo ระดับ session เท่านั้น คืนทั้งโครงช่อง+label ที่หายไปพร้อมกัน — หายไปเองเมื่อพ้นเวลาหรือกด "บันทึกร่าง")
7. รายการช่องที่เพิ่ม/ลบสะท้อนไป section "แก้ข้อความบนปุ่ม" ทันที (จำนวนอินพุตตาม cellCount ใหม่ = ผลรวมของทุก `cols[i]` ในทุกแถว) — flow เดิมของ label editing/chatBarText/บันทึก/เปิดใช้ **ไม่เปลี่ยน**

### Content outline (ภาษาไทย)

- หัวข้อ section: **"โครงช่อง"**
- ตัวนับ (ต่ำกว่าเพดาน): **"{n} ช่อง"** — (ถึงเพดาน 20): **"{n} / 20 ช่อง"** สีเปลี่ยนเป็น `text-danger-ink`
- หัวข้อย่อยเทมเพลต: **"เริ่มจากเทมเพลต"**
- แถว: **"แถวที่ {n}"**
- label สเต็ปเปอร์แถว: **"ความสูงของแถวนี้"**
- label สเต็ปเปอร์ช่อง: **"ช่อง #{n} · ความกว้าง"** (`#{n}` = เลขลำดับ global เดียวกับ badge วงกลมบน preview overlay และเลขในลิสต์ "แก้ข้อความบนปุ่ม" — ไม่ใช้เลขนับใหม่ต่อแถว กันสับสนสองระบบเลข)
- ปุ่มเพิ่มช่อง: **"+ เพิ่มช่องในแถวนี้"**
  - disabled เพราะแถวเต็ม: caption **"แถวนี้เต็ม 10 ช่องแล้ว"**
  - disabled เพราะรวมเต็ม: caption **"เมนูนี้ครบ 20 ช่องแล้ว"**
- ปุ่มเพิ่มแถว: **"+ เพิ่มแถวใหม่"**
  - disabled เพราะแถวครบ: caption **"ครบ 10 แถวแล้ว"**
  - disabled เพราะรวมเต็ม: caption **"เมนูนี้ครบ 20 ช่องแล้ว"**
- aria-label ปุ่ม `−`: **"ลดความสูงแถวที่ {n}"** / **"ลดความกว้างช่อง #{n}"**
- aria-label ปุ่ม `+`: **"เพิ่มความสูงแถวที่ {n}"** / **"เพิ่มความกว้างช่อง #{n}"**
- ปุ่มลบแถว aria-label: **"ลบแถวที่ {n}"**
- แคปชันช่องเล็ก: **"ช่องนี้เล็กมาก ลูกค้าอาจกดพลาดบนมือถือ"**
- confirm ลบแถวที่มี action ผูกอยู่ (หัวเรื่อง): **"ลบแถวที่ {n}?"**
  เนื้อหา (ประกอบจาก `ACTION_HINT`): **"ช่องนี้ {ACTION_HINT[type]} อยู่ — ลบแล้วจะต้องตั้งค่าปุ่มนี้ใหม่ทั้งหมด"** (ต่อท้ายทีละช่องถ้ามีหลายช่อง)
- ปุ่ม confirm: **"ลบแถวนี้"** / **"ยกเลิก"**
- แถบ undo: **"ลบแถวที่ {n} แล้ว"** + ลิงก์ **"เลิกทำ"**
- ป้ายหัวข้อเมื่อไม่ตรงเทมเพลตไหนเลย (`matchPresetKey()===null`): **"โครง {จำนวนแถว} แถว {จำนวนช่อง} ช่อง — ปรับเอง"**

### Edge states ที่ต้องออกแบบ

- **แถวเดียว/ช่องเดียว (โครง "เต็มใบ"):** ปุ่มลบแถวนั้นถูก `disabled` (ต้องมีอย่างน้อย 1 แถว 1 ช่องเสมอ) — ไม่ซ่อนปุ่ม ใช้ `disabled opacity-50` ตาม convention เดิม
- **แถวเต็ม 10 ช่อง (per-row cap):** เฉพาะปุ่ม "+เพิ่มช่องในแถวนี้" ของแถวนั้น `disabled` — แถวอื่นยังเพิ่มได้ปกติถ้ารวมยังไม่ถึง 20
- **ครบ 10 แถว (row cap):** ปุ่ม "+เพิ่มแถวใหม่" `disabled` — ช่องในแถวที่มีอยู่ยังเพิ่ม/ลดได้ปกติถ้ารวมยังไม่ถึง 20
- **รวมทั้งเมนูครบ 20 ช่อง (global cap):** ทุกปุ่ม "+เพิ่มช่อง"/"+เพิ่มแถวใหม่" ทุกจุด `disabled` พร้อมกัน ตัวนับหัว section ขึ้น "20 / 20 ช่อง" สีแดง — เพดานนี้ชนะทุกกรณี
- **น้ำหนักถึงเพดาน 1 หรือ 12:** ปุ่ม `−`/`+` ของสเต็ปเปอร์นั้น `disabled` เฉพาะฝั่งที่ชนเพดาน
- **ช่องเล็กกว่าเกณฑ์นิ้ว (~12% ของแกน):** เตือนด้วย ring สีส้ม + แคปชัน ไม่บล็อก (เกิดง่ายขึ้นเมื่อน้ำหนักต่างกันมาก — ดู Design decisions ข้อ 5)
- **ลบแถวที่ผูก action พิเศษ:** confirm ก่อนเสมอ (ดู flow ข้อ 5)
- **สลับโหมด AUTO ↔ CUSTOM หลังปรับโครงช่องแล้ว:** `layout` เป็น **state เดียวใช้ร่วมกัน** ไม่ล้างเมื่อสลับโหมด — โหมด CUSTOM ที่ยังไม่มีภาพยังโชว์ placeholder เดิม แต่เส้นแบ่งช่อง preview รอจนมีภาพก่อนจึงวาดทับ
- **เทมเพลตที่เลือกไว้ถูกแก้จนไม่ตรงกับ preset เดิมแล้ว:** ใช้ `matchPresetKey(layout) === null` เป็นตัวตัดสิน (ไม่ต้อง diff เอง — dev มี API ให้แล้ว) แล้วสลับ `templateTitle` เป็นข้อความ generic ตาม Content outline
- **โหลด/error/ว่างเปล่า:** ไม่มี network call ระหว่างแก้โครงช่อง (state ล้วน client-side เหมือน labels ปัจจุบัน) — error เดียวที่เกี่ยวคือ validation ตอนกด "บันทึกร่าง"/"เปิดใช้เมนู" (`hasEmptyLabel`, `chatBarOver`, cellCount>20) ใช้กลไก `canSubmit` เดิม ขยายเงื่อนไขเพิ่ม
- **จอกว้าง 1440+ (anti-slop #9):** คอลัมน์ขวา (พรีวิว) เป็น `sticky` แต่ไม่ยืดเต็มความสูงว่างเปล่า — คอลัมน์ซ้าย (โครงช่อง) ยาวขึ้นตามจำนวนแถว/ช่องจริง ลดปัญหาคอลัมน์ซ้ายสั้น/ขวายาวที่เคยมีในฟอร์มสั้น ๆ

### Impeccable compliance

- **Mode: Operate** (อ่าน `~/.claude/skills/impeccable/reference/operate.md` แล้ว) — นี่คือ product tool ของผู้ขาย ไม่ใช่ brand surface: เกณฑ์คือ "category-fluent user ไว้ใจได้ทันที" ไม่ใช่ความแปลกใหม่ ทุก control ในสเปกนี้ (สเต็ปเปอร์ `−`/`+`, การ์ดแยกใบ, ปุ่ม→confirm) **ไม่ประดิษฐ์ affordance ใหม่เลย** — เป็นการเรียงวัสดุที่มีอยู่แล้วในไฟล์เดียวกัน/หน้าพี่น้อง (`/orders`,`/products`) ตรงกับ craft-floor.md ("ไม่ปั้น custom form control เพื่อความแปลกใหม่") และ operate.md ("Consistency over surprise")
- **One Voice (primary ≤10% จอ):** `bg-primary` ปรากฏเฉพาะ (ก) ปุ่ม "เปิดใช้เมนู" (เดิม) (ข) badge เลขวงกลม บน preview overlay (เดิม) (ค) ring โฟกัสของสเต็ปเปอร์ที่กำลังโฟกัส (ใหม่ — ชั่วขณะเท่านั้น) (ง) ชิปเทมเพลตที่ `matchPresetKey()` ตรง (`primary/15` บาง ไม่ทึบ, ไม่ตายตัว — ดับเมื่อไม่ตรง) — สเต็ปเปอร์/การ์ดแถว/ปุ่มเพิ่มแถว-ช่องทั้งหมดเป็นโทนกลาง (`bg-light`, `text-default-700`) โดยตั้งใจ **ไม่ให้ตัวเครื่องมือแย่งซีนพรีวิว**
- **พระเอกของหน้า = พรีวิว ไม่ใช่ตัวควบคุมโครงช่อง** — โครงช่อง/สเต็ปเปอร์คือ "เครื่องมือ" ต้องหายไปในงาน (Product Principle #4) ส่วนภาพพรีวิวคือ "ผลลัพธ์ที่ลูกค้าจะเห็นจริง" ต้องเด่นที่สุดเสมอ — งานนี้ไม่ย้ายตำแหน่งพรีวิวเลย (เดสก์ท็อป: sticky คอลัมน์ขวา; มือถือ: ท้ายสุดก่อนปุ่ม action)
- **Verified-Means-Green:** ไม่มีจุดไหนในสเปกนี้ใช้เขียว — สถานะ "ลูกค้าเห็นเมนูนี้อยู่" (เขียวเดิม, จุดเดียวที่อนุญาต) ไม่ถูกแตะ ป้ายเตือนช่องเล็กใช้ **warning (ส้ม)** ไม่ใช่เขียว/แดง เพราะเป็นคำเตือนที่ยังกดใช้งานได้ (ไม่ใช่ error ที่บล็อก) — ตรง precedent BR-RSV-18 (00024): "เต็มแล้ว" = คำเตือนไม่ใช่ตัวบล็อก
- **Sentence case:** ทุก label ที่เขียนในสเปกนี้เป็นประโยคปกติ ไม่มี ALL CAPS
- **เงาผสมหมึก / anti-slop อื่น:** row card ใช้ `.card` มาตรฐาน Paces (เงา `--shadow` ผสมหมึกเทาอมน้ำเงินอยู่แล้วตาม token) — ไม่มี custom shadow/gradient ใหม่ ไม่มี hero-metric template ไม่มี eyebrow ตัวพิมพ์เล็ก
- **น้ำเสียง:** confirm ลบแถวบอกผลลัพธ์ตรง ๆ ("ต้องตั้งค่าปุ่มนี้ใหม่ทั้งหมด") ไม่ใช้ราชการ ("ไม่สามารถกู้คืนได้"), แคปชันช่องเล็กบอกผลที่จะเกิด ("ลูกค้าอาจกดพลาด"), caption disable บอกเหตุผลตรงตามเพดานจริง ไม่ใช่ "ไม่สามารถเพิ่มได้"
- **จุดที่ theme ขัดกับ Impeccable และคำตัดสิน:** ไม่มีจุดขัดจริงในส่วน required v1 — ทุก primitive ที่ใช้ (`.card`,`.btn.btn-icon`,`pacesConfirm`) เป็น token ที่ประกาศแล้วทั้งใน DESIGN.md/design.json (paces-card, paces-button-primary) และ paces-component-reference.md ครบ ไม่ต้องใช้ arbitrary value เลย จุดเดียวที่มีความเสี่ยงคือ **divider-drag บน preview (Phase 2)** ซึ่งต้องแต่ง ARIA slider เอง — จึงแยกเป็น optional/deferred ไม่รวมเป็น required

### Design decisions + rationale

1. **ทำไมไม่ใช้ "ลากเส้นแบ่ง" เป็นกลไกหลัก แต่ใช้สเต็ปเปอร์แทน** — ลากเส้นบางบนภาพที่ย่อจาก 2500px ลงมาเหลือ ~340px (สเกล ~7.3 เท่า) ด้วยนิ้วเป็นงานที่แม่นยำยาก และเส้นแบ่งระหว่างแถว/ช่องตั้งแต่ 3 ตัวขึ้นไปต้อง "ลากขอบเขตระหว่างคู่ที่ติดกัน" ซึ่งซับซ้อนกว่า native `<input type="range">` (thumb เดียว) รองรับ — ต้องประดิษฐ์ custom ARIA slider หลายตัว ขัด craft-floor.md ("Reinventing standard affordances") **สเต็ปเปอร์ `+`/`−` แก้ได้พร้อมกัน:** ใช้เหมือนกันทุกจอ 100%, tap target คุมด้วย `min-h-11` ที่มีอยู่แล้ว, mental model อิสระต่อ cell ตรงกับ `{h, cols}[]` เป๊ะ, การันตีโครงสร้างเหมือนเดิม (ไม่มีรูโหว่/ช่องซ้อน) — ลากบนพรีวิวยังมีประโยชน์จริงสำหรับ CUSTOM แต่เก็บเป็น**ทางเข้าเสริมเดสก์ท็อป (`lg:`) เท่านั้น** แนะนำเลื่อนไป Phase 2
2. **ทำไมสเต็ปเปอร์แสดงแค่ % ไม่แสดงเลขน้ำหนักดิบ (1–12)** — PRODUCT.md ผูกกลุ่มผู้ใช้ digital-literacy ต่ำ/ผู้สูงวัย และ frontend-design skill สั่งเขียนจาก "ฝั่งผู้ใช้ปลายทาง ไม่ใช่จากวิธีที่ระบบสร้าง" — เลข "1–12" เป็นรายละเอียด implementation ที่ไม่ต้องรู้
3. **ทำไมเทมเพลต 6 แบบไม่หายไป แต่ลดความสำคัญลง** — ลบทิ้งจะเสียทางลัดของร้านส่วนใหญ่ แต่ให้ยัง "ล็อกโหมด" จะขัดกับ feature request ตรง ๆ จึงเปลี่ยนเป็น**ตัวเซตค่าเริ่มต้นที่กดได้ตลอดเวลา ไม่ผูกโหมด** ไฮไลต์แบบ live ด้วย `matchPresetKey()` — เดิมเห็นเฉพาะ CUSTOM งานนี้ AUTO ได้ด้วย เป็นการยกระดับต่อเนื่อง ไม่ใช่ scope creep
4. **ทำไม "ลบแถว" ไม่ใช้ `⋯`/hs-dropdown** — มี action เดียวต่อแถว (ลบ) การยัด `⋯` ที่มีตัวเลือกเดียวเพิ่มคลิกโดยไม่ได้อะไร อีกทั้ง row list เป็น dynamic list ที่ `hs-dropdown` มีบันทึกไว้แล้วว่าพังจริง (§3 caveat ของ paces-component-reference.md) — ปุ่มถังขยะเดี่ยว + `pacesConfirm` ตรงกับกฎมากกว่า
5. **ทำไมช่องเล็กกว่านิ้ว "เตือน" ไม่ "บล็อก"** — ต่างจากรูโหว่/ช่องซ้อน (เป็นไปไม่ได้อยู่แล้วในโมเดล weighted-grid) ช่องเล็กยัง**กดโดนได้จริง**เพียงยากขึ้น — สอดคล้อง precedent BR-RSV-18 (00024) การบล็อกจะทำให้ร้านที่ตั้งใจเน้นปุ่มเดียวจริง ๆ ทำไม่ได้เลย
6. **ทำไมต้องมี confirm+undo แยกสองชั้นตอนลบ** — BR-RM-03 บอกว่าร้านแก้ **label** ได้อย่างเดียว action type ไม่ถูกแก้เอง ช่องที่ถูกลบแล้วเพิ่มใหม่ได้ action ตั้งต้นเสมอ **ไม่มีทางเอา action พิเศษกลับมาได้เอง** — **confirm** ป้องกันลบผิดโดยไม่ตั้งใจ, **undo ระดับ session** ป้องกันเคส "กดผิดแถว" โดยไม่ต้องเปิด confirm ซ้ำ — undo หายหลัง "บันทึกร่าง" เพราะค่าถูกส่งขึ้น LINE จริงแล้ว

### Anti-slop self-check

1. **เอาไปใช้กับสินค้าอื่นได้ทันทีไหม** — ไม่ได้ เฉพาะเจาะจงกับข้อจำกัดจริงของ LINE Rich Menu + lib จริง (น้ำหนัก 1–12, แถว≤10, ช่อง/แถว≤10, รวม≤20, `matchPresetKey()`, BR-RM-03) ผูกกับ `RichMenuEditor.tsx` ที่มีอยู่ก่อน
2. **มีของเด่นที่สุด 1 อย่างต่อจอไหม** — มี: พรีวิว (sticky ขวาเดสก์ท็อป/ท้ายสุดก่อนปุ่ม action มือถือ) โครงช่อง/สเต็ปเปอร์ตั้งใจโทนกลาง ไม่แย่งซีน
3. **มีอะไรซ้ำ/ค่าคงที่ที่ควรตัด** — ไม่มี ทุก element ทำงานจริง
4. **state ครบไหม** — ครบ: แถว/ช่องเดียว, per-row cap, row cap, global cap, น้ำหนักชน 1/12, ช่องเล็กกว่านิ้ว, ลบมี action ผูก vs ไม่มี, สลับโหมดไม่ล้าง state, จอกว้าง 1440+
5. **copy บอกสิ่งที่ระบบทำได้จริงไหม** — ใช่: caption disable บอกเหตุผลตรงตามเพดานจริง, confirm บอกผลลัพธ์จริง
6. **คำเดียวกันหมายถึงของเดียวกันทั้งสเปกไหม** — "ช่อง" ใช้คำเดียวกับที่มีอยู่แล้วในไฟล์ ไม่ปน "คอลัมน์"/"เซลล์"/"บล็อก" (HR16); เลข `#{n}` อ้างระบบเดียวกับ badge preview + label list
7. **สีสื่อความหมายถูกไหม** — เขียวไม่ถูกแตะ คำเตือนช่องเล็กใช้ส้มไม่ใช่แดง/เขียว
8. **แตะได้จริงบนมือถือไหม** — สเต็ปเปอร์ทุกปุ่ม `min-h-11` (44px)
9. **จอกว้าง 1440 คอลัมน์ไหนว่างเปล่า** — คอลัมน์ซ้ายยาวขึ้นตามจำนวนแถว/ช่องจริง

### Open questions (ให้เจ้าของโปรเจกต์ตัดสิน)

1. **ปุ่ม `+`/`−` ควรมี long-press เร่งความเร็วไหม** — ช่วงน้ำหนัก 1–12 กว้าง ไล่ 1→12 ต้องแตะ 11 ครั้งถ้าไม่มี long-press แนะนำเพิ่ม "กดค้าง = เร่งความเร็วหลัง ~500ms" แต่เป็นความซับซ้อนที่ควรยืนยันว่าคุ้มไหมสำหรับ v1
2. **ทำ divider-drag บน preview (เดสก์ท็อป) รอบนี้เลย หรือ Phase 2** — สเต็ปเปอร์ทำให้ v1 ใช้งานครบ 100% โดยไม่ต้องมี drag; drag ต้องแต่ง ARIA slider ใหม่ทั้งชุด แนะนำ Phase 2 แต่ user request พูดถึงลากเส้นตรง ๆ
3. **แถว/ช่องเรียงลำดับใหม่ได้ไหม (reorder)** — สเปกนี้ตั้งสมมติฐานลำดับคงที่ตามลำดับสร้าง ไม่มี drag-to-reorder เพราะไม่ถูกถามและเพิ่มความซับซ้อนสูง
4. **เกณฑ์ "เล็กกว่านิ้ว" ~12%** ยืมมาจากต้นแบบ freeform เดิม — เหมาะสมข้ามสองโมเดลไหม หรือควรคำนวณใหม่
5. **ต้องแก้ SRS/PRD ของ 00045 ไปด้วยไหม (HR11)** — โครงข้อมูลเปลี่ยนจาก `number[]` เป็น `{h, cols}[]` และ BR-RM-03 ("ร้านแก้ได้แค่คำ") ตอนนี้ต้องเติมว่าร้านแก้ **โครงช่อง** ได้ด้วย — ต้องมี BRD/PRD ส่วนขยายก่อน implement ไหม
