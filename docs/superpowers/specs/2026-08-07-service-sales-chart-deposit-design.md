## 1. ปัญหา

การ์ด "ยอดขาย" บน Mobile Command Center ของร้านบริการ ยืมชุดคำของร้านขายออนไลน์มาทั้งชุด —
**ยืนยันแล้ว / รอยืนยัน / จำนวนการเข้ารับบริการ** ซึ่งเป็นสถานะของ "การส่งของ" ไม่ใช่จังหวะเงินของงานบริการ

ร้านบริการรับเงินเป็น **2 จังหวะ**: มัดจำตอนจอง แล้วส่วนที่เหลือตอนลูกค้ามาถึงหน้างาน
กราฟเดิมไม่มีที่ให้ความจริงข้อนี้อยู่เลย — ยอดเต็มของงานถูกโยนลงวันที่สร้างออเดอร์ทั้งก้อน
ทั้งที่เงินส่วนใหญ่ยังไม่เข้ามือ

## 2. สิ่งที่ต้องได้

1. แท่ง **มัดจำ** (เหลือง) — เงินก้อนแรกที่เข้าจริง
2. แท่ง **เสร็จสิ้น** (เขียว) — ลูกค้ามาตามนัดและร้านกดปิดงานแล้ว
3. แท่ง **วันเข้ารับบริการ** (โปร่งลายทาง) — ยอดล่วงหน้าว่าวันนัดนั้นจะได้อีกกี่บาท **หักมัดจำที่รับไปแล้ว** และหายไปเองเมื่อลูกค้ามาจริง
4. **เลขฮีโร่ = เงินที่ได้รับจริง ณ วันนั้น/เดือนนั้น ไม่รวมยอดในอนาคต**

## 3. สิ่งที่พบระหว่างสำรวจ (เปลี่ยนขนาดงาน)

### 3.1 🛑 ปุ่ม "เสร็จสิ้น" ไม่มีอยู่จริงในระบบ

feature 00024 ทำครบถึงชั้น API แล้ว:

- `setAppointmentOutcome()` — `src/services/appointment.service.ts:305`
- `POST /api/orders/[token]/appointment/outcome` — route มีจริง, Valibot schema มีจริง (`validations.ts:1572`)

แต่ **ไม่มีหน้าจอไหนเรียกเลยสักที่** — `rg "appointment/outcome" --glob '*.tsx'` คืน 0
หน้าเดียวที่แตะ `appointmentStatus` ฝั่ง seller คือ `queues/components/AppointmentCalendar.tsx`
ซึ่งใช้แค่ทาสี event ไม่มี action ให้กด

**ผลถ้าไม่ทำ:** `appointmentStatus` ไม่มีทางเป็น `COMPLETED` → แท่งเขียว "เสร็จสิ้น" เป็น 0 ตลอดกาล
= ไทล์ที่ตายตั้งแต่วันเปิด (บทเรียนเดียวกับ `feedback_dead_tile_change_what_it_counts`)

### 3.2 ระบบไม่รู้ว่ามัดจำเข้ามือหรือยัง

`Order.depositAmount` เป็น snapshot ยอดที่ควรเก็บ (BR-RSV-46) — ไม่มีคอลัมน์บอกว่าได้รับแล้วหรือยัง
และงานบริการ **ไม่มีขั้นแนบสลิปโดยตั้งใจ** (BR-RSV-49/50 — มัดจำไม่กั้นการกันคิว)
ป้ายในฟอร์มเขียนว่า "มัดจำที่เก็บ" ซึ่งกำกวมระหว่าง "จะเก็บ" กับ "เก็บแล้ว"

**มติ user:** ต้องมีการยืนยันก่อนถึงจะนับเป็นเงินเข้า → ต้องมีคอลัมน์ใหม่

## 5. นิยามตัวเลข (SSOT)

> ทุกสูตรด้านล่างมีเงื่อนไขร่วม: `Order.status != 'CANCELLED'` และ `Shop.vertical === 'SERVICE_QUEUE'`
> คำว่า "มัดจำที่รับแล้ว" = `depositReceivedAt != null ? depositAmount : 0`

| ชั้น | ยอด | ลงตะกร้าวันไหน |
|---|---|---|
| **มัดจำ** (warning ทึบ) | `Σ depositAmount` เฉพาะใบที่ `depositReceivedAt != null` | วันของ **`depositReceivedAt`** (วันที่เงินเข้าจริง) |
| **เสร็จสิ้น** (success ทึบ) | `Σ (totalAmount − มัดจำที่รับแล้ว)` | **มีนัด:** วันของ `serviceStart` เมื่อ `appointmentStatus = 'COMPLETED'`<br>**ไม่มีนัด:** วันของ `createdAt` (D-5) |
| **วันเข้ารับบริการ** (primary ลายทาง) | `Σ (totalAmount − มัดจำที่รับแล้ว)` ของนัดที่ `appointmentStatus ∉ {COMPLETED, NO_SHOW}` | วันของ `serviceStart` · **`serviceStart` ≥ วันนี้** |
| **เลยวันนัด** (danger ลายทาง) | สูตรเดียวกัน | วันของ `serviceStart` · **`serviceStart` < วันนี้** |

**เลขฮีโร่ / ยอดรวม** = `มัดจำ + เสร็จสิ้น` เท่านั้น — ไม่รวม 2 ชั้นลายทาง

### 5.1 สมบัติที่ตามมาเอง (ไม่ต้องเขียนกฎเพิ่ม)

- **ไม่มีการนับซ้ำ** — เงินก้อนเดียวลงได้ตะกร้าเดียวเสมอ: มัดจำลงวันรับมัดจำ, ส่วนที่เหลือ (`total − มัดจำ`) ลงวันปิดงาน
- **`NO_SHOW` หายจากกราฟเอง** — มัดจำที่ริบไว้ยังนับอยู่ (เข้าไปแล้วตั้งแต่วันรับ) ส่วนที่เหลือไม่เคยถูกนับที่ไหนเลย แท่งลายทางหายไปพร้อมกัน
- **`RESCHEDULE_REQUESTED` ยังเป็นแท่งลายทาง** — ยังไม่ terminal เงินยังรออยู่ที่ `serviceStart` เดิม (BR-RSV-27: ขอเลื่อนไม่ย้ายเวลาจนกว่าร้านจะตัดสิน)
- **แท่งซ้อนกันได้ในวันเดียว** — ความสูงทั้งแท่ง = มูลค่างานของวันนั้น ส่วนที่ลายทางคือส่วนที่ยังไม่ได้รับ

### 5.2 จุดที่ต้องระวังตอนเขียน

- **ตะกร้าวันต้องตัดด้วยเวลาไทย** ทั้ง 3 คอลัมน์วันที่ (`depositReceivedAt` / `serviceStart` / `createdAt`) — ใช้ `thaiDayKey()` หรือ shift `TZ_OFFSET_MS` ชุดเดียวกับที่ `dashboard.service.ts` ใช้อยู่ ห้ามตัดด้วย UTC (บั๊กที่ 00033 เพิ่งแก้ไป)
- **`serviceStart` เป็น `Timestamptz(3)` ไม่ใช่ `@db.Date`** — ต่างจาก `checkIn` ของบ้านพัก ต้อง shift ก่อน bucket
- **ขอบเขต query กว้างขึ้น** — เดิม query แค่ `createdAt` ใน 2 เดือน ตอนนี้ต้องดึงใบที่ `serviceStart` ตกในเดือนนั้นด้วย (งานที่สร้างเดือนก่อนแต่นัดเดือนนี้) → เงื่อนไข `OR` 3 ทาง ไม่ใช่ `createdAt` อย่างเดียว
- **`prevTotalToDate` (ฐาน %เทียบเดือนก่อน) ต้องเปลี่ยนนิยามตาม** ไม่งั้นเทียบเลขคนละสูตร แล้ว % โกหก

## 6. ขอบเขตงาน

### A — คอลัมน์ + การรับมัดจำ

- migration เพิ่ม `Order.depositReceivedAt DateTime?` (additive, nullable, ไม่มี default)
  - 🛑 ถ้าจะเพิ่ม CHECK ต้องเขียนแบบ **additive อ่านของเดิมมาต่อท้าย** (`docs/conventions/migration-check-constraint-additive.md`)
- ฟอร์มสร้างงาน (`AppointmentBlock.tsx`) — checkbox "รับเงินมัดจำแล้ว" ติ๊กไว้เป็นค่าตั้งต้น (D-4)
  - ติ๊ก → `depositReceivedAt = Order.createdAt` (**ไม่ใช่ `now()`** — ออเดอร์ย้อนหลังตาม 00033 ต้องได้วันเดียวกับที่ผู้ขายระบุ ไม่งั้นมัดจำไปโผล่วันนี้ทั้งที่งานลงวันอื่น)
  - ไม่ติ๊ก → `null`
  - ซ่อนทั้ง checkbox เมื่อยอดมัดจำ = 0
- หน้ารายละเอียดงาน — ปุ่ม "รับมัดจำแล้ว" (set `= now()`) แสดงเมื่อ `depositAmount > 0 && depositReceivedAt == null`
- ฟอร์มแก้ไขงาน — ต้องไม่ทำให้ `depositReceivedAt` หายเงียบตอนแก้ยอดมัดจำ

### B — ปิดงาน (ต่อของที่มีอยู่แล้ว ไม่เขียน backend ใหม่)

- ปุ่ม **"เสร็จสิ้น" / "ไม่มาตามนัด"** ยิง `POST /api/orders/[token]/appointment/outcome` ที่มีอยู่แล้ว
- ข้อจำกัดที่ service บังคับอยู่แล้ว ต้องสะท้อนบน UI ไม่ให้ปุ่มโผล่ผิดจังหวะ:
  - กดได้ตั้งแต่ถึงเวลา `serviceStart` เป็นต้นไปเท่านั้น (BR-RSV-34 → `AppointmentNotStartedError`)
  - `COMPLETED`/`NO_SHOW` เป็น terminal กดซ้ำไม่ได้ (`AppointmentTerminalError`)
  - ไม่แตะ `Order.status` และไม่กระทบ Trust Score (BR-RSV-33/35)
- 🛑 **ตำแหน่งปุ่มทั้ง A และ B ต้องผ่าน `safepay-ux` ก่อน** (Hard Rule 8) และยึด `docs/conventions/seller-action-placement.md`
  — โดยเฉพาะ §5.1: หน้าที่เข้าโหมด full-screen ทำให้ `SellerBottomNav` หายทั้งก้อน

### C — กราฟ + ตัวเลข

- `dashboard.service.ts` — `SalesSeries` ได้ field ชุดใหม่สำหรับ `SERVICE_QUEUE`
  (คง `confirmedValues`/`unconfirmedValues` ไว้ให้ vertical อื่นใช้ต่อ ไม่รื้อ)
- `SalesChartCard.tsx` — 4 series ซ้อน + legend 4 ช่อง (ช่องแดงโผล่เฉพาะเมื่อมีนัดค้าง)
- `SalesChartSheet.tsx` — **ต้องเปลี่ยนตามในคอมมิตเดียวกัน** ใช้ `SalesSeries` ก้อนเดียวกับการ์ด ถ้าไม่แก้ การ์ดจะบอกเลขหนึ่ง ชีตบอกอีกเลขทั้งที่กดจากการ์ดใบนั้นเอง
- `sales/page.tsx` — เปลี่ยนนิยาม `revenue`/`unconfirmedRevenue` ตาม §5 (D-7)
- **ห้าม** hardcode สูตรซ้ำ — เขียนตัวตัดสินไว้ที่เดียว (`src/lib/service-revenue.ts`) แล้วให้ทุก surface เรียกตัวเดียวกัน ทำนองเดียวกับ `deriveShippingStage`/`countsAsRevenue`

## 7. ข้อที่ยังต้องเคาะตอน review

- **D-8 (ยังไม่เคาะ):** `/sales` มีคอลัมน์ "กำไรสุทธิ" ที่คำนวณจาก `revenue` ในแถวเดียวกัน (`revenue − COGS − expense`)
  พอ `revenue` เปลี่ยนเป็นเกณฑ์เงินสด กำไรในหน้านั้นก็ขยับตาม แต่การ์ด P&L ใน `/expenses` ยังใช้สูตรเดิม
  → **ข้อเสนอ:** ให้กำไรใน `/sales` เดินตาม `revenue` ใหม่ (ต้องบวกลบกันได้ในแถวเดียวกัน) แล้วบันทึกความต่างกับ `/expenses` ไว้เป็นหนี้ที่รู้ตัว
- **ป้ายคำ:** ร้าน `SERVICE_QUEUE` บางร้านอาจไม่เก็บมัดจำเลย — legend "มัดจำ 0" ทุกวันควรซ่อนทั้งช่องไหม
- **ประวัติ:** การกด "รับมัดจำแล้ว" / "เสร็จสิ้น" ควรลง `OrderEvent` ด้วยไหม (feature 00031 Order Activity Log) — ถ้าเอา = ชนิดใหม่ 2 ค่า และต้อง sync `docs/SRS.md`
