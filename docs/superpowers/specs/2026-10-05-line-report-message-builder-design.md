## 1. ข้อจำกัดของ LINE Flex กับ "rich text"

ตัวสร้างข้อความของ Deep ใช้ `type:'text'` ต่อบรรทัด ซึ่งกำหนดสไตล์ได้เป็น **ต่อ text component** คือ `weight` · `size` · `color`

> **อัปเดตหลังตรวจเอกสาร LINE (ดูหัวข้อ "ผลตรวจ span ของ LINE Flex" ท้ายไฟล์):** Flex มี component `span` ซ้อนใน `text.contents` จริง ⇒ ทำตัวหนา/สีเฉพาะคำที่เลือกในบรรทัดเดียวได้ mockup จึงแสดง toolbar แบบ "ทั้งบรรทัด" + "เฉพาะคำที่เลือก" (ยังจำกัดในชุดสีที่ปลอดภัยเดิม)

### 1.1 สไตล์ที่ builder เสนอ (และ map ไป Flex)

| ตัวควบคุม | ค่าที่เก็บ (key ไม่ใช่ hex) | Flex prop | หมายเหตุ |
|---|---|---|---|
| ตัวหนา (toggle) | `bold: boolean` | `weight: 'bold'` / `'regular'` | |
| ขนาด เล็ก | `size:'s'` | `size:'xs'` | ใช้เหมือนบรรทัดหมายเหตุของ builder |
| ขนาด ปกติ | `size:'m'` | `size:'sm'` | ค่าเริ่มต้น ตรงกับ `text()` ใน builder |
| ขนาด ใหญ่ | `size:'l'` | `size:'md'` | **ตั้งเพดานที่ `md` โดยตั้งใจ** ให้เท่าหัวรายงาน ไม่ใหญ่กว่า เพราะ "ยอดขาย (นับแล้ว)" และหัวรายงานต้องเป็นพระเอกของบับเบิล ข้อความของผู้ขายไม่ควรตะโกนทับ และพรีวิวไม่ต้องแก้ renderer (`TEXT_SIZE` มี xs/sm/md อยู่แล้ว) |
| สี ปกติ | `color:'ink'` | `FLEX_COLORS.INK` | ค่าเริ่มต้น |
| สี รอง | `color:'slate'` | `FLEX_COLORS.SLATE` | พรีวิว map → `text-default-700` ตาม `flex-preview-tokens` |
| สี เน้น | `color:'accent'` | `FLEX_COLORS.ACCENT` | น้ำเงิน seller `#236dc9` |

**ที่ไม่เสนอ พร้อมเหตุผลเฉพาะของ Deep:**
- **สีเขียว** — เขียวในรายงานนี้ = ยืนยันแล้ว ถ้าผู้ขายทาเขียวบน "ยอดขาย" ผู้อ่านจะเข้าใจว่าระบบยืนยัน (Verified-Means-Green)
- **สีแดง** — แดงในรายงานนี้ = "ดึงข้อมูลไม่สำเร็จ" จริงเท่านั้น (`DANGER` ที่ builder ใช้) ผู้ขายทาแดงจะทำให้ข้อความดูเหมือนระบบพัง
- **ขีดเส้นใต้** — อ่านเป็นลิงก์ ในแบรนด์ที่ต้านมิจฉาชีพ ข้อความที่ดูเหมือนลิงก์แต่ไม่ใช่ลิงก์คือความเสี่ยง (span รองรับ `decoration` แต่เราไม่เปิด)
- **ลิงก์ที่ผู้ขายกำหนดเอง** — ปุ่ม "เปิด Deep" ชี้ `sellerDashboardUrl()` ตายตัว ป้ายปุ่มแก้ได้ ปลายทางแก้ไม่ได้
- **อื่น ๆ** — ตัวเอียง · จัดชิด · พื้นหลัง · รูปภาพ · ตัวเลือก emoji (ผู้ขายพิมพ์ emoji เองในข้อความได้ตามปกติของ LINE ฝั่งเนื้อหาผู้ใช้ แต่ UI ของเราไม่มีตัวเลือก emoji ตาม HR12)

**ข้อจำกัดของข้อความอิสระ:**
- ≤ 120 ตัวอักษรต่อบล็อก
- ≤ 6 บล็อก
- รวมแล้ว bubble ต้อง ≤ 30,000 ไบต์ (เพดานเดิม `BUBBLE_MAX_BYTES`) วัดฝั่ง client ด้วย `TextEncoder` (ไม่ใช้ `Buffer`)
- ข้อความอิสระ **ไม่ถูกตัดทิ้งเงียบ ๆ** ตอน `fitToLimits` (ลำดับตัดคงเดิม: Top3 → ย่อรายร้าน → altText) ถ้ายังเกินให้บล็อก "บันทึก" ตั้งแต่ตอนแก้ ไม่ใช่ตอนส่ง

## 2. ส่วนที่ใช้ร่วมกันทุกทิศทาง

### 2.1 แคตตาล็อกบล็อก

คอลัมน์ "ล็อก?" = ลาก/เอาออกได้หรือไม่ · ค่าทั้งหมดมาจาก SSOT เดิม ห้ามคำนวณซ้ำในตัวจัดข้อความ

| บล็อก | แหล่งข้อมูล / SSOT | ล็อก? | ประเภทร้าน | หมายเหตุ |
|---|---|---|---|---|
| **หัวรายงาน** (ชื่อ + ช่วงวันที่ + "ข้อมูล ณ HH:MM น." + "รวม N ร้าน") | `titleOf()` / `titleOverride`, `rangeText(window)`, `formatTimeHM(computedAt)` | **ล็อก ตรึงบนสุด** เอาออกไม่ได้ ลากไม่ได้ (BR-LGS-08) | ทุกประเภท | แก้ได้เฉพาะ "ชื่อรายงาน" (ผ่าน `titleOverride` ที่มีอยู่) ช่วงวันที่และ "ข้อมูล ณ" แก้ไม่ได้ ป้าย "ทดสอบ" ของ kind TEST ใส่อัตโนมัติ รอบ 24:00 ใช้ชื่อ "สรุปวันที่ … (ครบทั้งวัน)" เมื่อไม่ override |
| **จำนวน{คำ}** | `combineTotals(shops).orders` + `reportOrderWord(shops)` | ไม่ล็อก | ทุกประเภท | label ผันตาม vertical: ขายออนไลน์ = คำสั่งซื้อ · ร้านบริการ = บริการ · บ้านพัก = บิลเข้าพัก · ผสม = **รายการ** (`MIXED_ORDER_WORD`) เก็บ key `orders_count` ไม่เก็บ label เพื่อไม่พังเมื่อเปลี่ยนร้านในกลุ่ม |
| **ยอดขาย (นับแล้ว) + ยังไม่นับ** | `t.confirmed`, `t.unconfirmed` ผ่าน `formatBaht` | ไม่ล็อก | ทุกประเภท | **ผูกเป็นบล็อกเดียว** ตามมติ OQ-1 บรรทัดรอง "ยังไม่นับเป็นยอดขาย ฿… (รอยืนยัน/รอขนส่งรับ)" ติดมากับบรรทัดหลัก แยกลากไม่ได้ เป็นตัวเดียวที่ตัวหนา |
| **ยกเลิก** | `t.cancelled` ("ใบที่เปิดในช่วงนี้", OQ-2) | ไม่ล็อก | ทุกประเภท | โทน neutral ไม่แดง |
| **รายร้าน** | `sortShops`, ต่อร้านมี `orders · confirmed`, `s.top3`, `s.profit` | ไม่ล็อก | ทุกประเภท | มีตัวเลือกย่อย 3 ตัว (ดู 2.1.1) กลุ่มร้านเดียว: ไม่มีหัว "แยกรายร้าน" และไม่มีแถวตัวเลขต่อร้าน เหลือเฉพาะ Top3/กำไร ตามที่ builder ทำอยู่ |
| **ยอดสะสมรอบนี้** | `cycleToDate.totals.confirmed` | ไม่ล็อก | ทุกประเภท | โผล่ใน palette เฉพาะเมื่อ `monthlyEnabled` และต้องมียอดขาย ส่งจริงเฉพาะรายวันที่ไม่ใช่รอบ 24:00 ผูกกับ `attachCycleToDaily` ถ้าบางร้านดึงไม่สำเร็จ ระบบเติมหมายเหตุ "ยอดรวมยังไม่ครบ…" เอง ทุกร้านล้ม = "ดึงข้อมูลไม่สำเร็จ" ไม่แสดง ฿0 |
| **กำไร** | `profitDisplay`, `s.profit`, `summary.profitSummable` | ไม่ล็อก แต่ **ต้องยืนยัน** (Swal warning) + แถบเตือนถาวร | ทุกประเภท (ผลต่างตามกติกา) | ยอดรวมกำไรแสดงเฉพาะ: หลายร้าน ∧ รวมกันได้ ∧ ไม่มีร้านล้ม ∧ ทุกร้านมีกำไร ร้านต่างกติกา = รายร้านเท่านั้น + หมายเหตุอัตโนมัติ |
| **หมายเหตุอัตโนมัติ** | `EXCLUDED_REASON` ("ไม่รวมร้าน X (ถูกล็อก/ถูกลบ)"), "ยอดรวมยังไม่ครบ…", "ยอดแต่ละร้านคิดตามกติกา…", "ค่าใช้จ่ายลงตามวันที่บันทึก…" | **ล็อก** อยู่ท้ายผืนงานเสมอ ไม่อยู่ใน palette | ทุกประเภท | โผล่เมื่อเกี่ยวข้องเท่านั้น (partial-data convention) ตัวจัดข้อความแสดงเป็นกล่องเทา "อัตโนมัติ" ใต้สุด เอาออกไม่ได้ |
| **ปุ่ม "เปิด Deep"** | `sellerDashboardUrl()` | ไม่ล็อก (ซ่อนได้) | ทุกประเภท | อยู่ footer ของ bubble ลากเข้ามาในเนื้อหาไม่ได้ (Flex footer แยกจาก body) ป้ายปุ่มแก้ได้ ≤ 20 ตัว ปลายทางแก้ไม่ได้ ไม่มี URL → ไม่แสดงบล็อกนี้ |
| **ข้อความ (อิสระ)** | — | ไม่ล็อก | ทุกประเภท | สไตล์ตามข้อ 1.1 + ตัวแปร ≤ 6 บล็อก |
| **เส้นคั่น** | Flex `separator` | ไม่ล็อก | ทุกประเภท | |

#### 2.1.1 ตัวเลือกย่อยของบล็อก "รายร้าน"
- **ตัวเลขต่อร้าน** (ปิดไม่ได้เมื่อเป็นหลายร้านและไม่มีตัวเลขอื่นเหลือ)
- **ขายดี 3 อันดับ** = `showTopProducts` หัวข้อผันตาม `resolveProductVocab(v).bestSellerTitle` บ้านพักไม่มีตัวเลือกนี้ (builder ข้าม LODGING)
- **กำไรต่อร้าน** ผูกกับบล็อก "กำไร" ไม่ใช่สวิตช์แยก

> **ข้อสรุปเรื่อง Top3:** brief ระบุ "Top 3 ต่อร้าน" กับ "แยกรายร้าน" เป็นสองบล็อก แต่ที่ builder ผลิตจริง Top3 อยู่ใต้ชื่อร้านแต่ละร้านเสมอ (OQ-3: ไม่รวมข้ามร้าน) ถ้าให้ลากแยกจะเสียความผูกกับร้าน และต้องรื้อ `renderBubble` หนักกว่าที่จำเป็น จึงทำเป็นตัวเลือกย่อย ใน palette แสดงเยื้องใต้ "รายร้าน" ถ้าต้องการให้ลากแยกจริงให้ถามผู้ตัดสิน (คำถามที่ 5)

### 2.2 รายการตัวแปร (token)

เก็บเป็น key คงที่ในข้อความ (`{sales_counted}`) แสดงเป็นชิปไทย label ผันตาม vertical เหมือนบล็อก

| ชิปที่เห็น | key | แปลงเป็น | เงื่อนไข |
|---|---|---|---|
| {ชื่อร้าน} | `shop_name` | ร้านเดียว = ชื่อร้าน · หลายร้าน = "N ร้าน" | ใช้ได้เสมอ |
| {จำนวนร้าน} | `shop_count` | จำนวนร้านที่นับในรายงาน | |
| {วันที่} | `date_range` | `rangeText(window)` | |
| {เวลาข้อมูล} | `computed_at` | "HH:MM น." | |
| {จำนวน{คำ}} เช่น {จำนวนคำสั่งซื้อ} / {จำนวนบริการ} / {จำนวนรายการ} | `orders_count` | จำนวนใบ | label ผันตาม vertical |
| {ยอดขาย (นับแล้ว)} | `sales_counted` | `formatBaht(confirmed)` | ชื่อชิปคงคำว่า "นับแล้ว" เสมอ ห้ามย่อเป็น "ยอดขาย" เพราะนิยามเดียวทั้งระบบ (HR16) |
| {ยังไม่นับ} | `sales_pending` | `formatBaht(unconfirmed)` | |
| {ยกเลิก} | `cancelled_count` | จำนวนใบ | |
| {ยอดสะสมรอบ} | `cycle_sales` | ยอดขายนับแล้วสะสมรอบ | ใช้ได้เฉพาะรายวันที่ไม่ใช่ 24:00 และเปิดรายเดือน |
| {กำไร} | `profit` | กำไรรวม | **ใช้ไม่ได้จนกว่ายืนยันกำไรแล้ว** ผ่าน Swal เดียวกับบล็อกกำไร |

**พฤติกรรมเมื่อส่งจริงแล้วคำนวณตัวแปรไม่ได้** (เช่น {กำไร} ตอนร้านต่างกติกา, {ยอดสะสมรอบ} ในรายงานรายเดือน): **บรรทัดนั้นไม่ถูกส่ง** แล้วบันทึกในประวัติ ไม่ส่งข้อความที่เขียนว่า "กำไร: -" เพราะอ่านเป็น "ไม่มีกำไร" ทั้งที่จริงคือคำนวณไม่ได้ ตรงกับที่ builder ทำกับยอดกำไรรวม (ตัดทิ้งเมื่อรวมไม่ได้) ตัวจัดข้อความต้องเตือนล่วงหน้าบนบล็อก (ดูข้อความข้อ 7)

**วิธีแทรก:**
- **เดสก์ท็อป:** ลากชิปจาก "+ ข้อมูล" ไปวางบน textarea ได้ตรง ๆ ใช้ HTML5 drag native (`dataTransfer.setData('text/plain','{sales_counted}')`) เบราว์เซอร์แทรกที่ตำแหน่งเคอร์เซอร์ให้เอง ไม่ต้องเขียนโค้ดเพิ่ม
- **ทุกอุปกรณ์:** ปุ่ม "+ ข้อมูล" เปิด picker แล้วแตะแทรกที่เคอร์เซอร์ (ทางหลักบนมือถือ เพราะ HTML5 drag ไม่ทำงานบนจอสัมผัส)
- **ตอนแก้:** ตัวแปรแสดงเป็น `{ชื่อ}` ในช่องพิมพ์ธรรมดา (`form-textarea`) **ไม่ทำ contentEditable ที่มีชิปในช่องพิมพ์** เพราะไม่มี theme match และ a11y/เคอร์เซอร์เปราะ ชิปจริงแสดงในโหมดอ่านและพรีวิว

### 2.3 พฤติกรรมร่วม (ทุกทิศทาง)

- **แถวบล็อก** (`BlockRow`) = `[grip-vertical 44px] [ชื่อ + บรรทัดสรุป] [ย้ายขึ้น] [ย้ายลง] [⋯]`

  - ล็อก = ไอคอน `lock` แทน grip ไม่มีปุ่มย้าย
- **ลาก:** ที่ grip เท่านั้น (`handle: '.sort-handle'`) เพื่อไม่แย่งการเลื่อนหน้าบนมือถือ มือจับใช้ `touch-none` (utility ปกติ ไม่ใช่ค่า arbitrary) คีย์บอร์ดของ `@hello-pangea/dnd`: Space ยก · ลูกศรย้าย · Space วาง · Esc ยกเลิก ข้อความประกาศผ่าน `provided.announce()` ภาษาไทย เช่น "ยกยอดขายแล้ว ตำแหน่งที่ 3 จาก 7" และ "ย้ายยอดขายไปตำแหน่งที่ 2"

- **บันทึก:** ส่วนเทมเพลตใช้ **บันทึกแบบกดปุ่ม ไม่ใช่ autosave** ต่างจากส่วนอื่นของหน้า (ดูเหตุผลข้อ 9.4) เมื่อมีการแก้ที่ยังไม่บันทึก:

  - เมื่อไม่มีการแก้ค้าง "ส่งทดสอบ" กลับเป็น primary ตามเดิม

### 4.3 การโต้ตอบ
- **เลือก:** แตะ/คลิกส่วนในบับเบิล = เลือก (พื้น `bg-primary/5` + ขอบ `border-primary`) ส่วนที่เป็นข้อความอิสระ แตะซ้ำ = เข้าโหมดพิมพ์ (ช่อง `form-textarea` แทนที่ตรงนั้น) ส่วนข้อมูล (ยอดขาย ฯลฯ) แตะแล้วแก้ข้อความไม่ได้ ได้แค่ย้ายหรือเอาออก
- **ลาก:** ที่ grip ของแต่ละส่วนใน bubble (react-sortablejs, `handle`) · เพิ่มบล็อกใหม่: แตะเส้น "＋" → เปิด picker (popover บนเดสก์ท็อป / bottom sheet บนมือถือ)
- **คีย์บอร์ด:** แต่ละส่วนเป็น `button`/`role="listitem"` tab ได้ Enter = เลือก · แถบเครื่องมือมี ↑ ↓ ตามกฎ a11y
- **แถบเครื่องมือ:** เดสก์ท็อป = ลอยยึดกับส่วนที่เลือก (ตำแหน่งคำนวณจาก rect → ต้องมี comment carve-out HR7 ถ้าใช้ `style`) · มือถือ = ติดขอบล่างเหนือ bottom nav (ไม่ลอยตามส่วน เพราะนิ้วกับคีย์บอร์ดบัง)

| ข้อดี | ข้อเสีย |
|---|---|
| ตรงกับแนวคิด "เห็นสิ่งที่ส่ง" ที่สุด ไม่มีขั้น "แปลงจากฟอร์มเป็นข้อความ" · ไม่มี palette แยกให้เรียน | **ความเสี่ยงสูงสุดของ 4 แบบ** (ดูด้านล่าง) · ต้องเพิ่ม id ต่อส่วนใน renderer · ผู้ขายอาจเข้าใจว่าตัวเลขในบับเบิลแก้ได้ |

**ความเสี่ยง:**
1. **WYSIWYG ไม่จริง 100%** — พรีวิวเรนเดอร์ด้วย Anuphan/Paces ส่วน LINE เรนเดอร์ด้วยฟอนต์ของเครื่องผู้รับ ความกว้างและการตัดบรรทัดต่างกัน การแก้บน "ของปลอม" ที่ดูเหมือนจริงเกินไปทำให้ผู้ขายเชื่อว่าตรงกันเป๊ะ ต้องมี caption "ตัวอย่าง การตัดบรรทัดในกลุ่มอาจต่างเล็กน้อย" ถาวร
2. ตัวเลขในบับเบิลเป็น **ตัวอย่าง** ที่แก้ไม่ได้ แต่หน้าตาเหมือนข้อมูลจริง (PRODUCT.md ห้ามให้ placeholder ดูเหมือนข้อมูลจริง) ต้องติดป้าย "ตัวอย่าง" บนตัวเลขทุกตัว
3. `FlexBubbleView` ปัจจุบันเรนเดอร์จาก Flex JSON ซึ่ง **ไม่มี id ของบล็อก** ใส่ key แปลกลง JSON ส่ง LINE ไม่ได้ (LINE อาจตีกลับ) ต้องให้ composer คืน "แผนที่ส่วน → id" แยกจาก JSON
4. a11y ของ element ที่ลากได้ + แก้ข้อความได้ + เลือกได้ในจุดเดียวซับซ้อนที่สุด

## 6. ทิศทางที่ 4 (d): "กองการ์ดมือถือ + ชีตเลือกบล็อก"

**แนวคิด:** ออกแบบสำหรับนิ้วโป้งก่อน ทุกบล็อกคือการ์ดแถวเดียวที่แตะแล้วขยาย การเพิ่มบล็อกคือชีตจากขอบล่าง ขยายขึ้นเป็นสองคอลัมน์เมื่อจอกว้าง ไม่มีโหมดแยก ไม่มี route แยก อยู่ในหน้าตั้งค่าเดิมต่อจากการ์ดร้าน/เวลา

### 6.3 การโต้ตอบ
- **ลาก:** ที่ grip เท่านั้น (`touch-none`) ทั้งสลับลำดับในกอง และลากจากชีต (hello-pangea, ชีตและกองอยู่ใน `DragDropContext` เดียว)
- **ชีตหดตอนลาก:** `onBeforeDragStart` → ชีตแปลงเป็นแถบ 64px และปลด `useLockBodyScroll` ขณะลาก (คุมเจ้าของ lock ที่เดียว) · `onDragEnd` → คงชีตพับไว้ มี "เปิดชีต" ให้กลับมา
- **คีย์บอร์ด:** การ์ดโฟกัสได้ Enter = ขยาย ปุ่ม ↑ ↓ อยู่ในแถบเครื่องมือของการ์ดที่ขยาย (≥44px) · ชีตใช้ focus trap ปิดด้วย Esc
- **เดสก์ท็อป:** "＋ เพิ่มบล็อก" เป็น popover (React-controlled ตาม `GroupMenu.tsx`) ลากชิปจาก popover ลงกองได้เช่นกัน

| ข้อดี | ข้อเสีย |
|---|---|
| คอมโพเนนต์เดียวใช้ได้ทั้ง 375 → 1180 (ไม่มีโหมดแยก) · อยู่ในหน้าเดิม sibling parity กับ `GroupDetailClient` สูงสุด ใช้การ์ดร้าน/เวลาเดิมทั้งก้อน · แก้ปัญหาลากจากชีตที่ตรงจุดจริงของมือถือ | ผืนงานแคบ ข้อมูลหลายร้านทำให้กองยาว · ชีตเป็น overlay (Operate mode เตือน "modal as first thought" ดูความเสี่ยง) · ไม่มีภาพรวมสามช่องแบบ (a) บนจอใหญ่ |

**ความเสี่ยง:**
1. **overlay ซ้อน overlay** — bottom nav 72px + ชีต + Swal (ยืนยันกำไร) บนมือถือ ต้องกำหนดลำดับ z-index และเจ้าของ scroll-lock ให้ชัด (convention `overlay-scroll-lock`)
2. **ชีตหดตอนลาก** เป็นพฤติกรรมไม่ standard ต้องทดสอบบน iOS Safari (convention `ios-safe-area`, `feedback_ios_fixed_overlay_visual_viewport`)
3. ทางเลือกถ้า critique ปฏิเสธชีต: "＋" ขยาย picker แบบ inline ในกอง (ไม่มี overlay) แลกกับลากข้ามไม่ได้เพราะไม่ต้องข้าม

## 9. Impeccable compliance

- **Mode: Operate** (หลังบ้านผู้ขาย) เกณฑ์ตัดสินคือ consistency กับหน้าพี่น้อง (`GroupDetailClient`, `public-profile/builder`) และการสแกนอ่านง่าย ไม่ใช่การแสดงออก ทิศทางที่ "กล้า" ที่สุด (b) จึงมีความเสี่ยงสูงสุดต่อเกณฑ์นี้
- **One Voice:** น้ำเงิน `bg-primary` อยู่เฉพาะ
  - ปุ่ม primary 1 ตัวต่อหน้า — "บันทึกเทมเพลต" เมื่อมีฉบับร่าง ไม่งั้น "ส่งทดสอบ" **ไม่เคยมีสอง primary พร้อมกัน**
  - ชิปตัวแปร (`bg-primary/10 text-primary` เหมือน chip เวลา)
  - เส้นแทรก/ขอบของบล็อกที่เลือกหรือกำลังลาก (`border-primary`, `bg-primary/5`)
  - สถานะกดของ "ตัวหนา" และตัวเลือก seg ที่เลือก
  - หัวบับเบิลในพรีวิว
  - ไม่มีพื้นน้ำเงินเต็มบล็อก ไม่มีสีม่วง (`#7367F0` ไม่อยู่ในหน้านี้)
- **Verified-Means-Green:** ไม่มีเขียวใหม่ในสเปกนี้ · "บันทึกแล้ว" เป็น neutral (ตามมติ addendum §4.4 ข้อ 7) · บล็อกกำไร = warning · ตัวเลือกสีข้อความ **ตัดเขียวและแดงออก** เพราะสองสีนี้สื่อความหมายในรายงาน (ข้อ 1.1) · จุด "ยังไม่บันทึก" บนแท็บ = warning
- **Sentence-case / ไทย:** ไม่มี ALL CAPS · ไม่มี eyebrow เหนือหัวข้อ · ป้ายส่วน "ข้อมูลที่ส่งได้/ข้อความของคุณ" เป็นหัวข้อกลุ่มที่ทำหน้าที่จริง ไม่ใช่ kicker ตกแต่ง
- **Ink-tinted shadow:** ใช้ shadow ของธีม (`shadow-lg` ลอย/ลาก) ไม่มีดำสนิท · ไม่มีกรอบโทรศัพท์ตกแต่ง
- **น้ำเสียง:** ปุ่มบอกผลลัพธ์ ("บันทึกเทมเพลต", "คืนเป็นแบบมาตรฐาน") · error บอกทางออก · เหตุที่ใช้ไม่ได้อธิบายเหตุ ไม่ใช้ "ไม่สามารถ…ได้" · ไม่ไฮป์
- **สิ่งที่เป็นพระเอกของหน้า:** พรีวิวบับเบิล (ในทิศทาง b ตัวบับเบิลเองคือเวที) ส่วนในบับเบิล พระเอกคือ "ยอดขาย (นับแล้ว)" ตัวเดียวที่ตัวหนา ข้อความของผู้ขายถูกเพดานขนาดที่ `md` ไม่ให้แย่งตำแหน่ง
- **จุดที่ theme ขัดกับ Impeccable และการตัดสิน**
  1. Impeccable Operate เตือน "modal as first thought" แต่ Hard Rule 8 บังคับ Swal สำหรับ confirm ที่บล็อกการตัดสินใจ → ใช้ Swal เฉพาะ 3 จุด (เปิดกำไร, คืนมาตรฐาน, ทิ้งฉบับร่าง) ส่วนการเอาบล็อกออกใช้ toast + ย้อนกลับ ไม่ใช่ modal
  2. **ชีตของทิศทาง d เป็น overlay จริง** ตัดสินว่ายอมรับได้เพราะ picker มี 10+ รายการ ที่ 375 ไม่มีที่อินไลน์ที่ไม่ดันกองหนีไป · จุดเสี่ยงที่ Controller ควรเพ่งตอน critique
  3. **Slate (`#808390`) ตก contrast** บนพื้นขาว (DESIGN.md: placeholder ต้อง ≥4.5:1) แต่ builder เดิมใช้ `SLATE` กับ "ยังไม่นับ…" และ Flex ส่งสีนี้จริงในกลุ่ม LINE → สีข้อความ "รอง" ในตัวเลือก **ติดป้ายว่า "ค่อนข้างจาง"** ส่วน UI ของเราใช้ `text-default-700` ไม่ใช่ slate เสมอ
  4. **เทมเพลตบันทึกด้วยปุ่ม ไม่ autosave** ขัดกับมติ base spec "autosave ทุกตัวควบคุม" ตัดสินแยกเพราะ (ก) ข้อความออกถึงกลุ่มทีมจริง ลบไม่ได้ (ข) การพิมพ์กลางคันถูกบันทึกแล้วส่งตอน 09:00 ได้ ต้องให้ Controller รับทราบ (คำถามที่ 4)
  5. ตำแหน่ง toolbar ลอยของ (b) ต้องใช้ `style` คำนวณ → ต้องมี comment carve-out HR7 บรรทัดเดียวกัน; z-80 ของชีต = carve-out เดิม (precedent `AccountSwitcherSheet`) ห้ามใส่ค่าดิบอื่น
  6. ใช้ `max-h-4/5` สำหรับชีต ไม่ใช้ `max-h-[80dvh]` (arbitrary)
- **ไอคอนที่ยังไม่ยืนยันกับ gallery ธีม** ถูกเลี่ยง (ปุ่ม toolbar ใช้ตัวหนังสือ) · ทุกชื่อที่เหลือมี precedent ในแอปแล้ว

## 10. Design decisions + rationale (รวม)

1. **สไตล์ต่อบล็อก ไม่ใช่ต่อคำ** ตามข้อจำกัด LINE ที่ brief ระบุ พร้อมแจ้งว่า `span` น่าจะมี → รอยืนยันก่อนอัปเกรด *(ยืนยันแล้วว่ามี — ดูท้ายไฟล์)*
2. **Top3 และกำไรต่อร้านเป็นตัวเลือกย่อยของ "รายร้าน"** ไม่ใช่บล็อกลอยอิสระ เพราะเกี่ยวกับร้านนั้น ๆ (OQ-3) และรื้อ `renderBubble` น้อยกว่า
3. **flag 5 ตัวคำนวณจากเทมเพลต** (บล็อกมี ⇔ flag เปิด) เพื่อไม่ให้มีสองความจริง
4. **ล็อก = ตรึงและเอาออกไม่ได้** สำหรับ หัวรายงาน/ข้อมูล ณ (BR-LGS-08) และหมายเหตุอัตโนมัติ (partial-data convention) ต่างกัน: แก้ชื่อรายงานได้ ส่วนช่วงวันที่/"ข้อมูล ณ" แก้ไม่ได้
5. **ข้อความอิสระไม่ถูกตัดเงียบ** บล็อกที่บันทึกตั้งแต่ตอนแก้เมื่อเกินเพดาน
6. **ลากกับแตะเป็นทางเดียวกันเสมอ** (precedent `LibraryPanel`) ปุ่มย้ายขึ้น/ลงบังคับทุกที่ (a11y)
7. **ชิปตัวแปรในช่องพิมพ์ใช้ `{ชื่อ}` ไม่ใช่ contentEditable** ลดความเสี่ยง a11y และต้นทุน dev ให้เหลือ native drop
8. **สี "รอง" ใช้ได้ แต่ไม่มีเขียว/แดง/ขีดเส้นใต้/ลิงก์เอง** เหตุผลเฉพาะของแบรนด์ที่ต้านมิจฉาชีพ

## 11. Anti-slop self-check

1. **เฉพาะ Deep ไหม:** ใช่ — ล็อก "ข้อมูล ณ" ตาม BR-LGS-08, ตัดสีเขียว/แดงตามความหมายในรายงาน, คำผันตามประเภทร้าน (`reportOrderWord`), หมายเหตุอัตโนมัติจากกฎ partial-data, ชื่อชิป "ยอดขาย (นับแล้ว)" ตามนิยามเดียวทั้งระบบ, ปุ่มเปิด Deep ชี้ URL ตายตัว กันข้อความดูเหมือนลิงก์หลอก ถ้าเอาไปใช้กับร้านค้า/CRM อื่นต้องรื้อเกือบหมด
2. **พระเอกหนึ่งอย่างต่อจอ:** (a) พรีวิวโทรศัพท์ + ไฮไลต์ข้ามคอลัมน์ · (b) ตัวบับเบิล · (c) ประโยคสรุปบนสุด · (d) กองการ์ด "ข้อความที่ส่ง" (ร้าน/เวลาเป็นแถวสรุปบาง ๆ) ภายในบับเบิล พระเอก = ยอดขาย (นับแล้ว) ตัวเดียวที่หนา
3. **ตัดของซ้ำ/คงที่:** ตัด `MetricsCard` (ซ้ำกับบล็อก) · ตัดโหมดตัวอย่างแยกของ palette และพรีวิว · ตัดการ์ดสรุปสถานะ · ไม่ใส่ตัวนับ "5 บล็อก" ที่ไม่ได้ช่วยตัดสินใจ (gauge ความยาวมีเหตุผลจริง = เพดาน LINE)
4. **State ครบ:** ตารางข้อ 8 — ค่าตั้งต้น, loading, ล้ม, ชื่อ 50 ตัวอักษร, ตัวเลข 0 และหลักล้าน, ผสมประเภทร้าน, บล็อกที่เงื่อนไขหาย, ออกจากหน้าตอนมีฉบับร่าง
5. **Copy:** ปุ่มบอกผลลัพธ์ ("บันทึกเทมเพลต") · ส่งทดสอบที่ disabled บอกเหตุและทางออก ("บันทึกเทมเพลตก่อน…") · ไม่แนะนำให้กดสิ่งที่ไม่มีในสถานะนั้น (เช่น แพ็กเกจหยุด → ไม่ชวนบันทึก)
6. **ศัพท์เดียวกัน:** "บล็อก" = หน่วยหนึ่งในข้อความ · "ตัวแปร" = ชิปข้อมูลในข้อความ · "เทมเพลต" = ชุดบล็อกทั้งก้อนของกลุ่ม · "ผืนงาน" ใช้เฉพาะ (a) · ศัพท์ธุรกิจ (ยอดขาย นับแล้ว ยังไม่นับ) ตรง SSOT ของ builder
7. **สีถูกความหมาย:** เขียวไม่มีเลย (ไม่มีอะไรยืนยันใหม่) · แดงเฉพาะการล้มจริงที่ builder ส่งอยู่แล้ว · "ยังไม่บันทึก" และกำไร = warning · สถานะเดียวกันสีเดียวกันทุกทิศทาง
8. **มือถือ:** grip/ปุ่มย้าย/ปุ่ม × ≥44px (`min-h-11`) · ลากที่ grip เท่านั้น (ไม่แย่งการเลื่อน) · toolbar ของ (b) ติดล่างเหนือ bottom nav ไม่ลอยตามส่วน · action หลักอยู่ action-bar ตามกฎ `seller-action-placement`

## ผลตรวจ span ของ LINE Flex

**แหล่ง:** https://developers.line.biz/en/reference/messaging-api/ (หัวข้อ "Span", ดึงเป็น `index.html.md` เมื่อ 2026-10-05)

**ผล: มีจริง** — `span` เป็น component ที่ใส่ใน `contents` ของ `text` ได้ ("This component renders multiple text strings in different styles. … Span is set to `contents` property of texts")

props ที่รองรับ:

| prop | ค่า | ใช้ใน builder ไหม |
|---|---|---|
| `type` | `span` (บังคับ) | ใช้ |
| `text` | ข้อความ (ถ้า text แม่ `wrap:true` ใช้ `\n` ขึ้นบรรทัดได้) | ใช้ |
| `color` | hex | ใช้ — จำกัดชุด ink / slate / accent เท่านั้น |
| `size` | ชุดขนาด Flex เดียวกับ text/icon | ไม่เปิดต่อคำ (ขนาดคงเป็นต่อบรรทัด กันข้อความกระโดด) |
| `weight` | `regular` / `bold` | ใช้ — "ตัวหนาเฉพาะคำที่เลือก" |
| `style` | `normal` / `italic` | ไม่เปิด (ตามข้อ 1.1) |
| `decoration` | `none` / `underline` / `line-through` | **ไม่เปิด** — ขีดเส้นใต้อ่านเป็นลิงก์ (ข้อ 1.1) · decoration ของ text แม่ทับ span ไม่ได้ |

**ผลต่อดีไซน์:** "rich text" ทำได้ทั้ง 2 ระดับ
- **ทั้งบรรทัด:** ตัวหนา · ขนาด 3 ระดับ · สี 3 สี (ตามข้อ 1.1 เดิม)
- **เฉพาะคำที่เลือก:** ตัวหนา และสีเน้น (accent) — เก็บในเทมเพลตเป็นช่วงข้อความ เช่น `[{text:'ยอดวันนี้ ', }, {text:'{ยอดขาย (นับแล้ว)}', bold:true, color:'accent'}]` แล้ว composer แปลงเป็น `text.contents: span[]`
- mockup แสดงทั้งสองระดับ (เลือกคำในช่องพิมพ์ แล้วกด "ตัวหนา (คำที่เลือก)" / "เน้น (คำที่เลือก)" — ในช่องพิมพ์เห็นเป็นเครื่องหมาย `**…**` และ `^^…^^` เพราะไม่ทำ contentEditable ตามข้อ 2.2)
