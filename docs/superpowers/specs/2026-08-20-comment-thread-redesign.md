# เธรดคอมเมนต์ "ดูยากเกินไป" — 3 ทางเลือก

**วันที่:** 2026-08-20
**ที่มา:** ลูกค้า (ผู้ขาย) รายงานผ่าน user ว่าเธรดคอมเมนต์ในกล่องแชท "ดูยากเกินไป"
**Mockup:** [`2026-08-20-comment-thread-redesign-mockup.html`](./2026-08-20-comment-thread-redesign-mockup.html) — 3 แบบ × 3 จอ (320 / 390 / เดสก์ท็อป)
**สถานะ:** รอ user เลือก · ยังไม่ผ่าน `safepay-ux` (จะส่งหลังเลือกได้แล้ว)

---

## 1. ปัญหาที่วัดได้ ไม่ใช่ความรู้สึก

จากภาพหน้าจอ prod ที่ user ส่งมา — ลูกค้า **1 คนกินพื้นที่ 3 บรรทัด** และมีของเรียงแนวนอน **6 ชิ้น**:

```
เวลา · ✓ตอบแล้ว · ตอบ · [ทักแชท] · คงเหลือ 6 วัน 23 ชั่วโมง 52 นาที
```

### 1.1 สีแดงที่ไม่ได้บอกอะไร

`คงเหลือ …` เป็น **สีแดงทุกแถวตั้งแต่เหลือ 6 วัน** ⇒ ทั้งจอแดงเท่ากันหมด

ผลคือสองอย่างพร้อมกัน: สีเลิกทำหน้าที่เตือน **และ** เคสด่วนจริง (เหลือ 2 ชั่วโมง) ไม่มีที่ให้ยกระดับไปอีก

> 🛑 นี่คือบทเรียนที่โปรเจกต์บันทึกไว้แล้วในไฟล์เดียวกัน — `PRIVATE_REPLY_URGENT_MS` มีคอมเมนต์เขียนว่า
> *"ถ้าแดงตั้งแต่ยังเหลือเกือบสัปดาห์ แดงก็เลิกแปลว่า 'ทำเดี๋ยวนี้'"* แต่บังคับเฉพาะที่ badge ของแถวรายการ
> ส่วนป้ายในเธรดยังแดงตายตัว

### 1.2 คำตอบของเราเองกินพื้นที่เท่าคำถามของลูกค้า

`แอดมินส่งรายละเอียดให้นะคะ` ซ้ำกันทุกใบ แต่ได้บับเบิลเต็มขนาด + avatar + ป้าย "ผู้ดูแลเพจ" + แถวเวลา
**ผู้ขายไม่ต้องอ่านสิ่งที่ตัวเองพิมพ์** — แต่มันกินครึ่งจอ

### 1.3 สัญญาณที่ผู้ขายต้องการคือสิ่งที่ "ไม่มีอยู่"

สิ่งที่ผู้ขายกำลังตามหาคือ **"ใครยังไม่ได้คุย"** ซึ่งบนจอปัจจุบันแสดงด้วยการ **ไม่มี** `✓ตอบแล้ว`
⇒ ต้องอ่านทีละแถวถึงจะรู้ว่าอันไหนขาด จอจึงตอบคำถามที่สำคัญที่สุดได้ช้าที่สุด

---

## 2. สิ่งที่ทั้ง 3 แบบแก้เหมือนกัน (ไม่ใช่ตัวตัดสิน)

| | |
|---|---|
| เส้นตายทักแชท | โผล่ **เฉพาะแถวที่ยังไม่ตอบ** ไม่ใช่ทุกแถว |
| สีของเส้นตาย | ไล่ตามเวลาที่เหลือจริง — เหลือ >24 ชม. เหลือง · <24 ชม. แดง |
| หน่วยเวลา | หน่วยหยาบหน่วยเดียว (`5 วัน` / `21 ชั่วโมง`) ไม่ใช่ 3 หน่วยเต็ม |
| คำตอบของเพจ | ไม่ได้พื้นที่เท่าคำถามของลูกค้าอีกต่อไป |

> ⚠️ **หน่วยหยาบขัดกับมติ 2026-08-04** ที่สั่งว่าต้องเอา 3 หน่วยเต็ม "เพราะคนต้องใช้ตัดสินใจว่าวันนี้ยังทันไหม"
> — user กลับมติข้อนี้ไปแล้วเมื่อ 2026-08-20 สำหรับ **รายการซ้าย** โดยระบุว่าเธรดยังใช้หน่วยเต็ม
> **ถ้าเลือกแบบใดแบบหนึ่งในเอกสารนี้ = กลับมติข้อนั้นในเธรดด้วย** ต้องยืนยันอีกครั้งก่อน implement

## 3. สามแบบ — ต่างกันที่ "สมมติฐานว่าอะไรทำให้ดูยาก"

### A — ยุบคำตอบของเพจ

**สมมติฐาน:** ผู้ขายยังอ่านเป็นบทสนทนาอยู่ แค่คำตอบของเราเองเกะกะ

คำตอบของเพจยุบเหลือบรรทัดเดียวกดขยาย (`ตอบแล้ว · 1`) · เมตาดาต้าย้ายไปชิดขวาของบับเบิลแทนแถวยาวใต้ข้อความ

- ✅ เปลี่ยนน้อยที่สุด ความเสี่ยง regression ต่ำสุด · ยังเป็นบทสนทนาตามลำดับเวลา
- ⚠️ ปุ่ม "ตอบ/ทักแชท" ต้องย้ายไปอยู่ที่อื่น (hover/กดค้าง) — ต้องออกแบบเพิ่ม
- ❌ ยังไม่ตอบคำถาม "เหลือใครบ้าง" ในวินาทีแรก

### B — แยกคอลัมน์งาน

**สมมติฐาน:** ที่ดูยากเพราะข้อความกับปุ่มปนกันในแถวเดียว ตาต้องกวาดสลับซ้าย-ขวาตลอด

บทสนทนาซ้าย · งาน (สถานะ + ปุ่ม) ตรึงเป็นคอลัมน์ขวา

- ✅ กวาดตาลงแนวตั้งครั้งเดียวรู้ทั้งจอ · ปุ่มอยู่ตำแหน่งเดิมทุกแถว
- ✅ ได้เปรียบที่สุดบนเดสก์ท็อป
- ❌ กินความกว้าง ~104px ต่อแถว — **ที่ 320px ข้อความเหลือแคบมาก ต้องดูจอนั้นให้หนัก**

### C — การ์ดต่อคน แยก "ยังไม่ได้คุย" ออกมาก่อน

**สมมติฐาน:** ผู้ขายไม่ได้อ่านบทสนทนา เขากำลังเคลียร์คิว

คนที่ยังไม่ตอบขึ้นเป็นการ์ดเต็มพร้อมปุ่ม · คนที่คุยจบแล้วยุบเหลือบรรทัดเดียวไปอยู่ท้ายจอ

- ✅ ตอบคำถาม "เหลือใคร" ได้ในวินาทีแรก ซึ่งคือเหตุผลเดียวที่ผู้ขายเปิดหน้านี้
- ❌ **เลิกเป็นบทสนทนา** — ลำดับเวลาหายไป และคำตอบของเพจไม่อยู่ติดกับคำถามอีก
- ❌ เปลี่ยนความหมายของหน้ามากที่สุด → เสี่ยงที่สุด

## 4. คำถามที่ต้องให้ user ตัดสิน

1. **ยอมรับสมมติฐานข้อไหน** (A / B / C) — หรือผสม เช่น "ยุบคำตอบเพจแบบ A + แยกคนที่ยังไม่ได้คุยแบบ C"
2. **ปุ่ม "ตอบ" กับ "ทักแชท" ควรอยู่ตลอดเวลา หรือโผล่ตอน hover/กดค้าง** — A สมมติว่าโผล่ตามต้องการ ส่วน B/C สมมติว่าอยู่ตลอด
3. **ยืนยันการกลับมติหน่วยเวลาในเธรด** (ดู §2)
4. **คนที่ "ตอบแล้ว" ควรหายไปจากสายตาเลยไหม** (C ทำแบบนั้น) หรือแค่จางลง

---

## 5. ขั้นตอนถัดไป

1. user เลือก → ตอบ 4 คำถามใน §4
2. ส่ง `safepay-ux` ออก Design Spec เต็ม (wireframe ทุกสถานะ · คีย์ i18n · Theme Source Mapping · Impeccable compliance)
3. **เขียนใหม่จาก spec** — 🛑 ห้ามยกโค้ดจาก `src/app/(paces)/seller/(chat)/inbox/comments/__prototype__/` ไปใช้ตรง ๆ
   มันเขียนใต้ข้อจำกัด prototype (ไม่มีเทส ไม่มี a11y ครบ ไม่ผูกกับ SSOT ของเวลา)
4. ถอดโฟลเดอร์ `__prototype__/` + `protoVariant` + `<PrototypeSwitcher/>` ออกจาก main

## 6. ของที่ทำไปแล้วและเกี่ยวข้อง

- prototype กดดูของจริงได้ที่ `/inbox/comments?post=<id>&variant=A|B|C` (opt-in ล้วน ไม่มี `?variant=` = ไม่มีอะไรเปลี่ยน)
- **แถวในรายการซ้าย** ถูก redesign ไปแล้ววันเดียวกัน (`b5cfc53e`) — โครงใหม่คือ โพสต์ / ลูกค้า / ชิป 2 ใบ
  เอกสารนี้พูดถึง **คอลัมน์เธรด** ซึ่งเป็นคนละที่
- `src/lib/comment-row-chips.ts` = SSOT ของ "แถวควรขึ้นชิปอะไร" ในรายการซ้าย — ถ้าเธรดจะใช้เกณฑ์เดียวกัน
  ต้องยืมตัวนี้ ห้ามเขียนใหม่ (HR16)
