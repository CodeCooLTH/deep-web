## 1. คำถามที่ต้นแบบนี้ตอบ

> **“หน้าตั้งค่า rich menu ของผู้ขายควรมีหน้าตาเป็นยังไง”**

ไม่ใช่คำถามว่า “ตรรกะถูกไหม” — ลำดับขั้นของ LINE API (สร้างเมนู → อัปโหลดรูป → ตั้งเป็น default → ผูกรายคน)
เป็นคำถามคนละข้อ ถ้าต้องการตอบข้อนั้นให้ทำต้นแบบแยกอีกตัว (logic demo)

**ขอบเขตที่ตกลงไว้** — ทั้ง 3 แบบต้องครอบให้ครบเท่ากัน:

1. เลือกเทมเพลต + อัปโหลดรูป + ผูก action ต่อช่อง
2. มีเมนูได้หลายชุด + สลับว่าชุดไหนเป็นเมนูเริ่มต้นของ OA
3. ตั้งเวลาเริ่ม–สิ้นสุด และ/หรือแยกเมนูตามกลุ่มผู้ใช้
4. วาดช่องเองแบบอิสระ (ไม่ยึดเทมเพลต)

## 3. สามแบบ — ต่างกันที่โครงสร้าง ไม่ใช่ที่สี

### A — แคนวาสเป็นพระเอก (`?v=A`)

สองคอลัมน์แบบ LINE Official Account Manager: ซ้ายเป็นรูปเมนูใหญ่ที่มีกรอบช่องวางทับ คลิกช่อง → แก้ในแผงขวา

- **affordance หลัก:** จัดการตรงบนรูป (direct manipulation)
- **ได้:** ความสัมพันธ์ “ช่องนี้ = ตรงไหนบนรูป” ชัดที่สุด · วาดช่องเองคือการลากบนแคนวาส ไม่ต้องมี UI แยก
- **เสีย:** มือถือแก้ไม่ได้ ทำได้แค่สลับชุดเมนู · แก้ action หลายช่องรัว ๆ ต้องคลิกไป-มา
- **ต้องยอมรับ:** เป็น desktop-only โดยตั้งใจ — ไม่ใช่ผลข้างเคียงที่ค่อยมารู้ทีหลัง

### B — รายการช่องเป็นพระเอก (`?v=B`)

ทิ้งแคนวาสใหญ่ เหลือพรีวิวเล็กปักข้างบน เนื้อหาหลักคือรายการช่องเรียงเป็นแถว/การ์ด แก้ action ได้ในแถวเลย

- **affordance หลัก:** ฟอร์มเป็นแถว
- **ได้:** ใช้ได้เต็มที่ทุกจอรวมมือถือ · กวาดตาเห็น “ช่องไหนยังไม่ผูก action” ทันที · ภาษาการออกแบบตรงกับ `/orders` `/products` ที่มีอยู่แล้ว (`sibling-surface-parity`)
- **เสีย:** “แถวนี้อยู่ตรงไหนบนรูป” ต้องพึ่งตัวอักษร A–F · วาดช่องเองกลายเป็นงานชั้นสองในชีตแยก
- **ต้องยอมรับ:** การวาดพื้นที่เองจะช้ากว่าแบบ A อย่างเห็นได้ชัด

### C — ตัวช่วยเป็นขั้น (`?v=C`)

แยกเป็น “คลังเมนู” (การ์ดรวมทุกชุด + สลับ default) กับ “ตัวช่วยสร้าง” 5 ขั้น: เทมเพลต → รูป → action → เวลา/กลุ่ม → ตรวจแล้วเผยแพร่

- **affordance หลัก:** เดินเป็นเส้นตรงทีละคำถาม
- **ได้:** ร้านที่ไม่เคยตั้ง rich menu ทำจบได้โดยไม่ต้องเดา · กันการเผยแพร่ทั้งที่ช่องยังว่างได้ตั้งแต่ต้นทาง · ทุกจอเท่ากัน
- **เสีย:** ร้านที่แค่อยากแก้ลิงก์เดียวต้องเดินผ่านหลายขั้น · ไม่เห็นภาพรวมพร้อมกัน
- **ต้องยอมรับ:** ต้องออกแบบ “ทางลัดกลับเข้าขั้นเดียว” ให้ดี ไม่งั้นกลายเป็นภาระของงานที่ทำบ่อย

## 5. คำตอบ — เลือกแบบ B

> **มติ (2026-08-14):** ใช้ **แบบ B — รายการช่องเป็นพระเอก** เป็นโครงของหน้าตั้งค่า rich menu
> ผู้ตัดสิน: เจ้าของโปรเจกต์ · ตัดสินจากการกดสลับดูต้นแบบทั้ง 3 แบบ

**สิ่งที่มติข้อนี้ผูกไว้ (ต้องไม่ถูกกลับเงียบ ๆ ตอน implement):**

| ประเด็น | สิ่งที่ตกลง |
|---|---|
| โครงหน้า | พรีวิวเล็กปักข้างบน/ข้าง — **ไม่มีแคนวาสใหญ่เป็นตัวเอก** |
| หน่วยของการแก้ | “ช่อง” เป็นแถว/การ์ด แก้ action ได้ในแถว ไม่ต้องเข้าโมดัลก่อน |
| มือถือ | **ต้องแก้ได้เต็มที่** ไม่ใช่แค่สลับชุด — ถ้าตอน implement มือถือทำไม่ได้ แปลว่าหลุดจากเหตุผลที่เลือก B |
| การมองเห็นช่องที่ยังไม่ผูก action | ต้องกวาดตาเห็นได้ทันทีจากรายการ (ตัวนับ + เน้นแถว) |
| ภาษาการออกแบบ | ยกจาก `/orders` · `/products` (การ์ดแยกใบบนมือถือ, ตารางบนเดสก์ท็อป) ตาม `sibling-surface-parity.md` |

**มติเพิ่มเติม (2026-08-14):** แบบ B แลกความเร็วของการ “วาดช่องเอง” ทิ้งไป — ตกลงว่า **ยืมโหมดแคนวาสของแบบ A มาเป็นทางเข้ารอง**

- หน้าหลักยังเป็น B ทุกจอ · แคนวาสเป็น **ทางเข้าที่สอง ไม่ใช่ทางเข้าหลัก** เปิดจากปุ่ม “จัดพื้นที่บนรูป”
- แคนวาสเป็น **เดสก์ท็อปเท่านั้น** — บนมือถือยังต้องปรับพื้นที่ได้ผ่านชีตทีละช่อง (ห้ามให้มือถือกลายเป็นอ่านอย่างเดียว ซึ่งขัดเหตุผลที่เลือก B ตั้งแต่แรก)
- แปลว่าโค้ดพิกัดช่อง (x/y/w/h บนรูป 2500×1686) มี **ผู้เขียน 2 ทาง** ต้องมี SSOT เดียวและต้องมีเทสผูก ไม่ใช่ปล่อยให้สองทางคำนวณเอง

## 5.1 ข้อสังเกตจากผู้ทำต้นแบบ (ก่อนตัดสิน — เก็บไว้เป็นบันทึก)

- ผลลัพธ์ที่น่าจะดีที่สุดคือ **ผสม** ไม่ใช่เลือกอันเดียว: โครง **B** เป็นหน้าหลัก (ใช้ได้ทุกจอ แก้เร็ว)
  \+ ยืมโหมดแคนวาสของ **A** มาเป็นปุ่ม “จัดพื้นที่บนรูป” สำหรับเดสก์ท็อป
  \+ ยืมตัวช่วยของ **C** มาใช้เฉพาะ **ตอนสร้างชุดแรก** แล้วครั้งต่อไปเข้าหน้า B ตรง ๆ
  ถ้าเห็นด้วยกับทิศนี้บอกได้ จะได้ไม่ต้องเลือกแบบใดแบบหนึ่งทั้งดุ้น
- **ยังไม่ได้ตัดสินและอยู่นอกต้นแบบนี้:** อะไรเกิดขึ้นเมื่อลบเมนูที่กำลังเป็น default อยู่ · ผูกเมนูรายคนแล้วจะ sync ตอนไหน · โควตาการเรียก LINE API ตอนอัปโหลดรูป (รูป 2500×1686 ผ่านทางไหน — เตือนว่า **ห้ามส่งผ่าน body ของ API route**, ต้องใช้ `@/lib/upload-client` ตาม `upload-body-size-limit.md`)
- ต้นแบบนี้ **ไม่ต่อ API ไม่มี state จริง** — ทุก input เป็นของตาย ตั้งใจให้เป็นแบบนั้น
