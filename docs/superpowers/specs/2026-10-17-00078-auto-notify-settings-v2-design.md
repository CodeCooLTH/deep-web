## 0. สรุปการตัดสินใจ

1. **ลำดับชั้นหน้า:** พระเอกคือ **สถานะชุด (ปิด / ทดสอบ / เปิด)** เพราะเป็นประตูของทุกอย่าง รองลงมาคือรายการจังหวะ (แต่ละจังหวะ = สวิตช์ + ข้อความ) ตารางลิงก์ขนส่งเป็นข้อมูลอ้างอิง ข้อควรรู้เป็นตัวหนังสือเบา
2. **ตัวแก้ข้อความฝังในแถวจังหวะ (กางทีละแถว)** ไม่ใช้โมดัล และไม่ใช้การ์ดซ้อนการ์ด พรีวิวอยู่คอลัมน์ขวา (ติดหน้าจอ) บนเดสก์ท็อป/แท็บเล็ต และอยู่ใต้ตัวแก้บนมือถือ
3. **พรีวิวเป็น "กรอบแชทตัวอย่าง" ไม่ใช่ภาพโทรศัพท์มีขอบเครื่อง:** ขอบเครื่องคือของตกแต่ง ไม่ให้ข้อมูล และ Paces ไม่มี primitive ให้ ใช้ `border` 1px + พื้น `default-50` พอ
4. **ตัวแก้ที่แสดงตัวแปรเป็นชิปไม่มีใน theme/paces:** ทำได้เป็น `contenteditable` แต่เสี่ยงกับการพิมพ์ภาษาไทยผ่าน IME ผมเสนอทางหลักตามที่ user ขอ พร้อมทางถอย `textarea` ให้ Controller เคาะ (U-A)
5. **หน้านี้ "ปิดงาน" ไม่ใช่ "จบงาน":** ระบบ 00073 เรียกขั้นสุดท้ายว่า **ปิดงาน** (ปุ่ม, ป้ายสถานะ, `closeServiceJob`) คำของ user คือ "จบงาน" ผมใช้ "ปิดงาน" ทุกที่ตาม HR16 (U-B)
6. **เพดาน 3 ข้อความต่อลูกค้าต่อวันชนกับ 3 จังหวะของร้านบริการพอดี:** งานเดียวที่สร้าง-เริ่ม-ปิดในวันเดียวใช้โควตาหมด งานที่สองของลูกค้าคนเดียวกันวันนั้นจะไม่ได้รับข้อความ (U-C)
7. **ตารางลิงก์ขนส่ง: แสดงอ่านอย่างเดียวในหน้านี้** ไม่ให้ร้านแก้ ลิงก์ผิดจะถึงลูกค้าโดยตรง และผมยืนยันได้แค่ Flash (จาก user) ว่าเป็นลิงก์หน้าติดตาม ส่วนว่ารับเลขใน query ได้ไหมยังไม่ยืนยัน
8. **ปุ่ม "เริ่มงาน" อยู่ใน `ServiceJobCard` เหนือปุ่ม "ปิดงาน"** เป็นปุ่มรอง (tonal) ไม่แย่งความเป็นพระเอกของ "ปิดงาน" (ซึ่งเป็นตัวที่เงินเข้ายอดขาย)
9. **ช่องค่าส่งที่ร้านจ่ายขนส่ง:** ใต้ "เลขพัสดุ" ใน `ShipForm` เป็น `input-group` ฿ แบบเดียวกับต้นทุนสินค้า ไม่บังคับ ว่าง ≠ 0

## 3. Section breakdown

### A. สถานะการส่ง (พระเอกของหน้า)

- Base: radiogroup ปุ่ม `btn min-h-11` จาก `ReportSettingsForm.tsx` (ตัวที่เลือก `bg-primary text-white`, ที่เหลือ `border-default-300 text-default-700 hover:bg-default-100`)
- ต้องมี arrow-key (roving tabindex) ตาม ARIA radiogroup ซึ่งตัวต้นแบบไม่มี ให้เพิ่ม
- **สีของสถานะไม่ใช้เขียว:** "เปิด" = ปุ่มที่เลือกเป็น primary เหมือนอีกสองตัว ความต่างสื่อด้วย **ข้อความประโยคใต้ปุ่ม** + ชิปด้านขวาของหัวการ์ด (ปิด = `bg-default-200 text-default-800`, ทดสอบ = `bg-warning/15 text-warning-ink`, เปิด = `bg-primary/15 text-primary-ink`) เหตุผล: เขียวสงวนให้ "ยืนยันแล้ว" (Verified-Means-Green) ส่วนเปิดส่งจริงคือการกระทำ ไม่ใช่การยืนยัน

| สถานะ | ประโยคใต้ปุ่ม |
|---|---|
| ปิด | "ปิดอยู่ ระบบไม่ส่งอะไรถึงลูกค้า ตั้งข้อความและเปิดสวิตช์ของแต่ละจังหวะไว้ก่อนได้" |
| ทดสอบ | "ส่งเฉพาะห้องทดสอบ {n} ห้อง ลูกค้าห้องอื่นไม่ได้รับอะไร" |
| เปิด | "เปิดอยู่ ระบบส่งตามจังหวะที่เปิดสวิตช์ไว้ ({n} จังหวะ) ไม่ส่งย้อนหลัง" |
| เปิด แต่ไม่มีจังหวะที่เปิดสวิตช์ | "เปิดอยู่ แต่ยังไม่มีจังหวะที่เปิดสวิตช์ ระบบจึงยังไม่ส่งอะไร" (กล่อง info `bg-info/15 text-info-ink`) |

- **เปลี่ยนเป็น "เปิด"** ต้องถามยืนยัน ผ่าน `pacesConfirm.warning` (Sweet Alerts ตาม HR8 ข้อ alert) ครั้งเดียวที่ประตู ไม่ถามที่สวิตช์ย่อย:
  - หัว: "เปิดให้ระบบส่งข้อความถึงลูกค้าจริง?"
  - เนื้อ: "ตั้งแต่ตอนนี้ {n} จังหวะที่เปิดสวิตช์ไว้จะส่งถึงลูกค้าในแชทที่ผูกกับ{noun} ไม่ส่งย้อนหลัง"
  - ปุ่ม: "เปิดส่งจริง" / "ยังก่อน" (`focusCancel: true`)
  - เหตุผลที่ขัดกับรอบแรก (รอบแรกไม่มีการยืนยัน): รอบแรกไม่มีประตูหลัก สวิตช์ทุกตัวเป็นการตัดสินใจเล็ก ๆ รอบนี้มีประตูเดียวที่เปลี่ยนจาก "ไม่มีผลกับลูกค้า" เป็น "ส่งถึงคนจริง" ซึ่งเป็นรูปเดียวกับที่ `OrderAgentClient` ใช้ถามตอนเปลี่ยนเป็น LIVE
  - ปิด และ ปิด→ทดสอบ ไม่ถาม
- **เพดานต่อวัน:** `input-group` มีช่องตัวเลข (`type="number" min=1 max=10 inputMode="numeric"`) และข้อความ "ข้อความ / ลูกค้า / วัน" เป็น suffix, บันทึกเมื่อ blur หรือ Enter ด้วย toast, ค่าตั้งต้น 3 (วันนับตามเวลาไทย) คำอธิบายใต้ช่อง: "นับรวมทุกจังหวะ เกินเพดานแล้วระบบไม่ส่งข้อความเพิ่มให้ลูกค้าคนนั้นจนถึงวันถัดไป" (U-C)

### B. ห้องทดสอบ (โผล่เฉพาะสถานะ "ทดสอบ")

- การ์ดแยกใต้การ์ดสถานะ ใช้ท่า `TestThreadsCard.tsx` ทั้งดุ้น (ตารางห้อง, ปุ่มเพิ่มห้อง, `pacesConfirm` ก่อนเพิ่มเพราะ "ระบบจะส่งข้อความถึงคนจริง" ในห้องนั้น)
- ข้อจำกัด 1-20 ห้อง (ตามที่ gochat-v3 ใช้) ถ้า 0 ห้อง: info "ยังไม่มีห้องทดสอบ ระบบจะไม่ส่งอะไรเลยจนกว่าจะเพิ่ม" พร้อมปุ่ม "เพิ่มห้องทดสอบ"
- `TestThreadsCard` เป็นของ "กลุ่มคำหนึ่ง ๆ" ไม่ใช่ของทั้งร้าน ชุดนี้ต้องการรายการห้องระดับร้านของตัวเอง ไม่ใช้ร่วมกับรายการของบอทเพราะสองรายการต่างความหมาย (บอทตอบเมื่อลูกค้าทัก vs ระบบส่งเมื่อเกิดเหตุการณ์) ถ้ารวมกัน การเพิ่มห้องในอันหนึ่งจะเปลี่ยนพฤติกรรมอีกอันโดยไม่รู้ตัว (U-D)

### C. จังหวะที่ส่ง

หนึ่งการ์ด `divide-y` หนึ่งแถวต่อจังหวะ (ไม่ใช่การ์ดต่อจังหวะ ไม่งั้นการ์ดซ้อนการ์ดเมื่อกางตัวแก้)

**หัวแถว (ปิดอยู่):**
- ไอคอนซ้าย: T1 `file-invoice`, T2 `truck-delivery`, T3 `player-play`, T4 `clipboard-check` (ตรงกับปุ่ม "ปิดงาน" ใน `ServiceJobCard.tsx:144`)
- ชื่อจังหวะ `text-sm font-medium text-default-900` + สวิตช์ขวา
- บรรทัดสอง `text-xs text-default-700`: สถานะ ("ปิดอยู่" / "เปิดอยู่ · เปิดเมื่อ {วันเวลา} โดย {ชื่อ}")
- บรรทัดสาม `text-xs text-default-600 truncate`: "ข้อความของร้าน: {ย่อหน้าแรก}" หรือ "ใช้ข้อความตั้งต้น" + ปุ่ม `btn btn-sm` "แก้ข้อความ" (มือถือ 44px จาก override)
- เมื่อสถานะชุดไม่ใช่ "เปิด": บรรทัดสถานะเติม " · ยังไม่ส่งเพราะชุดปิดอยู่" / " · ส่งเฉพาะห้องทดสอบ" เพื่อไม่ให้สวิตช์ ON หลอกว่ากำลังส่ง
- แถวที่กางอยู่: `border-s-3 border-primary` + พื้น `bg-primary/10`? ไม่ใช้พื้นสี (ซ้ำกับแถวเลือกในรายการแชท) ใช้แค่แถบซ้าย

**ตัวแก้ (กางใต้แถว)** เรียงบนลงล่าง:
1. **ตัวอย่างสำเร็จรูป:** กลุ่มปุ่ม segmented 3 ปุ่ม "มาตรฐาน / สั้น กระชับ / เป็นกันเอง" (ท่า `ChatbotTabs.tsx`: `bg-light flex gap-0.5 rounded-lg p-1`, ปุ่ม `min-h-11`) กดแล้วเติมลงตัวแก้ ยังไม่บันทึก ถ้าข้อความแก้ค้างอยู่ถามก่อน (`pacesConfirm.warning` "ใช้ตัวอย่างนี้แทนข้อความที่แก้อยู่?" / "ใช้ตัวอย่างนี้" / "เก็บข้อความเดิม") มือถือเลื่อนแนวนอนได้
2. **แถบเครื่องมือ:** ซ้าย `btn btn-sm` "+ ตัวแปร" (ไอคอน `plus`) · ขวา ตัวนับ "123/500" (`text-xs`; ≥450 `text-warning-ink`; =500 `text-danger-ink` และหยุดรับตัวอักษรเพิ่ม)
3. **ตัวแก้ข้อความ:** กล่อง `form-input` สูงอย่างน้อย `min-h-32` (≈8rem) แสดงตัวแปรเป็นชิป `badge rounded-full bg-primary/15 text-primary-ink text-2xs` ลบทั้งชิปด้วย Backspace
4. **ข้อผิดพลาด/คำเตือนใต้ตัวแก้** (ดู §7)
5. **พรีวิว** (เฉพาะมือถือ; เดสก์ท็อป/แท็บเล็ตอยู่คอลัมน์ขวา)
6. **แถวปุ่ม:** ปุ่มหลัก "บันทึกข้อความ" (`btn bg-primary text-white min-h-11`) · "คืนค่าตั้งต้น" (ปุ่ม ghost `border-default-300`, ปิดเมื่อข้อความตรงกับค่าตั้งต้นอยู่แล้ว) · "ยกเลิก" (ข้อความล้วน) · บรรทัดเล็ก "แก้ไขล่าสุดโดย {ชื่อ} {วันเวลา}" (กันกรณีสองคนแก้พร้อมกันที่คนหลังชนะ)
- แถวที่กางอยู่ได้ทีละแถว กางแถวอื่นขณะข้อความค้างอยู่ → ถามเก็บ/ทิ้ง (ท่า `closeSettings` ใน `ShippingSettingsRow.tsx`)

**พฤติกรรมตัวแก้:**
- พิมพ์ `{` → เมนูรายการตัวแปรโผล่ที่ตำแหน่งเคอร์เซอร์ (ตัวกรองตามที่พิมพ์ต่อ) เลือกด้วย ↑↓ Enter หรือแตะ Esc ปิด · ปุ่ม "+ ตัวแปร" เปิดเมนูชุดเดียวกัน (วางใต้ปุ่ม) · แต่ละรายการแสดง **ชื่อตัวแปร + ค่าตัวอย่าง** (`text-xs text-default-600`) · รายการสูงอย่างน้อย 44px บนมือถือ
- ตัวแปรที่ว่าง: ตัวแปรหาย, บรรทัดที่ตัวแปรทุกตัวว่างถูกตัดทั้งบรรทัด, บรรทัดว่างติดกันยุบ (พรีวิวแสดงผลนี้จริง ติ๊ก "ลองกรณีข้อมูลไม่ครบ" เพื่อเห็นเอง)
- การบันทึกจริงเป็นข้อความ `{ชื่อไทย}` ธรรมดา (ไม่เก็บ HTML)

### D. พรีวิว (กรอบแชทตัวอย่าง)

- คอลัมน์ขวา `lg:sticky lg:top-20` ในหน้านี้ (เลี่ยง `top-*` arbitrary; ใช้ scale มาตรฐาน) แสดงจังหวะที่กางอยู่ ถ้าไม่มีแถวกาง แสดงจังหวะแรกที่สวิตช์ ON ถ้าไม่มีเลย แสดงจังหวะแรกของร้านพร้อมป้าย "ตัวอย่างจากข้อความตั้งต้น"
- โครง: `card` + `card-header` (เส้นประ) ชื่อ "ตัวอย่างข้อความ" + ชิปเหตุการณ์ (`badge bg-default-200 text-default-800`, เช่น "เมื่อสร้างงานบริการเสร็จ") → กรอบแชท (`border border-default-300 bg-default-50 rounded-lg p-3`) มีแถบบน (รูปร้าน + ชื่อร้าน ตัดด้วย `truncate`) → ฟองข้อความฝั่งร้านในมุมมองลูกค้า: `bg-default-200 text-default-900 rounded px-4 py-3 text-sm`
- **ตัวเลือกช่องทาง** (เฉพาะจังหวะ T1, เพราะรูปต่างกัน) segmented 3 ปุ่ม "Messenger/IG | LINE | Deep":
  - Messenger/IG: ฟองข้อความเทมเพลต (ลิงก์เป็นตัวหนังสือธรรมดา)
  - LINE: **การ์ด Flex** (ชื่อรายการ, "และอีก n รายการ", ยอดสุทธิ, ปุ่มเปิดลิงก์) โดยข้อความเทมเพลตอยู่ส่วนบนของการ์ดใบเดียวกัน (U-E)
  - Deep: การ์ด ORDER ในแชทเดิม + ข้อความเทมเพลต
  - T2-T4 ไม่มีตัวเลือกช่องทาง (ข้อความธรรมดาทุกช่อง)
- ใต้กรอบ: ติ๊ก `form-checkbox` "ลองกรณีข้อมูลไม่ครบ" (ทำให้ชื่อลูกค้า, ขนส่ง, ลิงก์ติดตามว่าง) และบรรทัดบอกขนาดข้อความหลังเติมตัวแปร ("ยาว {n} ตัวอักษรหลังเติมข้อมูลจริง") เพราะเทมเพลต 500 ตัวมีตัวแปรรายการยาวได้เกินที่เห็น
- พรีวิวคำนวณจากฟังก์ชันตัวเดียวกับตัวส่งจริง (ตัวสร้างข้อความร่วม) ห้ามเขียนตัวเรนเดอร์ที่สองในหน้านี้ (HR16)
- ห้ามสุ่ม/ปั้นรายละเอียดการ์ด LINE เอง ม็อกอัพวาดเป็นกรอบการ์ดมีหัวข้อ-ยอด-ปุ่ม ตามโครงที่ `buildLineFlexOrderCard` รับ (title, extraItemCount, totalText, url, noun, buttonLabel)

### E. ลิงก์ติดตามพัสดุตามขนส่ง (อ่านอย่างเดียว)

- แสดงเฉพาะร้าน ONLINE_SALES
- การ์ดตาราง Paces (`table-wrapper` + `table`, ท่าเดียวกับ `TestThreadsCard`) เพราะหน้านี้เป็นที่เดียวที่ร้านเห็นว่า `{ลิงก์ติดตาม}` กลายเป็นอะไร และเป็นหลักฐานให้ตอบ Q-18

| ขนส่ง | ลิงก์ติดตาม | วิธีแนบเลข |
|---|---|---|
| Flash Express | `https://www.flashexpress.co.th/fle/tracking` | ลิงก์หน้าติดตาม + เลขแยกบรรทัด (ยังไม่ยืนยันว่ารับเลขใน query) |
| Kerry Express, Thailand Post, J&T Express, DHL | **รอยืนยัน** (ห้ามเดา ใส่ "รอยืนยัน" ในม็อกอัพ) | รอยืนยัน |
| อื่นๆ | ไม่มีลิงก์ | บรรทัดลิงก์ถูกตัด (BR-CS-C09) |

- คอลัมน์ "วิธีแนบเลข" เป็นชิป: "ลิงก์มีเลขในตัว" (`bg-default-200 text-default-800`) / "ลิงก์ + เลขแยกบรรทัด" (เหมือนกัน) / "ไม่มีลิงก์" ไม่ใช้เขียวหรือแดง
- คำอธิบายใต้ตาราง: "ตัวแปร {ลิงก์ติดตาม} ใช้ลิงก์ตามขนส่งที่เลือกตอนกรอกเลขพัสดุ ถ้าไม่มีลิงก์ของขนส่งนั้น ระบบตัดบรรทัดลิงก์ออก"
- **ไม่ให้แก้ในหน้านี้** เหตุผล: (1) ลิงก์ผิดถึงลูกค้าโดยตรงและไม่มี validation ว่าหน้าปลายทางรับเลข (2) ข้อมูลเป็นของระบบ (ใช้ร่วมกับข้อความแจ้งเลขแบบกดเอง) ไม่ใช่ของร้าน (3) รายชื่อขนส่งต้องตรงกับ `CARRIERS` ใน `ShipForm.tsx` (6 ตัว) และชื่อขนส่งจาก iShip ซึ่งสะกดไม่ตรงกัน ("KEX Express" vs "Kerry Express" ตามคอมเมนต์ใน ShipForm) ต้องมีตารางจับคู่เดียวใน `src/lib` (U-F)
- ข้อความแจ้งเลขแบบกดเอง (`trackingMessage()`) ต้องใช้ตารางเดียวกัน (PRD §13 ข้อ 3) แทนลิงก์ iShip ลิงก์เดียวเดิม

ไฟล์: `src/app/(paces)/seller/(dashboard)/orders/[token]/components/ServiceJobCard.tsx`

**หลักฐานจากโค้ด:** การ์ด "งานนี้" เป็นที่เดียวที่มี "ปิดงาน" ในหน้ารายละเอียด และ `ServiceCloseSheet` ตัวเดียวกันถูกเรียกจากหน้างาน/บอร์ดคิว/แชท (`OrderProgressBar.tsx:153`) 00073 ตัดขั้น "เริ่มบริการ" ทิ้งโดยเจตนา การเพิ่มต้อง **ไม่เปลี่ยนสถานะ** และไม่ทำให้ปิดงานต้องผ่านการเริ่มก่อน

```
ยังไม่เริ่ม                          เริ่มแล้ว (ยังไม่ปิด)
┌ งานนี้          [จองแล้ว] ┐        ┌ งานนี้       [จองแล้ว] ┐
│ ทำงานเสร็จแล้วกด "ปิดงาน"…  │        │ เริ่มงานเมื่อ 10:12 น.   │
│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │        │ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │

└─────────────────────────────┘
```

- **ปุ่ม "เริ่มงาน":** `btn bg-primary/15 text-primary hover:bg-primary/25 min-h-11 w-full gap-2` ไอคอน `player-play` วางเหนือ "ปิดงาน" ในกล่องเดียวกัน (คั่นเส้นประเดิม) ไม่ใช่ปุ่มทึบ เพราะ "ปิดงาน" คือการกระทำที่เงินเข้ายอดขายและ 00073 ตั้งให้เป็นพระเอก
- ลำดับ: ยังไม่เริ่ม → แสดง "เริ่มงาน" (tonal) + "ปิดงาน" (primary) · เริ่มแล้ว → แทนที่ปุ่มเริ่มด้วยบรรทัดข้อความ "เริ่มงานเมื่อ {เวลา}" `text-sm text-default-700` · ปิดแล้ว/ยกเลิกแล้ว/ไม่มาตามนัด → ไม่แสดงปุ่มเริ่ม
- ไม่มี "ยกเลิกการเริ่มงาน" ในรอบนี้ (ข้อความที่ส่งไปแล้วเรียกคืนไม่ได้ การมีปุ่มถอนจะสื่อว่าถอนได้)
- **เมื่อสวิตช์ T3 ทำงานจริง** (สถานะชุดเปิด หรือทดสอบและห้องนี้เป็นห้องทดสอบ + ผูกห้อง): กดแล้วถาม `pacesConfirm.warning` "เริ่มงานและแจ้งลูกค้า?" / เนื้อ "ระบบจะส่งข้อความเริ่มงานให้ลูกค้าในแชททันที" / "เริ่มงานและแจ้งลูกค้า" / "ยังไม่เริ่ม" (ผู้ขายกดผิด = ข้อความถึงลูกค้าจริง ซึ่งแก้คืนไม่ได้) · เงื่อนไขอื่น: กดครั้งเดียว บันทึกด้วย toast "บันทึกเวลาเริ่มงานแล้ว" ไม่ถามอะไร
- ไม่ปรากฏกับร้าน ONLINE_SALES และ LODGING
- **ไม่ถูกจำกัดด้วย "ยังไม่ถึงเวลานัด"** ต่างจากปุ่มปิดงาน (BR-RSV-34) ช่างอาจเริ่มก่อนนัดจริง เวลาที่บันทึกคือเวลาที่กด
- สิทธิ์: ผูกกับสิทธิ์ปิดงาน (O4) เหมือน `canClose` เพราะบทบาทฝ่ายช่างเป็นคนเริ่มงานจริง (U-G)
- ที่อื่นที่ควรมี (รอบถัดไป ไม่บังคับ): การ์ดงานในบอร์ดคิว `queues/page.tsx` และชีตสถานะออเดอร์ในแชท ผ่านคอมโพเนนต์เดียวกัน (ปุ่มเริ่มงานเป็นคอมโพเนนต์ที่ `ServiceJobCard` เรียก ไม่ก๊อป)
- a11y: ปุ่มมีข้อความ "เริ่มงาน" ไอคอน `aria-hidden`; บรรทัด "เริ่มงานเมื่อ…" เป็นข้อความธรรมดา

## 5. ช่องค่าส่งที่ร้านจ่ายขนส่ง (`ShipForm`)

ไฟล์: `src/app/(paces)/seller/(dashboard)/orders/[token]/components/ShipForm.tsx` (ใช้ทั้งหน้าต่างพัสดุแชทผ่านแท็บ "ส่งเอง" และหน้ารายละเอียดออเดอร์ผ่าน `ShippingCard`/`ShipmentEntryModal`)

```
ขนส่ง *            [-- เลือกขนส่ง --      v]
เลขพัสดุ *         [เช่น TH123456789        ]
ค่าส่งที่ร้านจ่ายขนส่ง
                   [฿] [0.00               ]
ต้นทุนของร้าน ไม่แสดงให้ลูกค้า — หักในกำไรของ{noun}นี้
```

- **ตำแหน่ง:** ใต้ "เลขพัสดุ" เป็นช่องที่ 3 (ช่องบังคับมาก่อนช่องไม่บังคับ)
- **ป้าย:** "ค่าส่งที่ร้านจ่ายขนส่ง" (คำของ user) ไม่ใช้ "ต้นทุนค่าส่ง" เพราะ "ค่าส่ง" เป็นคำที่ iShip ใช้ในฟอร์มเปิดพัสดุแล้ว (`ShipmentCreateForm.tsx:1048` "ค่าส่งโดยประมาณ") ให้ผู้ขายอ่านเป็นเรื่องเดียวกัน; คำอธิบายใต้ช่อง ("ต้นทุนของร้าน ไม่แสดงให้ลูกค้า") กันสับสนกับค่าส่งที่เก็บจากลูกค้า
- **รูปแบบ:** `input-group` + `input-group-text` ฿ + `form-input` `type="number" step="0.01" min="0" inputMode="decimal"` `placeholder="0.00"` ท่าเดียวกับ `ProductCostCardV2.tsx:66`
- **ไม่บังคับ, ว่าง ≠ 0:** ว่าง = "ยังไม่ระบุ" บันทึกเป็น null ไม่ใช่ 0 (docs/conventions/partial-data-must-be-labeled-or-filled.md) ในหน้ากำไรของคำสั่งซื้อ ต้องแยกให้ออก "ยังไม่ใส่ค่าส่ง" กับ "ค่าส่ง ฿0"
- **เมื่อกรอกแล้ว:** ใต้ช่องแสดง "หักในกำไรของ{noun}นี้ ฿{ค่า}" ด้วย `formatBaht` (`text-xs text-default-700`) ไม่มีเครื่องหมายลบชน ฿
- **ข้อผิดพลาด:** "ค่าส่งต้องเป็นตัวเลขตั้งแต่ 0 ขึ้นไป" ผูก `aria-describedby`/`aria-invalid` เหมือนช่องอื่นในฟอร์ม · เพดาน 99,999.99
- **โหมดแก้ไข (`mode="edit"`):** แสดงค่าเดิม แก้ได้ในฟอร์มเดียวกัน
- **ไม่ทำกับพัสดุ iShip:** ค่าส่งมาจาก iShip ตอนเปิดพัสดุแล้ว (PRD §13 ข้อ 6 ระบุเฉพาะแท็บส่งเอง) ฟอร์ม iShip ไม่เปลี่ยน
- **ไม่ส่งเข้าข้อความถึงลูกค้า** ไม่มีตัวแปรเกี่ยวกับค่านี้

## 9. a11y

- radiogroup สถานะ: `role="radiogroup"` + `aria-label="สถานะการส่ง"`, ปุ่ม `role="radio"` `aria-checked`, roving tabindex, ←→ ย้ายและเลือก
- สวิตช์: `<input type="checkbox" class="form-switch">` ผูก `<label htmlFor>` (ท่าต้นแบบ) · ความกว้างพื้นที่แตะ 44px มือถือจาก override ใน `safepay-overrides.css` · ค่าเปิด/ปิดมีข้อความ ไม่สื่อด้วยสีสวิตช์อย่างเดียว
- ตัวแก้: `role="textbox" aria-multiline="true" aria-label="ข้อความที่ส่งเมื่อ{จังหวะ}"` `aria-describedby` ไปที่ตัวนับ + ข้อผิดพลาด · ชิป `contenteditable="false"` มี `aria-label="ตัวแปร ชื่อลูกค้า"` · เมนูตัวแปร `role="listbox"`, รายการ `role="option"`, `aria-activedescendant`, ปิดด้วย Esc แล้วคืนโฟกัสให้ตัวแก้ · ตัวนับประกาศ (`aria-live="polite"`) เฉพาะตอนข้ามเกณฑ์ 450 และ 500 ไม่ประกาศทุกตัวอักษร
- พรีวิว: `role="region" aria-label="ตัวอย่างข้อความที่ลูกค้าจะได้รับ"` ไม่ใช้ `aria-live` (อัปเดตทุกการพิมพ์จะรบกวน screen reader)
- เป้าแตะ ≥44px มือถือ: ปุ่มตัวอย่าง, "+ ตัวแปร", รายการเมนู, ปุ่มแก้/บันทึก/คืนค่า
- คอนทราสต์: ทุกข้อความ `default-700/600` บนพื้นขาว ≥7:1; ชิปตัวแปรผ่านคู่ -ink; ข้อความ `text-2xs` เฉพาะในชิป (ขนาดเดียวกับชิปทั่วระบบ)
- `prefers-reduced-motion`: การกาง/หุบแถวไม่ต้องมีแอนิเมชัน (ไม่ใส่ transition)
- โฟกัส: เมื่อกดแก้ข้อความ ย้ายโฟกัสเข้าตัวแก้; เมื่อบันทึกแล้วคืนโฟกัสปุ่ม "แก้ข้อความ" ของแถวเดิม

## 11. Impeccable compliance

- **Mode: Operate** (ฟอร์มตั้งค่า รายการสวิตช์ ตาราง ผู้ขายใช้เป็นงานตั้งค่าครั้งเดียวแล้วกลับมาแก้ นาน ๆ ครั้ง) · scanability + ความคุ้นเคยของ pattern Paces ชนะการแสดงออก
- **พระเอก:** สถานะการส่ง (ปุ่มใหญ่ 44px, ประโยคอธิบายเข้มที่สุดใต้ปุ่ม) ที่เหลือถอย: จังหวะ (default-900 ชื่อ, 700/600 คำอธิบาย) → ตารางขนส่ง (อ้างอิง) → ข้อควรรู้ (เบาสุด)
- **จุดใช้ accent สีธีม (น้ำเงิน primary):** ปุ่มที่เลือกใน radiogroup · สวิตช์ ON · แถบซ้ายของแถวที่กางอยู่ · ปุ่ม "บันทึกข้อความ" · ชิปตัวแปร (`bg-primary/15`) ไม่ใช้ในที่อื่น ไม่มีปุ่ม primary มากกว่า 1 ตัวต่อโซน (ปุ่ม "เริ่มงาน" เป็น tonal เพื่อไม่แข่งกับ "ปิดงาน")
- **Verified-Means-Green:** ไม่มีเขียวเลย "เปิด" ไม่ใช่การยืนยัน
- **ม่วง:** หน้านี้ไม่ใช้ม่วง (ม่วง `--color-purple` เป็นของขอบรูปในรอบแรกเท่านั้น)
- **Sentence-case / น้ำเสียง:** บอกเหตุและทางออก ("ข้อความว่างไม่ได้ พิมพ์ข้อความ หรือกด ‘คืนค่าตั้งต้น’") ไม่ใช้ "ไม่สามารถ"/"คุณไม่มีสิทธิ์" ไม่ไฮป์ ไม่มี emoji
- **เงาผสมหมึก:** ไม่เพิ่มเงาใหม่ (การ์ดใช้ `--shadow` ของธีม)
- **ที่ theme ขัดกับ Impeccable:** (1) รูปแบบกรอบแชทตัวอย่างไม่มีใน theme ผมเลือกไม่วาดโทรศัพท์ตามข้อ "ไม่ตกแต่ง" (2) `border-s-3 border-primary` เป็นข้อยกเว้นที่ขึ้นทะเบียนใน DESIGN.md สำหรับ `(paces)` (3) ตัวแก้ contenteditable ไม่มี primitive ให้ copy ระบุไว้ชัดแล้ว (HR1)
- **ให้ Controller เพ่งตอน critique:** ความหนาแน่นของแถวที่กาง (ตัวแก้ + พรีวิว + ปุ่ม 3 ตัว บนมือถือยาวมาก), การใช้ชิป `bg-primary/15` จำนวนมากในตัวแก้ (One Voice), ลำดับ "ปิดงาน/เริ่มงาน" ว่าพระเอกยังชัด
