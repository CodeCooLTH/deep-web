งาน A — ThreadContextBar ยุบแถบ “ที่มา” ให้เหลือบรรทัดเดียว

ปัญหาที่ user ชี้ (สถานะปัจจุบันบน prod)

  • ใต้หัวเธรดมีแถบได้ถึง 5 ชั้น — ชื่อร้าน ~28px · โฆษณา ~57px · คอมเมนต์ ~57px · สถานะห้อง ~52px · สถานะนัด ~56px
  • เคสในภาพโดน 3 ชั้น = ~170px บวกหัวเธรด 61px ≈ 29% ของจอ ก่อนเห็นข้อความแรก
  • ชั้นสถานะห้อง/สถานะนัด เคยผ่านรอบยุบมาแล้ว ตั้งแต่ 2026-08-02 ด้วยเหตุผลเดียวกันเป๊ะ — โฆษณากับคอมเมนต์คือสองอันที่ตกหล่นเพราะถูกเพิ่มคนละเวลา

กติกาที่ต้องไม่หลุดตอน implement

  • ชื่อร้านเป็น items[0] เสมอ — คอมเมนต์ใน ChatThread.tsx:2075 เขียนไว้เองว่านี่คือข้อมูลที่ต้องรู้ ก่อนพิมพ์ ซ่อนแล้วผู้ขายตอบผิดร้าน ซึ่งถอนคืนไม่ได้
  • พื้นโปร่ง ห้าม bg-{semantic}/15 — ThreadStatusBar ที่อยู่ถัดลงมาใช้พื้นสีอยู่แล้ว สองแถบสีติดกันจะอ่านเป็นบล็อกเดียวที่แยกไม่ออกว่าอันไหนคือคำเตือน
  • แถวเต็มความกว้าง + border-b ไม่ใช่การ์ดลอย — user report 2026-07-26 ตัดสินไปแล้วว่าการ์ดลอยทำให้มีช่องว่างคั่นหัวแชท
  • ยุบเป็นค่าตั้งต้นเสมอ ไม่จำสถานะกาง — เหมือน ThreadStatusBar/OrderProgressBar ทุกประการ
  • detail ของแต่ละรายการคือ JSX เดิมยกมาทั้งก้อน ไม่แก้เนื้อใน — งานนี้เปลี่ยนที่เก็บ ไม่ได้ออกแบบเนื้อหาใหม่

4 จุดที่มีปุ่ม “ส่งสรุปนัด” — เปิดชีตตัวเดียวกันทั้งหมด (มติ D-2/D-4)

  • แผงลูกค้าข้างแชท — ร้าน SERVICE_QUEUE ที่ออเดอร์มีนัด: ปุ่มแรกใน footer เปลี่ยนคำจาก “ส่งเข้าแชท” เป็น “ส่งสรุปนัด” (ไม่เพิ่มปุ่มที่ 3 — ร้านคิวงานได้ NO_SHIPPING จึงไม่มีปุ่ม “สร้างพัสดุ” อยู่แล้ว)
  • แถบสถานะนัดในห้องแชท (ตอนกาง) — คอมเมนต์ที่ OrderProgressBar.tsx:146 เขียนไว้เองว่าการ์ดนี้อ่านอย่างเดียวเพราะ “ถ้าจะให้กดได้ = งานรอบถัดไป ผ่าน ux” — นี่คือรอบนั้น
  • /orders/[token] และ ปฏิทิน /queues — สองจุดนี้ ไม่มี conversationId ต้อง resolve จาก Conversation.customerId = Order.customerId โดย shopId ต้องอยู่ใน WHERE เป็นคีย์แรก (Customer เป็นตาราง global — query ด้วย customerId เปล่าจะได้ห้องแชทของร้านอื่น)
  • 0 ห้อง → ปุ่ม disabled พร้อมเหตุผล “ลูกค้ารายนี้ยังไม่มีห้องแชท” ห้ามซ่อนปุ่ม · 1 ห้อง → เปิดชีตตรง ๆ · >1 ห้อง → ชีตมีแถว “ส่งไปที่” ค่าตั้งต้น = คุยล่าสุด

ของที่มีอยู่แล้วแต่ไม่เคยมีทางเข้า — ปุ่มบนการ์ดปิดวงจรให้

  • (marketing)/o/[token]/AppointmentCard.tsx ให้ลูกค้ากด “ยืนยันนัด” / “ขอเลื่อนนัด” ได้จริงมาตั้งแต่ 00024 (เขียน CONFIRMED_BY_BUYER / RESCHEDULE_REQUESTED)
  • แต่ ไม่มีเส้นทางไหนพาลูกค้าไปถึงหน้านั้นเลย — ปุ่มบนการ์ดสรุปคือทางเข้าตัวแรก ⇒ สถานะที่ลูกค้ากดจะไหลกลับมาโผล่เองในปฏิทิน /queues และชิปในห้องแชท
  • ผลข้างเคียงที่ตั้งใจ: การ์ดนี้ไม่ใช่ป้ายอ่านอย่างเดียว มันคือจุดที่ร้านได้คำยืนยันกลับมาโดยไม่ต้องไล่ถาม
