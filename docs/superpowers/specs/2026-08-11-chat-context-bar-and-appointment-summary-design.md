## 1. ปัญหา (วัดจริงจากโค้ด ไม่ได้ประมาณ)

### 1.1 งาน A

ใต้หัวเธรดใน `ChatThread.tsx` มี "แถบ" ได้ถึง **5 ชั้นซ้อนกัน** แต่ละชั้นเป็นบล็อกของตัวเอง:

| ลำดับ | ชั้น | ที่มา | ความสูงโดยประมาณ (390px) |
|---|---|---|---|
| 1 | `กำลังตอบในนามร้าน X` | `ChatThread.tsx:2081` (00037) | ~28px |
| 2 | แบนเนอร์โฆษณา | `ChatThread.tsx:2098` (00018 E5) | ~57px |
| 3 | ที่มาคอมเมนต์ | `ChatThread.tsx:2167` (2026-08-10) | ~57px |
| 4 | `ThreadStatusBar` | ยุบเหลือบรรทัดเดียวแล้ว 2026-08-02 | ~52px (รวม `pt-4`) |
| 5 | `OrderProgressBar` | ยุบเหลือบรรทัดเดียวแล้ว 2026-08-05 | ~56px (รวม `pt-4`) |

เคสในภาพที่ user ส่งมาโดนชั้น 2+3+5 = **~170px** บวกหัวเธรด 61px ≈ **29% ของจอ** ก่อนเห็นข้อความแรก

🛑 **ข้อสังเกตที่ตัดสินทางแก้:** ชั้น 4 กับ 5 **เคยผ่านรอบยุบมาแล้ว** ด้วยเหตุผลเดียวกับที่ user กำลังบอกอยู่นี้ (`ThreadStatusBar.tsx:5` อ้าง user report 2026-08-02 ตรงตัวว่า *"การขึ้น alert box เยอะ ๆ ไม่ work มันรกหน้าจอมาก"*) — ชั้น 2 กับ 3 คือสองอันที่ **ไม่เคยผ่านรอบนั้น** เพราะถูกเพิ่มคนละเวลากัน ทางแก้จึงไม่ใช่การประดิษฐ์แพตเทิร์นใหม่ แต่คือการเอาแพตเทิร์นที่ตัดสินไปแล้วมาใช้กับสองอันที่ตกหล่น

### 1.2 งาน B

ท่อส่งการ์ดเข้าแชทมีอยู่ครบแล้ว — `CustomerPanel.tsx:333 sendToChat()` ยิง `POST /api/chat/conversations/[id]/messages` ด้วย `{ type:'ORDER', orderRefToken }` แล้ว route (`messages/route.ts:779`) ประกอบ **ข้อความที่ใช้ภาษาการซื้อของล้วน**:

```
คำสั่งซื้อ: {ชื่อรายการแรก}
ยอดสุทธิ ฿{ยอด}
https://deepthailand.app/o/{token}
```

ร้านคิวงานที่กดปุ่มนี้จึงส่ง **สิ่งที่ไม่มีวันนัด ไม่มีเวลา ไม่มีชื่อ ไม่มีเบอร์** ออกไป — ทั้งที่ทุกค่านั้นอยู่บนออเดอร์ใบเดียวกัน (`serviceStart` / `serviceEnd` / `buyerName` / `buyerContact` / `depositAmount` / `serviceResourceId`) ร้านเลยพิมพ์เองทุกใบ ซึ่งคือรูปหน้าจอที่ user ส่งมา

🛑 **ที่ต้องเห็นให้ชัด:** ปุ่ม "ส่งเข้าแชท" ที่มีอยู่ **ไม่ได้พัง** — มันทำงานถูกต้องทุกบรรทัดสำหรับสิ่งที่มันถูกเขียนมาเพื่อทำ (ออเดอร์ขายของ) สิ่งที่ขาดคือ **ร้านคิวงานไม่เคยมีคำของตัวเอง** งานนี้จึงเป็นการเติมสาขาที่หายไป ไม่ใช่การแก้บั๊ก

### 1.3 ของที่มีอยู่แล้วแต่ไม่มีทางเข้า (พบระหว่างสำรวจ)

`src/app/(marketing)/o/[token]/AppointmentCard.tsx` ให้ลูกค้ากด **"ยืนยันนัด"** และ **"ขอเลื่อนนัด"** ได้จริง (เขียน `appointmentStatus = CONFIRMED_BY_BUYER` / `RESCHEDULE_REQUESTED` ซึ่งไหลกลับไปโผล่ในปฏิทิน `/queues` และชิปในห้องแชท) — **แต่ทุกวันนี้ไม่มีเส้นทางไหนพาลูกค้าไปถึงหน้านั้นเลย** ปุ่มบนการ์ดสรุปจะเป็นทางเข้าตัวแรก

## 2. งาน A — `ThreadContextBar`

### 2.1 ขอบเขต

รวม **3 บล็อกที่ตอบคำถามเดียวกันว่า "แชทห้องนี้มาจากไหน / ฉันกำลังเป็นใคร"** ให้เหลือแถบเดียว:

- `กำลังตอบในนามร้าน X` (โหมดรวมหลายร้าน)
- แบนเนอร์โฆษณา
- ที่มาคอมเมนต์

**ไม่รวม** `ThreadStatusBar` (คำเตือน — มีโทน danger/warning) และ `OrderProgressBar` (ความคืบหน้าของงาน) เข้ามา: สามอย่างนี้ตอบคนละคำถาม และการยัดคำเตือนระดับ "ส่งข้อความไม่ได้" ลงไปเป็นชิปในแถวเดียวกับข้อมูลเฉย ๆ คือการลดเสียงของสิ่งที่ควรดังที่สุดบนจอ

### 2.2 สัญญาของ component

```ts
// src/app/(paces)/seller/(chat)/inbox/[conversationId]/components/ThreadContextBar.tsx
export interface ThreadContextItem {
  key: string
  /** ภาพย่อ 20px (รูปโฆษณา / ปกโพสต์) — null = ใช้ icon แทน */
  thumbUrl: string | null
  /** tabler icon — ทั้ง fallback ของ thumb และไอคอนนำในบรรทัดยุบ */
  icon: string
  /** คำนำสั้น ๆ ที่บอก "ประเภทของที่มา" — "จากโฆษณา" | "จากคอมเมนต์" | "ตอบในนามร้าน" */
  label: string
  /** เนื้อหาสำคัญที่สุดของรายการนั้น 1 บรรทัด (ตัดท้ายด้วย truncate) */
  short: string
  /** การ์ดเต็มตอนกาง — ยก JSX ของเดิมมาทั้งก้อน ไม่แก้เนื้อใน */
  detail: ReactNode
}

export default function ThreadContextBar({ items }: { items: ThreadContextItem[] }): JSX.Element | null
```

- `items.length === 0` → `return null`
- **ลำดับใน array = ลำดับความสำคัญ ตัวแรกคือตัวที่โชว์ตอนยุบ** (กติกาเดียวกับ `ThreadStatusBar` — caller เป็นคนเรียง)
- ลำดับที่ caller ต้องส่ง: **ร้าน → คอมเมนต์ → โฆษณา**

### 2.3 ทำไมร้านต้องเป็นตัวแรก (INVARIANT — ห้ามสลับ)

คอมเมนต์ที่ `ChatThread.tsx:2075` เขียนเหตุผลไว้เองว่าแถบชื่อร้านถูกวาง**เหนือ**ทุกอย่างเพราะ *"นี่คือข้อมูลที่ต้องรู้ **ก่อนพิมพ์** ส่วนอีกสองอันเป็นข้อมูลเฝ้าดูระหว่างคุย"*

ถ้าชื่อร้านไปอยู่หลัง `+N` ผลคือผู้ขายหลายร้าน **ตอบลูกค้าในนามร้านผิด** ซึ่งเป็นความเสียหายที่ถอนคืนไม่ได้ (ข้อความออกไปแล้ว) — ต่างจากการที่ผู้ขายไม่เห็นว่าแชทมาจากโฆษณาชิ้นไหน ซึ่งกดกางดูได้ตลอดเวลา

ผลลัพธ์ตามโหมด:

| โหมด | บรรทัดที่ยุบแสดง | badge |
|---|---|---|
| ร้านเดียว + คอมเมนต์ + โฆษณา | `จากคอมเมนต์ · ทุกรุ่นไหมคะ` | `+1` |
| รวมหลายร้าน + คอมเมนต์ + โฆษณา | `ตอบในนามร้าน BT Premium` | `+2` |
| ร้านเดียว + โฆษณาอย่างเดียว | `จากโฆษณา · เรามาแล้วครับ!` | — |

### 2.4 รูปทรง

**เป็นแถวเต็มความกว้างติดหัวแชท มี `border-b` ไม่ใช่การ์ดลอยที่มี padding รอบ**

เหตุผลไม่ใช่รสนิยม — `ChatThread.tsx:2099` บันทึก user report 2026-07-26 ไว้ว่าการ์ดลอยทำให้เกิดช่องว่างคั่นระหว่างหัวแชทกับแบนเนอร์ จึงถูกเปลี่ยนเป็นแถวเต็มความกว้างมาแล้วครั้งหนึ่ง (`ThreadStatusBar` ใช้ `px-4 pt-4` เป็นการ์ดลอยได้เพราะมันเป็น *คำเตือน* ที่ควรดูเหมือนของแปลกปลอมที่แทรกเข้ามา — แถบบริบทเป็นส่วนต่อของหัวเธรด)

```
ยุบ (สูง ~32px):
┌──────────────────────────────────────────────┐
│ ▣  จากคอมเมนต์ · ทุกรุ่นไหมคะ      +1    ⌄  │  border-b
└──────────────────────────────────────────────┘

กาง:
┌──────────────────────────────────────────────┐
│ [img40] แชทนี้ตอบกลับจากโฆษณาของคุณ        ✕ │  ← detail เดิม ไม่แก้
│         เรามาแล้วครับ! …          ดูโฆษณา    │
├──────────────────────────────────────────────┤
│ [img40] เรามาแล้วครับ! BT Premium …          │  ← detail เดิม ไม่แก้
│         💬 ทุกรุ่นไหมคะ           ดูคอมเมนต์  │
├──────────────────────────────────────────────┤
│ ⌃ ย่อที่มาของแชท                             │
└──────────────────────────────────────────────┘
```

class ของบรรทัดยุบ:

```
border-default-200 flex items-center gap-2 border-b px-4 py-1.5 text-xs
```

- ภาพย่อ `size-5 rounded object-cover shrink-0` · ไม่มีภาพ → `<Icon>` ขนาด `text-base`
- `label` = `text-default-700` · `short` = `text-default-800` ใน `<span className="min-w-0 flex-1 truncate">`
- badge `+N` = `bg-default-100 text-default-800 shrink-0 rounded px-1.5 text-2xs font-semibold` (**ไม่ใช่ `bg-card/60`** ที่ `ThreadStatusBar` ใช้ — ตัวนั้นวางบนพื้นสี `/15` แถบนี้พื้นโปร่ง)
- ปุ่มกาง `aria-expanded` + `aria-label` แยกกรณีมี/ไม่มี `+N` (บทเรียน WCAG 4.1.2 จาก `OrderProgressBar`)

### 2.5 โทนสี — ห้ามดังกว่าแถบที่อยู่ใต้มัน

พื้นโปร่ง ตัวอักษร `text-default-700/800` เท่านั้น **ห้ามใช้ `bg-{semantic}/15`** ใด ๆ

`ThreadStatusBar` ที่อยู่ถัดลงมาใช้ `bg-danger/15` / `bg-warning/15` / `bg-info/15` — ถ้าแถบบริบทมีพื้นสีด้วย ผู้ขายจะแยกไม่ออกว่าอันไหนคือ *"มีอะไรผิดปกติ"* กับ *"แชทนี้มาจากไหน"* และเมื่อโผล่พร้อมกันสองแถบสีติดกันจะอ่านเป็นบล็อกเดียวที่ตีความไม่ได้

ข้อยกเว้นเดียว: แถบชื่อร้านของเดิมใช้ `text-primary bg-primary/5` — **ค่านั้นถูกทิ้ง** เมื่อยุบรวม เพราะตอนนี้มันเป็นแค่ 1 ใน 3 รายการของแถบเดียวกัน ถ้ายังมีพื้นสีเฉพาะตัวจะกลายเป็นแถบที่เปลี่ยนสีไปมาตามว่ารายการแรกคืออะไร

### 2.6 ปุ่ม `✕` ปิดแบนเนอร์โฆษณา

**ย้ายไปอยู่ใน `detail` ตอนกางเท่านั้น** ไม่มีในบรรทัดยุบ

- ที่ 390px บรรทัดยุบมีงบพื้นที่: `px-4`(32) + thumb(20) + gap(8) + `+N`(24) + `⌄`(24) = 108px คงที่ เหลือ ~282px ให้ `label · short` — เติม `✕` เข้าไปเหลือ ~250px และได้ปุ่มสองตัวที่ **ผลลัพธ์ต่างกันคนละโลก** (ปิดถาวรต่อเธรด vs กางดู) วางห่างกัน 8px
- ปิดโฆษณาแล้วรายการหายจาก `items` → ถ้าเหลือรายการเดียวบรรทัดยุบเปลี่ยนเนื้อหาเอง ถ้าไม่เหลือเลยแถบหายทั้งแถบ
- localStorage key เดิม (`ChatThread.tsx:1189`) **ไม่แตะ** — สถานะที่ผู้ขายเคยปิดไว้ต้องยังจำได้หลัง deploy

### 2.7 พฤติกรรมการยุบ/กาง

- **ยุบเป็นค่าตั้งต้นเสมอ ไม่จำสถานะกาง** — เหมือน `ThreadStatusBar` และ `OrderProgressBar` ทุกประการ (ถ้าจำสถานะ ผู้ขายที่เผลอกางค้างไว้จะกลับไปเจอปัญหาเดิมทุกห้องโดยไม่รู้ว่าทำไม)
- ทำงานเหมือนกันทุก breakpoint — **ไม่มี `xl:` ที่กางเองบนจอใหญ่** (บทเรียน "one way, one behavior" จาก `OrderProgressBar` ที่ต้อง sync breakpoint กับ `CustomerPanel` ตลอด)

### 2.8 การแก้ `ChatThread.tsx`

ลบบล็อก `2081–2222` (3 ก้อน) แล้วแทนด้วย:

```tsx
<ThreadContextBar items={contextItems} />
```

โดย `contextItems` เป็น `useMemo` ที่ประกอบตามลำดับ ร้าน → คอมเมนต์ → โฆษณา และ **`detail` ของแต่ละตัวคือ JSX ก้อนเดิมยกมาทั้งดุ้น** (ย้ายเป็น helper component เล็ก ๆ ในไฟล์เดียวกัน: `ShopIdentityRow` / `CommentOriginRow` / `AdReferralRow`)

ตำแหน่งในลำดับ: **ใต้หัวเธรด เหนือ `ThreadStatusBar`** (ตำแหน่งเดิมของก้อนที่มันแทนที่)

## 3. งาน B — ส่งสรุปนัดหมายเข้าแชท

### 3.1 มติสถาปัตยกรรม: ไม่มี message type ใหม่

ฝั่งเราเก็บเป็น **`type:'ORDER'` + `orderRefToken` ตัวเดิม**

- `OrderCardView` แสดง `serviceStart` / `serviceEnd` / `appointmentStatus` / `depositAmount` **ได้อยู่แล้วตั้งแต่ 00024** (`CustomerPanel.tsx:381-387`)
- ⇒ ไม่มี migration · ไม่มีคอลัมน์ใหม่ · ไม่ต้องแก้ตัวอ่านฝั่งเธรด (`ChatThread.tsx:423 orderCard`) · การ์ดใบเก่าที่ส่งไปแล้วไม่เปลี่ยนหน้าตา
- สิ่งที่เปลี่ยนคือ **`body` ที่บันทึก** และ **payload ที่ยิงออกช่องทางนอก** เท่านั้น

### 3.4 API

```
POST /api/chat/conversations/{id}/messages
{
  "type": "APPOINTMENT",
  "orderRefToken": "…",
  "hiddenKeys": ["deposit"],
  "closing": "ยืนยันคิวเรียบร้อยค่ะ"
}
```

**ทำไม `type` ใหม่ที่ระดับ API ทั้งที่เก็บเป็น `ORDER`:** `type` ใน request คือ *"ผู้เรียกอยากให้ประกอบอะไร"* ส่วน `ChatMessage.type` คือ *"ของที่เก็บคือชนิดไหน"* — สองอันนี้ไม่จำเป็นต้องเท่ากัน และ route นี้มี precedent อยู่แล้ว (`IMAGE_GRID` ก็ไม่มีในตาราง) การใช้ `type:'ORDER'` แล้วดูจาก `serviceStart` ว่าจะประกอบแบบไหนคือการซ่อนสาขาไว้ใน implicit condition ซึ่งจะพังเงียบวันที่ร้านขายของมีออเดอร์ที่บังเอิญมี `serviceStart`

ด่านที่ route ต้องผ่าน (fail-closed ทุกข้อ):

1. `order.publicToken = orderRefToken AND order.shopId = conv.shopId` — ownership อยู่ใน `WHERE` ไม่ใช่ดึงมาเทียบทีหลัง
2. `order.serviceStart != null` — ไม่มีนัด → `400` `"คำสั่งซื้อนี้ไม่มีนัดหมาย"`
3. `shop.vertical === 'SERVICE_QUEUE'` (ผ่าน `canUseAppointments`) → ไม่ผ่าน `403`
4. `hiddenKeys` ผ่าน Valibot **allow-list** ของ `AppointmentSummaryKey` และ **ห้ามมี `'when'`** (ด่านที่สองของ S-1 — UI กันได้แค่คนที่เดินผ่านประตู)
5. `closing` ยาว ≤ `APPOINTMENT_CLOSING_MAX` · trim แล้วว่าง → ไม่มีบรรทัดปิดท้าย
6. `isTerminalAppointmentStatus(order.appointmentStatus)` → `400` `"นัดนี้จบแล้ว ส่งสรุปไม่ได้"` — ส่งใบยืนยันของนัดที่ให้บริการไปแล้ว/ไม่มาตามนัด คือการส่งข้อมูลที่ผิดออกไปหาลูกค้า

### 3.6 การหาห้องแชท (สำหรับปุ่มที่อยู่นอกห้องแชท)

`/orders/[token]` และ `/queues` **ไม่มี `conversationId`** ติดมากับหน้า

```ts
// GET /api/orders/{token}/conversations
prisma.conversation.findMany({
  where: { shopId: <activeShopId>, customerId: order.customerId },
  orderBy: { lastMessageAt: 'desc' },
  select: { id: true, channel: true, ... },
})
```

🛑 **`shopId` ต้องอยู่ใน `WHERE` เป็นคีย์แรกเสมอ** — `Customer` เป็นตาราง global (บทเรียน `DISTINCT ON ต้องมี shopId`) การ query ด้วย `customerId` เปล่า ๆ จะคืนห้องแชทของร้านอื่นที่ลูกค้าคนเดียวกันเคยคุยด้วย แล้วร้านจะส่งข้อมูลนัดของตัวเองเข้าห้องของร้านคู่แข่ง

| ผลลัพธ์ | พฤติกรรมของปุ่ม |
|---|---|
| 0 ห้อง | **ปุ่ม disabled + ข้อความ "ลูกค้ารายนี้ยังไม่มีห้องแชท"** — ห้ามซ่อนปุ่ม (ซ่อนแล้วร้านจะคิดว่าฟีเจอร์ไม่มี แทนที่จะรู้ว่าติดอะไร) |
| 1 ห้อง | เปิดชีตตรง ๆ ไม่มีแถวเลือก |
| >1 ห้อง | เปิดชีตพร้อมแถว "ส่งไปที่" ค่าตั้งต้น = คุยล่าสุด |

`order.customerId` เป็น `null` ได้ (ออเดอร์ที่ไม่มีเบอร์) → นับเป็นกรณี 0 ห้อง

## 4. Edge cases ที่ต้องมีคำตอบก่อนเขียนโค้ด

| # | เคส | พฤติกรรม |
|---|---|---|
| E-1 | นัดทั้งวัน (`isAllDayAppointment`) | `when` = `14 ส.ค. 2569 · ทั้งวัน` — **ต้องเรียก SSOT ตัวเดิม** ไม่ใช่เช็ค `00:00` เอง |
| E-2 | ไม่มี `serviceEnd` | `when` = วันที่อย่างเดียว (กติกาเดิมของ `appointmentText`) |
| E-3 | นัดอยู่ในอดีต | ยังส่งได้ (ร้านอาจส่งย้อนเป็นหลักฐาน) — แต่ `COMPLETED`/`NO_SHOW` ห้าม (§3.4 ข้อ 6) |
| E-4 | ออเดอร์ถูกยกเลิก (`status = CANCELLED`) | ปุ่มหายไปทุกจุด — กติกาเดิมของ footer `CustomerPanel` (`:392`) |
| E-5 | ร้านเปลี่ยน `vertical` ทีหลัง | ด่าน §3.4 ข้อ 3 อ่านค่าปัจจุบันเสมอ ไม่อ่านจากธงที่เก็บบนแถว (`stored-flag-vs-owner-truth.md`) |
| E-6 | ส่งซ้ำใบเดิม | **อนุญาต ไม่กันซ้ำ** — ร้านส่งเตือนซ้ำก่อนถึงวันนัดเป็นพฤติกรรมปกติ (ต่างจากการ์ดสินค้าที่ idempotent) |
| E-7 | นัดถูกเลื่อนหลังส่งการ์ดไปแล้ว | การ์ดเดิมในเธรดยัง render จาก `orderRefToken` ⇒ **อัปเดตตามอัตโนมัติ** ส่วนที่ลูกค้าได้บน Messenger/LINE เป็น snapshot ค้างไว้ — ปุ่ม `/o/{token}` ยังพาไปหาค่าล่าสุดเสมอ |
| E-8 | ช่องทางส่งไม่ผ่าน (หน้าต่าง 24 ชม. ปิด / LINE โควตาหมด) | ตกไปเส้นทาง `SEND_FAILED` เดิมทุกประการ — บับเบิลแดงพร้อมเหตุผล ไม่ใช่หายเงียบ |

## 6. นอกขอบเขตรอบนี้

- **ไม่แตะ** `ThreadStatusBar` และ `OrderProgressBar` (นอกจากปุ่มใหม่ที่ §3.7 ข้อ 2 และการ import `appointmentText` กลับ)
- **ไม่ทำ** การส่งสรุปอัตโนมัติเมื่อสร้างนัด / เตือนล่วงหน้าก่อนถึงวันนัด — คนละฟีเจอร์ ต้องมีเรื่องเวลาส่ง โควตา และการยกเลิก
- **ไม่ทำ** ส่งสรุปเป็นชุดหลายนัดในข้อความเดียว
- **ไม่แตะ** ปุ่ม "ส่งเข้าแชท" ของร้านขายของและบ้านพัก — พฤติกรรมเดิมทุกประการ
- **ไม่ทำ** ให้ร้านแก้วันนัด/เบอร์จากในชีต (มติ D-6 — แก้ต้องผ่านฟอร์มจริงที่เขียน `AppointmentReschedule`)
