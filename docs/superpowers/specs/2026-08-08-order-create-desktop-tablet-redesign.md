## 4. Trend 2026 ที่นำมาใช้ (และที่ตัดทิ้ง)

**นำมาใช้**
1. **accordion ที่ซ่อน required field = anti-pattern** — NN/g: บนเดสก์ท็อป การเลื่อนหน้าง่ายกว่าการตัดสินใจว่าจะคลิกหัวข้อไหน → **สลับตรรกะ: ของบังคับกางถาวร ของทางเลือกพับ**
2. **hybrid ไม่ใช่ wizard เต็มรูป** — ฟิลด์หลัก "permanently visible" ฟิลด์ที่ใช้น้อยพับ (งานนี้ทำซ้ำสิบ ๆ ครั้งต่อวัน wizard เพิ่มคลิกสะสม)
3. **Smart Paste / paste-to-fill เป็นมาตรฐาน 2026** — Deep มี `parseOrderMessage()` อยู่แล้ว ควรยกเป็นทางเข้าที่เห็นตั้งแต่เปิดหน้า (ไม่ต้องเปลี่ยนเป็น LLM — เป็นเรื่องหลังบ้านคนละรอบ)
4. **dense dashboard 2026 = "spreadsheet-fast แต่เบา"** ไม่ใช่การ์ดใหญ่หนา → ตัวเลขชิดขวา + `tabular-nums`
5. **inline validation ลด error rate 22%** (Baymard) → ขยาย 3-state ของที่อยู่ไปทุกฟิลด์บังคับ
6. **command palette / keyboard-first = ทางลัดเสริม ไม่ใช่ทางเดียว** — persona ของ Deep มี digital-literacy หลากหลาย

**ตัดทิ้งเพราะขัด Impeccable / DESIGN.md**
gradient · การ์ดตัวเลขใหญ่ (hero-metric) · eyebrow ตัวพิมพ์เล็ก · choreography ตอนโหลดหน้าฝั่งผู้ขาย · ม่วงเป็นพื้นกว้าง (ฝั่งผู้ขาย primary = น้ำเงิน `#236dc9`) · full-page wizard progress bar เป็นแกนหลัก

| แบบ | คลิก J1<br>(เดิม 5) | แก้ | เสี่ยง | หมายเหตุ |

### รายละเอียดที่ต้องรู้ก่อนเลือก

**A** — ตัดสถานะเปิด/ปิดของบล็อกลูกค้า·ช่องทาง·ที่อยู่·คิวงานทิ้ง เหลือ `ส่วนลด/ภาษี/หมายเหตุ` ที่ยังพับ · ปุ่มวางจากแชทขึ้นมาเป็นบรรทัดแรกของบล็อกลูกค้า · **ไม่แก้ F1** (นี่คือเหตุผลที่เสี่ยงต่ำสุด) · ต้องยืนยันว่าแผงขวาที่ยาวขึ้นไม่ดันแถบยอดรวมหลุดจอ

**B** — โครงล่างเหมือน A ทุกอย่าง ต่างแค่ยกกล่องวางข้อความขึ้นเป็นของชิ้นแรก · แยกข้อมูลให้ดูก่อน ยังไม่เติมทันที ต้องกด "ยืนยัน — เติมให้" (กันวางผิดข้อความ) · ข้อความยืนยันใช้**สีฟ้าไม่ใช่เขียว** — เขียวสงวนไว้กับสิ่งที่ระบบยืนยันแล้วจริง (Verified-Means-Green)

**C** — ลำดับและน้ำหนักบล็อกผันตาม `Shop.vertical`: ขายออนไลน์ → ที่อยู่จัดส่งขึ้นมาที่สองทันทีหลังลูกค้า · ร้านบริการ → คิวงานขึ้นมาแทนตำแหน่งนั้น และแผงขวากว้างขึ้นเป็น 55% เพราะไม่ต้องเสียที่ให้ช่องที่อยู่ · บ้านพัก → ฟอร์มสั้นสุด จึงยกสรุปยอดขึ้นมาในสายตา · **ที่อยู่ยังอยู่ครบทุกประเภท** เปลี่ยนแค่บังคับ/ไม่บังคับ กับตำแหน่ง

**D** — เดสก์ท็อป = A ทุกประการ ของใหม่อยู่ที่แท็บเล็ตล้วน ๆ: เนื้อหากว้าง 672px กลางจอ · ช่องกรอกเข้าคู่ 2 คอลัมน์ · การ์ดสินค้า 2 ใบต่อแถว · ปุ่มบันทึกขึ้นแถบบน · เปลือกนอก (เมนู/แถบล่าง) **ไม่แตะ** ยังสลับที่ 1024px
🛑 **ข้อควรตัดสินใจ:** `DESIGN.md` ระบุว่าหลังบ้านฝั่งผู้ขายมี **breakpoint เส้นเดียวที่ `lg`** โดยตั้งใจ (ลด surface การเทส) แบบนี้จะเป็นหน้าแรกที่มีเส้นแบ่งภายในที่ 768 — หน้าอื่นอาจขอตามมา และต้องทดสอบเพิ่มอีก 1 ช่วงจอจริง ๆ

**E** — ตะกร้า+ยอดรวม+ปุ่มบันทึกลอยขวา 280px เห็นตลอด · **แต่นับคลิกได้ 5 เท่าเดิม** เพราะต้องสลับแท็บเพิ่ม 1 ครั้ง · ถ้าฟิลด์ที่ผิดอยู่คนละแท็บต้องมีป้ายแดงบนหัวแท็บ (ตรรกะใหม่ที่ A–D ไม่ต้องมี) · กระทบ F7 และลิงก์ที่เปิดหน้าพร้อม `?product=` / `?appointmentDate=` มาให้แล้ว

## 6. Design Spec ร่วม (ใช้กับทุกแบบ)

### Impeccable compliance — Mode: Operate
- ฟอร์มธุรกรรมที่ใช้ซ้ำหลายสิบครั้ง/วัน → ใช้ familiarity ที่มีอยู่แล้วในแอปเอง ไม่ประดิษฐ์ affordance ใหม่ · ไม่มีแบบไหนเสนอ modal wizard เต็มจอ
- **One Voice** — น้ำเงินปรากฏเฉพาะ: ปุ่มบันทึก (solid ปุ่มเดียวของหน้า) · ปุ่ม/ชิปทางลัด (`bg-primary/15`) · ring การ์ดที่เลือกอยู่ · badge จำนวนตะกร้า ไม่มีแบบไหนใช้สีธีมเป็นพื้นกว้าง
- **Verified-Means-Green** — เขียวใช้เฉพาะ "ลูกค้าเก่า" (ระบบเจอ record จริงในฐาน) · "เติมให้แล้วจาก paste" = ฟ้า (info) · "รอเลือกที่อยู่" = ส้ม/แดง
- **anti-slop** — พระเอกของหน้าคือ *แถวสินค้าที่กำลังเพิ่ม* + *ปุ่มบันทึก* เท่านั้น ไม่มีการ์ดตัวเลขใหญ่แข่ง
- **HR7** — ไม่เพิ่ม arbitrary value ใหม่ ยกเว้นแบบ E ที่ต้องคำนวณ `calc(100vh-9.5rem)` ใหม่ (มี `nav-tabs` เพิ่มเข้ามาในความสูงที่ต้องหักลบ) — ต้องวัดจริงตอน implement ห้ามเดา

### Token
สี: `bg-primary`/`text-primary` · `bg-{semantic}/15 text-{semantic}-ink` · `text-default-{400,500,700,900}` · `bg-card`/`bg-body-bg`

### กติกา responsive
1. เส้นแบ่งหลักยังเป็น `lg` (1024px) ทุกแบบ **ยกเว้น D** ที่เพิ่มเลเยอร์ที่ `md` (768px) เฉพาะภายในไฟล์ของฟอร์มนี้
2. เปลือกนอก (แถบบน/เมนู/แถบล่าง) **ไม่เปลี่ยนทุกแบบ** — ยังสลับที่ 1024px, ไม่แตะ `.seller-mobile-shell`
3. แท็บเล็ตยังอยู่ใต้เปลือกมือถือเสมอ — สิ่งที่เปลี่ยนได้คือเนื้อหาใน `<main>` เท่านั้น
4. tap target ≥44px ทุก breakpoint
5. <768px ไม่แตะ — ทุกแบบที่กระทบ `QuickForm` ต้องเช็กว่าพฤติกรรมที่ <768px ไม่เปลี่ยน

## 7. คำแนะนำของทีม

**A เป็นฐาน → ทาบ treatment ของ B ทับ → C ต่อยอด** (ทั้งสามเป็นชั้นของงาน implement เดียวกัน ไม่ใช่ตัวเลือกที่ต้องเลือกแทนกัน)
**D แยกเป็นเฟส 2** ถ้ายืนยันว่า iPad เป็นเครื่องที่ผู้ขายใช้จริง — เพราะมันเป็นตัวเดียวที่แก้ F1 ซึ่งเป็นต้นเหตุจริงของคำว่า "ใช้ยาก" บนแท็บเล็ต
**E ไม่แนะนำ** — นับคลิกแล้วไม่ดีขึ้นจากปัจจุบันเลย (5→5) ในขณะที่เสี่ยง regression สูงสุด

## 8. รอ user เคาะ

1. **เลือกแบบไหน** (หรือ A+B+C รวมกันตามคำแนะนำ)
2. **iPad เป็นเครื่องที่ผู้ขายใช้จริงไหม** — ตัดสินว่าจะลงทุนใน D (ตั้ง precedent breakpoint 768) หรือหยุดที่ A+B+C
3. **เปลี่ยนช่องทาง/การชำระเงินจาก react-select เป็น native `<select class="form-select">`** ตาม Hard Rule 6 (ฟิลด์ผูกฟอร์มต้องเป็น native) — เสีย search-as-you-type แต่ตัวเลือกมีแค่ 4–6 อัน · เป็นการแก้หนี้เดิม ไม่ใช่ regression ใหม่
4. **แบบ B: การ์ด paste ยุบได้ + จำสถานะ** — ยุบถาวรหลังกดซ่อน 1 ครั้ง หรือกางใหม่ทุกครั้งที่เปิดหน้า
5. **แบบ D: ปุ่มบันทึกที่แถบบน (เฉพาะแท็บเล็ต) + แถบล่างเดิม** — เก็บทั้งคู่ หรือเลือกจุดเดียวตาม `seller-action-placement.md`
