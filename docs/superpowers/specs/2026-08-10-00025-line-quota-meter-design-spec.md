# Design Spec — มาตรวัดโควตา LINE ในห้องแชท (00025 · S-14b)

**วันที่:** 2026-08-10 · **Gate:** `safepay-ux` (Hard Rule 8) · **Mode:** Operate
**ต่อจาก:** `2026-08-09-00025-line-oa-ui-design-spec.md` §ส่วน B ข้อ 4 (ปิดคำถามที่ค้างไว้ 4 ข้อ + แก้จุดที่สเปกเดิมอ้างตำแหน่งโค้ดผิดไปแล้ว)
**ม็อกอัพ:** `2026-08-10-00025-line-quota-meter-mockup.html` (3 จอ: 375 / 768 / 1280)

---

## 1. ปัญหาที่แก้

ฝั่งหลังบ้าน (S-9) อ่านโควตาและบล็อกการส่งได้แล้ว แต่ **ไม่มีอะไรโผล่บนหน้าจอเลย** — ผู้ขายรู้ว่าโควตาหมดได้ทางเดียวคือกดส่งแล้วโดนปฏิเสธ ซึ่งเป็นจังหวะที่พิมพ์ข้อความจบไปแล้ว

## 2. สิ่งที่ทำ

**แคปชันบรรทัดเดียวข้างปุ่มส่ง** (ไม่ใช่แถบใหม่เหนือเธรด) รวมคำตอบสองเรื่องที่ผู้ขายถามก่อนกดส่งไว้ในประโยคเดียว: *ใบนี้ส่งฟรีไหม* กับ *โควตาเหลือเท่าไหร่*

## 3. คำตอบของคำถามที่ค้างจากสเปก 2026-08-09

### Q1 — LINE ใช้หน้าต่างฟรีแบบไหน

**LINE ใช้ reply token 60 วินาที แยกขาดจากหน้าต่าง 24 ชั่วโมงของ Meta 100%** และ **ไม่มีแถบสถานะหน้าต่างแบบ Meta เลย** (หน้าต่างที่ปิดเกือบตลอดเวลาไม่คุ้มกับ chrome ถาวรที่กินความสูงทุกครั้งที่เปิดเธรด)

🛑 **สิ่งที่พบระหว่างสำรวจ — ของเดิมผิดอยู่ก่อนแล้ว 3 จุด ไม่ใช่ความเสี่ยงของงานใหม่:**

1. `page.tsx` คำนวณหน้าต่างด้วย `getWindowState(lastInboundAt)` (24 ชม. ของ Meta) **กับเธรด LINE ด้วย**
2. แถบสถานะ `'window'` เขียนคำว่า **"Meta"** อยู่ในข้อความ ซึ่งไม่ใช่กติกาของ LINE
3. **`syncInboundWindowFromMeta()` ยิง Graph API ของ Meta ด้วย channel access token ของ LINE** ทุกครั้งที่เปิดเธรด LINE ที่ลูกค้าทักเกิน 24 ชม. — คำขอที่ไม่มีวันสำเร็จ และ `getLastInboundTime` กลืน error คืน `null` จึงไม่เคยมีใครเห็น เหลือไว้แค่ latency ที่จ่ายฟรีทุกครั้ง

ทั้ง 3 จุดแก้ในคอมมิตเดียวกัน (กันไม่ให้มาตรวัดใหม่ถูกฝังอยู่ใต้ข้อมูลเก่าที่ผิด)

### Q2 — แคปชัน "ส่งฟรี" หมดอายุคาหน้าจอ (60 วินาที)

ใช้ตัวจับเวลาที่มีอยู่แล้วในไฟล์ (`liveWindowOpen`) เป็น **ตัวพลิก boolean เงียบ ๆ** — ไม่มีตัวเลขวินาทีปรากฏบนจอเลย (BRD AC-005-05: เป็น "ข้อมูล ไม่ใช่การนับถอยหลัง") แคปชันเปลี่ยนจาก "ส่งฟรี" เป็นสถานะโควตาเองเมื่อครบเวลา

🛑 แก้บั๊กแฝงที่ไปด้วยกัน: `expiryTs` เดิมเป็น lazy-init ครั้งเดียวตอน mount ไม่รีเซ็ตเมื่อ prop เปลี่ยน — จำเป็นสำหรับ Q3 (รีเฟรชกลาง session)

### Q3 — ความสดของตัวเลขหลังกดส่ง

**เลือก `router.refresh()` หลังส่งสำเร็จ (เฉพาะเธรด LINE)** ไม่ใช่ให้ POST คืนโควตากลับมา และไม่ใช่ให้ client นับลดเอง

- ค่าที่ถูกต้องอยู่ใน DB **ตั้งแต่ก่อน response กลับมาด้วยซ้ำ** (`noteLinePushConsumed` / `replyTokenUsedAt` เขียนในทรานแซกชันของการส่ง) — RSC อ่านใหม่แล้วตรง 100% โดยไม่ต้องเพิ่ม endpoint
- **ไม่แตะสัญญาของ `POST /messages`** ซึ่ง Messenger/IG/แอปผู้ซื้อใช้ร่วมกัน และรูปแบบ `{messages, sendBatchId, quota}` ของ API.md §4.6 ผูกกับงาน batching (S-10) ที่ยังไม่ landed
- **ไม่ให้ client นับลดเอง** เพราะ client แยกไม่ออกว่าใบนั้นถูกส่งด้วย reply (ไม่กินโควตา) หรือ push และมีพนักงานหลายคนส่งพร้อมกันจากคนละเครื่อง — จะได้เลขที่ "ดูน่าเชื่อ" แต่ไม่มีที่มา

### Q4 — ตำแหน่ง

สเปกเดิมอ้างบรรทัดปุ่มส่งที่ย้ายไปแล้วตั้งแต่ 2026-08-06 (ปุ่มอยู่ **ในกล่องช่องพิมพ์** ไม่ใช่แถวแยกข้างนอก) — แคปชันจึงไปอยู่แถวเดียวกับปุ่มส่งภายในกล่อง

ที่ 320px: ปุ่มส่ง ~78px คงที่ เหลือให้แคปชัน ~194px — ข้อความย่อที่ยาวสุด (`เหลือ 32/300 ใกล้หมด`) พอดี และมี `min-w-0 truncate` เป็นตาข่าย · ไม่ชนกับการยุบแถบเครื่องมือเข้าเมนู `⋯` ที่ <768px (คนละแถว)

### Q5 — popover รายละเอียด: **ตัดออก**

เนื้อหาเกือบทั้งหมดซ้ำกับแคปชันเต็ม เหลือแค่ "เวลาที่ดึงล่าสุด" ซึ่งมีค่าเฉพาะตอนอ่านไม่ได้ — และกรณีนั้นบอกด้วยประโยคเดียวได้แล้ว (สถานะ 8) ตัดแล้วแคปชันเป็น `<span>` ไม่ใช่ปุ่ม ไม่ต้องมี focus/aria-expanded และไม่เพิ่มเป้ากดในแถบที่แน่นอยู่แล้ว

### Q6 — ปุ่มส่งตอนโควตาหมด

**ปิด (disabled) เฉพาะสถานะ 7** — กล้าปิดเพราะ **server รับรองว่าจะปฏิเสธ 409 แน่นอน** ในเงื่อนไขเดียวกันนี้ (TFR-LINE-06 ข้อ 5) ไม่ใช่การเดาแทนผู้ใช้

🛑 ไม่ปิดด้วยสัญญาณ reactive เดิม (`quotaExceeded` ที่รู้จากการยิงแล้วโดนปฏิเสธ) เพราะค่านั้นค้างทั้ง session ข้ามวันข้ามเดือนได้ — คงไว้เป็นแถบเตือน (warning) ตามเดิม และ **ไม่ขึ้นพร้อมกับ `quotaBlocked`** (สองแถบพูดเรื่องเดียวกันคนละน้ำเสียงบนจอเดียว = ผู้ขายไม่รู้ว่าอันไหนจริง)

## 4. ตรรกะที่ยกออกเป็นฟังก์ชันบริสุทธิ์ (บังคับ)

| ไฟล์ | หน้าที่ | เทส |
|---|---|---|
| `src/lib/line/reply-window.ts` | `getLineReplyWindowState()` — นิยามเดียวของ "ตอบฟรีได้อยู่ไหม" ที่ **ทั้งฝั่งส่งและหน้าจอเรียกร่วมกัน** (HR16 — เดิมฝั่งส่งเขียน inline) | 5 เคส · mutation 2 แบบ |
| `src/lib/line/quota-caption.ts` | `deriveLineQuotaCaption()` — คำ/โทน/`blocking` ครบ 8 สถานะ | 12 เคส · mutation 2 แบบ |

`blocking` คือ boolean ตัวเดียวที่ปิดช่องพิมพ์ของ LINE ทั้งหมด — เขียนกลับด้านเมื่อไหร่ก็ผ่าน `tsc`/build/detector ทุกด่าน เพราะสิ่งที่ผิดคือความหมายไม่ใช่รูปแบบ (`docs/conventions/ui-boolean-needs-a-testable-home.md`)

**กติกาที่เทสล็อกไว้:** `blocking = true` ได้ทางเดียว = หน้าต่างฟรีปิด **และ** รู้แน่ว่าโควตาหมด (ค่า `stale` ไม่มีวันทำให้บล็อก — ฝั่ง server ก็ไม่บล็อกด้วยค่าแบบนั้นเหมือนกัน ถ้าหน้าจอบล็อกเองจะกลายเป็นสองมาตรฐาน)

## 5. Impeccable compliance

- **One Voice** — ไม่เพิ่ม `bg-primary`/`text-primary` เลย ปุ่ม "ส่ง" ยังเป็นพระเอกเดียวของแถบ
- **Verified-Means-Green** — "ส่งฟรี" **ไม่ใช้เขียว** (หน้าต่าง 60 วินาทีเป็นสถานะชั่วคราวที่สุดในระบบ ยิ่งไม่ควรผูกกับสีที่สงวนให้ trust signal)
- **สองโทน** — แถบ `quotaBlocked` ใช้ `bg-danger/15` + `text-danger-ink` ตาม token ที่มีอยู่แล้วในไฟล์เดียวกัน
- **anti-slop** — ตัด popover (ข้อมูลซ้ำ) · ตัดแถบหน้าต่างของ Meta ออกจาก LINE (ข้อมูลผิด) · ไม่มี hero-metric
- **น้ำเสียง** — สถานะที่บล็อกต้องบอกทางออกเสมอ ไม่ใช่แค่ "ส่งไม่ได้"
- **โทนสีไล่ตามน้ำหนักข่าว** — `quiet` (ไม่รู้ ยังส่งได้) เงียบกว่า `neutral` (ปกติ) โดยตั้งใจ: ความไม่รู้ต้องไม่ดูเหมือนคำเตือน

## 6. ไม่ทำในรอบนี้

- แบนเนอร์ถาวร "ข้อความที่ตอบจากแอป LINE OA จะไม่ขึ้นที่นี่" (ส่วน B ข้อ 2 ของสเปกเดิม)
- popover รายละเอียดโควตา (ตัดตาม Q5)
- แสดงโควตาในหน้า `/settings/channels` (การ์ดช่องทาง) — คนละหน้าจอ คนละงาน
- batching (`parts[]`) และ `quota.consumed` ใน response ของ POST — S-10
- รีเฟรชโควตาเมื่อ **ลูกค้า** ทักเข้ามาใหม่ (รีเฟรชเฉพาะหลัง "เราส่งเอง")
