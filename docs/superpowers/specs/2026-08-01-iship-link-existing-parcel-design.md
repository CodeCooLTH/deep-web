# ผูกพัสดุที่มีอยู่แล้วบน iShip เข้ากับคำสั่งซื้อ (feature 00022 ส่วนขยาย)

**วันที่:** 2026-08-01
**สถานะ:** implemented (ยังไม่ผ่าน browser QA / ยังไม่ apply migration)
**ต่อยอดจาก:** `docs/20 - Features/00022 - iShip Shipping Integration/`

---

## 1. ปัญหา

ร้านจำนวนหนึ่งทำงานสลับลำดับกับที่ระบบสมมติไว้ — เปิดพัสดุบนเว็บ iShip ตั้งแต่ตอนแพ็กของ
แล้วค่อยมาบันทึกคำสั่งซื้อใน Deep ทีหลัง (บางทีตอนกลางคืน) ของเดิมรองรับแค่ "สร้างพัสดุใหม่"
ร้านกลุ่มนี้จึงเหลือทางเลือกแค่เปิดพัสดุใบที่สอง (เสียเงินซ้ำ) หรือเลิกใช้ส่วนจัดส่งของเราไปเลย

มีปัญหาแฝงอีกข้อที่แก้ได้ด้วยทางเดียวกัน: ใบที่ระบบเรายิง `create_order` สำเร็จแล้วแต่ response
หายกลางทาง — พัสดุเกิดขึ้นจริงฝั่ง iShip แต่เราไม่มีเลข ก่อนหน้านี้กู้คืนไม่ได้เลย

## 3. สิ่งที่ค้นพบระหว่างออกแบบ (สำคัญกว่าที่คิด)

### 3.1 `query_orders` ส่งที่อยู่มาครบอยู่แล้ว
`IShipOrderRow` ในโค้ดประกาศไว้แค่ 5 ฟิลด์ (`track_no/status/status_name/status_desc/updated_at`)
แต่ payload จริงมี `dst_name/dst_phone/dst_address/dst_district/dst_area/dst_province/dst_zipcode`
`courier_code` `cod_amount` `ref_code` `custom_order_id` ขนาดกล่อง และเวลาสร้าง — ครบทุกอย่างที่
หน้าจอนี้ต้องใช้

**ผลต่อดีไซน์:** ทั้งหน้าเลือกใบใช้ **1 คำขอ** ไม่ต้องวน `get_order` รายใบ (ซึ่งจะกลายเป็น
หลักร้อยคำขอต่อการเปิดแผงหนึ่งครั้ง)

### 3.2 กับดักชื่อฟิลด์ตัวใหม่ — `dst_area`
ขาออก (`create_order`) เรารู้แน่แล้วว่า `dst_district`=ตำบล, `dst_amphure`=อำเภอ (BR-ISHIP-31)
แต่ **ขาเข้า** iShip ส่งกลับเป็น `dst_district` + **`dst_area`** ซึ่งเป็นชื่อที่ไม่เคยโผล่ฝั่งขาออก

ตัวอย่างในเอกสารของ iShip ใส่ค่า `"สายไหม"` ไว้ทั้งสองช่อง — **จึงพิสูจน์จากเอกสารไม่ได้**
ว่าช่องไหนเป็นระดับไหน (เป็นรูปแบบเดียวกับที่ unit test ของเราเคยเกือบพลาด: ค่าเท่ากันแล้ว
จับคู่กลับหัวก็ยังเขียว)

**ที่เลือก:** ตำบล ← `dst_district` (สมมาตรกับขาออก), อำเภอ ← `dst_amphure` ถ้ามี ไม่งั้น `dst_area`
**ที่ยอมรับความเสี่ยงได้:** flow นี้บังคับให้ร้านดูตารางเทียบที่อยู่ก่อนกดผูกเสมอ ถ้าจับคู่กลับหัว
ร้านจะเห็นตำบลกับอำเภอสลับที่กันทันที — ต่างจากขาออกที่ส่งผิดแล้วเงียบสนิท

**ยังต้องยืนยัน:** ยิง `query_orders` กับบัญชีจริงที่มีพัสดุซึ่งตำบลกับอำเภอ**ต่างกัน** (ดู §8)

## 4. สถาปัตยกรรม

### 4.1 lib — `src/lib/iship/unlinked.ts` (pure, ไม่มี prisma/token)
- `parseParcelRow` / `parseParcelRows` — แกะแถวแบบ **รับได้หลายสะกด** (`created`/`created_at`,
  `dst_amphure`/`dst_area`, `cod_amount` ที่เป็นสตริง) เพราะเอกสารกับ prod ไม่ตรงกันมาแล้ว
- `diffReceiverAddress` — ตารางเทียบ 7 แถว เทียบแบบ canonical (ตัดคำนำหน้า ต./อ./จ., ยุบช่องว่าง,
  `กรุงเทพ`=`กรุงเทพมหานคร`, เบอร์เทียบเฉพาะตัวเลข) เพื่อไม่ให้ฟ้องเรื่องไร้สาระจนร้านเลิกอ่าน
- `matchesQuery` — ตัวกรองช่องค้นหา (กรองในหน่วยความจำ ไม่ยิงถาม iShip ใหม่ทุกตัวอักษร)
- ถือ type ที่หน้าจอใช้ (`UnlinkedParcelView`, `ParcelPreview`) ไว้ที่นี่ ไม่ใช่ใน service —
  client component จะได้ import type ได้โดยไม่ลาก server module ติดไป

### 4.2 service — `src/services/iship.service.ts`
| ฟังก์ชัน | หน้าที่ |
|---|---|
| `listUnlinkedParcels(shopId)` | 1 คำขอ 7 วัน → ตัดใบที่ยกเลิก → ตัดใบที่ `trackingNo` ถูกใช้แล้ว (ทั้งตาราง ไม่ใช่แค่ร้านนี้ เพราะ partial unique เป็นระดับตาราง) → ติดป้ายใบ orphan |
| `previewLink(shopId, orderId, trackingNo)` | อ่านพัสดุจาก iShip ใหม่ + คืนตารางเทียบ |
| `linkShipment(...)` | สร้างแถว `OrderShipment` `source=LINKED` แล้วเติมไทม์ไลน์ |
| `unlinkShipment(shopId, shipmentId)` | **ลบแถว** (ดู §5.3) + คืนสถานะออเดอร์ |

### 4.3 API
| Endpoint | หมายเหตุ |
|---|---|
| `GET /api/seller/iship/unlinked` | คืนรายการ — มี PII ผู้รับ จึง `private,no-store` + `requireGeneralShop` |
| `GET /api/seller/iship/unlinked/preview` | `?orderId=|orderToken=&trackingNo=` |
| `POST /api/seller/iship/shipments/link` | `{orderId|orderToken, trackingNo, addressResolution}` |
| `POST /api/seller/iship/shipments/[id]/unlink` | คนละเรื่องกับ `/cancel` |

`addressResolution` **ไม่มีค่าปริยาย** โดยเจตนา — เป็นคำตอบของคำถามที่ร้านต้องตอบ
ค่าปริยายเงียบ ๆ จะกลายเป็นการเขียนทับที่อยู่โดยร้านไม่รู้ตัว

## 5. จุดที่ตัดสินใจแล้วมีเหตุผลเฉพาะ

### 5.1 ยิงถาม iShip ซ้ำตอนกดผูก ทั้งที่รายการมีข้อมูลแล้ว
เซิร์ฟเวอร์เชื่อที่อยู่จาก client ไม่ได้ (แก้ payload แล้วเขียนที่อยู่มั่วเข้าออเดอร์ได้) จึงต้อง
อ่านใหม่ตอนผูกอยู่แล้ว — ถ้าตารางเทียบมาจากข้อมูลชุดเก่า ร้านจะยืนยันสิ่งหนึ่งแต่ระบบเขียน
อีกสิ่งหนึ่ง จึงให้ขั้นยืนยันอ่านจากแหล่งเดียวกับที่จะเขียนจริง

### 5.2 `idempotencyKey` คนละรูป
ใบที่ผูกใช้ `link:<trackNo>:<attemptGroup>` ไม่ใช่ `<orderId>:<attempt>` — ใบนี้ไม่เคยมี
`custom_order_id` ของเราฝั่ง iShip การใช้รูปเดิมจะอ่านผิดว่าเราเป็นคนยิง `create_order`

### 5.3 เลิกผูก = **ลบแถว** ไม่ใช่ mark `CANCELLED`
partial unique `OrderShipment_trackingNo_key` ครอบทุกแถวที่ `trackingNo` ไม่ null **โดยไม่สนสถานะ**
ถ้าปิดใบด้วย `CANCELLED` เลขนั้นจะถูกจองไว้ตลอดกาล แล้วร้านที่ผูกผิดใบจะเอาไปผูกกับคำสั่งซื้อ
ที่ถูกต้องไม่ได้อีกเลย — ขัดกับเหตุผลทั้งหมดที่ปุ่มนี้มีอยู่

### 5.4 ข้อยกเว้นของ BR-ISHIP-41 (ระบบขยับสถานะคำสั่งซื้อเอง)
เดิมห้ามเด็ดขาด เหตุผลคือพัสดุที่เราเปิดเองจะเดินทางตอนที่ร้านยังดูหน้าจออยู่ ให้ร้านกดยืนยันเองไม่เสียเวลา

การผูกย้อนหลังเป็นคนละสถานการณ์ — พัสดุอาจถึงมือผู้ซื้อไปแล้วก่อนที่ออเดอร์จะถูกบันทึกด้วยซ้ำ
ถ้าไม่ขยับให้ ผู้ซื้อที่เปิดลิงก์ออเดอร์จะเห็นข้อมูลขัดกับความจริงตรงหน้า

**ขอบเขตของข้อยกเว้น:** เฉพาะ `advanceOrderIfDispatched()` ที่ถูกเรียกจาก `linkShipment` เท่านั้น
webhook/sync ยังไม่ขยับสถานะเหมือนเดิม

**ผลข้างเคียงที่ต้องรู้:** ฟังก์ชันนี้เขียน `ShipmentTracking` ซึ่ง **ทำลายข้อสังเกตเดิม** ที่
`order.service.ts` เขียนกำกับไว้ว่า "ไม่มีจุดไหนใน iShip flow เขียนลงตารางนั้น จึงเชื่อได้ว่า
2 model ไม่ทับกัน" — ใช้ `upsert` (ไม่ใช่ `create`) เพราะ `orderId` เป็น unique และออเดอร์ที่ร้าน
เคยกด "แจ้งจัดส่ง" ด้วยมือมาก่อนจะมีแถวอยู่แล้ว

เงื่อนไขที่จะขยับ: `order.status === 'PENDING'` **และ** `impliesDispatched(carrierStatus)`
(`impliesDispatched` ต่างจาก `suggestsShipped` เดิมตรงที่รวม `delivered`/`return*` ด้วย —
ใบที่ส่งถึงแล้วต้องเข้าเงื่อนไข ไม่งั้นออเดอร์ค้าง "รอจัดส่ง" ทั้งที่ของถึงมือคนซื้อแล้ว)

### 5.5 เติมไทม์ไลน์ย้อนหลังทันทีที่ผูก
เรียก `getTraces(shopId, shipmentId)` ที่มีอยู่แล้ว (upsert `ShipmentEvent` + sync `carrierStatus`)
ต่อจากการสร้างแถวทันที — แถบความคืบหน้า 4 ขั้นจึงชี้ตำแหน่งจริงตั้งแต่วินาทีแรก
**ล้มแล้วห้าม rollback การผูก** เพราะกรณีที่พบบ่อยที่สุดคือ "ขนส่งยังไม่สแกน" ซึ่ง iShip
ตอบ HTTP 500 ไม่มีข้อความ (ไม่ใช่ความผิดพลาดจริง)
