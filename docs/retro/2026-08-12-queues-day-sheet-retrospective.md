## 1. ปัญหา + หลักฐาน

### P1 — การ์ดถูกดันหลุดขอบซ้ายทั้งจอ (ขึ้น prod แล้ว user เจอเอง)

ผู้ขายเปิด `/queues` บนมือถือแล้วเห็นชื่อลูกค้าถูกตัดหัวทุกใบ (`hanawit Atikitchinnawut`,
`akkapon Jakchum`) เบอร์โทรก็ขาดหลักต้น — จอใช้ไม่ได้จริง

**กลไก 2 ชั้นซ้อนกัน:**

1. ชื่อเพจจริงยาว `Messenger · BT Premium Auto Xenon คลอง4 ธัญบุรี` **ไม่ถูกตัด** ทั้งที่ใส่
   `truncate` ไว้แล้ว — flex item มี `min-width:auto` เป็นค่าตั้งต้น ("อย่าหดต่ำกว่าเนื้อหา")
   `truncate` บอกแค่ "ถ้าล้นให้ตัด" ไม่ได้บอกว่ากล่องกว้างเท่าไร ⇒ ตัวหนังสือ**ดันกล่องกว้างขึ้น**
2. กล่องเลื่อนของชีตใช้ `overflow-y-auto` และตามสเปก CSS **ถ้าแกนหนึ่งไม่ใช่ `visible` อีกแกน
   จะถูกคำนวณเป็น `auto` ให้เอง** ⇒ ลูกล้นแนวนอนพิกเซลเดียว ทั้งชีตกลายเป็น "เลื่อนข้างได้"

**ไม่มี gate ไหนจับได้** — `tsc` / build / `theme-guard` / impeccable hook ผ่านหมด เพราะคลาสทุกตัว
มีอยู่จริงและสะกดถูก สิ่งที่ผิดคือ *ผลลัพธ์เชิงเรขาคณิต*

### P2 — ทำการปัดเปลี่ยนวัน แล้วถอดออกในวันถัดมา

user: *"เอา slide ข้าง ออกก็ได้นะ ไม่สวยเลย"* — ถอดทิ้งทั้งก้อน (axis lock + `touch-action` +
`touchcancel` + transform + threshold) ที่เพิ่งเขียนไปเมื่อวาน

### P3 — "ห้องแชทของลูกค้ารายนี้" กลายเป็นมี 2 นิยามในวันเดียวกัน

งานคู่ขนาน ("ส่งสรุปนัด" `f7b03585`) เพิ่ม `GET /api/orders/[token]/conversations`
scope ด้วย `shopId + customerId` · ส่วนปุ่ม "ทักแชท" บนการ์ดของผมใช้
`ExternalContact.conversations[0]` scope ด้วย `(shopChannelId, customerId)`

สองอันตอบคำถามเดียวกัน แต่ให้คำตอบต่างกันได้จริง: ลูกค้าที่เคยทักมาทางเพจ A แล้วออเดอร์ผูกกับเพจ B
ตัวหนึ่งจะเจอห้อง อีกตัวจะไม่เจอ ⇒ ปุ่มสองปุ่มบนจอเดียวกันพาไปคนละที่ (**HR16**)

`rebase` ผ่านสะอาดไม่มี conflict เพราะอยู่คนละไฟล์กันสนิท (**HR17 คลาสเดียวกันเป๊ะ**)

## 2. รากของปัญหา

### R1 — mockup ใช้ fixture ที่สั้นกว่าข้อมูลจริงครึ่งหนึ่ง (รากของ P1)

mockup ทั้ง 3 เวอร์ชันเขียนชื่อเพจว่า **"BT Premium"** (10 ตัวอักษร) ส่วนของจริงคือ
**"BT Premium Auto Xenon คลอง4 ธัญบุรี"** (34 ตัวอักษร) ⇒ **mockup ไม่มีวันแสดงอาการนี้ ต่อให้
เปิดดูกี่รอบ** และผมยกชื่อลูกค้า/เลขออเดอร์จริงจากภาพหน้าจอมาใช้แล้ว แต่ *ลืมทำแบบเดียวกันกับชื่อเพจ*
— หยิบข้อมูลจริงมาบางฟิลด์ แล้วเดาที่เหลือ ซึ่งอันตรายกว่าเดาทั้งหมดเพราะมันดู "เหมือนของจริง"

### R2 — ประกาศเองว่ายังไม่ได้ตรวจ แล้ว push (รากที่สองของ P1)

ผมเขียนในรายงานตอน push เองว่า *"ยังไม่ได้กดจริงสักครั้ง"* แล้ว push ขึ้น prod — บั๊กเห็นได้
**ในวินาทีแรกที่เปิดจอ**

🛑 **นี่คือรอยเดิมเป๊ะ ๆ ของฟีเจอร์เดียวกัน** — retro `2026-08-09-appointment-duration-picker`
เขียนไว้เองว่า *"การรู้ตัวว่าไม่ได้ตรวจ + เขียนกำกับไว้ ไม่ได้ลดความเสียหาย มันแค่ทำให้สืบสวนเร็วขึ้น"*
บทเรียนที่เขียนเป็นเอกสารอย่างเดียว กันการซ้ำไม่ได้ — **ห่างกัน 3 วัน ฟีเจอร์เดียวกัน คนเขียนคนเดียวกัน**

### R3 — ลงแรงกับทางที่ตัวเองประเมินแล้วว่าไม่น่าเชื่อถือ (ราก P2)

ผมเขียนไว้ในสเปกด้วยตัวเองก่อนลงมือว่า:

> "ปัดเป็น **ทางลัด ไม่ใช่ทางเดียว** — iOS/WebView ยึด 'ปัดขวาจากขอบซ้าย' ไว้เป็นปุ่มย้อนกลับ
> อยู่แล้ว และผู้ใช้คีย์บอร์ด/screen reader ปัดไม่ได้เลย ลูกศรจึงเป็นของบังคับ"

รู้ครบทุกข้อ **แล้วยังทำ** โดยไม่ถามสักคำว่าจะเอาไหม — เพราะมันอยู่ในม็อกอัพที่ user ดูแล้ว
แต่ "ไม่ได้ทัก" ≠ "อยากได้" โดยเฉพาะกับของที่ **ภาพนิ่งแสดงไม่ได้** (ม็อกอัพวาดการปัดเป็นเฟรมนิ่ง
ได้อย่างเดียว ผู้ใช้จึงไม่มีทางรู้ว่ามันจะรู้สึกยังไงจนกว่าจะได้จับของจริง)

### R4 — งานคู่ขนานสองสายแตะโดเมนเดียวกันโดยไม่มีใครประกาศ SSOT ก่อน (ราก P3)

ทั้งสองสายเพิ่ม "หาห้องแชทของลูกค้า" ในวันเดียวกัน คนละไฟล์ คนละ endpoint —
`comm -12` ของ HR17 คืนค่าว่างเพราะมันเทียบ **ชื่อไฟล์** ไม่ได้เทียบ **คำถามที่โค้ดตอบ**

## 3. Convention ที่ต้องรับไปใช้

### C1 — `truncate` ในกล่อง flex ต้องมาเป็นชุด 3 ตัว
เขียนเพิ่มแล้วที่ `docs/conventions/flex-header-truncation.md` **§5**
(`min-w-0` ที่กล่อง + `max-w-full` ที่ลูก + `overflow-x-hidden` ที่กล่องเลื่อนเป็นชั้นกันพลาด)

### C2 — fixture ในม็อกอัพต้องเป็น "ค่าที่ยาวที่สุดที่มีอยู่จริง" ไม่ใช่ค่าที่อ่านสวย
ถ้าหยิบข้อมูลจริงมาใช้ในม็อกอัพแล้ว **ต้องหยิบให้ครบทุกฟิลด์** — หยิบมาบางฟิลด์แล้วเดาที่เหลือ
อันตรายกว่าเดาทั้งหมด เพราะม็อกอัพจะดูน่าเชื่อถือกว่าที่มันเป็น
👉 ยังไม่มีที่อยู่เป็นเอกสารกลาง — **action item #3**

### C3 — ของที่ "ภาพนิ่งแสดงไม่ได้" ต้องถามก่อนลงมือ ไม่ใช่ทำแล้วให้ตัดสินทีหลัง
gesture / transition / haptic / เสียง — ม็อกอัพยืนยันมันไม่ได้เลยโดยธรรมชาติ ⇒ "user ไม่ทัก"
ในรีวิวม็อกอัพ **ไม่นับเป็นการอนุมัติ** ของกลุ่มนี้
👉 **action item #4**

### C4 — HR17 ต้องเทียบ "คำถามที่โค้ดตอบ" ไม่ใช่แค่ชื่อไฟล์
เมื่องานคู่ขนานแตะโดเมนเดียวกัน (แม้คนละไฟล์) ต้องอ่าน commit message ของอีกฝั่งจริง ๆ
ก่อน rebase — `comm -12` จับได้แค่การชนระดับไฟล์

## 4. สิ่งที่ทำถูกและควรทำซ้ำ

1. **แยก endpoint รายวันออกจากรายเดือนตั้งแต่ก่อนเขียนโค้ด** — ตัดสินจาก *ขนาดของคำขอ* ไม่ใช่
   *หน้าจอที่เรียก* และรับ `date` ไม่รับ `from/to` เพื่อให้เพดานถูกบังคับด้วยรูปร่างของ input
   ⇒ เบอร์ลูกค้าอยู่ใน flight payload ครั้งละ 1 วัน ไม่ใช่ 1 เดือน
2. **แก้ TFR-010 พร้อมโค้ดในคอมมิตเดียวกัน** — และแยกให้ชัดว่าบรรทัดไหนของมันเป็น *กฎ*
   บรรทัดไหนเป็น *ความต้องการ ณ ตอนนั้น* (บรรทัดที่สามเลิกเป็นจริงแล้ว จึงเขียนใหม่ ไม่ใช่แอบเติม field)
3. **mutation testing จริง ไม่ใช่แค่เขียนไว้ในหัวไฟล์** — รันครบ 5 แบบ แดงทุกตัว แล้วคืนไฟล์
   (เคยมีเคสในรีโปนี้ที่เทสยืนยันพฤติกรรมที่เป็นบั๊กให้เขียวมาตลอด)
4. **HR17 จับของจริงได้ 2 รอบ** — รอบแรก Prisma client ค้างเวอร์ชันเก่าหลัง rebase (`tsc` แดง 4 จุด
   จาก `richMenuContext`) แก้ด้วย `prisma generate` · รอบสอง main แซงไป 3 commit ระหว่างแก้บั๊ก
5. **เทียบ baseline ด้วย `stash` ก่อนสรุปว่าเทสที่แดงไม่ใช่ของเรา** — 20 fail / 8 files เท่ากันเป๊ะ
   ทั้งก่อนและหลัง ไม่มีอันไหนเกี่ยวกับ appointment
