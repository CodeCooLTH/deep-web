## 1. Problems

### P1 — AC ที่เขียนไว้ในเอกสารครบถ้วน แต่ไม่เคยถูก implement เลย

feature 00037 เขียนไว้ตรงตัวใน 3 ที่:
- `BRD.md` **AC-06-6**: "บันทึกรายการที่ร้านของร่างไม่ตรงกับร้านของเธรด → **ปฏิเสธ** ไม่ใช่บันทึกเข้าร้านใดร้านหนึ่ง"
- `DraftOrderProvider.tsx:48`: "`shopId` ที่ส่งไปกับ POST ต้องมาจากค่านี้ค่าเดียว **ห้ามผสมกับ activeShopId เด็ดขาด**"
- `PRD.md` FR-UNI-06: "ร่างออเดอร์พก `shopId` ติดตัว และถูกปฏิเสธถ้าไม่ตรงกับเธรด"

ความจริงในโค้ด: `OrderCreateForm` รับ prop `shopId` มาแล้ว **โยนทิ้ง** (`shopId: _shopId` — destructure แล้วไม่ถูกใช้ที่ไหนเลยทั้งไฟล์) และ `POST /api/orders` **ไม่มีที่ให้ใส่** ด่านนั้นไม่เคยถูกสร้างขึ้นมา

### P2 — อาการที่ผู้ใช้เห็นเป็นอาการที่เบาที่สุดในสามแบบ

ออเดอร์ที่คีย์จากเธรดร้าน B ขณะ active ร้าน A:

| ชนิดรายการ | ผลลัพธ์ |
|---|---|
| มีนัด (คิวงาน) | `404 RESOURCE_NOT_FOUND` ← **ตัวที่ user ถ่ายรูปมา** |
| เลือกสินค้าจากแคตตาล็อก | `400 พบสินค้าที่ไม่ใช่ของร้านนี้` |
| **พิมพ์รายการเอง ไม่มีนัด** | **`201` เข้าร้านผิดถาวร ไม่มีอะไรฟ้อง + ไม่ผูกลูกค้าให้ด้วย** |

สิ่งที่ปกป้องเราอยู่คือ "บังเอิญมี object ที่ผูกร้านอยู่ใน payload" (คิวงาน/สินค้า) ไม่ใช่ด่านจริง
⇒ **เคสที่เงียบที่สุดคือเคสที่ payload สะอาดที่สุด**

### P3 — เทสที่บันทึกไว้เองว่า "ยังไม่มีวิธี repro"

`TestCase.md` B-24 เขียนว่า *"ถูกปฏิเสธ (ยังไม่มีวิธี repro จากหน้าจอ — ต้องยิง API ตรง)"*
ประโยคนี้แปลว่า **"ไม่เคยทดสอบ"** ไม่ใช่ "ทดสอบยาก" — และมันอยู่ในเอกสารมา 3 วันโดยไม่มีใครสะดุด

### P4 — 🚨 prod 500 ระหว่างทาง: หน้า `/o/[token]` พังทั้งหน้าสำหรับผู้ซื้อที่ล็อกอิน

```
PrismaClientValidationError: prisma.user.findUnique({ where: { id: undefined }, select: { phone: true } })
digest: 3758181775
```

`session` callback เติม `user.id` ให้เฉพาะเมื่อ `token.userId` มีค่า **และ** หาแถว `User` เจอจริง
⇒ session ที่ไม่เป็น null แต่ไม่มี `id` เกิดได้ · หน้านั้นเช็คแค่ `if (!session)` แล้ว
`session.user as { id: string }` ต่อทันที

**ไม่ใช่บั๊กจากงานรอบนี้** — มาจากชุด "Order Link ยกเครื่อง" ของอีก session ที่ขึ้น prod พร้อมกัน
แต่พบเพราะ deploy รอบนี้ และกลายเป็นงานของรอบนี้

### P5 — แพตเทิร์นเดียวกันมีอีก 58 จุด ไม่ใช่ 19 อย่างที่ผมรายงานไว้ตอนแรก

ผมประเมินจาก grep หยาบ ๆ แล้ว **พูดตัวเลข "ประมาณ 19 จุด" ออกไปเหมือนเป็นข้อเท็จจริง**
พอไล่จริงได้ 58 (ยังไม่รวม 80 จุดที่ปลอดภัยอยู่แล้วเพราะส่งทั้ง session เข้า helper ที่เช็คเอง)

### P6 — ความผิดพลาดของผมเองระหว่างทาง 4 อย่าง

1. **เกือบทำ regression ตอนแก้ข้อความ error** — ผมจะเขียน `data.message ?? fallback` ซึ่งจะทำให้
   error กลุ่มที่ใส่ข้อความไทยไว้ในคีย์ `error` (`ShippingAddressRequired`/`OutOfStock`/วันที่นอกช่วง)
   ร่วงไป fallback ทั้งกลุ่ม — `safepay-ux` เป็นคนจับได้ ไม่ใช่ผม
2. **เขียนเทสที่ไม่ยืนยันอะไรเลย** — ด่านกัน drift ของ `ishipCreateMode` รุ่นแรกเช็คแค่
   `src.toContain('resolveChatIshipCreateMode')` ซึ่ง**เขียวอยู่ทั้งที่โค้ดถูกเปลี่ยนเป็นค่าคงที่**
   (บรรทัด `import` ก็ match) จับได้เพราะรัน mutation ไม่ใช่เพราะอ่านทวน
3. **regex ในเทสพลาดช่องว่าง** — `/ishipCreateMode[:=]/` ไม่ match `ishipCreateMode = …`
   (ตัว `=` มีช่องว่างนำหน้า) เทสแดงกับโค้ดที่ถูก
4. **สคริปต์แทรก `import` ผิดที่** — ตัวแทรกเลือก "บรรทัด `import` สุดท้าย" ซึ่งบังเอิญเป็น
   บรรทัดเปิดของ import หลายบรรทัด ⇒ ไฟล์พัง (`_shared.ts`) `tsc` เป็นตัวจับ
   ตรงกับบทเรียนเดิม `feedback_script_edits_bypass_hooks`

### P7 — การปิดบั๊กหนึ่งปลุกบั๊กที่หลับอยู่

`ishipCreateMode` เป็น state ตัวเดียวทั้ง provider (ค่าของร้าน active) ส่งให้ฟอร์มของทุกร่าง
**ผิดมาตลอด** แต่ไม่มีใครไปถึงเพราะสร้างออเดอร์ข้ามร้านไม่เคยสำเร็จ — พอคอมมิต #1 เปิดเส้นทาง
ค่าที่ผิดอยู่แล้วจึงเริ่มมีผล

## 2. Root causes

| # | ทำไมถึงเกิด |
|---|---|
| R1 | **`activeShopId` เปลี่ยนความหมายไปแล้วตั้งแต่ 00037 แต่โค้ดฝั่งเขียนไม่ได้เปลี่ยนตาม** — ก่อนหน้านั้น "ร้านที่ active" = "ร้านที่ผู้ใช้กำลังมองอยู่" เสมอ ฟีเจอร์นั้นตัดความเท่ากันทิ้ง แล้วมีการไล่แก้ฝั่ง *อ่าน* ครบ (`resolveChatScope` + กฎห้ามเรียก `requireActiveShop` ใน `(chat)/**`) แต่ฝั่ง *เขียน* ไม่ได้อยู่ในขอบเขตนั้นเพราะ route ของออเดอร์ไม่ได้อยู่ใต้ `api/chat/**` |
| R2 | **กฎถูกเขียนเป็นคอมเมนต์/เอกสาร ไม่ใช่เป็นโค้ดที่บังคับได้** — คอมเมนต์ที่ `DraftOrderProvider.tsx:48` พูดถูกทุกตัวอักษร แต่คอมเมนต์บังคับอะไรไม่ได้ |
| R3 | **type cast คือการปิดตา ไม่ใช่ตัวช่วย** — `as { id: string }` ทำให้ `tsc` เชื่อว่ามีค่าแน่ ๆ · `as _shopId` (ตั้งชื่อขึ้นต้น `_`) ทำให้ linter เงียบเรื่องตัวแปรไม่ถูกใช้ ทั้งสองอย่างคือการบอกเครื่องมือว่า "ไม่ต้องดูตรงนี้" |
| R4 | **ไม่มี gate ไหนของโปรเจกต์ตรวจ "ความหมาย"** — `tsc`/build/เทส/`theme-guard`/grep ผ่านหมดทุกด่านทั้ง 5 บั๊ก เพราะทุกบรรทัด "ถูก" ในตัวเอง สิ่งที่ผิดคือข้อสมมติ |
| R5 | **checklist ที่ยอมรับคำว่า "repro ไม่ได้" เป็นสถานะจบ** — ไม่มีกลไกไหนแยก "ทดสอบแล้วผ่าน" ออกจาก "ยังไม่เคยทดสอบ" |

## 3. Conventions to adopt

### C1 — `docs/conventions/session-exists-is-not-identity.md` (สร้างแล้ว ✅)
"มี session" ≠ "รู้ว่าเป็นใคร" — ตรวจสิ่งที่จะเอาไปใช้จริง (`id`) ไม่ใช่กล่องที่ห่อมันอยู่
ใช้ `sessionUserId()` จาก `@/lib/session-user` เท่านั้น · คืน `null` ห้าม throw (throw = 500 = อาการเดิม)
ลงทะเบียนใน `CLAUDE.md` แล้ว + เทส `[blocker]` สแกนซอร์สทั้ง `src/app/`

### C2 — AC ในเอกสาร ≠ AC ที่ถูก implement (ใหม่ — ต้องบังคับตอนปิดฟีเจอร์)
ก่อน mark AC ใด ๆ ว่าเสร็จ ต้องชี้ได้ว่า **โค้ดบรรทัดไหน** บังคับกฎนั้น และ **เทสตัวไหน**
ยืนยัน — คอมเมนต์ที่อธิบายกฎไม่นับ, prop ที่ส่งมาแล้วไม่ถูกใช้ไม่นับ

🛑 **ประโยคใน `TestCase.md` ว่า "ยังไม่มีวิธี repro จากหน้าจอ" = ธงแดง ไม่ใช่หมายเหตุ** —
แปลว่า "ไม่เคยทดสอบ" ต้องมีเทสอัตโนมัติแทน หรือประกาศว่ายังไม่เสร็จ

### C3 — เทสที่สแกนซอร์สต้องจับ "การเรียก" และ "การถูกนำไปใช้" ไม่ใช่ "ชื่อที่โผล่ในไฟล์"
`toContain('ชื่อฟังก์ชัน')` เขียวได้จากบรรทัด `import` เพียงอย่างเดียว
ต้องเป็น `toContain('ชื่อฟังก์ชัน(')` + regex ที่ผูกกับตัวแปรปลายทาง **และพิสูจน์ด้วย mutation ทุกตัว**

### C4 — ปิดบั๊กแล้วต้องถามว่า "เส้นทางที่เพิ่งเปิด พาไปเจออะไรที่ไม่เคยมีใครเดินไปถึง"
บั๊กที่หลับอยู่หลังบั๊กอีกตัวจะตื่นทันทีที่ตัวแรกถูกแก้ (`ishipCreateMode`)
คลาสเดียวกับ `unlayered-css-beats-utilities.md` — งานใหม่ไม่ได้สร้างบั๊ก แต่ปลุกมัน

### C5 — ตัวเลขที่ยังไม่ได้นับ ห้ามพูดเหมือนนับแล้ว
"ประมาณ 19 จุด" กลายเป็น 58 — ถ้ายังไม่ได้ไล่จริง ให้พูดว่า "ยังไม่ได้นับ" แล้วค่อยนับ

## 4. What went right

1. **systematic-debugging ทำงานจริง** — ไม่แตะโค้ดเลยจนกว่าจะไล่ครบทั้งสาย แล้วถาม user 2 คำถาม
   ที่ตัดทางเลือกได้จริง (สร้างจากจอไหน / มีหลายร้าน+เปิดกล่องรวมไหม) คำตอบล็อกสาเหตุทันที
2. **เขียนเทสให้แดงก่อนแก้** — เทส route แดง 4/5 ตั้งแต่ก่อนแตะโค้ด (ข้อที่เขียวคือ "ไม่ส่ง shopId
   → พฤติกรรมเดิม" ซึ่งควรเขียวอยู่แล้ว) เป็นหลักฐานว่าเทสจับของจริง
3. **mutation testing จับเทสปลอมได้ 2 ครั้ง** — ทั้งด่าน drift ของ `ishipCreateMode` และด่านสแกน
   ของ `sessionUserId` ถ้าไม่รัน mutation ทั้งคู่จะเขียวตลอดกาล
4. **ux gate จับ regression ที่ผมกำลังจะสร้าง** (2 คอนเวนชันของ error message) และตัดสินตรง ๆ ว่า
   งาน wiring ไม่ต้องมี spec — ไม่ได้เขียนสเปกเปล่า ๆ มาให้ครบพิธี
5. **ตรวจความเสียหายบน prod ด้วยข้อมูลจริงก่อนสรุป** — ออเดอร์ทั้ง 17 ใบตั้งแต่ 08-08 มีนัดติดทุกใบ
   ⇒ เส้นทางผิดร้านล้มทุกครั้ง ไม่เคยบันทึกสำเร็จ **ไม่มีข้อมูลที่ต้องย้ายคืน** (ถ้าไม่เช็ค
   จะได้แต่เดา และการเดาทั้งสองทางแพงพอกัน)
6. **HR17 จับ push แทรกได้จริง 1 ครั้ง** — เช็ค fast-forward ซ้ำหลัง build แล้วเจอว่ามีคน push
   ระหว่างนั้น ถ้า push ต่อจะทับงานคนอื่น
7. **หา stack trace ของ prod ได้ทั้งที่ log API ตอบ 403** — `vercel logs <deployment>` สตรีม
   ของใหม่ได้ เปิดค้างแล้วให้ user กดซ้ำ ⇒ ได้ trace เต็มในนาทีเดียว หลังจากอ่านโค้ดเดาอยู่นาน
