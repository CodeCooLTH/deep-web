## 3. บทเรียนรอง (สองอันนี้เป็นอาการของอันเดียวกัน)

### 3.1 สเปกอ้าง affordance ที่ไม่มีอยู่จริง

สเปกเขียนว่าปุ่มจุดที่ 4 จะอยู่ใน "popover ของนัด" ในปฏิทิน `/queues` — **popover ไม่เคยมี**
`AppointmentCalendar.tsx:285` ผูก `eventClick` ไปที่ `router.push('/orders/{token}')` ตรง ๆ
ผมรู้ตอนจะลงมือ ไม่ใช่ตอนเขียนสเปก แล้ว user เคาะจุดเรียกไป **4 จุดโดยอิงสเปกที่ผิด**

บทเรียน: **ข้อความในสเปกที่บอกว่า "ปุ่มจะอยู่ใน X" คือคำอ้างว่า X มีอยู่** — ต้องเปิดไฟล์ยืนยันก่อน
เอาไปให้ user ตัดสิน ไม่งั้นมติที่ได้มาถูกสร้างบนของที่ไม่มี

### 3.2 ยกฟีเจอร์ใหม่มาโดยไม่เทียบกับฝาแฝดที่เพิ่ง ship

การ์ดสินค้าที่ ship ไป 2026-08-11 **มี** idempotent-guard พร้อมเหตุผลเขียนไว้ครบในหัวไฟล์
(`reply token ของ LINE ใช้ได้ครั้งเดียว กดซ้ำ = push = เงินร้านจริง`) — การ์ดสรุปนัดวิ่งผ่านท่อเดียวกันเป๊ะ
ผมยกเว้น guard นั้นด้วยเหตุผลของตัวเอง ("ส่งเตือนซ้ำเป็นเรื่องปกติ") **โดยไม่ได้เปิดไฟล์นั้นอ่าน**

จับได้ตอน grilling รอบ 3 · user ตัดสินสุดท้ายว่า **ปล่อยให้ส่งซ้ำได้** (ดู §5) — มติเดิมถูก
แต่กระบวนการที่ได้มันมาผิด: ถ้าไม่มีใครถาม มันจะเป็นการยกเว้นที่ไม่มีใครรู้ว่ามีอยู่
