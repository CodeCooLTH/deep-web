# Retro — iShip: ลองใหม่แล้วไม่เปลี่ยน / ชิปโกหก / เครดิตไม่พอ (2026-08-06 รอบเย็น)

**ขอบเขต:** user ส่งภาพหน้าจอ error มา 1 ใบ → สืบจากฐาน prod → เจอ 3 บั๊กคนละชั้น deploy 4 รอบ
(`ec3ade1c` · `b6cf5243` · `bc33dc34` · `61ffea08`)
**วิธีเดินงาน:** systematic-debugging (สืบก่อนแก้) → TDD (เทสแดงก่อนทุกตัว) → cherry-pick ขึ้น main ทีละคอมมิต

## Problems

### P-1 "ลองใหม่" ที่ไม่เคยลองอะไรใหม่เลย

`retryShipment()` อัปเดต `receiverSnapshot` **เฉพาะตอนมี `receiverPatch` แนบมา** ส่วน
`createShipment()` ที่เจอใบ FAILED ค้างอยู่ `return retryShipment(shopId, userId, active.id)`
โดยไม่ส่ง patch ต่อ — สองบรรทัดนี้อยู่คนละฟังก์ชัน แต่ละอันอ่านแล้วดูสมเหตุสมผล พอต่อกันกลายเป็น
"ร้านแก้ที่อยู่ → ระบบเขียนที่อยู่ใหม่ลงออเดอร์ → แล้วยิงที่อยู่เก่าออกไป"

ร้านกดไป 2 ครั้ง เห็นข้อความเดิมเป๊ะทั้งสองครั้ง โดยไม่มีอะไรบอกว่าที่แก้ไปแล้วไม่ถูกใช้

**บทเรียน:** snapshot ที่ freeze ไว้ตอนสร้าง กับ "ค่าที่ต้องใช้ตอนยิงใหม่" เป็นคนละคำถาม —
ทุกครั้งที่มีปุ่ม "ลองใหม่" ต้องตอบให้ได้ว่ามันอ่านค่าจากที่ไหน ถ้าอ่านจาก snapshot เดิม
มันไม่ใช่ retry มันคือ replay

### P-2 ชิปบอกว่า "สร้างพัสดุแล้ว" ทั้งที่ไม่มีเลขพัสดุ

นิยาม "ออเดอร์นี้มีพัสดุแล้ว" ถูกเขียนไว้ 5 ที่ 4 ที่ใช้ `status='CREATED' AND isDryRun=false`
เหมือนกันหมด เหลือ LATERAL join ใน `order-stage.service.ts` ที่เดียวที่ใช้ `<> 'CANCELLED'`
ซึ่งนับใบที่ **สร้างไม่สำเร็จ** ว่ามีพัสดุแล้ว

น่าเจ็บใจตรงที่ในไฟล์ `order-stage.ts` มีคอมเมนต์เตือนเรื่องนี้ไว้เองว่า *"ถ้าแยกกันเขียน
วันหนึ่งจะกดไทล์ที่บอก 5 แล้วเข้าไปเจอ 4 ใบ"* — คอมเมนต์อยู่ที่ **ฟังก์ชันที่คำนวณ** แต่บั๊กอยู่ที่
**query ที่ป้อนข้อมูลเข้าไป** คนละไฟล์ คนแก้ query ไม่มีทางเห็นคอมเมนต์นั้น

**บทเรียน:** กติกาที่ต้องใช้ร่วมกันหลายที่ ต้องบังคับด้วย "ฟังก์ชัน/ค่าคงที่ตัวเดียว" ไม่ใช่คอมเมนต์
เตือนใจ — และต้องวางไว้ที่ **จุดที่ดึงข้อมูล** ไม่ใช่แค่จุดที่ตีความข้อมูล

### P-3 regex จับรูปปฏิเสธภาษาไทย แล้วพลาดรูปที่ผู้ให้บริการใช้จริง

`เครดิต.*ไม่พอ` ไม่ match `"เครดิตไม่เพียงพอ"` เพราะไม่มีสตริง `ไม่พอ` ในประโยคเลย
(`ไ-ม-่-เ-พ-ี-ย-ง-พ-อ`) — ตาคนอ่านผ่านแล้วรู้สึกว่า "ครอบคลุมแล้ว" ทั้งที่ไม่

ผลคือเงินไม่พอถูกจัดเป็น `UPSTREAM_ERROR` ซึ่ง `retryable = true` → จอบอก "ระบบขนส่งขัดข้องชั่วคราว
กรุณากดลองใหม่" → ร้านกดวน 3 และ 4 ครั้งในสองใบ **ระบบไม่ได้ขัดข้องเลยสักนิด**

**บทเรียน:** จับ "คำนาม" (เครดิต/ยอดเงิน) ทนกว่าจับ "รูปปฏิเสธ" (ไม่พอ/ไม่เพียงพอ/ไม่เหลือ) —
ภาษาไทยมีรูปปฏิเสธหลายแบบและผู้ให้บริการเปลี่ยนคำเมื่อไหร่ก็ได้ (ไฟล์ `errors.ts` เขียนหลักการนี้
ไว้ที่หัวไฟล์เองด้วยซ้ำ แต่แพตเทิร์นข้างล่างไม่ได้ทำตาม)

### P-4 ข้อยกเว้นที่ออกแบบไว้ดี แต่ไม่เคยทำงาน

`IShipError` มีข้อยกเว้นเดียวของ BR-ISHIP §6.4 ให้ `REJECTED_BY_CARRIER` ต่อท้ายข้อความดิบจากขนส่ง
("กรุณากรอก สีสินค้า …") พร้อมคอมเมนต์อธิบายเหตุผลยาว 3 บรรทัด — แต่ `toShipmentView()` สร้าง error
จาก `code` เปล่า ๆ ไม่เคยส่ง `upstreamMessage` เข้าไป **ข้อยกเว้นนั้นจึงตายตั้งแต่วันแรก**

**บทเรียน:** โค้ดที่มี "ทางพิเศษ" ต้องมีเทสยืนยันว่าทางนั้นถูกเดินจริงจากจุดที่ผู้ใช้เห็น ไม่ใช่เทส
เฉพาะที่ตัวคลาส

## What went well

- **สืบก่อนแก้จ่ายคุ้มมาก** — ภาพหน้าจอบอกแค่ "ที่อยู่ไม่ผ่าน" แต่ `OrderShipment.lastErrorMessage`
  ในฐาน prod เก็บข้อความดิบไว้ครบ ทำให้เห็นทันทีว่า snapshot สะกดผิด 3 ช่อง ส่วนออเดอร์ถูกต้องแล้ว
  = แก้แล้วไม่ถูกใช้ ไม่ใช่แก้ไม่ถูก การเก็บ payload/ข้อความดิบไว้ในฐานคือสิ่งที่ทำให้ทั้งวันนี้จบได้
- **timestamp ต่างกัน 0.6 วินาที** (`Order.updatedAt` 10:59:10.681 vs `OrderShipment.updatedAt`
  10:59:11.274) คือหลักฐานชิ้นที่ปิดคดี — พิสูจน์ว่าเป็นคำขอเดียวที่เขียนออเดอร์แล้วยิงต่อ
  ไม่ใช่คนกดสองครั้ง
- **เทสแดงก่อนทุกตัว** รวมถึงตัวที่เขียนหลังแก้ (ยกโค้ดกลับชั่วคราวเพื่อดูให้เห็นว่าแดงจริง) —
  เทสตัวที่สองจับได้ว่า override ถูกทิ้ง (`FlashExpressA` แทน `KerryExpress`) ซึ่งเป็นบั๊กคนละตัวกับ
  ที่ user รายงาน
- **ยืนยันการแก้กับข้อมูลจริงก่อน push** — รัน SQL เก่า/ใหม่เทียบกันบน prod (read-only) เห็น
  `hasShipment` เปลี่ยน true → false ในใบที่ user ชี้มาจริง ๆ
