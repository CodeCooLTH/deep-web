## 1. ปัญหา + หลักฐาน

### 1.1 สิ่งที่ user ขอ vs สิ่งที่พังจริง

user ส่งภาพหน้าจอมาพร้อมประโยค *"ลูกค้าแกง"* — ค้นหาลูกค้าด้วย `0 8 6 5 3 5 2960`
แล้วขึ้น "ไม่พบลูกค้าเดิม" · คำขอคือ **"อยากได้ script ตรวจสอบและแนะนำ แต่ไม่อยากให้ replace ทันที"**

พอไล่โค้ดจริง พบว่าใต้คำขอนั้นมี **บั๊กที่มีอยู่ก่อนแล้ว 4 ตัว** ที่ไม่มีใครรู้:

| # | ที่ | อาการ |
|---|---|---|
| 1 | `api/orders/customers/route.ts` | ค้นด้วย `contact.includes(q)` บนคำค้นดิบ ⇒ เบอร์ที่มีช่องว่าง **หาไม่เจอทั้งที่ลูกค้ามีอยู่ในฐาน** แล้วหน้าจอเชิญให้สร้างลูกค้าซ้ำ |

### 1.2 🛑 P0 สองตัวที่ **ผมสร้างเองในคอมมิตก่อนหน้าไม่กี่นาที**

`/impeccable critique` จับได้ ไม่ใช่ `tsc`/build/eslint/detector/เทส (ผ่านหมดทุกตัว)

**P0-1 — error ที่ผู้ใช้ไม่มีวันเห็น**
สเปกเขียนว่า *"chip แทนที่ error ไม่ขึ้นซ้อนกัน"* ผม implement ตรงตัวที่ผู้เรียก:

```tsx
{hintVisible ? <PhoneSuggestHint/> : errors.buyerContact && <p className="text-danger">…}
```

**ค่าที่มี chip คือค่าที่ยังบันทึกไม่ผ่านเสมอ** ⇒ เทอร์นารีนั้นเลือกข้าง `hint` ตลอดกาล
error จาก Yup **ไม่มีวันถูก render เลยไม่ว่ากดบันทึกกี่ครั้ง** และช่องไม่เคยได้ `is-invalid`
ขณะที่ `OrderCreateForm.tsx:985` ยิง toast ว่า **"ดูช่องที่ทำเครื่องหมายสีแดง"**

ปลายทางจริง: ร้านกดบันทึก → toast แดงเด้ง → กวาดตาหาสีแดงทั้งฟอร์ม → ไม่เจอ → กดซ้ำ

**P0-2 — ด่านที่กันไว้ครึ่งเดียว**
ผมเขียนด่าน "มี chip ค้าง = ยังไม่เปิดชีตค้นหา" ที่ `CustomerQuickBlock` พร้อมคอมเมนต์
อธิบายเหตุผลยาว 5 บรรทัด แล้ว **ไม่ได้ใส่ที่เดสก์ท็อป** — ทั้งที่ dropdown ของเดสก์ท็อป
เป็น portal `fixed` วางที่ `anchor.bottom + 4` ซึ่งทับ chip พอดี และแผ่นที่มาทับเขียนว่า
*"ไม่พบลูกค้าเดิม — พิมพ์ต่อเพื่อบันทึกเป็นลูกค้าใหม่"* = สั่งให้สร้างลูกค้าซ้ำด้วยเบอร์เพี้ยน
โดยบังทางที่ถูกไว้ข้างหลังตัวเอง

**เหตุผลที่ผมเขียนกำกับไว้ที่มือถือ ใช้ได้กับเดสก์ท็อปทุกตัวอักษร**

### 1.3 🛑 เทส `[blocker]` ที่เขียนเอง เขียวทั้งที่ควรแดง — 2 ครั้งใน session เดียว

**ครั้งที่ 1** — สัญญาหลักของฟีเจอร์คือ *"เบอร์ที่ chip เสนอ ต้องผ่านด่านบันทึกได้เสมอ"*
เขียนเทสที่ป้อน output ของ chip เข้า `CreateOrderSchema` ตัวจริง (หลบ tautology สำเร็จ)
รัน mutation "ผ่อนกฎให้ chip รับ 9 หลัก" → **เทสยังเขียว 42/42**

เพราะ **ไม่มี input ไหนในชุดทดสอบที่ผลิตเบอร์ 9 หลักออกมาได้เลย** แม้ผ่อนกฎแล้ว
ต้องเติม `092079164` เข้าไปก่อนถึงจับได้

**ครั้งที่ 2** — เทสว่า `_`/`+66` ต้องไม่ค้างอยู่ในที่อยู่ เขียน `expect(addressLine).not.toMatch(/0_9_2/)`
รัน mutation "ให้ `stripPhone` กลับไปใช้ regex เก่า" → **เทสยังเขียว 17/17**

เพราะผมวางเบอร์ไว้**คนละบรรทัด**กับที่อยู่ในข้อมูลทดสอบ ตัวที่ค้างจึงไม่มีทางโผล่ใน `addressLine`
พอย้ายมาบรรทัดเดียวกันถึงเห็นว่าเบอร์ที่ลบไม่ออก **กลายเป็น `addressLine` ทั้งดุ้น**

### 1.4 ข้อความที่บอกกฎผิดหลังบีบ regex

`/impeccable clarify` จับได้ว่ามี **3 จุดยังเขียนว่า "ขึ้นต้นด้วย 0"** หลังบีบเป็น 06/08/09 แล้ว
⇒ ผู้ใช้แก้ตามคำแนะนำแล้วยังบันทึกไม่ผ่าน · และคำเดียวกันถูกเขียน **3 แบบ**

## 2. รากของปัญหา

### 2.1 mutation ที่เงียบ = **ชุดข้อมูลทดสอบอ่อน** ไม่ใช่ mutation เลือกผิด

ผมเกือบตีความผลครั้งแรกว่า "mutation ตัวนี้ไม่เกี่ยวกับเทส" แล้วข้ามไป

ความจริงคือ mutation ทำหน้าที่ของมันสมบูรณ์ — มันบอกว่า **โค้ดที่ผิดกับโค้ดที่ถูกให้ผลเหมือนกัน
บนทุก input ที่ผมป้อน** ซึ่งแปลว่าเทสนั้นไม่ได้กันสิ่งที่มันอ้างว่ากัน

โปรเจกต์นี้มีวัฒนธรรม mutation อยู่แล้ว (`rule-must-be-enforced-not-described.md` สั่งไว้)
แต่ **ไม่มีที่ไหนเขียนว่าจะอ่านผล "mutation แล้วยังเขียว" ยังไง** — ซึ่งเป็นผลลัพธ์ที่หลอกที่สุด
เพราะมันหน้าตาเหมือนความสำเร็จ

### 2.2 กฎที่เขียนเพื่อแก้ปัญหา *เลย์เอาต์* ถูก implement เป็นการลบ *สัญญาณ*

FR-CUS-E1-06 *"chip แทนที่ error ไม่ขึ้นซ้อนกัน"* เกิดจากโจทย์จริงคือ 3 จอวางของใต้ช่องคนละแบบ
เจตนาคือ **"ไม่มีสองบรรทัด"** ไม่ใช่ **"ยอมให้ผู้ใช้ไม่เห็นว่าตัวเองถูกบล็อก"**

ผมอ่านสเปกที่ตัวเองเขียนแล้ว implement ตามตัวอักษร โดยไม่ได้ถามว่า *"ถ้าทั้งสองอย่าง
ต้องแสดงพร้อมกันจริง ๆ จะเกิดอะไร"* — ซึ่งเป็นเคสที่เกิด **ทุกครั้ง** ไม่ใช่เคสหายาก

### 2.3 คอมเมนต์ที่อธิบายเหตุผลของด่าน ไม่ได้ทำให้ด่านไปอยู่ครบทุกที่

ผมเขียนคอมเมนต์ 5 บรรทัดอธิบายว่าทำไมต้องกันชีตไม่ให้เปิดทับ chip แล้ววางด่านที่เดียว
**การเขียนเหตุผลไว้ดี ๆ ให้ความรู้สึกว่าจัดการเรื่องนั้นครบแล้ว** ทั้งที่มันครอบแค่ call site เดียว

คลาสเดียวกับ `sibling-surface-parity.md` แต่ทิศกลับ — อันนั้นคือ "ไม่ได้อ่านหน้าพี่น้อง"
อันนี้คือ "อ่านแล้ว เขียนเหตุผลแล้ว แต่ไม่ได้ไปทำที่หน้าพี่น้อง"

### 2.4 ข้อความอธิบายกฎ อยู่คนละที่กับกฎ

`^0[0-9]{9}$` กับประโยค "ขึ้นต้นด้วย 0" ถูกเขียนคู่กันใน 27 ไฟล์ พอบีบ regex ด้วยสคริปต์
มันแก้เฉพาะ regex กับข้อความที่ **สะกดตรงกันเป๊ะ** — 3 จุดที่เขียนคนละสำนวนจึงรอด
และกลายเป็นข้อความที่บอกกฎผิด

## 4. สิ่งที่ทำถูกและควรทำซ้ำ

1. **นับข้อมูล prod ก่อนตัดสินใจบีบ regex** — user สั่ง "เอาเข้ม ๆ เลย" โดยยังไม่รู้ว่ากี่แถวจะตก
   ผลคือ 24 แถว **เป็นบัญชีทดสอบล้วน** และ 2 บัญชีรีวิว Meta/Apple ล็อกอินด้วยรหัสผ่านไม่ใช่ OTP
   ⇒ ความเสี่ยงจริง = 0 · ถ้าไม่นับจะเถียงกันด้วยความรู้สึก

2. **แยก "ด่านขาเข้า" ออกจาก "ตัวตีความข้อมูลเก่า"** — `normalizePhone()` ไม่ถูกบีบตาม
   เพราะมันตอบคนละคำถาม การบีบมันคือเปลี่ยนความหมายของข้อมูลเก่าย้อนหลัง
   ทั้งสองเกณฑ์วางติดกันในไฟล์เดียวตาม HR16

3. **grilling ก่อนลงมือ** — 6 รอบคำถาม จับได้ว่าคำสั่งเดิมมี 2 ประโยคที่ขัดกันเอง
   ("ไม่อยากให้ replace" กับ "ช่วยตัดอักษรออกให้") และจับกิ่งเบอร์บ้านที่จะบานปลาย
   ไปทั้ง auth/OTP/iShip ได้ก่อนเขียนโค้ดแม้บรรทัดเดียว

4. **ตรวจข้ออ้างของ subagent ซ้ำเอง** — `safepay-ux` อ้าง `bg-primary/15 text-primary`
   ว่ามีในธีม ผม grep ยืนยันเองก่อนใช้ (ถูกจริง) — ธีมนี้เคยพลาดเรื่องคลาสที่ไม่มีอยู่จริง 3 ครั้ง

5. **แยกพื้นที่นิ้วออกจากก้อนสี** — user บอก "ใหญ่ไป" 2 รอบ ทางแก้ที่ถูกคือ
   `<button>` โปร่งใส 44px + `<span>` สี 24px ไม่ใช่ลด tap target ที่ `PRODUCT.md` ประกาศเอง
