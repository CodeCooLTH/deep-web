## Root causes

1. **P1 — เทสกริดด้วย "รูปถ่าย" ไม่ใช่ "เนื้อหาจริงของร้าน":** โปสเตอร์จัตุรัสข้อมูลแน่นคือ format หลักที่ร้านใช้ยิงโปร แต่ตอน build/QA กริดใช้รูปทั่วไปที่ครอปแล้วยังดูรู้เรื่อง. เอกสาร Meta ไม่บอกสัดส่วนการครอปของ tile — สิ่งเดียวที่พิสูจน์ได้คือส่งเนื้อหาจริงแล้วดูฝั่งลูกค้า
2. **P1 (การวินิจฉัย) — screenshot อย่างเดียวตัดสินไม่ได้ว่า "ผิดยังไง":** กว่าจะรู้ว่าครอป ต้องดึงไฟล์ต้นฉบับจาก storage มาเปิดเทียบกับ screenshot — ก่อนหน้านั้นไล่สมมติฐานผิดไปหลายทาง (ส่งผิดห้อง/ส่งซ้ำ/echo)
3. **P2 — เพดาน layout เป็น px ตายตัวบน layout ที่ยืดหยุ่น:** 420 ถูกเลือกตอนคิดถึงจอเดสก์ท็อปเปล่า ๆ ไม่ได้คิดรวมคิวรูปแนบ/reply bar/จอเตี้ย และ `overflow-hidden` ของการ์ดทำให้การล้น**ไม่มีอาการ** จนกระทั่งปุ่มหาย
4. **P3 — เปิด session ในเวิร์กทรีไหนก็แก้ในนั้นโดยอัตโนมัติ:** ไม่ได้ถามก่อนว่า "โค้ดที่ user เห็นพังอยู่ รันจากที่ไหน" — บั๊กจาก prod ต้องเทียบไฟล์กับ `origin/main` ก่อนแตะ (`git log HEAD..origin/main -- <file>`)

## Conventions to adopt

1. **ส่งผ่าน template/การเรนเดอร์ของ platform ภายนอก (image_grid, media template, การ์ดใด ๆ ของ Meta/LINE) ต้อง QA ด้วยเนื้อหาจริงของร้านฝั่งผู้รับก่อน ship** — โดยเฉพาะรูปที่มีตัวหนังสือ/ข้อมูล (โปสเตอร์) เพราะการครอป/ย่อของ platform ไม่อยู่ในเอกสารและเราคุมไม่ได้. รูปถ่ายทั่วไปผ่าน ≠ โปสเตอร์ผ่าน
2. **วินิจฉัยปัญหา "แสดงผลผิด" ของรูป: ดึง asset ต้นฉบับจาก storage มาเปิดเทียบกับที่ตาเห็นเสมอ** — ต่อยอด `docs/conventions/user-supplied-image-assets.md` (เปิดดูรูปก่อนใช้) ให้ครอบขาวินิจฉัยด้วย ไม่ใช่แค่ขา build
3. **ขนาด/เพดานของ UI ที่อยู่ใน flex column สูงจำกัด ห้ามเป็น px ตายตัว — ต้องวัดจากพื้นที่จริงหรือพิสูจน์ได้ว่า element ถัดไป (โดยเฉพาะปุ่ม action หลัก) ไม่มีวันหลุดจอ** และระวัง `overflow-hidden` ทำให้การล้น "ไม่มีอาการ" — จุดที่คิดว่า "ไม่มีทางล้น" คือจุดที่ล้นเงียบที่สุด
4. **บั๊กที่รายงานจาก prod: ก่อนแก้ ให้เช็คว่าเวิร์กทรีปัจจุบันมีโค้ดเดียวกับ prod ไหม** (`git log HEAD..origin/main -- <ไฟล์ที่จะแก้>` ต้องว่าง) — ไม่ว่างแปลว่าต้องแก้บน main checkout ไม่ใช่เวิร์กทรีที่บังเอิญเปิดอยู่

## What went right

- **prod DB (SELECT) + storage ต้นฉบับ = หลักฐานปิดเคส** — timeline ของ `ChatMessage` แยกได้ว่าอะไรคือกริด (createMany, mid + `#1`), อะไรคือส่งทีละใบ, อะไรคือ echo; เทียบ fileId พิสูจน์ว่า "ส่งถูกตัว แค่เรนเดอร์พัง" → fix ตรงจุด ไม่แตะสิ่งที่ไม่พัง
- **memory ช่วยไว้จริง** — `project_chat_delivery_receipt_grid` (จากอีก session เช้าเดียวกัน) ทำให้รู้ว่า main มีเครื่อง partial-send ใหม่ → ไม่ทับงานเขา และ fix ไปลงที่ที่ prod รันจริง
- **gate `safepay-ux` กับงาน behavior ก็มีประโยชน์** — spec ชี้ว่าข้อเสนอเดิม (สัดส่วน % ของ viewport) ยังเดาอยู่ และให้สูตรวัด slack จาก DOM จริงที่ self-correct + นับ toolbar/reply bar/คิวรูปให้เองโดยไม่ไล่บวกรายชิ้น
- ถอดกริดที่ **ผู้เรียกรายเดียว** (`handleSend`) — endpoint/สัญญา partial-send ฝั่ง server คงไว้ ถ้าจะฟื้นกริด (ทาง `is_hero_image`) ไม่ต้องรื้อใหม่
