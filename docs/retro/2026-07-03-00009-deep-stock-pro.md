## Problems

1. **P1 — Branch diverged จาก main 47 commit โดยไม่รู้ตัวจนถึงตอน merge.** ตอนสั่ง "merge main แล้ว push" เข้าใจว่าเป็น FF 14-commit-ahead ธรรมดา แต่จริง ๆ `origin/main` ล้ำหน้า local main (a7415ff) ไป 47 commit (feat 00008 Business Account + badge + auction redesign จาก worktree main-2/3/5). Evidence: `git rev-list --left-right --count origin/main...main` = `47 0`; `git merge-base --is-ancestor origin/main HEAD` = NO.
   - **ผลกระทบ:** เป็น real merge ไม่ใช่ FF; conflict `schema.prisma` + auto-merge `order.service.ts` (live prod HIGH RISK).

2. **P2 — Migration timestamp collision.** ทั้ง 00008 (`20260702000001_add_business_account_packages`) และ 00009 (`20260702000001_add_deep_stock_pro_schema`) ใช้ prefix `20260702000001` เดียวกัน → 00009 เรียง lexical แทรก **กลาง** ระหว่าง 00008's `..._000001` กับ `..._000002_owner_cutover` (ซึ่ง apply prod ไปแล้ว) = out-of-order pending migration.
   - **ผลกระทบจริง = ไม่มี.** `prisma migrate deploy` เห็น 30 migrations, apply เฉพาะตัว pending (`add_deep_stock_pro_schema`) โดยไม่ complain/ไม่ re-run ตัวเก่า (build log 02:05:18-19 "All migrations have been successfully applied"). ปลอดภัยเพราะ additive-only ไม่พึ่ง 00008.

3. **P3 — Blocking Regression Gate (S-24) รันจริงไม่ได้.** worktree main-4 ไม่มี `.env`/`.env.local` + Claude ไม่คุม dev server → รัน `npm run e2e` / TC-INV-01..73 ไม่ได้. baseline เขียนเองว่า S-24 = "🛑 Blocking ก่อน merge/sign-off, FAIL แม้ 1 = BLOCKED" แต่ push ไปโดยยังไม่รัน (user authorize accepted-risk "verify ที่ prod").

## Root causes

- **P1:** worktree หลายตัว (main-2/3/4/5) ทำ feature ขนานบน shared repo + push main เอง; local `main` ref ของ main-4 ไม่ได้ sync กับ origin ก่อนแตก branch 00009 → มองไม่เห็น 47 commit จนถึงตอน merge. ไม่มีขั้น `git fetch` + เทียบ `origin/main` **ก่อน** เริ่ม implement phase.
- **P2:** เลข migration timestamp ตั้ง manual (`20260702000001`) โดยไม่เช็คว่า worktree อื่นจอง prefix เดียวกันไปแล้ว — เหมือนบทเรียน feature-number-collision แต่ระดับ migration ([[feedback_feature_number_collision]]).
- **P3:** โครงสร้าง worktree ที่ Controller ทำงาน (main-4) ไม่มี env → เป็น env-less by design; regression gate ที่ต้อง runtime DB/dev-server ทำในนี้ไม่ได้ตั้งแต่ต้น. Scope baseline ตั้ง S-24 blocking โดยไม่ได้ระบุ "รันที่ไหน/ใคร" → gate ที่บังคับไม่ได้ในทางปฏิบัติ.
- **P4:** สมมติว่ามี `timeout` binary (Linux-ism) บน macOS.

## Conventions to adopt

1. **ก่อนเริ่ม implement phase ที่ branch จาก local main → `git fetch origin` + เช็ค `git rev-list --left-right --count origin/main...HEAD` เสมอ.** ถ้า origin/main ล้ำหน้า → rebase/merge ให้ current ก่อนเริ่ม ไม่ใช่ค้างไว้เจอตอน merge ปลายทาง. (worktree ขนานหลายตัวบน shared repo = ต้อง sync บ่อย)
2. **Migration timestamp ต้อง collision-check ข้าม worktree/branch ก่อนตั้ง:** `git log --all --name-only | grep "prisma/migrations/<prefix>"` — ถ้า prefix ชน ให้บวก timestamp ให้ unique (เช่นใช้เวลาจริง). Out-of-order additive migration ไม่ fail `migrate deploy` แต่ hygiene ควรเลี่ยง.
3. **Blocking regression gate ต้องระบุ execution locus ใน scope baseline:** "รันที่ worktree ไหน (ที่มี env) / ใคร (user vs Claude) / ถ้าทำ pre-merge ไม่ได้ → fallback = prod smoke-test manual + ใคร sign-off". gate ที่บังคับไม่ได้ = ต้อง downgrade เป็น accepted-risk อย่างเปิดเผยตั้งแต่ Gate 0 ไม่ใช่ค้นพบตอนจะ push.
4. **ห้ามใช้ `timeout <n> <cmd>` ใน Bash tool บน macOS** — ใช้ Bash tool `timeout` param แทน.

## What went right (anchor ที่ควรทำซ้ำ)

1. **หยุดก่อน push เมื่อพบ divergence.** ไม่ blind `git merge origin/main && git push` — ตรวจ conflict surface (`comm -12` ของ 2 diff-name-only) ก่อน, ทำ local merge (reversible) + verify tsc/build **ก่อน** push (irreversible). Controller ถาม user ก่อน push เพราะ scope เปลี่ยนจาก FF → real merge + prod migration.
2. **Schema conflict resolve แบบ union สะอาด.** conflict ทั้ง 2 จุดเป็น additive-both (คนละ feature เพิ่มคนละ relation) → เก็บทั้งคู่ ไม่มีใครทับใคร; prisma generate + tsc=0 ยืนยัน.
3. **`order.service.ts` auto-merge ถูกต้อง.** 00009 แตะ stock-deduct region, 00008 แตะ buyer-badge-eval region — คนละ function ไม่ทับ. Verify ด้วย grep ว่า merged มีทั้ง `tx.stockMovement.create` (00009) + `evaluateBadges(...,"BUYER")` (00008) ครบ ไม่ใช่เชื่อ auto-merge เฉย ๆ ([[feedback_verify_dont_assume]]).
4. **Additive-only migration + short-circuit design ของ S-5.** shop ที่ไม่มี entitlement ACTIVE (ส่วนใหญ่) = path เดิม byte-identical → zero-regression by construction ไม่ใช่แค่หวังผล test.
5. **Build-log evidence สำหรับ migration apply.** ไม่เดาว่า deploy READY = migration ผ่าน — ดึง build log ยืนยันบรรทัด "Applying migration ... All migrations have been successfully applied" จริง.
