## Root causes

1. **P1** — เวลาเห็นไฟล์เดียวกันถูกแก้ทั้งสองฝั่ง สมองไปโฟกัสที่ "จะ merge ผ่านไหม" ซึ่งเป็นคำถามผิด
   คำถามที่ถูกคือ "เจตนาของอีกฝ่ายคืออะไร และของเราต้องวางทับตรงไหน"
2. **P2** — สำรวจจาก schema ที่ตัวเองกำลังแก้ (`OrderShipment`) ไม่ได้สำรวจจาก **ทางเข้าที่ผู้ใช้ใช้จริง**
   (โมดัล "แจ้งเลขพัสดุ" มี 3 แท็บ: ส่งเอง / สร้างพัสดุ iShip / เลือกจาก iShip) — ถ้าเปิดหน้าจอดูก่อน
   จะเห็นทันทีว่ามีมากกว่าหนึ่งทาง
3. **P3** — เลือก SQL เพราะ "เร็วกว่า" โดยยังไม่รู้ว่าจะมีผู้ใช้ที่สองของนิยามเดียวกัน — ตัดสินเรื่อง
   performance ก่อนตัดสินเรื่อง correctness boundary
4. **P4** — ค้นด้วย pattern ที่ตั้งจาก **ชื่อแบรนด์** แต่ไฟล์ตั้งชื่อตาม **การออกเสียง/หลบอักขระพิเศษ**
   (`&` ในชื่อไฟล์ต้อง escape ใน URL คนจึงเลี่ยงไปสะกด `and`)
5. **P5** — คิดถึง "ปุ่มนี้สำคัญแค่ไหน" (จึงใส่พื้นทึบให้เด่น) แทนที่จะคิดว่า "แถวนี้พูดภาษาอะไร"
6. **P6** — ถือว่าไฟล์ที่ user ส่งมา "พร้อมใช้" โดยไม่เปิดดูสัดส่วน/พื้นหลังก่อน

## Conventions to adopt

### C1 — ไฟล์ที่อีก session แตะพร้อมกัน: เช็คว่า "ของทั้งสองฝั่งอยู่ครบ" ไม่ใช่แค่ "rebase ไม่แดง"
หลัง rebase ทุกครั้งที่ชนไฟล์เดียวกัน ต้อง grep marker ของทั้งสองฝ่ายแล้วนับ ไม่ใช่ดูแค่ exit code
```bash
git log --oneline --name-only HEAD~N..origin/main | cat   # ก่อน rebase: เขาแตะไฟล์ไหน
# หลัง rebase: นับ marker ของเรา + ของเขา
for m in <marker ของเรา> <marker ของเขา>; do rg -c -- "$m" <file>; done
```
เจอว่าไฟล์ถูกเขียนใหม่ทั้งไฟล์จากทั้งสองฝั่ง → **ทิ้งของเรา เอาของเขาเป็นตั้งต้น แล้ววางเจตนาเรากลับ**
(ขยายจาก `feedback_merge_take_theirs_then_reapply_intent`)

### C2 — ก่อนแตะ "ข้อมูลที่ผู้ใช้กรอก" ให้ไล่ทางเข้าจากหน้าจอ ไม่ใช่จาก schema
ฟิลด์เดียวกันมักมีมากกว่าหนึ่งทางเข้าและมักเก็บคนละที่ (เลขพัสดุ = `ShipmentTracking` หรือ
`OrderShipment`) วิธีจับ: หาโมดัล/ฟอร์มที่ผู้ใช้กรอกค่านั้น แล้วนับว่ามีกี่แท็บ/กี่ปุ่ม submit
→ ดู `docs/conventions/one-value-many-entry-points.md`

### C3 — ตัวเลขที่ผู้ใช้กดแล้วต้องเห็นรายการตรงกัน ห้ามมีนิยาม 2 ชุด
ถ้ามีทั้ง "ตัวนับ" และ "ตัวกรอง" ของสิ่งเดียวกัน ต้องผ่านฟังก์ชัน pure ตัวเดียวกัน แม้จะแลกด้วยการ
โหลดแถวมานับใน TS แทน `COUNT` ใน SQL — ความเร็วที่ได้ไม่คุ้มกับบั๊ก "กดเลข 5 เข้าไปเจอ 4"
(กรณีนี้รับได้เพราะหน้า `/orders` ดึงออเดอร์ทั้งร้านอยู่แล้ว และ select แค่ 3 คอลัมน์)

### C4 — ค้นไฟล์ที่ user เพิ่งอัปโหลด ให้ list ทั้งโฟลเดอร์ก่อนค่อย filter
อย่าเดา pattern จากชื่อแบรนด์ — คนตั้งชื่อไฟล์เลี่ยงอักขระพิเศษเสมอ (`&` → `and`, ช่องว่าง → `-`)
```bash
ls -la <dir>                       # ดูทั้งหมดก่อน
diff <(ls before) <(ls after)      # หรือเทียบว่าอะไรเพิ่มมา
```
เป็นคลาสเดียวกับ Hard Rule 11 ("นับความครบด้วยชื่อไฟล์ ไม่ใช่จำนวนไฟล์")

### C5 — ปุ่มใหม่ต้องพูดภาษาเดียวกับแถวที่มันไปอยู่
ก่อนตั้ง class ให้ปุ่ม/ชิปใหม่ ให้อ่าน class ของ **เพื่อนบ้านในคอนเทนเนอร์เดียวกัน** ก่อนเสมอ แล้ว
ถามว่า "แถวนี้ใช้ภาษาไหน" (พื้นใส+สีบทบาท / พิลล์ทึบ / เส้นขอบ) — ความเด่นมาจากตำแหน่งและป้ายกำกับ
ไม่ใช่จากการเปลี่ยนภาษาของตัวเอง

### C6 — asset ที่ user ส่งมาต้อง "เปิดดู" ก่อนใช้ ไม่ใช่แค่ก๊อป
เช็ค 3 อย่างเสมอ: **สัดส่วน** (จัตุรัสไหม — ถ้าไม่ `object-cover` จะครอปเนื้อหาทิ้ง) · **พื้นหลัง**
(โปร่งใส/ขาว/สี — พื้นขาวบนการ์ดขาวต้องมี `ring`) · **ขนาดไฟล์**
→ ดู `docs/conventions/user-supplied-image-assets.md`

## What went right

1. **rebase-แล้ว-build ทุกครั้ง** — 8 รอบ ไม่มีครั้งไหนที่ push ของที่ยังไม่เคย build (ตาม
   `feedback_build_after_rebase_not_before` + `feedback_verify_then_push_separately`)
2. **แมปโลโก้ที่ระดับแบรนด์ไม่ใช่รายรหัส** — dropdown จริงมี 17 รายการแต่เป็นแพ็กเกจของ 9 แบรนด์
   (Flash 6 แบบ) แมปรายรหัสจะต้องเติมใหม่ทุกครั้งที่ iShip ออกแพ็กเกจ แล้วของใหม่ตกเป็นตัวย่อเงียบ ๆ
   ทดสอบครอบทั้ง 20 ตัวเลือกก่อนบอกว่าเสร็จ
3. **ถามก่อนเดาเรื่อง asset ที่ไม่มี** — ไม่ไปหาโลโก้ขนส่งจากอินเทอร์เน็ตมาใส่เอง (สิทธิ์ในภาพ +
   ห้ามพึ่งโฮสต์นอก) และไม่เดาสีแบรนด์มาทำ badge (ชนกฎห้าม hardcode สีนอก token)
4. **ตรวจ HR9/HR12 ด้วยตัวเองหลังแก้ไฟล์ด้วย python/perl** — script edit ไม่ trigger PostToolUse hook
   (`feedback_script_edits_bypass_hooks`) จึง grep เองทุกครั้ง; theme-guard จับ `🛑` ในคอมเมนต์ได้จริง 1 ครั้ง
5. **การแก้บั๊กคีย์บอร์ดคิดเผื่อบั๊กที่จะตามมา** — `blur()` ทำให้คีย์บอร์ดยุบ ซึ่งยิง `resize`/`scroll`
   ที่ listener เดิมผูกกับ `onClose` = เมนูจะเด้งหายเอง จึงเปลี่ยนเป็น reposition ในโหมด overlay
   (แย่กว่าอาการเดิมถ้าไม่คิดเผื่อ)
