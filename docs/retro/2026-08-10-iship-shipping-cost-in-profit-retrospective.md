# Retro — ต้นทุนค่าส่งจริงจาก iShip เข้าระบบกำไร (2026-08-09 → 08-10)

**ขอบเขต:** `c3164c44` → `9fd1bf92` (10 คอมมิต) · feature 00016 ส่วนขยาย + 00022
**จุดตั้งต้น:** user รายงาน *"ระบบต้นทุนของเราไม่นับรวมค่าจัดส่งจริง ทั้งตอนที่ขอครั้งแรก และตอนที่ขนส่งรับของจริง กำไรเลยผิดอยู่"*

## 1. Problems

### P1 — ค่าส่งไม่เคยถูกนับเป็นต้นทุนเลยสักที่เดียว และคอลัมน์ที่ตั้งใจเก็บมันก็ว่างทั้งฐาน

`computeOrderProfit()` (`src/lib/order-profit.ts:37-51`) และ `sumOrders()` (`src/services/pnl.service.ts:41-51`) ไม่รู้จัก `OrderShipment` เลย — ไม่มี surface ไหนอ่านมันตอนคิดกำไร

ลึกกว่านั้น: `OrderShipment.carrierPrice` มีคอลัมน์มาตั้งแต่ `20260726000000` แต่
- **จุดเขียนมีจุดเดียวทั้งรีโป** — `handleStatusWebhook()` (`iship.service.ts:1578`)
- **จุดอ่านมีศูนย์จุด** (คอมเมนต์ในสคีมาเขียนว่า "แสดงเฉย ๆ" ซึ่งไม่จริง ไม่มีหน้าไหน render)
- **webhook ตายบน prod** — env production ทั้ง 33 ตัวไม่มี `ISHIP_WEBHOOK_SECRET` และ route ตอบ 404 ทุกคำขอเมื่อไม่ได้ตั้ง secret

**หลักฐาน:** พัสดุ active 140 ใบบน prod — `carrierStatus` เต็มทั้ง 140 (polling ทำงาน) แต่ `carrierPrice` ว่างทั้ง 140

### P2 — ราคาค่าส่งซ่อนอยู่ใต้ชื่อฟิลด์ที่แปลว่าคนละเรื่อง

`query_orders`/`get_order` **ไม่มี `price`/`total_price`** — ตัวที่บอกค่าส่งจริงคือ **`discount_price`** ซึ่งชื่อแปลว่า "ส่วนลด" และ **`actual_weight`** คือน้ำหนักที่ชั่งจริง (แยกจาก `weight` ที่ร้านแจ้ง)

พิสูจน์ด้วยการยิง `check-price` ที่ `actual_weight` รายใบเทียบกับ `discount_price` → **ตรงกัน 55/56 ใบ** ส่วนใบที่ 56 (`TH066536981258`) ตรงกับ quote ที่น้ำหนักตอนคิดเงิน

### P3 — `weight` แปลกลับด้านกันในสอง endpoint ของ API เดียวกัน

`query_orders` → `weight` = ที่ร้านแจ้ง (มี `actual_weight` แยก) · `get_order` → `weight` = ที่ชั่งจริง (ไม่มี `actual_weight` เลย) — ยืนยันกับพัสดุจริง 12 ใบ ตรงกันทุกใบ

**คลาสเดียวกับ `dst_district` ที่ทำให้ 23 ออเดอร์บน prod เก็บที่อยู่สลับกันเมื่อ 2026-08-07** — ห่างกันแค่ 3 วัน

### P4 — `cod_fee` ถูกทิ้งโดยไม่จำเป็นมาตลอด

`cod_fee` ประกาศไว้ที่ `client.ts:338` ตั้งแต่ 2026-08-06 แต่ **ไม่เคยถูกเก็บหรือใช้ที่ไหนเลยทั้งรีโป** — และมันคือค่าที่ **iShip รู้ตั้งแต่วินาทีที่สร้างพัสดุ** (คิดจาก % ของยอด COD ไม่ต้องรอชั่ง) ยืนยันกับใบ `status=1`: `cod_fee=12.63` มีแล้วทั้งที่ `discount_price` ยังเป็น 0

### P5 — 🛑 ตัวเลขบางส่วนที่ไม่มีป้ายกำกับ ทำให้ผู้ใช้รายงานว่า "ระบบคำนวณผิด"

หลัง deploy รอบแรก user ทักมาว่า *"วันที่ 9 ได้ 31 ออเดอร์ ขั้นต่ำออเดอร์นึงต้อง 34 บาทแล้ว มันน่าจะเกินหรือเปล่า"* — จอขึ้น ฿328.88

ตรวจแล้ว **ตัวเลขถูกตามข้อมูลที่มี** แต่มีราคาจริงแค่ 7 ใบ อีก 24 ใบขนส่งยังไม่เข้ารับ iShip จึงยังไม่คิดเงิน

**ต้นตอคือเงื่อนไขที่ Controller เขียนเอง**: ป้ายเตือนครอบแค่ `shipping === 0` (ยังไม่มีสักใบ) กรณี **"มาบางส่วน"** ซึ่งเกิดบ่อยที่สุดจึงหลุดทุกวัน

### P6 — คำสั่ง SQL ตัดวันผิด 7 ชั่วโมง แล้วเกือบพาไล่ผิดทางทั้งกระดาน

`Order.createdAt` เป็น **`timestamp without time zone`** (เก็บ UTC) — `AT TIME ZONE 'Asia/Bangkok'` จึง**ตีความ**ค่าเป็นเวลาไทยแล้วแปลงเป็น UTC = เลื่อน**กลับทาง** ต้องใช้ `+ interval '7 hours'`

ผลคือรอบแรกผมได้ "วันที่ 9 มี 16 ออเดอร์" ขณะที่จอขึ้น 31 แล้วเกือบสรุปว่า **เป็นคนละร้านกัน** ก่อนจะย้อนมาตรวจชนิดคอลัมน์

### P7 — type ของ series ถูกประกาศซ้ำ 2 ที่ ทำให้ `tsc` มองไม่เห็นการเปลี่ยนชื่อฟิลด์

เปลี่ยน `expenseValues` → `shippingValues` ที่ `dashboard.service.ts` แล้ว **`tsc` ผ่านเงียบ ๆ** เพราะฝั่งจอใช้ type ที่ประกาศเองใน `dashboard/_constants/command-center.ts`

## 2. Root causes

| # | ปัญหา | ทำไมถึงเกิด | ทำไมถึงไม่มีใครเห็น |
|---|---|---|---|

## 3. Conventions to adopt

### C1 — 🛑 ค่าที่ผู้ให้บริการภายนอกส่งมา: ตัดสินจาก payload จริง ไม่ใช่จากชื่อฟิลด์ (ขยายของเดิม)

`docs/conventions/external-payload-schema.md` มีอยู่แล้วและ**เขียนถูกแล้ว** แต่รอบนี้พิสูจน์ว่าต้องขยายอีก 2 ข้อ:

1. **ชื่อฟิลด์อาจไม่เกี่ยวกับความหมายเลย** ไม่ใช่แค่ "ตรงข้ามกันสองทิศทาง" — `discount_price` = ค่าส่งที่ถูกเรียกเก็บจริง ไม่ใช่ส่วนลด
2. **การไม่มีฟิลด์ที่คาดว่าจะมี คือข้อมูลอย่างหนึ่ง** — `price`/`total_price` ไม่มีในขาเข้าเลย นั่นบอกว่า "ต้องหาที่อื่น" ไม่ใช่ "ระบบเขาลืมส่ง"

**วิธีที่ได้ผลจริง:** หาค่าที่รู้คำตอบอยู่แล้วจากอีกทาง (`check-price` ที่น้ำหนักจริง) แล้วไล่จับคู่กับทุกฟิลด์ที่เป็นตัวเลขในแถว — ตรงกัน 55/56 ใบคือหลักฐาน ไม่ใช่การตีความชื่อ

### C2 — 🛑 ห้ามคำนวณค่าที่เป็น "เงินที่ถูกหักไปแล้ว" ย้อนหลังด้วยการถามราคาใหม่

`check-price` ให้ **ราคาวันที่ยิง** ไม่ใช่ **เงินที่ถูกหักจริงตอนนั้น** — ต่างกัน 1 ใบใน 56 (`TH066536981258` 38 vs 41) และผิดแบบเงียบ ๆ ไม่มีอะไรฟ้อง

ค่าที่เป็น "ประวัติการเงิน" ต้องอ่านจากที่ระบบต้นทางบันทึกไว้เท่านั้น การ re-quote ใช้ได้อย่างเดียวคือทำ **ค่าประมาณที่ติดป้ายว่าเป็นค่าประมาณ**

### C3 — 🛑 ตัวเลขที่ยังมาไม่ครบ ต้องตัดสินใจว่าจะ "บอก" หรือ "เติมให้เต็ม" — ห้ามปล่อยครึ่ง ๆ

ตัวเลขบางส่วนที่หน้าตาเหมือนตัวเลขที่ครบแล้ว **อันตรายกว่าไม่มีตัวเลข** เพราะผู้ใช้ไม่มีทางรู้ว่ามันยังไม่จบ ได้แต่สรุปว่าระบบคำนวณผิดแล้วเลิกเชื่อทั้งหน้า (เกิดจริงในรอบนี้ ภายในไม่ถึงวันหลัง deploy)

ทางเลือกมี 2 ทางเท่านั้น:
- **บอก** — ป้ายกำกับที่ครอบ **ทั้ง 3 สถานะ** (ครบ / บางส่วน / ยังไม่มี) ไม่ใช่แค่สถานะสุดขั้ว
- **เติมให้เต็ม** — หาค่าสำรองที่ดีที่สุดที่มี แล้วให้ค่าจริงเขียนทับทีหลัง

รอบนี้ user เลือกทาง 2 และสั่งให้ **ไม่ต้องแสดงป้าย** (*"ลูกค้ารู้อยู่แล้ว"*) — ซึ่งใช้ได้เพราะเลือกทางเติมให้เต็มแล้ว ถ้ายังเป็นทาง "ปล่อยว่าง" การไม่มีป้ายคือบั๊กเดิมซ้ำ

### C4 — 🛑 ก่อนตัดวันใน SQL ต้องเช็คชนิดคอลัมน์ก่อนเสมอ

`information_schema.columns` ก่อนเขียน `GROUP BY` ที่แปลงเขตเวลา:
- `timestamp without time zone` (เก็บ UTC) → `col + interval '7 hours'`
- `timestamptz` → `col AT TIME ZONE 'Asia/Bangkok'`

ใช้ผิดตัวได้ผลลัพธ์ที่ยังดูใช้ได้ ไม่ error และเลื่อนวันไป 7 ชั่วโมง — พอไปเทียบกับหน้าจอแล้วไม่ตรง จะไล่ผิดทางไปหาสาเหตุที่ไม่มีอยู่จริง

### C5 — type ที่ถูกประกาศซ้ำเพราะข้ามเส้น server/client ต้องมีคอมเมนต์ชี้กันไปมา

`tsc` จับ drift ไม่ได้โดยนิยาม — อย่างน้อยต้องเขียนไว้ทั้งสองฝั่งว่า "แก้ที่นี่ต้องแก้อีกที่ด้วย" พร้อม path

## 4. What went right

1. **doc-first ทำงานจริง** — PRD/BRD ถูกเขียนก่อนแตะโค้ด และ "Open Gate" ที่ประกาศไว้ (ห้าม implement ก่อนยืนยันชื่อฟิลด์) เป็นตัวที่กันไม่ให้เดา `price` แล้วเขียนโค้ดผิดทั้งชุด
2. **dry-run ก่อนเขียนทุกครั้ง** — จับได้ว่าวิธีกวาดตามวันหาย 55/140 ใบ ก่อนเขียนอะไรลงฐาน
3. **เทียบสองวิธีที่ไม่เกี่ยวกัน** — กวาดตามวัน vs ไล่จากเลขพัสดุ ได้ยอดรวมเท่ากันเป๊ะ (฿4,113.00 + ฿1,312.54) = ยืนยันซึ่งกันและกัน
4. **mutation test จับเทสที่ผ่านโดยบังเอิญได้** — เทส null-guard รอบแรกเขียวทั้งที่ถอด guard ออก (เพราะ `Number(null)` เป็น 0 พอดี) ต้องแก้เคสให้ `codFee` มาแต่ `carrierPrice` ยังไม่มา ถึงจับได้จริง
5. **user ท้วงว่า "ปรกติเห็นก็ยิงให้ได้ ทำไมรอบนี้ไม่ได้"** แล้วกลายเป็นว่าทำได้ทุกขั้น — วิธีทำถูกบันทึกไว้ในหน่วยความจำตัวเองตั้งแต่ 2 วันก่อน (ดู `feedback_dont_declare_blocked_before_trying`)
