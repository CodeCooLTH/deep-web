# Retro — ตำบล/อำเภอ ขาเข้าจาก iShip สลับกันมาตลอด + โมดัลสถานะพัสดุที่ชวนกดวน (2026-08-07)

**Commit:** `70016446` (mapping + backfill), `f751a400` (โมดัล FAILED) — merge เข้า `main` แล้ว
**จุดตั้งต้น:** user ส่งภาพหน้าจอ error "ที่อยู่ผู้รับไม่ผ่านการตรวจสอบของขนส่ง" มาพร้อมประโยคว่า *"ทั้ง ๆ ที่ iShip แจ้งว่ากรุณาใช้ที่อยู่จากไฟล์นี้"* + ลิงก์ Google Sheet

---

## 1. Problems

### P1 — ที่อยู่ปลายทางของ 23 ออเดอร์บน prod ถูกบันทึกสลับ ตำบล ↔ อำเภอ

หลักฐาน (ออเดอร์ที่ user รายงาน `DP256908949FB6EA`):

```
ฐาน prod : subdistrict(ตำบล) = "กัลยาณิวัฒนา"   ← จริง ๆ คืออำเภอ
            district(อำเภอ)   = "แจ่มหลวง"       ← จริง ๆ คือตำบล
ไฟล์ iShip: เชียงใหม่, กัลยาณิวัฒนา(อำเภอ), แจ่มหลวง(ตำบล), 58130
```

ผลคือ `dst_district`/`dst_amphure` ที่ยิงออกไปเป็นคู่ที่ **ไม่มีอยู่จริง** ในชุดข้อมูลของ iShip → ขนส่งตีตก

**ขนาดของปัญหาที่เจอตอนสแกนทั้งฐาน:** 73 ออเดอร์ที่มีข้อมูลตำบล → **สลับ 23 ใบ** (08-01 ถึง 08-07) + อีก 3 ใบเขียน "อ.เมือง" เฉย ๆ ซึ่งไฟล์ของ iShip ไม่มี = 26 ใบที่เปิดพัสดุไม่ผ่านหรือกำลังจะไม่ผ่าน

### P2 — ต้นเหตุอยู่คนละหน้าจอ คนละสัปดาห์ กับที่ error โผล่

`DP256908949FB6EA` (08-07) ไม่ได้ผูกพัสดุจาก iShip เลย — มันเป็นออเดอร์ที่หยิบ **ที่อยู่ลูกค้าเก่า** มาจากใบ 08-04 ซึ่งเป็นใบที่ผูกมา ความเพี้ยนจึงเดินทางข้ามออเดอร์ผ่านฟีเจอร์ "ลูกค้าเก่า" โดยไม่มีใครแตะมันอีกเลย

### P3 — โมดัลตอนล้มเหลวเชิญให้ร้านกดสิ่งที่ไม่มีวันสำเร็จ

ปุ่ม "ลองใหม่" เป็นปุ่มทึบเต็มความกว้าง**เสมอ** ไม่ว่า error นั้นจะกดซ้ำแล้วมีโอกาสผ่านหรือไม่ และมีประโยคปิดท้ายจอว่า *"กดลองใหม่ได้เรื่อย ๆ"* แสดงเหมือนกันทุกกรณี

### P4 — ใบ FAILED ปิดทางถอย "ส่งเอง" ทั้งแถบ

`orders/[token]/page.tsx` ส่ง `hasIshipShipment={Boolean(shipmentPanel?.shipment)}` ซึ่งนับใบ FAILED ด้วย → `ShipmentEntryModal` ซ่อน segmented "ส่งเอง" → ร้านที่เปิดพัสดุกับ iShip ไม่ได้ (เครดิตหมด/token เสีย) **กรอกเลขพัสดุที่ไปส่งเองมาก็ไม่ได้** ทั้งที่ของส่งไปแล้ว
บรรทัดที่ห่างกัน ~30 บรรทัดในไฟล์เดียวกัน (`hasShipment`) นิยามถูกอยู่แล้วว่าต้อง `CREATED && !isDryRun`

### P5 — `docs/conventions/external-payload-schema.md` ถูกอ้างจาก CLAUDE.md และ spec 2 ใบ แต่ไม่เคยมีไฟล์อยู่จริง

## 2. Root causes

### RC1 (P1) — เดาว่า response สมมาตรกับ request แล้วรับความเสี่ยงไว้ด้วยด่านที่พึ่งสายตาคน

`parseParcelRow()` แมป `dst_district → subdistrict(ตำบล)` เพราะ **ฝั่งขาออกเป็นแบบนั้น** ความจริงคือ:

| | ตำบล | อำเภอ |
|---|---|---|
| ขาออก `create_order` | `dst_district` | `dst_amphure` |
| ขาเข้า `query_orders`/`get_order` | **`dst_area`** | **`dst_district`** |

พิสูจน์เมื่อ 2026-08-07 ด้วย `GET /api/get_order` กับพัสดุจริง 2 ใบ (`TH066536981258` → `dst_district=กาญจนดิษฐ์` อำเภอ, `dst_area=ช้างซ้าย` ตำบล)

หัวไฟล์เขียนไว้เองว่า *"พิสูจน์จากเอกสารไม่ได้"* แล้วปิดท้ายว่ารับได้เพราะ *"การผูกพัสดุมีขั้นเทียบที่อยู่สองคอลัมน์ให้ร้านตรวจด้วยตาเสมอ ถ้าจับคู่กลับหัวจริง ร้านจะเห็นทันที"* — **ผ่านไป 23 ใบไม่มีใครทักสักใบ** คนที่กดผูกกำลังยืนยันว่าเป็นพัสดุใบที่ตั้งใจ ไม่ได้กำลังตรวจ mapping ของ API

### RC2 (P1) — unit test ที่แต่งค่าเองตามข้อสันนิษฐานผิด จะเขียวเสมอ

`unlinked.test.ts` มีเทสชื่อ *"dst_district เข้าช่องตำบล และ dst_area เข้าช่องอำเภอ ไม่สลับกัน"* พร้อมคอมเมนต์อธิบายว่าจงใจแก้ค่าให้ตำบลกับอำเภอ **ต่างกัน** เพื่อไม่ให้ถูกหลอก — แต่ค่าที่ใส่มาจากข้อสันนิษฐานเดียวกับที่โค้ดใช้ เทสจึงยืนยันได้แค่ว่า "โค้ดทำตามที่คนเขียนคิด" ไม่ได้ยืนยันว่า "คนเขียนคิดถูก"

เทสที่ยึดค่าจากปลายทางจริงเท่านั้นที่มีอำนาจตัดสินเรื่องแบบนี้

### RC3 (P1) — ค่าที่ผิดยังหน้าตาถูกต้องทุกประการ

"กัลยาณิวัฒนา" กับ "แจ่มหลวง" เป็นสตริงไทยที่สมเหตุสมผลทั้งคู่ `tsc` เขียว Valibot ผ่าน หน้าจอแสดงผลสวย ไม่มีชั้นไหนในระบบที่รู้จัก "ชุดคู่ตำบล–อำเภอที่มีอยู่จริง" ทั้งที่ไฟล์ชุดนั้น **อยู่ในรีโปเราเอง** (`public/data/iship-address.json`) และถูกใช้เป็นแหล่งข้อมูลของ picker อยู่แล้ว

### RC4 (P3) — ปุ่มถูกออกแบบจาก layout ไม่ใช่จากความหมายของ error

โดเมนมี `IShipError.retryable` มาตั้งแต่แรก แต่หน้าจอไม่เคยอ่านค่านั้นเลย ปุ่มทึบจึงอยู่ตำแหน่งตายตัว ความรู้ว่า "กดซ้ำแล้วไม่ผ่านแน่ ๆ" มีอยู่ในระบบแต่ไม่เคยเดินทางถึงตา

รอบแรกที่แก้ยัง**ทำพลาดซ้ำในรูปแบบใหม่**: สลับให้ปุ่ม "แก้ข้อมูล" ขึ้นเป็นปุ่มทึบเมื่อ retry ถูกลดตำแหน่ง แต่เคสเครดิตไม่พอก็เข้าเงื่อนไขนั้นด้วย → ปุ่มทึบเต็มความกว้างกลายเป็น "แก้ที่อยู่" ทั้งที่แก้ที่อยู่ไม่ได้ช่วยอะไรเมื่อเงินไม่พอ ส่วนปุ่มเติมเงินที่แก้ได้จริงเป็น `btn-sm` สูง 28px (ต่ำกว่าเกณฑ์แตะ 44px) ซุกอยู่ในกล่องแดง — **บั๊กเดิมย้ายเจ้าภาพ ไม่ได้หายไป** จับได้จาก impeccable critique ไม่ได้จับได้เอง

### RC5 (P4) — นิยาม "ออเดอร์นี้มีพัสดุแล้ว" กระจายอยู่หลาย call site

เคยแก้นิยามนี้ไปแล้วรอบหนึ่งเมื่อ 2026-08-06 (`order-stage.service.ts` นับใบ FAILED เป็น "สร้างพัสดุแล้ว") แต่แก้เฉพาะจุดที่รายงานเข้ามา ไม่ได้ไล่ทุกที่ที่ถามคำถามเดียวกัน

## 3. Conventions to adopt

1. **ก่อนแมป field ของ response ภายนอกเข้าโครงข้อมูลเรา ต้องมี payload จริงจากปลายทางเป็นหลักฐาน** — เอกสาร ความสมมาตรของชื่อฟิลด์ และ "ฝั่งขาออกเป็นแบบนี้" ไม่นับ. ยิง endpoint จริงด้วยข้อมูลที่ค่าสองช่อง **ต่างกัน** แล้วเทียบกับชุดข้อมูลอ้างอิงของผู้ให้บริการ → `docs/conventions/external-payload-schema.md` §2
2. **ห้ามอ้าง "ให้ผู้ใช้ตรวจด้วยตา" เป็นด่านกันข้อมูลเพี้ยน** — ผู้ใช้ที่กดผ่านหน้าจอนั้นกำลังทำงานอื่นอยู่เสมอ. ยอมรับความไม่แน่นอนได้ แต่ต้องกันด้วยเทสที่ยึดค่าจริง หรือด้วยการตรวจกับชุดข้อมูลอ้างอิงตอนเขียนลงฐาน → §3
3. **ข้อมูลที่ผู้ใช้กรอกแล้วส่งให้ระบบภายนอกตรวจ ต้องยึดชุดข้อมูลของระบบนั้นเป็น SSOT** และเมื่อสงสัยว่าเพี้ยน ให้สแกนทั้งฐานเทียบชุดนั้น (เช็คคู่ปกติ → เช็คคู่สลับ → ที่เหลือดูด้วยตา) เจอทั้งคลาสในนาทีเดียวแทนการไล่ทีละใบ → §5
4. **UI ที่ผูกกับ error ภายนอก: ปุ่มทึบใบเดียว ชี้ทางที่แก้ได้จริงตามชนิด error และข้อความประกอบต้องผูกกับชนิด error ด้วย** ห้ามซ่อนปุ่มที่ถูกลดตำแหน่ง (จัดหมวดผิดแล้วซ่อน = ผู้ใช้ออกจากทางตันไม่ได้) → §6
5. **เทสที่แต่งค่าเองตามข้อสันนิษฐานของโค้ด ไม่มีอำนาจตัดสินความถูกต้องของข้อสันนิษฐานนั้น** — เทสคู่ที่อ่อนไหวแบบนี้ต้องยึดค่าจาก payload จริงและอ้าง track no./คำสั่งที่ใช้ยิงไว้ในคอมเมนต์

## 4. What went right

1. **user ให้เบาะแสที่ตัดทางผิดไปได้ทั้งเส้นตั้งแต่ข้อความแรก** — "iShip บอกให้ใช้ที่อยู่จากไฟล์นี้" ทำให้ตรวจไฟล์ก่อนอย่างอื่น แล้วพบว่าชุดข้อมูลในรีโปตรงกับ Sheet เป๊ะทั้ง 7,662 แถว จึงตัด "ข้อมูลเก่า" ออกได้ทันทีและไปโฟกัสฝั่งที่เขียนข้อมูล
2. **ภาพหน้าจอชุดที่สองของ user คือตัวชี้เป้าจริง** — ส่งจอเดียวกันสองสถานะ (ถูก/สลับ) มาให้เทียบ แล้วสรุปเองว่า "เหมือนระบบเอาตำบลไปเป็นอำเภอ" ตรงเป้าตั้งแต่ยังไม่มีใครเปิดโค้ด
3. **สแกนทั้งฐานแทนการซ่อมใบเดียว** — ถ้าแก้เฉพาะออเดอร์ที่ร้องเรียน จะเหลือ 25 ใบรอระเบิดทีหลัง และไม่มีทางรู้ว่าเป็นบั๊กเชิงระบบ (23/23 สลับหมด = ไม่ใช่คนกรอกผิด)
4. **ยิง API จริงเพื่อปิดคำถาม** แทนการเลือกคำตอบที่ดูสมเหตุสมผลกว่า — ค่าใช้จ่ายคือ 2 request แต่ได้ข้อสรุปที่เอาไปเขียนเป็นเทสถาวรได้
5. **impeccable critique จับ P0 ที่รอบแรกพลาด** (บั๊กปุ่มย้ายเจ้าภาพ + ทางตัน "ส่งเอง") — gate ที่ CLAUDE.md บังคับไว้ทำงานจริงในรอบนี้ ไม่ใช่พิธีกรรม
6. **`retryShipment` อ่านที่อยู่จาก `Order` ใหม่ทุกครั้ง** (แก้ไปเมื่อ 2026-08-06) ทำให้ backfill มีผลทันที ร้านกด "ลองใหม่" ได้เลยโดยไม่ต้องแก้อะไรในจอ
