## 3. บทเรียนรอง — เหตุผลที่ไม่ได้ตรวจ ทำให้ตัดของที่ถูกทิ้ง

ตอนแก้ตาม Impeccable critique ผมตัด section header (h5 เส้นประ = ลายเซ็น Paces) ออกจาก `ProfileForm` ด้วยเหตุผลว่า **"`/account` กับ `/shop` แยกด้วยตาไม่ออกเพราะ header เหมือนกันเป๊ะ"**

`safepay-ux` เปิด `ShopForm.tsx` ตรวจแล้วพบว่า **`/shop` ไม่ได้ใช้ h5 เส้นประเลยสักจุด** (ใช้ไอคอนวงกลม + stepper คนละแบบ) — การชนที่กลัวไม่มีอยู่จริง ผลคือหน้าหนึ่งมี 2 การ์ด อันบนไม่มีหัว อันล่างมี ซึ่งอ่านเหมือนบั๊ก

**บทเรียน:** เหตุผลที่ใช้ "ลบ" ของที่ระบบกำหนดไว้ ต้องมีหลักฐานระดับเดียวกับเหตุผลที่ใช้ "เพิ่ม" — ที่นี่คือแค่เปิดไฟล์เพื่อนบ้านดู 10 วินาที

## 4. สิ่งที่ทำได้ดี

### 4.1 ดึงกฎที่ต้อง mirror ออกเป็น helper แทนที่จะแก้ 2 ที่ให้เหมือนกัน

`needsRegistration`/`needsOnboarding` ถูกอ่าน 2 ที่ที่ต้องตรงกันเป๊ะเสมอ (`jwt` → proxy บังคับ redirect ที่ edge; `session` → UI แสดงสถานะ) เดิมกันด้วยคอมเมนต์ "mirror logic ใน jwt callback ด้านบน" ซึ่งกันได้แค่ตอนคนอ่านคอมเมนต์เจอ — ดึงเป็น `lib/onboarding-gate.ts` แล้ว drift ไม่ได้เชิงโครงสร้าง ไม่ใช่เชิงวินัย

**เกณฑ์ที่ใช้ตัดสิน:** ถ้าเอกสาร/คอมเมนต์ต้องเตือนว่า "อย่าลืมแก้อีกที่" นั่นคือสัญญาณว่ามันควรเป็นที่เดียว

### 4.2 ไม่เชื่อสเปกตัวเองเมื่อมันชนกับความจริง

สเปกเขียนว่าปุ่ม "กลับไปร้านเดิม" ให้ไป "ร้านธุรกิจแรกที่เป็นสมาชิก" — จะพาไปผิดร้านทันทีที่ user อยู่หลายร้าน (ซึ่งเป็นเคสปกติของกลุ่มนี้) เปลี่ยนเป็นจำร้านที่มาจากจริงผ่าน `sessionStorage` ก่อนทับ `activeShopId`

เช่นเดียวกับปุ่ม "เพิ่มเบอร์โทร" ที่เกือบลิงก์ไป `/register` เพื่อประหยัดโค้ด แล้วพบว่า proxy ปล่อยเข้า `/register` เฉพาะตอน `needsRegistration = true` ซึ่งผู้ถูกเชิญเป็น false เสมอ = ปุ่มที่เด้งกลับ dashboard ทันที

### 4.3 ตรวจข้อมูลจริงก่อนตอบคำถามเชิงสมมติฐาน

user ถามว่า "ทุก account ควรมีเบอร์โทรป่ะ" — แทนที่จะตอบจากความรู้สึก ไล่โค้ดพบว่า `upsertOAuthUser` สร้าง User โดยไม่มี phone แล้ว SELECT จาก prod ได้ตัวเลข: **10 บัญชี ไม่มีเบอร์ 6 · ไม่มีทั้งเบอร์และรหัสผ่าน 5** ซึ่งกลายเป็นที่มาของ FR-PAC-11 (แถบเตือนบัญชีที่กู้คืนไม่ได้)

## 5. เรื่องที่ gate จับได้จริง

| gate | จับอะไรได้ |
|---|---|
| `safepay-ux` (theme review) | `max-w-2xl` หาย · header ไม่สมมาตร · `SellerEmptyState` ที่ควร reuse แต่ compose ใหม่ · คอมเมนต์ที่อ้างข้อเท็จจริงผิดเรื่อง Icon ใน server component |
| Impeccable critique | ทางเข้ามือถือที่ทำให้ feature ไม่ปิดโจทย์ตัวเอง · contrast 2.13:1 ที่มี token แก้อยู่แล้ว · tap target 20px · เมนูที่โค้ดสวนคอมเมนต์ตัวเอง |
| Impeccable detector | **0 findings** ทั้งที่ critique ให้ 25/40 — ยืนยันบทเรียนเดิมว่า detector ผ่าน ≠ ดีไซน์ดี |

## 7. ข้อเสนอให้ promote เป็น convention

**"ยืนยันขอบเขตก่อนประกาศว่ามีอยู่แล้ว"** — ก่อนสรุปว่าฟีเจอร์/ความสามารถใดมีอยู่ในระบบแล้ว (โดยเฉพาะก่อนตัดมันออกจาก scope หรือก่อนสั่ง subagent) ต้องเปิดไฟล์ที่รับผิดชอบเรื่องนั้นและระบุได้ว่า **ทำอะไรได้บ้าง / ทำอะไรไม่ได้** เป็นข้อ ๆ การมีอยู่ของ path/โฟลเดอร์/ชื่อ component ไม่ใช่หลักฐาน

กฎเดียวกันครอบ `Base:` line: อ้างไฟล์ธีมได้เมื่อ **เปิดอ่านและก็อปโครงมาจริง** เท่านั้น
