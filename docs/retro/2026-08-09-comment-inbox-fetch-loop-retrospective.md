## 1. Problems

### P1 — อ็อบเจกต์ที่ hook คืน ถูกใส่ลง dep array แล้วกลายเป็นลูปไม่รู้จบ

`CommentsClient.tsx` effect ที่ดึงรายการโพสต์เขียน deps ไว้ว่า

```
}, [channelId, show.postStatus, channelTab, refreshPosts, listBusy])
```

`useListBusy()` คืน **object literal ใหม่ทุก render** (`return { busy, run, begin }`) ซึ่งไม่มีวัน
เท่ากับของ render ก่อนตาม `Object.is` วงจรจึงเป็น:

> fetch เสร็จ → `setPosts`/`setCounts` (array/object ใหม่ทุกครั้ง) → re-render → `listBusy` เป็น
> อ็อบเจกต์ใหม่ → effect รันใหม่ → fetch อีก

เร็วเท่า round-trip ไม่มีเงื่อนไขไหนหยุดเลย · `filterFirstRun` ที่มีอยู่กันได้แค่ **mount แรก**
ซึ่งเป็นคนละเรื่องกับลูปนี้ทั้งหมด

**แก้:** ดึง `begin` ออกมาถือเป็นตัวแปรของตัวเอง (`beginBusy`) แล้วใส่ตัวนั้นใน deps — ตัวมันเป็น
`useCallback([minMs])` จึงเสถียรข้าม render พฤติกรรมแผงโหลดไม่เปลี่ยนสักจุด

### P2 — **การ memo อ็อบเจกต์ที่ hook คืน ไม่ใช่ทางแก้** (ทางที่ดูเป็นธรรมชาติที่สุดและผิด)

สัญชาตญาณแรกคือไปห่อ `return { busy, run, begin }` ด้วย `useMemo` ที่ `useListBusy` แล้วจบ
— ไม่จบ เพราะ `busy` **ต้องเปลี่ยนตามงาน** อยู่แล้วโดยนิยามของ hook ตัวนี้ อ็อบเจกต์จึงยังเปลี่ยน
identity ทุกครั้งที่แผงเปิด/ปิด ผลคือลูปเดิมยังอยู่ แค่เดินช้าลงเป็นจังหวะละ ~350ms (`MIN_VISIBLE_MS`)
แทนที่จะเร็วเท่า RTT — **อาการเบาลงจนดูเหมือนหาย แต่ไม่หาย**

บทเรียน: hook ที่คืนทั้ง "สถานะที่เปลี่ยน" และ "ฟังก์ชันที่เสถียร" ปนกันในอ็อบเจกต์เดียว จะ memo
ให้ปลอดภัยไม่ได้เลย ทางแก้อยู่ที่ **ฝั่งผู้เรียกต้อง dep เฉพาะฟังก์ชัน** เท่านั้น

### P3 — ไม่มี gate ไหนเห็น เพราะ dep array ก้อนนี้ "ถูก" ตามกฎที่เราบังคับใช้เอง

`tsc` เขียว · `next build` เขียว · `theme-guard`/detector/grep gate เขียวหมด และ
`react-hooks/exhaustive-deps` **จะบอกให้ใส่ `listBusy` แบบนั้นเป๊ะ ๆ** ถ้าถามมัน

นี่คือดีเพนเดนซีที่ *ครบถ้วนและผิด* — เครื่องมือทุกตัวของเราตรวจ "รูปแบบ" ส่วนสิ่งที่ผิดคือ
**ความเสถียรของ identity** ซึ่งไม่มีอะไรในรีโปนี้วัดได้ (คลาสเดียวกับ Hard Rule 16 ที่ว่า gate
ตรวจรูปแบบไม่ตรวจความหมาย)

### P4 — `/orders` ใช้ hook ตัวเดียวกันมา 2 วันโดยไม่พัง จึงไม่มีใครสงสัย hook

`useListBusy` ถูกเขียนขึ้นเพื่อ `/orders` เมื่อ 2026-08-07 และที่นั่นเรียก `run()` จาก
**event handler อย่างเดียว ไม่เคยมี effect ผูกกับมันเลย** — hook จึงมีประวัติ "ปลอดภัย" ที่เป็นจริง
เฉพาะกับรูปแบบการใช้งานแบบหนึ่งเท่านั้น

`/inbox/comments` หยิบ hook นี้ไปใช้ตอน critique รอบ 2 ด้วยเหตุผล sibling-surface-parity
(ถูกต้องแล้ว) แต่ **ใช้คนละท่า** — ห่อที่ effect เพราะตัวกรองหน้านี้ trigger ผ่าน state ไม่ใช่ผ่าน
handler เดียว. การหยิบของที่ "พิสูจน์แล้วว่าใช้ได้" ไปใช้ ไม่ได้พาการพิสูจน์นั้นติดไปด้วย ถ้ารูปแบบ
การเรียกต่างกัน

### P5 — ผมใช้ `rg -rn` แล้วอ่านผลลัพธ์ที่ถูกดัดแปลงโดยไม่รู้ตัว

คำสั่งแรกที่ไล่หา `mapChatServiceError` คือ `rg -rn "mapChatServiceError" .` — `-r` ของ ripgrep
คือ **`--replace`** ไม่ใช่ recursive ผลที่ได้กลับมาจึงเป็นซอร์สที่ทุก match ถูกแทนด้วยตัวอักษร `n`:

```
./src/app/api/chat/conversations/[id]/messages/route.ts:function n(e: unknown, context: string) {
```

ผมอ่านแล้วสรุปชั่วขณะว่า "ไฟล์นี้ถูก minify?" ซึ่งผิดสนิท และรอบถัดมาที่ค้น `commentOriginNoInbound`
ก็ได้ผลเป็น `n?: boolean` ทำให้เกือบสรุปว่าชื่อฟิลด์ในไฟล์ไม่ตรงกับที่เพิ่งอ่าน

**เสียหายจริงในรอบนี้: ไม่มี** (จับได้ภายในสองคำสั่งเพราะผลลัพธ์ขัดกับไฟล์ที่เพิ่ง `Read` มาเอง)
แต่คลาสนี้อันตรายเพราะ **ripgrep ไม่ error** มันทำตามที่สั่งเป๊ะ ๆ แล้วคืนผลที่หน้าตาเหมือนซอร์สจริง
ทุกประการ ถ้าไปเจอในไฟล์ที่ยังไม่เคยเปิดอ่าน จะไม่มีอะไรขัดให้เอะใจเลย

### P6 — `build` และ `npm test` ในเวิร์กทรีนี้ล้มด้วยเหตุสิ่งแวดล้อม ไม่ใช่โค้ด

- `npm run build` → `BUILD_EXIT=1` ที่ `Error: [link-intent] NEXTAUTH_SECRET ไม่ได้ตั้งค่า — fail-closed`
  เพราะเวิร์กทรีนี้ไม่มี `.env.local` (CLAUDE.md บันทึกข้อจำกัดนี้ไว้แล้วตั้งแต่ 08-04)
  พิสูจน์ว่าไม่เกี่ยวกับโค้ดด้วยการ build ซ้ำโดยใส่ค่า dummy → `BUILD_EXIT=0`
- `npm test` = `dotenv -e .env -- npx vitest` ซึ่ง `.env` ก็ไม่มี
- `npx vitest run` เปล่า ๆ **ดูดไฟล์ `e2e/*.spec.ts` (Playwright) เข้ามาด้วย** เพราะ vitest config
  ไม่มี `include`/`exclude` → FAIL 15 ไฟล์รวดที่ไม่ใช่หนี้จริงสักไฟล์ ต้อง scope เป็น `npx vitest run src/`

ทั้งสามอย่างทำให้ "ตัวเลขที่เห็นรอบแรก" ไม่ใช่ตัวเลขที่ควรรายงาน — ต้องแยกให้ออกทุกครั้งว่ากำลังดู
ความล้มเหลวของโค้ด หรือความล้มเหลวของที่ที่รันมัน

## 2. Root causes

1. **hook คืนอ็อบเจกต์ที่ประกอบด้วยของสองชนิด** (state ที่ต้องเปลี่ยน + callback ที่เสถียร)
   โดยไม่มีอะไรในซิกเนเจอร์บอกผู้เรียกว่าอันไหนเอาไปใส่ deps ได้
2. **สัญญาการใช้งานของ hook ไม่ได้ถูกเขียนไว้ที่ตัว hook** — ความรู้ว่า "เรียกจาก handler เท่านั้น"
   อยู่ในรูปแบบโค้ดของ `/orders` ไม่ได้อยู่ในคอมเมนต์หรือ type ที่คนหยิบไปใช้ต่อจะเห็น
3. **ไม่มีชั้นไหนวัด referential stability** และเครื่องมือที่ควรจะเตือน (`exhaustive-deps`)
   กลับเป็นตัวที่แนะนำให้เขียนแบบที่พัง

## 3. Conventions to adopt

- 🛑 **ห้ามใส่ "ค่าที่ hook คืนมาทั้งก้อน" ลง dep array ถ้า hook นั้นคืน object/array literal**
  ให้ destructure เอาเฉพาะ `useCallback`/`useRef` ที่ต้องใช้จริงไปใส่แทน — เขียนไว้แล้วที่
  `docs/conventions/hook-return-identity-in-deps.md`
- 🛑 **hook ที่คืนหลายค่ารวมกัน ต้องเขียนที่ตัว hook เองว่าอันไหน dep ได้ อันไหนไม่ได้**
  ไม่ใช่ปล่อยให้ผู้เรียกอนุมานจากตัวอย่างการใช้งานของหน้าอื่น
- 🛑 **หยิบ hook/คอมโพเนนต์จากหน้าพี่น้องมาใช้ ต้องดูว่า "ท่าเรียก" เหมือนกันไหม ไม่ใช่แค่ว่ามันถูกใช้
  ที่นั่นแล้วไม่พัง** — `sibling-surface-parity.md` บอกให้ยกของมาใช้ซ้ำ ซึ่งถูก แต่หลักฐานความปลอดภัย
  ผูกกับรูปแบบการเรียก ไม่ได้ผูกกับตัวโมดูล
- 🛑 **`rg -r` คือ `--replace`** ห้ามใช้เป็น "recursive" (ripgrep เดินโฟลเดอร์ให้เองอยู่แล้ว)
  ผลลัพธ์ที่ถูกแทนค่าหน้าตาเหมือนซอร์สจริงและไม่มี error ใด ๆ เตือน
- 🛑 **แยก "โค้ดพัง" ออกจาก "ที่รันพัง" ก่อนรายงานเลขใด ๆ** — เวิร์กทรีที่ไม่มี `.env.local`
  ทำให้ `build`/`npm test` ล้มด้วยเหตุที่ไม่เกี่ยวกับ diff เลย ต้องพิสูจน์ด้วยการรันซ้ำแบบใส่ค่า dummy
  และต้อง scope vitest เป็น `src/` ไม่งั้นได้ Playwright ปนมา

## 4. What went right

- **ตั้งสมมติฐานจากรูปร่างโค้ดแล้วไปพิสูจน์ทันที ไม่ไล่เดาที่ realtime/poll** — คำว่า "ยิงรัว ๆ"
  ชวนให้ไปมองระบบ realtime หรือ interval 60 วิ ก่อนเป็นอันดับแรก แต่การไล่ dep array ของทุก effect
  ที่แตะ `fetch` พาไปถึงตัวการภายในไม่กี่คำสั่ง
- **เทียบกับหน้าที่ใช้ของเดียวกันแล้วไม่พัง** (`/orders`) เป็นขั้นตอนที่ทำให้มั่นใจว่าต้นเหตุคือ
  *ท่าเรียก* ไม่ใช่ตัว hook — ซึ่งเปลี่ยนทางแก้จาก "ไปแก้ hook" เป็น "แก้ dep + เขียนสัญญาไว้ที่ hook"
- **mutation test ก่อนเชื่อว่าเทสใช้ได้** — คืน dep เดิมกลับไป เทสแดงพร้อมชี้ไฟล์และเนื้อ deps
  (`CommentsClient.tsx → deps [channelId, show.postStatus, channelTab, refreshPosts, listBusy]`)
  คืนกลับ เขียว
- **เทสกันซ้ำเขียนแบบไม่ hardcode รายชื่อไฟล์** — สแกนทุกไฟล์ที่เรียก `useListBusy()` เอง
  หน้าใหม่ที่หยิบ hook ไปใช้ทีหลังถูกตรวจอัตโนมัติโดยไม่มีใครต้องมาแก้เทส
  พร้อมเคสที่สองที่ยืนยันว่า "ยังหาไฟล์เจออยู่จริง" กันเทสเขียวเพราะไม่เจออะไรเลย
- **เทียบเลขเทสแดงกับ baseline ที่บันทึกไว้** — 18 แดงตรงกับที่ CLAUDE.md เขียนไว้เป๊ะ และตรวจซ้ำ
  ว่าไฟล์เทสที่แดงทั้ง 6 ไฟล์ไม่มีไฟล์ไหน import โค้ดที่แก้เลย
- **ทำตาม HR17 ครบ** — rebase ก่อน แล้วค่อย build (build ล้มรอบแรกเพราะ env จริง ๆ ไม่ใช่เพราะ
  คอมมิตที่แทรกเข้ามา) เช็ค fast-forward ซ้ำแยกคำสั่งก่อน push และเช็คว่าไม่มีไฟล์ทับซ้อนกับฝั่ง main

## 5. สิ่งที่ยังไม่ได้ทำ (หนี้จากรอบนี้)

1. **browser QA** — ยังไม่เคยกดจริง user รับไปตรวจเองบน prod ตามที่ตกลงกันไว้
   จุดที่ต้องดู: เปิด `/inbox/comments` แล้วดู Network tab ว่า `/api/chat/comments/posts`
   ยิงครั้งเดียวตอนกรอง ไม่ใช่ยิงต่อเนื่อง
2. **หนี้จาก retro `2026-08-09-comment-inbox-polish-and-critique` §4 ยังไม่ได้แตะเลยสักข้อ**
   (หยุดมาแก้บั๊กนี้ก่อน) — ที่สำรวจไว้แล้วว่าทำได้จริง: toast ตอนกดส่งยังพูดกฎ 24 ชม.
   ในเธรดที่ลูกค้าไม่เคยพิมพ์ (`mapChatServiceError` ไม่มี conversation ในมือ — ทางแก้ที่หาไว้แล้ว
   คือ resolve บริบทที่ฝั่ง server ใน catch ของ POST เพราะ `conv` ถูก fetch อยู่แล้ว
   และแก้ที่เดียวได้ทุกพื้นผิว ไม่ต้องแตะ client) · minor 5 ข้อจาก critique รอบ 2 ·
   เทสแดง `channel-chat-ingest`
3. **ไม่มีเทสที่พิสูจน์ referential stability จริง ๆ** — เทสที่เพิ่มรอบนี้อ่าน *ซอร์ส* ไม่ได้ render
   hook เพราะ vitest ตั้ง `environment: "node"` และรีโปไม่มี `jsdom`/`@testing-library/react`
   ถ้าวันไหนเพิ่มดีเพนเดนซีชุดนั้น ควรเสริมเทสที่ render จริงแล้ววัด identity
4. **vitest config ไม่มี `exclude` ของ `e2e/`** — ทำให้ `npx vitest run` เปล่า ๆ ใช้ไม่ได้เลย
   ควรเพิ่มเพื่อให้คำสั่งที่คนพิมพ์โดยสัญชาตญาณให้ผลที่ถูก
