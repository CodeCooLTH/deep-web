## Root causes

1. **P1 — ตีความ "Impeccable ชนะเรื่องสี" (HR8) กว้างเกินขอบเขตที่มันตั้งใจ** กฎนั้นหมายถึง *ลำดับชั้น/น้ำเสียง/ความหมายของสี* ไม่ได้อนุญาตให้เปลี่ยน **เฉด (hue)** ของสีแบรนด์ที่ธีมกำหนด การแก้คอนทราสต์ที่ถูกต้องต้องคงเฉดเดิม
2. **P1 — เชื่อ mapping จาก subagent โดยไม่ตรวจสมมติฐานที่มันตั้ง** สเปกของ `safepay-ux` เขียนกติกาว่า *"ทุก `text-{tone}` ที่ใช้เป็นสีตัวอักษร**หรือสีไอคอน** → `-ink` เสมอ"* ซึ่งรวมไอคอนเข้าไปด้วย — ตรงนั้นคือจุดผิด แต่ผมรับมาทั้งก้อนเพราะตารางละเอียดถึงระดับ file:line จนดูน่าเชื่อ **ความละเอียดของ output ไม่ใช่หลักฐานว่าสมมติฐานถูก**
3. **P1 — ไม่ได้ถามว่า token ที่จะใช้มาจากไหน** ใช้เวลา 10 วินาที grep `theme/paces` ก็รู้ว่า `-ink` ไม่มีในธีม แต่ไม่ได้ทำ เพราะเห็นว่ามันถูกใช้ใน `(paces)` อื่นแล้ว 77 จุดจึงเหมาว่า "เป็นของที่ใช้ได้"
4. **P2 — ยอมรับ "verify ไม่ได้" เป็นเหตุผลให้ push ต่อ** แทนที่จะถือเป็นเงื่อนไขบล็อกสำหรับงานที่ผลลัพธ์เป็น *สิ่งที่ตาเห็น* งานที่ตรวจด้วย tsc/curl ได้จริง (Range 206, rawMessage) ปลอดภัย แต่งานสีเป็นคนละประเภทและถูกปฏิบัติเหมือนกัน
5. **P3 — แก้ control flow แล้วไม่ได้ไล่ว่า "ใครเคยพึ่ง side-effect ของ flow เดิม"** การที่ error ถูกโยนก่อนสร้างแถวคือ *สัญญาโดยบังเอิญ* ที่ฝั่ง client พึ่งอยู่ พอเอาออกจึงพังในที่ที่ไม่ได้แก้
6. **P5 — คอมเมนต์อธิบาย "ทำไม" ไม่ถูก re-validate ตอนเงื่อนไขเปลี่ยน** เหตุผล append-only ถูกอ้างอิงต่อทั้งที่ฟีเจอร์ลบข้อความมาทีหลังแล้ว

## Conventions to adopt

1. **แก้คอนทราสต์ห้ามเปลี่ยนเฉด** — ปรับความสว่าง/ความเข้มของ token เดิมได้ ห้ามสลับไปตระกูลสีอื่น ถ้าเฉดที่เข้มพอจนผ่านเกณฑ์ทำให้สีเปลี่ยนความหมาย (เหลือง→น้ำตาล) แปลว่า **ทางแก้ไม่ใช่การเปลี่ยนสีตัวอักษร** ให้ไปแก้ที่ตัว token หรือเปลี่ยนพื้นหลังแทน
2. **ไอคอนที่ "สี = ตัวตน" ไม่อยู่ใต้กฎคอนทราสต์ข้อความ** — ดาวต้องเหลือง โลโก้ช่องทางต้องเป็นสีของช่องทาง WCAG 1.4.11 ไม่บังคับเมื่อข้อมูลมีในรูปแบบอื่นแล้ว (เรียงลำดับ/`aria-label`/เมนู) แยกจากไอคอนที่อยู่คู่ข้อความเพื่อสื่อสถานะ ซึ่งใช้กฎเดียวกับข้อความ
3. **ก่อนใช้ token สี ต้อง grep `theme/` ว่ามีจริงไหม** — ถ้าไม่มี = เป็นส่วนขยายของโปรเจกต์ ต้องรู้ตัวและระบุเหตุผลใน commit ไม่ใช่ใช้เพราะ "ที่อื่นก็ใช้"
4. **งานที่ผลลัพธ์เป็นสิ่งที่ตาเห็น ห้าม push ก่อนเห็นด้วยตา** — สี/เฉด/spacing/ไอคอน ไม่ใช่ประเภทเดียวกับ logic ถ้า browser QA ทำไม่ได้จริง ให้ **หยุดและบอก user ให้ดูให้** ไม่ใช่ push แล้วเขียน known-gap
5. **แก้ control flow ต้องไล่ side-effect ที่คนอื่นพึ่งอยู่** — ถามว่า "ก่อนหน้านี้บรรทัดนี้กันอะไรไม่ให้เกิด" ไม่ใช่แค่ "บรรทัดนี้ทำอะไร"
6. **คอมเมนต์ที่อ้างกฎ ต้อง re-validate ตอนแก้โค้ดรอบนั้น** — ถ้ากฎที่อ้างถูกยกเลิกไปแล้วโดยฟีเจอร์ทีหลัง ให้แก้คอมเมนต์ในรอบเดียวกัน

## What went right

1. **`rawMessage` คืนทุนภายใน 8 นาที** — เปิดคอลัมน์ตอน ~11:20 สายที่ไม่ได้รับเกิด 11:28 จับ payload ได้ทันทีจนสร้างการ์ดสายโทรได้ในวันเดียวโดยไม่ต้องเดา และตอบปริศนา `[ข้อความจากระบบของ Facebook]` ที่ค้างมาหลายวันได้ว่ามันมาจาก `graph-backfill` ไม่ใช่ webhook — **การเก็บ input ดิบไว้มีค่ากว่าการเดาเก่ง**
2. **ปิดคำถามด้วยการยิงจริง ไม่ใช่เชื่อคอมเมนต์เก่า** — คอมเมนต์ในโค้ดอ้างว่า Graph คืนค่าว่าง ผมยิง `GET /{mid}?fields=…` ด้วย page token จริงและได้ `HTTP 200 { "message": "" }` ไม่มี `attachments` เลย → ปิดประเด็นถาวร ไม่ต้องมีใครมาลองซ้ำอีก
3. **merge ที่อีก session รื้อไฟล์เดียวกัน โดยไม่ทับงานเขา** — `git log HEAD..origin/main -- <file>` ก่อน resolve ทำให้เห็นว่าเขา *ออกแบบใหม่* ไม่ใช่แก้บรรทัด จึงเอาโครงของเขาทั้งไฟล์แล้ววางเจตนาของเรากลับทีละข้อ และ **ตัดข้อเสนอของตัวเองทิ้ง 1 ข้อ** เพราะสวนทางกับงานเขา
4. **ยึดลำดับ migration-ก่อน-deploy** — ตรวจว่า `postinstall` รันแค่ `prisma generate` ไม่ได้รัน `migrate deploy` จึง apply migration บน prod ก่อน push ถ้าสลับลำดับ ทุก webhook จะเขียนแถวไม่ผ่าน = แชทพังทั้งระบบ
5. **impeccable critique จับของที่ tsc/gate ทั้งหมดมองไม่เห็น** — ตัวแปรตาย, คอนทราสต์, ปุ่มเดียวทำงาน 2 แบบ ล้วนผ่าน gate อัตโนมัติหมด
