# Retro — ส่งรูปเข้า LINE ไม่ได้ → การ์ดในแชทครบทุกช่องทาง

> **ช่วงเวลา:** 2026-08-10 (เย็น) → 2026-08-11
> **จุดตั้งต้น:** ร้านแจ้งว่า "chat line ส่งรูปไม่ได้ ขึ้นว่ายังไม่รองรับ"
> **คอมมิต (เรียงตามที่ขึ้น prod):** `9e60ba20` ส่งไฟล์แนบ LINE · `b265c9bb` ปุ่มส่งบอกโควตา+นับถอยหลัง · `ff7b2576` การ์ดออเดอร์ Flex + รับ postback · `486ff764` การ์ดสินค้า LINE · `850f1ef3` การ์ดสินค้า Messenger/IG + โหมดที่ 4 · `617bb496` UI การ์ดรูปใหญ่ · `d26eadfb` รูปเต็มกรอบในแอป · `7f02faa3` รูปเต็มกรอบฝั่ง Meta
> **สถานะ:** ขึ้น prod ครบ · user ทดสอบเองบนเครื่องจริงระหว่างทางทุกรอบ

## 1. Problems

### P-1 🛑 ฟีเจอร์สร้างเสร็จแล้ว แต่ถูกปิดไว้ด้วย default-deny ที่ไม่มีใครกลับมาเปิด — และ **เทสยืนยันบั๊กให้เขียว 8 วัน**

อาการที่ร้านแจ้งไม่ใช่โค้ดพัง แต่คือ `ATTACHMENT_CHANNELS` ใน `chat-attachment.ts` ไม่มี `'LINE'`
บรรทัดนั้นเขียนไว้ 2026-08-02 ตอน 00025 ยังไม่ live โดยตั้งใจให้ default deny — แล้ว S-8 (ขาออก)
เสร็จ ติ๊ก ✔ ใน SDS และ `line-adapter` แปลง IMAGE/VIDEO/AUDIO ได้ครบมาตลอด **แต่ไม่มีใครกลับมาลบชื่อ
LINE ออกจาก deny-list**

น่าเจ็บที่สุดคือมีเทสชื่อ *"ช่องทางที่ยังไม่ live = default deny ไม่ใช่ default allow"* ที่ยืนยัน
`LINE → ok:false` ไว้เป็น **หลักฐานว่าระบบทำงานถูก** เทสนั้นเขียวทุกวันเป็นเวลา 8 วันขณะที่ร้านส่งรูปไม่ได้

### P-2 🛑 ข้อห้ามในเอกสาร 3 ที่ อ้าง ID ของ **ฟีเจอร์อื่น** — และมันทำให้เกณฑ์ที่ user ขอไว้จริงหายไปทั้งข้อ

user ขอ countdown 59 วิ ผมไปเปิดดูก่อนว่าทำไมถึงห้าม พบว่า `line-oa-ui-design-spec` ·
`line-quota-meter-design-spec` · `scope baseline` และคอมเมนต์ในโค้ด ห้ามไว้ชัดเจนโดยอ้าง **"BRD AC-005-05"**

**`AC-005-05` ไม่มีอยู่ใน BRD ของ 00025 เลย — เป็น ID ของ feature 00019 (AI Reply Assistant) ซึ่งพูดเรื่องตัวเลขสต็อก**

ของจริงคือ bullet ไม่มีเลขใต้ `FR-LINE-05` และมี **สองข้อวางติดกัน**:
1. *"เธรดแสดงให้ร้านเห็นว่า…**และเหลือเวลาเท่าไร**"* ← **ไม่เคยถูก implement เลย**
2. *"ต้องไม่กดดันจนร้านรีบตอบผิด ๆ — เป็นข้อมูล ไม่ใช่การนับถอยหลังที่สร้างความเครียด"*

ข้อ 2 ถูกอ่านเป็น "ห้ามตัวเลข" แล้วข้อ 1 หายไปพร้อมกัน สิ่งที่ user ขอในวันนี้จึงไม่ได้ขัดมติ —
**มันคือเกณฑ์ที่ค้างมาตั้งแต่แรก**

### P-3 🛑 เปิด backend โดยไม่ดูว่าใครเป็นคนกด — และเป็นบทเรียนที่ผมเพิ่งเตือนเองเมื่อวานก่อน

รอบ `486ff764` ผมเปิดการ์ดสินค้าให้ LINE เสร็จ push ขึ้น prod โดย**ไม่เคยเช็คว่ามี UI ไหนเรียกมัน**
ความจริงคือ **ไม่มีปุ่มไหนในระบบส่ง `type=PRODUCT` เลยสักปุ่ม** — แผง "เลือกสินค้า" ทั้ง 3 โหมด
เติมข้อความ+รูปลงช่องพิมพ์เท่านั้น และหัวไฟล์ `ProductPickerPanel.tsx` เขียนเหตุผลไว้เองว่า
*"Messenger/IG คืน 400"*

สิ่งที่จับได้คือ **คำถามของ user** ("แล้วมันกดส่งสินค้ายังไงอ่ะ") ไม่ใช่ tsc/เทส/build

เมื่อวันก่อนผมเพิ่งอธิบายกฎนี้เองตอนทำ postback ("ตัวรับต้องมาก่อนตัวส่ง เพราะส่งปุ่มไปแล้วไม่มีตัวรับ
= ลูกค้ากดแล้วเงียบหาย") แล้ววันถัดมาก็เดินเข้าฝั่งตรงข้ามของกฎเดียวกัน

### P-4 🛑 HR17 ของจริง — commit คู่ขนานก็อป `object-contain` ไปตอนที่ผมกำลังแก้บรรทัดนั้น

`76c3a9b6` (การ์ดสินค้าหลายรายการ) ถูก push แทรกระหว่างที่ผมแก้ `ProductCardBubble` เป็น `object-cover`
ตามที่ user สั่ง — และการ์ดใหม่ของเขา **ยกภาษาการออกแบบมาจากไฟล์ผม รวม `object-contain`**

`git rebase` ผ่านสะอาด ไม่มี conflict สักบรรทัด เพราะเป็นโค้ดคนละก้อน ถ้าเชื่อว่า "rebase ผ่าน =
ปลอดภัย" ผลจะเป็น: ส่งสินค้า 1 ใบ = รูปเต็ม · ส่งหลายใบ = มีแถบขาว — **การ์ดชนิดเดียวกันในเธรดเดียวกัน
อ่านเป็นคนละภาษา โดยไม่มี tsc/เทส/theme-guard ตัวไหนฟ้อง**

รูปแบบเดียวกับ `b51afb48` ที่ CLAUDE.md บันทึกไว้ (ชิปใหม่ก็อป `focus:outline-none` ตอน audit
กำลังแก้บรรทัดนั้น) — คราวนี้ HR17 ทำงานเพราะ **ทำตามขั้นตอนของมันจริง** ไม่ใช่เพราะโชคดี

### P-5 เทสที่เทียบกับค่าคงที่ของตัวเอง = ยืนยันว่า "โค้ดทำตามค่าคงที่" ไม่ใช่ "ค่าคงที่ถูก"

`expect(meta.height).toBe(META_CARD_HEIGHT)` เขียวตลอดแม้เปลี่ยนกรอบจาก 1080×1080 กลับไป 1200×628
เพราะสองฝั่งของสมการขยับพร้อมกัน — จับได้ตอนทดสอบด้วย mutation เท่านั้น ต้องตรึง **อัตราส่วน**
(`WIDTH === HEIGHT`) แยกออกมาเป็นข้อของตัวเอง

### P-6 ตีความประโยคในเอกสารภายนอกว่าเป็น "ข้อบังคับ" ทั้งที่มันบอก "สิ่งที่ระบบทำได้"

เอกสาร Meta: *"Messenger scales or crops photos in the generic template that are not 1.91:1"*
ผมอ่านแล้วสรุปว่าถูกบังคับ จึงทำรูป 1.91:1 + `contain` ซึ่งได้แถบขาวหนา

**ภาพจริงที่ user ส่งมาล้มการตีความนั้นในภาพเดียว** — การ์ด Facebook ของร้านอื่นแสดงรูปสูงกว่า 1.91:1
และเห็นเต็มใบ พอไม่ถูกบังคับ จัตุรัส + `cover` ชนะทั้งสองทาง: เต็มกรอบ **และ** เสียเนื้อรูปน้อยกว่า
(แนวตั้ง 3:4 เสีย ~25% แทน ~72%)

### P-7 เขียนโค้ด "เผื่อ" ที่พิสูจน์ไม่ได้ว่าทำงาน

เวอร์ชันแรกของ `buildLinePreviewJpeg` มีบันไดคุณภาพ 4 ขั้น — mutation พิสูจน์ว่า **ขั้นที่ 2–4
ไม่มีทางถูกเรียกเลย** (วัดจริง: ต้นทาง 14.3MB → ขั้นแรกได้ 124KB ต่ำกว่าเพดาน 8 เท่า) ตัดทิ้งแล้ว

## 2. Root causes

| # | สาเหตุร่วม |
|---|-----------|
| R-1 | **ไม่มีใครเป็นเจ้าของ "ประตูที่ปิดไว้ชั่วคราว"** — default-deny/flag/ข้อจำกัดชั่วคราว ถูกเขียนตอนของยังไม่พร้อม แล้วไม่มีกลไกไหนทวงคืนตอนของพร้อม (P-1) |
| R-2 | **การอ้าง ID ในเอกสารไม่เคยถูกตรวจว่ามีจริง** และเมื่อถูกคัดลอกต่อหลายไฟล์ ความถี่ถูกอ่านเป็นความน่าเชื่อถือ (P-2) |
| R-3 | **"เสร็จ" ถูกนิยามที่ชั้นที่ตัวเองแตะ** ไม่ใช่ที่เส้นทางของผู้ใช้ตั้งแต่ปุ่มถึงปลายทาง (P-3) |
| R-4 | **เครื่องมือทุกตัวตรวจ "รูปแบบ" ไม่มีตัวไหนตรวจ "ความสอดคล้อง"** — ทั้ง P-4 P-5 P-7 ผ่าน tsc/build/guard หมด |
| R-5 | **ประโยคในเอกสารภายนอกถูกอ่านโดยไม่แยกว่าเป็นข้อบังคับหรือคำอธิบาย** (P-6) — ทิศเดียวกับ `docs/conventions/domain-term-single-definition.md` ทิศกลับ |

## 3. Conventions to adopt

### C-1 ประตูที่ปิดชั่วคราวต้องผูกกับเงื่อนไขปลดล็อก ไม่ใช่ความทรงจำ

`ATTACHMENT_CHANNELS` แบบ default-deny ยังถูกต้อง — สิ่งที่ขาดคือ **ตัวทวง** เมื่อเงื่อนไขที่ทำให้ปิดหมดไป
เขียนคอมเมนต์ให้ระบุ *"ปลดเมื่อ S-8 เสร็จ"* ยังไม่พอ เพราะไม่มีใครอ่านคอมเมนต์ตอนปิดงาน S-8

**ทางที่ใช้ได้จริง:** เทสที่ผูก deny-list กับความสามารถจริงของ adapter — ถ้า adapter ส่งชนิดนั้นได้แล้ว
แต่ deny-list ยังปิดอยู่ ให้แดง (ยังไม่ได้ทำในรอบนี้ — ดู action items)

### C-2 🛑 ID ที่เอกสารอ้าง ต้อง `rg` หาในไฟล์ต้นทางก่อนเชื่อ — และอ่านเกณฑ์ "ทั้งชุด"

`rg -n "<ID>" "docs/20 - Features/<ฟีเจอร์นี้>/"` — ถ้าเจอในโฟลเดอร์ฟีเจอร์อื่นแปลว่าอ้างข้ามกันมา
และเมื่อเจอของจริงแล้ว **ต้องอ่านข้อที่อยู่ติดกันด้วย** เพราะข้อที่ถูกยกมามักมีคู่ที่ขอสิ่งตรงข้าม
และข้อที่ถูกข้ามจะไม่มีใครสังเกตเพราะไม่มีโค้ดให้พัง (บันทึกเพิ่มใน `feedback_docs_claimed_constraint_verify_in_code`)

### C-3 🛑 ก่อนบอกว่าฟีเจอร์เสร็จ ต้องตอบให้ได้ว่า **"ผู้ใช้กดตรงไหน"**

ไม่ใช่ "route รับ payload นี้ได้แล้ว" แต่คือ `rg -n "type: 'X'" src --glob '*.tsx'` แล้วเห็นปุ่มจริง
ถ้าไม่มี = งานยังไม่เสร็จ ไม่ว่า backend จะสมบูรณ์แค่ไหน

คู่กับกฎที่มีอยู่แล้ว (ตัวรับต้องมาก่อนตัวส่ง) — **ทั้งสองข้อคือกฎเดียวกัน: อย่าปล่อยให้ปลายด้านหนึ่ง
ของเส้นทางลอยอยู่คนเดียว**

### C-4 ตรึง "ความตั้งใจ" ไม่ใช่ "ค่าที่โค้ดใช้"

เทสที่เทียบผลลัพธ์กับค่าคงที่ที่โค้ดเดียวกันใช้ = tautology เสมอ ต้องมีอย่างน้อย 1 ข้อที่ตรึง
*คุณสมบัติ* ที่ตั้งใจไว้ (อัตราส่วน 1:1 · ไฟล์ต้องไม่มีแถบขาวที่มุม) แยกจากค่าคงที่

### C-5 ประโยคในเอกสารภายนอกที่ขึ้นต้นด้วยพฤติกรรมของระบบเขา ให้ถามว่า "บังคับ หรือ แค่บอกว่าเขาทำอะไร"

*"X scales or crops photos that are not 1.91:1"* = คำอธิบายพฤติกรรม ไม่ใช่ข้อกำหนดขาเข้า —
หาหลักฐานจากของจริงที่ระบบนั้นแสดงผลอยู่ (ภาพหน้าจอจากผู้ใช้จริงชนะเอกสารเสมอเมื่อขัดกัน)

## 4. What went right

- **HR17 ทำงานจริง** — `comm -12` หาไฟล์ที่ทั้งสองฝั่งแตะ ทำทุกครั้งก่อน push (7 ครั้งในวันเดียว) และครั้งที่ 7 คือครั้งที่จับ P-4 ได้
- **mutation testing จับของที่เทสเขียวปกปิดไว้ 3 ครั้ง** — บันไดคุณภาพที่ไม่มีวันถูกเรียก (P-7) · ownership guard ที่ถอดออกแล้วไม่มีอะไรแดง · เทสอัตราส่วนที่เป็น tautology (P-5)
- **แยกเวิร์กทรีตั้งแต่ต้น** — เวิร์กทรี `chats-line` มีงานค้างของอีก session ที่ compile ไม่ผ่าน ถ้าทำงานทับที่นั่นจะแยกไม่ออกว่า error ไหนของใคร
- **verify หลัง rebase เสมอ ไม่ใช่ก่อน** — จับ Prisma client ที่เก่ากว่า schema ได้ 3 ครั้ง (คนอื่นเพิ่มคอลัมน์ `productLike`/`productRefIds` ระหว่างทาง)
- **user ทดสอบบนเครื่องจริงทุกรอบและส่งภาพกลับมา** — ทั้ง P-3 และ P-6 ถูกจับด้วยภาพหน้าจอ ไม่ใช่ด้วยเครื่องมือ

## 6. หมายเหตุปิดท้าย

รอบนี้ **ทุกปัญหาที่มีค่าถูกจับด้วยคำถามหรือภาพหน้าจอของ user ไม่ใช่ด้วยเครื่องมือ**:

- *"chat line ส่งรูปไม่ได้"* → เจอประตูที่ปิดค้างมา 8 วัน
- *"countdown 59 วิ ได้ไหม"* → เจอ ID ที่อ้างผิดฟีเจอร์ในเอกสาร 3 ที่
- *"แล้วมันกดส่งสินค้ายังไงอ่ะ"* → เจอว่า backend ที่เพิ่ง push ไม่มีใครเรียก
