# Retro — กำไรรายออเดอร์ในหน้ารายการ + a11y audit

**ขอบเขต:** 6 คอมมิตที่ขึ้น prod ในรอบเดียวกัน
`b08be66c` (ชื่อสินค้า + กำไร) → `433b675b` (audit P1+P2) → `780322d8` (audit รอบกวาด)
→ `cc1870d5` (ถอด 2 สถานะ) → `ab74bd32` (ไอคอน+ตัวเลข + ป้าย HR16)
รวม `032d7913` (ตัวกรองวันที่เจาะจง) ที่อยู่ต้นรอบเดียวกัน

**บริบทที่สำคัญ:** รอบนี้เดินคู่ขนานกับอีกอย่างน้อย 3 session ที่ทำงานบน `main` พร้อมกัน
(00016 ต้นทุน · 00037 กล่องแชทรวม · 00039 ตัวชี้วัด · 00024 นัดหมาย) — main ขยับ **11 คอมมิต**
ระหว่างที่รอบนี้ทำงานอยู่ และมีคน push แทรกตอนกำลัง build

## 1. Problems

### P1 — บรรทัดที่เพิ่งเขียนเอง "ไม่ถูกอ่านออกมาเลยสักคำ" (a11y)

`OrderProfitInline` ใส่ `aria-label` บน `<p>` แล้ว `aria-hidden` ลูกทุกตัวกันอ่านซ้ำ
`role=paragraph` ไม่รองรับชื่อจากผู้เขียน → label ถูกทิ้ง → เนื้อในซ่อนหมด → **เงียบสนิท**

ที่เจ็บคือ **`MiniShipmentTimeline.tsx` ในโฟลเดอร์เดียวกันทำถูกอยู่แล้ว** ด้วย `role="img"`
ผมไม่ได้เปิดอ่านก่อนเขียน ทั้งที่ `sibling-surface-parity.md` เขียนกฎนี้ไว้ตรงตัวมาตั้งแต่ 08-03

### P2 — โมดัล 8 ใบขาด `aria-modal` มาตลอด และ audit รอบแรกกวาดไม่เจอ

รอบแรกผมรัน grep ไม่กี่ชุดแล้วสรุปว่า "เจอ 2 ข้อ" — พอ user สั่ง "P1+P2 ก่อนแล้วค่อย push"
จึงกลับไปไล่ใหม่ เจออีก 8 ใบทันที **ความต่างคือรอบสองไล่ตาม "รูปร่างโค้ด" (`role="dialog"`
ที่ไม่มี `aria-modal` ในทั้ง tag) ไม่ใช่ตามชื่อไฟล์หรือ grep บรรทัดเดียว**

### P3 — ออกแบบผิดทาง 3 รอบเพราะเดาแทนที่จะถาม

บรรทัดกำไรถูกรื้อ 3 รอบในวันเดียว:

| รอบ | ทำอะไร | user ว่าไง |
|---|---|---|
| 1 | คำเต็ม 6 สถานะ ("กำไรขั้นต้นไม่เกิน ฿360") | "ทำไมถึงมีคำว่า…" |
| 2 | ถอด 2 สถานะที่ hedge ออก | "เอาออกก่อน สร้างความสับสน" (ผมยังแนะนำให้คงคำว่า "ไม่เกิน" ไว้ — user override) |
| 3 | ไอคอน + ตัวเลขล้วน | ✅ |

ux spec รอบแรกออกแบบมาดีในเชิงความถูกต้อง (แยก 6 สถานะ บอกความไม่แน่นอนครบ) แต่
**ไม่มีใครถามว่าผู้ขายที่กำลังกวาดตาดูรายการ 50 ใบต้องการอ่านประโยคต่อแถวไหม**

### P4 — ตอบคำถาม user ไม่ครบจนเขาเคาะบนข้อมูลไม่ครบ

ตอนถามว่าใบที่ต้นทุนไม่ครบควรทำยังไง ผมบอกว่า "ตัวเลขสูงกว่าความจริง" — **เรื่องขนาด**
แต่ความจริงคือ **ทิศทางก็ผิดได้** (ใบที่คำนวณได้บวกอาจพลิกเป็นขาดทุนเมื่อกรอกต้นทุนครบ)
user เคาะ "โชว์เลขเหมือนกันหมด" บนข้อมูลชุดที่ขาดไป — ต้องไปบอกทีหลัง

### P5 — `tsc` แดง 2 รอบด้วยเหตุเดียวกัน และแทบไม่ได้เอะใจ

หลัง rebase ทั้งสองครั้ง `tsc` แดงเพราะ Prisma client ในเวิร์กทรีเก่ากว่า schema ที่
session อื่นเพิ่ง push (`viaStandby`, `deliveredAt`, `ShopNotificationPref`, `PushToken.platform`)
แก้ด้วย `prisma generate` ซึ่งไม่แตะฐานข้อมูล — **ถ้าไม่ verify หลัง rebase จะไม่มีทางเห็น**

### P6 — rebase ชนกลางไฟล์ที่อีก session เพิ่ง redesign

`OrderProfitCard.tsx` ถูก `fc9d4e60` เขียนใหม่ (เข้าโครง Paces + badge "ต้นทุนไม่ครบ"
ที่กดไป `/products?cost=missing` ได้) **พร้อมกับที่ผมกำลังสกัด `present()` ออกจากไฟล์นั้น**
เขาแก้ **คำใน `note`** ไปด้วย ถ้า resolve แบบเอาของเราล้วน คำของเขาจะถูกย้อนกลับเงียบ ๆ

## 2. Root causes

| # | สาเหตุที่แท้จริง |
|---|---|
| P1 | เขียนโค้ดใหม่โดยไม่เปิดอ่านไฟล์พี่น้องที่แก้ปัญหาเดียวกันไว้แล้ว — และ **ไม่มี gate ไหนตรวจ "ความหมาย" ของ ARIA ได้** markup ถูกทุกตัวอักษร มันแค่ไม่ทำงาน |
| P2 | audit รอบแรกไล่จาก **ชื่อ/บรรทัด** ไม่ใช่ **รูปร่างโค้ด** · และผมประกาศว่า "เจอ 2 ข้อ" ทั้งที่ยังไม่ได้ไล่ให้ครบ (`enumerate-by-code-shape` — บทเรียนที่มีอยู่แล้วในรีโป) |
| P3 | ux spec ตอบคำถาม "แสดงยังไงให้ถูกต้อง" แต่โจทย์จริงคือ "แสดงยังไงให้กวาดตาได้" — **Mode: Operate บอกอยู่แล้วว่า scanability ชนะความครบถ้วน** แต่ spec เขียนความครบถ้วนไว้ก่อน |
| P4 | สรุปความเสี่ยงให้ user เป็น "ตัวเลขเพี้ยน" ก้อนเดียว ทั้งที่มันมี 2 มิติ (ขนาด/ทิศทาง) ที่คนละความรุนแรง |
| P5 | เวิร์กทรีนี้ share รีโปกับ session อื่นที่แก้ schema — Prisma client เป็น artifact ที่ไม่ได้อยู่ใน git จึงไม่ถูก rebase ตามมาให้ |
| P6 | ไฟล์ที่ทั้งสองฝั่งแตะ = จุดที่ git บอกไม่ได้ว่าปลอดภัยไหม (นี่คือ Hard Rule 17 ที่ main promote ขึ้นในวันเดียวกัน) |

## 3. Conventions to adopt

### ใหม่: `docs/conventions/aria-name-requires-supporting-role.md`

`aria-label` ใช้ได้เฉพาะ role ที่รองรับชื่อจากผู้เขียน · `<p>`/`<div>`/`<span>` เปล่าไม่รองรับ ·
แพตเทิร์น "label ที่พ่อ + `aria-hidden` ลูก" ทำให้เงียบสนิทถ้าไม่ประกาศ role · `title` ไม่ใช่
ตัวแทน (มือถือไม่มี hover) · `role="dialog"` ต้องมี `aria-modal` **ยกเว้น** popover ที่หน้าหลัง
ยังกดได้ · สคริปต์สแกน regex เชื่อผลดิบไม่ได้ ต้องเปิดไฟล์ยืนยัน

### ขยายของเดิม 2 ข้อ

- **`sibling-surface-parity.md`** — เพิ่มว่ากฎนี้ครอบ **แพตเทิร์น a11y** ด้วย ไม่ใช่แค่ตัวกรอง/แท็บ/empty state
- **HR16 (นิยามศัพท์ธุรกิจ)** — เมื่อ **ตัดคำอธิบายออกจากจอ** ตัวที่เคยแบกนิยามไว้จะหายไปด้วย
  ต้องหาที่ใหม่ให้ **ในคอมมิตเดียวกัน** (รอบนี้ = หัวคอลัมน์ + แคปชั่นเหนือการ์ด ครั้งเดียวต่อหน้า)

### กติกาการถาม user

**แยกความเสี่ยงเป็นมิติ ๆ ก่อนถาม** — "ตัวเลขเพี้ยน" ไม่ใช่คำตอบเดียว มันมี
*ขนาดเพี้ยน* (ยอมรับได้ง่าย) กับ *ทิศทางเพี้ยน* (สีเขียวทั้งที่ขาดทุน — คนละเรื่อง)
ถ้าไม่แยกให้ user เห็น เขาจะเคาะบนข้อมูลไม่ครบแล้วเราต้องกลับไปแก้ทีหลัง

## 4. What went right

1. **user เป็นคนจับบั๊กที่ static ทุกชั้นมองไม่เห็น** — "ทำไมถึงมีคำว่า…" คือสัญญาณว่า
   design ผิด ไม่ใช่คำถามเพื่อความเข้าใจ (ตรงกับ `feedback_user_does_visual_qa`)
2. **สกัด `present()` เป็น SSOT ก่อนที่จะมีสอง surface** — พอ `fc9d4e60` เปลี่ยนคำในการ์ด
   หน้า detail ผม diff ค่าที่ออกจอทุกตัวแล้วยกเข้า SSOT ได้ครบ ไม่มีคำไหนถูกย้อนกลับเงียบ ๆ
3. **ux gate จับกับดักที่จะพลาดแน่ ๆ** — `presentOrderProfit()` คืน `tone: 'danger'` ให้ทั้ง
   "ขาดทุนอย่างน้อย" (ต้องซ่อน) และ "ขาดทุนจากใบนี้" (ต้องโชว์) แยกจาก tone ไม่ได้
   ต้องอ่าน `hasMissingCost` ดิบ — ux ชี้จุดนี้ก่อนเขียนโค้ด
4. **สิทธิ์ถูกกั้นที่ server ก่อนคำนวณ และ omit คีย์ทิ้ง** ไม่ใช่ให้ component เลือกไม่ render
   (หัวไฟล์ `order-profit.ts` เตือนเรื่องนี้ไว้เอง — รอบนี้อ่านก่อนเขียน)
5. **ตรวจ false positive ก่อนรายงาน** — สคริปต์สแกนบอกว่ามี `<img>` ไม่มี `alt` 2 จุดและ
   `<input>` ไม่มีชื่อ 2 จุด เปิดดูแล้วเป็น false positive ทั้งหมด ไม่ได้แก้มั่ว
6. **verify หลัง rebase ทุกครั้ง แยกคำสั่งจาก push** — จับได้ 3 อย่างคนละชนิด: Prisma client
   เก่า 2 รอบ · มีคน push แทรกตอน build เสร็จ · ไฟล์ที่ทั้งสองฝั่งแตะ
