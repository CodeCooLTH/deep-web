## 1. Problems

### P1 — ฟีเจอร์ที่เพิ่ง ship ไม่ทำงานในเคสที่สำคัญที่สุด และ user เป็นคนจับได้

`6fdd85fd` ทำให้ป้าย "ไม่สำเร็จ" บอกเหตุผลได้ — ผมรายงานว่าเสร็จ แล้ว user ถามกลับมาสั้น ๆ ว่า
*"มันต้องเก็บเหตุผลแยกกันป่าว"* แล้วต่อด้วย *"เพราะ reply ไม่ผ่าน อาจจะทักแชทได้ก็ได้"*

ตรวจแล้วถูกต้อง: `errorMessage` เป็นคอลัมน์เดียวที่ทั้งสองฝั่งใช้ร่วมกัน และ
`comment-private-reply.service.ts:275` เขียน `errorMessage: null` ตอนทักแชทสำเร็จ ⇒ **เคสที่ user
ยกมาพอดี (ตอบใต้คอมเมนต์ไม่ผ่าน แต่ทักแชทได้) เหตุผลฝั่งสาธารณะถูกล้างทิ้งทุกครั้ง** ป้ายจะขึ้น
"ไม่สำเร็จ" เปล่า ๆ เหมือนเดิมเป๊ะ — ฟีเจอร์ที่เพิ่ง ship ไม่ช่วยอะไรเลยในเคสนั้น

**ผมเห็นข้อจำกัดนี้แล้วด้วยซ้ำ** — เขียนไว้เองท้ายรายงานว่า "ถ้า public ล้มแต่ private สำเร็จ
errorMessage จะถูกเขียน null ทับ… ยังไม่แตะเพราะเป็นการเปลี่ยนพฤติกรรมฝั่งเขียนซึ่งควรแยกรอบ"
แต่จัดมันเป็น *ข้อจำกัดที่ยอมรับได้* ทั้งที่มันคือ **เคสที่ทำให้ฟีเจอร์นั้นไร้ผล**

🛑 **บทเรียน: "ข้อจำกัดที่รู้ตัว" ต้องถูกทดสอบว่ามันกินเคสไหนของฟีเจอร์ที่เพิ่งทำ ไม่ใช่บันทึกแล้วผ่าน**
ถ้าข้อจำกัดนั้นทำให้ฟีเจอร์ไม่ทำงานในเคสที่พบบ่อย มันไม่ใช่หนี้ มันคือฟีเจอร์ที่ยังไม่เสร็จ
เกณฑ์ที่ใช้ได้จริง: *ไล่เคสของฟีเจอร์ที่เพิ่งทำทีละเคส แล้วถามว่าข้อจำกัดนี้กินเคสไหนไปบ้าง*

### P2 — SSOT ที่สร้างไว้กันบั๊กคลาสหนึ่ง ไม่มี production code เรียกเลยสักที่

`countUnansweredComments()` ใน `src/lib/comment-tree-visibility.ts` ถูกสร้างเมื่อ 08-09 เพื่อให้
"เลขแถวซ้าย" กับ "ชิปในเธรด" ใช้กติกาเดียวกัน — ตรวจรอบนี้พบว่า **ไม่มีใครเรียกเลย** มีแต่เทสของ
ตัวเอง ชิปในเธรดยังนับด้วยสูตร inline ของตัวเองที่ `CommentsClient.tsx`

นี่คือ **P5 ของ retro เมื่อวานซ้ำเป๊ะ** ("SSOT ที่มีผู้บริโภคศูนย์ราย") — และมันเกิดซ้ำใน
**รอบเดียวกับที่เขียนบทเรียนนั้นลงไปเอง** เพราะบทเรียนถูกเขียนไว้ในเอกสาร ไม่ได้ถูกแปลงเป็นด่าน

### P3 — เทสที่ผูกกับรูปร่างสตริง แตกเพราะการเรียงใหม่ที่ไม่ได้เปลี่ยนกฎอะไรเลย

`comment-unanswered-count.test.ts` ตัด substring ด้วย `sql.indexOf('WHEN NOT EXISTS (')` —
พอย้าย `UNANSWERED` จาก branch แรกไปเป็น `ELSE` (ซึ่งทำให้ CASE อ่านง่ายขึ้นและกฎเหมือนเดิมทุกข้อ)
เทสแดงทันที ทั้งที่สิ่งที่มันตั้งใจปกป้องไม่ได้เปลี่ยนเลย

**นี่คือ P11 ของ retro เมื่อวานซ้ำอีกตัว** (เทสผูกกับตำแหน่ง) เขียนใหม่ให้แยก CASE เป็นคู่
`{predicate, result}` แล้ว assert เชิงกฎแทน

ระหว่างแก้ยังพลาดซ้อนอีกชั้น: assert แรกกวาดทั้ง SQL ซึ่งมี CASE **สองชั้น** (ระดับคอมเมนต์ +
ระดับโพสต์) แล้วไปจับ `THEN 'UNANSWERED'` ของชั้นโพสต์ที่ถูกต้องอยู่แล้ว → ต้อง scope ด้วย
`commentCaseSql()` ก่อน

### P4 — เกือบสร้างของใหม่ที่ user ไม่ได้อยากได้ เพราะ ux ตอบตามโจทย์ที่ผมตั้ง

รอบ "สถานะที่ 4" ผมส่ง ux ไปออกแบบ `IN_CHAT` เป็นสถานะใหม่ + แท็บที่ 5 — ux ทำมาครบถ้วนดีมาก
แล้ว user ทักกลางทางว่า *"tab ด้านบน ให้มีแค่ 2 tab พอ"* + *"ก็พอไม่ต้องเพิ่มมมเยอะ"*

ทางที่ถูกกลายเป็น **ไม่ต้องเพิ่มอะไรเลย** — ให้ "ทักแชทไปแล้ว" ตกเข้าสถานะที่มีอยู่แล้วตามว่าใคร
เป็นคนทัก (บอททัก → BOT_ANSWERED · คนกดทัก → HUMAN_ANSWERED) ซึ่งตรงกับความหมายเดิมของสองค่านั้น
พอดี ไม่ต้องมี enum ใหม่ ไม่ต้องมีป้ายใหม่ ไม่ต้องมี migration

**บทเรียน:** ก่อนส่ง ux ต้องถามตัวเองก่อนว่า *"แก้ด้วยของที่มีอยู่แล้วได้ไหม"* — ถ้าไม่ถาม
ผู้เชี่ยวชาญจะออกแบบของใหม่ให้อย่างดีตามที่เราสั่ง แล้วเราจะได้ของที่ดีแต่ไม่จำเป็น

### P5 — เดา layout ที่ user ต้องการ แล้วต้องรื้อทำใหม่ทั้งบล็อก

`15e70120` ทำการ์ด 2 โซนในสตรีมข้อความ (ผ่าน ux gate เรียบร้อย) — user ตอบกลับว่า
*"ไม่ครับ ต้อง merge เป็นด้านบนที่เดียว"* + *"มันกินพื้นที่เวลาอยู่บน mobile"* ต้องถอดออก 92 บรรทัด
แล้วเขียนใหม่เป็นแถวเดียวติดหัวแชท (`3f73b8a1`)

ต้นเหตุ: user เขียนว่า *"เหมือน ads"* ตั้งแต่แรก ซึ่งหมายถึง **ตำแหน่ง** (แถวติดหัวแชท) ไม่ใช่แค่
**หน้าตา** — ผมตีเป็นอย่างหลังแล้วส่ง ux ไปด้วยการตีความนั้น

รอบแก้ผมใช้ `AskUserQuestion` พร้อม ASCII preview 3 แบบ user เลือกได้ในคลิกเดียวและตรงเป้าทันที
**ควรใช้ตั้งแต่รอบแรก** — คำว่า "เหมือน X" มีความหมายได้ทั้งตำแหน่ง/หน้าตา/พฤติกรรม

### P6 — สคริปต์ Python ตัดบล็อก JSX ผิดตำแหน่งเพราะนับวงเล็บไม่เป็น

ตอนถอดการ์ดเดิม เขียนสคริปต์หา `)}` ตัวแรกหลังบรรทัดเปิด — ไปเจอ `)}` ของ ternary **ที่ซ้อนอยู่ข้างใน**
แล้วตัดบล็อกขาดครึ่ง (ถอดไป 47 บรรทัดจากที่ควรเป็น 92) จับได้เพราะพิมพ์บริบทรอบจุดตัดออกมาดูก่อน
กู้ด้วย `git checkout --` แล้วหาขอบเขตจริงด้วยการอ่านไฟล์

**ไม่มีอะไรเสียหาย** เพราะไฟล์ commit ไปแล้วและตรวจก่อนรันต่อ — แต่ถ้าเผลอ commit ทับคือของพัง

## 2. Root causes

1. **บทเรียนถูกเขียนเป็นเอกสาร ไม่ถูกแปลงเป็นด่าน** — P2/P3 คือบทเรียนของ retro เมื่อวานที่ซ้ำใน
   วันถัดมาทันที เอกสารกันได้เฉพาะคนที่บังเอิญเปิดอ่านตอนกำลังทำเรื่องนั้นพอดี
2. **"หนี้ที่รู้ตัว" ไม่มีเกณฑ์ตัดสินว่าอันไหนเป็นหนี้จริง อันไหนคือฟีเจอร์ที่ยังไม่เสร็จ** (P1)
3. **ตีความคำสั่งสั้น ๆ ของ user ด้วยการเดา แทนที่จะให้เลือกจากภาพ** (P4/P5) — ทั้งสองรอบเสียเวลา
   ไปกับการสร้างของที่ต้องรื้อ ทั้งที่ต้นทุนการถามคือหนึ่งคลิก

## 3. Conventions to adopt

- 🛑 **"ข้อจำกัดที่รู้ตัว" ต้องไล่เทียบกับเคสของฟีเจอร์ที่เพิ่งทำก่อนบันทึกเป็นหนี้** — ถ้ามันกินเคส
  ที่พบบ่อย นั่นคือฟีเจอร์ที่ยังไม่เสร็จ ไม่ใช่หนี้ · ห้ามใช้เหตุผล "ควรแยกรอบ" กับข้อจำกัดที่ทำให้
  ของที่เพิ่ง ship ไม่ทำงาน → `docs/conventions/known-limitation-vs-unfinished.md`
- 🛑 **สร้าง SSOT แล้วต้องต่อสายผู้เรียกให้ครบในคอมมิตเดียวกัน และเทสต้อง assert ว่ามีผู้เรียกจริง**
  — ไฟล์ที่มีแต่เทสของตัวเองคือ dead code ที่หน้าตาเหมือนด่าน (ซ้ำ 2 วันติด)
- 🛑 **เทสที่ตรวจ SQL/โครงสร้าง ต้อง parse เป็นโครงแล้ว assert เชิงกฎ ห้าม `indexOf` สตริง** และต้อง
  scope ให้ตรงชั้นก่อนเสมอเมื่อโครงมีหลายชั้น (CASE ซ้อน CASE)
- 🛑 **คำว่า "เหมือน X" ของ user กำกวมเสมอ** (ตำแหน่ง/หน้าตา/พฤติกรรม) — ใช้ `AskUserQuestion`
  พร้อม ASCII preview ให้เลือก **ก่อน**ลงมือ ไม่ใช่หลังโดนตีกลับ ต้นทุนหนึ่งคลิก แลกกับการรื้อทั้งบล็อก
- 🛑 **ห้ามใช้สคริปต์หาขอบเขตบล็อก JSX ด้วยการ match วงเล็บปิดตัวแรก** — ต้องอ่านไฟล์ยืนยันเลขบรรทัด
  จริงก่อนตัด และพิมพ์บริบทรอบจุดตัดออกมาดูเสมอ
- 🛑 **ก่อนส่ง `safepay-ux` ต้องตอบตัวเองก่อนว่า "แก้ด้วยของที่มีอยู่แล้วได้ไหม"** — ux ออกแบบตาม
  โจทย์ที่เราตั้ง ถ้าโจทย์คือ "เพิ่มสถานะใหม่" จะได้สถานะใหม่ที่ดีมาก ทั้งที่คำตอบคือไม่ต้องเพิ่ม

## 4. What went right

- **user ถามคำถามเดียวแล้วพลิกทั้งการออกแบบ** — "มันต้องเก็บเหตุผลแยกกันป่าว" ทำให้เจอว่าฟีเจอร์ที่
  เพิ่ง ship ไม่ทำงานในเคสหลัก · การตอบว่า "ใช่ และนี่คือหลักฐานว่ามันสำคัญกว่าที่ผมประเมิน"
  ดีกว่าการปกป้องงานที่เพิ่งทำ
- **mutation test ทุก `[blocker]`** — 6 ตัวรอบนี้ ทำครบทุกตัว และ 2 ตัวจับได้จริงตอนทดลองย้อนโค้ด
  (ถอด branch `CommentReplyLog` ออกจาก SQL · คืน `errorMessage: null` แบบเดิม)
- **backfill แยกฝั่งจาก "ลำดับการเขียนที่โค้ดเดิมรับประกันไว้" ไม่ใช่การเดา** — private เขียนทีหลัง
  เสมอ ⇒ private FAILED = ค่าที่เหลือเป็นของ private แน่นอน · เคสที่ถูกล้างไปแล้วไม่เดาแทน ปล่อย NULL
- **HR17 ทำครบทุกรอบ** — rebase 8 ครั้งใน 2 วัน มี 1 ครั้งที่อีกฝั่งแตะ `schema.prisma` เหมือนกัน
  เปิด diff อ่านก่อนแล้วยืนยันว่าคนละโมเดล (`OrderShipment` vs `CommentReplyLog`) · build ใหม่หลัง
  rebase ทุกครั้ง · เจอ Prisma client เก่าในเวิร์กทรี 3 รอบ แก้ด้วย `prisma generate` ตามที่ HR17 เขียนไว้
- **เทียบเลขเทสแดงกับ baseline ทุกครั้ง** — 18 แดงชุดเดิม 6 ไฟล์เดิม และตรวจเหตุผลของไฟล์ที่
  เกี่ยวกับโค้ดที่แตะทุกครั้งว่ายังเป็นเหตุเดิม (`server-only` boundary / mock ไม่ครบ)
- **ตอบ user ว่า "ยังไม่ใช่รุ่นล่าสุด" ด้วยหลักฐาน ไม่ใช่ความรู้สึก** — ชี้ 3 จุดในภาพที่ถอดออกไปแล้ว
  (label/เส้นคั่น/วันที่) แล้ว grep `origin/main` ยืนยันว่าคำเหล่านั้นเหลือ 0 จุดในไฟล์
