## เกิดอะไรขึ้น

เช้าวันเดียวกันเพิ่ง "แก้" ปัญหาเธรดที่ Meta AI ตอบแล้วไม่เข้าระบบ ด้วยการ subscribe
`messaging_handovers` ครบทั้งสองชั้น — **ตอนเย็น user รายงานว่ายังไม่เข้าอยู่ดี** พร้อมเธรดตัวอย่าง

ตรวจซ้ำแล้วทั้งสองชั้นครบจริง (อ่านสดจาก Graph ไม่ได้เดา) แปลว่า **สมมติฐานเดิมผิดเอง ไม่ใช่ทำไม่ครบ**

ตัวที่ขาดจริงคือ **`standby`** ซึ่งเป็นคนละ field และไม่เคยมีบน `page` topic เลยตั้งแต่วันแรก

| field | หน้าที่จริง |
|---|---|
| `messaging_handovers` | บอกว่า**สิทธิ์คุมห้องเปลี่ยนมือ** — ไม่ได้ขนข้อความมาด้วยเลย |
| **`standby`** | **ขนข้อความของห้องที่เราไม่ใช่เจ้าของเธรด** |

## บทเรียนที่ 1 — 🛑 "ครบทั้งสองชั้นแล้ว" ตอบแค่คำถามว่า *ครบไหม* ไม่ได้ตอบว่า *ถูกตัวไหม*

เอกสารที่เขียนเมื่อเช้าออกแบบเช็คลิสต์ไว้ดี (ตรวจชั้นแอป + ชั้นเพจ) แต่**เช็คลิสต์นั้นตรวจได้เฉพาะ
field ที่เรารู้จักแล้วว่าต้องมี** — มันไม่มีทางบอกได้เลยว่ายังมี field ที่เราไม่เคยรู้ว่ามีอยู่

สิ่งที่จะจับได้คือคำถาม *"ถ้าแก้ถูกแล้ว ทำไมอาการยังเหมือนเดิมทุกประการ"* ซึ่งต้องกลับไปตั้งต้นใหม่
ทั้งกระดาน ไม่ใช่ไล่ตรวจว่าทำตามเช็คลิสต์ครบหรือยัง

**ทำอะไรต่อ:** เพิ่มหัวข้อ "เพิ่ม field ถูกชั้นแล้ว แต่**ผิดตัว**" ใน
`docs/conventions/webhook-subscription-two-layers.md` แล้ว

## บทเรียนที่ 2 — 🛑 ตารางของเครื่องมือไม่ใช่ความจริง และผมเอามาสรุปแทนเอกสาร

ผมตอบ user ไปว่า **"ไม่มี field เหลือให้เพิ่มแล้ว"** โดยอ้าง `devtools_webhook_list action=list_topics`
ของ Meta DevTools MCP ซึ่งไม่ลิสต์ `standby` ใน topic `page` (ลิสต์ให้เฉพาะ `instagram` กับ
`whatsapp_business_account`)

**คำตอบนั้นผิด** เอกสาร Messenger เขียนตรงตัวว่า subscribe ได้:

> "…the events will be delivered to standby channel. **You can subscribe to this callback by
> selecting the `standby` field** when setting up your webhook."

และ MCP ไม่ได้แค่ลิสต์ไม่ครบ — มัน **ปฏิเสธคำสั่งเพิ่ม** ด้วย (`Fields not available for topic
"page": standby`) ถ้าเชื่อตรงนั้นคือปิดประตูตัวเองสนิท ทางที่ใช้ได้คือยิง
`POST /{app-id}/subscriptions` ผ่าน Graph ตรงด้วย app token

**นี่คือคลาสเดียวกับ HR16 ทิศกลับ** ("ข้อจำกัดที่เอกสารอ้าง ต้องเช็คกับโค้ด") แต่ย้ายมาอยู่ที่
*เครื่องมือ* แทน *เอกสาร*: คำว่า "ไม่มี/ทำไม่ได้" ที่ออกจากปาก tool คือการอ้างข้อเท็จจริง
ซึ่งต้องพิสูจน์ก่อนใช้เป็นเหตุผลที่จะ **ไม่ทำ** อะไร — และข้อจำกัดปลอมชนิดนี้ไม่มีทางถูกเทสจับ
เพราะมันทำให้เราไม่เขียนโค้ดเลย

**สิ่งที่ทำให้รอด: user ส่งลิงก์เอกสาร Meta Business Agent มาให้** ซึ่งเป็นเอกสารฝั่ง WhatsApp
(ผิดแพลตฟอร์ม) แต่เขียนโครงว่าต้อง subscribe `messages` + **`standby`** + `messaging_handovers`
— คำว่า `standby` ในนั้นคือเบาะแสที่พาไปหาหน้า Messenger ตัวจริง **ลิงก์ที่ "ผิด" กลับเป็นตัวปลดล็อก
ทั้งเรื่อง** เพราะมันชนกับข้อสรุปของผมตรง ๆ

## บทเรียนที่ 3 — คอลัมน์ `rawMessage.source` คือเครื่องมือที่ทำให้วินิจฉัยได้ใน 10 นาที

`ChatMessage.rawMessage->>'source'` (`webhook` / `graph-backfill` / `outbound-response`) ถูกใส่ไว้
ตั้งแต่ 2026-08-03 ด้วยเหตุผลอื่น แต่รอบนี้มันคือทั้งหมดของการวินิจฉัย:

```
13:26:05.367  BUYER  webhook         "Hello"              <- มี ms = ของสด
12:55:38      BUYER  graph-backfill  "สวัสดีครับ"          <- ปัดเป็นวินาที = เราไปดึงเอง
```

**หลักฐานชี้ขาดคือเธรด `b6064da8`** ที่เส้นแบ่งอยู่ที่ "ใครถือห้อง" ไม่ใช่ "payload หน้าตายังไง":

```
11:36:48  graph-backfill  Your AI agent will respond.
11:39:06  graph-backfill  You took over this chat from your AI agent.
11:39:11.478  webhook     <- กลับมาทันที เพจเดิม เธรดเดิม ลายเซ็นเดิม schema เดิม
```

บั๊กฝั่งเรา (ลายเซ็นตก / Valibot ตี event ตก) **ไม่มีทางเลือกพังตามแกนนี้ได้** — ตัวแปรเดียวที่
เปลี่ยนคือใครถือห้อง

**หลักทั่วไป:** ค่าที่เก็บว่า "ข้อมูลแถวนี้มาทางไหน" ราคาถูกมากตอนเขียน แต่เป็นสิ่งเดียวที่แยก
"ระบบภายนอกไม่ส่ง" ออกจาก "เรารับแล้วทำหาย" ได้ — สองอย่างนี้หน้าตาเหมือนกันเป๊ะในฐานข้อมูล

## บทเรียนที่ 4 — user ถามคำถามที่ถูกกว่าข้อสรุปของผม

ผมสรุปไปว่า "Meta ไม่ส่งมาให้เรา" แล้ว user ถามกลับสั้น ๆ ว่า **"หรือเราไม่ได้รับผ่าน webhook ครับ"**

นั่นคือการชี้ว่าผม**อนุมาน** ไม่ได้**พิสูจน์** — ผมแยกไม่ได้จริง ๆ ระหว่าง "Meta ไม่ส่ง" กับ
"ส่งแล้วเราทิ้ง" เพราะดึง Vercel runtime log ย้อนหลังไม่ได้ (ลอง 4 endpoint 404 หมด — plan นี้ไม่เปิด
API ให้ query)

ผลดีคือมันบังคับให้แยกสองอย่างนี้ออกจากกันแล้วตอบตามที่พิสูจน์ได้จริง แทนที่จะเดินหน้าทำ poller
บนข้อสรุปที่ยังไม่แน่น (ซึ่งเป็นสิ่งที่ผมเสนอไปแล้วในรอบก่อนหน้า และ**ไม่ต้องทำเลยในที่สุด**)

**ทำอะไรต่อ:** เพราะ log ย้อนหลังอ่านไม่ได้ จึงเก็บ event ลงฐานแทน (`ChatHandoverEvent`) —
`console.log` ที่อ่านย้อนหลังไม่ได้มีค่าเท่ากับไม่มี

## บทเรียนที่ 5 — ตารางที่ "ว่างเปล่า" คือผลการทดลองที่มีค่า

สร้าง `ChatHandoverEvent` เพื่อจับ **app id ของ Meta AI** (ไม่มีในเอกสารสาธารณะ) ที่จำเป็นต่อปุ่ม
"เปิด AI กลับ" — deploy แล้วให้ user กด Respond yourself / Turn on AI responses ใน Business Suite

**ผลคือ 0 แถว** ⇒ Meta ไม่ยิง `messaging_handovers` สำหรับการสลับกับ AI ของตัวเองเลย

ผลลบนี้ **ประหยัดงานทั้งก้อน**: มันปิดแผน "ปุ่มเปิด AI กลับ" ตั้งแต่ก่อนลงมือทำ UI แทนที่จะไปพัง
ตอนต่อสายจริง — และการยืนยันด้วย `take/release/pass_thread_control` อีก 3 ครั้งก็ได้เหตุผลครบว่า
ทำไมถึงทำไม่ได้ (Conversation Routing ไม่ได้เปิด + แอปเราไม่เคยเป็นเจ้าของเธรด เจ้าของคือ Page Inbox)

**หลักทั่วไป:** เมื่อฟีเจอร์พึ่งข้อมูลจากระบบภายนอกที่ยังไม่เคยเห็นของจริง ให้ลงชั้นเก็บหลักฐาน
ก่อนเสมอ (เล็ก ไม่มี UI) แล้วค่อยออกแบบ — ไม่ใช่ออกแบบตามที่เอกสารบอกว่าควรจะมี

## บทเรียนที่ 6 — ผมอธิบายจนหัวหน้าอ่านแล้วสรุปผิดว่า "ทำอะไรไม่ได้"

หลังได้ผลเทส ผมรายงานเป็นตาราง error 3 บรรทัด + ทางเลือก A/B + คำถามปลายเปิด user ตอบกลับว่า:

> "ไม่เข้าใจ สรุปคือเราทำอะไรไม่ได้"

**ทั้งที่ความจริงคือติดแค่ 1 ใน 6 ข้อ** — อีก 5 ข้อทำได้หมด และข้อที่สำคัญที่สุด (ข้อความเข้า
real-time) เสร็จไปแล้ว

ต้นเหตุ: ผมเรียงจาก *กลไกที่ค้นพบ* ไม่ใช่ *สิ่งที่ผู้อ่านต้องตัดสินใจ* — พอเปิดหัวด้วยข้อความ error
ของ Graph 3 บรรทัด ผู้อ่านก็อ่านทั้งย่อหน้าเป็น "ล้มเหลว"

พอเปลี่ยนเป็นตารางเช็คลิสต์ ✅/❌ ต่อสิ่งที่ **user ขอมาเอง** แล้วบอกว่าติดข้อไหนข้อเดียว user ตอบ
กลับทันทีว่า "เอาเลยครับ ลุย 4 ข้อนั้น"

**หลักทั่วไป:** รายงานผลการสืบสวนให้เรียงตาม **สิ่งที่ผู้ใช้ขอ** ไม่ใช่ตามลำดับที่เราค้นพบ และ
ข้อจำกัดทางเทคนิคต้องมาหลังคำตอบว่า "ได้/ไม่ได้" เสมอ

## บทเรียนที่ 7 — ux เดาสตริงผิด แต่กระบวนการจับได้

Design Spec ระบุคำแปลของข้อความระบบตัวที่ 4 ว่า *"เพราะลูกค้าขอคุยกับคน"* พร้อมกำกับเองว่าเป็น
สมมติฐานที่ต้องยืนยันกับฐานก่อนขึ้น prod

query จริงได้: `Your AI agent transferred this chat to you because your customer is **ready to buy**.`
— **ลูกค้าพร้อมซื้อ** ไม่ใช่ขอคุยกับคน คนละความหมายกันคนละเรื่อง (ถ้าหลุดไป ผู้ขายจะอ่านสัญญาณ
การขายที่สำคัญที่สุดกลับด้าน)

ที่รอดเพราะ ux เขียน Open Question กำกับไว้เอง แทนที่จะกลืนสมมติฐานลงไปในสเปกเงียบ ๆ

**ทำอะไรต่อ:** เทส `parseMetaAiHandoffNotice` ใช้สตริงที่ copy จากฐาน prod ตรงตัว + คอมเมนต์กำกับว่า
ห้ามแต่งค่าเอง (เทสที่แต่งค่าตามข้อสันนิษฐานของโค้ด ยืนยันได้แค่ว่า "โค้ดทำตามที่คนเขียนคิด") ·
พิสูจน์ด้วย mutation แล้วว่าจับ regression ได้จริง

## หนี้ที่เหลือ

- **ยังไม่ยืนยันว่าส่งข้อความผ่านไหมตอน AI ถือห้อง** — ถ้าไม่ผ่าน ต้องเพิ่ม rule ใน
  `src/lib/chat-send-failure.ts` เมื่อรู้ error code จริง (ห้ามเขียนคำแปลเดาล่วงหน้า)
- browser QA ทั้งชุด (user ตรวจเอง)
- ไม่มีป้ายบนบับเบิลว่า "Meta AI ตอบ" — ถ้าทำต้องเลือกไอคอนที่ไม่ชนกับ `robot` (DeepBot) และ
  `sparkles` (DeepAI)
- **ทาง B ที่ยังไม่แตะ:** เปิด Conversation Routing บนเพจจะปลดล็อก take/pass/release ครบ แต่เปลี่ยน
  พฤติกรรม routing ของทั้งเพจที่ร้านใช้ขายจริง
- `ChatThread.tsx` ไม่ prettier-clean อยู่ก่อนแล้ว — บล็อกที่ถูกห่อด้วย fragment รอบนี้จึงย่อหน้า
  ไม่ตรง (format ทั้งไฟล์จะได้ diff ปนหลายร้อยบรรทัดจนรีวิวไม่ได้)
