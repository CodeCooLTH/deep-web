## 1. Problems

### P-1 🛑 เดาค่าจาก "จำนวน" ทั้งที่สองอย่างมีจำนวนเท่ากันแต่ความหมายต่าง

รอบแรกเลย์เอาต์ถูก derive จากจำนวนปุ่ม (`layoutFor(count)`) ซึ่งใช้ได้ตราบใดที่ **เราเป็นคนกำหนดปุ่มเอง**
พอเปิดให้ร้านอัปโหลดภาพของตัวเอง กลไกนี้พังทันที เพราะ `top-1-bottom-2` (1 บน + 2 ล่าง) กับ
`row-3` (สามช่องเรียงนอน) **มี 3 ช่องเท่ากันทั้งคู่**

ผลถ้าไม่แก้: ภาพที่กราฟิกร้านออกแบบมาเป็นสามช่องเรียงนอน จะถูกวางพื้นที่กดเป็น T-split ทับลงไป
⇒ **ลูกค้ากดโดนช่องผิด** โดยที่ร้านเห็นภาพตัวเองถูกต้องทุกอย่าง และไม่มี `tsc`/เทส/ตาเปล่าจับได้เลย

น่าสนใจว่าตอนเขียนรอบแรกมีคอมเมนต์กำกับไว้เองว่า *"ไม่รองรับ 5 ปุ่มเพราะจะมีช่องที่ขนาดไม่เท่าเพื่อน
ซึ่งเพิ่มโอกาสที่ภาพกับพิกัดไม่ตรงกัน"* — คิดถึงความเสี่ยง "ภาพไม่ตรงพิกัด" ไว้แล้ว แต่ไม่ได้คิดว่า
**ตัวกลไก derive-from-count เองคือช่องทางที่ทำให้มันเกิด**

### P-2 🛑 mutation จับเทสที่ผมเขียนเองได้ **5 ครั้งในวันเดียว** — ทุกตัวเขียวสนิทและดูน่าเชื่อถือ

| # | เทสที่ดูถูกต้อง | ทำไมมันพิสูจน์อะไรไม่ได้ |
|---|-----------------|--------------------------|
| 1 | `chatBarText` เกิน 14 ตัว → ปฏิเสธ | อักษรไทยเป็น BMP ตัวเดียว `.length` ให้เลขเท่ากับ `Array.from().length` เป๊ะ ⇒ เปลี่ยนกลับไปใช้ `.length` เทสก็ยังเขียว |
| 2 | `readImageSize` อ่านขนาด JPEG ได้ | ไม่มีเคสที่ยืนยันว่า **ไม่สลับ** width/height — สลับแล้วภาพ 2500×1686 กลายเป็น 1686×2500 ⇒ ร้านเปิดเมนูไม่ได้เลยสักร้าน |
| 3 | แถวสุดท้ายกลืนเศษแนวตั้ง | กรอบจริง 1686 หาร 2 แถวลงตัวพอดี ⇒ กิ่งนั้นไม่มีทางถูกเรียกด้วยค่าจริง |
| 4 | ด่าน consent มาก่อนการยิง LINE | `indexOf('CONSENT_REQUIRED')` ไปเจอสตริงเดียวกันใน **type union ตอนต้นไฟล์** ⇒ อยู่ก่อนเสมอตลอดกาล แม้ย้ายด่านไปไว้หลังสร้างเมนูแล้ว |
| 5 | ด่าน `type !== 'PRODUCT'` (idempotent guard) | เคสที่มีใช้ `TEXT` ที่ `productRefIds` ว่าง ⇒ ตกที่การเทียบความยาวแทน ถอดด่านออกก็ยังเขียว |

ทั้งห้าตัวเป็นเทสที่ **ผมเขียนเองในรอบเดียวกันกับโค้ด** และอ่านผ่านตาแล้วคิดว่าครอบคลุม

### P-3 🛑 เวิร์กทรีถูกลบทิ้งระหว่างทำงาน — commit ที่ยังไม่ push อยู่ในสถานะ dangling

Orca ย้าย `line-send-image` ไป `.orca-worktree-trash` เวลา 16:21 พร้อมกับ branch `meta-card-square`
งานรอดเพราะ git object อยู่ในรีโปหลัก ไม่ได้อยู่ในโฟลเดอร์เวิร์กทรี แต่ถ้าปล่อยไว้จะโดน `git gc`
เก็บทิ้งในที่สุด — กู้ด้วยการสร้าง branch ชี้ commit ที่ dangling

**สิ่งที่แย่กว่าคือ: ผมไม่รู้เลยจนกระทั่งพยายาม `cd` เข้าไปแล้ว shell ตอบว่าไม่มีโฟลเดอร์นี้**

### P-4 เอกสารกับโค้ดจะขัดกันถ้าไม่มีใครทัก

user สั่งให้ทำสิ่งที่ **กลับมติ D-RM-2** ที่ตัวเองเคาะไว้เมื่อไม่กี่ชั่วโมงก่อน (จาก "เทมเพลตอย่างเดียว"
เป็น "อัปโหลดเองได้") — `safepay-ux` เป็นคนทักว่าต้องแก้ BRD ก่อน dev เริ่ม ไม่ใช่ปล่อยให้เอกสารคง
คำว่า "อัปโหลดภาพเองไม่ได้" ไว้ขณะที่โค้ดทำตรงข้าม

ถ้าไม่มีใครทัก เอกสารจะกลายเป็นกับดักที่วางไว้รอคนถัดไปทันที

### P-5 grep ที่ผมเขียนเองรายงาน "0 จุด" ทั้งที่มีของอยู่จริง

ตรวจ HR7 ด้วย pattern `(text|bg|p|m|...)-\[` แล้วรายงานว่าไม่มี arbitrary value —
ความจริงคือ `pb-[calc(...)]` มีอยู่ **แต่ `p-\[` ไม่ match `pb-[`**

รอบสองยังพลาดอีกชั้น: เขียน carve-out comment ไว้ **คนละบรรทัด**กับ class ทั้งที่ `theme-guard`
ตัดเฉพาะบรรทัดเดียวกัน (บทเรียนที่ CLAUDE.md บันทึกไว้แล้วตั้งแต่ 2026-08-07)

### P-6 ตัวส่งอัตโนมัติตัวแรกบน LINE เจอค่าตั้งต้นที่เป็นกับดัก

`sendOutboundMessage` ตั้งต้น `sendMethod = 'PUSH'` แล้วค่อยพยายามอัปเกรดเป็น `REPLY`
⇒ ผู้ส่งอัตโนมัติที่เรียกตอนหน้าต่างฟรีปิดอยู่ จะ **push ทันทีโดยไม่มีใครสั่ง = ใช้เงินร้านเอง**
ซึ่ง BR-LINE-18 ห้ามไว้ตรงตัว · ด่านที่มีอยู่เดิมกันเฉพาะเส้น fallback หลัง `REPLY_TOKEN_INVALID`

และ **การเช็คหน้าต่างก่อนเรียกอย่างเดียวไม่พอ** เพราะระหว่าง "เช็คแล้วเปิด" กับ "claim token ได้จริง"
มี event ใหม่แย่ง token ไปได้ ⇒ ด่านต้องอยู่ **หลัง CAS**

## 2. Root causes

| # | สาเหตุร่วม |
|---|-----------|
| R-1 | **กลไกที่ถูกต้องภายใต้เงื่อนไข "เราคุมข้อมูลเอง" จะพังทันทีที่ข้อมูลมาจากผู้ใช้** (P-1) — derive-from-count ปลอดภัยตราบใดที่เราเป็นคนกำหนดปุ่ม |
| R-2 | **เทสที่เขียนพร้อมโค้ดโดยคนเดียวกัน มีแนวโน้มยืนยัน "สิ่งที่คนเขียนคิด" ไม่ใช่ "สิ่งที่ตั้งใจ"** (P-2) — และการอ่านทวนไม่ช่วย เพราะมันดูถูกต้องทุกบรรทัด |
| R-3 | **สถานะของเครื่องมือรอบตัวเปลี่ยนได้โดยเราไม่รู้** (P-3) — เวิร์กทรี, prisma client, `next-env.d.ts`, ไฟล์ untracked ของ session อื่น |
| R-4 | **เครื่องมือตรวจที่เขียนเองไม่ได้ถูกตรวจ** (P-5) — grep/regex เป็นโค้ดที่ผิดได้เหมือนโค้ดอื่น แต่ไม่มีใครทดสอบมัน |
| R-5 | **ค่าตั้งต้นของฟังก์ชันเดิมถูกออกแบบให้เหมาะกับผู้เรียกที่เป็นมนุษย์** (P-6) — ผู้เรียกชนิดใหม่ (ระบบอัตโนมัติ) ต้องการค่าตั้งต้นตรงข้าม |

## 3. Conventions to adopt

### C-1 🛑 ห้าม derive ค่าที่มีความหมายจาก "จำนวน" ถ้ามีสองความหมายที่จำนวนเท่ากันได้

เกณฑ์ตัดสิน: *"มีสองค่าที่ต่างกันจริง แต่ให้ตัวเลขเดียวกันไหม"* — ถ้าใช่ ต้องเป็น **คีย์ที่เลือก**
ไม่ใช่การเดา แม้วันนี้จะยังมีค่าเดียวก็ตาม

อาการเมื่อพลาด: ระบบทำงานต่อได้ปกติ ไม่มี error ไม่มี type ผิด — ความเสียหายไปโผล่ที่ปลายทาง
(ผู้ใช้กดผิดปุ่ม/ข้อมูลเข้าผิดช่อง) และไม่มีใครโยงกลับมาถึงต้นเหตุได้

รายละเอียด → `docs/conventions/no-derive-meaning-from-count.md`

### C-2 mutation testing ต้องทำ **ทุกด่าน** ไม่ใช่ทุกไฟล์

รอบนี้ mutation จับได้ 5 ครั้ง และ **ทุกครั้งคือเทสที่เพิ่งเขียนเสร็จในนาทีนั้น** ⇒ การอ่านทวนเทส
ไม่ใช่ตัวแทนของ mutation ได้เลย

ท่าที่ได้ผล: ไล่ทีละ **ด่าน/เงื่อนไข** (ไม่ใช่ทีละไฟล์) แล้วถามว่า *"ถ้าลบเงื่อนไขนี้ทิ้ง เทสตัวไหนแดง"*
ถ้าตอบไม่ได้ = เงื่อนไขนั้นยังไม่มีเทส

🛑 กับดักเฉพาะที่เจอซ้ำ: **เทสที่ยึด `indexOf('SOME_STRING')` เพื่อตรวจลำดับ** — สตริงเดียวกันมักปรากฏ
ใน type union/import/คอมเมนต์ตอนต้นไฟล์ด้วย ต้องยึด **คำสั่งจริง** (`if (!row.consentAt)`)

### C-3 commit ในเวิร์กทรีที่เครื่องมือภายนอกจัดการ ยังไม่ปลอดภัยจนกว่าจะ push

Orca/IDE/สคริปต์อาจลบเวิร์กทรีเมื่อไหร่ก็ได้ · git object รอดแต่ **branch หายไปด้วย** ⇒ commit
กลายเป็น dangling ที่รอ `git gc`

ท่าที่ปลอดภัย: push บ่อยกว่าที่คิด หรืออย่างน้อยสร้าง branch ในรีโปหลัก และถ้าเวิร์กทรีหายให้
`git cat-file -t <sha>` ยืนยันว่า commit ยังอยู่ แล้ว `git branch <name> <sha>` ปักหมุดทันที

### C-4 grep ที่ใช้เป็น "ด่าน" ต้องพิสูจน์ว่ามันจับของจริงได้ก่อนเชื่อผล

ก่อนรายงานว่า "0 จุด" ให้ยิง pattern เดียวกันกับบรรทัดที่ **รู้ว่ามีของ** อย่างน้อยหนึ่งครั้ง
ถ้าจับไม่ได้แปลว่า pattern ผิด ไม่ใช่โค้ดสะอาด (คู่กับบทเรียน `rg -r` ที่เคยบันทึกไว้แล้ว)

### C-5 ผู้เรียกชนิดใหม่ต้องตรวจ "ค่าตั้งต้น" ของฟังก์ชันเดิมเสมอ

ฟังก์ชันที่เขียนไว้สำหรับมนุษย์กด มักมีค่าตั้งต้นแบบ "พยายามส่งให้สำเร็จที่สุด" ซึ่งตรงข้ามกับสิ่งที่
ระบบอัตโนมัติต้องการ (ยอมไม่ส่งดีกว่าใช้เงินผู้ใช้) — เพิ่ม **ธงที่ผู้เรียกประกาศเจตนา** และวางด่าน
ณ จุดที่ตัดสินใจจริง ไม่ใช่ก่อนเรียก

## 6. หมายเหตุปิดท้าย

รอบนี้ต่างจากรอบก่อนตรงที่ **ปัญหาส่วนใหญ่ถูกจับด้วยเครื่องมือ ไม่ใช่ด้วยคำถามของ user** —
mutation จับได้ 5 · ux จับได้ 3 · HR17 จับได้ 1 · การยืนยันกับซอร์สทางการจับได้ 2

แต่สิ่งที่ยังเหมือนเดิมทุกรอบคือ **`tsc` เขียว · เทส 2,400+ ข้อเขียว · theme-guard ผ่าน · build ผ่าน
