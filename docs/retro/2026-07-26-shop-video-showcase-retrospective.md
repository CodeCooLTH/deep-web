## 1. สิ่งที่ทำได้ดี

### 1.1 ยืนกรานให้ "ความเป็นเจ้าของ" เป็นข้อกำหนด ไม่ใช่ทางเลือก

ตอนแรกฟีเจอร์นี้ออกแบบเป็น "วาง URL คลิปแล้วฝัง" ซึ่งทำเสร็จเร็วกว่ามาก user เป็นคนดักเองว่า *"ต้องการันตีด้วยว่าวีดีโอที่เอามาต้องเป็นเจ้าของจริง ๆ"* แล้วเปลี่ยนเป็นเลือกจากบัญชีที่เชื่อมไว้

นี่คือการตัดสินใจที่ถูกต้องที่สุดของงานรอบนี้ ถ้าปล่อยให้วาง URL ได้ คลิปบนหน้าร้านจะไม่มีน้ำหนักเป็นหลักฐานเลย และแย่กว่านั้นคือกลายเป็นเครื่องมือให้ร้านหลอกลวงยืมความน่าเชื่อถือของคนอื่นมาใช้ บนหน้าที่ผู้ซื้อไว้ใจที่สุดพอดี

**บทเรียน:** บนแพลตฟอร์มที่ขายเรื่องความน่าเชื่อถือ ฟีเจอร์ที่ "แสดงอะไรบางอย่างเพื่อสร้างความเชื่อมั่น" ต้องถามเสมอว่าปลอมได้ไหม ถ้าปลอมได้ง่ายกว่าที่ผู้ชมจะตรวจสอบ ฟีเจอร์นั้นทำร้ายผู้ซื้อมากกว่าช่วย

### 1.2 แยก "ตรวจไม่ได้" ออกจาก "ไม่ใช่ของคุณ"

`listPickableVideos` เดิมคืน `[]` เมื่อดึงจาก Meta ไม่สำเร็จ ปลายทางจึงสรุปว่าไม่มีคลิปไหนเป็นของร้านนี้ แล้วตอบ 403 "มีคลิปที่ไม่ได้อยู่ในบัญชีที่เชื่อมไว้" — กล่าวหาร้านที่สุจริตทั้งที่ปัญหาคือ API ล่ม

แก้ด้วยการคืน `{items, failed}` และเพิ่ม 503 `VERIFY_UNAVAILABLE`

**บทเรียน:** ค่าว่างที่แปลว่า "ไม่มี" กับที่แปลว่า "ไม่รู้" ต้องแยกชนิดข้อมูลออกจากกันตั้งแต่ต้นทาง ไม่ใช่ให้ปลายทางเดา — โดยเฉพาะเมื่อการเดาผิดกลายเป็นการกล่าวหาผู้ใช้

### 1.3 บังคับความปลอดภัยด้วยชนิดข้อมูล ไม่ใช่ด้วยวินัย

`buildEmbedUrl` รับ `ParsedVideo` เท่านั้น ไม่รับ string จึงไม่มีทางเรียกด้วยค่าที่ผู้ใช้พิมพ์มาตรง ๆ ได้เลย ต่อให้คนเขียนโค้ดคนต่อไปไม่รู้เหตุผล

## 2. สิ่งที่พลาด

### 2.1 ข้าม Documentation-First ทั้งฟีเจอร์ (Hard Rule 11)

ฟีเจอร์นี้ลงโค้ดและ deploy prod ไปแล้วโดยไม่มี PRD/BRD เลย เอกสารทั้ง 7 ฉบับเพิ่งเขียนย้อนหลังตอน user สั่งเก็บหนี้

เหตุผลตามจริงคือขอบเขตเปลี่ยนหลายรอบภายในวันเดียว (แปะลิงก์ → เลือกจากบัญชีที่ยืนยัน → เพิ่ม Facebook → เพิ่มยอดวิว) แต่นั่นเป็น**คำอธิบาย ไม่ใช่ข้อแก้ตัว** — CLAUDE.md เขียนไว้ตรง ๆ แล้วว่า back-fill retroactive = หนี้ ไม่ใช่ default และเป็นบทเรียนซ้ำจาก 00012

**แก้ครั้งหน้า:** ขอบเขตที่ยังไม่นิ่งคือเหตุผลให้เขียน PRD สั้น ๆ *ก่อน* ไม่ใช่เหตุผลให้ข้าม การเขียน PRD 20 บรรทัดตอนขอบเขตเปลี่ยนรอบที่สอง จะจับได้เองว่ากำลังสร้างของคนละชิ้นกับที่ตกลงไว้

### 2.2 QA แค่ viewport เดียวแล้วถือว่าจบ

รอบก่อนวัดแค่ 430px พอมาวัดแท็บเล็ต/เดสก์ท็อปตอนเก็บหนี้ เจอทันทีว่าปุ่มเล่นบนคลิปไม่ได้อยู่กลางรูป แต่ตกไปอยู่ล่างกรอบจนโดนตัด — อยู่ในหน้าที่ deploy prod ไปแล้ว

สาเหตุคือ `inset-block-start-0` ไม่ได้ให้ CSS อะไรเลยในโปรเจกต์นี้ คลาสสะกดถูก ไม่มี error ไม่มี warning tsc ผ่านหมด browser ทิ้งกฎที่ไม่รู้จักไปเงียบ ๆ

**แก้ครั้งหน้า:** งาน UI ต้องวัดอย่างน้อย 3 ขนาด (มือถือ/แท็บเล็ต/เดสก์ท็อป) และวัด **computed style** ไม่ใช่ดูแค่ screenshot — ตรงกับ `feedback_browser_qa_catches_what_static_misses` ที่บันทึกไว้แล้วแต่รอบนี้ยังทำไม่ครบ

### 2.3 ไม่ได้สำรวจของที่โปรเจกต์มีอยู่แล้วก่อนสร้างใหม่

ใช้เวลาไปกับไอคอนช่องทางสามรอบ: ครั้งแรกลืมใส่ prefix `tabler:` (ไอคอนหายเงียบ ๆ ไม่มี error) ครั้งที่สองเปลี่ยนเป็น `simple-icons` ครั้งที่สาม user ทักว่า *"ไปเอา icon มาจากไหนเนี่ย ดูหน้าแชทมะ"* — ปรากฏว่าโปรเจกต์มีไฟล์โลโก้แบรนด์จริงใน `public/images/logos/` ที่หน้าแชทใช้มาตั้งแต่ feat 00018 แล้ว

ทั้งสามรอบเลี่ยงได้ด้วยการ `ls public/images/logos/` ครั้งเดียว

**แก้ครั้งหน้า:** ก่อนสร้าง asset/helper/pattern ใด ๆ ให้ค้นก่อนว่ามีของเดิมไหม โดยเฉพาะสิ่งที่ "ต้องมีเหมือนกันทั้งระบบ" เช่นโลโก้ช่องทาง สีสถานะ รูปแบบวันที่ — ของพวกนี้ถ้าทำใหม่คือสร้างความไม่สอดคล้องโดยอัตโนมัติ

### 2.4 เชื่อโครงสร้างข้อมูลของ API โดยไม่เปิดผลลัพธ์จริงดู

Instagram `GET /media` คืน `id` ที่ดูเหมือนใช้ได้ทันที แต่เป็น media id ซึ่งประกอบ URL ฝังแล้วได้หน้าเปล่า ค่าที่ใช้ได้จริงคือ shortcode ที่ซ่อนอยู่ใน `permalink`

บั๊กนี้ผ่าน tsc ผ่าน unit test ผ่านทุกด่าน และแสดงผลออกมาเป็น iframe เปล่าที่ไม่มี error

**แก้ครั้งหน้า:** integration กับ API ภายนอกต้องเปิด response จริงดูอย่างน้อยหนึ่งครั้งก่อนเขียนโค้ดแปลงข้อมูล ชื่อฟิลด์ที่ "ดูเหมือนใช่" ไม่ใช่หลักฐาน

### 2.5 สรุปเกินจากตัวอย่างเดียว

ตอบ user ว่าไม่มีร้านไหนเชื่อม Instagram ไว้ ทั้งที่เช็คแค่ร้านทดสอบร้านเดียว user แก้ให้เองว่า *"มีนะ ธนภัทร ไง"* ซึ่งเป็นร้านที่มีคลิปจริง 7 คลิปและกลายเป็นข้อมูลทดสอบหลักของงานทั้งรอบ

**แก้ครั้งหน้า:** คำตอบที่ขึ้นต้นว่า "ไม่มี…" ต้องมาจาก query ที่กวาดทั้งชุด ไม่ใช่จากตัวอย่างที่หยิบมาดู

## 4. สิ่งที่ต้องเปลี่ยนจริงในรอบถัดไป

1. **ฟีเจอร์ใหม่ = เปิดโฟลเดอร์ docs ก่อนแตะโค้ด** ไม่มีข้อยกเว้นเรื่อง "ขอบเขตยังไม่นิ่ง" — ขอบเขตไม่นิ่งยิ่งต้องเขียน
2. **QA UI = 3 viewport ขั้นต่ำ + วัด computed style** ไม่ใช่ screenshot อย่างเดียว
3. **ก่อนสร้าง asset/helper ที่ต้องสอดคล้องทั้งระบบ ให้ค้นของเดิมก่อนเสมอ**
4. **แตะ API ภายนอก = เปิด response จริงดูก่อนเขียน mapping**
