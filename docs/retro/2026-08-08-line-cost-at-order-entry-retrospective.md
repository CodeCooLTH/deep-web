# Retro — ต้นทุนรายบรรทัดตอนเปิดบิล (FR-EXP-17) · 2026-08-08 (รอบสอง)

user ถามคำถามเดียว: *"ร้านธนภัทร ทำการบันทึกต้นทุน ครบทุกสินค้าหรือยัง"* — คำตอบตรง ๆ คือ "เหลือ 6 ตัวจาก 23" แต่การไล่ตรวจต่อพบว่า **ทั้งร้านไม่มีออเดอร์รายการไหนมีต้นทุนเลยสักรายการ (0 จาก 95)** ทั้งที่สินค้า 17 ตัวตั้งไว้แล้ว → นำไปสู่ FR-EXP-17

---

## 1. Problems

### P-1 คำขอระบุ 2 กรณี แต่จริง ๆ เป็นเส้นทางเดียวกัน

user สั่งว่า *"พิมพ์ชื่อสินค้าเองในบิล (ไม่ผูกสินค้า), Quick-Create ต้องให้ระบุต้นทุน"* — ฟังดูเหมือน 2 flow ที่ต้องออกแบบแยก

ความจริง: `createOrder` **ไม่เคยสร้างรายการที่ไม่ผูกสินค้าเลย** ทุกรายการที่พิมพ์ชื่อเองถูกส่งเข้า Quick-Create ซึ่ง `tx.product.create` ให้เสมอแล้วผูกกลับ (`order.service.ts:322-342`)

หลักฐานจาก prod: **`OrderItem` ทั้ง 110 แถวมี `productId` ครบ ไม่มี null สักตัว**

ถ้ารับคำขอมาออกแบบตรง ๆ จะได้ UI สองชุดสำหรับเส้นทางเดียว

### P-2 🛑 agent ล็อกมติจากถ้อยคำในเอกสาร ไม่ใช่จากโค้ด — และเอกสารผิด

`safepay-product` ล็อก Out-of-Scope ว่า *"ห้ามให้กรอกต้นทุนตอนแก้ไขออเดอร์ เพราะขัด D-5 ที่ว่า snapshot เกิดตอนสร้างเท่านั้น"* โดยอ้าง FR-EXP-02 ที่เขียนว่า *"Snapshot เกิดที่จุดสร้าง order …**เท่านั้น**"*

ความจริง: `updateOrder` **re-snapshot อยู่แล้ว** — คอมเมนต์ในโค้ดเขียนเองว่า `// 5) cost snapshot (เหมือน createOrder)` และ `PATCH /api/orders/[token]` validate ด้วย `CreateOrderSchema` ตัวเดียวกับตอนสร้าง

ถ้าทำตาม agent: ซ่อนช่องในหน้าแก้ไข ทั้งที่ระบบเขียนทับค่าอยู่ดี = ผู้ขายแก้ไม่ได้โดยไม่ได้ป้องกันอะไรเลย

### P-3 เอกสารประกาศข้อจำกัดที่โค้ดไม่เคยมี

FR-EXP-02 เขียนคำว่า "เท่านั้น" ตั้งแต่รอบแรกของ 00016 — ไม่มีใครเทียบกับ `updateOrder` ที่เขียนขึ้นในรอบเดียวกัน

**คลาสเดียวกับ Hard Rule 16 แต่กลับทิศ:** รอบก่อนคือ *โค้ดนิยามศัพท์ชนกับนิยามที่มีอยู่* รอบนี้คือ *เอกสารประกาศข้อจำกัดที่โค้ดไม่มี* — ทั้งคู่คือ "เอกสารกับโค้ดพูดคนละเรื่อง" และทั้งคู่ทำให้คนถัดไปตัดสินใจผิด

### P-4 คำตอบแรกที่ "ถูก" แต่แทบไม่มีประโยชน์

คำถามคือ "บันทึกต้นทุนครบหรือยัง" — คำตอบตรงตัว (เหลือ 6 ตัว) **ถูกแต่ตอบไม่ตรงสิ่งที่ user อยากรู้จริง** ซึ่งคือ "ระบบเก็บต้นทุนได้จริงหรือยัง"

ต้อง query 6 รอบต่อเนื่องกว่าจะถึงคำตอบที่มีความหมาย: 6 สินค้าขาด → 95 รายการไม่มีต้นทุน → **ทั้ง 95 ไม่มีเลยแม้สินค้าจะตั้งแล้ว** → เพราะ snapshot ล็อกตอนสร้าง → สินค้าเพิ่งตั้งต้นทุนวันนี้ 08:33–08:40 ส่วนออเดอร์ล่าสุด 07:58 → ไม่มีออเดอร์ไหนเกิดหลังต้นทุนถูกตั้งเลย

### P-5 เกือบรายงาน seed data เป็นหลักฐาน

ตอนหาว่า "กลไก snapshot เคยทำงานจริงบน prod ไหม" เจอ 5 รายการที่มีต้นทุน — เกือบตอบว่า "ทำงานได้แล้ว"

สังเกตทัน: ออเดอร์ลงวันที่ 07-26 / 07-31 / 08-03 แต่ **เวลาเป็น 16:51 เหมือนกันหมดทุกใบ** และสินค้าถูกแก้ 08-04 16:51 เหมือนกันอีก = รูปแบบของสคริปต์ seed ไม่ใช่คนกดจริง

**ยังไม่มีหลักฐานจาก prod เลยว่าเส้นทางนี้เคยทำงานจริง** — ต้องรอออเดอร์ใบถัดไปของร้าน

## 2. Root causes

| # | ทำไม |
|---|---|
| P-1 | ผู้ใช้อธิบายจาก **สิ่งที่เห็นบนหน้าจอ** ("พิมพ์ชื่อเอง" กับ "เลือกจากรายการ" ดูต่างกันชัดเจนตอนใช้งาน) ส่วนโค้ดยุบทั้งสองเป็นเส้นทางเดียวหลังบ้าน — คำอธิบายของผู้ใช้ไม่ใช่แผนที่ของโค้ด |
| P-2 | agent ถูกส่งไปเขียนเอกสาร จึงอ่านเอกสารเป็นแหล่งความจริง — และ prompt ของผมไม่ได้สั่งให้ยืนยันข้อจำกัดที่เอกสารอ้างกับโค้ดก่อน |
| P-3 | คำว่า "เท่านั้น" ถูกเขียนตอนออกแบบ (ก่อน implement) แล้วไม่มีใครกลับมาแก้เมื่อ `updateOrder` ถูกเขียนให้ re-snapshot — เอกสารบันทึก *เจตนา* แต่ถูกอ่านเป็น *ข้อเท็จจริง* |
| P-4 | คำถามที่ผู้ใช้ถามมักเป็น **ตัวแทน** ของคำถามที่เขาอยากรู้จริง — "ครบหรือยัง" คือวิธีถามว่า "มันทำงานไหม" |
| P-5 | ข้อมูล seed อยู่ในฐานเดียวกับข้อมูลจริง ไม่มีคอลัมน์ไหนบอกว่าแถวไหนเป็น seed — ต้องดูรูปแบบ timestamp เอา |

## 3. Conventions to adopt

### C-1 🛑 ข้อความในเอกสารที่อ้างพฤติกรรมของโค้ด ต้องยืนยันกับโค้ดก่อนใช้ตัดสินใจ — โดยเฉพาะเมื่อใช้เป็นเหตุผลที่จะ **ไม่ทำ** อะไร

กฎนี้เป็น **ทิศกลับของ Hard Rule 16**:

| ทิศ | อาการ | เคสจริง |
|---|---|---|
| HR16 | โค้ดนิยามศัพท์ใหม่ ชนกับนิยามที่มีอยู่แล้ว | "กำไร" ที่ชนกับ `NET_PROFIT_FORMULA` |
| **C-1 (ใหม่)** | **เอกสารประกาศข้อจำกัดที่โค้ดไม่เคยมี** | FR-EXP-02 "snapshot เกิดตอนสร้างเท่านั้น" ขณะที่ `updateOrder` re-snapshot |

**เมื่อไหร่ที่ต้องเช็ค:** ทุกครั้งที่เอกสาร/agent อ้างข้อจำกัดของระบบเป็นเหตุผลไม่ทำอะไร — `rg` หาฟังก์ชันที่เกี่ยวข้องแล้วอ่านจริง ก่อนยอมรับ

**ทำไมสำคัญกว่าที่ดู:** ข้อจำกัดปลอมไม่มีวันถูกจับได้จากการทดสอบ เพราะมันทำให้เรา*ไม่*เขียนโค้ด — ไม่มีอะไรให้เทสจับ มันจะอยู่ต่อไปเรื่อย ๆ จนกว่าจะมีคนบังเอิญเปิดโค้ดดู

→ เขียนไว้ใน `docs/conventions/domain-term-single-definition.md` §"ทิศกลับ"

### C-2 ข้อมูลบน prod ที่ดูเหมือนหลักฐาน อาจเป็น seed — ตรวจรูปแบบ timestamp ก่อนอ้าง

seed อยู่ในฐานเดียวกับข้อมูลจริงและไม่มีคอลัมน์บอก — สัญญาณที่ใช้ได้จริง: **นาที/วินาทีเดียวกันข้ามหลายแถวที่ควรเกิดคนละเวลา** (`16:51` ทั้ง 5 แถวจาก 3 วันต่างกัน)

ก่อนอ้างข้อมูล prod เป็นหลักฐานว่า "ฟีเจอร์ทำงานแล้ว" ให้ดู `createdAt`/`updatedAt` ของกลุ่มนั้นก่อนเสมอ

### C-3 คำขอที่ระบุหลายกรณี — ตรวจก่อนว่าเป็นเส้นทางเดียวกันไหม

ผู้ใช้อธิบายจากสิ่งที่เห็นบนหน้าจอ ซึ่งอาจยุบเป็นเส้นทางเดียวหลังบ้าน (หรือกลับกัน — ดู `one-value-many-entry-points.md` ที่เป็นทิศตรงข้าม)

วิธีตรวจที่ถูกที่สุด: query ฐานจริงหาว่าข้อมูลที่ควรต่างกันตามคำอธิบาย จริง ๆ แล้วต่างกันไหม (`productId IS NULL` = 0 ตอบทั้งคำถามในคำสั่งเดียว)

## 4. What went right

1. **Query prod ก่อนออกแบบ** — พบว่า 2 กรณีเป็นเส้นทางเดียว ประหยัดงานครึ่งหนึ่งและกัน UI ซ้ำซ้อน
2. **ไม่รับมติของ agent ทั้งดุ้น** — เปิดโค้ดเช็คข้ออ้าง "ขัด D-5" แล้วพบว่าข้ออ้างผิด (P-2)
3. **จับ seed data ได้ก่อนรายงาน** — ถ้าพลาดจะกลายเป็นการยืนยันว่าฟีเจอร์ทำงานทั้งที่ยังไม่มีหลักฐาน
4. **เทสล็อก `??` ไม่ใช่ `||`** — จุดที่พลาดง่ายที่สุดของงานนี้: ถ้าใช้ `||` การกรอกต้นทุน **0** จะถูกมองว่า "ไม่ได้กรอก" แล้วไปหยิบต้นทุนเดิมมาแทน เทส 8 ข้อล็อกทั้งสองทิศ (snapshot + write-back)
5. **ux กางเลขงบพื้นที่จริงแล้วฆ่าดีไซน์ที่ชัดที่สุด** — คอลัมน์ใหม่เป็นคำตอบแรกที่ทุกคนคิด แต่ตัวเลข (364px คงที่ vs 337.5px ที่มี) พิสูจน์ว่าตะกร้าล้นอยู่**ก่อน**งานนี้แล้ว
6. **`resolveLineCosts()` ตัวเดียวใช้ทั้ง create และ update** — ตั้งใจกันไม่ให้เกิดคลาส HR16 ซ้ำในงานของตัวเอง
7. **เจอทางแก้ที่ใช้ได้ทันทีโดยไม่ต้องรอโค้ด** — ออเดอร์ PENDING 9 ใบเปิดแล้วบันทึกใหม่ได้ต้นทุนเลย เพราะ `updateOrder` re-snapshot (ผลพลอยได้จากการค้นพบใน P-2)
