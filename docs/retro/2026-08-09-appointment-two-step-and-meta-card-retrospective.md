## บทเรียนหลักของรอบนี้ (ข้อเดียวที่สำคัญกว่าข้ออื่นทั้งหมด)

### เมื่อ gate เตือนแล้วเลือกทางที่เบากว่า ให้ถือว่ายังไม่ได้แก้ — ไม่ใช่ "แก้แล้วบางส่วน"

รอบ 2026-08-08 `/impeccable critique` ชี้ P0 ไว้ตรง ๆ ว่าในกล่องแคบ ส่วนเลือกเวลาที่เพิ่งย้ายเข้ามาจะบีบรายการคิวจนเหลือ 0px และ **เสนอทางแก้ไว้ 2 ทาง โดยแนะนำให้แยกเป็น 2 ขั้น**

ผมเลือกทางที่เบากว่า (ให้เลื่อนแทนการบีบ) เพราะมันแก้อาการที่ critique วัดได้จริง — รายการไม่หายแล้ว

**วันถัดมา user กลับมาบอกเรื่องเดิม**: "ตรงเลือกเวลาใน mobile ใช้ยาก" แล้วจบลงที่การทำทางที่ critique แนะนำไว้ตั้งแต่แรกอยู่ดี

สิ่งที่ผมทำผิดไม่ใช่การเลือกทางเบา — แต่คือการ **ตีความ "อาการหายแล้ว" ว่าเท่ากับ "ปัญหาถูกแก้แล้ว"** critique พูดถึงต้นเหตุ (ปฏิทินกินพื้นที่ทั้งที่ทำหน้าที่จบไปแล้ว) ส่วนสิ่งที่ผมวัดคืออาการ (รายการถูกบีบ) การให้เลื่อนแก้อาการโดยไม่แตะต้นเหตุ — ปฏิทินยังกิน 320px กลางจออยู่เหมือนเดิม แค่ตอนนี้ผู้ใช้เลื่อนผ่านมันไปได้

> **กติกา:** เมื่อ gate เสนอทางแก้ที่ใหญ่กว่าที่เราตั้งใจจะทำ ให้ตอบให้ได้ก่อนว่า *ทางเบาที่เลือกแก้ต้นเหตุที่มันชี้ หรือแก้แค่อาการที่มันวัดได้* — ถ้าเป็นอย่างหลัง ให้บันทึกเป็นหนี้ที่ยังเปิดอยู่ อย่าปิดงาน

**ต้นทุนจริง:** งานรอบ 08-09 ทั้งรอบ (ux gate + implement + verify + deploy) คือราคาของการไม่ทำให้จบตั้งแต่ 08-08

## บทเรียนที่ 2 — คนละทีมแก้บั๊กคลาสเดียวกันคนละชนิดพร้อมกัน แล้ว guard ทับกัน

`949e22d5` ชนกับ `6aaaa2a6` ของอีก session ที่ push ขึ้น main ระหว่างที่ผมกำลังทำอยู่ ทั้งคู่แก้ **บรรทัดเดียวกันเป๊ะ** ด้วยเหตุผลเดียวกัน:

| ฝั่ง | อาการ | guard ที่เติม |
|---|---|---|
| อีก session | การ์ดสินค้า carousel ของ Meta ตกเป็นบรรทัดระบบ | `!hasGenericCards` |
| ผม | การ์ดคำขอชำระเงินของ Meta ตกเป็นบรรทัดระบบ | `!isMetaOrderCard` |

**ถ้าเลือกข้างใดข้างหนึ่งตอน resolve conflict อีกฝั่งจะพังเงียบทันที** — และมันจะพังแบบที่ tsc/เทสจับไม่ได้เลย เพราะทั้งสองทางคอมไพล์ผ่านและไม่มีเทสที่ครอบทั้งคู่พร้อมกัน

คำตอบที่ถูกคือ **เอาทั้งสอง guard** (`!hasGenericCards && !isMetaOrderCard`) ซึ่งจะรู้ได้ก็ต่อเมื่อเปิดอ่าน diff ของอีกฝั่งก่อน ไม่ใช่ดูแค่ว่าบรรทัดไหนชน

> **กติกา (ต่อยอด HR17):** conflict ที่ทั้งสองฝั่ง "เติมเงื่อนไขให้นิพจน์เดียวกัน" แทบไม่เคยเป็นการเลือกข้าง — มันคือการรวมเงื่อนไข ให้ตั้งข้อสงสัยไว้ก่อนว่าคำตอบคือ AND ไม่ใช่ either

## บทเรียนที่ 3 — คอมเมนต์ที่บันทึก "ข้อเท็จจริงของโลกภายนอก" หมดอายุได้โดยไม่มีใครรู้

`meta-order-card.ts` เขียนไว้ตั้งแต่ 2026-07-31 ว่า:

> "**ไม่มีข้อความสถานะการชำระเงินเลยสักรายการในฐาน** (สำรวจ ChatMessage ทั้งหมด) → เราจึงไม่รู้ว่าจ่ายแล้วหรือยัง ห้ามเขียน 'รอชำระเงิน' เป็นข้อเท็จจริง"

ตอนเขียนถูกทุกคำ และเป็นการยับยั้งชั่งใจที่ดี — แต่พอเส้น Graph sync เริ่มเก็บ `subtitle` (2026-08-07) ข้อเท็จจริงนั้นเปลี่ยนทันที **โดยไม่มีอะไรไปแตะคอมเมนต์นั้นเลย** ผลคือไฟล์นี้ถือข้อมูลที่ล้าสมัยไว้เป็นเหตุผลของการไม่ทำอะไร

ต่างจากบทเรียน 08-08 (คอมเมนต์ที่ประกาศ **สมมติฐานของโค้ดเรา**) ข้อนี้คือคอมเมนต์ที่ประกาศ **สถานะของระบบภายนอก** ซึ่งเปลี่ยนได้เองโดยเราไม่ได้ทำอะไรผิด

> **กติกา:** คอมเมนต์ที่อ้างผลสำรวจข้อมูล ("สำรวจทั้งฐานแล้วไม่มี…") ต้องมี **วันที่กำกับ** และเมื่อมีคนแก้เส้นที่ป้อนข้อมูลนั้น ต้องกลับมาอ่านคอมเมนต์ที่อ้างผลสำรวจของมัน

## บทเรียนที่ 4 — เทสที่ยืนยัน "สิ่งที่ระบบบันทึก" ไม่ได้ยืนยันว่า "ระบบแสดงผลมันได้"

บั๊กการ์ด Facebook มีเทสอยู่แล้วที่ **คาดหวังสตริงที่พังตรงตัว**:

```ts
expect(data.body).toBe('[การ์ดจาก Facebook] ฿360.00 order — Waiting for payment')
```

เทสนี้เขียวมาตลอดและถูกต้องทุกประการในขอบเขตของมัน (ฝั่ง ingest บันทึกถูก) — แต่ไม่มีใครถามว่า **ฝั่งแสดงผลอ่านสตริงนี้ออกไหม** ทั้งสองฝั่งมี parser คนละตัว คนละไฟล์ ไม่มีเทสไหนเชื่อมกัน

> **กติกา:** ค่าที่ฝั่งหนึ่งเขียนแล้วอีกฝั่งต้องอ่าน ให้มีเทสที่ **ยืนยันทั้งคู่ในเคสเดียวกัน** — เทสใหม่ในรอบนี้ (`meta-order-card.test.ts`) จึงมีเคสที่พิสูจน์ว่า parser สองตัวจับข้อความเดียวกันได้ทั้งคู่ เพื่อให้ "ใครต้องชนะ" เป็นข้อเท็จจริงที่ตรึงไว้ ไม่ใช่ลำดับบรรทัดที่ใครก็สลับได้

## สิ่งที่ทำได้ดี

- **ถามก่อนเดา 2 จุดที่เป็นการตัดสินใจของ product** — ทรงของจอเลือกเวลา (แยก 2 ขั้น) และภาษาของสถานะการ์ด (คำของ Meta ไม่แปลไทย) ทั้งคู่เป็นเรื่องที่ถ้าเดาผิดต้องรื้อทั้งรอบ
- **ปฏิเสธการเดาที่ดูเหมือนช่วยผู้ใช้** — ไม่จำแนกสี badge ตามความหมายของคำสถานะ (เช่นเดาว่า "Paid" = เขียว) เพราะยังไม่รู้ว่า Meta ใช้คำอะไรได้บ้าง การเดาผิดคือการยืนยันสิ่งที่ไม่รู้ (Verified-Means-Green)
- **รักษาพฤติกรรมที่ user เคยเคาะไว้** — จิ้มวันยังเป็น preview ไม่กระโดดเข้าขั้น 2 เอง เพราะ "จิ้มดูหลายวันเทียบคิว" เป็นสิ่งที่ user สั่งไว้เมื่อ 08-07
- **ไม่แตะงานของอีก session ในเวิร์กทรีที่แชร์กัน** — commit เฉพาะไฟล์ตัวเอง และ rebase ใน worktree ชั่วคราวแยกทุกครั้ง (rebase ตรง ๆ ทำไม่ได้เพราะเวิร์กทรีมีงานค้างของเขาตลอดเวลา)
