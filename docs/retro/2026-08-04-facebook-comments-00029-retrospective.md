## 1. Problems

### P1 — พิมพ์ในแชทมือถือแล้วเธรดเด้งขึ้น-ลงทุกตัวอักษร (บั๊กที่ลูกค้าแจ้ง)
**หลักฐาน:** วิดีโอจากลูกค้า (`~/Downloads/807425473.262850.mp4`) — ไม่มี log ไม่มี error ไม่มี stack trace
**ที่แก้:** `src/hooks/useComposerHeight.ts` (`5ad1bdc7`)

ปัญหาเห็นเฉพาะ Safari/iOS — Chrome DevTools emulation ไม่เคยเห็น เพราะไม่ใช่บั๊กของ layout แต่เป็นพฤติกรรม **scroll clamping ของ WebKit** ระหว่าง forced layout

### P2 — `rawMessage` ที่เก็บไว้ "สืบไม่ได้" เพราะเก็บของที่ผ่าน Valibot มาแล้ว
**หลักฐาน:** ตอนสืบเคส 2 message id ที่ขึ้นข้อความ placeholder — เปิด `rawMessage` แล้วไม่เจอ field แปลก ๆ เลย ทั้งที่ทั้งฟีเจอร์นี้มีไว้ตอบคำถามว่า "Meta ส่งอะไรมาที่เราไม่รู้จัก"
**ที่แก้:** `b91ff3ed` — เก็บ `rawEvent` ที่จับคู่ตาม index ก่อนเข้า schema (`extractMessagingEventsWithRaw`)

### P3 — webhook subscribe ขาดแบบเงียบ 2 ชั้น — read receipt/รีแอ็กชันตายไปทั้งกล่อง
**หลักฐาน:** เธรด ~445 รายการไม่มี read receipt เลยสักอัน ทั้งที่โค้ดฝั่งรับมีครบ
สาเหตุคือ subscribe มี **2 ชั้นที่ไม่เกี่ยวกัน**: field ระดับ App (App Dashboard) กับ `subscribed_fields` ระดับเพจ (ตอน connect) — ชั้นไหนขาดก็เงียบเหมือนกัน ไม่มี error ไม่มี 4xx

### P4 — ตอบคอมเมนต์ไม่ได้ `(#200) Permissions error` ทั้งที่เพิ่ม scope ในโค้ดแล้ว
**หลักฐาน:** user กดตอบคอมเมนต์ → `{"error":"Facebook ปฏิเสธการตอบ: (#200) Permissions error"}`
ตรวจด้วย `debug_token` แล้วพบว่า token ที่ออกวันที่ 31 ก.ค./1 ส.ค. **ไม่มี** `pages_read_user_content`/`pages_manage_engagement` เพราะ **scope ผูกกับ token ตอนกด grant ไม่ได้ผูกกับแอป** — แก้ `CONNECT_SCOPES` ในโค้ดไม่ได้ย้อนแก้ token ที่ออกไปแล้ว

### P5 — 🛑 หน้าคอมเมนต์ถูกรื้อ 4 รอบเพราะประดิษฐ์เอง ทั้งที่หน้าพี่น้องมี pattern อยู่แล้ว
**หลักฐาน (ชัดที่สุดของรอบนี้):**

| รอบ | commit | user บอกอะไร |
|---|---|---|
| 1 | `b12f5507` | "ขนาดของ video เล็กเกินไป และคอมเม้นต่างๆ ชิดซ้ายไม่อยู่ตรงกลาง" |
| 2 | `9fb29d96` | "ผมไม่เห็น comment เลย งั้นเราทำเป็น 2 ฝั่งดีไหม ซ้ายขวา 50%" |
| 3 | `994f4956` | "ตรง header อยากให้เป็นแบบนี้ [ภาพ Business Suite]" |
| 4 | `e6337442` | **"ตรงตัวกรองและสถานะทำไมไม่ทำเหมือน ตรงข้อความ"** |

รอบที่ 4 คือของแพงที่สุด — ตัวกรองเพจ (pill group) + แท็บสถานะ (underline) **มีอยู่แล้วใน `InboxList.tsx`** ที่อยู่โฟลเดอร์เดียวกัน ห่างกัน 2 ระดับ แต่ผมประดิษฐ์ปุ่มชุดใหม่ขึ้นมาเอง

### P6 — ตัวเลข "ยังไม่ตอบ" ไม่ตรงกันในหน้าเดียว (ซ้าย 7 ขวา 8)
**หลักฐาน:** user ส่งภาพหน้าจอที่ตัวเลขสองที่ในจอเดียวกันไม่ตรง
สาเหตุ: นิยาม "ยังไม่ตอบ" ถูกเขียนซ้ำ 2 ที่ (`listCommentPosts` กับฝั่ง thread) แล้วนับไม่เหมือนกัน — **บั๊กตระกูลเดียวกับ `shipping-address-status.ts` เมื่อ 2026-08-02 เป๊ะ ๆ** (กฎเดียวเขียนซ้ำหลายที่ = UI โกหก)

### P7 — วิดีโอล้นกรอบ iframe
ปลั๊กอินวิดีโอของ Facebook เรนเดอร์ตาม **ค่า `width` ใน URL** ไม่ใช่ขนาดของ iframe ที่ครอบ — ตั้ง `width` คงที่แล้วย่อ iframe ด้วย CSS จึงล้นเสมอ

### P8 — ตอบยาวเกิน user ตามไม่ทัน
**หลักฐาน:** user พิมพ์ตรง ๆ ว่า **"ไม่เข้าใจ ทีละข้อได้ไหม"**
ผมยัด 3-4 เรื่องต่อหนึ่งข้อความมาหลายรอบ (แก้ layout + ตัวกรอง + วิดีโอ + ตัวเลข ในคำตอบเดียว) แล้วอ้างว่า "ทำครบแล้ว" ซึ่ง user ตรวจไม่ได้ว่าอันไหนเสร็จจริง

### P9 — ผมพูดผิดเองแล้วต้องแก้ 3 จุดในรอบนี้
1. แปลง timezone ผิดทาง (`AT TIME ZONE 'Asia/Bangkok'` บน timestamp ที่เป็น UTC อยู่แล้ว) → สรุปว่า read receipt "ค้างเก่า" ทั้งที่จริงเป็นของปัจจุบัน
2. อ่านผล `requirements` ของ App Review ผิด — endpoint นั้นรายงาน **ร่างถัดไป** ไม่ใช่ของที่ยื่นไปแล้ว → เกือบทำให้ user ยื่นซ้ำ
3. สรุปเร็วไปว่า "เล่นวิดีโอในหน้าเราไม่ได้" ทั้งที่ปลั๊กอินสาธารณะของ Facebook เล่นได้จริง

### P10 — push main ไม่ผ่านเพราะอีก session แซง
`git push origin HEAD:main` โดน reject (non-fast-forward) — ต้อง fetch + rebase + **build ใหม่หลัง rebase** แล้วค่อย push (เป็นไปตาม `feedback_build_after_rebase_not_before` ที่มีอยู่แล้ว — กฎทำงาน ไม่ใช่ปัญหาใหม่)

## 2. Root causes

| # | ปัญหา | ทำไม (ชั้นที่ 1) | ทำไม (ชั้นที่ 2 — ของจริง) |
|---|---|---|---|
| P1 | เธรดเด้งบน iOS | วัดความสูง textarea ด้วย `height:auto` | กล่อง composer หดชั่วขณะ → รายการข้างบนสั้นลง → **WebKit clamp `scrollTop` ทันที** (Chrome ไม่ clamp) → คืนความสูงแล้วตำแหน่งไม่กลับ. บั๊กที่เห็นเฉพาะเอนจิน = emulator ไม่มีวันจับได้ |
| P2 | rawMessage สืบไม่ได้ | เก็บ `event` ที่ผ่าน Valibot | **สับสนระหว่าง "ข้อมูลที่ระบบใช้" กับ "หลักฐานดิบไว้สืบ"** — ของสองอย่างนี้ต้องเก็บคนละชั้น ชั้นหลังห้ามผ่าน schema |
| P3 | webhook เงียบ | subscribe ไม่ครบ | Meta ออกแบบให้ "ไม่ subscribe = ไม่ส่ง" ไม่ใช่ "= error" → **ความเงียบไม่ใช่หลักฐานว่าไม่มีอะไรเข้ามา** และเราไม่มีตัววัดว่าเคยได้ field นี้ครั้งสุดท้ายเมื่อไหร่ |
| P4 | scope ไม่ติด | เพิ่ม scope ในโค้ดแล้วคิดว่าจบ | **OAuth scope ผูกกับ token ตอน grant** — โค้ดคุมได้แค่ "ครั้งหน้าจะขออะไร" ของที่ออกไปแล้วต้องให้ผู้ใช้เชื่อมใหม่เท่านั้น |
| P5 | รื้อ 4 รอบ | ไม่ได้ดูหน้าพี่น้องก่อนสร้าง | **ผมข้าม `safepay-ux` (Hard Rule 8) ทุกรอบของงานนี้** — ux เป็นด่านที่หน้าที่ตรง ๆ คือไปเปิด theme + หน้าที่มีอยู่แล้วมาแมป. ข้ามด่านนี้ = ประดิษฐ์เอง = user กลายเป็นคนรีวิว UI แทน |
| P6 | ตัวเลขไม่ตรง | นิยามเขียนซ้ำ 2 ที่ | เหมือน P5 — ไม่ได้มองหาของที่มีอยู่ก่อนเขียนใหม่ **เป็นบั๊กซ้ำรอยเดิมจาก 2026-08-02 ห่างกัน 1 วัน** |
| P7 | วิดีโอล้น | ตั้ง width คงที่ | ปลั๊กอินฝังของเจ้าอื่นเรนเดอร์ตาม param ใน URL ไม่ใช่ CSS ของเรา — **สมมติว่ามันทำตัวเหมือน element ของเราเอง** |
| P8 | ตอบยาวเกิน | อยากรายงานให้ครบ | ครบ ≠ ตรวจสอบได้ **งานที่ user ต้องกดดูเองทีละจุด ต้องส่งทีละจุด** ไม่งั้น user เสียเวลาแยกเองว่าอันไหนคืออันไหน |
| P9 | พูดผิด 3 จุด | สรุปจากค่าที่เห็นทันที | ทั้ง 3 เคสคือ **ตีความ output ของเครื่องมือโดยไม่อ่านว่าเครื่องมือนั้นนิยามค่าตัวเองว่าอะไร** (tz ของคอลัมน์, ความหมายของ endpoint, ความสามารถจริงของปลั๊กอิน) |

## 3. Conventions to adopt

### C1 — 🛑 สร้างหน้าใหม่ในกลุ่มที่มีหน้าพี่น้องอยู่แล้ว ต้อง "เปิดหน้าพี่น้องอ่าน" ก่อนเขียนบรรทัดแรก
เขียนเป็นเอกสารเต็มที่ `docs/conventions/sibling-surface-parity.md` แล้ว

สรุปกฎ: ก่อนสร้าง page/panel ใหม่ใต้ route group เดิม ต้อง `ls` โฟลเดอร์พี่น้อง + เปิดไฟล์ที่มี element ประเภทเดียวกัน (ตัวกรอง/แท็บ/หัวข้อ/empty state) **แล้วยกมาใช้ซ้ำ** — ถ้าเลือกไม่ยกมา ต้องเขียนเหตุผลใน commit ว่าทำไมหน้านี้ต้องต่าง
ตัวชี้วัด: ถ้า user ต้องเป็นคนบอกว่า "ทำไมไม่ทำเหมือนหน้า X" = ละเมิดข้อนี้แล้ว

### C2 — "ตัวเลข/สถานะเดียวกันที่โผล่มากกว่า 1 ที่" ต้องมาจากฟังก์ชันเดียว
ต่อยอดบทเรียน `shipping-address-status.ts` (2026-08-02): นิยามที่ผู้ใช้ **เห็นเป็นตัวเลข** (ตัวนับยังไม่ตอบ, badge, สถานะครบ/ไม่ครบ) ห้ามเขียน where clause ซ้ำในสองไฟล์ — ยกเป็นฟังก์ชัน/constant ตัวเดียวแล้ว import
เช็คง่าย ๆ: จอเดียวที่โชว์ตัวเลขเดียวกัน 2 จุด → ต้อง grep ให้เจอว่ามาจาก symbol เดียวกัน

### C3 — เพิ่ม OAuth scope = งาน 2 ขา ไม่ใช่ขาเดียว
เพิ่มใน `CONNECT_SCOPES` แล้ว **ยังไม่จบ** — ต้อง (ก) บอก user ให้กดเชื่อมเพจใหม่ (ข) ยืนยันด้วย `debug_token` ว่า token ใหม่มี scope ครบจริง ก่อนบอกว่าแก้แล้ว
ห้ามสรุปว่า "แก้แล้ว" จากการที่โค้ดมีคำนั้นอยู่

### C4 — หลักฐานดิบต้องเก็บก่อนผ่าน validator เสมอ
field ที่มีไว้ debug (`rawMessage`, `rawEvent`, log ของ webhook) ต้องบันทึก payload **ก่อน** เข้า Valibot/zod — ของที่ผ่าน schema แล้วคือ "ข้อมูลที่เรารู้จัก" ซึ่งตรงข้ามกับสิ่งที่ต้องการตอนสืบ

### C5 — ตอบทีละข้อเมื่องานต้องให้ user ไปกดดูเอง
งานที่ปิดด้วยการที่ user ไปกดดูบนจอ ให้ส่งทีละข้อ + รอผล ไม่รวบ 3-4 เรื่องในข้อความเดียว (user สั่งตรง ๆ 2026-08-03: "ไม่เข้าใจ ทีละข้อได้ไหม")

## 4. What went right

- **แก้บั๊กจากวิดีโอที่ไม่มี log เลยได้สำเร็จ** — ใช้การเทียบเฟรม + harness เทียบพฤติกรรม Chrome/WebKit จนชี้ได้ว่าเป็น scroll clamping ไม่ใช่เดาแล้วแปะ (systematic-debugging ทำงานจริง)
- **realtime ของแท็บความคิดเห็นเลือก Broadcast-from-Database แบบ signal-only** — trigger ส่งแค่ `postId`/`commentId` ไม่ฝังข้อความลูกค้า แล้วให้ client refetch ผ่าน GET ที่ auth (`20260803180000_page_comment_realtime_broadcast`) — โปรเจกต์นี้ไม่มี RLS การส่งทั้งแถวคือ data leak รอเกิด. เขียน grep-gate + rollback note ไว้ในไฟล์ migration ด้วย
- **migration 3 ตัวขึ้น prod ได้เรียบ** — ตรวจ `_prisma_migrations` ว่ามีแต่รายการที่ตั้งใจก่อน apply ทุกครั้ง (หลังเหตุการณ์ฐาน prod ถูกล้าง 31 ก.ค. เรื่องนี้สำคัญกว่าเดิมมาก)
- **ไม่ยอมเดาว่า "Meta คงไม่ให้"** — ยิง Graph ถามตรง ๆ ทีละคอมเมนต์จนพิสูจน์ได้ว่า `from` ไม่มีจริงในเส้นดึงย้อนหลัง แล้วเลือกทางแก้ที่ทำได้ (จับคู่ชื่อจาก id ของคนเดียวกันที่เคยมาทาง webhook) แทนที่จะปล่อย "ผู้ใช้ Facebook" ทิ้งไว้เฉย ๆ
- **เลิก hardcode `#0866FF` แล้วใช้ `ChannelBadgeOverlay` เดิม** (`65c69962`) — impeccable hook จับได้ และการแก้คือ "ไปหาของกลางที่มีอยู่" ไม่ใช่ "ปิด rule"
- **doc-first ทำครบก่อนโค้ด** — PRD+BRD ของ 00029 เขียนและให้ user เคาะ 4 คำถามค้างก่อนเริ่ม implement (`26d982d3`, `5dbe41d1`, `44b4df2b`) ตรงตาม Hard Rule 11
