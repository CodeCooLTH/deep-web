## 1. Problems

### P-1 🛑 สรุปผลการทดลองโดยคุมตัวแปรไม่ครบ แล้วรายงานหัวหน้าไปแล้ว

ผู้ใช้ทดสอบบน prod ได้ `(#100) Cannot tag messages with 'HUMAN_AGENT' without prior approval.`
ผมรายงานทันทีว่า **"ปิด open question ได้แล้ว — Standard Access ไม่พอ ต้องผ่าน App Review"**

**หลักฐานว่าผิด:** หัวหน้าถามกลับว่า *"มั่นใจแล้วใช่ไหม ลองเช็ค mcp + official document"* → ตรวจแล้วพบว่า
ฟีเจอร์ **"Human Agent" ไม่เคยถูกเพิ่มเข้า use case ของแอปเลยสักครั้ง** (privileges 17 รายการ ไม่มีตัวนี้)

สิ่งที่การทดลองพิสูจน์ได้จริงคือ **"ไม่เคยขอสิทธิ์ = ถูกปฏิเสธ"** ซึ่งเป็นคนละคำถามกับ
**"ขอแล้วรออนุมัติ = ถูกปฏิเสธหรือไม่"** — คำถามหลังคือ open question ตัวจริง และยังไม่ถูกตอบ

🛑 **น่าเจ็บเป็นพิเศษเพราะรีโปนี้มีบทเรียนคลาสนี้เขียนไว้แล้ว** — `docs/conventions/graph-access-depends-on-subject.md`
เกิดจากเหตุการณ์ที่ทีมสรุปว่า endpoint "ยิงไม่ได้" หลังทดสอบกับ subject ชนิดเดียว แล้วคำอธิบายผิดนั้น
ปิดทางสืบสวนไป 6 วัน — ผมอ่านไฟล์นั้นในรอบนี้เอง อ้างถึงมันในเอกสารเอง แล้วก็ยังทำซ้ำ

### P-2 ข้อสันนิษฐานใน Gate 0 baseline ถูกเขียนเป็นข้อเท็จจริงโดยไม่ตรวจ

A-04 เขียนว่า `META_HUMAN_AGENT_ENABLED` *"มีอยู่แล้วบน Vercel prod แต่ตั้งเป็นค่าว่าง/ไม่ตั้ง"*
ความจริงคือ **ไม่เคยถูกตั้งบน prod เลย** (ตรวจด้วย `vercel env ls production` ตอน Gate 2)

ผลลัพธ์ปลายทางเหมือนกัน (fail-closed) จึงไม่มีอะไรพัง — แต่ประโยคนั้นสื่อว่า "มีคนเคยพิจารณาค่านี้แล้ว"
ซึ่งไม่จริง และเป็นข้อสันนิษฐานที่ตรวจได้ด้วยคำสั่งเดียวตั้งแต่ต้น phase

### P-3 เส้นทาง Human Agent ไม่ทิ้งร่องรอยในเคสที่ต้องสืบมากที่สุด (D-08)

`sendOutboundMessage` ใส่ `messageTag` ลง `rawMessage` **เฉพาะตอนสำเร็จ** (`:3506`) ส่วนตอน
**Meta ปฏิเสธ** (`:3494`/`:3496`) บันทึกแค่ `ok:false/httpStatus/code/subcode/error` — ไม่มี `messageTag`
และ `sendOutboundImageGrid::createMany` ไม่มี field `rawMessage` เลย

⇒ เคส "พยายามติด tag แล้วถูกปฏิเสธ" คือเคสเดียวที่ไม่มีหลักฐานใน DB ทั้งที่เป็นเคสที่ต้องตอบ Meta ให้ได้
ถ้าถูกทักว่ามีการใช้สิทธิ์ผิดนโยบาย — **ไม่มี gate ไหนจับได้** เพราะโค้ดถูกทุกบรรทัด มันแค่ไม่บันทึก

### P-4 mitigation ที่เขียนใน PRD อ่อนกว่าที่ตัวเอกสารประเมินความเสี่ยงไว้

PRD §6.1 ให้ความเสี่ยง "ร้านใช้สิทธิ์ส่งโปรโมชัน" = **สูง (Meta อาจระงับแอปทั้งระบบ)** แต่ mitigation
ที่เขียนคือ *"ด่านโค้ดกันบอท + UI มีข้อความเตือน"* — ด่านกันบอทไม่เกี่ยวกับเรื่องนี้เลย (บอทกับโปรโมชัน
คนละปัญหา) เหลือของจริงคือ **ป้ายเตือน 1 บรรทัดที่บังคับอะไรไม่ได้**

หัวหน้าเป็นคนจับได้ด้วยคำถามเดียว: *"เราจะรู้ได้ไงว่าลูกค้าจะไม่พิมพ์โปรโมชัน"*

### P-5 named subagent ส่งงานกลับไม่ได้ เสียเวลา 3 รอบ

dispatch `safepay-product` แบบ **ตั้งชื่อ** (`name: product-human-agent`) → รัน background → แจ้ง idle
2 ครั้งโดยไม่มีผลงานส่งกลับมา ต้อง re-dispatch แบบไม่ตั้งชื่อจึงได้งาน
(มี memory `feedback_named_subagents_deliver_via_disk` บันทึกไว้แล้ว แต่ผมไม่ได้อ่านก่อน dispatch)

## 2. Root causes

| # | Root cause |
|---|---|
| P-1 | **ผลการทดลองที่ "ตรงกับสิ่งที่คาดไว้" ถูกตรวจน้อยกว่าผลที่ขัดความคาดหมาย** — error พูดถึงชื่อ tag ตรง ๆ ทำให้รู้สึกว่าคำตอบชัดจนไม่ต้องตรวจอะไรอีก · และผมมีแรงจูงใจให้ปิด open question เพราะมันเป็นรายการค้างในเอกสารที่ผมเขียนเอง |
| P-1 | **ไม่ได้ลิสต์ตัวแปรก่อนตีความผล** — การทดลองมี 2 ตัวแปร (ฟีเจอร์ถูกเพิ่มเข้าแอปหรือยัง / อนุมัติหรือยัง) ผมตรวจตัวที่สองอย่างเดียวแล้วสรุปทั้งคู่ |
| P-2 | Gate 0 baseline เขียนจาก "สิ่งที่น่าจะเป็น" ของสภาพแวดล้อมภายนอก (Vercel) ซึ่ง **ไม่ได้อยู่ในรีโป** จึงไม่มีอะไรบังคับให้ตรวจ ต่างจากข้อเท็จจริงเรื่องโค้ดที่ agent เปิดไฟล์อ่านได้ทันที |
| P-3 | `rawMessage` ถูกออกแบบมาเพื่อ **เก็บ payload ที่ได้รับ** (debugging ขาเข้า) แล้วถูกยืมมาใช้เก็บ "สิ่งที่เราส่งออกไป" ทีหลัง — พอเป็นการยืม จึงไม่มีใครไล่ว่าเส้นทางล้มเหลวต้องเก็บอะไรบ้าง |
| P-4 | ตอนเขียน PRD ช่อง mitigation ถูกเติมด้วยของที่ **มีอยู่แล้ว** แทนที่จะถามว่า "ของที่มีอยู่กันความเสี่ยงข้อนี้ได้จริงไหม" — ด่านกันบอทถูกหยิบมาใส่เพราะมันอยู่ใกล้มือ |
| P-5 | ไม่ได้เช็ค memory ก่อน dispatch — `feedback_named_subagents_deliver_via_disk` มีอยู่ตรงประเด็นเป๊ะ |

## 3. Conventions to adopt

### C-1 🛑 ก่อนสรุปผลการทดลองกับระบบภายนอก ต้องลิสต์ตัวแปรทั้งหมดก่อน แล้วยืนยันว่าคุมได้กี่ตัว

เกณฑ์: **"ถ้าผลออกมาแบบนี้ มีสาเหตุอื่นอีกกี่อย่างที่ให้ผลเหมือนกัน"** — ตอบไม่ได้ = ยังสรุปไม่ได้

- error ที่ระบุชื่อสิ่งที่เราส่งไป (tag/field/scope) **พิสูจน์แค่ว่า "เราส่งไปจริง"** ไม่ได้พิสูจน์ว่า
  "เงื่อนไขที่เราคิดว่าขาดคือเงื่อนไขที่ขาดจริง"
- ก่อนบอกว่า "X ไม่พอ" ต้องยืนยันว่า **X ถูกตั้งค่าครบแล้ว** ไม่ใช่ว่า X ไม่เคยมีอยู่เลย
- ขยายจาก `graph-access-depends-on-subject.md` (ทดสอบ ≥2 subject) มาเป็น: **ทดสอบ ≥2 สถานะของตัวแปรที่กำลังสรุปถึง**

### C-2 ข้อสันนิษฐานเกี่ยวกับสภาพแวดล้อมภายนอกใน scope baseline ต้องมี "คำสั่งที่ใช้ตรวจ" กำกับ

ถ้าเขียน A-xx ว่าด้วย env/deployment/สิทธิ์ภายนอก ต้องแนบคำสั่งที่พิสูจน์ได้ (`vercel env ls production`,
MCP action) และ **รันจริงตอน Gate 0** ไม่ใช่ตอน Gate 2 — ข้อสันนิษฐานที่ตรวจได้ด้วยคำสั่งเดียวไม่ควร
ค้างเป็นข้อสันนิษฐาน

### C-3 🛑 ฟีเจอร์ที่มีความเสี่ยงระดับ "ถูกระงับทั้งแอป" ต้องมี audit trail ก่อน ไม่ใช่หลัง

ถ้า PRD ประเมินความเสี่ยงข้อไหนว่า **กระทบผู้ใช้คนอื่นที่ไม่ได้ทำผิด** (multi-tenant blast radius)
ต้องตอบ 2 ข้อนี้ได้ก่อน ship:
1. **ถ้าเกิดขึ้นจริง เราจะรู้ได้ยังไงว่าใครทำ** — ถ้าตอบไม่ได้ = ยังไม่พร้อม
2. **เส้นทางล้มเหลวถูกบันทึกเท่าเส้นทางสำเร็จไหม** — เคสที่ต้องสืบมักเป็นเคสที่ล้ม ไม่ใช่เคสที่ผ่าน

### C-4 ช่อง mitigation ห้ามเติมด้วย "ของที่มีอยู่แล้ว" โดยไม่ถามว่ามันกันข้อนี้ได้จริงไหม

เขียน mitigation แล้วต้องอ่านย้อนว่า **"ถ้าคนตั้งใจทำสิ่งนี้ ของที่เขียนไว้หยุดเขาได้ตรงไหน"** —
ป้ายเตือน/คำอธิบาย/เอกสาร = **ไม่ใช่ mitigation** ให้เขียนตรง ๆ ว่า "ยังไม่มี mitigation" ดีกว่าเขียน
ของที่ฟังดูมีแต่บังคับอะไรไม่ได้ (ตรงกับ `known-limitation-vs-unfinished.md`)

### C-5 dispatch subagent ที่ต้องการ "ผลงานกลับมา" ห้ามตั้งชื่อ

read-only agent ที่ผลงานคือรายงาน (product/planner/ux/reviewer/security) → **spawn โดยไม่ตั้ง `name`**
ตั้งชื่อ = รัน background แล้วผลไม่ถูกส่งกลับ (มีใน `feedback_named_subagents_deliver_via_disk` อยู่แล้ว
— รอบนี้ยืนยันซ้ำว่าเป็นจริงและเสียเวลา 3 รอบ)

## 4. What went right

1. **ux gate ประหยัดงานจริง ไม่ใช่พิธีกรรม** — TFR-HA-05 ที่วางแผนว่าจะแก้ UI กลายเป็น "ไม่ต้องแตะ JSX
   เลยสักบรรทัด" เพราะ copy เดิมเขียนระดับ "เธรดนี้ทำอะไรได้" มาตั้งแต่ต้น · รอบ error rule ux ก็ตรวจ
   โค้ดจริงแล้วยืนยันว่าไม่ต้องแก้ component เพราะ `retryable` เป็นคุณสมบัติของ *เหตุผล* ไม่ใช่ของบับเบิล
2. **reviewer ตอบคำถามที่ผมค้างใจแบบปิดประเด็น** — ผมสงสัยว่า branch `postback` ตัดเส้นทางเดิมไหม
   reviewer พิสูจน์ว่าก่อนหน้านี้ schema ไม่มี field `postback` เลย Valibot จึงทิ้งคีย์ทุกครั้ง ⇒
   เป็น additive ล้วน ไม่ใช่ regression
3. **เทส `[blocker]` พิสูจน์ด้วย mutation จริงทุกตัว** และ reviewer รัน mutation ซ้ำเองอีกรอบ ไม่เชื่อ
   รายงาน dev — คืนโค้ดสะอาดทั้งสองรอบ (ผมตรวจ `diff --stat` เทียบก่อน/หลังเองด้วย)
4. **HR17 ทำงานจริง 2 รอบ** — rebase ทั้งสองครั้งเจอว่า `origin/main` แตะไฟล์เป้าหมายเดียวกัน
   (`channel-chat.service.ts`, `page.tsx`, `ChatThread.tsx` จากงาน 00025/00024/00041) เลขบรรทัดใน
   เอกสารล้าสมัยทั้งหมด — ถ้า dispatch ด้วยเลขเก่าจะพาไปแก้ผิดที่
5. **หัวหน้าจับ 2 อย่างที่ระบบทั้งชุดจับไม่ได้** — P-1 (สรุปเร็วไป) และ P-4 (mitigation อ่อน) ทั้งคู่
   ผ่าน tsc/build/เทส/reviewer/security มาหมด เพราะไม่ใช่ปัญหาเชิงรูปแบบ

## 6. หมายเหตุปิดท้าย

งานรอบนี้ **ฝั่งโค้ดเสร็จสมบูรณ์และพิสูจน์แล้วว่าถูกทั้งเส้น** — สิ่งที่เหลือทั้งหมดอยู่นอกมือเรา
(App Review ของ Meta) หรือเป็นหนี้ที่รู้ตัวและบันทึกไว้แล้ว

บทเรียนที่ควรจำที่สุดจาก phase นี้ไม่ใช่เรื่องเทคนิค แต่คือ **error message ที่ตรงกับสมมติฐานของเรา
เป็นสิ่งที่อันตรายที่สุดที่จะเชื่อ** เพราะมันหยุดการตรวจสอบ — และคำถามเดียวของหัวหน้า
(*"มั่นใจแล้วใช่ไหม"*) มีค่ามากกว่า gate อัตโนมัติทั้งหมดที่เรามีรวมกันในเคสนี้
