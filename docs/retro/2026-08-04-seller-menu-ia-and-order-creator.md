## Problems

### P1 — เกือบ push ทั้งที่ build ล้ม เพราะ grep ผลลัพธ์แทนที่จะดู exit code

รัน `npm run build 2>&1 | grep -iE "compiled successfully|failed|error"` แล้วเจอ
`✓ Compiled successfully` เลยเข้าใจว่าผ่าน — ที่จริง exit code เป็น `1` เพราะผมยิง build ซ้อนกันเอง
จน `.next/lock` ชน (`⨯ Unable to acquire lock at .next/lock`) ข้อความ "Compiled successfully"
ที่ grep เจอเป็นของ **รอบก่อนหน้า** ที่ยังเขียน log ค้างอยู่

จับได้ตอนเปลี่ยนมาวัด `echo "BUILD_EXIT=$?"` ตรง ๆ — ซึ่งเป็นบทเรียนที่ **มีบันทึกไว้แล้ว**
ที่ `feedback_verify_then_push_separately` ("grep ผล build ไม่ match ≠ ผ่าน") แต่ยังทำซ้ำ

### P2 — เขียนชื่อตารางที่ไม่มีอยู่จริงลงคอมเมนต์กฎ แล้ว commit ไป 4 ที่

คอมเมนต์กฎ "ห้ามเปลี่ยน slug" ใน `src/lib/seller-menu.ts`, เทส, และ spec อ้างตาราง
`ShopShortcut` — **ไม่มีใน schema เลย** ของจริงคือ `SellerShortcutPreference.slugs`

เนื้อกฎถูก (slug ถูกเก็บใน DB จริง เปลี่ยนแล้วเมนูลัดหลุดจริง) แต่ชี้ไปตารางที่ไม่มีอยู่
คนที่มาอ่านทีหลังจะไปหาแล้วไม่เจอ

เจอโดยบังเอิญตอนไล่เช็ค migration บน prod — query หาตารางชื่อนั้นไม่เจอ ตอนแรกนึกว่า prod drift

### P3 — `pkill -f "next dev"` ฆ่า dev server ของทุกโปรเจกต์บนเครื่อง

ตอนจะล้าง `.next` ที่ค้าง ใช้ `pkill -f "next dev"` ซึ่งแมตช์ command line ทั้งเครื่อง
หลังคำสั่งนั้น `ps aux | grep "[n]ext dev"` เหลือ 0 process — เครื่องนี้รันหลายโปรเจกต์
พร้อมกัน (SafePay = 4000, อื่น ๆ 3000–3002)

ซ้ำร้าย ใส่ `pkill` ไว้ใน compound command เดียวกับที่ start server ใหม่ → คำสั่ง start
โดน kill ตัวเองด้วย เสียเวลาไล่หาอีกรอบว่าทำไม server ไม่ขึ้น

### P4 — เทสที่แดงมานานโดยไม่มีใครเห็น

`getSellerPageTitle.test.ts` assert ป้าย `/verification` = "การยืนยันตัวตน" ซึ่งเลิกใช้ไปแล้ว
(ก่อนงานนี้ป้ายจริงคือ "ยืนยันตน") และ `/customers` = "ผู้ซื้อ" ทั้งที่จริงเป็น "ลูกค้า"

**แดงมาก่อนงานนี้** แต่จมอยู่ในกอง 100 เคสที่แดงอยู่แล้ว (e2e Playwright ที่ vitest หยิบมารัน
+ integration ที่ต้องต่อ DB) จนไม่มีใครสังเกต — สัญญาณเตือนที่เสียงดังตลอดเวลา = สัญญาณที่ไม่มีใครฟัง

### P5 — เขียนข้อความ error ที่แนะนำวิธีแก้ซึ่งใช้ไม่ได้จริง

รอบแรกเขียนใน dropdown ว่า `"โหลดรายการบัญชีไม่สำเร็จ ลองปิดแล้วเปิดเมนูนี้ใหม่"` —
**เป็นคำแนะนำที่ไม่จริง** เพราะ Preline toggle dropdown ด้วย CSS ไม่ได้ unmount component
`useEffect([])` จึงไม่ยิงซ้ำตอนเปิดใหม่ ทางเดียวที่ fetch ใหม่คือโหลดหน้าใหม่

จับได้ตอนอ่านทวนก่อน commit เปลี่ยนเป็น "ลองโหลดหน้านี้ใหม่อีกครั้ง"

### P6 — ระบบไม่เคยเก็บว่าใครสร้างออเดอร์ แต่ UI พูดเหมือนรู้

`ShippingActivity.tsx` ฮาร์ดโค้ด `STEP_ACTOR.PLACED = 'ระบบ'` และคำอธิบายเขียนว่า
"ผู้ขายสร้างคำสั่งซื้อแล้ว" — **ขัดกันเองในแถวเดียวกัน** (บนบอกผู้ขาย ล่างบอกระบบ)

คำว่า "ผู้ขาย" ก็ผิดตั้งแต่มี feature 00012 (พนักงานที่ถูกเชิญเปิดบิลแทนได้)
`POST /api/orders` รู้ `session.user.id` อยู่แล้วตลอดมา แค่โยนทิ้ง

## Root causes

| # | ทำไมถึงเกิด |
|---|---|
| P1 | วัดผลด้วย "ข้อความที่หาเจอ" แทน "สัญญาณที่เครื่องมือคืนมา" — grep บน log ที่มีหลายรอบปนกันไม่มีทางแยกได้ว่าบรรทัดไหนของรอบไหน; และยิง build ซ้อนโดยไม่เช็คว่ามีตัวเก่ารันอยู่ |
| P2 | เขียนคอมเมนต์อธิบายกฎ "จากความจำ" ว่าฟีเจอร์เมนูลัดเก็บอะไรไว้ที่ไหน แทนที่จะเปิด `schema.prisma` ดูชื่อจริง — ปัญหาเดียวกับ `feedback_write_docs_from_code_not_memory` แต่เกิดกับคอมเมนต์ในโค้ดแทนที่จะเป็นเอกสาร |
| P3 | เลือก pattern ที่ "น่าจะตรงพอ" (`-f "next dev"`) โดยไม่คิดว่าเครื่อง user มีอะไรรันอยู่บ้าง ทั้งที่มี memory `project_dev_port_4000` บอกไว้ชัดว่ามีหลายโปรเจกต์ |
| P4 | ไม่เคยมีใครถือว่า "จำนวนเทสแดง" เป็นตัวเลขที่ต้องคุม — พอ baseline แดง 100 เคส เทสที่แดงเพิ่มทีละอันก็มองไม่เห็น |
| P5 | เขียน copy ของ error state จากสมมติฐานว่า component จะ re-mount โดยไม่ได้ตรวจว่า Preline ทำงานยังไงจริง ๆ |

## Conventions to adopt

### C1 — Hard Rule 15 (ใหม่): deploy รัน migrate ให้อยู่แล้ว ต้องแจ้ง user เสมอ

`vercel.json` → `"buildCommand": "prisma migrate deploy && prisma generate && next build"`
มีมาตลอดแต่ไม่เคยถูกเขียนไว้ที่ไหน — ทุกคนจึงเข้าใจว่าต้องรัน migrate ชี้ prod เอง
ซึ่งเป็นความเสี่ยงล้วน ๆ ที่ไม่ได้แลกอะไรกลับมา (ฐาน prod เคยถูกล้างทั้งฐานมาแล้วครั้งหนึ่ง)

รายละเอียดเต็ม: `docs/conventions/migrate-on-deploy.md`

### C2 — วัด build/test ด้วย exit code เท่านั้น ห้าม grep ตัดสิน

```bash
# ถูก
npm run build > /tmp/build.log 2>&1; echo "BUILD_EXIT=$?"

# ผิด — log อาจมีหลายรอบปนกัน "Compiled successfully" ของรอบก่อนก็ match ได้
npm run build 2>&1 | grep -i "compiled successfully"
```

และก่อนยิง build ต้องเช็คว่าไม่มีตัวเก่ารันอยู่ (`pgrep -f "next build"`) — `.next/lock`
ชนแล้ว exit 1 โดยที่ข้อความ error ไม่มีคำว่า error

### C3 — kill process ตาม PID ที่ฟัง port ห้าม pkill ตามชื่อคำสั่ง

```bash
# ถูก — แตะเฉพาะโปรเจกต์นี้
lsof -nP -iTCP:4000 -sTCP:LISTEN -t | xargs -r kill

# ผิด — ฆ่า dev server ของทุกโปรเจกต์บนเครื่อง user
pkill -f "next dev"
```

และห้ามใส่ kill ไว้ใน compound command เดียวกับที่ start ตัวใหม่

### C4 — ชื่อ table/column/field ในคอมเมนต์ต้องเปิด schema ดู ไม่ใช่เขียนจากความจำ

คอมเมนต์ที่อ้างชื่อ entity ในฐานข้อมูลมีค่าเท่ากับเอกสาร — ชื่อผิด = พาคนไปหาของที่ไม่มีอยู่
ก่อนเขียนชื่อตาราง/คอลัมน์ลงคอมเมนต์ `grep "model X" prisma/schema.prisma` ให้เห็นกับตาก่อน

### C5 — copy ของ error state ต้องแนะนำวิธีแก้ที่ใช้ได้จริงเท่านั้น

ก่อนเขียน "ลองทำ X ดู" ต้องรู้ว่า X ทำให้เกิดอะไรขึ้นจริงในโค้ด — dropdown ที่ toggle ด้วย CSS
ไม่ unmount, `useEffect([])` ไม่ยิงซ้ำ, modal ที่ portal ไว้ก็เหมือนกัน
ข้อความที่แนะนำทางที่ไม่ได้ผลแย่กว่าไม่แนะนำอะไรเลย เพราะผู้ใช้จะลองแล้วสรุปว่าระบบพังหนักกว่าเดิม

### C6 — เจอ UI ที่เขียนคำตายตัวแทนข้อมูลจริง ให้ถามว่า "ข้อมูลนั้นอยู่ในมือแล้วหรือยัง"

`STEP_ACTOR.PLACED = 'ระบบ'` อยู่มาเป็นเดือนพร้อมคอมเมนต์อธิบายว่าทำไมถึงเป็นคำตายตัว —
แต่ `session.user.id` อยู่ใน route ที่สร้างออเดอร์มาตลอด ห่างกันแค่การส่ง parameter ตัวเดียว

placeholder ที่มีคอมเมนต์อธิบายไว้ดี ๆ อ่านเหมือนการตัดสินใจที่จบแล้ว ทั้งที่จริงเป็นหนี้ที่รอคนมาปิด

## What went right

1. **ux gate จับของที่ผมมองไม่เห็น 2 รอบ** — รอบเมนู: `AppMenu` render `<Link>` อย่างเดียว
   ทำให้รายการ "โปรไฟล์ ↗" ที่ผมออกแบบไว้ implement ไม่ได้เลยถ้าไม่แก้ก่อน; และบนมือถือ
   sidebar+topbar ถูกซ่อนทั้งคู่ ฟีเจอร์จะใช้ไม่ได้กับคนส่วนใหญ่ รอบออเดอร์: ชี้ว่าห้ามใส่
   avatar placeholder ให้ step อื่นเพื่อความสม่ำเสมอทางสายตา เพราะเป็นการแต่งข้อมูลที่ไม่มีจริง

2. **ตรึงกฎที่พังเงียบไว้ด้วยเทสทันที** — เทสใหม่ 13 เคสใน `seller-menu.test.ts` ตรึง slug set
   ทั้งชุดไว้ ถ้าใครเผลอ rename slug ตอน refactor เทสจะแดงทันที ไม่ต้องรอผู้ใช้มาบอกว่า
   เมนูลัดหาย (ซึ่งเป็นอาการที่ไม่มี error log)

3. **ไม่ backfill ข้อมูลที่เดาไม่ได้** — ออเดอร์เก่า 14 ใบบน prod ไม่มีทางรู้ว่าใครสร้าง
   ตัดสินใจปล่อย NULL แล้วให้หน้าจอแสดง "ระบบ" ต่อไป แทนที่จะยัดเจ้าของร้านลงไปให้ดูสวย —
   ร้านที่มีพนักงานหลายคนจะกลายเป็นบันทึกเท็จทันที

4. **ตรวจ prod ด้วย object จริง ไม่ใช่ตารางประวัติ** — `_prisma_migrations` บอกว่า apply ครบ 100
   แต่ฐานนี้เคยถูกล้างแล้วสร้างประวัติกลับมา จึงไล่เช็คว่า table/column/constraint มีจริง
   (รวม unmanaged CHECK `Shop_vertical_check`) ก่อนสรุป

5. **browser QA ครบทุกสาขาก่อน push** — เมนู 3 vertical + PERSONAL/BUSINESS + dropdown 3 กรณี
   + มือถือ; ออเดอร์ทั้งกรณีมีคนสร้างและกรณี null — ทั้งหมดกดจริงผ่าน CDP ไม่ใช่เดาจากโค้ด
