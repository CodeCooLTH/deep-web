## อาการที่ user รายงาน

> กดปุ่มสร้างคำสั่งซื้อในหน้าแชท → กด "กระจายที่อยู่" → ระบบเหมือนจะเลือกที่อยู่ได้ถูกต้อง
> แต่พอกดบันทึก จะแจ้งว่ายังไม่ได้เลือกที่อยู่ ทั้ง ๆ ที่ใน UI ขึ้นเลือกที่อยู่สำเร็จไปแล้ว

## ต้นเหตุ — 2 ชั้น ที่ให้อาการเดียวกัน

### ชั้นที่ 1: parser แกะไม่ครบในรูปแบบที่ร้านเจอบ่อยที่สุด

รันของจริงกับข้อความ 4 แบบก่อนแก้ (หลักฐานที่ทำให้เห็นว่าเป็นบั๊กจริง ไม่ใช่การเดา):

| ข้อความที่วาง | ผลลัพธ์เดิม |
|---|---|
| `… แขวงคลองตัน เขตคลองเตย กรุงเทพ 10110` | **จังหวัดว่าง** — หาจังหวัดจาก marker `จ.` อย่างเดียว ที่อยู่ กทม. ไม่มี |
| `สมชาย ใจดี 99/9 ม.5 ต.บางรัก … โทร 08…` (บรรทัดเดียว) | **ที่อยู่ + ชื่อ ว่างทั้งคู่** — บรรทัดที่มีคำว่า "โทร" ถูกข้ามทั้งบรรทัด |
| เบอร์อยู่บรรทัดล่างสุดลอย ๆ | **ที่อยู่ = เบอร์โทร** (บรรทัดเบอร์เข้าเกณฑ์ `^\d`) |

### ชั้นที่ 2: UI นิยาม "เลือกที่อยู่แล้ว" ไม่ตรงกับกฎที่ service ใช้ปฏิเสธ

- ปุ่มที่อยู่ถือว่า "เลือกแล้ว" เมื่อมี `subdistrict || province` **อย่างใดอย่างหนึ่ง**
- `createOrder` (SSOT) บังคับ `line1 + province + postcode` ครบ
- ผล: บรรทัดเด่นบนปุ่ม (`ต.X · อ.Y`) เต็ม → ดูเหมือนครบ; บรรทัดล่างที่ว่างไม่มีอะไรบอกว่านั่นคือปัญหา
- ซ้ำร้าย `setError('shippingAddress.line1'|'.province'|'.postcode')` ถูกเรียกตอน submit **มาตลอด**
  แต่ **ไม่มี component ไหน render** ทั้ง quick form และ POS → เหลือแต่ toast ลอย ๆ ที่ไม่ชี้จุด
- กฎ "ครบพอบันทึกไหม" ยังถูกเขียนซ้ำ 3 ที่ แล้วนิยามไม่ตรงกันทั้ง 3

## สิ่งที่แก้

**parser** — เพิ่มรายชื่อ 77 จังหวัด สะกดตามชุดข้อมูล iShip (`public/data/iship-address.json`)
ไว้จับกรณีไม่มี marker + normalize `กรุงเทพมหานคร`/`กทม.` → `กรุงเทพ`; ตัดเบอร์ออกจากบรรทัด
แทนการข้ามทั้งบรรทัด + แยกชื่อที่นำหน้าบ้านเลขที่; บรรทัดที่มีแต่เบอร์ไม่ถูกหยิบมาเป็นที่อยู่อีก
+ ทางสำรองสำหรับที่อยู่แบบคอนโด/ห้อง

**UI** — ยกกฎออกมาไว้ที่ `src/lib/shipping-address-status.ts` ที่เดียว แล้วให้ทุก surface เรียกใช้;
ปุ่มมี 3 สถานะจริง (ยังไม่เลือก เทา / ขาดช่องบังคับ danger + บอกว่าขาดอะไร + วิธีแก้ / ครบ primary);
render error ของ `line1`/`province`/`postcode` ครบทั้ง 2 surface; ตำบล-อำเภอ ไม่บล็อกการบันทึก
ตาม SSOT แต่เตือนเหลืองว่าต้องเติมก่อนเปิดพัสดุ iShip

**Verified-Means-Green ที่ละเมิดจริง** — `AddressSearchPanel` เดิมขึ้นเช็กถูก **สีเขียว** กับที่อยู่
ที่ยังไม่ครบ พร้อมคอมเมนต์เขียนกำกับว่า `(Verified-Means-Green)` ทั้งที่กำลังละเมิดกฎนั้นเอง
→ เขียวสงวนไว้กับ verified/สำเร็จของระบบ เปลี่ยนเป็น primary เมื่อครบ / danger เมื่อขาด

## บทเรียน

1. **สถานะ "ครบแล้ว" บน UI ต้อง derive จากกฎเดียวกับ validation ฝั่ง service** — ถ้าเขียนคนละที่
   คนละนิยาม UI จะโกหกโดยไม่มีอะไรฟ้อง จนกว่าผู้ใช้จะกดบันทึกแล้วงง
   (บันทึกเป็น memory `feedback_ui_complete_state_must_mirror_validation`)
2. **`setError` ที่ไม่มีใคร render = error เงียบ** — เจอ `setError` ที่ไหน ให้ grep ว่ามีจุดแสดง
   `errors.<path>` จริงหรือเปล่า อยู่เสมอ
3. **heuristic parser ต้องมีหลักฐานก่อนแก้** — การ dump ผลลัพธ์จริงของข้อความ 4 แบบใช้เวลาไม่กี่นาที
   แต่เปลี่ยน "เดาว่าน่าจะพังตรงไหน" เป็น "เห็นว่าพัง 3 แบบ" ได้ทันที ทำก่อนเขียนโค้ดแก้เสมอ
4. **คอมเมนต์ที่อ้างกฎ ไม่ได้แปลว่าโค้ดทำตามกฎ** — `(Verified-Means-Green)` เขียนกำกับอยู่บนโค้ด
   ที่ละเมิดกฎนั้นพอดี; อ่านสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่คอมเมนต์อ้าง
