# Public Order Count — ออเดอร์ที่นับได้บนหน้าร้านสาธารณะ (SSOT)

> เอกสารนี้คือแหล่งความจริงเดียวของคำถาม **"ออเดอร์ใบไหนนับเป็นผลงานของร้านบนหน้าสาธารณะได้"**
> อัปเดต: 2026-08-10 (user เคาะเกณฑ์ "กลาง")
> โค้ด SSOT: `src/lib/public-order-count.ts` — ห้ามเขียนเงื่อนไขซ้ำที่อื่น

---

## ปัญหาที่กฎนี้แก้

หน้าร้านสาธารณะนับ `status = CONFIRMED` อย่างเดียวมาตลอด เหตุผลเดิมถูกต้องและยังใช้อยู่:

> `PENDING` เป็นสิ่งที่**ร้านสร้างเองได้ไม่จำกัด** — มิจฉาชีพเปิดร้านแล้วสร้างออเดอร์ทิ้งไว้ 50 รายการ
> ก็ได้ "50 จำนวนลูกค้า" ฟรี ๆ ซึ่งขัดพันธกิจของทั้งแพลตฟอร์ม (`shop.service.ts`)

แต่เกณฑ์นี้ลงโทษร้านที่ขายจริงผ่านแชท เพราะ **ผู้ซื้อแทบไม่กลับมากดยืนยันรับของ** — เคสจริงที่บันทึกไว้
ใน `product.service.ts:463` คือร้านธนภัทร์: **SHIPPED 23 ใบ · CONFIRMED 0 ใบ** ทั้งที่ขายจริงต่อเนื่อง

ผลคือหน้าที่ควรพิสูจน์ว่าร้านนี้ขายจริง กลับแสดงตัวเลขต่ำกว่าความจริงมาก

## หลักที่ใช้ตัดสิน

**นับได้เมื่อมีหลักฐานที่ร้านสร้างขึ้นเองไม่ได้** — ไม่ใช่ "ออเดอร์เดินไปไกลแค่ไหน"

| หลักฐาน | ใครเป็นคนสร้าง | ปลอมได้ไหม |
|---|---|---|
| `Order.status = PENDING` | ร้าน | ✅ ปลอมได้ |
| `Order.status = SHIPPED` | **ร้าน** (`order.service.ts:883`) | ✅ ปลอมได้ |
| `OrderShipment.status = CREATED` | ร้าน (กดสร้างใบปะหน้า) | ✅ ปลอมได้ (เสียค่าเครดิตแต่ทำได้) |
| `Order.status = CONFIRMED` | **ผู้ซื้อ** (ปลดล็อกด้วยเบอร์ตัวเอง) | ❌ |
| `OrderShipment.carrierStatus` ที่ขยับจริง | **ขนส่ง** | ❌ |

🛑 `SHIPPED` กับ `CREATED` **ห้ามใช้เป็นเกณฑ์** แม้จะดูเหมือน "ของออกไปแล้ว" — ทั้งคู่เป็นการกระทำ
ของร้าน ไม่ใช่หลักฐานจากบุคคลที่สาม

## BR-POC-01 — เกณฑ์นับ

ออเดอร์ใบหนึ่ง **นับได้** เมื่อ `status ≠ CANCELLED` **และ** เข้าเงื่อนไขข้อใดข้อหนึ่ง:

1. `status = CONFIRMED` — ผู้ซื้อกดยืนยันรับของแล้ว (ครอบออเดอร์ที่กรอกเอง/ไม่ผ่านขนส่งในระบบ)
2. มี `OrderShipment` ที่ `status = CREATED` และ `isDryRun = false` และ **`carrierStatus` อยู่ในชุดที่
   ยืนยันว่าขนส่งขยับพัสดุจริงแล้ว**

## BR-POC-02 — ชุด carrierStatus ที่นับได้ (เกณฑ์ "กลาง")

**นับ:** `with_branch` · `in_transit` · `progress` · ทุกสถานะที่ `terminal = true` (ส่งถึง/เก็บเงินสำเร็จ/ตีกลับถึงร้าน)

🛑 **ไม่นับ `picked_up`** ทั้งที่อยู่ในกลุ่ม in-transit ของระบบ — ป้ายไทยของมันคือ **"พัสดุเข้าระบบ"**
และมีบันทึกว่าขนส่งบางเจ้า (SPX) ยิงสถานะนี้ **ตั้งแต่ตอนสร้างพัสดุ** ไม่ใช่ตอนรับของจริง
(`docs/conventions/…` — trace feed ≠ current state) ถ้านับ `picked_up` ร้านที่ใช้เจ้านั้นจะได้แต้ม
ฟรีทันทีที่กดสร้าง = กลับไปสู่ช่องโหว่เดิมที่กฎนี้ตั้งใจปิด

**ตีกลับก็ยังนับ** — `return_success` แปลว่าการซื้อขายเกิดขึ้นจริงและของเดินทางจริง แค่จบไม่สวย
ซึ่งเป็นคนละคำถามกับ "สำเร็จไหม" (ดู BR-POC-04)

## BR-POC-03 — ตัวเลขที่ใช้เกณฑ์นี้

ใช้ **นิยามเดียวกันทั้งหมด** ห้ามให้ตัวใดตัวหนึ่งนับคนละแบบ (Hard Rule 16):

- **ออเดอร์** (`completedOrders`)
- **จำนวนลูกค้า** (`customerCount`) — นับ `customerId` ไม่ซ้ำจากชุดเดียวกัน
- **ลูกค้าซื้อซ้ำ** (`repeatCustomerCount`) — ลูกค้าที่มี ≥2 ใบในชุดเดียวกัน
- **"ขายแล้ว N" บนการ์ดสินค้า** (`getConfirmedOrderCountByProduct`)

## BR-POC-04 — อัตราความสำเร็จ **ไม่** ใช้เกณฑ์นี้

`completionRate` ยังคงใช้ `CONFIRMED` เป็นตัวตั้งตามเดิม (feature 00039 BR-OSM-*)

เหตุผล: คำว่า "สำเร็จ" หมายถึง **ผู้ซื้อได้ของและพอใจพอจะกดยืนยัน** — พัสดุที่ยังเดินทางอยู่ยัง
ไม่ใช่ความสำเร็จ มันอาจถูกตีกลับได้ ถ้านับ in-transit เป็นสำเร็จ ตัวเลขจะพองและกฎ BR-OSM ที่
ทั้ง feature 00039 สร้างขึ้นมาเพื่อความซื่อสัตย์จะไร้ความหมาย

🛑 **ผลข้างเคียงที่ต้องยอมรับและต้องอธิบายบนหน้าจอ:** "ออเดอร์" กับ "อัตราสำเร็จ" จะใช้ตัวหาร
คนละชุดโดยตั้งใจ — ผู้ซื้อที่เอา 71 ไปหารกับ 93% แล้วไม่ลงตัวต้องมีคำอธิบายให้อ่าน ไม่ใช่ปล่อยให้
สงสัยเงียบ ๆ (นี่คือเหตุผลที่ Hard Rule 16 บังคับว่า ถ้านิยามต่างกันต้อง **ตั้งชื่อต่างกันชัด** และ
**บอกผู้ใช้บนหน้าจอ** ไม่ใช่แค่เขียนคอมเมนต์)

## สิ่งที่กฎนี้ไม่ได้เปลี่ยน

- **`Order.status` ไม่ถูกแตะ** — `CONFIRMED` ยังต้องมาจากผู้ซื้อกดเท่านั้น (BR-ISHIP-41)
  เพราะมันไปคิด Trust Score + สิทธิ์รีวิว การให้ขนส่งดัน status ได้ = ปั่นคะแนนด้วยพัสดุปลอม
  กฎฉบับนี้เปลี่ยนแค่ **วิธีนับตอนแสดงผล** ไม่ได้เปลี่ยนสถานะของออเดอร์
- **Trust Score** ยังคำนวณจากสูตรเดิม ไม่ได้ผูกกับกฎนี้
- ร้านประเภทอื่น (`SERVICE_QUEUE` / `LODGING`) ไม่มีพัสดุ จึงเหลือเงื่อนไข `CONFIRMED` อย่างเดียว
  โดยอัตโนมัติ ไม่ต้องเขียน branch แยก
